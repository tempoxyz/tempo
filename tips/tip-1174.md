# TIP-1174: Lane-Split State Access Repricing

## Abstract

This TIP replaces the EIP-2929 access costs with a per-lane schedule. Accesses
the protocol knows in advance (declared, prewarmed, or inferred) pay a
**declared price**: 2,000 for a read and 4,900 for a write, then 100 per access.
Payment lane transactions carry no list and are priced as if they had a
complete one, so their already optimized costs stay where they are. Undeclared
first accesses in the general lane cost about twice the declared price (4,000
to read, 10,000 to write). Legacy EIP-2930 access lists become read
declarations, and clients load their read sets before execution.

This is component 1 of the [TIP-1139](./tip-1139.md) state access program.

## Motivation

State lookups that execution discovers one at a time are the expensive part of
contract execution, and they get worse as state grows. Payment lane
transactions are different: they only call allow-listed native precompiles whose
state the client derives itself and preloads, and they are already heavily
optimized. This TIP therefore splits pricing by lane rather than raising every
cold access:

- **Payment lane:** priced as if it carried a complete list (section 5), which
  keeps today's TIP-20 costs within ±2,000 gas per transfer.
- **General lane:** first accesses that were not declared cost about twice the
  declared price, which sets the incentive to declare before state grows to the
  point where misses are expensive.
- **Declared accesses:** priced at the declared price in every lane. Before
  [TIP-1176](./tip-1176.md) the only way to declare is a legacy EIP-2930 list,
  which this TIP turns into a real read set that clients prefetch.

Read and write warmth are tracked separately so that later TIPs can price
write declarations ([TIP-1176](./tip-1176.md)) without changing this model.

The prices are transitional. Tempo state is currently small enough to be served
mostly from memory, so they are not derived from worst-case database latency;
the aim is to set the incentive structure early.

### Alternatives considered

- **Raise all cold costs uniformly:** penalizes payments, whose accesses are
  already preloaded, and gives contracts no way to lower their cost.
- **Dynamic access lists for payment transactions** (have senders or the
  protocol attach an explicit list): adds bytes and signing complexity for
  accesses the client can already derive; inference gives the same price.
- **Reject or revert on undeclared accesses:** makes inclusion depend on
  simulation accuracy; undeclared prices bound the cost of a miss instead.

## Assumptions and amended TIPs

- [TIP-1060](./tip-1060.md) (storage credits) is active before this TIP.
- [TIP-1016](./tip-1016.md) (execution/state gas separation) is active in the
  same or an earlier hardfork and applied first; this TIP is written against
  TIP-1016 accounting.
- Gas is computed from signed declarations and consensus state only, never from
  local cache residency or prefetch success.
- Lane limits are unchanged by this TIP; [TIP-1177](./tip-1177.md) changes them.
- At activation this TIP amends TIP-1060: its 5,000-gas SSTORE execution
  residual (`SSTORE_SET_COST`), the net-metering SSTORE refunds it retains, and
  the gas for reading and writing credit counters during SSTORE are replaced by
  sections 8 and 9. All other TIP-1060 rules remain in force.

## Terms

- **Lane:** a separate execution-gas budget within a block (TIP-1010).
- **Payment transaction:** a transaction that the active TIP-1045 classifier
  admits to the payment lane.
- **Native precompile:** protocol code at a fixed address implemented in the
  client, including every TIP-20 token, the TIP-403 policy registry, the fee
  manager, and the storage-credits precompile.
- **Envelope processing:** signature and key checks, authorization-list
  processing, nonce validation and update, fee-token selection, fee reservation,
  refund and distribution, and storage-credit settlement.
- **Warm and cold:** as in EIP-2929, a resource is warm once the transaction has
  paid for or been granted access to it.
- **Declared, inferred, and undeclared:** a declared resource is in a signed
  access list; an inferred one is derived by the protocol (payment lane calls
  and storage-credit counters); anything else is undeclared.

# Specification

## 1. Resources and warmth

Pricing tracks five kinds of warmth per transaction: account read and account
write per address, storage read and storage write per slot, and code per
address. A warm access costs **100 gas** in every lane. A resource becomes warm
by declaration, by prewarming or envelope processing (section 4), by paying a
first-access price, or, for code, by being deployed (section 7).

A first write marks read and write warmth, but a prior read does not make a
write warm. Warmth is consensus bookkeeping, never physical cache state;
prefetching never makes anything warm, and touching a resource never upgrades
its declared permission.

Declared, prewarmed, envelope, and inferred warmth last for the whole
transaction. All other warmth is journaled with call frames like the EIP-2929
access set: kept on success, discarded on revert or exceptional halt. Each price
is deducted before the lookup it pays for.

## 2. Prices

| Access | Declared / inferred | General lane, undeclared |
| --- | ---: | ---: |
| Account or storage read | 2,000 | 4,000 |
| Account or storage write | 4,900 | 10,000 |
| Code component | 3,000 | 6,000 |
| Bytecode load (account read + code) | 5,000 | 10,000 |
| Any warm access | 100 | 100 |

Declared prices are paid once, at declaration, and every access within the
permission then costs 100. Undeclared prices are complete charges for the first
access of that kind. The declared write price is 4,900 so that a declared first
write, with its 100-gas access, costs 5,000, the same as a cold SSTORE update
today. Payment transactions pay declared prices at first access instead
(section 5).

These replace the EIP-2929 cold and warm costs for SLOAD, SSTORE, account
access, and calls. Transactions in the payment lane are priced from the declared
column; all other transactions are priced from the general column.
[TIP-1177](./tip-1177.md) adds an access list lane column.

## 3. Legacy access lists

On transaction types that carry an EIP-2930 `access_list` (including type
`0x76`), the list is a read declaration at declared prices:

- each listed address is account-read-warm and code-warm for 5,000 (replacing
  EIP-2930's 2,400 per address);
- each listed storage key is read-warm for 2,000 (replacing 1,900 per key).

Duplicate entries are charged each time, entries for prewarmed addresses are
still charged, and legacy lists grant no write permission. Payment transactions
keep the TIP-1045 empty-list requirement.

## 4. Prewarmed and protocol-managed accesses

**Prewarmed addresses** are account-read-warm and code-warm without declaration:

- the addresses EIP-2929 and later EVM rules place in the initial
  accessed-address set (the sender, top-level call targets, the block
  beneficiary, and EVM precompiles), but not EIP-2930 entries;
- every Tempo native precompile address, including every TIP-20 token address.

Prewarming covers only the account and its code or dispatch. Storage of a
prewarmed address and its account writes are charged normally.

Top-level calls are charged as today: entering a call costs no access charge for
its target, and each call after the first in a batch keeps its existing
intrinsic charge (currently 2,600). If a target is an EIP-7702 delegating
account, its delegation target is not prewarmed and is charged as a code load
(section 7). A top-level contract creation is charged as today: the new account
is read- and write-warm, and its code is code-warm once deployed.

**Envelope processing** keeps its existing bounded charges and needs no
declarations. Every resource it reads before user execution is read-warm for the
rest of the transaction, and every resource it writes (such as the sender's
fee-token balance) is read- and write-warm. The exemption covers only these
protocol actions: the same resources accessed from user calls are charged
normally, and any user code invoked by the protocol is charged as user
execution.

## 5. Payment lane inference

Payment transactions are limited by the TIP-1045 allow-list to native precompile
calls (TIP-20 and TIP20ChannelReserve) whose resources follow from the call
arguments, fixed storage layouts, and a bounded number of native lookups. They
are priced as if they carried a complete list, with the declared price charged
at first access:

- A first read costs 2,000 + 100.
- A first write costs 4,900 + 100, or 2,900 + 100 if the resource is already
  read-warm, or 100 if envelope processing wrote it. Read then write therefore
  totals 2,100 + 3,000 = 5,100.
- Later accesses cost 100.

Inference covers all persistent accesses of the native implementation,
including policy registry, receive-policy, guard, and keychain lookups, and
storage-credit counter reads and writes (section 9). Pricing depends only on the
lane, not on whether a client derived the accesses in advance. Native calls
outside the payment lane get no inference. Payment calls never execute user
code; this is a permanent requirement of the payment lane: no allow-list entry
may ever reach user code, and every entry MUST keep a bounded access set that
clients can derive natively.

## 6. Undeclared accesses

An undeclared access, or a write to a resource declared read-only, pays its
lane's full undeclared price and execution continues normally. Outside inference
(sections 5 and 9), a write to a resource that is only read-warm, whether from a
read declaration, a paid read, prewarming, or an envelope read, pays the full
undeclared write price, not the difference. If the price cannot be paid, the
current frame halts with ordinary out-of-gas before the lookup. A miss never
makes a transaction invalid and never changes its lane.

## 7. Operations

**Storage.** SLOAD pays the read price, or 100 when read-warm. SSTORE pays the
write price, or 100 when write-warm, for every transition including no-ops. The
static-context prohibition and 2,300-gas SSTORE sentry still apply.

**Account metadata.** `BALANCE`, `EXTCODEHASH`, and other account metadata
reads pay the read price. Account writes by user execution (value transfers,
nonce changes, account creation) pay the write price, including no-op writes. A
call with zero value writes no account. SLOAD and SSTORE need no separate
account read of the storage-owning account.

**Code loads.** `CALL`, `CALLCODE`, `DELEGATECALL`, `STATICCALL`,
`EXTCODESIZE`, and `EXTCODECOPY` pay the account read price (or 100 if
account-read-warm) and the code component (or nothing if code-warm). Under this
TIP the code component is charged whether or not the address has code;
[TIP-1175](./tip-1175.md) charges it only when code is loaded. A cold contract
therefore costs the full bytecode row and a prewarmed or legacy-listed address
costs 100. These replace the opcodes' previous base and access costs; memory,
copy, value-transfer, account-creation, stipend, and 63/64 rules still apply.
The `CALL` family charges an EIP-7702 delegation target as a further code load.
Native precompiles are prewarmed, so dispatching them costs 100.

**Creation.** `CREATE` and `CREATE2` keep their computation, initcode,
deposit, and state-gas charges. The creator's nonce increment and the new
account are account writes. Deployed code is code-warm. `SELFDESTRUCT` keeps its
restrictions and opcode charge, with account accesses charged as above.

**Native precompiles.** Persistent accesses use the same resource identities and
rules as EVM operations. Each native storage write operation, including atomic
read-modify-write operations such as balance increment and decrement, is one
write; a separate native read before it pays separately. Implementations MUST
NOT split one logical operation into separately charged parts, and each native
method's operation sequence is part of its gas specification.

## 8. Refunds

Each write price has an **access component**, equal to the read price of the
same column, and a **write component**, the remainder:

| Column | Access component (never refunded) | Write component (refundable) |
| --- | ---: | ---: |
| Declared / inferred | 2,000 | 2,900 |
| General lane, undeclared | 4,000 | 6,000 |

At the end of user execution, for each slot that was the target of at least one
SSTORE or native storage write during user execution, in a frame that (with its
ancestors) did not revert, and whose final value equals its value when user
execution began, the slot's write component is added once to the execution
refund counter. The column is the one that priced the slot's write permission. A
slot that envelope processing wrote has a zero write component and earns no
refund. This covers no-op, `X -> Y -> X`, and `0 -> Y -> 0`;
`X -> Y -> X -> Y` gets nothing. Account writes and warm charges are never
refunded. These refunds are computed before TIP-1060 credit settlement and
replace all other SSTORE execution refunds.

## 9. Storage credits

TIP-1060 credit transitions and TIP-1016 state gas are unchanged. When a slot is
created or cleared, the protocol reads the storage-owning account's credit
counter, and when it mints or consumes a credit it writes the counter. Both are
charged as inferred accesses in every lane: the read costs 2,000 + 100 the first
time in a transaction and 100 after, and the write costs 2,900 + 100 the first
time and 100 after. This warmth survives reverts. Counters are never
credit-accounted and their writes carry no state gas. Direct user calls to the
storage-credits precompile are charged normally.

## 10. Loading read sets

Clients MUST validate bounds, signatures, fee authorization, and intrinsic gas
before prefetching. Clients SHOULD prefetch every legacy access list entry and,
for payment transactions, the resources derived natively from the allow-listed
calls. Never fetch all storage of an address or follow unlisted code. Clients MAY
skip or cancel prefetch without affecting gas.

## 11. Activation

At activation the prices take effect and the transaction pool is revalidated.
Earlier blocks replay under their own rules. Wallets and sponsors MUST
re-estimate gas, and contracts that forward fixed gas amounts need compatibility
testing.

# Gas Cost Impact

Projections, not measurements, against today's TIP-1016 and TIP-1060 schedule.
Payment lane, user-path state access only:

| Operation | Baseline | Proposed | Change |
| --- | ---: | ---: | ---: |
| TIP-20 transfer, existing recipient balance | 16,300 | 16,300 | 0 |
| TIP-20 transfer, new recipient balance, no credit | 20,500 | 18,500 | −2,000 |
| Finite allowance in `transferFrom` (incremental) | 5,000 | 5,100 | +100 |
| Credit minted when a transfer clears the sender's balance | 5,000 | 5,100 | +100 |

General lane contract execution (legacy lists can declare reads only, so a
legacy-listed slot that is later written pays the undeclared write):

| Storage sequence | Baseline | Undeclared | Legacy-listed |
| --- | ---: | ---: | ---: |
| Cold SLOAD | 2,100 | 4,000 | 2,100 |
| Ten reads of one cold slot | 3,000 | 4,900 | 3,000 |
| Cold read then write | 5,000 | 14,000 | 12,100 |
| Cold contract call | 2,600 | 10,000 | 5,100 |

Until [TIP-1176](./tip-1176.md) adds write declarations, contract writes in the
general lane pay the undeclared price. Shipping TIP-1176 in the same hardfork
avoids that interim cost.

# Tooling

`eth_estimateGas` uses legacy declarations, payment inference, and undeclared
prices. `eth_createAccessList` remains EIP-2930 and its output is now priced at
declared read prices.

# Observability

Clients MUST emit per-transaction undeclared-access counts by kind and
read/write. Traces MUST classify each access as declared, prewarmed,
envelope-warmed, inferred, or undeclared. Resource identities MUST NOT be
unbounded metric labels.

# Threat Model

Senders can omit or pad declarations; undeclared prices and upfront declaration
charges bound this. Payment inference only reaches allow-listed native calls with
empty lists, which never run user code. The cheapest undeclared lookup in the
general lane is 4,000 gas, so a 30M general lane holds at most 7,500 undeclared
lookups (about 14,300 cold SLOADs today).

**Unpaid payment-lane prefetch (open problem).** Clients prefetch the whole
derived set of a payment transaction at admission, but it pays only for accesses
execution reaches. Future TIPs should remove conditional state access from
allow-listed payment calls.

# Invariants and Validation

1. Each declared or inferred permission is paid for at most once per
   transaction, after which accesses within it cost 100.
2. Other first accesses pay their lane's undeclared price before the lookup.
3. Prefetch and cache state never warm a resource, and a read never warms a
   write.
4. Declared, prewarmed, envelope, and inferred warmth survive reverts; other
   warmth is journaled.
5. Refunds return at most the write component of a restored slot.
6. Envelope exemptions are unreachable from user calls.

Reference tests MUST cover every permission, resource, and column combination;
read-then-write misses; warm repeats; all SSTORE transitions and restore refunds;
credit-counter reads and writes; legacy lists; payment inference for all native
dependency paths; envelope-touched slots; nested reverts and out-of-gas; and
activation and historical replay. TIP-20 paths MUST be validated with the
[TIP-20 gas scenarios](../crates/node/tests/it/gas/tip20_transfers.rs).
