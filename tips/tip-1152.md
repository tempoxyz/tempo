# TIP-1152: T14 Hardfork Meta TIP

## Abstract

T14 proposes configurable accounts, removal of admin access keys, state-gas
accounting, encrypted forced Zone withdrawals, and TIP-20 payment storage
changes. This meta TIP links their specifications and collects additional
T14-gated protocol changes, including proposer fee-recipient enforcement.

## Motivation

Collect the T14 upgrade scope and implementation links in one place for review.

# Additional protocol changes

These changes are not covered by an individual T14 TIP. They are proposed behind
T14; pre-T14 execution rules are preserved.

## 1. Bound validator endpoint lengths

**PR**: [#8206](https://github.com/tempoxyz/tempo/pull/8206) · **Author**: @hamdiallam

Amends [TIP-1017](./tip-1017.md) from T14 onward. ValidatorConfig V2's
`addValidator`, `rotateValidator`, and `setIpAddresses` require each `ingress`
and `egress` input to be at most 255 bytes, matching the one-byte endpoint
length prefixes in validator signature messages.

Endpoint validation checks ingress before egress, and each endpoint's byte
length before its format. An oversized endpoint reverts with
`InvalidIp(string input)`, carrying the rejected input, before signature
encoding or verification. Malformed inputs within the limit continue to revert
with `NotIpPort(string input, string backtrace)` for ingress and
`NotIp(string input, string backtrace)` for egress.

Pre-T14 execution retains its existing validation and signature-encoding
behavior for historical replay. ValidatorConfig V1 behavior is unchanged. This
amendment does not revalidate stored endpoints or change the storage layout.
Signature messages continue to use the original endpoint bytes and their
one-byte length prefixes. TIP-1017 retains its original T2 specification; this
section specifies the T14 delta.

## 2. Default consensus to deferred verification after the fork boundary

**PR**: [#8438](https://github.com/tempoxyz/tempo/pull/8438) · **Author**: @decofe

Defaults `--consensus.verification-mode` to `hardfork`. Selects immediate or
deferred verification once per epoch using the previous epoch's finalized
boundary-block timestamp, or genesis for epoch zero. Deferred verification
starts when that timestamp reaches T14; explicit `immediate` and `deferred`
overrides remain available.

## 3. Pause Zone refund claims and batch settlement

**PR**: [#8295](https://github.com/tempoxyz/tempo/pull/8295) · **Author**: @decofe

The T14 portal runtime blocks refund claims and batch settlement while paused.
The sequencer idles batch preparation and submission until the portal resumes.
Older portal runtimes retain their existing behavior.

## 4. Charge sponsored Zone withdrawal fees in the default fee token

**PR**: [#8439](https://github.com/tempoxyz/tempo/pull/8439) · **Author**: @0xKitsune

A sponsored withdrawal burns its fee from the sponsor in the Zone default fee
token, captured from the portal's first enabled token at genesis. Unsponsored
withdrawals, including calls through a contract, burn principal plus fee from
the caller in the withdrawal token. The outbox and backing checker use the same
T14 gate.

## 5. Allow Zone TIP-20 transfers with portal-admin opt-in

**PR**: [#8549](https://github.com/tempoxyz/tempo/pull/8549) · **Author**: @adityapk00

Enables `transfer`, `transferFrom`, and their memo variants only when the Zone
runs T14 rules and the portal admin has enabled transfers. The setting defaults
to false and is read from finalized Tempo state. Transfers reject Permit2
callers, honor the token's L1 pause flag, and revert on receive-policy rejection
instead of diverting funds to `ReceivePolicyGuard`. Portal account access still
gates L1 addresses rather than Zone recipients.

## 6. Activate dynamic Zone base fees

**PR**: [#8401](https://github.com/tempoxyz/tempo/pull/8401) · **Author**: @adityapk00

Alongside TIP-1012's forced exits, this activates the T7 dynamic base-fee
controller on Zones at T14, with a 0.6 gwei floor.

## 7. Enforce the proposer's registered fee recipient

**PR**: [#8572](https://github.com/tempoxyz/tempo/pull/8572) · **Author**: @SuperFluffy

Block execution rejects a block if its beneficiary differs from the proposer's
`ValidatorConfigV2` fee recipient, or if the proposer has no entry. The recipient
is resolved from parent state. A registered zero address burns the fees. This
prevents a proposer from redirecting fees using only its consensus key.
