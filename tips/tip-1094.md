# TIP-1094: Zone Virtual Deposit Addresses

## Abstract

This TIP defines a reserved 20-byte address containing a public zone ID, a key version, and an encrypted zone-local master ID and user tag. Anyone can register a recipient in the zone's native registry; no L1 master registration is required. Ordinary TIP-20 transfers to the address fund the zone's portal and append a deposit to its existing queue, once the portal admin has enabled virtual deposits. The zone resolves the encrypted identifier and credits the registered master; a failed deposit refunds its sender. Mints to the address revert. Operators rotate keys by initializing a new key version and can retire old versions on Tempo.

## Motivation

A reusable address lets an ordinary wallet, exchange, or payment system deposit into a zone without constructing an encrypted portal call. Unlike TIP-1022 virtual addresses, it does not publicly reveal the recipient's master ID. Each registration has 65,536 aliases per key version, with no per-address registration or lookup table. A registered master accepts any token enabled for deposits in the zone.

Master registration and lookup stay in confidential zone state, so registration does not publish the recipient's existence or its ID-to-recipient mapping on Tempo. Each zone has an independent registry; receiving in multiple zones requires a registration in each, rather than one shared L1 registration. One recipient can have multiple master IDs in the same zone.

The [Zones protocol](https://github.com/tempoxyz/zones/blob/a88c2ac6b6b407225e2861c660806faccc0217df/specs/spec.md#deposits) already has an encrypted-only user deposit API: `deposit()` and `depositEncrypted()` accept the same ECIES payload. This TIP adds a second encrypted recipient encoding, FF1, to the same ordered queue. Each decoder produces a recipient for the shared zone-side mint and failure handling; an FF1 address is not converted into an ECIES payload. The existing ECIES API and its encrypted memo remain unchanged. Address-deposit memos are public.

## Assumptions

- `ZoneFactory` assigns stable, nonzero `uint32` zone IDs and resolves each to its registered portal. This TIP extends the native Tempo transfer dispatch, shared portal runtime, native zone inbox/outbox, zone-local registry, and batch prover together at activation; older queued deposits keep their existing encoding and meaning.
- Zone-local recipient bindings are immutable and covered by the zone execution proof. The native inbox reads them directly from zone state, without an L1 registry read or a cross-contract storage-read extension.
- Each participating zone preserves one immutable, confidential FF1 key per initialized key version, for the life of the zone. Issuance under a version starts only after that version's initialization is settled. Losing any initialized key can stop execution; changing an address's recipient by substituting another key is forbidden.
- Liveness requires continued zone execution, data and witness availability, valid batch settlement, and Tempo-side withdrawal processing. A refund parked by the existing refund machinery also requires recipient action and restored permission before it can be delivered. This TIP does not provide forced inclusion or recovery from permanent zone failure.
- Native TIP-20 dispatch must be able to call the portal's `depositVirtual` (see [Tempo Routing and Queueing](#tempo-routing-and-queueing)). With the Solidity portal runtime, this requires EVM2, because the pre-EVM2 precompile interface cannot call Solidity; this TIP then activates only in a protocol version where EVM2 is live. If the native ZonePortal precompile (planned for T15) is active, the call is native-to-native and does not depend on EVM2. *(Author note: the EVM2 dependency was added before the native portal was proposed; confirm which portal this TIP targets.)*

# Specification

## Address Encoding

```
[ zoneId: 4 bytes ][ magic: 9 bytes ][ version: 1 byte ][ ciphertext: 6 bytes ]
```

An address is reserved if and only if bytes `[4:13]` equal `0xFCFCFCFCFCFCFCFCFC`. `zoneId` is big-endian at `[0:4]`, `version` is at `[13]`, and the ciphertext is at `[14:20]`. `version` is the key version: values `0x01` through `0xFF` each select one zone key (see [Key Versions and Rotation](#key-versions-and-rotation)). Version `0x00` is unsupported and reverts on Tempo. All matching addresses, including version `0x00`, are reserved and MUST NOT receive a literal TIP-20 balance through recipient-bearing operations. Zone ID zero is unregistered.

TIP-1022's magic, `0xFDFDFDFDFDFDFDFDFDFD` at `[4:14]`, is distinct. Dispatch never chains the two resolvers.

The plaintext is the six-byte concatenation `masterId || userTag`: the exact four zone-local ID bytes followed by two opaque tag bytes, matching TIP-1022's field widths. Every tag from `0x0000` through `0xFFFF` is valid. Encrypt all six bytes together; neither field appears separately in the address. Tags select aliases of the same immutable recipient registration, not different zone accounts. Derivation is deterministic for a fixed zone, version, key, master, and tag. The same master and tag produce unrelated ciphertexts under different versions. The token is not encoded in the address and does not select an FF1 permutation. The outer format and 48-bit FF1 domain are the same for every version.

## Zone-Local Master Registry

Activate a native zone registry precompile at `0xFDC0000000000000000000000000000000000000`, the address used by TIP-1022 on Tempo but currently not registered as a zone precompile. This is an independent zone-local registry, not an L1 mirror. Its activation does not enable TIP-1022 virtual-address forwarding inside the zone or change the L1 registration API. The zone node and prover MUST execute the same implementation. Calls use the zone's existing direct-call-only precompile rules and ordinary transaction admission and fee metering.

```solidity
interface IZoneAddressRegistry {
    function registerMaster(address recipient, bytes32 salt) external returns (bytes4 masterId);
}
```

`registerMaster` is permissionless: the caller need not be the recipient and no recipient signature is required. Registration creates only a receiving alias, granting the caller no authority over the recipient, its funds, or authenticated address issuance. A funded third party can submit and pay for registration without funding the recipient first; a recipient-originated transaction may also use sponsorship where supported by the zone.

Registration does not name a token. A registered master accepts any token enabled for deposits in this zone, including tokens enabled later. Registration does not enable a token or bypass the deposit path's canonical-token, initialization, enablement, pause, fee, admission, or recipient-policy checks. Token availability is checked by the existing deposit path, not by registration.

### Registration requests and ID allocation

Clients SHOULD generate a 32-byte salt with a cryptographically secure random generator. The salt identifies a registration request; there is no grinding or proof-of-work check. Compute:

```
requestHash = keccak256(abi.encodePacked(
    "TEMPO-ZVDA-MASTER-v1", bytes4(zoneId), recipient, salt
))
```

The domain is the exact ASCII string `TEMPO-ZVDA-MASTER-v1`, with no terminator. `zoneId` is the executing zone's configured four-byte big-endian ID, not a caller-supplied value; `recipient` is exactly 20 bytes and `salt` exactly 32 bytes. Neither `msg.sender` nor transaction ordering affects `requestHash`. Including the recipient prevents a copied request from redirecting its registration. The `-v1` in this domain versions the request format; it is unrelated to the address key version.

The registry allocates IDs sequentially from `0x00000000` through `0xFFFFFFFF`. A proof-covered `uint64 nextMasterId` starts at zero; it must represent the terminal exhausted value `0x100000000` without wrapping. After validating the recipient, first look up `requestHash`: an existing request returns its allocated ID without advancing the counter. For a new request, require `nextMasterId < 0x100000000`, assign the four-byte big-endian value of `nextMasterId`, store the immutable recipient binding and request-to-ID record, then increment the counter. All writes are atomic. At `nextMasterId == 0x100000000`, new requests revert with `MasterIdSpaceExhausted()`; existing requests remain idempotent.

New IDs depend on execution order, so clients MUST use the returned ID or the recipient discovery RPC rather than predict one before execution. Copying the same request is harmless: both submitters receive the same ID bound to the original recipient. Different salts allow multiple IDs for one recipient. Allocated IDs are never reused, giving a lifetime limit of 4,294,967,296 registrations per zone. Master IDs are independent of key versions: one ID has aliases under every initialized version. Allocation order and registration count can be inferred by registration submitters from returned IDs; they are not exposed as fields in public deposit addresses.

### Registration and Storage Rules

- Reject zero, TIP-20 token addresses, TIP-1022 virtual addresses, and zone virtual deposit addresses as recipients, using the namespace checks below. Invalid recipients revert with `InvalidMasterAddress()`.
- Each `masterId` binds permanently to one recipient. Callers cannot request, overwrite, delete, rotate, or reassign an ID or its binding. Sequential allocation prevents ID collisions. Repeating a `(recipient, salt)` request returns its original ID without additional allocation or storage writes.
- Multiple IDs MAY bind to the same recipient through different salts. There is no one-ID-per-address or one-ID-per-recipient constraint. ID `0x00000000` is valid; absence is represented by a zero recipient, not by a special ID.
- Store entries in the precompile's own zone state. Let `R = keccak256("tempo.zvda.masterRegistry")`; the recipient for the `bytes4 masterId` occupies `keccak256(abi.encode(masterId, R))`. The stored word has twelve zero high bytes and the 20-byte recipient address in its low bytes. The slot is covered by the zone state witness.
- Let `Q = keccak256("tempo.zvda.registrationIds")`; the request record occupies `keccak256(abi.encode(requestHash, Q))` and stores `uint64(uint32(masterId)) + 1` in the low eight bytes, with zero high bytes. Zero denotes an absent request; the offset permits both the first and last IDs to be represented, including the last ID's record value `0x100000000`. Store `nextMasterId` in the low eight bytes of slot `keccak256("tempo.zvda.nextMasterId")`, with zero high bytes. Interpret the four ID bytes as an unsigned big-endian integer when computing the request record. Reserve all three namespaces against overlapping precompile state. New requests pay ordinary hash, counter, and new-storage costs; ordinary fees and zone admission remain necessary to protect against state growth and ID-space exhaustion.
- Registry lookup is internal to native execution and the authenticated issuance service; the precompile exposes no public mapping getter or enumeration API. Storage/proof RPCs, traces, receipts, logs, errors, and simulations MUST NOT expose another recipient's registration or mapping to an unauthorized user or to Tempo observers. The native inbox and prover read the proof-covered mapping internally without a public getter call or an EVM2 cross-contract storage read. Missing or invalid registry witnesses invalidate execution; they are not evidence that an ID is unregistered.

The submitting party necessarily knows the recipient it registers and the returned ID, but this does not authorize it to derive that recipient's deposit addresses or inspect recipient-private activity. Registration calldata and results remain subject to zone confidentiality; do not publish a registration event or mapping on L1. Address issuance MUST wait until both registration and the issuing version's key initialization are settled. An unregistered ID encountered during deposit processing takes the existing failure path, not an implicit registration path.

## FF1 Parameters

Use FF1 with AES-256 as specified in [NIST SP 800-38G](https://csrc.nist.gov/pubs/sp/800/38/g/upd1/final):

| Parameter | Value |
|---|---|
| Key | The zone's 32-byte key for the address's `version` |
| Radix | 2 |
| Numeral-string length | 48 binary digits |
| Tweak | `"TEMPO-ZVDA-v" \|\| decimal(version) \|\| zoneId` |

The tweak is the 12-byte ASCII string `TEMPO-ZVDA-v`, then the version number written in decimal ASCII digits without leading zeros, then the four big-endian zone ID bytes. For version 1 the tweak is `0x54454D504F2D5A5644412D7631 || zoneId` (17 bytes); for version 10 it is `0x54454D504F2D5A5644412D763130 || zoneId` (18 bytes). Expand each plaintext byte most-significant bit first, in byte order; pack the output in the same order. Decryption reverses this operation. Do not truncate a conventional cipher, hash, or MAC. The deposited token MUST NOT affect the key, tweak, or decryption: all tokens resolve a given address to the same registration. The version-1 conformance vectors are unchanged.

|---|---|---|---|---|---|

## Tempo Routing and Queueing

The intercepted entrypoints are exactly `transfer`, `transferFrom`, `transferWithMemo`, `transferFromWithMemo`, and `systemTransferFrom`. `mint` and `mintWithMemo` to a reserved destination MUST revert with the existing TIP-20 `InvalidRecipient()` error; an issuer that wants to fund a zone deposit address mints to itself and then transfers. Fee-payment and reward-recipient paths reject the reserved format instead of queueing. Non-TIP-20 assets are outside this TIP.

For a reserved destination, Tempo MUST:

1. Require a version other than `0x00` and resolve `zoneId` to a registered portal; otherwise revert with `UnsupportedAddressVersion(uint8)` or `ZoneUnregistered(uint32)`.
2. Perform the entrypoint's usual balance, pause, allowance, and spending-limit checks. TIP-403 evaluates the sender where applicable and the portal as the Tempo recipient. The hidden recipient is checked only inside the zone. TIP-1028 checks the portal using the operation's ordinary originator; a blocked receive policy reverts this operation rather than diverting escrow to `ReceivePolicyGuard`.
3. Debit `from` and credit the portal. Never credit the literal destination. Reject amounts that do not fit the portal's `uint128` amount field.
4. Invoke the native-dispatch-only portal operation below. Any portal failure rolls back the entire originating call, including balance changes, fees, allowances, and events.

The native TIP-20 calls the portal with the token's own address as `msg.sender`, exactly once after crediting it. This applies to both the Solidity portal runtime and the native ZonePortal precompile; the portal rules below are the same for either implementation. The portal derives the token from that caller and verifies it is an initialized canonical TIP-20 precompile as well as an enabled token; matching a user-supplied token parameter or an arbitrary enabled ERC-20 is insufficient. Only the native recipient-routing path may make this call, and it fixes every argument from the originating operation. Ordinary contract calls cannot impersonate that precompile. Include the portal call in normal gas accounting and reentrancy protection.

### One New Deposit Type

Append `ZoneVirtual = 2` to the current `DepositType` enum, preserving `WithdrawalBounceBack = 0` and ECIES `Deposit = 1`. Existing type values and payloads MUST NOT be reinterpreted.

```solidity
struct VirtualDeposit {
    address token;
    address originator;  // the debited account
    uint128 amount;      // net of the deposit fee
    address destination;
    bool hasMemo;
    bytes32 memo;        // MUST be zero if hasMemo is false
}

/// Called only by a canonical native TIP-20; msg.sender identifies the token.
/// Tokens have already been credited; this call MUST NOT pull them again.
function depositVirtual(
    address originator, uint128 grossAmount,
    address destination, bool hasMemo, bytes32 memo
) external returns (bytes32 newCurrentDepositQueueHash);
```

`transferFrom` uses the debited owner as `originator`, not the spender. `hasMemo` is true only for memo-bearing entrypoints, including when the memo is zero. There is no separate refund-address field: a failed deposit refunds `originator`.

The portal verifies magic and its own zone ID. It then MUST revert with `VirtualDepositsDisabled()` unless the admin has enabled virtual deposits (see [Portal Controls](#portal-controls)), and with `AddressVersionRetired(uint8)` if `version` is below the portal's minimum accepted version. If the portal supports TIP-1151 deposit authorizations and enforces them, it MUST revert with `DepositAuthorizationRequired()`, because a plain transfer cannot carry an authorization. The portal then applies the existing deposit checks for portal/token pauses, token enablement, depositor membership, outstanding unprocessed-deposit capacity, minimum amount, and fees. Apply depositor membership to `originator`, never to the dispatch's synthetic caller. Apply the existing refund-recipient validation to `originator`. The existing gateway exception and all other access rules remain in force.

Capacity is measured by `depositCount - lastProcessedDepositNumber`, not by the number of deposits in a Tempo block. Virtual and ECIES deposits share the existing public-admission limit below `MAX_UNPROCESSED_DEPOSITS`. Preserve the reserve for withdrawal-generated deposits and the guarded allowance for one callback-triggered deposit. Only accepted batch settlement advances `lastProcessedDepositNumber`; a new Tempo block does not restore capacity. Apply these checks and counter updates atomically with funding, fee payment, and enqueueing.

Deduct and pay the existing deposit fee, form `VirtualDeposit` with the net amount, and append exactly one entry:

```
currentDepositQueueHash = keccak256(abi.encode(
    DepositType.ZoneVirtual, virtualDeposit, currentDepositQueueHash
))
```

Increment the existing deposit counter and emit `VirtualDepositMade`. This type consumes the same user-deposit capacity as ECIES deposits, preserving the capacity reserved for withdrawal bounce-backs. The new type changes the inbox's decoder and execution proof, but not queue ordering, hash chaining, numbering, or settlement commitments. ECIES deposits alone consume `DecryptionData` entries; virtual deposits consume none.

### Portal Controls

The portal adds two admin-only controls, gated like the existing access-policy controls:

```solidity
function setVirtualDepositsEnabled(bool enabled) external;
function retireAddressVersionsBelow(uint8 minimumVersion) external;
```

Virtual deposits start disabled for every portal. While they are disabled, `depositVirtual` reverts with `VirtualDepositsDisabled()`, so the originating transfer reverts on Tempo and no funds move. Disabling affects only new deposits: deposits already in the queue are processed normally. Each call emits `VirtualDepositsEnabledUpdated(bool)`.

`retireAddressVersionsBelow` sets the portal's minimum accepted key version, which starts at `0x01`. It MUST revert with `InvalidVersionRetirement(uint8)` unless `minimumVersion` is greater than the current minimum; the minimum can only rise. After the call, `depositVirtual` reverts with `AddressVersionRetired(uint8)` for any lower version. Deposits already in the queue under a retired version are processed normally. Each call emits `AddressVersionsRetired(uint8)`. Retirement has no notice delay: the admin can already stop all virtual deposits at once with `setVirtualDepositsEnabled(false)`, and both controls fail on Tempo before any funds move. Operators SHOULD announce a retirement in advance so recipients can reissue addresses (see [Key Versions and Rotation](#key-versions-and-rotation)).

The sequencer-side depositor allowlist rejects an ECIES deposit by supplying zeroed decryption data, which sends it down the failure path. Virtual deposits consume no decryption data, and their processing takes no sequencer input (see [Zone Resolution and Shared Processing](#zone-resolution-and-shared-processing)), so that allowlist cannot reject them. A zone that relies on the sequencer-side allowlist to admit depositors SHOULD NOT enable virtual deposits. Portal-enforced depositor membership still applies to `originator`.

### TIP-20 Events

Preserve TIP-1022's logical two-hop event convention, substituting the portal for the resolved master. Emit `Transfer(from, destination, grossAmount)`, then `TransferWithMemo(from, destination, grossAmount, memo)` if present, then `Transfer(destination, portal, grossAmount)`.

These routing events precede the portal fee-transfer events and `VirtualDepositMade`. The intermediate address never holds a balance. Reverts remove all events. Success means the deposit was queued, not that the zone recipient has already been credited.

## Zone Resolution and Shared Processing

The native inbox consumes the authenticated queue in its existing order. The ECIES decoder is unchanged; the virtual decoder checks magic, a nonzero version, and matching zone ID, loads the committed key for that version, decrypts the six-byte ciphertext, and resolves `masterId` through the zone-local registry in the execution state at that point. This lookup is covered by the zone state witness, not an L1 registry proof. Do not cache absence across registrations; a registration executed after this deposit's processing cannot retroactively change its result.

For a registered master, read its recipient. Never reinterpret the ciphertext using the deposited token or retry resolution against another registration.

Both decoders feed the existing zone mint path. For virtual deposits, use `mint` when `hasMemo` is false and `mintWithMemo` otherwise. Apply the ordinary zone recipient checks, including TIP-403 and the TIP-1028 precheck that prevents diverting a deposit into `ReceivePolicyGuard`. A successful virtual deposit credits exactly the registered `masterAddress`; `userTag` is attribution metadata only.

Tempo admission already checks the actual transfer sender's TIP-403 authorization where applicable, and TIP-1028 evaluates delivery to the portal using the operation's ordinary originator. These checks do not evaluate the hidden zone recipient's receive policy. Preserve the existing zone mint semantics: the zone-side TIP-1028 precheck and mint use `ZoneInbox` (`0x1c00000000000000000000000000000000000001`) as the sender, not the deposit's original sender. The zone recipient's sender allowlist therefore accepts or rejects the inbox as a whole; it does not distinguish individual depositors through this path. The zone still checks the hidden recipient's TIP-403 authorization and receive policy before crediting it.

Invalid address encoding, a version with no initialized key, an unregistered/invalid master, or a caught recipient/mint rejection selects the committed failure action. There is no sequencer-supplied rejection flag or recipient override. Roll back a failed mint's partial state before recording its failure. A missing/invalid witness, inconsistent queue payload, out-of-gas, or other execution-system failure invalidates the system transaction or batch; it MUST NOT be converted into a recipient failure or used to cancel a valid deposit.

After a successful mint or recorded failure action, advance the deposit queue once. Record the destination and decoded attribution only in recipient-authorized zone execution data. Ordinary withdrawals and internal withdrawal-bounce-back deposits keep their existing behavior.

## Failure Actions

| Deposit origin | Failure action |
|---|---|
| Existing ECIES deposit | Existing refund to its explicit `tempoRefundRecipient` |
| Virtual-address transfer | Existing refund to `originator` |

A failed virtual deposit calls the existing inbox-only outbox bounce-back operation with the token, net amount, and `originator`. After proof settlement, the portal attempts the refund, charges the existing processing fee when collectable, and parks undeliverable amounts in its existing refund registry. Membership, token pauses, and receive-policy changes can delay delivery or require a later claim. They do not cause a second zone mint or a second bounce-back.

TIP-1028's `ReceivePolicyGuard` cannot hold a failed deposit inside the zone instead: its recovery authority exists only on Tempo, so funds held by it in a zone could never be claimed.

## Key State and Execution

FF1 decryption is an internal operation of the native inbox, following the existing native ECIES execution model. There is no separately callable decrypt precompile, cross-contract storage read, or dependency on the removed `ZoneConfig` contract.

Store version keys in a namespaced mapping owned by the native inbox at `0x1c00000000000000000000000000000000000001`. Let `S = keccak256("tempo.zvda.addressKeys")`; for version `v`, the initialized flag occupies `keccak256(abi.encode(uint256(v), uint256(S)))` and the key occupies the next slot. The flag is zero or one; it distinguishes an unconfigured key from a configured all-zero key. These slots are reserved and MUST NOT overlap other inbox state.

Add this system-only inbox entrypoint:

```solidity
/// Initialize the next key version exactly once; emits no key material.
/// Callable only as the optional key-initialization system transaction.
function initializeVirtualAddressKey(uint8 version, bytes32 key) external;
```

The zone block format permits at most one such system transaction, immediately after `advanceTempo` and before user transactions, with an optional `(version, key)` field in the block witness. It is absent from blocks that do not advance Tempo. The block validator and prover MUST bind this field to the exact system transaction and enforce its position and system origin; an ordinary call with a claimed sender is insufficient. Versions are initialized in order: the first initialization MUST use version `0x01`, and each later one MUST use the highest initialized version plus one. Initialization reverts if `version` is `0x00`, out of order, or already initialized, including when the supplied key equals the existing key. Successful initialization stores the key and sets the flag in the proof-covered state. Existing zones begin with no initialized version; the operation cannot rewrite genesis or historical state.

Address issuance under a version MUST wait for settlement of that version's initialization. Because initialization follows that block's deposit processing, its key becomes usable by the next `advanceTempo`. The native inbox reads its own key for the address's version directly when processing virtual deposits. A deposit whose version has no initialized key at processing time takes the `KeyUnconfigured` failure path. Once a version is configured, unavailable key data or a missing state witness is an execution failure, not an unconfigured-key bounce-back.

The key is confidential execution state, not merely a hidden getter. User-scoped storage/proof queries, transaction and block responses, traces, simulations, logs, and state dumps MUST NOT expose the key, initialization calldata, or decryption inputs. Access control must also prevent users from requesting another master's decoded attribution. All executing replicas, including RPC-only followers, and all systems handling initialization, state, or batch witnesses become custodians of every initialized FF1 key. They need not hold the shared ECIES private key, but cannot be treated as outside the FF1 confidentiality boundary.

### Key Versions and Rotation

Each version has one key, and that key never changes. Rotation therefore means initializing a new version, not replacing a key. Each version's key MUST be generated uniformly at random and independently of every other version's key and every other zone's keys. All versions use the same FF1 parameters; only the key and the decimal version in the tweak differ. A zone can initialize at most 255 versions in its lifetime.

Operators MUST retain every initialized key, with protected backups, for the life of the zone. A retired version's key is still needed to process deposits already queued under it and to re-execute historical blocks. The setter cannot clear a key, and an operator cannot change the interpretation of an initialized version. Addresses under every initialized version remain valid until the portal admin retires that version.

The *issuance version* is the highest version whose initialization is settled. Address issuance uses the issuance version unless the authorized recipient asks for a specific settled version (see [Recipient RPC](#recipient-rpc)). Issuance MUST NOT use a version below the portal's minimum accepted version.

To rotate keys, the operator:

1. Generates a new random key and stores protected backups.
2. Initializes the next version with the key-initialization system transaction.
3. Waits for the batch containing that block to settle. The new version then becomes the issuance version, and new addresses use it.
4. Tells recipients to reissue addresses. Master IDs and tags carry over: the same `(masterId, userTag)` under the new version is a new, unrelated address for the same recipient.
5. Optionally, once recipients have migrated, calls `retireAddressVersionsBelow` on the portal. Tempo then reverts new deposits to older versions with `AddressVersionRetired(uint8)`, so senders see a failed transfer instead of funds in flight.

A leaked key does not reveal recipients: the registry that maps master IDs to recipients stays in confidential zone state. A holder of a leaked key can decrypt every address under that version. That reveals each address's master ID and tag, and so which addresses share a master. A leaked key also lets its holder derive every alias of a known master ID under that version. Rotation limits this to addresses under the leaked version; addresses under the new version are unlinkable to the old ones without the new key. Rotation cannot undo disclosure of past addresses.

### Execution Budget

This draft proposes a fixed additional `ZVDA_DECRYPT_GAS = 10_000` for each FF1 decryption, plus zone-local registry storage and existing policy-read and mint costs. This proposed tariff has not been benchmarked and MUST be validated or revised before approval. The constant is independent of key, plaintext, and ciphertext. Registration meters its fixed-size hash, input, and storage operations normally; initialization uses ordinary system-call input and storage metering. Tempo dispatch and queue insertion consume their normal native/EVM execution gas; the existing user deposit fee formula is unchanged. Before activation, benchmark the new paths and confirm that the complete queue at `MAX_UNPROCESSED_DEPOSITS` fits the zone system-transaction budget, including worst-case mixtures of ECIES, virtual, and withdrawal-bounce-back entries, recipient failures, and outstanding token enablements. Changing the agreed fixed tariff or capacity requires an explicit protocol parameter change, not operator-local tuning.

## Namespace and Compatibility Rules

- L1 TIP-1022 master registration MUST reject the reserved zone-address format. If an older L1 registered master matches it, TIP-1022 resolution reverts. The independent zone registry also rejects this format, zero, TIP-1022 virtual addresses, and token addresses as masters. Neither resolver forwards into the other.
- Inside a zone, all seven recipient-bearing TIP-20 entrypoints (the five intercepted on Tempo, plus `mint` and `mintWithMemo`) reject zone virtual addresses as destinations. Withdrawal requests, ordinary refund-recipient fields, reward recipients, and literal policy-subject operations also reject them. Zero is not a valid refund address.
- Approvals and transaction origination retain literal-address semantics. The namespace reservation does not prove that no corresponding EOA or contract can exist. No pre-activation literal balance is silently swept, routed, or burned by this TIP.
- A refund targets the debited account, not the external user of a forwarding contract. Routers and exchanges must handle late refunds and claims; ordinary transfer compatibility does not guarantee their application can recover or attribute a refund. Use the existing ECIES API with an explicit refund recipient when that control is needed.

# Tooling

## Recipient RPC

The authenticated zone RPC MUST let a recipient discover its master IDs, derive aliases, and reconcile processed virtual deposits without the registration submitter or access to a sender's receipt. Require these read-only methods:

```
zone_listDepositMasters(cursor, limit, auth) -> { snapshot, masters, nextCursor }
zone_getDepositMaster(masterId, auth) -> { snapshot, master }
zone_deriveDepositAddress(masterId, userTag, version, auth) -> { address, version }
zone_listDepositResults(masterId, cursor, limit, auth) -> { snapshot, results, nextCursor }
zone_getDepositResult(depositNumber, auth) -> { snapshot, result }
```

### Authorization and snapshots

Every method uses the zone's authenticated redacted RPC and scopes access to the registered recipient or a delegate authorized to act as that recipient. Use the zone's account authorization framework, including authorized Keychain keys. Contract masters require recipient-authorized contract or delegate authentication; deployment or payment for registration alone grants no authority. `auth` MUST bind the zone and chain, method, all supplied parameters, and a nonce or expiry. Listing masters authorizes the recipient account rather than a caller-selected master. Authorization is checked on every request, including cursor continuation; revoked delegates cannot continue reading an earlier snapshot.

Queries use the latest zone state settled by an accepted batch at a finalized Tempo block. `snapshot` contains `zoneBlockNumber`, `zoneBlockHash`, `tempoBlockNumber`, and `tempoBlockHash`, with the Tempo fields identifying that finalized settlement block. Never silently substitute an unsettled zone head. Issuance requires both the registration and the requested version's key to be settled; listing an owned registration does not require an initialized key.

`masterId` is a four-byte hex data value and `userTag` is a two-byte hex data value. Values with another byte length are invalid parameters, not implicitly padded or truncated. `version` is a one-byte hex data value or `null`. Block/deposit numbers, amounts, and `limit` use Ethereum JSON-RPC hex quantities. `cursor` is `null` for a first page. `limit` MUST be between 1 and 100. A continuation cursor is opaque and bound to the authorized recipient, method, master filter, and snapshot. `nextCursor` is `null` at the end. A stale or unavailable snapshot returns `-32004`; invalid parameters or a cursor from another scope return `-32602`. Cursors, counts, and page boundaries MUST NOT reveal another recipient's records.

An unknown, unsettled, or unauthorized master returns `master: null`; an inaccessible deposit returns `result: null`. A result-list query for such a master returns an empty page. Derivation returns the same `-32005` error for an unavailable or unauthorized master, without disclosing its owner. Authentication failures use the existing zone RPC errors. Nodes MUST NOT distinguish unauthorized objects from absent objects through response content.

### Master discovery and issuance

`zone_listDepositMasters` returns only IDs bound to the authenticated recipient, including registrations submitted or sponsored by another account and multiple IDs for the same recipient. Entries are ordered by unsigned `masterId` and appear once, even after idempotent registration calls. `zone_getDepositMaster` returns the same entry shape for an authorized ID:

```
{
  masterId, recipient, registrationTransactionHash,
  registrationZoneBlockNumber, registrationZoneBlockHash,
  addressVersions, issuanceVersion
}
```

Registration metadata identifies the first successful insertion, not an idempotent repeat. `addressVersions` lists versions with settled initialized keys that are at or above the portal's minimum accepted version, as of the snapshot. `issuanceVersion` is the highest of them, or `null` if there is none. Returning this filtered metadata does not grant access to the registration transaction's full calldata or receipt, which may involve other recipients. The recipient need not know the salt or obtain the returned ID from the submitter.

`zone_deriveDepositAddress` returns the deterministic address for an authorized master and tag. A `null` `version` selects the issuance version; a non-null `version` MUST be one of the master's `addressVersions`, and any other value returns `-32602`. The result echoes the version used. An optional bulk method MUST enforce the same authorization, tag bounds, and version rules. The registration submitter has no issuance authority merely because it paid for registration. Never offer public derivation for arbitrary masters. Clients may cache issued addresses until their version is retired.

### Deposit attribution

Result methods return only processed virtual deposits whose registry resolution identified the authorized recipient at processing time. `zone_listDepositResults` filters by that recipient's `masterId` and orders by increasing deposit number. `zone_getDepositResult` provides a direct lookup without requiring the originating Tempo transaction's sender to share a receipt. Each result contains:

```
{
  depositNumber, masterId, userTag, version, destination, token,
  originator, amount, hasMemo, memo, tempoTransactionHash,
  zoneBlockNumber, zoneBlockHash, outcome, failureReason
}
```

`token` in a deposit result is the deposited token. `amount` is the net queued amount after the deposit fee. `outcome` is `Credited` or `RefundEnqueued`; `failureReason` is `null` for a credit and the recorded reason otherwise. A refund being enqueued does not mean it has been delivered or made claimable on Tempo. Use the existing public withdrawal and refund records to track those later steps.

An authorized recipient can see a failed deposit when resolution identified its master before the failure. Invalid encodings, unconfigured keys, and unregistered masters that never identified a recipient remain operator-only results. Registering an ID later MUST NOT expose or reattribute an earlier unresolved deposit. An unprocessed deposit returns `result: null`; no recipient outcome is reported before settled processing.

Nodes MUST maintain private, rebuildable indexes of first registrations and processed results from confidential canonical zone execution and the authenticated Tempo queue. These indexes do not change consensus registry storage or introduce per-alias registration. A node without the required index or settled history returns `-32004`, not a misleading empty result. Raw registry enumeration, storage/proof queries, unrelated receipts, and public logs remain unavailable; only these recipient-filtered views are added.

## SDKs and operations

SDKs expose permissionless zone registration, random-salt generation without grinding, recipient discovery of allocated IDs and versions, structural detection and decoding (`zoneId`, version, ciphertext), authenticated derivation, and the conformance vectors. Receiving setup registers each zone independently and waits for settlement before requesting addresses; sending wallets need no custom payload construction. Clients retain the recipient and salt for safe registration retries and use a new salt when requesting another master ID for the same recipient. Wallets should show the destination zone alongside the address. A transfer of a token the zone does not credit, or to a recipient the zone rejects, can queue successfully on Tempo and then refund asynchronously with fees after zone processing. Wallets should distinguish queue acceptance from completed credit. Issuers fund deposit addresses by minting to themselves and transferring. Operator runbooks cover enabling virtual deposits, initialization, witness/replica confidentiality, backups, and key rotation and retirement without making those deployment procedures consensus rules.

Clients SHOULD NOT choose user tags randomly. The two-byte tag space is small enough for random selections to repeat long before all 65,536 tags are used. Allocate tags sequentially without reuse, coordinating allocation across wallets/apps sharing a master ID or using separate master IDs for independent allocators. Sequential tag order is hidden by encrypting the ID and tag together. When a master exhausts its tags, register another ID rather than wrapping the tag counter. A rotation does not reset tag allocation: reissuing tag `t` under a new version gives the same customer a new address. Deliberate address reuse remains valid, but links payments and can make attribution ambiguous; random registration salts are separate from user tags and remain recommended.

# Observability

Use one public event for virtual deposits, and one for each portal control:

```solidity
event VirtualDepositMade(
    bytes32 indexed newCurrentDepositQueueHash,
    address indexed originator,
    address token, address destination, uint128 netAmount, uint128 fee,
    uint64 depositNumber, bool hasMemo, bytes32 memo
);

event VirtualDepositsEnabledUpdated(bool enabled);

event AddressVersionsRetired(uint8 minimumVersion);
```

Existing batch/deposit counters track processing, and existing refund events distinguish delivery from parked claims. Public events and errors never contain decrypted identifiers, failure reasons, or key material. The inbox records a private result keyed by deposit number, with success attribution or a failure reason from `{InvalidAddress, KeyUnconfigured, UnregisteredMaster, InvalidMaster, MintFailed}`; visibility follows recipient/operator authorization. System/witness failures are reported separately and do not emit a committed deposit-failure result.

# Threat Model

Tempo observers and depositors see the zone, version, token, amount, sender, destination, and any memo. Repeated use of an address is linkable. They must not learn another master's hidden identifier from address issuance or public outputs.

The operator and every replica or proving component that holds an FF1 key are trusted for confidentiality. Recipient selection is nevertheless a deterministic, proof-covered state transition: sequencer input cannot substitute a recipient, change a configured key, or choose to reject an otherwise valid deposit. The operator can withhold service or disclose a key. Key compromise reveals the master ID and tag behind every past and future address under that version, but not the recipient; there is no forward secrecy within a version. Rotation limits exposure to the leaked version (see [Key Versions and Rotation](#key-versions-and-rotation)).

Arbitrary ciphertexts need not have been issued by the zone. FF1 provides confidentiality and invertibility, not address authentication. Recipients must distribute addresses through authenticated channels, and senders must preserve the complete address.

# Invariants

1. For a fixed zone, version, and key, FF1 is invertible and distinct plaintexts have distinct ciphertexts. A configured key never changes, and versions are initialized in order.
2. A successful intercepted Tempo operation credits portal escrow and creates exactly one matching queue entry. No literal reserved-address balance is credited. A revert undoes the complete operation. Mints to the reserved format always revert.
3. A successful zone credit goes to exactly the immutable zone-local registered master selected by the committed key for the address's version and authenticated zone state. Anyone may register a recipient, but the registration caller cannot alter its binding or acquire issuance authority. Multiple IDs may bind to that recipient. Neither the sequencer nor the depositor can override the failure action committed by native dispatch.
4. A deposit cannot both credit the zone and create a refund liability. Each queued liability is consumed at most once.
5. Account for pending deposits, settled zone balances, pending withdrawals/refunds, and parked refunds as separate stages of the existing bridge accounting. Fees leave escrow only when actually paid. Do not equate transient portal balance with zone supply while messages are in flight.
6. Given the stated continued-execution and settlement assumptions, each virtual deposit reaches a zone credit or a delivered or claimable refund. Invalid recipient data has a finite failure path; invalid proofs and missing execution data never authorize a failure action.
7. No public output or user-scoped RPC response exposes a secret key or another recipient's decoded attribution.
8. While virtual deposits are disabled, or for a version below the portal's minimum accepted version, no new virtual deposit is queued. The minimum accepted version never decreases. Deposits queued before either control changed are processed normally.

# Security Considerations

Every six-byte ciphertext decrypts to a plaintext. For `N` registered masters, a random ciphertext under an initialized version resolves to some registered master with probability `N / 2^32`, before recipient checks. A corrupted address can therefore credit an unintended master. Binding the zone and version into the tweak changes the permutation; it does not authenticate the encoded zone or guarantee rejection if someone edits it. This TIP does not add a checksum. Authenticated address distribution remains necessary.

Recipient confidentiality does not cover an admitted token's malicious policy controller. The zone checks the hidden recipient against the token's TIP-403 policy before crediting, and a rejection produces a public refund on Tempo. A controller can therefore test whether address `X` belongs to a candidate: block the candidate, send a small deposit to `X`, and watch for a refund. Blocking half of a candidate set per probe identifies one recipient among `2^k` candidates in `k` probes, at the cost of `k` deposit and refund fees. Any admitted token's controller can run this probe against any address, including a token admitted after the address was issued. ECIES deposits have a weaker form of the same leak, one observation per deposit someone else makes; reusable addresses let the controller probe on demand. Token admission should therefore be restricted to trusted issuers and policy controllers; this mitigates but does not eliminate the attack. Uniform private failure reasons, delays, and fees do not hide public refund outcomes. Closing this oracle requires private failure handling inside the zone, which is outside this TIP. TIP-1028's `ReceivePolicyGuard` cannot provide it, because its recovery authority exists only on Tempo.

The domain has only `2^48` values per version, and each master has 65,536 tags per version. Determinism reveals address reuse; amounts, timing, public memos, and external knowledge can also link deposits. Authentication of issuance is essential because public enumeration of a candidate master's tags would reveal its address set. Use fresh, non-randomly allocated tags where appropriate, and keep private attribution out of public memos. More aliases require another registered master ID.

The FF1 keys protect privacy, while committed execution protects recipient selection after issuance. Neither proves to a recipient that a malicious issuance service returned the requested master's address; authenticated issuance is trusted for correctness. Deleting a local key or withholding a witness cannot legitimately cause a configured address to be refunded. Proof verification and confidential-state handling must preserve these distinctions.

Permissionless registration is not proof of recipient participation or ownership by the submitter. Binding the request hash to the recipient prevents copying a registration from redirecting funds; copying the same request is harmless and idempotent. Callers cannot choose an ID or take over an existing binding, but they can consume the finite ID space by paying for registrations with new salts. Widening IDs does not remove exhaustion or state-growth risk. There is no proof of work: ordinary registration fees and zone admission must account for both state growth and the permanent 4,294,967,296-registration lifetime cap. Exhaustion stops new registrations, not processing or issuance for existing masters. Registration submitters can infer allocation order and registration count; malicious operators or public exports can reveal mappings. Registrations and all associated execution data otherwise share the zone's confidentiality boundary, with no L1 registration required.

The portal admin can disable virtual deposits or retire versions at any time. Both controls make new transfers revert on Tempo and never affect queued deposits, so they cannot strand funds. A careless retirement breaks every address a recipient issued under the retired versions until the recipient reissues; the admin cannot lower the minimum again.

# Alternatives Considered

- Keep only ECIES deposits: stronger randomized, authenticated encryption, but requires a payload and a portal call instead of an ordinary transfer to an address.
- Store a private address-to-recipient mapping: simpler lookup logic, but requires durable per-address state and recovery. This TIP retains stateless address derivation.
- Bind each registration to one token, with an optional any-token wildcard: narrows the issuer-policy probing oracle to one token's policy controller. It does not close the oracle, and it adds a token constraint to registration, resolution, RPC, and failure handling. This TIP leaves the oracle to a separate design for private failure handling.
- Bind FF1's tweak to the deposited token: a wrong-token payment resolves unrelated plaintext and may credit another registered master. One token-independent permutation per version avoids this.
- Allow mints to deposit addresses: lets an issuer fund a zone recipient in one call, but a failed mint has no sender to refund. Handling it requires burning portal escrow through a new privileged TIP-20 operation that bypasses issuer roles, pauses, and policies. Issuers instead mint to themselves and transfer, which uses the ordinary refund path.
- Rotate a key in place: keeps one version, but changes the recipient of every outstanding address. Versioned keys keep old addresses valid and let the admin retire them explicitly.
- Reuse the L1 TIP-1022 registry: allows one registration for multiple zones, but publicly reveals the master registration and requires L1 registry witnesses during zone resolution. A zone-local native registry keeps recipient registration private and lookup within ordinary zone execution.
- Derive IDs from a recipient-bound hash with grinding: allows clients to predict an ID before execution, but adds client work and collision retries in the smaller ID space. Sequential allocation instead provides collision-free IDs without grinding; request salts retain idempotency without granting the registration submitter authority.
- Expose the master ID: avoids encryption but loses recipient concealment.
- Separate memo/no-memo deposit variants: unnecessary; one canonical `hasMemo` bit preserves the distinction without duplicating the queue and API.

# Success Criteria

Independent implementations reproduce the vectors and agree on registration, queue, credit, and refund transitions, and on key-version initialization and retirement. A third party can register an unfunded recipient in a zone, and that recipient can obtain addresses after settlement without an L1 master registration. Ordinary TIP-20 transfers can use issued addresses without constructing an ECIES payload, once the portal admin enables virtual deposits. An operator can rotate to a new key version while old addresses keep working, then retire the old version. Existing ECIES deposits remain compatible, issuance needs no per-address state, confidentiality holds within the stated trust boundary, and operational status distinguishes queued deposits, credited deposits, and claimable refunds.
