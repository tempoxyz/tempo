# TIP-1094: Zone Virtual Deposit Addresses

## Abstract

This TIP lets anyone deposit into a zone with an ordinary TIP-20 transfer on mainnet. The Zone deposit virtual address holds a public zone ID, a key version, and a 6-byte ciphertext. Only the zone can decrypt the ciphertext to determine which address to credit in the zone. 
 
Upon TIP-20 detecting a transfer to a Zone Virtual Deposit Address, the protocol reroutes the transfer to the zone and initiates a zone deposit. The zone then decrypts the ciphertext and processes the deposit if possible. The zone credits the registered recipient, or refunds the sender on Tempo if the deposit fails. 


## Motivation

Zones accept user deposits only through the portal's `deposit()` and `depositEncrypted()` calls ([Zones protocol](https://github.com/tempoxyz/zones/blob/a88c2ac6b6b407225e2861c660806faccc0217df/specs/spec.md#deposits)). Both require the sender to build an ECIES payload that encrypts the recipient and memo to the sequencer's key. Many systems (wallets, exchanges, and payment systems) can send ordinary TIP-20 transfers, but would need integration work to build that payload and call the portal.

This TIP gives each zone recipient the option to have reusable addresses on mainnet that work with a plain transfer and do not reveal who the recipient is. The central idea is to encrypt the recipient's identifier into the address itself. The zone registers the recipient privately and assigns it a 4-byte master ID. The recipient adds a 2-byte user tag to tell senders apart. The zone encrypts those 6 bytes with FF1, a standard NIST cipher whose output is the same size as its input to generate a ciphertext. Only the zone holds the key, so only the zone can recover the master ID and credit the recipient.

Because addresses are computed from the master ID and tag, there is no per-address state. Registration and lookup stay in confidential zone state, so Tempo mainnet never learns that a recipient registered. Each zone has its own registry; receiving in several zones takes one registration in each.


### Alternatives considered

- **Keep only ECIES deposits.** Stronger, randomized, authenticated encryption, but every sender has to integrate it.
- **Store a private address-to-recipient mapping.** Lookup is simpler, but every address becomes durable state that must be stored and recovered. Encrypting the identifier into the address needs no such state.
- **Reuse the L1 TIP-1022 registry.** One registration would serve every zone, but it needs L1 registry witnesses during zone processing, and the registration is public on Tempo, so anyone could link a deposit address's master ID to its recipient.
- **Expose the master ID.** No encryption is needed, but the recipient is no longer hidden.


## Assumptions

| Assumption | If violated |
|---|---|
| `ZoneFactory` assigns stable, nonzero `uint32` zone IDs and resolves each to its registered portal. | Tempo cannot route a deposit address to its zone. |
| Recipient bindings in the zone registry are immutable and covered by the zone execution proof. The native inbox reads them directly from zone state, without an L1 registry read or a cross-contract storage-read extension. | A deposit could be credited to a recipient other than the registered one. |
| Each zone keeps every FF1 key it has initialized, confidentially, for the life of the zone. A zone can have several keys over time; the address's key version byte says which one encrypted it (see [Key versions](#key-versions)). Substituting another key for a version is forbidden. | A lost key can stop zone execution. A substituted key changes the recipient behind every address under that version. |
| The zone keeps executing, its data and witnesses stay available, batches settle, and Tempo processes withdrawals. | Queued deposits are stuck. This TIP adds no forced inclusion and no recovery from permanent zone failure. A parked refund also needs the refund recipient to act, with permission restored. |

# Specification

## Overview

### Terms

| Term | Meaning |
|---|---|
| Deposit address | A 20-byte address in the reserved format: zone ID, magic bytes, key version, ciphertext. |
| Key version | The address byte that selects which zone key encrypts the address. Versions run from `0x01` to `0xFF`. |
| Master ID | A 4-byte number that the zone registry assigns to one recipient. |
| User tag | A 2-byte number the recipient uses to tell its own addresses apart. It does not change where funds go. |
| Recipient | The zone account that a master ID credits. |
| Issuance version | The highest key version whose initialization is settled. New addresses use it. |
| Originator | The Tempo account debited by the transfer. Refunds go to it. |
| Zone operator | The party that runs the zone's sequencer and holds its FF1 keys. |
| Portal admin | The zone portal's admin on Tempo. It controls version retirement. |
| Virtual deposit | The deposit-queue entry that a transfer to a deposit address creates. |
| Minimum accepted version | The lowest key version the portal still accepts. It starts at `0x01` and only rises. |

### Lifecycle

1. The zone operator configures key version 1 on the sequencer. The sequencer initializes it in the first eligible zone block, and it can be used once that block settles.
2. A recipient registers itself in the zone registry and receives a master ID.
3. The recipient asks the zone's authenticated RPC for addresses, one per user tag.
4. A sender transfers a TIP-20 token to an address. Tempo moves the tokens to the zone's portal, and the portal queues a virtual deposit.
5. The zone decrypts the address, looks up the master ID, and credits the recipient. If any check fails, the zone refunds the originator on Tempo.
6. Later, the zone operator can configure a new key version for the sequencer to initialize, and the portal admin can retire old ones.

### Authority boundary

Each step has one party that can authorize it, and the checks that limit them are proof-covered or enforced on Tempo:

| Step | Who authorizes it | What limits them |
|---|---|---|
| Retire key versions | Portal admin | Retirement reverts only new transfers on Tempo; queued deposits still process ([Portal controls](#portal-controls)). |
| Register a recipient | The recipient | The registration is bound to the caller; a call for another account reverts ([Registering a recipient](#registering-a-recipient)). |
| Issue addresses | The recipient, through the authenticated RPC | No public derivation; the payer of a registration cannot issue an address ([Recipient RPC](#recipient-rpc)). |
| Choose the credited recipient | Nobody | The zone's proof-covered execution decrypts and looks up the recipient; the sequencer has no input ([Processing in the zone](#processing-in-the-zone)). |
| Reject a deposit | The token's TIP-403 policy and the recipient's TIP-1028 receive policy, checked in the zone, and the sequencer via the `rejected` flag | A rejection is a public refund on Tempo. The sequencer can reject a deposit but can't redirect it. |

The last row is the boundary that matters most. A refund is public, so a token's policy controller can potentially learn who owns an address by blocking candidates and watching which deposits come back. Given that zones will presumably work with trusted issuers, we view this threat as minimal, but provide more details below ([Threat Model](#threat-model)).

### Worked example

Acme wants customer deposits into zone 7. Zone 7's version-1 key is the test key `000102…1f`.

1. Acme sends `registerMaster(acme, salt)` in zone 7 with a fresh random salt. The registry assigns the next free master ID, say 41 (`0x00000029`), and emits `MasterRegistered(acme, 41)`, which only Acme can read. Nothing about this appears on Tempo.
2. After settlement, Acme finds master 41 in its `MasterRegistered` logs and calls `zone_deriveDepositAddresses` for master 41, tag 1. The zone encrypts `00000029 0001` under version 1 and returns `0x00000007fcfcfcfcfcfcfcfcfc015a951fcc7419`. Acme gives this address to its customer Bob.
3. Bob sends 100 OUSD to that address with a plain `transfer`. Tempo sees the reserved format and finds zone 7's portal. It moves 100 OUSD from Bob to the portal and calls `depositVirtual`.
4. Suppose zone 7's deposit fee is 0.10 OUSD (the real fee is the zone's TIP-1171 operational deposit fee). The portal keeps the fee and queues a virtual deposit of 99.90 OUSD. Bob's transaction succeeds. Explorers show Bob → deposit address → portal.
5. Zone 7 processes the deposit. It decrypts the version-1 ciphertext `5a951fcc7419` to master 41, tag 1, and finds Acme in the registry. It mints 99.90 OUSD to Acme in the zone and records "tag 1" privately.
6. Acme reads its `VirtualDepositProcessed` logs from the zone RPC and sees 99.90 OUSD from Bob on tag 1.

If Acme is blocked by OUSD's TIP-403 policy, step 5 fails instead. The zone queues a refund of 99.90 OUSD to Bob. After the batch settles, the portal pays Bob on Tempo, minus its processing fee.

Later, zone 7 rotates to version 2. The same master and tag now give `0x00000007fcfcfcfcfcfcfcfcfc020f43b3cc4c63`, again using the test key. The version-1 address Acme gave Bob keeps working until the admin retires version 1.

### Scope

In scope: TIP-20 `transfer`, `transferFrom`, `transferWithMemo`, `transferFromWithMemo`, and `systemTransferFrom` to deposit addresses; the zone registry; key versions; the recipient RPC.

Out of scope:

- Mints to deposit addresses. They revert.
- Non-TIP-20 assets.
- Binding an address to one token.
- Hiding failed deposits from Tempo observers.
- Forced inclusion and recovery from permanent zone failure.

## Address format

```
[ zoneId: 4 bytes ][ magic: 9 bytes ][ version: 1 byte ][ ciphertext: 6 bytes ]
```

An address is a deposit address if and only if bytes `[4:13]` equal `0xFCFCFCFCFCFCFCFCFC`. `zoneId` is big-endian at `[0:4]`, `version` is at `[13]`, and the ciphertext is at `[14:20]`. Zone ID zero is unregistered.

`version` is the key version. Values `0x01` through `0xFF` each select one zone key (see [Key versions](#key-versions)). Version `0x00` is unsupported and reverts on Tempo.

Every address with the magic bytes is reserved, including version `0x00`. A reserved address MUST NOT receive a literal TIP-20 balance through any recipient-bearing operation, except a payout from a TIP-1034 channel opened before T15 (see [Changes to other components](#changes-to-other-components)).

TIP-1022 uses different magic bytes, `0xFDFDFDFDFDFDFDFDFDFD` at `[4:14]`. Routing never chains the two resolvers.

### Plaintext

The plaintext is 6 bytes: the 4-byte master ID followed by the 2-byte user tag. Every tag from `0x0000` through `0xFFFF` is valid. All 6 bytes are encrypted together, so neither field appears in the address.

Tags select aliases of one recipient registration. Derivation is deterministic for a fixed zone, version, key, master ID, and tag. The same master ID and tag give unrelated ciphertexts under different versions.

The token is not part of the address. The deposited token MUST NOT affect the key, the tweak, or decryption, so every token resolves an address to the same registration. 

### FF1 encryption

Addresses use FF1 with AES-256, as specified in [NIST SP 800-38G](https://csrc.nist.gov/pubs/sp/800/38/g/upd1/final):

| Parameter | Value |
|---|---|
| Key | The zone's 32-byte key for the address's `version` |
| Radix | 2 |
| Numeral-string length | 48 binary digits |
| Tweak | `"TEMPO-ZVDA-v" \|\| decimal(version) \|\| zoneId` |

The tweak is the 12-byte ASCII string `TEMPO-ZVDA-v`, then the version number in decimal ASCII digits without leading zeros, then the 4 big-endian zone ID bytes. For version 1 the tweak is `0x54454D504F2D5A5644412D7631 || zoneId`, which is 17 bytes. For version 10 it is `0x54454D504F2D5A5644412D763130 || zoneId`, which is 18 bytes.

Each plaintext byte expands most-significant bit first, in byte order. The output packs in the same order, and decryption reverses this. Implementations MUST NOT truncate a conventional cipher, hash, or MAC in place of FF1. Every version uses the same FF1 parameters; only the key and the tweak's version digits differ. Conformance vectors are in [Interfaces](#ff1-conformance-vectors).

## Key versions

### Key storage and initialization

FF1 decryption runs inside the native inbox, following the existing native ECIES model. There is no callable decrypt precompile, no cross-contract storage read, and no dependency on the removed `ZoneConfig` contract.

The native inbox at `0x1c00000000000000000000000000000000000001` stores keys by version (layout in [Interfaces](#storage-layouts)). Each version has a 0-or-1 initialized flag. The flag separates an unconfigured version from a configured all-zero key. FF1 has no proof of correct decryption, so every verifier holds the keys: zone full node operators and provers can read them from state. The redacted RPC never serves them.

A key is set by the system-only call `initializeVirtualAddressKey(version, key)`. These rules apply:

1. A zone block MUST NOT contain more than one key-initialization system transaction. If present, it comes immediately after `advanceTempo` and before user transactions. The block witness carries it as an optional `(version, key)` field. Blocks that do not advance Tempo MUST NOT contain it.
2. The block validator and prover MUST bind the witness field to the exact system transaction and enforce its position and system origin. An ordinary call with a claimed sender MUST NOT initialize a key.
3. The first initialization MUST use version `0x01`. Each later one MUST use the highest initialized version plus one.
4. Initialization MUST revert if its calldata is not the canonical ABI encoding of `(version, key)`, including any trailing bytes, or if `version` is `0x00`, out of order, or already initialized. This includes a repeat with the same key.
5. Success stores the key, sets the flag in proof-covered state, and emits `VirtualAddressKeyInitialized(version)`.

Configuring the address keys is part of running a T15 zone, as with the sequencer's other keys. Each key file the sequencer is given names its version. In each block that advances Tempo, the sequencer initializes the lowest configured version that is not yet in state, once the version before it is, right after `advanceTempo`, so at most one version per block. Initialized keys are read from state, so a sequencer only needs keys that are not yet rotated in.

Existing zones start with no initialized version. Initialization cannot rewrite genesis or historical state. It runs after the block's deposit processing, so a new key is first usable at the next `advanceTempo`.

### Key confidentiality

A key is confidential execution state. User-scoped storage and proof queries, transaction and block responses, traces, simulations, logs, and state dumps MUST NOT expose any key, initialization calldata, or decryption input.

Every executing replica holds every initialized key, including RPC-only followers. So does every system that handles initialization, state, or batch witnesses. These systems need not hold the ECIES private key, but they are inside the FF1 confidentiality boundary.

### Rotation

A version's key never changes. Rotation means initializing the next version. Replacing a key in place was rejected because it would change the recipient behind every outstanding address under that version. Each version's key MUST be generated uniformly at random, independently of every other version's key and every other zone's keys. A zone can initialize at most 255 versions in its lifetime.

Operators MUST keep every initialized key, with protected backups, for the life of the zone. A retired version's key is still needed for deposits already queued under it and to re-execute historical blocks. No call clears a key, and an operator cannot change the meaning of an initialized version. Addresses under an initialized version stay valid until the portal admin retires that version.

To rotate, the operator:

1. Generates a new random key and stores protected backups.
2. Configures the key as the next version on the sequencers, which initialize it with the key-initialization system transaction.
3. Waits for the batch containing that block to settle. The new version becomes the issuance version.
4. Tells recipients to reissue addresses. A master ID and tag carry over: the same pair under the new version is a new, unrelated address for the same recipient.
5. Optionally, after recipients migrate, asks the portal admin to call `retireAddressVersionsBelow` on the portal (see [Portal controls](#portal-controls)). Tempo then reverts new transfers to older versions with `AddressVersionRetired(uint8)`.

A leaked key plus one known address-to-recipient link, such as a past payment or a published address, reveals every address of that recipient under that version. The registry stays in confidential zone state, so the key alone does not name recipients. The key's holder can decrypt every address under that version. That reveals each address's master ID and tag, and so which addresses share a master. The holder can also derive every alias of a known master ID under that version. One known binding of a master ID to its recipient, for example from a sponsored registration or a past payment, then links every address under that master to that recipient. Addresses under other versions stay unlinkable without their keys. Rotation cannot undo disclosure of addresses already issued.

## Registering a recipient

### The registry

A native zone registry precompile is deployed at `0x1C00000000000000000000000000000000000005` at the T15 boundary. It is separate from the TIP-1022 registry at `0xFDC0000000000000000000000000000000000000`. The zone registry stores only TIP-1094 master IDs, does not change the L1 registration API, and is never consulted when resolving a TIP-1022 virtual address.

The zone node and the prover MUST execute the same registry implementation. Calls follow the zone's existing direct-call-only precompile rules, transaction admission, and fee metering.

A recipient is registered with `registerMaster`, which takes the recipient and a salt and returns a master ID (see [Interfaces](#zone-registry)). Only the recipient registers itself: `registerMaster` reverts with `Unauthorized()` unless `recipient` is `msg.sender`. A registration submitted for another account would show its submitter whether that account had already registered the salt, from the call's gas and from the sequential IDs assigned around it in the same transaction ([ID allocation](#id-allocation)). A recipient without funds can still register through fee sponsorship where the zone supports it; the sponsor pays the fee but does not submit the call.

A registration does not name a token. A registered master ID accepts any token enabled for deposits in the zone, including tokens enabled later. Registration does not enable a token. It does not bypass the deposit path's canonical-token, initialization, enablement, pause, fee, admission, or recipient-policy checks. Binding a registration to one token, with an optional any-token wildcard, was considered. It narrows the issuer-policy probing attack to one token's policy controller but does not close it, and it adds a token constraint to registration, processing, the RPC, and failure handling.

### Request hash

Clients SHOULD generate the 32-byte salt with a cryptographically secure random generator. The salt identifies a registration request. There is no grinding or proof-of-work check.

```
requestHash = keccak256(abi.encodePacked(
    "TEMPO-ZVDA-MASTER-v1", bytes4(zoneId), recipient, salt
))
```

The domain is the exact ASCII string `TEMPO-ZVDA-MASTER-v1`, with no terminator. Its `-v1` versions the request format and is unrelated to key versions. `zoneId` is the executing zone's configured 4-byte big-endian ID, not a caller-supplied value. `recipient` is exactly 20 bytes and `salt` exactly 32 bytes. Neither `msg.sender` nor transaction order affects `requestHash`; `msg.sender` is only checked against `recipient` before the hash is computed. Because the hash includes the recipient, a copied request cannot redirect a registration.

### ID allocation

The registry assigns IDs in order from `0x00000000` through `0xFFFFFFFF`. A proof-covered `uint64 nextMasterId` starts at zero and can hold the exhausted value `0x100000000` without wrapping. `registerMaster` runs these steps:

1. Revert with `Unauthorized()` if `recipient` is not `msg.sender`.
2. Revert with `InvalidMasterAddress()` if `recipient` is zero, a TIP-20 token address, a TIP-1022 virtual address, or a deposit address.
3. If `requestHash` already has a record, return its ID. Do not advance the counter, write storage, or emit an event.
4. Revert with `MasterIdSpaceExhausted()` if `nextMasterId == 0x100000000`.
5. Assign the 4-byte big-endian value of `nextMasterId`. Store the recipient binding and the request record, then increment the counter. These writes MUST be atomic. Emit `MasterRegistered(recipient, masterId)`.

New IDs depend on execution order. Recipients MUST use the ID the registry assigned, from their `MasterRegistered` logs or a `registerMaster` simulation for themselves, and MUST NOT predict an ID. Deriving IDs from a recipient-bound hash with grinding would let clients predict them, but clients would pay for grinding and retry collisions in the 4-byte space. Copying a request is harmless: it maps to the same ID, bound to the same recipient.

Each master ID binds permanently to one recipient. No call can request, overwrite, delete, rotate, or reassign an ID or its binding. Sequential allocation prevents ID collisions. Several IDs MAY bind to one recipient through different salts; there is no one-ID-per-address or one-ID-per-recipient rule. ID `0x00000000` is valid. An unregistered ID is represented by a zero recipient. IDs are never reused, so a zone has a lifetime limit of 4,294,967,296 registrations. Master IDs are independent of key versions: one ID has aliases under every initialized version.

IDs come from one shared counter, so any account can infer allocation order and the registration count. Deposit addresses expose neither. The counter is also why registration is limited to the recipient: a caller that registers itself, then another `(recipient, salt)` pair, then itself again in one transaction would learn from its own two IDs whether the middle request was new. A repeated request also costs far less gas than a new one. Restricting the caller to its own registrations leaves both signals about the caller alone.

### Registry confidentiality

Registry lookup is internal to native execution and the authenticated issuance service. The precompile has no public getter and no enumeration API. Storage and proof RPCs, traces, receipts, logs, errors, and simulations MUST NOT expose another recipient's registration to an unauthorized user or to Tempo observers. Registration calldata and results are confidential zone data. Implementations MUST NOT publish a registration event or mapping on Tempo. The zone's `MasterRegistered` log is served only to its recipient ([Deriving addresses](#deriving-addresses)).

The native inbox and the prover read the proof-covered mapping internally, without a public getter call or an EVM2 cross-contract storage read. A missing or invalid registry witness invalidates execution. It is not evidence that an ID is unregistered.

A fee sponsor of a registration sees its recipient and salt and may learn the assigned ID. Even with the ID it cannot derive the recipient's addresses or see the recipient's private activity. When the recipient is a contract, a registration shows only that the contract made the call, not that whoever controls it agreed or owns it.

## Issuing addresses

The recipient gets addresses from the authenticated zone RPC (see [Recipient RPC](#recipient-rpc)). Issuance under a version MUST wait until both the registration and that version's key initialization are settled. Issuance uses the highest settled version unless the recipient asks for another. Issuance MUST NOT use a version below the portal's minimum accepted version. No other party can derive a recipient's addresses, including the account that paid for registration.

Clients SHOULD NOT choose user tags at random. With 65,536 tags, random picks repeat long before the space is used up due to the Birthday Paradox. Clients SHOULD allocate tags in order without reuse. Wallets and apps that share a master ID SHOULD coordinate allocation, or use separate master IDs. Encryption hides the order. When a master ID runs out of tags, register another ID instead of wrapping the counter. Rotation does not reset tag allocation: reissuing tag `t` under a new version gives the same customer a new address.

Reusing an address is valid, but it links payments and can make attribution ambiguous.

## Sending to a deposit address

### Routing on Tempo

Tempo intercepts exactly `transfer`, `transferFrom`, `transferWithMemo`, `transferFromWithMemo`, and `systemTransferFrom`. `mint` and `mintWithMemo` to a deposit address MUST revert with the existing TIP-20 `InvalidRecipient()` error. An issuer that wants to fund a deposit address mints to itself and then transfers. Mints are excluded because a failed mint has no sender to refund: handling it would need a new privileged TIP-20 burn of portal escrow that bypasses issuer roles, pauses, and policies. Fee-payment and reward-recipient paths MUST reject deposit addresses instead of queueing.

For a transfer to a deposit address, Tempo MUST:

1. Revert with `UnsupportedAddressVersion(uint8)` if the version is `0x00`. Revert with `ZoneUnregistered(uint32)` if `zoneId` does not resolve to a registered portal.
2. Run the entrypoint's usual balance, pause, allowance, and spending-limit checks. TIP-403 checks the sender where it applies, and checks the portal as the Tempo recipient. TIP-1028 checks the portal using the operation's ordinary originator. A blocked TIP-1028 receive policy reverts the transfer; it does not divert escrow to `ReceivePolicyGuard`.
3. Revert if the amount does not fit the portal's `uint128` amount field.
4. Debit `from` and credit the portal. Never credit the deposit address itself.
5. Call the portal's `depositVirtual`. If it fails, revert the whole transfer, including balance changes, fees, allowances, and events.

The hidden recipient is checked only inside the zone.

The token calls `depositVirtual` exactly once, after crediting the portal, with its own address as `msg.sender`. Only a transfer made directly to the token routes: when another precompile moves the token to a deposit address (for example a fee AMM burn), the token reverts with `InvalidRecipient()`, since the portal would see that precompile as `msg.sender`. A zero-amount transfer to a deposit address reverts with `InvalidAmount()`: `transferFrom` of zero needs no allowance, so it could name any account as the originator. These portal rules are the same for the Solidity portal runtime and the native ZonePortal precompile. The portal derives the token from `msg.sender`. It MUST verify that the caller is an initialized canonical TIP-20 precompile and an enabled token. A user-supplied token parameter or an enabled ERC-20 is not enough. Only native transfer routing can make this call, and routing fixes every argument from the originating transfer. Ordinary contract calls cannot impersonate the token precompile. The call counts toward normal gas accounting and reentrancy protection.

### Portal checks

`depositVirtual` receives the tokens already credited and MUST NOT pull them again. Its `originator` is the debited account. For `transferFrom`, that is the owner, not the spender. `hasMemo` is true only for memo-bearing entrypoints, even when the memo is zero. When `hasMemo` is false, `memo` MUST be zero. One flag replaces separate memo and no-memo deposit types, which would duplicate the queue entry and API. There is no refund-address field: a failed deposit refunds `originator`.

The portal MUST run these checks in order, reverting at the first failure:

1. If `hasMemo` is false, `memo` is zero. Otherwise revert with `InvalidVirtualDeposit()`.
2. The magic bytes and its own zone ID. Otherwise revert with `InvalidVirtualDeposit()`.
3. `version` is nonzero and at least the minimum accepted version. Otherwise revert with `AddressVersionRetired(uint8)`.
4. `originator` is not a zone portal (`0x5AD0…` prefix). Otherwise revert with `InvalidBouncebackRecipient()`. A portal is the originator only when a withdrawal pays out to a deposit address; reverting makes the payout fail on Tempo so the withdrawal bounces back to its fallback recipient, instead of queuing a deposit whose refund no one could claim.
5. The existing deposit checks: portal and token pauses, token enablement, depositor membership, minimum amount, and fees. Depositor membership applies to `originator`, never to the routing call's caller. The existing refund-recipient validation applies to `originator`, which is also the refund recipient. A callback gateway therefore cannot originate a virtual deposit under access control: the gateway exception covers depositors, not refund recipients. All other access rules stay in force.

The fee is TIP-1171's deposit fee, operational plus congestion. A plain transfer cannot pass `maxFee`, so it accepts only the operational fee, like the legacy deposit signatures: while a congestion fee applies, the transfer reverts with `FeeTooHigh` and moves no funds. The one deposit a withdrawal callback may return pays no congestion fee.

### Queue entry

This TIP appends `ZoneVirtual = 2` to the `DepositType` enum. `WithdrawalBounceBack = 0` and the ECIES `Deposit = 1` keep their values. Existing type values and payloads MUST NOT be reinterpreted.

The portal deducts and pays the existing deposit fee. It then builds a `VirtualDeposit` with the net amount and appends exactly one entry:

```
currentDepositQueueHash = keccak256(abi.encode(
    DepositType.ZoneVirtual, virtualDeposit, currentDepositQueueHash
))
```

The portal increments the existing deposit counter and emits `VirtualDepositMade`. The new type changes the inbox's decoder and the execution proof. It does not change queue ordering, hash chaining, numbering, or settlement commitments. Only ECIES deposits consume `DecryptionData` entries; virtual deposits consume none. A virtual deposit's only sequencer input is the `rejected` flag ([Sequencer-side depositor allowlist](#portal-controls)).

### Transfer events

Routing follows TIP-1022's two-hop event convention, with the portal in place of the master. The token emits, in order:

1. `Transfer(from, destination, grossAmount)`
2. `TransferWithMemo(from, destination, grossAmount, memo)`, if the entrypoint has a memo
3. `Transfer(destination, portal, grossAmount)`

These events come before the portal's fee-transfer events and `VirtualDepositMade`. The transfer never credits the deposit address. A revert removes all events. A successful transfer means the deposit is queued, not that the recipient is credited.

## Portal controls

The portal adds one admin-only control, gated like the existing access-policy controls, so it is frozen once the admin abdicates `AccessPolicy`. Virtual deposits are on for every zone from T15; there is no switch that turns them on or off. A deposit to a version with no initialized key is refunded with `KeyUnconfigured` ([Processing in the zone](#processing-in-the-zone)).

**Version retirement.** `retireAddressVersionsBelow(uint8 minimumVersion)` raises the minimum accepted version, which starts at `0x01`. The call MUST revert with `InvalidVersionRetirement(uint8)` unless `minimumVersion` is exactly the current minimum plus one, so each call retires one version and a single mistyped value cannot retire every issued address. After it, `depositVirtual` reverts with `AddressVersionRetired(uint8)` for lower versions. Deposits already queued under a retired version are processed normally. Each call emits `AddressVersionsRetired(uint8)`.

Retirement has no notice delay. It fails on Tempo before funds move. The portal admin SHOULD announce a retirement in advance so recipients can reissue addresses.

**Sequencer-side depositor allowlist.** The sequencer rejects a virtual deposit by setting `rejected` on the queued deposit. The zone refunds `originator`. `rejected` is a field of the per-deposit `QueuedDeposit` entry the sequencer passes to `advanceTempo`, next to the deposit's type and data. It is not part of the deposit hash chain: the inbox still checks each entry's type and data against the portal's queue hash. It is part of the zone block's input, so the execution proof covers it, as it covers `DecryptionData`. The inbox reads it only for virtual entries and ignores it on ECIES deposits and withdrawal bounce-backs. With the allowlist on, the sequencer sets the flag if `originator` isn't listed, or if the recipient it resolves from the parent zone state isn't listed. If the address doesn't resolve to a recipient, only `originator` is checked; the deposit fails in the zone anyway. Portal-enforced depositor membership still applies to `originator`.

## Processing in the zone

The native inbox consumes the authenticated queue in its existing order. The ECIES decoder does not change. A deposit address is not converted into an ECIES payload: each decoder produces a recipient, and both feed the same mint and failure handling. For a virtual deposit, the inbox:

1. Checks the `rejected` flag. If it is set, the inbox refunds `originator` and skips the remaining steps.
2. Checks the magic bytes, a nonzero version, and a matching zone ID.
3. Loads the committed key for that version and decrypts the 6-byte ciphertext.
4. Looks up the master ID in the zone registry, in the execution state at that point.
5. Mints to the recipient through the existing zone mint path: `mint` when `hasMemo` is false, `mintWithMemo` otherwise.

The lookup is covered by the zone state witness, not an L1 registry proof. The inbox MUST NOT cache absence across registrations. A registration executed after this deposit cannot change its result. The inbox MUST NOT reinterpret the ciphertext using the deposited token, or retry resolution against another registration.

The mint runs the ordinary zone recipient checks, including TIP-403 and the TIP-1028 precheck that prevents diverting a deposit into `ReceivePolicyGuard`. A successful virtual deposit credits exactly the registered recipient. The user tag is attribution metadata only.

Tempo-side checks cover the transfer's sender and the portal, not the hidden recipient. Inside the zone, the TIP-1028 precheck and the mint use `ZoneInbox` (`0x1c00000000000000000000000000000000000001`) as the sender, as for existing deposits. A recipient's sender allowlist therefore accepts or rejects the inbox as a whole. It cannot tell individual depositors apart on this path. The zone still checks the recipient's TIP-403 authorization and receive policy before crediting.

Any of these selects the committed failure action (see [Failures and refunds](#failures-and-refunds)): an invalid address encoding, a version with no initialized key at processing time, an unregistered master ID, or a caught recipient or mint rejection. Only the last one has a recipient, so only it emits `VirtualDepositFailed`; the others refund silently, like a rejected ECIES deposit.

An unregistered master ID takes the failure path; processing never registers it. The sequencer can force the failure path with `rejected`, but can't pick a recipient. The flag is ignored on ECIES deposits and withdrawal bounce-backs. A failed mint's partial state MUST be rolled back before the failure is recorded.

Execution-system failures are different. A missing or invalid witness, an inconsistent queue payload, out-of-gas, or a missing key for an initialized version invalidates the system transaction or the batch. Such a failure MUST NOT become a recipient failure or cancel a valid deposit.

After a successful mint or a recorded failure, the inbox advances the deposit queue once. The destination and decoded attribution are recorded only in recipient-authorized zone execution data. Ordinary withdrawals and internal withdrawal bounce-backs keep their existing behavior.

## Failures and refunds

| Deposit | Failure action |
|---|---|
| Existing ECIES deposit | Existing refund to its `tempoRefundRecipient` |
| Virtual deposit | Existing refund to `originator` |

A failed virtual deposit calls the existing inbox-only outbox bounce-back operation with the token, the net amount, and `originator`. After the batch settles, the portal attempts the refund and charges the existing processing fee when it can collect it. It parks undeliverable amounts in its existing refund registry. Membership, token pauses, and receive-policy changes can delay delivery or require a later claim. They never cause a second zone mint or a second bounce-back.

TIP-1028's `ReceivePolicyGuard` cannot hold a failed deposit inside the zone, because its recovery authority exists only on Tempo.

## Recipient RPC

A recipient needs two things from the zone: its deposit addresses, which only the zone can compute because only zone nodes hold the address key, and the outcome of each deposit sent to them. The authenticated zone RPC provides the first with one method, `zone_deriveDepositAddresses`. The second uses the existing private `eth_getLogs` over the inbox's result events. Neither needs an index beyond zone state and logs.

### Authorization

Both use the zone's authenticated redacted RPC and its existing authorization tokens. The caller is the token's account, including through authorized Keychain keys and configurable-account owners. A contract recipient needs one of those to act for it. Deploying a contract or paying for its registration grants no access.

### Deriving addresses

`zone_deriveDepositAddresses` returns one address per requested user tag for a master ID registered to the caller. At most 1024 tags are accepted per call. The node reads the registry and key versions at the zone block the portal last settled (`ZonePortal.blockHash()` as of the latest finalized Tempo block), so a registration or key initialization is usable only once it has settled. The response names that block.

A `null` or absent `version` selects the highest initialized version. Any version that is uninitialized, zero, or below the portal's minimum accepted version is rejected with `-32602`. An unregistered master ID and another recipient's master ID are rejected with the same error, so the method does not reveal registrations. Nodes MUST NOT offer derivation for master IDs the caller does not own. Clients may cache addresses until their version is retired.

A recipient finds its master IDs in its `MasterRegistered(recipient, masterId)` logs, which the registry emits the first time a master ID is assigned and the redacted RPC serves only to `recipient` (topic 1). Recipients MUST take their IDs from these logs, not from a simulation, since allocation depends on execution order. A simulation of `registerMaster` for another recipient reverts like the call itself, so simulations do not confirm another recipient's registrations.

### Deposit results

`VirtualDepositProcessed` and `VirtualDepositFailed` index the resolved recipient `to` first. The redacted RPC serves them through `eth_getLogs`, filters, and receipts only to that recipient, and only when the zone inbox emitted them. The caller filters by topic 0 and its own address in topic 1. Both carry the originator, token, net amount, master ID, and user tag. `VirtualDepositProcessed` also carries the version and memo. The originator is never served them unless it is also the recipient (a self-funded deposit), because they name the recipient behind the address it paid.

A recipient sees a failed deposit only if lookup resolved to it before the failure. Failures that never identified a recipient (sequencer rejections, invalid encodings, unconfigured keys, unregistered master IDs) have a zero `to` and are served to no one. `VirtualDepositFailed` means a refund was enqueued, not that it was delivered on Tempo; the existing refund records track that.

## Changes to other components

- **TIP-1022.** L1 master registration MUST reject deposit addresses. If an older L1 master matches the format, TIP-1022 resolution reverts. The zone registry rejects deposit addresses, zero, TIP-1022 virtual addresses, and token addresses as recipients. Neither resolver forwards into the other.
- **TIP-20 inside a zone.** All seven recipient-bearing entrypoints reject deposit addresses as destinations with `InvalidRecipient()`: the five intercepted on Tempo, plus `mint` and `mintWithMemo`. Withdrawal requests reject a deposit address as `to` with `InvalidWithdrawalRecipient()`, and as fallback recipient with `InvalidFallbackRecipient()`. Refund-recipient fields, reward recipients, and literal policy-subject operations also reject them. Zero is not a valid refund address.
- **TIP-1034.** From T15, channel `open` rejects a deposit address as payee with `InvalidPayee()`. A channel payout is not one of the routed transfer entrypoints, and a deposit address can never submit vouchers, so such a channel could never pay out. Channels opened before T15 are unaffected: their payouts to a payee in the deposit-address format stay literal TIP-20 credits, since such an address had no owner before T15 either.
- **Literal addresses.** Approvals and transaction origination keep literal-address semantics. The reservation does not prove that no account or contract exists at a deposit address. This TIP does not sweep, route, or burn any balance an address held before T15.
- **TIP-1180.** When identity enforcement is on, a virtual deposit is checked like any deposit: from the L1 `originator` to the recipient found in the zone registry, after the lookup and before the mint. A denied deposit is refunded to `originator` with reason `MintFailed`. That refund is public on Tempo, so, like issuer-policy probing, a sender can learn whether its originator is allowed to pay the hidden recipient. The portal keeps the minimum accepted version in its own slot at the end of the portal layout.
- **ECIES deposits.** Unchanged, including the encrypted memo, except that `tempoRefundRecipient` cannot be a deposit address. The portal reverts such a deposit with `InvalidBouncebackRecipient()`, as it does for a TIP-1022 virtual address: a parked refund is claimed by the address it is parked under, which a deposit address can never be.

## Execution budget

Each FF1 decryption costs a fixed `ZVDA_DECRYPT_GAS = 10_000`, independent of the key, plaintext, and ciphertext. Registry storage, existing policy reads, and the mint cost extra.

Registration meters its fixed-size hash, input, and storage operations normally. Key initialization uses ordinary system-call input and storage metering. Tempo routing and queueing use normal native and EVM gas.

A `ZoneVirtual` entry counts as one deposit in TIP-1171's per-block limit. A block of `DEPOSITS_PER_BUCKET` virtual entries, each taking the worst case (decode, decrypt, a successful registry lookup, a failed policy check and mint, then the refund), MUST fit the zone system-transaction budget.

### Storage layouts

Both precompiles declare their state as ordinary fields, so their layout follows the declaration order.

Zone registry precompile:

- slot 0: `mapping(uint32 masterId => address recipient)`
- slot 1: `mapping(bytes32 requestHash => uint64)`, the master ID plus one, or zero when unrecorded
- slot 2: `uint64 nextMasterId`

A new request pays ordinary hash, counter, and new-storage costs. Ordinary fees and zone admission are what limit state growth and ID exhaustion.

Native inbox: the address keys are `mapping(uint8 version => bytes32 key)`, declared after the existing inbox fields. A zero key means the version is not initialized, so `initializeVirtualAddressKey` rejects a zero key.

### RPC methods

```
zone_deriveDepositAddresses({ masterId, userTags, version }, auth)
  -> { zoneBlockHash, version, addresses }
```

`masterId` is 4 bytes of hex data, `userTags` is a list of 1 to 1024 integers in `[0, 65535]`, and `version` is an integer in `[1, 255]`, `null`, or absent; `null` and absent both select the highest initialized version. `addresses` follows the order of `userTags`.

# Threat Model

The most consequential attack is **issuer-policy probing**. A token's TIP-403 policy controller can learn who owns a deposit address. The zone checks the hidden recipient against the token's policy before crediting, and a rejection produces a public refund on Tempo. To test whether address `X` belongs to Carol, the controller blocks Carol, sends a small deposit to `X`, and watches for a refund. Blocking half of a candidate set per probe finds one recipient among `2^k` candidates in `k` probes, for `k` deposit and refund fees.

Any accepted token's controller can probe any deposit address, including through a token the zone accepts after the address was issued. ECIES deposits leak in a weaker way: the controller gets one observation per deposit someone else makes. Deposit addresses let the controller probe whenever it likes. Zones should accept only tokens with trusted issuers and policy controllers. That reduces the risk but does not remove it. Private failure reasons, delays, or fees do not help, because the refund itself is public. Closing the attack needs private failure handling inside the zone, which this TIP does not provide.

The sequencer-side allowlist leaks in a similar way. Anyone can learn whether a known account is listed by sending it an ECIES deposit and watching for a refund; that already holds today. A deposit address adds a new leak: whether its hidden owner is listed right now. The prober cannot change the list, but every listing or delisting is a fresh probe. If an address switches between refunded and credited right after account `X` is listed or delisted, `X` is its owner. When few accounts change at once, this identifies the owner outright. The prober must wait for list changes and pay a deposit and refund fee per probe, so the leak is slower than issuer-policy probing, but it does not need a malicious issuer. Zones that list and delist often should treat deposit-address ownership as visible to anyone willing to pay those fees.

| Actor | Capability and trust | Boundary check and failure consequence |
|---|---|---|
| Tempo observer or depositor | Sees the zone, version, token, amount, sender, address, and memo of every deposit. Trusted with nothing. | FF1 encryption and the confidential registry ([Address format](#address-format), [Registry confidentiality](#registry-confidentiality)). It can link reuse of one address, but not learn its master ID or recipient. |
| Token policy controller | Sets the token's TIP-403 policy, which the zone applies to the hidden recipient. Trusted not to probe recipients. | None. It can identify address owners by probing (above). Zones limit exposure by accepting only trusted tokens. |
| Registering account | Registers itself under salts it chooses and pays for it, or has a fee sponsor pay. Trusted with nothing. | `registerMaster` reverts unless the recipient is the caller, the request hash binds the recipient, and issuance needs the recipient's authorization ([ID allocation](#id-allocation), [Authorization](#authorization)). It can use up IDs and infer allocation order, but cannot register another account, learn whether another account is registered, choose an ID, take over a binding, redirect funds, or issue addresses. |
| Operator, sequencer, and other key holders | Hold every FF1 key and the registry, sequence blocks, and run the RPC. Trusted to keep keys and the registry confidential. | Recipient selection is proof-covered with no sequencer input ([Processing in the zone](#processing-in-the-zone)). A malicious operator can withhold service, disclose keys and mappings, or reject any deposit with `rejected` (refunded to `originator`), but can't change a recipient or a key. |
| Issuance service | Returns addresses to recipients. Trusted to return the requested master's address. | Only authentication of the service. A malicious service can hand out an address for the wrong master; nothing in the address lets the recipient check it. |
| Portal admin | Retires key versions. Trusted to retire versions only after recipients migrate. | Retirement reverts new transfers on Tempo before funds move and leaves queued deposits alone ([Portal controls](#portal-controls)). A careless admin can break issued addresses, but cannot strand queued funds or lower the minimum version again. |

A leaked key reveals the master ID and tag behind every address under that version, past and future. With one known master-ID-to-recipient binding, it links every address under that master to that recipient. A version has no forward secrecy. Rotation limits the exposure to the leaked version (see [Rotation](#rotation)).

The FF1 keys protect privacy. Committed execution protects recipient selection once an address is issued. Apart from the sequencer's `rejected` flag, deleting a local key or withholding a witness cannot legitimately turn a configured address's deposit into a refund. Proof verification and confidential-state handling must keep these cases apart.

Residual risks:

- **Corrupted addresses.** Every 6-byte ciphertext decrypts to some plaintext. With `N` registered master IDs, a random ciphertext under an initialized version resolves to some registered master with probability `N / 2^32`, before recipient checks. A corrupted address can therefore credit the wrong recipient. Including the zone and version in the tweak changes the permutation, but does not authenticate the address. This TIP adds no checksum. FF1 provides confidentiality and invertibility, not authentication. Recipients must distribute addresses through authenticated channels, and senders must keep the complete address.
- **Linkability.** Each version has `2^48` addresses, and each master ID has 65,536 tags per version. Deterministic derivation reveals address reuse. Amounts, timing, public memos, and outside knowledge can also link deposits. Public enumeration of a candidate master's tags would reveal its address set, which is why issuance requires authentication. Keep private attribution out of public memos.
- **ID exhaustion and state growth.** Registration needs no proof of work, so registration fees and zone admission must cover state growth and the permanent 4,294,967,296-registration cap. Wider IDs would not remove this risk. Exhaustion stops new registrations only; existing master IDs keep working.
- **Disclosure by the operator.** A malicious operator or a public export can reveal registry mappings. Registrations and their execution data otherwise share the zone's confidentiality boundary.

# Invariants

1. For a fixed zone, version, and key, FF1 is invertible, and distinct plaintexts have distinct ciphertexts. An initialized key never changes, and versions are initialized in order.
2. A successful intercepted transfer credits the portal and creates exactly one matching queue entry. No TIP-20 operation credits a deposit address, except a payout from a TIP-1034 channel opened before T15; a balance held before T15 stays where it is. A revert undoes the whole transfer. Mints to deposit addresses always revert.
3. A successful zone credit goes to exactly the registered recipient selected by the committed key for the address's version and the authenticated zone state. A registration's caller cannot change its binding or gain issuance authority. Neither the sequencer nor the depositor can change where a refund goes. The sequencer can force the failure path with `rejected`; the zone does not check why.
4. A deposit never both credits the zone and creates a refund. Each queued refund is consumed at most once.
5. Pending deposits, settled zone balances, pending withdrawals and refunds, and parked refunds are separate stages of bridge accounting. Fees leave escrow only when actually paid. Accounting MUST NOT equate the portal's balance with zone supply while messages are in flight.
6. Under the stated liveness assumptions, every virtual deposit ends in a zone credit or a delivered or claimable refund. Invalid recipient data has a finite failure path. Invalid proofs and missing execution data never authorize a failure action.
7. No public output or user-scoped RPC response exposes a key or another recipient's decoded attribution.
8. No new virtual deposit is queued for a version below the minimum accepted version. The minimum accepted version never decreases. Deposits queued before it changed are processed normally.

Tests MUST cover:

- **Encoding:** the conformance vectors for versions 1, 2, and 10; master ID and tag packing; the decimal-version tweak; boundary tags and round trips; version `0x00` rejection and cross-zone routing.
- **Registration:** recipient-bound, zone-separated request hashing without proof of work; ordered, execution-dependent IDs; registration for another account reverting with `Unauthorized()`, directly and through a contract, without assigning an ID; invalid recipients; idempotent copied requests; several salts for one recipient; immutable bindings; atomic counter, request, and recipient writes; the first and last IDs; exhaustion without wraparound, including the 64-bit counter and offset records at `0x100000000` and idempotent retries after exhaustion; missing registry witnesses versus proven absence.
