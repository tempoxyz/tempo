# TIP-1094: Zone Virtual Deposit Addresses

## Abstract

This TIP lets anyone deposit into a zone with an ordinary TIP-20 transfer to a reusable 20-byte address. The address holds a public zone ID, a key version, and a 6-byte ciphertext. Only the zone can decrypt the ciphertext into a master ID and a user tag. Each master ID has 65,536 addresses per key version.

This TIP adds a recipient registry inside each zone, a new deposit type in the existing queue, and routing in TIP-20 transfers. Registration is permissionless and private to the zone. The zone credits the registered recipient, or refunds the sender on Tempo if the deposit fails.

The portal admin must enable the feature. Mints to these addresses revert. Operators rotate keys by adding a key version, and can retire old versions. This TIP does not hide failed deposits: a token issuer can probe who owns an address by blocking candidates and watching for refunds.

## Motivation

Zones accept user deposits only through the portal's `deposit()` and `depositEncrypted()` calls ([Zones protocol](https://github.com/tempoxyz/zones/blob/a88c2ac6b6b407225e2861c660806faccc0217df/specs/spec.md#deposits)). Both require the sender to build an ECIES payload that encrypts the recipient and memo to the sequencer's key. Wallets, exchanges, and payment systems send ordinary TIP-20 transfers, so they cannot deposit into a zone today.

TIP-1022 virtual addresses solve the same problem on Tempo, but the master ID is visible in every address. Anyone can group all payments to one master. That is acceptable on Tempo and defeats the purpose of a private zone.

This TIP gives each zone recipient reusable addresses that work with a plain transfer and do not reveal who the recipient is. The central idea is to encrypt the recipient's identifier into the address itself. The zone registers the recipient privately and assigns it a 4-byte master ID. The recipient adds a 2-byte user tag to tell its customers apart. The zone encrypts those 6 bytes with FF1, a standard cipher whose output is the same size as its input, so the ciphertext fits in a 20-byte address. Only the zone holds the key, so only the zone can recover the master ID and credit the recipient.

Because addresses are computed from the master ID and tag, there is no per-address state. Registration and lookup stay in confidential zone state, so Tempo never learns that a recipient registered. Each zone has its own registry; receiving in several zones takes one registration in each.

The existing ECIES deposit API and its encrypted memo do not change. Deposits through a deposit address have public memos.

### Alternatives considered

- **Keep only ECIES deposits.** ECIES gives stronger, randomized, authenticated encryption. It still needs a payload and a portal call, which ordinary wallets cannot make.
- **Store a private address-to-recipient mapping.** Lookup is simpler, but every address becomes durable state that must be stored and recovered. Encrypting the identifier into the address needs no such state.
- **Reuse the L1 TIP-1022 registry.** One registration would serve every zone. It publishes the registration on Tempo and needs L1 registry witnesses during zone processing.
- **Expose the master ID.** No encryption is needed, but the recipient is no longer hidden.

Alternatives to individual mechanisms are discussed next to the choice they affect.

# Specification

## Overview

### Terms

| Term | Meaning |
|---|---|
| Deposit address | A 20-byte address in the reserved format: zone ID, magic bytes, key version, ciphertext. |
| Key version | The address byte that selects which zone key encrypts the address. Versions run from `0x01` to `0xFF`. |
| Master ID | A 4-byte number that the zone registry assigns to one recipient. |
| User tag | A 2-byte number the recipient uses to tell its own addresses apart. It does not change where funds go. |
| Recipient | The zone account that a master ID credits. |
| Issuance version | The highest key version whose initialization is settled. New addresses use it. |
| Originator | The Tempo account debited by the transfer. Refunds go to it. |
| Virtual deposit | The deposit-queue entry that a transfer to a deposit address creates. |
| Minimum accepted version | The lowest key version the portal still accepts. It starts at `0x01` and only rises. |

### Lifecycle

1. The portal admin enables virtual deposits on the portal.
2. The operator initializes key version 1 in the zone and waits for settlement.
3. Anyone registers a recipient in the zone registry and receives a master ID.
4. The recipient asks the zone's authenticated RPC for addresses, one per user tag.
5. A sender transfers a TIP-20 token to an address. Tempo moves the tokens to the zone's portal, and the portal queues a virtual deposit.
6. The zone decrypts the address, looks up the master ID, and credits the recipient. If any check fails, the zone refunds the originator on Tempo.
7. Later, the operator can initialize a new key version, and the admin can retire old ones.

### Authority boundary

Each step has one party that can authorize it, and the checks that limit them are proof-covered or enforced on Tempo:

| Step | Who authorizes it | What limits them |
|---|---|---|
| Accept virtual deposits at all | Portal admin | Controls only stop new deposits on Tempo; queued deposits still process ([Portal controls](#portal-controls)). |
| Register a recipient | Anyone | The registration is bound to the named recipient and grants the caller nothing ([Registering a recipient](#registering-a-recipient)). |
| Issue addresses | The recipient, through the authenticated RPC | No public derivation; the payer of a registration cannot issue ([Recipient RPC](#recipient-rpc)). |
| Choose the credited recipient | Nobody | The zone's proof-covered execution decrypts and looks up the recipient; the sequencer has no input ([Processing in the zone](#processing-in-the-zone)). |
| Reject a deposit | The token's TIP-403 policy and the recipient's TIP-1028 receive policy, checked in the zone | A rejection is a public refund on Tempo. |

The last row is the boundary that matters most. A refund is public, so a token's policy controller can learn who owns an address by blocking candidates and watching which deposits come back. This TIP does not close that leak ([Threat Model](#threat-model)).

### Worked example

This example is illustrative. Acme wants customer deposits into zone 7. Zone 7's version-1 key is the test key `000102…1f`.

1. Someone sends `registerMaster(acme, salt)` in zone 7 with a fresh random salt. It does not have to be Acme. The registry assigns the next free master ID, say 41 (`0x00000029`). Nothing about this appears on Tempo.
2. After settlement, Acme asks the RPC for master 41, tag 1. The zone encrypts `00000029 0001` under version 1 and returns `0x00000007fcfcfcfcfcfcfcfcfc015a951fcc7419`. Acme gives this address to its customer Bob.
3. Bob sends 100 USDC to that address with a plain `transfer`. USDC sees the reserved format and finds zone 7's portal. It moves 100 USDC from Bob to the portal and calls `depositVirtual`.
4. Suppose zone 7's deposit fee is 0.10 USDC (the real fee is set by the zone's gas rate). The portal keeps the fee and queues a virtual deposit of 99.90 USDC. Bob's transaction succeeds. Explorers show Bob → deposit address → portal.
5. Zone 7 processes the deposit. It decrypts the 6 bytes to master 41, tag 1, and finds Acme in the registry. It mints 99.90 USDC to Acme in the zone and records "tag 1" privately.
6. Acme calls `zone_listDepositResults(41)` and sees 99.90 USDC from Bob on tag 1.

If Acme is blocked by USDC's TIP-403 policy inside the zone, step 5 fails instead. The zone queues a refund of 99.90 USDC to Bob. After the batch settles, the portal pays Bob on Tempo, minus its processing fee.

Later, zone 7 rotates to version 2. The same master and tag now give `0x00000007fcfcfcfcfcfcfcfcfc020f43b3cc4c63`, again using the test key. Bob's old address keeps working until the admin retires version 1.

### Scope

In scope: TIP-20 `transfer`, `transferFrom`, `transferWithMemo`, `transferFromWithMemo`, and `systemTransferFrom` to deposit addresses; the zone registry; key versions; the recipient RPC.

Out of scope:

- Mints to deposit addresses. They revert.
- Non-TIP-20 assets.
- Binding an address to one token.
- Hiding failed deposits from Tempo observers.
- Forced inclusion and recovery from permanent zone failure.

## Address format

```
[ zoneId: 4 bytes ][ magic: 9 bytes ][ version: 1 byte ][ ciphertext: 6 bytes ]
```

An address is a deposit address if and only if bytes `[4:13]` equal `0xFCFCFCFCFCFCFCFCFC`. `zoneId` is big-endian at `[0:4]`, `version` is at `[13]`, and the ciphertext is at `[14:20]`. Zone ID zero is unregistered.

`version` is the key version. Values `0x01` through `0xFF` each select one zone key (see [Key versions](#key-versions)). Version `0x00` is unsupported and reverts on Tempo.

Every address with the magic bytes is reserved, including version `0x00`. A reserved address MUST NOT receive a literal TIP-20 balance through any recipient-bearing operation.

TIP-1022 uses different magic bytes, `0xFDFDFDFDFDFDFDFDFDFD` at `[4:14]`. Routing never chains the two resolvers.

### Plaintext

The plaintext is 6 bytes: the 4-byte master ID followed by the 2-byte user tag. These match TIP-1022's field widths. Every tag from `0x0000` through `0xFFFF` is valid. All 6 bytes are encrypted together, so neither field appears in the address.

Tags select aliases of one recipient registration. They do not select different zone accounts. Derivation is deterministic for a fixed zone, version, key, master ID, and tag. The same master ID and tag give unrelated ciphertexts under different versions.

The token is not part of the address. The deposited token MUST NOT affect the key, the tweak, or decryption, so every token resolves an address to the same registration. Binding the tweak to the token was rejected: a wrong-token payment would decrypt to an unrelated plaintext and could credit another registered master.

### FF1 encryption

Addresses use FF1 with AES-256, as specified in [NIST SP 800-38G](https://csrc.nist.gov/pubs/sp/800/38/g/upd1/final):

| Parameter | Value |
|---|---|
| Key | The zone's 32-byte key for the address's `version` |
| Radix | 2 |
| Numeral-string length | 48 binary digits |
| Tweak | `"TEMPO-ZVDA-v" \|\| decimal(version) \|\| zoneId` |

The tweak is the 12-byte ASCII string `TEMPO-ZVDA-v`, then the version number in decimal ASCII digits without leading zeros, then the 4 big-endian zone ID bytes. For version 1 the tweak is `0x54454D504F2D5A5644412D7631 || zoneId`, which is 17 bytes. For version 10 it is `0x54454D504F2D5A5644412D763130 || zoneId`, which is 18 bytes.

Each plaintext byte expands most-significant bit first, in byte order. The output packs in the same order, and decryption reverses this. Implementations MUST NOT truncate a conventional cipher, hash, or MAC in place of FF1. Every version uses the same FF1 parameters; only the key and the tweak's version digits differ. Conformance vectors are in [Interfaces](#ff1-conformance-vectors).

## Key versions

### Key storage and initialization

FF1 decryption runs inside the native inbox, following the existing native ECIES model. There is no callable decrypt precompile, no cross-contract storage read, and no dependency on the removed `ZoneConfig` contract.

The native inbox at `0x1c00000000000000000000000000000000000001` stores keys by version (layout in [Interfaces](#storage-layouts)). Each version has a 0-or-1 initialized flag. The flag separates an unconfigured version from a configured all-zero key.

A key is set by the system-only call `initializeVirtualAddressKey(version, key)`. These rules apply:

1. A zone block MUST NOT contain more than one key-initialization system transaction. If present, it comes immediately after `advanceTempo` and before user transactions. The block witness carries it as an optional `(version, key)` field. Blocks that do not advance Tempo MUST NOT contain it.
2. The block validator and prover MUST bind the witness field to the exact system transaction and enforce its position and system origin. An ordinary call with a claimed sender MUST NOT initialize a key.
3. The first initialization MUST use version `0x01`. Each later one MUST use the highest initialized version plus one.
4. Initialization MUST revert if `version` is `0x00`, out of order, or already initialized. This includes a repeat with the same key.
5. Success stores the key and sets the flag in proof-covered state.

Existing zones start with no initialized version. Initialization cannot rewrite genesis or historical state. It runs after the block's deposit processing, so a new key is first usable at the next `advanceTempo`.

### Key confidentiality

A key is confidential execution state. User-scoped storage and proof queries, transaction and block responses, traces, simulations, logs, and state dumps MUST NOT expose any key, initialization calldata, or decryption input.

Every executing replica holds every initialized key, including RPC-only followers. So does every system that handles initialization, state, or batch witnesses. These systems need not hold the ECIES private key, but they are inside the FF1 confidentiality boundary.

### Rotation

A version's key never changes. Rotation means initializing the next version. Replacing a key in place was rejected because it would change the recipient behind every outstanding address under that version. Each version's key MUST be generated uniformly at random, independently of every other version's key and every other zone's keys. A zone can initialize at most 255 versions in its lifetime.

Operators MUST keep every initialized key, with protected backups, for the life of the zone. A retired version's key is still needed for deposits already queued under it and to re-execute historical blocks. No call clears a key, and an operator cannot change the meaning of an initialized version. Addresses under an initialized version stay valid until the portal admin retires that version.

To rotate, the operator:

1. Generates a new random key and stores protected backups.
2. Initializes the next version with the key-initialization system transaction.
3. Waits for the batch containing that block to settle. The new version becomes the issuance version.
4. Tells recipients to reissue addresses. A master ID and tag carry over: the same pair under the new version is a new, unrelated address for the same recipient.
5. Optionally, after recipients migrate, calls `retireAddressVersionsBelow` on the portal (see [Portal controls](#portal-controls)). Tempo then reverts new transfers to older versions with `AddressVersionRetired(uint8)`.

A leaked key does not reveal recipients, because the registry stays in confidential zone state. The key's holder can decrypt every address under that version. That reveals each address's master ID and tag, and so which addresses share a master. The holder can also derive every alias of a known master ID under that version. Addresses under other versions stay unlinkable without their keys. Rotation cannot undo disclosure of addresses already issued.

## Registering a recipient

### The registry

A native zone registry precompile activates at `0xFDC0000000000000000000000000000000000000`. TIP-1022 uses that address on Tempo, but no zone precompile uses it today. The zone registry is independent of the L1 registry. Its activation does not enable TIP-1022 forwarding inside the zone or change the L1 registration API.

The zone node and the prover MUST execute the same registry implementation. Calls follow the zone's existing direct-call-only precompile rules, transaction admission, and fee metering.

A recipient is registered with `registerMaster`, which takes the recipient and a salt and returns a master ID (see [Interfaces](#zone-registry)). Registration is permissionless. The caller need not be the recipient, and no recipient signature is needed. Registration gives the caller no authority over the recipient, its funds, or address issuance. A third party can pay for registration before the recipient has any funds. A recipient's own registration transaction may use sponsorship where the zone supports it.

A registration does not name a token. A registered master ID accepts any token enabled for deposits in the zone, including tokens enabled later. Registration does not enable a token. It does not bypass the deposit path's canonical-token, initialization, enablement, pause, fee, admission, or recipient-policy checks. Binding a registration to one token, with an optional any-token wildcard, was considered. It narrows the issuer-policy probing attack to one token's policy controller but does not close it, and it adds a token constraint to registration, processing, the RPC, and failure handling.

### Request hash

Clients SHOULD generate the 32-byte salt with a cryptographically secure random generator. The salt identifies a registration request. There is no grinding or proof-of-work check.

```
requestHash = keccak256(abi.encodePacked(
    "TEMPO-ZVDA-MASTER-v1", bytes4(zoneId), recipient, salt
))
```

The domain is the exact ASCII string `TEMPO-ZVDA-MASTER-v1`, with no terminator. Its `-v1` versions the request format and is unrelated to key versions. `zoneId` is the executing zone's configured 4-byte big-endian ID, not a caller-supplied value. `recipient` is exactly 20 bytes and `salt` exactly 32 bytes. Neither `msg.sender` nor transaction order affects `requestHash`. Because the hash includes the recipient, a copied request cannot redirect a registration.

### ID allocation

The registry assigns IDs in order from `0x00000000` through `0xFFFFFFFF`. A proof-covered `uint64 nextMasterId` starts at zero and can hold the exhausted value `0x100000000` without wrapping. `registerMaster` runs these steps:

1. Revert with `InvalidMasterAddress()` if `recipient` is zero, a TIP-20 token address, a TIP-1022 virtual address, or a deposit address.
2. If `requestHash` already has a record, return its ID. Do not advance the counter or write storage.
3. Revert with `MasterIdSpaceExhausted()` if `nextMasterId == 0x100000000`.
4. Assign the 4-byte big-endian value of `nextMasterId`. Store the recipient binding and the request record, then increment the counter. These writes MUST be atomic.

New IDs depend on execution order. Clients MUST use the returned ID or the recipient RPC and MUST NOT predict an ID. Deriving IDs from a recipient-bound hash with grinding would let clients predict them, but clients would pay for grinding and retry collisions in the 4-byte space. Copying a request is harmless: both submitters get the same ID, bound to the same recipient.

Each master ID binds permanently to one recipient. No call can request, overwrite, delete, rotate, or reassign an ID or its binding. Sequential allocation prevents ID collisions. Several IDs MAY bind to one recipient through different salts; there is no one-ID-per-address or one-ID-per-recipient rule. ID `0x00000000` is valid. An unregistered ID is represented by a zero recipient. IDs are never reused, so a zone has a lifetime limit of 4,294,967,296 registrations. Master IDs are independent of key versions: one ID has aliases under every initialized version.

Submitters can infer allocation order and registration counts from the IDs they receive. Deposit addresses do not expose either.

### Registry confidentiality

Registry lookup is internal to native execution and the authenticated issuance service. The precompile has no public getter and no enumeration API. Storage and proof RPCs, traces, receipts, logs, errors, and simulations MUST NOT expose another recipient's registration to an unauthorized user or to Tempo observers. Registration calldata and results are confidential zone data. Implementations MUST NOT publish a registration event or mapping on Tempo.

The native inbox and the prover read the proof-covered mapping internally, without a public getter call or an EVM2 cross-contract storage read. A missing or invalid registry witness invalidates execution. It is not evidence that an ID is unregistered.

A submitter knows the recipient and the returned ID. That does not let it derive the recipient's addresses or see the recipient's private activity. A registration also does not show that the recipient agreed to it, or that the submitter owns the recipient.

## Issuing addresses

The recipient gets addresses from the authenticated zone RPC (see [Recipient RPC](#recipient-rpc)). Issuance under a version MUST wait until both the registration and that version's key initialization are settled. Issuance uses the issuance version unless the recipient asks for another settled version. Issuance MUST NOT use a version below the portal's minimum accepted version. No other party can derive a recipient's addresses, including the account that paid for registration.

Clients SHOULD NOT choose user tags at random. With 65,536 tags, random picks repeat long before the space is used up. Clients SHOULD allocate tags in order without reuse. Wallets and apps that share a master ID SHOULD coordinate allocation, or use separate master IDs. Encryption hides the order. When a master ID runs out of tags, register another ID instead of wrapping the counter. Rotation does not reset tag allocation: reissuing tag `t` under a new version gives the same customer a new address.

Reusing an address is valid, but it links payments and can make attribution ambiguous.

## Sending to a deposit address

### Routing on Tempo

Tempo intercepts exactly `transfer`, `transferFrom`, `transferWithMemo`, `transferFromWithMemo`, and `systemTransferFrom`. `mint` and `mintWithMemo` to a deposit address MUST revert with the existing TIP-20 `InvalidRecipient()` error. An issuer that wants to fund a deposit address mints to itself and then transfers. Mints are excluded because a failed mint has no sender to refund: handling it would need a new privileged TIP-20 burn of portal escrow that bypasses issuer roles, pauses, and policies. Fee-payment and reward-recipient paths MUST reject deposit addresses instead of queueing.

For a transfer to a deposit address, Tempo MUST:

1. Revert with `UnsupportedAddressVersion(uint8)` if the version is `0x00`. Revert with `ZoneUnregistered(uint32)` if `zoneId` does not resolve to a registered portal.
2. Run the entrypoint's usual balance, pause, allowance, and spending-limit checks. TIP-403 checks the sender where it applies, and checks the portal as the Tempo recipient. TIP-1028 checks the portal using the operation's ordinary originator. A blocked TIP-1028 receive policy reverts the transfer; it does not divert escrow to `ReceivePolicyGuard`.
3. Revert if the amount does not fit the portal's `uint128` amount field.
4. Debit `from` and credit the portal. Never credit the deposit address itself.
5. Call the portal's `depositVirtual`. If it fails, revert the whole transfer, including balance changes, fees, allowances, and events.

The hidden recipient is checked only inside the zone.

The token calls `depositVirtual` exactly once, after crediting the portal, with its own address as `msg.sender`. These portal rules are the same for the Solidity portal runtime and the native ZonePortal precompile. The portal derives the token from `msg.sender`. It MUST verify that the caller is an initialized canonical TIP-20 precompile and an enabled token. A user-supplied token parameter or an enabled ERC-20 is not enough. Only native transfer routing can make this call, and routing fixes every argument from the originating transfer. Ordinary contract calls cannot impersonate the token precompile. The call counts toward normal gas accounting and reentrancy protection.

### Portal checks

`depositVirtual` receives the tokens already credited and MUST NOT pull them again. Its `originator` is the debited account. For `transferFrom`, that is the owner, not the spender. `hasMemo` is true only for memo-bearing entrypoints, even when the memo is zero. When `hasMemo` is false, `memo` MUST be zero. One flag replaces separate memo and no-memo deposit types, which would duplicate the queue entry and API. There is no refund-address field: a failed deposit refunds `originator`.

The portal MUST run these checks in order, reverting at the first failure:

1. The magic bytes and its own zone ID.
2. Virtual deposits are enabled. Otherwise revert with `VirtualDepositsDisabled()`.
3. `version` is at least the minimum accepted version. Otherwise revert with `AddressVersionRetired(uint8)`.
4. If the portal supports TIP-1151 deposit authorizations and enforces them, revert with `DepositAuthorizationRequired()`. A plain transfer cannot carry an authorization.
5. The existing deposit checks: portal and token pauses, token enablement, depositor membership, unprocessed-deposit capacity, minimum amount, and fees. Depositor membership applies to `originator`, never to the routing call's caller. The existing refund-recipient validation applies to `originator`. The existing gateway exception and all other access rules stay in force.

Capacity is measured as `depositCount - lastProcessedDepositNumber`, not per Tempo block. Virtual and ECIES deposits share the existing public limit below `MAX_UNPROCESSED_DEPOSITS`. The reserve for withdrawal-generated deposits and the allowance for one callback-triggered deposit stay as they are. Only accepted batch settlement advances `lastProcessedDepositNumber`; a new Tempo block does not free capacity. Capacity checks and counter updates MUST be atomic with funding, fee payment, and queueing.

### Queue entry

This TIP appends `ZoneVirtual = 2` to the `DepositType` enum. `WithdrawalBounceBack = 0` and the ECIES `Deposit = 1` keep their values. Existing type values and payloads MUST NOT be reinterpreted.

The portal deducts and pays the existing deposit fee. It then builds a `VirtualDeposit` with the net amount and appends exactly one entry:

```
currentDepositQueueHash = keccak256(abi.encode(
    DepositType.ZoneVirtual, virtualDeposit, currentDepositQueueHash
))
```

The portal increments the existing deposit counter and emits `VirtualDepositMade`. The new type changes the inbox's decoder and the execution proof. It does not change queue ordering, hash chaining, numbering, or settlement commitments. Only ECIES deposits consume `DecryptionData` entries; virtual deposits consume none.

### Transfer events

Routing follows TIP-1022's two-hop event convention, with the portal in place of the master. The token emits, in order:

1. `Transfer(from, destination, grossAmount)`
2. `TransferWithMemo(from, destination, grossAmount, memo)`, if the entrypoint has a memo
3. `Transfer(destination, portal, grossAmount)`

These events come before the portal's fee-transfer events and `VirtualDepositMade`. The deposit address never holds a balance. A revert removes all events. A successful transfer means the deposit is queued, not that the recipient is credited.

## Portal controls

The portal adds two admin-only controls, gated like the existing access-policy controls.

**Enable switch.** `setVirtualDepositsEnabled(bool)` turns virtual deposits on or off. They start disabled on every portal. While disabled, `depositVirtual` reverts with `VirtualDepositsDisabled()`, so the transfer reverts on Tempo and no funds move. Disabling affects only new deposits; deposits already queued are processed normally. Each call emits `VirtualDepositsEnabledUpdated(bool)`.

**Version retirement.** `retireAddressVersionsBelow(uint8 minimumVersion)` raises the minimum accepted version, which starts at `0x01`. The call MUST revert with `InvalidVersionRetirement(uint8)` unless `minimumVersion` is greater than the current minimum. After it, `depositVirtual` reverts with `AddressVersionRetired(uint8)` for lower versions. Deposits already queued under a retired version are processed normally. Each call emits `AddressVersionsRetired(uint8)`.

Retirement has no notice delay. The admin can already stop all virtual deposits at once with the enable switch, and both controls fail on Tempo before funds move. Operators SHOULD announce a retirement in advance so recipients can reissue addresses.

**Sequencer-side depositor allowlist.** That allowlist rejects an ECIES deposit by supplying zeroed decryption data. The deposit then takes the failure path. Virtual deposits use no decryption data, and their processing takes no sequencer input. The allowlist therefore cannot reject them. A zone that relies on the sequencer-side allowlist to admit depositors SHOULD NOT enable virtual deposits. Portal-enforced depositor membership still applies to `originator`.

## Processing in the zone

The native inbox consumes the authenticated queue in its existing order. The ECIES decoder does not change. A deposit address is not converted into an ECIES payload: each decoder produces a recipient, and both feed the same mint and failure handling. For a virtual deposit, the inbox:

1. Checks the magic bytes, a nonzero version, and a matching zone ID.
2. Loads the committed key for that version and decrypts the 6-byte ciphertext.
3. Looks up the master ID in the zone registry, in the execution state at that point.
4. Mints to the recipient through the existing zone mint path: `mint` when `hasMemo` is false, `mintWithMemo` otherwise.

The lookup is covered by the zone state witness, not an L1 registry proof. The inbox MUST NOT cache absence across registrations. A registration executed after this deposit cannot change its result. The inbox MUST NOT reinterpret the ciphertext using the deposited token, or retry resolution against another registration.

The mint runs the ordinary zone recipient checks, including TIP-403 and the TIP-1028 precheck that prevents diverting a deposit into `ReceivePolicyGuard`. A successful virtual deposit credits exactly the registered recipient. The user tag is attribution metadata only.

Tempo-side checks cover the transfer's sender and the portal, not the hidden recipient. Inside the zone, the TIP-1028 precheck and the mint use `ZoneInbox` (`0x1c00000000000000000000000000000000000001`) as the sender, as for existing deposits. A recipient's sender allowlist therefore accepts or rejects the inbox as a whole. It cannot tell individual depositors apart on this path. The zone still checks the recipient's TIP-403 authorization and receive policy before crediting.

Any of these selects the committed failure action (see [Failures and refunds](#failures-and-refunds)):

- invalid address encoding;
- a version with no initialized key at processing time (`KeyUnconfigured`);
- an unregistered or invalid master ID;
- a caught recipient or mint rejection.

An unregistered master ID takes the failure path; processing never registers it. There is no sequencer-supplied rejection flag and no recipient override. A failed mint's partial state MUST be rolled back before the failure is recorded.

Execution-system failures are different. A missing or invalid witness, an inconsistent queue payload, out-of-gas, or a missing key for an initialized version invalidates the system transaction or the batch. Such a failure MUST NOT become a recipient failure or cancel a valid deposit.

After a successful mint or a recorded failure, the inbox advances the deposit queue once. The destination and decoded attribution are recorded only in recipient-authorized zone execution data. Ordinary withdrawals and internal withdrawal bounce-backs keep their existing behavior.

## Failures and refunds

| Deposit | Failure action |
|---|---|
| Existing ECIES deposit | Existing refund to its `tempoRefundRecipient` |
| Virtual deposit | Existing refund to `originator` |

A failed virtual deposit calls the existing inbox-only outbox bounce-back operation with the token, the net amount, and `originator`. After the batch settles, the portal attempts the refund and charges the existing processing fee when it can collect it. It parks undeliverable amounts in its existing refund registry. Membership, token pauses, and receive-policy changes can delay delivery or require a later claim. They never cause a second zone mint or a second bounce-back.

TIP-1028's `ReceivePolicyGuard` cannot hold a failed deposit inside the zone, because its recovery authority exists only on Tempo.

## Recipient RPC

The authenticated zone RPC MUST let a recipient find its master IDs, derive addresses, and reconcile processed virtual deposits. The recipient needs neither the registration submitter nor the sender's receipt. The RPC MUST provide these read-only methods (signatures in [Interfaces](#rpc-methods)): `zone_listDepositMasters`, `zone_getDepositMaster`, `zone_deriveDepositAddress`, `zone_listDepositResults`, and `zone_getDepositResult`.

### Authorization

Every method uses the zone's authenticated redacted RPC. Access is scoped to the registered recipient or a delegate authorized to act for it, through the zone's account authorization framework, including authorized Keychain keys. A contract recipient needs recipient-authorized contract or delegate authentication. Deploying a contract or paying for its registration grants no access.

`auth` MUST bind the zone and chain, the method, every supplied parameter, and a nonce or expiry. Listing masters authorizes the recipient account, not a caller-selected master ID. Authorization MUST be checked on every request, including cursor continuations, so a revoked delegate cannot keep reading an earlier snapshot. No user can read another master ID's decoded attribution.

### Snapshots and parameters

Queries MUST use the latest zone state settled by an accepted batch at a finalized Tempo block. `snapshot` holds `zoneBlockNumber`, `zoneBlockHash`, `tempoBlockNumber`, and `tempoBlockHash`; the Tempo fields identify the settlement block. Nodes MUST NOT substitute an unsettled zone head. Listing an owned registration does not need an initialized key.

Parameter rules:

- `masterId` is 4 bytes of hex data, `userTag` is 2 bytes, and `version` is 1 byte or `null`. Any other length is an invalid parameter, never padded or truncated.
- Block numbers, deposit numbers, amounts, and `limit` are Ethereum JSON-RPC hex quantities. `limit` MUST be between 1 and 100.
- `cursor` is `null` for the first page. A continuation cursor is opaque and bound to the authorized recipient, method, master filter, and snapshot. `nextCursor` is `null` on the last page.

Errors:

- A stale or unavailable snapshot returns `-32004`.
- Invalid parameters, or a cursor from another scope, return `-32602`.
- Authentication failures use the existing zone RPC errors.

Responses MUST NOT let a caller tell an unauthorized object from an absent one. An unknown, unsettled, or unauthorized master returns `master: null`, and a result list for it returns an empty page. An inaccessible deposit returns `result: null`. Derivation returns `-32005` for an unavailable or unauthorized master, without revealing its owner. Cursors, counts, and page boundaries MUST NOT reveal another recipient's records.

### Discovering master IDs

`zone_listDepositMasters` returns only IDs bound to the authenticated recipient. That includes registrations another account submitted or sponsored, and every ID the recipient has. Entries are ordered by unsigned master ID. Each appears once, even after repeated registration calls. `zone_getDepositMaster` returns the same entry for one authorized ID.

Registration metadata describes the first successful insertion, not a repeat. `addressVersions` lists versions whose key initialization is settled and that are at or above the portal's minimum accepted version, as of the snapshot. `issuanceVersion` is the highest of them, or `null` if there is none. This metadata does not grant access to the registration transaction's full calldata or receipt, which may involve other recipients. The recipient does not need the salt.

### Deriving addresses

`zone_deriveDepositAddress` returns the address for an authorized master ID and tag. A `null` `version` selects the issuance version. A non-null `version` MUST be one of the master's `addressVersions`; any other value returns `-32602`. The response states the version used. An optional bulk method MUST apply the same authorization, tag, and version rules. Nodes MUST NOT offer public derivation for arbitrary master IDs. Clients may cache addresses until their version is retired.

### Deposit results

Result methods return only processed virtual deposits whose lookup resolved to the authorized recipient at processing time. `zone_listDepositResults` filters by master ID and orders by increasing deposit number. `zone_getDepositResult` looks up one deposit directly.

In a result, `token` is the deposited token and `amount` is the net queued amount after the deposit fee. `outcome` is `Credited` or `RefundEnqueued`. `failureReason` is `null` for a credit and the recorded reason otherwise. `RefundEnqueued` does not mean the refund was delivered or made claimable on Tempo; the existing withdrawal and refund records track those steps.

A recipient can see a failed deposit if lookup resolved to its master ID before the failure. Failures that never identified a recipient stay operator-only: invalid encodings, unconfigured keys, and unregistered master IDs. A later registration MUST NOT expose or reattribute an earlier unresolved deposit. An unprocessed deposit returns `result: null`. No outcome is reported before settled processing.

### Indexes

Nodes MUST keep private, rebuildable indexes of first registrations and processed results. They build them from confidential canonical zone execution and the authenticated Tempo queue. The indexes do not change consensus registry storage or add per-address registration. A node without the needed index or settled history MUST return `-32004`, not an empty result. Raw registry enumeration, storage and proof queries, unrelated receipts, and public logs stay unavailable.

## Changes to other components

- **TIP-1022.** L1 master registration MUST reject deposit addresses. If an older L1 master matches the format, TIP-1022 resolution reverts. The zone registry rejects deposit addresses, zero, TIP-1022 virtual addresses, and token addresses as recipients. Neither resolver forwards into the other.
- **TIP-20 inside a zone.** All seven recipient-bearing entrypoints reject deposit addresses as destinations: the five intercepted on Tempo, plus `mint` and `mintWithMemo`. Withdrawal requests, refund-recipient fields, reward recipients, and literal policy-subject operations also reject them. Zero is not a valid refund address.
- **Literal addresses.** Approvals and transaction origination keep literal-address semantics. The reservation does not prove that no account or contract exists at a deposit address. This TIP does not sweep, route, or burn any balance an address held before activation.
- **ECIES deposits.** Unchanged, including the encrypted memo and the explicit `tempoRefundRecipient`.

## Execution budget

This draft proposes a fixed `ZVDA_DECRYPT_GAS = 10_000` for each FF1 decryption. Registry storage, existing policy reads, and the mint cost extra. The tariff is not benchmarked and MUST be validated or revised before approval. It does not depend on the key, plaintext, or ciphertext.

Registration meters its fixed-size hash, input, and storage operations normally. Key initialization uses ordinary system-call input and storage metering. Tempo routing and queueing use normal native and EVM gas. The deposit fee formula does not change.

Before activation, benchmark the new paths. Confirm that a full queue at `MAX_UNPROCESSED_DEPOSITS` fits the zone system-transaction budget. The worst case mixes ECIES, virtual, and withdrawal bounce-back entries, recipient failures, and pending token enablements. Changing the tariff or capacity requires an explicit protocol parameter change, not operator tuning.

### Storage layouts

Zone registry precompile:

- Recipient: let `R = keccak256("tempo.zvda.masterRegistry")`. The recipient for `bytes4 masterId` is at `keccak256(abi.encode(masterId, R))`. The word has 12 zero high bytes and the 20-byte recipient in its low bytes. The zone state witness covers the slot.
- Request record: let `Q = keccak256("tempo.zvda.registrationIds")`. The record is at `keccak256(abi.encode(requestHash, Q))`. It stores `uint64(uint32(masterId)) + 1` in the low 8 bytes, with zero high bytes. The master ID's 4 bytes are read as an unsigned big-endian integer. Zero means no request. The offset lets both the first and the last ID be stored; the last ID's record is `0x100000000`.
- Counter: `nextMasterId` is in the low 8 bytes of slot `keccak256("tempo.zvda.nextMasterId")`, with zero high bytes.

These three namespaces are reserved against overlap with other precompile state. A new request pays ordinary hash, counter, and new-storage costs. Ordinary fees and zone admission are what limit state growth and ID exhaustion.

Native inbox:

- Keys: let `S = keccak256("tempo.zvda.addressKeys")`. For version `v`, the initialized flag is at `keccak256(abi.encode(uint256(v), uint256(S)))` and the key is in the next slot. These slots are reserved and MUST NOT overlap other inbox state.

# Threat Model

The most consequential attack is **issuer-policy probing**. A token's TIP-403 policy controller can learn who owns a deposit address. The zone checks the hidden recipient against the token's policy before crediting, and a rejection produces a public refund on Tempo. To test whether address `X` belongs to Carol, the controller blocks Carol, sends a small deposit to `X`, and watches for a refund. Blocking half of a candidate set per probe finds one recipient among `2^k` candidates in `k` probes, for `k` deposit and refund fees.

Any accepted token's controller can probe any deposit address, including through a token the zone accepts after the address was issued. ECIES deposits leak in a weaker way: the controller gets one observation per deposit someone else makes. Deposit addresses let the controller probe whenever it likes. Zones should accept only tokens with trusted issuers and policy controllers. That reduces the risk but does not remove it. Private failure reasons, delays, or fees do not help, because the refund itself is public. Closing the attack needs private failure handling inside the zone, which this TIP does not provide.

| Actor | Capability and trust | Boundary check and failure consequence |
|---|---|---|
| Tempo observer or depositor | Sees the zone, version, token, amount, sender, address, and memo of every deposit. Trusted with nothing. | FF1 encryption and the confidential registry ([Address format](#address-format), [Registry confidentiality](#registry-confidentiality)). It can link reuse of one address, but not learn its master ID or recipient. |
| Token policy controller | Sets the token's TIP-403 policy, which the zone applies to the hidden recipient. Trusted not to probe recipients. | None. It can identify address owners by probing (above). Zones limit exposure by accepting only trusted tokens. |
| Registration submitter | Chooses the recipient and salt of its own request and pays for it. Trusted with nothing. | The request hash binds the recipient, and issuance needs the recipient's authorization ([ID allocation](#id-allocation), [Authorization](#authorization)). It can use up IDs and infer allocation order, but cannot choose an ID, take over a binding, redirect funds, or issue addresses. |
| Operator, sequencer, and other key holders | Hold every FF1 key and the registry, sequence blocks, and run the RPC. Trusted to keep keys and the registry confidential. | Recipient selection is proof-covered with no sequencer input ([Processing in the zone](#processing-in-the-zone)). A malicious operator can withhold service or disclose keys and mappings, but cannot change a recipient, change a key, or reject a valid deposit. |
| Issuance service | Returns addresses to recipients. Trusted to return the requested master's address. | Only authentication of the service. A malicious service can hand out an address for the wrong master; nothing in the address lets the recipient check it. |
| Portal admin | Turns virtual deposits on or off and retires key versions. Trusted to retire versions only after recipients migrate. | Both controls revert new transfers on Tempo before funds move and leave queued deposits alone ([Portal controls](#portal-controls)). A careless admin can stop new deposits or break issued addresses, but cannot strand queued funds or lower the minimum version again. |

A leaked key reveals the master ID and tag behind every address under that version, past and future. It does not reveal recipients. A version has no forward secrecy. Rotation limits the exposure to the leaked version (see [Rotation](#rotation)).

The FF1 keys protect privacy. Committed execution protects recipient selection once an address is issued. Deleting a local key or withholding a witness cannot legitimately turn a configured address's deposit into a refund. Proof verification and confidential-state handling must keep these cases apart.

Residual risks:

- **Corrupted addresses.** Every 6-byte ciphertext decrypts to some plaintext. With `N` registered master IDs, a random ciphertext under an initialized version resolves to some registered master with probability `N / 2^32`, before recipient checks. A corrupted address can therefore credit the wrong recipient. Including the zone and version in the tweak changes the permutation, but does not authenticate the address. This TIP adds no checksum. FF1 provides confidentiality and invertibility, not authentication. Recipients must distribute addresses through authenticated channels, and senders must keep the complete address.
- **Linkability.** Each version has `2^48` addresses, and each master ID has 65,536 tags per version. Deterministic derivation reveals address reuse. Amounts, timing, public memos, and outside knowledge can also link deposits. Public enumeration of a candidate master's tags would reveal its address set, which is why issuance requires authentication. Keep private attribution out of public memos.
- **ID exhaustion and state growth.** Registration needs no proof of work, so registration fees and zone admission must cover state growth and the permanent 4,294,967,296-registration cap. Wider IDs would not remove this risk. Exhaustion stops new registrations only; existing master IDs keep working.
- **Disclosure by the operator.** A malicious operator or a public export can reveal registry mappings. Registrations and their execution data otherwise share the zone's confidentiality boundary.

# Invariants

1. For a fixed zone, version, and key, FF1 is invertible, and distinct plaintexts have distinct ciphertexts. An initialized key never changes, and versions are initialized in order.
2. A successful intercepted transfer credits the portal and creates exactly one matching queue entry. No deposit address ever holds a balance. A revert undoes the whole transfer. Mints to deposit addresses always revert.
3. A successful zone credit goes to exactly the registered recipient selected by the committed key for the address's version and the authenticated zone state. A registration's caller cannot change its binding or gain issuance authority. Neither the sequencer nor the depositor can override the failure action.
4. A deposit never both credits the zone and creates a refund. Each queued refund is consumed at most once.
5. Pending deposits, settled zone balances, pending withdrawals and refunds, and parked refunds are separate stages of bridge accounting. Fees leave escrow only when actually paid. Accounting MUST NOT equate the portal's balance with zone supply while messages are in flight.
6. Under the stated liveness assumptions, every virtual deposit ends in a zone credit or a delivered or claimable refund. Invalid recipient data has a finite failure path. Invalid proofs and missing execution data never authorize a failure action.
7. No public output or user-scoped RPC response exposes a key or another recipient's decoded attribution.
8. While virtual deposits are disabled, or for a version below the minimum accepted version, no new virtual deposit is queued. The minimum accepted version never decreases. Deposits queued before either control changed are processed normally.

These are activation requirements. This draft includes no implementation. Tests MUST cover:

- **Encoding:** the conformance vectors for versions 1, 2, and 10; master ID and tag packing; the decimal-version tweak; boundary tags and round trips; version `0x00` rejection and cross-zone routing.
- **Registration:** recipient-bound, zone-separated request hashing without proof of work; ordered, execution-dependent IDs; third-party registration; invalid recipients; idempotent copied requests; several salts for one recipient; immutable bindings; atomic counter, request, and recipient writes; the first and last IDs; exhaustion without wraparound, including the 64-bit counter and offset records at `0x100000000` and idempotent retries after exhaustion; missing registry witnesses versus proven absence.
- **Keys:** in-order, one-time initialization, including a zero test key; out-of-order and repeated initialization; the 255-version limit; unconfigured versus missing-witness behavior, including deposits to a version initialized after they were queued.
- **Issuance and RPC:** settled issuance and registration/deposit ordering; issuance-version selection and explicit-version derivation; denial of issuance to the registration submitter; discovery of sponsored registrations; deduplicated pagination; scoped cursors and delegate revocation; absent versus unauthorized responses; strict field widths for master ID, tag, and version; settled snapshots and index recovery; private attribution of resolved failures; no retroactive attribution after a later registration; sequential tag allocation without wrapping.
- **Routing and queue:** all five intercepted entrypoints and their event order; `mint` and `mintWithMemo` reverting with `InvalidRecipient()`; absent versus zero memos; `transferFrom` refunding the owner; mixed ECIES, virtual, and internal queues, with exact ECIES decryption-data use; the enable switch and raise-only retirement, both reverting on Tempo before funds move and leaving queued deposits alone; `DepositAuthorizationRequired()` under enforced deposit authorization; capacity across several Tempo blocks; the reserved callback and bounce-back admission.
- **Policy and settlement:** token pauses and policy changes; Tempo sender authorization versus hidden-recipient authorization; `ZoneInbox` as the zone-side sender; exactly-once settlement; namespace rejection; confidential outputs; worst-case system gas at the full queue and token-enablement caps.

# Success criteria

- Independent implementations reproduce the vectors. They agree on registration, queueing, credit, refund, key initialization, and retirement.
- A third party can register a recipient that holds no funds. That recipient can get addresses after settlement, with no L1 registration.
- Ordinary TIP-20 transfers reach recipients through deposit addresses, once the portal admin enables them, with no ECIES payload.
- An operator can rotate to a new key version while old addresses keep working, then retire the old version.
- Existing ECIES deposits keep working. Issuance needs no per-address state. Confidentiality holds within the stated trust boundary.
- Operational status distinguishes queued deposits, credited deposits, and claimable refunds.
