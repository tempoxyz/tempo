# TIP-1168: Account-State Signature Verification in SignatureVerifier.verify

## Abstract

From T15, TIP-1020's `verify(account, hash, signature)` answers whether `signature` approves `hash` for `account` under the account's state at call time. It routes by signature type to the primitive-key check with TIP-1113 retirement, `verifyKeychainAdmin` or `verifyConfigurableAccount`. `recover` stays the stateless primitive, equivalent to `ecrecover`. Callers that need a result independent of account state, such as payment channel settlement, MUST use `recover`.

## Motivation

TIP-1020 `verify` only says which key signed. From T14 an account can migrate to a configurable account (TIP-1113). Its original key keeps recovering to the same address, but no longer acts for the account. A contract that treats `verify(account, …)` as the account's approval keeps accepting the retired key, and rejects the owners' configurable account signatures. Getting this right today takes a commitment read and a choice between four `verify*` functions, which every integrator has to know about.

On Ethereum, `ecrecover` says who signed and ERC-1271 says whether an account approves. This TIP gives Tempo the same split in one precompile: `recover` for the first, `verify` for the second.

Alternatives considered:

- **A new `verifyAccount` function.** It leaves `verify` as the obvious name with the less safe meaning.
- **Making `recover` stateful.** It would break the `ecrecover` equivalence and the settlement paths that rely on it.

## Assumptions

- Mainnet traces show three contracts have called `verify`. Their maintainers can switch to `recover(hash, signature) == signer` before T15 where they need a stateless check.
- TIP-1113 retirement, TIP-1137 keychain admin rules and TIP-1107 configurable account verification are active from T14, so T15 only routes to existing checks.

# Specification

## Overview

`verify` keeps its selector and arguments. Before T15 its behavior is unchanged: it returns whether a primitive signature recovers to `account`. From T15 it reads `account`'s current state, as `verifyKeychain`, `verifyKeychainAdmin` and `verifyConfigurableAccount` already do.

## Mechanics

From T15, `verify(account, hash, signature)` decodes `signature` as a Tempo signature and routes by its type:

| Signature | Result |
|---|---|
| Primitive (secp256k1, P256, WebAuthn) | `true` only when it recovers to `account` and `account` has no configuration commitment |
| Keychain (`0x03`, `0x04`) | The result of `verifyKeychainAdmin(account, hash, signature)` |
| Configurable account (`0x05`) | The result of `verifyConfigurableAccount(account, hash, signature)` |

- A valid signature that doesn't approve for `account` returns `false`.
- A malformed signature reverts with `InvalidFormat()`. A routed call reverts where the function it routes to would.
- Gas is the gas of the routed check. A primitive signature that recovers to `account` adds the commitment read of `account` under the normal account-access schedule.
- Like `verifyConfigurableAccount`, `verify` calldata isn't held to the primitive-signature size cap. The signature decoder bounds it.
- Ordinary access keys don't approve for the account. From T14, `verifyKeychainAdmin` accepts only the account's own non-retired key (TIP-1137).
- State is read at call time, including earlier changes in the same transaction.

From T15, TIP-1020's invariants SV6 and SV7 apply to `recover` only. `verify` accepts keychain and configurable account signatures as above.

## Interfaces

```solidity
interface ISignatureVerifier {
    /// @notice Verifies whether a Tempo signature approves a hash for an account.
    /// @param account Before T15, the expected signer. From T15, the account expected to approve hash.
    /// @param hash The message hash that was signed
    /// @param signature Before T15, a primitive signature. From T15, a primitive, keychain or
    /// configurable account signature.
    /// @return True if the signature approves hash for account, false otherwise.
    /// Reverts with InvalidFormat() for a malformed signature, and where the routed check reverts.
    function verify(address account, bytes32 hash, bytes calldata signature) external view returns (bool);
}
```

No new errors or events.

# Compatibility

| Integration | What changes |
|---|---|
| Contracts calling `verify` for account approval | No change needed. From T15, a migrated account's original key is rejected and its owners' configurable account signatures are accepted. |
| Contracts calling `verify` for a stateless signer check | Switch to `recover(hash, signature) == signer` before T15, or the result can flip when the signer migrates. |
| Payment channel vouchers ([TIP-1034](./tip-1034.md)) | Settlement uses `recover`. The reference implementation moves from `verify` to `recover`. |
| `recover`, `verifyKeychain`, `verifyKeychainAdmin`, `verifyConfigurableAccount` | Unchanged. |
| SDKs and docs | Document `verify` as the default check of account approval, and `recover` as the `ecrecover` equivalent. |

# Observability

N/A. `verify` is a view function. Its result for a block is reproducible from state at that block.

# Threat Model

The main risk is a contract that relies on `verify` staying stateless. A signature that verified when it was made can stop verifying after the signer migrates or revokes an access key. In settlement-style flows, where one party holds a signature to redeem later, the signer could void it. Those flows MUST use `recover`, and this TIP moves the TIP-1034 reference implementation to it.

| Actor | Capability | Boundary |
|---|---|---|
| Retired original key | Signs primitive signatures for a migrated account | From T15, `verify` rejects them. `recover` still returns the address. |
| Configurable account owners | Sign `0x05` approvals | `verify` accepts them under the current configuration. |
| Access key holder | Signs keychain signatures | Only the account's own non-retired key approves, as in `verifyKeychainAdmin`. |
| Integrator relying on stateless `verify` | Holds signatures to redeem later | Must switch to `recover` before T15. |

Before T15, `verify` keeps accepting a retired key, as TIP-1113 already states.

# Invariants

- Before T15, `verify` returns exactly what it returned under TIP-1020.
- From T15, for every account with a nonzero commitment, `verify` with that account's original-key primitive signature returns `false`.
- From T15, for every primitive signature, `verify` returns `true` only if it recovers to `account` and `account` has no commitment.
- From T15, for every keychain or configurable account signature, `verify` returns the same result as, or reverts like, `verifyKeychainAdmin` or `verifyConfigurableAccount`.
- `recover`'s result never depends on account state.

Tests must cover `verify` at T14 and T15 with a retired original key, a configurable account signature for its own and another account, an ordinary access key, a malformed signature, and a configurable account signature beyond the primitive-signature size cap.
