# TIP-1168: Account-State Signature Verification in SignatureVerifier.verify

## Abstract

From T15, this TIP makes TIP-1020's `verify(account, hash, signature)` the one call that checks whether an account approves a hash. It accepts every Tempo signature type and reads the account's current state. A migrated account's retired original key stops passing, and its owners' signatures start passing. `recover` stays stateless, the `ecrecover` equivalent, for callers that must not depend on account state.

## Motivation

Terms from earlier TIPs:

| Term | Meaning |
|---|---|
| SignatureVerifier | TIP-1020's precompile. `recover(hash, signature)` returns the signer. `verify(account, hash, signature)` returns whether the signer is `account`. |
| Primitive signature | A secp256k1, P256 or WebAuthn signature, the only kinds TIP-1020 accepts. |
| Keychain signature | Type `0x03` or `0x04`: wraps a signature by the account's own key or by an access key it registered. TIP-1020 rejects these. |
| Configurable account | An account controlled by weighted owners and an approval threshold (TIP-1107). Its signatures, type `0x05`, carry owner approvals. |
| Commitment | The stored hash of an account's configuration. Zero means an ordinary account (TIP-1113). |
| Retired key | An account's original key, once its commitment is nonzero. |
| Stateful checks | `verifyKeychain`, `verifyKeychainAdmin` and `verifyConfigurableAccount`, added after TIP-1020. They read account state. |
| T14, T15 | Network upgrades. Configurable accounts activate at T14, this TIP at T15. |

From T14, an account can migrate to a configurable account (TIP-1113). Its original key still recovers to the account's address. That key no longer acts for the account.

Today `verify` only compares the recovered key with `account`. A contract that treats `verify(account, …)` as the account's approval therefore:

- accepts the retired original key;
- rejects the owners' configurable account signatures.

A correct check today takes a commitment read and a choice between `verify` and the three stateful checks. Ethereum splits the two questions: `ecrecover` says who signed, and ERC-1271 says whether an account approves. This TIP gives Tempo the same split, with `recover` and `verify`.

Alternatives considered:

- **A new `verifyAccount` function.** It would leave the obvious name, `verify`, with the unsafe meaning.
- **A stateful `recover`.** It would break `ecrecover` equivalence and the settlement flows that rely on it.

## Assumptions

- Three contracts have called `verify` on mainnet. Those that need a stateless check can switch to `recover(hash, signature) == signer` before T15.
- The checks `verify` routes to are active from T14 (TIP-1107, TIP-1113, TIP-1137).

# Specification

## Overview

`verify` keeps its selector. Before T15 it is unchanged.

From T15, `verify` reads `account`'s state at call time, like `verifyKeychain`, `verifyKeychainAdmin` and `verifyConfigurableAccount`. It decodes the signature, routes it by type to one existing check, and returns that check's result. `recover` never reads state.

## Mechanics

### Routing

From T15, `verify` decodes `signature` and routes by type:

- **Primitive** (secp256k1, P256, WebAuthn): `true` only if it recovers to `account` and `account` has no configuration commitment.
- **Keychain** (`0x03`, `0x04`): same result as `verifyKeychainAdmin`. Only the account's own non-retired key approves, never an ordinary access key.
- **Configurable account** (`0x05`): same result as `verifyConfigurableAccount`.

From T15, TIP-1020 invariants SV6 (type-byte disambiguation) and SV7 (keychain rejection) apply to `recover` only.

### Results and failures

- A valid signature that doesn't approve for `account` returns `false`.
- A malformed signature reverts with `InvalidFormat()`.
- A routed check reverts where it would on its own.

### Gas and calldata

- Gas is the routed check's. A primitive signature that recovers to `account` adds one commitment read.
- Calldata isn't held to the primitive-signature size cap. The decoder bounds it.

## Interfaces

No new selectors, errors or events. `verify`'s first parameter is renamed from `signer` to `account`.

```solidity
function verify(address account, bytes32 hash, bytes calldata signature) external view returns (bool);
```

# Compatibility

`verify` has no meaningful production usage yet: three contracts have called it on mainnet.

| Integration | What changes |
|---|---|
| `verify` used as account approval | Nothing to do. From T15 retired keys fail and owner signatures pass. |
| `verify` used as a stateless signer check | Switch to `recover(hash, signature) == signer` before T15. |
| Payment channel vouchers ([TIP-1034](./tip-1034.md)) | Use `recover`. The reference implementation switches. |
| `recover` and the other `verify*` functions | Unchanged. |

# Observability

N/A: `verify` is a view function, reproducible from state at any block.

# Threat Model

The main risk is a contract that relies on stateless `verify` to redeem signatures later, such as vouchers. After T15, the signer can void them by migrating or revoking a key. Such flows MUST use `recover`.

| Actor | Boundary |
|---|---|
| Retired original key | From T15, `verify` rejects it. `recover` still returns its address. |
| Configurable account owners | `verify` accepts their quorum under the current configuration. |
| Access key holder | Rejected unless it is the account's own non-retired key. |

# Invariants

- Before T15, `verify` returns what it returned under TIP-1020.
- From T15, `verify` never returns `true` for a primitive signature of an account with a nonzero commitment.
- From T15, keychain and configurable account signatures give the same result, or revert, as the check they route to.
- `recover` never depends on account state.

Tests cover `verify` at T14 and T15 with a retired original key, a configurable account signature for its own and another account, an ordinary access key, a malformed signature, and a signature beyond the size cap.
