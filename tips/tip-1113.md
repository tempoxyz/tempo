# TIP-1113: Account Migration and Original-Key Retirement

## Abstract

This TIP lets an existing account become a configurable account at its current address, through one transaction signed by its original key. Balances, approvals, roles and access keys stay in place.

From then on, Tempo's protocol rejects the original key as the account's authority, including for transactions, TIP-20 `permit` and keychain checks. The key still works where the protocol doesn't reach: other chains, zones, and applications that call `ecrecover` without checking for code. It can also settle vouchers on [payment channels](./tip-1034.md) it funded before migration.

## Motivation

[TIP-1107](./tip-1107.md) enables configurable accounts for new accounts on Tempo. An existing account can't get that without a new address, and much of what an account holds is tied to its address. As an example, consider Bob. His account holds his balances, open approvals to several applications and an issuer role on a TIP-20 token. It also has an access key on his laptop and a funded payment channel, and his customers pay to it. To get a 2-of-3 under TIP-1107, he would have to move all of that to a new address and tell everyone who pays him.

Migration allows him to upgrade to a configurable account while keeping the address, and additionally retires his existing key. When migration writes the account's commitment (TIP-1107's stored hash of the configuration), that same write retires the original key. This is a stronger protocol level guarantee than, e.g., EIP-7702 delegation: under that, Bob could run wallet code, but his original key could always change or remove the delegation.

# Specification

## Overview

**Terms.** These add to the terms in [TIP-1107](./tip-1107.md#overview).

| Term | Meaning |
|---|---|
| Configurable account | An account controlled by weighted owners and a threshold, as defined in TIP-1107. |
| Commitment | The 32-byte hash of the account's current configuration, stored in its account leaf. Zero means the account isn't configurable. |
| Account code marker | The one byte of code, `0xef`, that a configurable account carries so contracts route its signatures to ERC-1271. |
| Original-key authority | Accepting the original key's ordinary signature (secp256k1, P256 or WebAuthn) for the account, without a configurable-account signature around it. |
| Retired | An account's original key is retired once its commitment is nonzero. |

**Lifecycle.**

1. **Prepare.** Bob picks three owners, each with weight 1: his phone passkey, his laptop passkey and a hardware key. He picks a threshold of 2. His wallet checks that the account has no code, no EIP-7702 delegation and no commitment.
2. **Sign.** Bob's original key signs a transaction whose only call is `upgradeAccount(2, owners)`.
3. **Migrate.** The protocol builds a version-1 configuration, stores its commitment, installs the account code marker and emits `AccountUpgraded`. Version 0 belongs to derived addresses.
4. **Afterwards.** Bob's direct transactions need two of his owners. His original key is retired on Tempo:

| Bob's original key… | After migration |
|---|---|
| Signs a transaction as the account | Rejected with `RootKeyRetired` |
| Signs a TIP-20 `permit`, including one signed before migration | Rejected |
| Signs vouchers on the channel he funded earlier | Still accepted against that deposit |
| Opens a channel, or tops one up, as voucher signer | Rejected |
| Controls the address on another chain or a zone | Yes |
| Signs a Permit2 signature transfer | Rejected. Permit2 sees the account's code and checks the signature through ERC-1271 |
| Signs for an application that calls `ecrecover` without checking for code | Accepted by that application |

His address, balances, storage, approvals, issuer role, nonce state and laptop access key are unchanged. Migration does not revoke access keys.

## Mechanics

### Eligibility

- The transaction's only top-level call MUST be `upgradeAccount`, with `msg.sender == tx.origin == tx.from`.
- It MUST carry an ordinary (secp256k1, P256 or WebAuthn) outer signature from the original key. Access-key signatures are invalid.
- It MUST NOT carry an authorization list or a `key_authorization`.
- Ordinary fee sponsorship is allowed.
- The account MUST have no code, no EIP-7702 delegation and a zero commitment.

### Installing the configuration

```text
salt   = keccak256("tempo:configurable-account:upgrade" || account)
config = (salt, version = 1, threshold, owners)
```

The domain is raw ASCII and `account` is 20 bytes. The protocol then:

1. Validates the configuration under TIP-1107.
2. Requires a nonzero hash.
3. Stores it as the commitment and installs TIP-1107's [account code marker](./tip-1107.md#account-code).
4. Emits `AccountUpgraded`.

The original key's signature on the calldata is the only approval required. The new owners do not co-sign. A version-1 configuration MAY list the original key as an owner. It then signs inside configurable-account signatures with its configured weight, like any other owner.

| Outcome | Result | Next step |
|---|---|---|
| Success | Commitment, code marker and event remain. Later direct transactions need a configurable-account signature at version 1 or later. The account can't migrate again. | Use the new owners. |
| Call fails | Commitment, marker and event roll back. The original key stays authoritative. Normal fee and nonce rules apply. | Recheck eligibility, configuration and nonce, then resubmit. |

Failures are checked in this order:

1. Not the only call, or an authorization list or `key_authorization` present: `UpgradeMustBeOnlyCall`.
2. Outer signature not an ordinary signature from the original key: `PrimitiveRootRequired`.
3. Account has code or delegation: `AccountHasCode`.
4. Account already has a commitment: `AccountAlreadyConfigurable`.
5. Invalid configuration: `InvalidConfig`.

Gas:

- Ordinary precompile, input and event costs.
- The salt and commitment hashes.
- One account access.
- The zero-to-nonzero commitment write: 250,000 gas, as for registration in TIP-1107.
- TIP-1000's new-account cost when the commitment write creates the sender. That happens when the sender is still empty at the write: zero nonce, zero balance and no code. TIP-20 balances don't count. The cost is charged during execution.
  - With `nonce_key == 0`, or a transaction type without nonce keys, the protocol nonce write has already created the sender, so nothing more is charged.
  - With a 2D or expiring nonce, the sender is still empty, so the cost applies. The `nonce == 0` charge pays for the nonce-key slot and expiring-nonce gas for replay protection, not for the account.
  - Sponsorship doesn't change this.

### Retirement check

From T14, the protocol reads the signer's commitment before accepting original-key authority. A zero commitment changes nothing. If it is nonzero:

- **Transactions.** A sender, `key_authorization` signer or separate fee payer is rejected with `RootKeyRetired(account)`, reading the commitment at the transaction's position in the block.
- **Access keys.** An ordinary inner signature is rejected the same way when the signing key ID has a nonzero commitment. The parent's commitment isn't checked.
- **Authorization lists.** An EIP-7702 or Tempo entry whose authority has a nonzero commitment is skipped, so it never installs or removes delegation.
- **Protocol operations.** TIP-20 `permit`, `verifyKeychain` and `verifyKeychainAdmin` revert with `RootKeyRetired(account)` before changing state. They read the commitment at call time, including earlier changes in the same transaction.
- **Authority helpers.** Boolean helpers return `false`, including where a key ID equals the account. `isAdminKey` and internal admin checks MUST NOT treat `key_id == account` as original-key authority.
- **Payment channels.** See [Payment channel settlement](#payment-channel-settlement).

The check applies only to ordinary signatures. A configurable delegate under TIP-1111 isn't rejected for having a commitment, and authorization-list entries signed with access keys stay skipped.

These keep working: an original key that is also an owner, signing inside a configurable-account signature; `msg.sender` authority from authenticated transactions; and pure signature functions (`ecrecover`, TIP-1020 `recover` and `verify`), which only say who signed. Protocol code that treats their result as account authority MUST apply this check itself.

### Payment channel settlement

[TIP-1034](./tip-1034.md) payment channel `open` and any nonzero `topUp` reject a retired voucher signer: the channel's `authorizedSigner`, or the payer if none is set.

Settlement doesn't check retirement. Otherwise a payer could migrate, void the vouchers the payee already holds, and withdraw the deposit. Settlement instead keeps the channel's fixed signer and payee. A compromised retired key can still sign vouchers, but only against deposits made before migration, only to that channel's payee, and the deposit can't grow because top-ups are rejected. Blocking migration until every channel closes would avoid this exception, but it would need an index of channels by signer and would delay migration.

### Ordering and permanence

- The commitment is read at the transaction's position in the block. A later transaction in the same block can't use authority that an earlier migration retired.
- Pending transactions MUST be revalidated when a commitment changes or the chain reorgs. A cached zero is not proof of authority.
- For derived addresses, registration (TIP-1107) retires the key before the first call runs. Retirement stays even if the calls revert.
- An address that has only received funds still has a zero commitment, so its key is not retired.
- Later owner updates follow TIP-1107. They replace one nonzero commitment with another and retire nothing new. No execution path clears a commitment back to zero, so retirement is permanent.
- Migration writes only TIP-1107's commitment and account code marker. It adds no other state. Commitment reads follow the normal account-access schedule. An already loaded account adds no read charge.

### Access keys

Migration keeps every grant the account made, with its expiry, limits, scopes, spending counters and revocation state. That includes admin grants made before T14, which keep unrestricted spending until revoked ([TIP-1137](https://github.com/tempoxyz/tempo/pull/8204)). If the account is itself a delegate on another account, its grants keep working through its new owners ([TIP-1111](./tip-1111.md#delegates-that-migrate)).

### Cross-chain recovery

This subsection is guidance on how to implement cross-chain recovery for configurable accounts. The underlying problem this looks to solve is that a derived address for a configurable account exists only on Tempo, so funds sent to it on another chain are lost. A wallet that wants recovery on other chains can create the account another way:

1. Generate a fresh secp256k1 key. Its address becomes the account.
2. Immediately, before the address is shared or funded, have that key sign `upgradeAccount`. It installs the real owners and should not include itself. Sponsorship lets this happen before the account has funds.
3. Keep the key offline as a recovery credential, or discard it.

The key is retired on Tempo, but it still controls the address on other EVM chains, so the holder can move mistaken transfers out. It also currently keeps full authority over the address on zones. Applications that call `ecrecover` without checking for code still treat it as the account, and on other chains the address has no code at all. So it is a live credential:

- Don't use the address on other chains. Only recover mistaken transfers, and move them elsewhere.
- Don't sign anything with the key except recovery.
- Don't leave long-standing approvals to applications that call `ecrecover` without checking for code. Approve only what a batch needs and reset it in the same batch.
- Show who holds the key, separately from the account's owners. If the key is discarded, show that the account has no cross-chain recovery.

Accounts with several owners can use the same flow, with the key held by whoever is responsible for cross-chain recovery.

## Interfaces

`upgradeAccount` is added to TIP-1107's configurable-account precompile.

```solidity
interface IConfigurableAccountUpgrade {
    struct ConfigurableAccountOwner {
        address owner;
        uint8 weight;
    }

    /// @notice Migrates msg.sender to a version-1 configuration.
    /// @param threshold The approval threshold.
    /// @param owners The owners, sorted by address.
    /// @return commitment The stored commitment.
    /// @dev Only a direct original-key transaction with this as its sole call may invoke it.
    /// Existing access keys are kept.
    function upgradeAccount(uint8 threshold, ConfigurableAccountOwner[] calldata owners)
        external returns (bytes32 commitment);

    event AccountUpgraded(
        address indexed account,
        bytes32 indexed commitment,
        bytes32 salt,
        uint8 threshold,
        ConfigurableAccountOwner[] owners
    );

    error PrimitiveRootRequired();
    error UpgradeMustBeOnlyCall();
    error AccountAlreadyConfigurable();
    error AccountHasCode();
    error InvalidConfig();
}
```

Added error for the retirement check:

```solidity
error RootKeyRetired(address account);
```

# Compatibility

| Integration | What changes |
|---|---|
| Migration wallets | Follow the migration checklist below. |
| Applications that use `ecrecover` | Migration installs the account code marker, so Permit2 and other verifiers that check for code route the account's signatures to ERC-1271 and reject the original key. Allowances the original key granted before migration, including Permit2 allowances, stay usable by their spenders. Applications that call `ecrecover` without checking for code still accept the key: ERC-2612 permits on non-TIP-20 tokens, signed orders, and SIWE or [TIP-1053](./tip-1053.md) sign-in, which only checks that the recovered signer equals the expected account. They should check `getConfigCommitment` before trusting a recovered address. |
| Token approvals | There is no configurable-account permit. Use a quorum-signed `approve`, optionally batched with the application call. Permit2 signature flows work through ERC-1271, with owners signing the configurable-account digest. |
| Sponsors | A migrated address can no longer sponsor other accounts' fees. |
| Payment channels | Existing deposits stay redeemable. Top-ups and new channels need a non-retired signer. If the key may be compromised, close channels it funded. |
| Other configurable accounts | If the original key is an owner of another account, it keeps its weight there until that account removes it. |
| Error handling | Tell `RootKeyRetired` apart from an invalid signature. A zero commitment doesn't say whether an account is an ordinary account or an unregistered derived address. |
| Zones | The original key keeps authority over the address's zone funds until zones support configurable accounts. Withdraw zone funds before discarding the key. |

Migration checklist for wallets:

1. Show the new owners, the threshold and every access key that will survive, including unrestricted admin grants made before T14. Say so if the list may be incomplete.
2. Check locally that the new owners can reach the threshold.
3. If the key may be compromised, first move zone funds and revoke allowances granted to Permit2 or to applications that call `ecrecover` without checking for code. Migration can't include other calls.
4. Migrate.
5. With the new quorum, revoke unwanted access keys, then list active grants again at finalized state. The original key could have added keys before migration landed.
6. Confirm the commitment at finalized state, and keep the configuration from `AccountUpgraded`.

# Observability

| Event | Fields | Question it answers |
|---|---|---|
| `AccountUpgraded` (MUST be emitted on successful migration) | `account` (indexed), `commitment` (indexed), `salt`, `threshold`, `owners` | Which account migrated, and to what configuration? |

A failed migration leaves no event and no commitment. If no event appears, the migration may still be pending, or it may have failed. Check the transaction result and the current commitment before retrying.

This TIP adds no other event. Retirement is visible as a nonzero commitment at the chosen block. `RootKeyRetired(account)` identifies the retired account. It doesn't record the role in which the key was used.

# Threat Model

This threat model covers the original key: what it can do before migration, and what it keeps afterwards.

Some risks are accepted by the design. Retirement covers only Tempo's protocol, not applications that skip the code check, other chains or zones. Migration doesn't revoke access keys, so recovery from a compromised key must revoke them explicitly.

The most consequential attack is a compromised original key racing the owner's migration. Before migration lands, the attacker can submit a competing `upgradeAccount` with their own owners, or add access keys that survive migration. The protocol can't tell the two apart, so migration protects only an account whose key is still trusted when it migrates.

| Actor | Capability and trust | Boundary check and failure consequence |
|---|---|---|
| Original key before migration | Controls the account. Trusted to migrate as the user intends. | [Eligibility](#eligibility) and the sole-call rule. A compromised key can install other owners, or add grants that survive. |
| Original key after migration | Controls funded-channel vouchers, other chains, zones, and applications that call `ecrecover` without checking for code. Trusted to stay offline. | The [retirement check](#retirement-check) covers Tempo's protocol only. A compromised key can drain those channels to their fixed payees, the zone funds, and allowances in applications that skip the code check. |
| Migration wallet | Shows the owners, threshold and grants. Trusted to display them accurately. | The key's signature binds the real calldata. A misleading wallet installs an unintended quorum. |
| Relayer | Submits signatures made before migration. Not trusted. | Signatures are checked against current state, so old ones fail, except channel vouchers. |
| Channel payee | Holds a claim on a deposit. | Settlement keeps the fixed signer and payee, so migration can't void the claim. |

# Invariants

These hold in every state reachable from T14 activation through valid transactions.

- For every successful migration, the account afterwards has a nonzero version-1 commitment and the account code marker, and any later `upgradeAccount` for it fails.
- For every failed migration, the commitment, marker and event roll back, the original key stays authoritative, and normal fee and nonce effects apply.
- For every migration, the address, balances, storage, nonce state and all outgoing grants with their counters are unchanged, including revoked, expired and pre-T14 admin grants.
- For every account, once its commitment is nonzero it never returns to zero.
- For every account with a nonzero commitment, its original key's ordinary signature fails in every case of the [retirement check](#retirement-check) except channel settlement, whether or not the key is also an owner.
- For every signature created before retirement and submitted afterwards, the retirement check applies, except for channel vouchers.
- For every transaction later in the same block than a migration, the retired authority is rejected.
- For every skipped authorization-list entry, delegation for the retired account is unchanged.
- For every voucher settlement, the result doesn't depend on the signer's commitment, and a retired signer's channel deposit never increases.
- For every configurable parent, its own commitment doesn't block its active delegates. The check applies to the signing key ID.
- For every migration that creates the sender, TIP-1000's new-account cost is charged exactly once, under every nonce type and with or without sponsorship. A nonempty sender pays none.
