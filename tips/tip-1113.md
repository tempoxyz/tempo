# TIP-1113: Account Migration and Original-Key Retirement

## Abstract

This TIP lets an existing account become a configurable account at its current address, through one transaction signed by its original key. Balances, approvals, roles and access keys stay in place.

From then on, Tempo's protocol rejects the original key as the account's authority, including for transactions, TIP-20 `permit` and keychain checks. The key still works where the protocol doesn't reach: other chains, zones, and applications that call `ecrecover` without checking for code. It can also settle vouchers on channels it funded before migration.

## Motivation

[TIP-1107](./tip-1107.md) gives new accounts owners that can change. An existing account can't get that without a new address, and much of what an account holds is tied to its address. Consider Bob. His account holds his balances, open approvals to several applications and an issuer role on a TIP-20 token. It also has an access key on his laptop and a funded payment channel, and his customers pay to it. To get a 2-of-3 under TIP-1107, he would have to move all of that to a new address and tell everyone who pays him.

Migration keeps the address, but installing owners is only half the job. If Bob's original key could still sign on its own, the new owners would protect nothing. So when migration writes the account's commitment (TIP-1107's stored hash of the configuration), that same write retires the original key.

The same retirement rule applies to new accounts. If anyone held a key for a derived address (see TIP-1107's Assumptions), registration would retire it.

Alternatives considered:

- **EIP-7702 delegation.** Bob could run wallet code, but his original key could always change or remove the delegation.
- **Blocking migration until every channel closes.** This would avoid the channel-voucher exception below, but needs an index of channels by signer and delays migration.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| TIP-1107's commitment can never be cleared by execution. | Clearing it would restore the original key's authority. |
| TIP-1107 and TIP-1111 activate in the same fork as this TIP. | A migrated account could lack signing, rotation or access-key support, or keep an unretired key. |
| Applications that check signatures independently of the protocol decide for themselves whether to honour retirement. | They may keep accepting the original key (see Compatibility). |

# Specification

## Overview

**Terms.** This TIP uses TIP-1107's terms. **Original-key authority** means accepting the original key's ordinary signature (secp256k1, P256 or WebAuthn) for the account, without a configurable-account signature around it. An account's original key is **retired** once its commitment is nonzero.

**Who authorises what.** The original key authorises the migration itself. After that, the installed quorum authorises everything, as in TIP-1107. The trust boundary is the moment the migration transaction executes. Before it, the original key is fully trusted. After it, the key has no protocol authority on Tempo.

**Lifecycle.** This example is illustrative.

1. **Prepare.** Bob picks three owners, each with weight 1: his phone passkey, his laptop passkey and a hardware key. He picks a threshold of 2. His wallet checks that the account has no code, no EIP-7702 delegation and no commitment.
2. **Sign.** Bob's original key signs a transaction whose only call is `upgradeAccount(2, owners)`.
3. **Migrate.** The protocol builds a version-1 configuration, stores its commitment, installs the account code marker and emits `AccountUpgraded`. Version 0 belongs to derived addresses.
4. **Afterwards.** Bob's direct transactions need two of his owners. His original key is retired on Tempo:

| Bob's original key… | After migration |
|---|---|
| Signs a transaction as the account | Rejected with `RootKeyRetired` |
| Signs a TIP-20 `permit`, including one signed before migration | Rejected |
| Signs vouchers on the channel he funded earlier | Still accepted against that deposit |
| Opens a channel, or tops one up, as voucher signer | Rejected |
| Controls the address on another chain or a zone | Yes |
| Signs a Permit2 signature transfer | Rejected. Permit2 sees the account's code and checks the signature through ERC-1271 |
| Signs for an application that calls `ecrecover` without checking for code | Accepted by that application |

His address, balances, storage, approvals, issuer role, nonce state and laptop access key are unchanged. Migration does not revoke access keys.

**Scope.** This TIP defines migration and the retirement check. Later owner updates follow TIP-1107. They replace one nonzero commitment with another and retire nothing new.

## Mechanics

### Eligibility

- The transaction's only top-level call MUST be `upgradeAccount`, with `msg.sender == tx.origin == tx.from`.
- It MUST carry an ordinary (secp256k1, P256 or WebAuthn) outer signature from the original key. Access-key signatures are invalid.
- It MUST NOT carry an authorization list or a `key_authorization`. A single call makes it clear what the key approved, and stops a migration from hiding other delegation changes.
- Ordinary fee sponsorship is allowed.
- The account MUST have no code, no EIP-7702 delegation and a zero commitment.

### Installing the configuration

```text
salt   = keccak256("tempo:configurable-account:upgrade" || account)
config = (salt, version = 1, threshold, owners)
```

The domain is raw ASCII and `account` is 20 bytes. The protocol then:

1. Validates the configuration under TIP-1107.
2. Requires a nonzero hash.
3. Stores it as the commitment and installs TIP-1107's [account code marker](./tip-1107.md#account-code).
4. Emits `AccountUpgraded`.

The original key's signature on the calldata is the only approval required. The new owners do not co-sign. A version-1 configuration MAY list the original key as an owner. It then signs inside configurable-account signatures with its configured weight, like any other owner.

| Outcome | Result | Next step |
|---|---|---|
| Success | Commitment, code marker and event remain. Later direct transactions need a configurable-account signature at version 1 or later. The account can't migrate again. | Use the new owners. |
| Call fails | Commitment, marker and event roll back. The original key stays authoritative. Normal fee and nonce rules apply. | Recheck eligibility, configuration and nonce, then resubmit. |

Failures are checked in this order:

1. Not the only call, or an authorization list or `key_authorization` present: `UpgradeMustBeOnlyCall`.
2. Outer signature not an ordinary signature from the original key: `PrimitiveRootRequired`.
3. Account has code or delegation: `AccountHasCode`.
4. Account already has a commitment: `AccountAlreadyConfigurable`.
5. Invalid configuration: `InvalidConfig`.

Gas:

- Ordinary precompile, input and event costs.
- The salt and commitment hashes.
- One account access.
- The 20,000-gas zero-to-nonzero commitment write.
- TIP-1000's new-account cost, including state gas, if the write creates the sender. The write creates the sender if it is still empty at that point: zero nonce, zero balance and no code. TIP-20 balances live in token storage, so they don't count. The cost is charged during execution.
  - With `nonce_key == 0`, or a transaction type without nonce keys, the protocol nonce write creates the sender before the call. Nothing more is charged.
  - With a 2D or expiring nonce, the sender is still empty at the write, so the cost applies. Their `nonce == 0` charge pays for the new nonce-key slot, and expiring-nonce gas pays for replay protection, not for the account.
  - Sponsorship doesn't change this.

### Retirement check

From T14, before the protocol accepts original-key authority, it reads the signer's commitment. A zero commitment changes nothing. A nonzero commitment has these effects:

| Where the key is used | Commitment read | State used | Result |
|---|---|---|---|
| Transaction sender, `key_authorization` signer, or separate fee payer | The recovered signer's | The transaction's position in the block | Reject with `RootKeyRetired(account)` |
| Access-key signature with an ordinary inner signature | The signing key ID's, not the parent's | The transaction's position in the block | Reject with `RootKeyRetired(account)` |
| EIP-7702 or Tempo authorization-list entry | The entry's authority | Before changing delegation | Skip the entry. Never install or remove delegation for that account. |
| Protocol operation that takes a signature (listed below) | The required signer's | Call time, including earlier changes in the same transaction | Revert with `RootKeyRetired(account)` before changing state |
| Boolean authority helper | The signing key, or the implicit identity where key ID equals account | Call time | Return `false` |
| Settlement of vouchers on a channel | None | Ordinary channel state | Unaffected. Other settlement checks still apply. |

The protocol operations are:

- **TIP-20 `permit`** checks the owner's commitment before granting an allowance.
- **Payment-channel `open` and any nonzero `topUp`** reject a retired voucher signer: the channel's `authorizedSigner`, or the payer if none is set.
- **`verifyKeychain` and `verifyKeychainAdmin`** check the signing key's commitment.
- **`isAdminKey` and internal admin checks** MUST NOT treat `key_id == account` as original-key authority once that account has a commitment.

This check applies to ordinary signatures, so a configurable access-key delegate under TIP-1111 is not rejected for having a commitment. Authorization-list entries signed with access keys are skipped today, and they stay skipped.

These keep working:

- **Owner approvals.** An original key that is also an owner signs inside a configurable-account signature, and its approval counts with its configured weight.
- **`msg.sender` authority.** Calls made by the account through an authenticated transaction keep it.
- **Pure signature functions.** `ecrecover` and TIP-1020 `recover` and `verify` only say who signed. They don't say who controls an account. Protocol code that treats their result as account authority MUST apply this check itself.

### Channel settlement

Settlement doesn't check retirement. If it did, a payer could migrate, void vouchers the payee already holds, and withdraw the deposit. Instead, settlement keeps the channel's fixed signer and payee. A compromised retired key can still sign vouchers against deposits made before migration. It can pay only that channel's fixed payee, and the deposits can't grow, because top-ups are rejected.

### Ordering and permanence

- The commitment is read at the transaction's position in the block. A later transaction in the same block can't use authority that an earlier migration retired.
- Pending transactions MUST be revalidated when a commitment changes or the chain reorganises. A cached zero is not proof of authority.
- For derived addresses, registration (TIP-1107) retires the key before the first call runs. Retirement stays even if the calls revert.
- An address that has only received funds still has a zero commitment, so its key is not retired.
- This TIP writes no state of its own. Commitment reads follow the normal account-access schedule. An already loaded account adds no read charge.

### Access keys

Migration keeps every grant the account made, with its expiry, limits, scopes, spending counters and revocation state. That includes admin grants made before T14. They keep unrestricted spending (TIP-1111). If the account is itself a delegate on another account, its grants keep working through its new owners ([TIP-1111](./tip-1111.md#delegates-that-migrate)).

### Cross-chain recovery

This subsection is guidance, not consensus rules.

A derived address exists only on Tempo, so funds sent to it on another chain are lost. A wallet that wants recovery on other chains can create the account another way:

1. Generate a fresh secp256k1 key. Its address becomes the account.
2. Immediately, before the address is shared or funded, have that key sign `upgradeAccount`. It installs the real owners and should not include itself. Sponsorship lets this happen before the account has funds.
3. Keep the key offline as a recovery credential, or discard it.

The key is retired on Tempo, but it still controls the address on other EVM chains, so the holder can move mistaken transfers out. It also keeps full authority over the address on zones. Applications that call `ecrecover` without checking for code still treat it as the account, and on other chains the address has no code at all. So it is a live credential:

- Don't use the address on other chains. Only recover mistaken transfers, and move them elsewhere.
- Don't sign anything with the key except recovery.
- Don't leave long-standing approvals to applications that call `ecrecover` without checking for code. Approve only what a batch needs and reset it in the same batch.
- Show who holds the key, separately from the account's owners. If the key is discarded, show that the account has no cross-chain recovery.

Accounts with several owners can use the same flow, with the key held by whoever is responsible for cross-chain recovery.

## Interfaces

`upgradeAccount` is added to TIP-1107's configurable-account precompile.

```solidity
interface IConfigurableAccountUpgrade {
    struct ConfigurableAccountOwner {
        address owner;
        uint8 weight;
    }

    /// @notice Migrates msg.sender to a version-1 configuration.
    /// @param threshold The approval threshold.
    /// @param owners The owners, sorted by address.
    /// @return commitment The stored commitment.
    /// @dev Only a direct original-key transaction with this as its sole call may invoke it.
    /// Existing access keys are kept.
    function upgradeAccount(uint8 threshold, ConfigurableAccountOwner[] calldata owners)
        external returns (bytes32 commitment);

    event AccountUpgraded(
        address indexed account,
        bytes32 indexed commitment,
        bytes32 salt,
        uint8 threshold,
        ConfigurableAccountOwner[] owners
    );

    error PrimitiveRootRequired();
    error UpgradeMustBeOnlyCall();
    error AccountAlreadyConfigurable();
    error AccountHasCode();
    error InvalidConfig();
}
```

Added error for the retirement check:

```solidity
error RootKeyRetired(address account);
```

# Compatibility

| Integration | What changes |
|---|---|
| Migration wallets | Follow the migration checklist below. |
| Applications that use `ecrecover` | Migration installs the account code marker, so Permit2 and other verifiers that check for code route the account's signatures to ERC-1271 and reject the original key. Allowances the original key granted before migration, including Permit2 allowances, stay usable by their spenders. Applications that call `ecrecover` without checking for code still accept the key: ERC-2612 permits on non-TIP-20 tokens, signed orders, and SIWE or TIP-1053 sign-in. They should check `getConfigCommitment` before trusting a recovered address. |
| Token approvals | There is no configurable-account permit. Use a quorum-signed `approve`, optionally batched with the application call. Permit2 signature flows work through ERC-1271, with owners signing the configurable-account digest. |
| Sponsors | A migrated address can no longer sponsor other accounts' fees. |
| Payment channels | Existing deposits stay redeemable. Top-ups and new channels need a non-retired signer. If the key may be compromised, close channels it funded. |
| Other configurable accounts | If the original key is an owner of another account, it keeps its weight there until that account removes it. |
| Error handling | Tell `RootKeyRetired` apart from an invalid signature. A zero commitment doesn't say whether an account is an ordinary account or an unregistered derived address. |
| Zones | The original key keeps authority over the address's zone funds until zones support configurable accounts. Withdraw zone funds before discarding the key. |

Migration checklist for wallets:

1. Show the new owners, the threshold and every access key that will survive, including unrestricted admin grants made before T14. Say so if the list may be incomplete.
2. Check locally that the new owners can reach the threshold.
3. If the key may be compromised, first move zone funds and revoke allowances granted to Permit2 or to applications that call `ecrecover` without checking for code. Migration can't include other calls.
4. Migrate.
5. With the new quorum, revoke unwanted access keys, then list active grants again at finalized state. The original key could have added keys before migration landed.
6. Confirm the commitment at finalized state, and keep the configuration from `AccountUpgraded`.

# Observability

| Event | Fields | Question it answers |
|---|---|---|
| `AccountUpgraded` (MUST be emitted on successful migration) | `account` (indexed), `commitment` (indexed), `salt`, `threshold`, `owners` | Which account migrated, and to what configuration? |

A failed migration leaves no event and no commitment. If no event appears, the migration may still be pending, or it may have failed. Check the transaction result and the current commitment before retrying.

This TIP adds no other event. Retirement is visible as a nonzero commitment at the chosen block. Validation errors identify the retired account and the role in which its key was used.

# Threat Model

The most consequential attack is a compromised original key racing the owner's migration. Before migration lands, the attacker can submit a competing `upgradeAccount` with their own owners, or add access keys that will survive migration. The protocol can't tell the two apart. Migration only protects an account whose key is still trusted when it migrates.

| Actor | Capability and trust | Boundary check and failure consequence |
|---|---|---|
| Original key before migration | Controls the account. Trusted to migrate as the user intends. | [Eligibility](#eligibility) and the sole-call rule. A compromised key can install other owners, or add grants that survive. |
| Original key after migration | Controls funded-channel vouchers, other chains, zones, and applications that call `ecrecover` without checking for code. Trusted to stay offline. | The [retirement check](#retirement-check) covers Tempo's protocol only. A compromised key can drain those channels to their fixed payees, the zone funds, and allowances in applications that skip the code check. |
| Migration wallet | Controls the owners, threshold and grants shown. Trusted to display them accurately. | The key's signature binds the real calldata. A misleading wallet installs an unintended quorum. |
| Relayer | Submits signatures made before migration. Not trusted. | Signatures are checked against current state, so old ones fail, except channel vouchers. |
| Channel payee | Holds a claim on a deposit. | Settlement keeps the fixed signer and payee, so migration can't void the claim. |

Residual risks:

- Retirement covers only Tempo's protocol, not applications, other chains or zones.
- Migration doesn't revoke grants. Recovery must revoke them explicitly.

# Invariants

- A successful migration leaves a nonzero commitment at version 1, and the account can't migrate again.
- A failed migration rolls back the commitment and event and leaves the original key authoritative, with normal fee and nonce effects.
- Migration preserves the address, balances, storage, nonce state, and all outgoing grants with their counters, including revoked, expired and pre-T14 admin grants.
- The original key may stay an owner or be dropped. Either way, its bare signature fails in every row of the retirement table except channel settlement.
- Signatures created before retirement fail when relayed afterwards, except channel vouchers.
- Later transactions in the same block can't use retired authority.
- Skipped authorization-list entries never install or remove delegation for a retired account.
- Voucher settlement doesn't depend on the signer's commitment, and a retired signer's channel deposit can't increase.
- A configurable parent's commitment doesn't block its active delegates. The check applies to the signing key ID.
- A migration that creates the sender charges TIP-1000's new-account cost exactly once, under every nonce type, with or without sponsorship. A nonempty sender pays none.
