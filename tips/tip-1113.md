# TIP-1113: In-Place Account Migration

## Abstract

An existing account can adopt configurable ownership without changing its address.

- The original root key authorizes migration.
- Migration installs the owner configuration and permanently disables bare root authority.
- Existing access keys keep their current permissions.

## Motivation

Users should be able to gain key rotation while keeping their balances, allowances, roles, and application history at the same address.

This TIP carries forward the migration behavior proposed in [TIP-1104](https://github.com/tempoxyz/tempo/pull/7445). It uses account-leaf storage and the separate root-disablement rules.

## Assumptions

TIP-1108 account commitments, TIP-1109 configuration updates, TIP-1111 access-key support, and TIP-1114 native authorization are active. TIP-1112 root-key disablement must activate no later than migration.

Migration has its own hardfork gate. Before that gate, `upgradeAccount` must be rejected without writing a commitment or emitting `AccountUpgraded`. Activating configurable accounts alone must not enable migration. The target fork remains unassigned until the implementation and the release checks below are complete.

## Threat Model

The root key is trusted until migration succeeds. A compromised root can race migration or choose different owners.

The protocol cannot prove that the new owners still possess their keys. An inaccessible quorum can lock the account. Migration has no undo operation; the original root can regain authority only if a current owner quorum explicitly includes it in a later configuration.

Preserving outgoing access-key grants also preserves the authority they already confer. Migration is not a revocation of wallet-provider or automation access. Root disablement does not invalidate application signatures that bypass TIP-1112, such as a contract accepting an unchecked `ecrecover` result.

# Specification

## Interface

Extend the TIP-1109 precompile at the same address with:

```solidity
interface INativeMultisigUpgrade {
    struct MultisigOwner {
        address owner;
        uint8 weight;
    }

    /// Migrate msg.sender using threshold and sorted owners.
    /// Return the stored hash.
    /// Only a direct primitive-root transaction with upgradeAccount as its sole
    /// call may invoke this. Reverts if already configured, code-bearing,
    /// unauthorized, or given an invalid configuration. Access keys are retained.
    function upgradeAccount(
        uint8 threshold,
        MultisigOwner[] calldata owners
    ) external returns (bytes32 commitment);

    event AccountUpgraded(
        address indexed account,
        bytes32 indexed commitment,
        bytes32 salt,
        uint8 threshold,
        MultisigOwner[] owners
    );

    error PrimitiveRootRequired();
    error UpgradeMustBeOnlyCall();
    error AccountAlreadyConfigurable();
    error AccountHasCode();
    error InvalidConfig();
}
```

## Migration transition

### Who can migrate

- Require a Tempo transaction of type `0x76` in the normal transaction execution context, not a subblock transaction.
- `upgradeAccount` must be the only top-level call.
- Reject contract callbacks, nested calls, `DELEGATECALL`, and `STATICCALL`.
- Require `msg.sender == tx.origin == tx.from`.
- Require a direct secp256k1, P256, or WebAuthn outer signature recovered to `tx.from` and accepted as current root authority before execution.
- Do not allow access-key authority.
- Do not allow a multisig witness to authorize migration, including one whose owners include the original root.
- Reject an authorization list or `key_authorization` in the same transaction. Migration must not hide simultaneous delegation changes.
- Allow ordinary fee sponsorship.

The account must have empty code, no EIP-7702 delegation, and a zero configuration commitment at call time. Reject protocol-reserved account addresses under the same eligibility rules as TIP-1114.

Caller equality alone is not authorization. The transaction handler must pass authenticated root identity, signature class, execution context, and the validated sole-call restrictions to the precompile. This authority must not be writable through calldata or EVM storage and must not survive a transaction boundary, a discarded builder attempt, or a reused simulation context. Simulation and estimation may model the same restrictions but cannot supply authority to a later included transaction.

The root signature binds the complete migration calldata under the existing transaction signing rules, including chain and nonce protection. Privy API authorization signatures and HTTP idempotency keys are wallet transport concerns, not replacements for these onchain checks.

### Installing the configuration

Construct the initial migrated configuration as follows:

```text
salt = keccak256("tempo:multisig:upgrade" || account)
config = (salt, version = 1, threshold, owners)
```

- Encode the domain as raw ASCII and `account` as 20 bytes.
- Validate the configuration using TIP-1114.
- Apply the positive-version rules: the migrating address may be an explicit owner. Do not require the new owners to derive the migrating address under TIP-1110.
- Require its TIP-1108 hash to be nonzero.
- Store that hash and emit `AccountUpgraded`.
- Later updates follow TIP-1109.

The original root may be an explicit owner. For example, a user can migrate to a 1-of-1 configuration using their existing key, then rotate it later.

The root's signed calldata authorizes the chosen configuration. No additional owner signature is required onchain.

If the call fails, revert the commitment and event. This includes failure while emitting the event or charging gas. Unlike TIP-1114 first-use registration, migration must not write the commitment outside the execution rollback checkpoint. Normal rules still apply to transaction fees and nonce consumption.

### Errors and gas

After transaction authentication and hardfork checks have passed, check precompile failures in this order:

1. Sole-call and authorization restrictions: `UpgradeMustBeOnlyCall`.
2. Root authority: `PrimitiveRootRequired`.
3. Code or delegation: `AccountHasCode`.
4. Existing commitment: `AccountAlreadyConfigurable`.
5. Configuration validity: `InvalidConfig`.

Map all invalid owner-list, weight, threshold, and configuration cases to `InvalidConfig`. A previously migrated account attempting a second bare-root transaction may be rejected by TIP-1112 before reaching the precompile; the error order above does not override transaction validation.

Charge:

- Ordinary precompile, input, and event costs.
- Standard Keccak gas for the salt and commitment.
- TIP-1108 account access and the zero-to-nonzero commitment write.
- TIP-1000 account-creation cost, including its state-gas portion, if successful migration creates an account leaf not already paid for by another account-creation effect of the transaction.

Count nonce-key creation and account-leaf creation separately. A `nonce == 0` charge for a new 2D nonce key does not pay for the migrating account leaf. Expiring nonces do not substitute for the account-creation charge either. Determine account creation from the transaction's pre-state and its actual account-creation effects, not from a zero transaction nonce or a TIP-20 balance. Charge creation exactly once, including for sponsored transactions. Commitment writes follow TIP-1108 and do not mint storage credits.

## What remains unchanged

Migration preserves the account's:

- Address and balances.
- Application storage and permissions.
- Nonce state, apart from normal transaction effects.

Existing ordinary and admin access keys granted by the migrating account keep their expiry, limits, scopes, spending counters, and revocation state. Migration does not rewrite their stored key types or reactivate expired or revoked grants.

- Admin access keys cannot rotate owners.
- Delegates whose own root authority is retired still follow TIP-1111 and TIP-1112.

From the next transaction, direct signing requires a matching witness at version one or later. TIP-1112 rejects bare root signatures.

Migration provides no CREATE2 recovery guarantee on another chain. It also does not disable the root key on other chains.

## Incoming access-key grants

Suppose treasury A gives account B permission to spend $100 per day.

- The grant currently records B's address and signature type.
- B migrates to a configurable account and keeps the same address.
- B's original EOA key is disabled. Its configured owners must now sign.
- The existing grant still expects the old signature type, so B can no longer use it.
- A cannot register B again at the same address. AccountKeychain rejects reused key IDs, even after revocation.

This TIP preserves B's outgoing grants, not primitive grants that other accounts gave to B. Under the current TIP-1111 rules, migration must not silently convert A's primitive grant to a multisig grant or skip its stored signature-type check. B's retired root cannot use that grant, and B's owner quorum cannot use it with the old primitive type.

A must explicitly grant access to a fresh delegate key ID if it wants to restore B's delegated capability; revoking the old grant does not make its key ID reusable. Wallets must warn that incoming primitive grants become unusable and that there is no incoming-grant enumeration guarantee.

Type-independent grants are deferred. Adopting them requires a separate TIP-1111 change and approval; they are not an implicit side effect or prerequisite of migration.

# Tooling

- Show the new owners, threshold, retained access keys, and permanent root disablement before migration.
- Check that the proposed quorum can sign locally before submission. This is a wallet check, not an additional onchain signature.
- Check the complete proposed configuration against the signature limits active on the target chain, including any per-transaction ZK-signature cap if OIDC owners are supported. A successful `upgradeAccount` call alone does not prove that a usable signing quorum exists.
- Disclose if access-key enumeration is incomplete. Users wanting quorum-only control must revoke unwanted grants separately.
- A wallet-provider exit flow must exclude the provider's key from the new owners and revoke provider-controlled outgoing grants before migration or in a subsequent owner-authorized transaction. Revocations cannot be batched with `upgradeAccount`; do not report the exit complete until their receipts are finalized.
- Retain the full version-one configuration before submission, including the salt derived from the account, so an unavailable indexer cannot prevent subsequent signing.
- Verify the expected commitment in finalized canonical state and retain the configuration from `AccountUpgraded`.
- On a lost submission response, look up the original transaction hash and finalized commitment before requesting another root signature. Wallet HTTP retries must retain their idempotency key; they do not change chain replay rules.
- Then use TIP-1114 for direct signing and keep valid access-key flows available.

# Observability

Emit `AccountUpgraded` on successful migration. Together with later `MultisigConfigUpdated` events, it provides the configuration history.

Pools must revalidate affected pending root transactions, key authorizations, delegates, and fee-payer roles after migration or a reorg under TIP-1112. A cached signature recovery or a prior zero commitment is not proof of current authority.

# Release checks

Before scheduling migration, provide executable evidence for these cases in the implementation, not only wallet simulations or a configurable-account devnet:

| Boundary | Required cases |
|---|---|
| Activation | Reject before the migration fork; require root retirement at activation; builder, pool, execution, and RPC agree at the fork boundary. |
| Root authority | Accept direct secp256k1, P256, and WebAuthn roots; reject ordinary and admin access keys, multisig witnesses, callbacks, delegate/static calls, subblocks, extra calls, and both authorization-list forms. |
| Configuration | Cover each invalid owner, weight, order, threshold, and count; allow the root as an explicit positive-version owner; sign with the new quorum and rotate after migration. |
| Account state | Reject code, EIP-7702 delegation, reserved addresses, and prior commitments; preserve balances, application storage, outgoing grants, limits, scopes, counters, and revocation state. |
| Atomicity | Revert on write or event out-of-gas with no commitment or event; preserve ordinary fee/nonce effects; rollback and reorg restore the corresponding root authority. |
| Retirement | Reject old-root authority later in the same block across every TIP-1112 role; allow it only as an explicit owner approval; reject stale pre-signed permits in protocol precompiles. |
| Gas and replay | Cover protocol, 2D, and expiring nonces, empty accounts, and fee sponsorship; charge each created state object once; reject replay and repeated migration. |
| Context isolation | Invalid transactions, discarded builder attempts, and RPC simulations cannot seed migration authority in later transactions. |
| Incoming grants | An old primitive grant cannot be used by the retired root or by a substituted owner quorum; restoring delegation requires an explicitly authorized fresh key ID. |

The release review must also verify a wallet-provider root signing the exact one-call transaction and the resulting owner quorum signing from the unchanged address. Root-retirement enforcement and its regression tests are hard dependencies; this TIP must not be activated merely because its precompile selector exists.

# Invariants

- Successful migration always leaves a nonzero configuration hash.
- Migration preserves existing access-key state, including admin, revoked, and expired grants.
- Test migration with and without the original root as an explicit owner.
- Test atomic failure, repeated migration, and bare-root rejection later in the same block.
- Migration authority is transaction-local and cannot be obtained from caller equality alone.
- Successful migration cannot leave a bare-root bypass, reset an outgoing grant's counters, or silently reinterpret an incoming grant.
- Account and nonce-key creation charges are independent, and migration writes and events share one execution rollback checkpoint.
