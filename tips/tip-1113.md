# TIP-1113: In-Place Account Migration

## Abstract

An existing primitive account can become configurable without changing its address. Its final root-authorized transition installs a configuration and permanently disables bare root authority. Existing access keys remain subject to their current permissions.

## Motivation

Balances, allowances, roles, and application history should not have to move to a new address to gain key rotation. This component carries forward the migration behavior proposed in [TIP-1104](https://github.com/tempoxyz/tempo/pull/7445), using account-leaf storage and the split root-disablement rules.

## Assumptions

TIP-1111 and TIP-1112 activate with this TIP. The migrating account has no code or EIP-7702 delegation and no existing commitment. The root key is trusted until migration succeeds; a compromised root can race or choose a different configuration.

## Threat Model

Delegates must not migrate their parent. Migration must not silently grant or revoke access-key permissions, revive old roots, or imply CREATE2 recovery. Choosing an inaccessible quorum can lock the account; the protocol cannot infer whether users still possess their keys.

# Specification

## Interface

Extend the TIP-1109 precompile at the same address with:

```solidity
interface INativeMultisigUpgrade {
    struct MultisigOwner { address owner; uint8 weight; }

    /// Migrate msg.sender using threshold and sorted owners; return stored hash.
    /// Only a direct primitive-root transaction with upgradeAccount as its sole
    /// call may invoke this. Reverts if already configured, code-bearing,
    /// unauthorized, or given an invalid configuration. Access keys are retained.
    function upgradeAccount(uint8 threshold, MultisigOwner[] calldata owners)
        external returns (bytes32 commitment);

    event AccountUpgraded(address indexed account, bytes32 indexed commitment,
        bytes32 salt, uint8 threshold, MultisigOwner[] owners);

    error PrimitiveRootRequired();
    error UpgradeMustBeOnlyCall();
    error AccountAlreadyConfigurable();
    error AccountHasCode();
    error InvalidConfig();
}
```

## Migration transition

Require the only top-level call to be `upgradeAccount`, with `msg.sender == tx.origin == tx.from`, a primitive outer signature, and no access-key authority. Reject transactions carrying an authorization list or `key_authorization`, so migration cannot hide simultaneous delegation changes. Ordinary sponsorship is allowed.

Require empty code, no EIP-7702 delegation, and a zero commitment. Construct:

```text
salt = keccak256("tempo:multisig:upgrade" || account)
config = (salt, version = 1, threshold, owners)
```

The domain is raw ASCII and `account` is 20 bytes. Validate the configuration under TIP-1114 and require its TIP-1108 hash to be nonzero. Write that hash and emit `AccountUpgraded`; its configuration version is always one. Later updates preserve this salt and increment the version.

The existing address is retained, not re-derived. It may itself appear as an explicit primitive owner: migrating to a 1-of-1 configuration containing the original root gains future key rotation without requiring a new key immediately.

No additional owner signature is required onchain: the current root authorizes the chosen configuration through the signed calldata. A failed call reverts the commitment and event. Normal transaction fees and nonce consumption still follow ordinary execution rules.

Check errors in this order: sole-call/sidecar restrictions (`UpgradeMustBeOnlyCall`), root authority, code/delegation, existing commitment, then configuration validity (`InvalidConfig`). Charge ordinary precompile, input, and event costs, standard Keccak gas for the salt and commitment, and TIP-1108 account access plus the zero-to-nonzero write.

## What remains unchanged

Keep the account's balances, application storage and permissions, and nonce state, apart from normal transaction effects. Existing ordinary and admin access keys retain their expiry, limits, scopes, and revocation state. Admin access keys cannot rotate owners. Keys whose own root authority is retired still follow TIP-1111/TIP-1112; migration never overrides delegate validation.

From the next transaction, direct authority requires the version-one or later matching witness. Bare root signatures are rejected by TIP-1112. The account acquires no CREATE2 recovery guarantee on another chain, and Tempo migration does not disable a root key elsewhere.

# Tooling

Before migration, display the proposed owners, threshold, retained access keys, and irreversibility. Obtain a local readiness signature from the proposed quorum before submission; this is a wallet check, not a second protocol authorization. If complete access-key enumeration is unavailable, disclose that additional grants may exist.

After success, verify the expected commitment in finalized canonical state and retain the full configuration from `AccountUpgraded`. Switch direct signing to TIP-1114; keep valid access-key flows. Reorgs return the UI to the authority supported by canonical state. Users who want quorum-only control must revoke unwanted delegates separately.

# Observability

Emit `AccountUpgraded` once on successful migration. Together with subsequent `MultisigConfigUpdated` events it reconstructs the complete configuration history. No automatic keychain revocation events are emitted.

# Invariants

Test migration with and without the root as owner, retained ordinary/admin/revoked/expired access keys, rejected delegated and code-bearing callers, duplicate migration, atomic failure, same-block root rejection, sponsorship, later rotation, and reorgs. Preserve the original address and application relationships.
