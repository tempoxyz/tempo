# TIP-1113: In-Place Account Migration

## Abstract

This TIP lets an existing account install a version-one owner configuration at the same address. Its primitive root signs a sole-call migration; TIP-1112 permanently disables bare root authority for direct signing at T14.

Migration requires no code, EIP-7702 delegation, or existing configuration. It preserves balances, application state, regular access-key grants, and nonce state apart from normal transaction effects. Regular grants received from other accounts remain usable by the current owner quorum; TIP-1109 governs later owner updates.

## Motivation

Existing users need key rotation while keeping their balances, allowances, roles, and application history at the same address. [TIP-1104](https://github.com/tempoxyz/tempo/pull/7445) proposed in-place migration; this TIP carries that capability into the configurable-account design.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| TIP-1108 commitments, TIP-1109 updates, TIP-1111 access keys, and TIP-1114 configurable account authorisation activate with migration at T14. | A migrated account could lack storage, signing, rotation, or delegation support. |
| TIP-1112 root disablement activates at the same fork. | The original root could bypass the new quorum in protocol signing. |
| TIP-1137 admin access-key removal activates at T14. | Pre-T14 admin keys could retain spending authority outside the new quorum. |

# Specification

## Overview

**Migration** installs the first owner configuration on an existing account. The root authorises the transition; the configuration controls subsequent direct transactions.

1. **Prepare:** choose the owners and threshold, and check that the account is eligible.
2. **Approve:** the original root signs a transaction whose only call is `upgradeAccount`.
3. **Migrate:** validate the configuration, store its version-one commitment, and emit `AccountUpgraded`.
4. **Confirm:** verify the commitment in canonical state and use the new owners for subsequent direct transactions.

| State | Before migration | After successful migration |
|---|---|---|
| Configuration commitment | Zero | Nonzero, at version one |
| Direct protocol signing | Primitive root key | Current owner quorum |
| Address and application state | Existing account | Preserved |
| Grants made by this account | Existing permissions and spending state | Regular grants preserved; stored admin keys remain revoked under TIP-1137 |
| Regular grants received from others | Usable if otherwise valid | Usable by the current owner quorum, with existing restrictions and spending state |

For example, a user migrates to a 1-of-1 configuration with their existing key at weight one and threshold one. The key then signs through a version-one multisig witness. A later owner update can replace it. If migration fails, the commitment and event roll back and the original root remains authoritative.

Migration changes direct protocol signing on Tempo. The root remains usable on other chains, allowing [TIP-1110's cross-chain recovery flow](./tip-1110.md#cross-chain-recovery).

## Migration transition

### Who can migrate

- `upgradeAccount` must be the only top-level call.
- Require `msg.sender == tx.origin == tx.from`.
- Require a primitive outer signature from the root key.
- Do not allow access-key authority.
- Reject an authorization list or `key_authorization` in the same transaction. Migration must not hide simultaneous delegation changes.
- Allow ordinary fee sponsorship.

The account must have empty code, no EIP-7702 delegation, and a zero configuration commitment.

### Installing the configuration

Construct the initial migrated configuration as follows:

```text
salt = keccak256("tempo:configurable-account:upgrade" || account)
config = (salt, version = 1, threshold, owners)
```

1. Encode the domain as raw ASCII and `account` as 20 bytes.
2. Validate the configuration using TIP-1114.
3. Require its TIP-1108 hash to be nonzero.
4. Store that hash and emit `AccountUpgraded`.

The original root MAY be an explicit owner.

The root's signed calldata authorizes the chosen configuration. No additional owner signature is required onchain.

| Outcome | Authority and state | Next action |
|---|---|---|
| Migration succeeds | Version-one commitment and `AccountUpgraded` remain. Bare root direct signing is disabled. | Use the current owner configuration; the account cannot migrate again. |
| Migration call fails | Revert the commitment and event. The original root authority remains unchanged. Normal transaction fee and nonce rules still apply. | Recheck eligibility, configuration, and nonce before resubmitting with the root. |

### Errors and gas

Check failures in this order:

1. Sole-call and authorization restrictions: `UpgradeMustBeOnlyCall`.
2. Root authority: `PrimitiveRootRequired`.
3. Code or delegation: `AccountHasCode`.
4. Existing commitment: `AccountAlreadyConfigurable`.
5. Configuration validity: `InvalidConfig`.

Charge:

- Ordinary precompile, input, and event costs.
- Standard Keccak gas for the salt and commitment.
- TIP-1108 account access and the zero-to-nonzero commitment write.
- TIP-1000's new-account cost, including its state-gas portion, if the commitment write creates the sender.

The commitment write creates the sender if the sender is empty (zero nonce, zero balance, no code) at the write. A TIP-20 balance does not make the sender nonempty. The cost is the one TIP-1114 registration charges, but `upgradeAccount` charges it during execution rather than in intrinsic gas.

For an initially empty sender:

- With `nonce_key == 0`, or a transaction type without a nonce key, charge nothing more. The protocol nonce write creates the sender before the call, and the `nonce == 0` charge pays for it.
- With a 2D or expiring nonce, charge it. The sender is still empty at the write. The `nonce == 0` charge pays for the new nonce-key slot, and expiring-nonce gas pays for replay protection.

Fee sponsorship does not change this charge.

## Changes to other components

Migration preserves the account's address, balances, application storage and permissions, and nonce state apart from normal transaction effects.

Regular access keys granted by the migrating account keep their expiry, limits, scopes, spending counters, and revocation state under [TIP-1111](./tip-1111.md#owner-rotation-and-revocation). Stored pre-T14 admin keys remain revoked under TIP-1137; migration does not reactivate them.

Delegates whose own root authority is retired still follow TIP-1111 and TIP-1112.

From the next transaction, direct signing requires a matching witness at version one or later. TIP-1112 rejects bare root signatures.

## Delegation compatibility

For a valid regular grant, [TIP-1111](./tip-1111.md#migration-compatibility) validates the migrated delegate's current owner quorum at the same address, independent of the grant's original signature type.

For example, treasury A grants B $100/day. After B migrates, its current quorum uses the same grant with unchanged permissions and spending state. B's retired root cannot use it independently.

## Interfaces

Extend the TIP-1109 precompile at the same address with:

```solidity
interface IConfigurableAccountUpgrade {
    struct ConfigurableAccountOwner {
        address owner;
        uint8 weight;
    }

    /// Migrate msg.sender using threshold and sorted owners.
    /// Return the stored hash.
    /// Only a direct primitive-root transaction with upgradeAccount as its sole
    /// call may invoke this. Reverts if already configured, code-bearing,
    /// unauthorized, or given an invalid configuration. Regular access keys are retained.
    function upgradeAccount(
        uint8 threshold,
        ConfigurableAccountOwner[] calldata owners
    ) external returns (bytes32 commitment);

    event AccountUpgraded(
        address indexed account,
        bytes32 indexed commitment,
        bytes32 salt,
        uint8 threshold,
        ConfigurableAccountOwner[] owners
    );

    error PrimitiveRootRequired();
    error UpgradeMustBeOnlyCall();
    error AccountAlreadyConfigurable();
    error AccountHasCode();
    error InvalidConfig();
}
```

# Compatibility

- Show the new owners, threshold, retained regular access keys, and permanent disablement of bare root direct signing before migration. Stored pre-T14 admin keys are revoked under TIP-1137.
- Check that the proposed quorum can sign locally before submission. This is a wallet check, not an additional onchain signature.
- Disclose incomplete access-key enumeration; quorum-only control remains unverified.
- For quorum-only control, revoke all active regular grants, including pre-T14 regular grants, before migration. Revocation needs a separate transaction because `upgradeAccount` must be the only call. Recheck after finalized migration and use the current quorum to revoke any remaining grants. The root could have added them before migration committed.
- Show that grants received from other accounts require the migrated delegate's current owner quorum under the [delegation rules](#delegation-compatibility).
- Show [TIP-1112's retirement effects](./tip-1112.md): outstanding protocol permits become invalid, including pre-migration signatures. Channels with retired voucher signers allow settlement against existing deposits but cannot receive additional funds; new channels need a non-retired authorized signer. Application signature checks retain TIP-1112's separate trust boundary.
- If the retiring root may be compromised, prompt users to close channels where it is the voucher signer. It can still sign against their remaining deposits.
- Warn that migration does not retire the root key on zones. Funds the account holds on zones stay under the old key, so move them before migrating if that key may be compromised.
- Verify the expected commitment in finalized canonical state and retain the configuration from `AccountUpgraded`.
- Then use TIP-1114 for direct signing and keep valid access-key flows available.

# Observability

`AccountUpgraded` records a successful migration's configuration and commitment. Later `ConfigurableAccountConfigUpdated` events extend the configuration history. Match the latest configuration to the account's commitment in finalized canonical state.

A failed migration call leaves no configuration write or migration event. An absent event alone does not distinguish a pending transaction from a failed one; check the transaction result and current commitment before retrying.

# Threat Model

| Actor | Trust |
| --- | --- |
| Original root holder | The primitive-signature and sole-call checks authorize the transition. Until it commits, the root can race migration, install attacker-controlled owners, or add regular grants that survive migration. |
| Migration wallet | Trusted to show the signed owners, threshold, and retained grants. The root's calldata approves the transition; the protocol collects no additional approval from the new owners. |
| New owners | Their current quorum controls subsequent direct protocol signing and rotation. They must retain keys sufficient to meet the threshold; configuration validation does not prove possession. |
| Existing delegates | Active regular grants retain their permissions, spending counters, and revocation state. Grant authority cannot authorize migration or owner rotation. Stored pre-T14 admin grants are revoked under TIP-1137. |

An inaccessible quorum can lock the account. Keeping the old key as an explicit owner does not restore bare root direct signing.

# Invariants

- Successful migration always leaves a nonzero configuration hash.
- Migration preserves outgoing access-key grants, spending counters, and revocation state, including legacy, revoked, and expired grants.
- The original root may remain an explicit owner or be omitted from the new configuration.
- Successful migration disables bare root authority, except funded-channel settlement under TIP-1112, regardless of whether the original root remains an owner.
- Failed migration rolls back the configuration write and event.
- Failed migration follows normal transaction fee and nonce rules.
- An account that already has a configuration cannot migrate again.
- Later transactions in the same block cannot use the migrated account's bare root authority outside TIP-1112's funded-channel settlement exception.
- A transaction that migrates an empty sender pays TIP-1000's new-account cost exactly once, including its state-gas portion, under every nonce type, with or without fee sponsorship.
- Migration adds no new-account cost for a nonempty sender.
