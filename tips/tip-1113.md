# TIP-1113: In-Place Account Migration

## Abstract

This TIP lets a primitive root migrate its account to version-one configurable ownership through a sole-call transaction. The address, balances, application state, regular access grants, and nonce state survive, apart from normal transaction effects. TIP-1112 then permanently disables bare root direct signing. The current quorum uses received grants and authorises later updates under TIP-1109.

## Motivation

Existing users need key rotation while keeping their balances, allowances, roles, and application history at the same address. [TIP-1104](https://github.com/tempoxyz/tempo/pull/7445) proposed in-place migration; this TIP carries that capability into the configurable-account design.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| TIP-1108 commitments, TIP-1109 updates, TIP-1111 access keys, and TIP-1114 configurable account authorisation activate with migration at T14. | A migrated account could lack storage, signing, rotation, or delegation support. |
| TIP-1112 root disablement activates at the same fork. | The original root could bypass the new quorum in protocol signing. |

# Specification

## Overview

**Migration** installs the first owner configuration on an existing account. The root authorises the transition; the configuration controls subsequent direct transactions.

1. **Prepare:** choose owners and threshold; check eligibility.
2. **Approve:** the original root signs a sole `upgradeAccount` call.
3. **Migrate:** store the validated version-one commitment and emit `AccountUpgraded`.
4. **Confirm:** verify canonical state and use the new owners for direct transactions.

For example, a user migrates to 1-of-1 ownership with their existing key at weight one and threshold one. It then signs a version-one multisig witness and can authorize later rotation. If migration fails, the commitment and event roll back; original root authority remains.

Migration changes direct protocol signing on Tempo; the root remains usable on other chains for [cross-chain recovery](./tip-1110.md#cross-chain-recovery).

## Migration transition

### Who can migrate

- `upgradeAccount` must be the only top-level call, with `msg.sender == tx.origin == tx.from`.
- Require a primitive outer signature from the root key; access-key authority is invalid.
- Reject an authorization list or `key_authorization` in the same transaction.
- Allow ordinary fee sponsorship.

The account must have empty code, no EIP-7702 delegation, and a zero configuration commitment.

### Installing the configuration

Construct the initial migrated configuration as follows:

```text
salt = keccak256("tempo:configurable-account:upgrade" || account)
config = (salt, version = 1, threshold, owners)
```

1. Encode the domain as raw ASCII and `account` as 20 bytes.
2. Validate the configuration using TIP-1114.
3. Require its TIP-1108 hash to be nonzero.
4. Store that hash and emit `AccountUpgraded`.

The root's signed calldata authorizes the configuration without additional onchain owner signatures. The root MAY remain an explicit owner.

| Outcome | Authority and state | Next action |
|---|---|---|
| Migration succeeds | Version-one commitment and `AccountUpgraded` remain; bare root direct signing is disabled. | Use the current configuration; migration cannot repeat. |
| Migration call fails | Commitment and event revert; root authority is unchanged. Normal fees and nonce rules apply. | Recheck eligibility, configuration, and nonce before resubmitting with the root. |

### Errors and gas

Check failures in this order:

1. Sole-call and authorization restrictions: `UpgradeMustBeOnlyCall`.
2. Root authority: `PrimitiveRootRequired`.
3. Code or delegation: `AccountHasCode`.
4. Existing commitment: `AccountAlreadyConfigurable`.
5. Configuration validity: `InvalidConfig`.

Charge:

- Ordinary precompile, input, and event costs.
- Standard Keccak gas for the salt and commitment.
- TIP-1108 account access and the zero-to-nonzero commitment write.
- TIP-1000's new-account cost, including its state-gas portion, if the commitment write creates the sender.

The commitment write creates an empty sender (zero nonce, zero balance, no code); TIP-20 balances do not affect emptiness. Charge TIP-1114's new-account registration cost if the sender is still empty at that write, during execution rather than in intrinsic gas.

For an initially empty sender:

- With `nonce_key == 0`, or a transaction type without a nonce key, charge nothing more. The protocol nonce write creates the sender before the call, and the `nonce == 0` charge pays for it.
- With a 2D or expiring nonce, charge it. The sender is still empty at the write. The `nonce == 0` charge pays for the new nonce-key slot, and expiring-nonce gas pays for replay protection.

Fee sponsorship does not change this charge.

## Changes to other components

Migration preserves the account's address, balances, application storage and permissions, and nonce state apart from normal transaction effects.

Regular access keys granted by the migrating account keep their expiry, limits, scopes, spending counters, and revocation state under [TIP-1111](./tip-1111.md#owner-rotation-and-revocation).

Delegates whose own root authority is retired still follow TIP-1111 and TIP-1112.

Subsequent direct transactions require a matching witness at version one or later; TIP-1112 rejects bare root signatures.

## Delegation compatibility

Under [TIP-1111](./tip-1111.md#migration-compatibility), a migrated delegate's current quorum uses valid regular grants at the same address without changing permissions or spending state, regardless of the grant's original signature type.

## Interfaces

Extend the TIP-1109 precompile at the same address with:

```solidity
interface IConfigurableAccountUpgrade {
    struct ConfigurableAccountOwner {
        address owner;
        uint8 weight;
    }

    /// Migrate msg.sender using threshold and sorted owners.
    /// Return the stored hash.
    /// Only a direct primitive-root transaction with upgradeAccount as its sole
    /// call may invoke this. Reverts if already configured, code-bearing,
    /// unauthorized, or given an invalid configuration. Regular access keys are retained.
    function upgradeAccount(
        uint8 threshold,
        ConfigurableAccountOwner[] calldata owners
    ) external returns (bytes32 commitment);

    event AccountUpgraded(
        address indexed account,
        bytes32 indexed commitment,
        bytes32 salt,
        uint8 threshold,
        ConfigurableAccountOwner[] owners
    );

    error PrimitiveRootRequired();
    error UpgradeMustBeOnlyCall();
    error AccountAlreadyConfigurable();
    error AccountHasCode();
    error InvalidConfig();
}
```

# Compatibility

- Before migration, show the new owners, threshold, retained regular access keys, and permanent disablement of bare root direct signing.
- Check locally that the proposed quorum can sign before submission; no additional onchain signature is required.
- Disclose incomplete access-key enumeration; quorum-only control remains unverified.
- For quorum-only control, revoke all active regular grants, including pre-T14 grants, before migration in a separate transaction. Recheck after finalization and revoke remaining grants with the current quorum: the root could have added them before migration committed.
- Show that grants received from other accounts require the migrated delegate's current owner quorum under the [delegation rules](#delegation-compatibility).
- Show [TIP-1112's retirement effects](./tip-1112.md): protocol permits, including pre-migration signatures, become invalid. Channels with retired voucher signers can settle existing deposits but cannot receive additional funds; new channels need a non-retired authorized signer. Application signature checks retain a separate trust boundary.
- Prompt users to close channels whose voucher signer is a possibly compromised retiring root; it can still authorize their remaining deposits.
- Warn that the old key retains authority on zones. Move funds before migrating if that key may be compromised.
- Verify the expected commitment in finalized canonical state and retain `AccountUpgraded`'s configuration. Then use TIP-1114 direct signing or valid access-key flows.

# Observability

Match `AccountUpgraded`'s configuration and commitment, followed by any `ConfigurableAccountConfigUpdated` events, to the commitment in finalized canonical state.

An absent event can mean pending or failed migration; check the transaction result and current commitment before retrying. Failure follows the [transition rules](#installing-the-configuration).

# Threat Model

| Actor | Trust |
| --- | --- |
| Original root holder | The [root and sole-call checks](#who-can-migrate) authorize migration. Until it commits, the root can race it to install attacker-controlled owners or add grants that survive migration. |
| Migration wallet | Trusted to show the signed owners, threshold, and retained grants. Misrepresentation can install an unintended quorum; the protocol requires no new-owner approval. |
| New owners | Their current quorum controls direct signing and rotation. They must retain enough keys to meet the threshold; configuration validity does not prove possession. |
| Existing delegates | Regular grants retain permissions, spending counters, and revocation state. Grant authority cannot authorize migration or owner rotation. |

An inaccessible quorum can lock the account. Keeping the old key as an explicit owner does not restore bare root direct signing.

# Invariants

- Successful migration always leaves a nonzero configuration hash.
- Migration preserves outgoing access-key grants, spending counters, and revocation state, including legacy, revoked, and expired grants.
- The original root may remain an explicit owner or be omitted from the new configuration.
- Successful migration disables bare root authority, except funded-channel settlement under TIP-1112, regardless of whether the original root remains an owner.
- Failed migration rolls back the configuration write and event.
- Failed migration follows normal transaction fee and nonce rules.
- An account that already has a configuration cannot migrate again.
- Later transactions in the same block cannot use the migrated account's bare root authority outside TIP-1112's funded-channel settlement exception.
- A transaction that migrates an empty sender pays TIP-1000's new-account cost exactly once, including its state-gas portion, under every nonce type, with or without fee sponsorship.
- Migration adds no new-account cost for a nonempty sender.
