# TIP-1123: Store DKG ceremony configuration in execution state

## Abstract

This TIP extends [TIP-1070](./tip-1070.md). It removes the next ceremony's players and mode from the boundary block's DKG outcome. Instead, TIP-1070's post-execution hook at the end of each boundary block also snapshots them from ValCfgV2 into new slots of TIP-1070's `CurrentCommittee` precompile. Consensus reads them from finalized state instead of the state of an unfinalized parent.

## Motivation

The [DKG outcome](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/dkg-onchain-artifacts/src/lib.rs#L29-L45) in each boundary block includes the next ceremony's players and whether it rotates the network identity. Validators [read both](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1244-L1262) from [ValCfgV2](./tip-1017.md) at the boundary block's parent, when proposing and when verifying. This has two problems:

- The parent is unfinalized and may be on a fork, so building or verifying a boundary block needs the post-state of a possibly non-canonical block through a dedicated [overlay](https://github.com/tempoxyz/tempo/blob/3bde631dcf98dbf44ae104f6a53e1cf20f4ca785/crates/node/src/executed_state.rs).
- A restarting node must find and decode the last boundary header to learn the current ceremony configuration.

Deriving the configuration during execution makes it a deterministic function of the block, committed by the state root. Keeping the current configuration in the [TIP-1070](./tip-1070.md) committee precompile lets consensus, peer discovery, tooling, and contracts read it from the latest state.

## Assumptions

- Consensus selects the outcome for the next epoch, including the failed-ceremony fallback, from dealer logs up to the parent of the boundary block. This TIP does not change outcome selection.
- ValCfgV2 ([TIP-1017](./tip-1017.md)) is initialized, and its active validators have unique, valid Ed25519 keys.

## Threat model

- **Proposer**: controls boundary `extra_data`. As today, validators compare it with their own outcome before execution. The configuration record is derived by execution and committed by the state root; the proposer influences it only by choosing which registry transactions `B(E)` includes, as with any transaction.
- **ValCfgV2 owner**: registry changes up to and including the boundary block of `E` configure the ceremony running during `E+1`; later changes do not affect it. As today, a registry with no active validators makes the next boundary block invalid.
- **Users and contracts**: cannot write the records. The precompile has no entrypoint that writes slots `2` and `3`.

# Specification

Let `B(E)` be the last block of epoch `E`, at height `h` where `h % epoch_length == epoch_length - 1`, and let `O(E+1)` be the outcome consensus selects for epoch `E+1`.

This TIP extends [TIP-1070](./tip-1070.md): it changes the outcome encoding that TIP-1070's system call decodes, adds two storage slots and a getter to its `CurrentCommittee` precompile, and adds a write to its post-execution hook. Every TIP-1070 requirement that this TIP does not change continues to apply, including the boundary predicate, the visibility rules, and the system-call execution conventions.

## Boundary outcome

The `extra_data` of an activated `B(E)` MUST be the encoding of `O(E+1)`:

```rust
struct DkgOutcome {
    epoch: u64,                        // E+1
    output: Output<MinSig, PublicKey>, // public output, no private shares
}
```

This is the legacy `OnchainDkgOutcome` encoding without its trailing `next_players` and `is_next_full_dkg` fields. Because the new encoding is a prefix of the legacy one, decoders MUST reject trailing bytes. Validators compare the encoding, epoch included, with their locally computed `O(E+1)` before execution. Non-boundary `extra_data` is unchanged.

## Storage

This TIP adds two slots to the `CurrentCommittee` precompile at `CURRENT_COMMITTEE_ADDRESS`, after TIP-1070's. The whole layout is normative:

| Slot | Value |
| --- | --- |
| `0` | `uint64 epoch` (TIP-1070): the epoch of the committee, and the epoch during which the ceremony runs |
| `1` | `bytes32[] publicKeys` (TIP-1070): the committee |
| `2` | `bytes32[] dkgPlayers`: Ed25519 keys, strictly ascending in Commonware public-key order |
| `3` | `bool isFullDkg`: `1` for a full DKG, `0` for a reshare |

Arrays use the Solidity storage layout: the slot holds the length, and the elements occupy consecutive slots from `keccak256(slot)`. Both arrays hold at most `u16::MAX` keys, the limit of the `Output` decoder.

As in TIP-1070, the precompile MUST persist only the current record and MUST NOT append a record per epoch. Every write MUST overwrite the previous value and MUST zero every element slot that the previous array used and the new one does not. This applies to TIP-1070's `publicKeys` as well. Once written, `dkgPlayers` is never empty, so an empty `dkgPlayers` means slots `2` and `3` are uninitialized.

## Interface

From activation, the precompile MUST also dispatch:

```solidity
error Uninitialized();

/// @notice The DKG ceremony running during `epoch`.
/// @return dealers The committee of `epoch`, which deals in the ceremony.
/// @return players The players of the ceremony, who receive shares for `epoch + 1`.
function getDkgCeremony()
    external view
    returns (uint64 epoch, bytes32[] memory dealers, bytes32[] memory players, bool isFullDkg);
```

`getDkgCeremony()` MUST return slots `0` to `3` in order, with `dealers` read from TIP-1070's `publicKeys`, and MUST revert with `Uninitialized()` while `dkgPlayers` is empty. Before activation, the precompile MUST treat its selector as unknown. The precompile MUST NOT expose any entrypoint that writes slots `2` or `3`.

`dealers` duplicates `getCommitteeMembers()` so that callers get the full ceremony from one state, rather than from two calls that may be evaluated at different blocks.

## System operation

At the end of each activated `B(E)`, TIP-1070's post-execution hook MUST:

1. Decode `extra_data` as `DkgOutcome` instead of the legacy `OnchainDkgOutcome`, and call `setCommitteeMembers(outcome.epoch, output.players())` as TIP-1070 specifies.
2. Read ValCfgV2 from the post-transaction state of `B(E)`, and write slots `2` and `3` directly:
   - `dkgPlayers`: the public keys of all validators returned by `getActiveValidators()`, sorted as in the table above.
   - `isFullDkg`: `getNextNetworkIdentityRotationEpoch() == outcome.epoch`. Any other value, including `0` or a past epoch, selects a reshare.

The epoch is taken from the outcome, which consensus verifies, not computed from the height. Snapshotting after the block's transactions replaces [TIP-1017's player selection](./tip-1017.md#dkg-player-selection) at the parent of `B(E)`: registry changes in `B(E)` itself apply to the ceremony in `E+1`. As with the committee, transactions in `B(E)` observe the ceremony record for `E`.

Step 2 is not a call: it has no calldata and no entrypoint. Like TIP-1070's system call, it MUST NOT count against the block gas limit, transfer value, or mint or consume [TIP-1060](./tip-1060.md) storage credits. The two steps write disjoint slots, so their order does not affect the state root.

`B(E)` MUST be rejected if `extra_data` does not decode as exactly one `DkgOutcome`, a ValCfgV2 read reverts, a key is not a valid Ed25519 public key, two active validators share a key, or the number of keys is `0` or exceeds `u16::MAX`. The hook MUST NOT fall back to a filtered or deduplicated set, the previous record, or a reshare. Outside activated boundaries, it MUST NOT modify slots `2` and `3`.

## Consensus

When it enters epoch `E+1`, consensus takes the committee and public polynomial from `O(E+1)` in the header of `B(E)`, and the players and mode of the ceremony running during `E+1` from the precompile in finalized state, whose `epoch` MUST be `E+1`. Neither is recomputed from the current registry, including after a restart. Recovering a share revealed in the ceremony that produced `O(E+1)` needs no historical state: recovery applies only if that ceremony succeeded, so its players are `O(E+1).output.players()`, its dealers are `O(E).output.players()`, and it was a full DKG exactly when the network identity changed between `O(E)` and `O(E+1)`. Both outcomes are read from boundary headers.

Peer discovery takes the committee and the ceremony players from the precompile, where today it uses `players` and `next_players`.

## Activation

The activating hardfork is TBD and MUST be at or after T8, which deployed the precompile. A boundary `B(E)` is activated exactly when its own timestamp is at or after the fork; its parent's timestamp is irrelevant. That timestamp selects the outcome encoding, whether consensus reads ValCfgV2 at the parent of `B(E)`, and whether the system operation runs, including during replay and in header-based verifiers. The proposer MUST fix the timestamp of `B(E)` before constructing its outcome; verifiers take it from the proposed header.

If the parent of `B(E)` is before the fork and `B(E)` is after it, `B(E)` follows these rules in full: its outcome omits `next_players` and `is_next_full_dkg`, nobody reads the parent's state, and the ceremony in `E+1` is configured from the post-state of `B(E)`. The ceremony running during `E` keeps the configuration from the legacy outcome of `B(E-1)`.

Activation MUST NOT deploy code or write storage. In particular, it MUST NOT initialize slots `2` and `3` from the current registry or the latest legacy outcome; the first activated boundary initializes them. Until then, consensus MUST configure the ongoing ceremony from the legacy outcome of the last pre-activation boundary, and `getDkgCeremony()` MUST revert with `Uninitialized()` rather than return `getActiveValidators()` or any other inferred fallback.

If the hardfork is active from genesis, the genesis header MUST use the new encoding, and the genesis allocation MUST set all four slots for epoch `0` from the genesis DKG outcome and ceremony configuration.

# Tooling

Every decoder of boundary `extra_data` selects the encoding by the boundary's timestamp. This includes consensus, finalization verification, chainspec network identity, inspectors, and test helpers. Legacy fixtures remain for pre-activation blocks.

`tempo consensus info` SHOULD report the current dealers and the ceremony players and mode from the precompile. It SHOULD also list the validators currently active in ValCfgV2 as prospective players for the next epoch. Each entry includes its role and current network addresses, so partners can maintain firewall allowlists.

# Observability

On entering an epoch, nodes log the epoch, output digest, committee, ceremony players, and mode. The system operation emits no receipts or EVM events.

# Invariants

1. After every activated `B(E)`, the `extra_data` of `B(E)` equals the outcome every honest validator computed. The configuration record is derived from ValCfgV2 in the post-transaction state of `B(E)`. The shared `epoch` is `E+1`.
2. The configuration record changes only at activated boundaries or in genesis.
3. All validators run the ceremony during an epoch with the same players and mode, regardless of later registry changes or restarts.
