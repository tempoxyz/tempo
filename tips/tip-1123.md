# TIP-1123: Derive DKG configuration at epoch entry

## Abstract

When entering epoch `E`, derive its DKG players and ceremony mode from the executed state of the finalized boundary block of epoch `E-1`. Remove `next_players` and `is_next_full_dkg` from the on-chain DKG outcome, leaving only the epoch and cryptographic output. Activate the new encoding and configuration rules together through a hardfork.

## Motivation

The validator currently reads validator configuration at the parent of a proposed boundary block: [`next_players`](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1258-L1262) and the [next full DKG epoch](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1244-L1251) populate the redundant fields in the [on-chain outcome](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/dkg-onchain-artifacts/src/lib.rs#L29-L45). Both proposal construction and verification depend on those reads, even though the fields repeat information already committed by execution state. A failed schedule read currently defaults to resharing.

Epoch entry already requires the previous epoch's boundary to be finalized. Reading configuration at that boundary removes the validator's dependency on speculative execution state when producing or verifying a DKG outcome. The result is a smaller artifact and one authoritative configuration snapshot for each ceremony.

## Assumptions

- Consensus finalizes the boundary before entering the next epoch. Finalization alone does not imply execution has made its post-state available; epoch initialization waits for both.
- Validator configuration and its decoding rules remain authoritative for active DKG players and scheduled network identity rotation. This TIP does not change administrative permissions or validator eligibility rules.
- The node can obtain the boundary post-state when initializing or reconstructing an epoch. Missing or pruned state requires synchronization or recovery of that state, not substitution of a newer snapshot.
- All validators upgrade before activation. Historical headers and genesis retain their existing encoding unless a new chain explicitly activates this TIP at genesis.

# Specification

## Epoch configuration

Let `B(E-1)` be the last block of epoch `E-1`, and let `S(B)` be the state after executing that block, including its system calls. For an epoch governed by this TIP, initialization MUST:

1. Authenticate the finalized boundary `B(E-1)` and its hash, and decode its DKG outcome. The outcome's `epoch` MUST equal `E`.
2. Wait until execution has made `S(B(E-1))` available. Resolve the state by the authenticated block hash, not by the current head or a height whose canonical mapping can change.
3. Read the active validators and scheduled network identity rotation epoch from ValCfgV2 at that same snapshot. Enumerate only the active set at the boundary; do not scan all active and inactive entries.
4. Derive the ordered, deduplicated player set using the existing active-validator selection and public-key decoding rules. This is the current [`next_players` selection](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/mod.rs#L201-L213) with an empty set of additional known peers, evaluated at the boundary instead of its parent.
5. Set the ceremony mode to full DKG exactly when the scheduled network identity rotation epoch in `S(B(E-1))` equals `E`; otherwise select resharing. The validator currently reads this value through [`next_full_dkg_epoch`](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/mod.rs#L215-L232).
6. Retain this configuration for epoch `E` before participating in its DKG ceremony or consensus. Do not refresh it during the epoch.

A failed configuration read MUST leave initialization pending or return an explicit error. It MUST NOT select resharing, an empty player set, or configuration from another block as a fallback. Retries MUST remain pinned to the same boundary hash. An unusable configuration MUST prevent ceremony initialization under the existing validity constraints.

The consensus committee and DKG dealers for `E` remain determined by the preceding ceremony's outcome under the existing rules. The newly derived player set participates in the ceremony running during `E`, whose successful output becomes usable in `E+1`. These sets MUST NOT be conflated. A full ceremony continues to construct its transcript without a previous output; a reshare continues to use the previous output. Dealer selection, transcript versions, thresholds, share verification, and ceremony failure behavior otherwise remain unchanged.

If execution changes validator configuration in a boundary block, those changes apply when entering the following epoch. Configuration changes after that boundary cannot change the already initialized ceremony. This explicitly moves the sampling point from the parent's post-state to the boundary's post-state.

Equivalently, the ceremony players of epoch `E+1` are the ValCfgV2 entries marked active in the post-state of `B(E)`. Read that snapshot when entering `E+1`, before processing its first block, whose parent is `B(E)`. Reading the post-state of the first block or any later block of `E+1` is not equivalent: rotation or deactivation may already have removed entries from the active set. The ceremony mode is likewise fixed from the rotation schedule at `B(E)`.

Having the boundary block available does not by itself guarantee access to its post-state: the existing [boundary header lookup](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1565-L1593) can succeed independently of the [state lookup](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/validators.rs#L145-L165). Validators MUST retain the derived configuration for the epoch, including across restart, or retain or recover the boundary state needed to reconstruct it. They MUST NOT reconstruct it from a later active set.

## On-chain outcome

```rust
struct OnchainDkgOutcome {
    epoch: u64,
    output: Output<MinSig, PublicKey>,
}
```

The encoding is identical to the previous version, with the `next_players` and `is_next_full_dkg` fields omitted.

## Consumers and recovery

The validator MUST use the applicable artifact encoding when verifying proposals, initializing DKG, executing blocks, or recovering historical ceremonies. Tooling that reads boundary headers MUST use the same encoding rules. The epoch and consensus committee exposed in execution state remain unchanged.

The validator MUST use the same epoch configuration to identify ceremony participants for communication. The consensus layer continues to use the epoch's consensus committee, while the validator must also be able to communicate with ceremony players outside that committee. Address updates MUST NOT redefine the ceremony's player set.

Startup, restart, and fast sync MUST initialize the epoch using its preceding finalized boundary, even when execution has advanced further. Persisted configuration is a cache and MUST be associated with the epoch, boundary hash, and applicable rules. Stale or incompatible cached configuration MUST be rebuilt before replaying local ceremony state; a usable private share still requires verification against the on-chain polynomial.

Reconstructing a historical ceremony for public-dealing share recovery MUST use the configuration that governed that ceremony: legacy artifact fields before activation, or the post-state of its preceding finalized boundary after activation. This is the same epoch-initialization rule applied to a historical epoch, and may require an older boundary snapshot. Missing recovery state MUST NOT be replaced with current configuration or cause an invalid share to be accepted; the node may continue as an observer under existing rules when its current epoch configuration is available.

At genesis, use the trusted genesis block and its post-state in place of a preceding boundary when this TIP is active from genesis. Otherwise retain existing genesis initialization and historical artifact decoding.

## Hardfork activation and compatibility

The activating hardfork is not yet scheduled. Let `H` denote its configured activation condition. For each boundary block, use the chain specification and that block's own timestamp to determine whether `H` is active. Proposal construction MUST determine the candidate timestamp before selecting the artifact format; verification uses the timestamp committed in the header.

| Boundary rules | Artifact written and validated | Configuration for the following epoch |
| --- | --- | --- |
| Before `H` | Existing epoch, output, next players, and full-DKG flag | Existing legacy artifact fields and validation rules |
| At or after `H` | Epoch and output only | That finalized boundary's executed post-state |

The first boundary at or after activation uses the new format even if its ending epoch began under legacy rules. That epoch's existing DKG transcript and cached configuration remain unchanged; the resulting reduced artifact seeds the next epoch, which derives its configuration from the finalized boundary. Activation between boundaries MUST NOT restart or reconfigure an in-flight ceremony.

Codec selection MUST depend on the block's applicable hardfork rules, never on a trial decode or the node's current wall clock. Historical replay MUST preserve pre-fork encodings and validation behavior, including legacy configuration reads. The new rules MUST NOT reinterpret legacy artifacts or accept their redundant suffix after activation. Execution and consensus MUST switch their artifact decoders together.

This is a consensus change: header bytes change, and the configuration sampling point changes. It cannot be deployed as an unconditional local refactor. No migration of historical headers or new precompile storage layout is required.

# Tooling

Update boundary artifact codecs, inspectors, fixtures, and DKG test helpers to accept block hardfork context. Update full-ceremony tests to inspect the boundary configuration and resulting ceremony behavior instead of asserting `is_next_full_dkg` in new artifacts. Preserve legacy fixtures for historical replay.

Recovery and state-pruning documentation MUST identify the finalized boundary snapshots needed for current epoch initialization and historical share recovery. Operators must be able to distinguish unavailable execution state from an invalid DKG outcome. No new public transaction, contract ABI, or user command is required.

# Observability

The following structured events MUST be available; existing DKG logs may be extended to provide them:

- Epoch configuration initialized: epoch, boundary height and hash, applicable hardfork, configuration source (`legacy_artifact` or `boundary_state`), player count, scheduled rotation epoch when read from state, and derived ceremony mode. This identifies the snapshot and rules used to start a ceremony.
- Epoch configuration unavailable or invalid: epoch, boundary height and hash, failed operation, and error. Emit on the initial failure and changes in failure reason, with repeated retries rate-limited. This distinguishes execution lag or pruned state from invalid configuration.

Retain existing ceremony success, failure, and outcome-mismatch reporting. Never log private shares or private dealings. Success means valid boundaries can be proposed and verified without DKG configuration state reads, while nodes agree on epoch configuration after execution of the finalized boundary.

# Threat Model

Boundary proposers and DKG participants may be Byzantine. Verifiers still authenticate finalization, validate dealer logs, and independently check the cryptographic outcome; a proposer cannot provide an alternative player set or ceremony mode in the reduced artifact.

Validator configuration administrators retain their existing authority to select active validators and schedule rotation. The committed boundary state defines the effect of authorized changes. This TIP grants no new permissions.

Execution providers and local storage are trusted to serve state matching the authenticated boundary root. Lag, pruning, and stale caches are availability hazards and MUST NOT produce a different ceremony configuration. A finalized header obtained from consensus is insufficient until its matching execution state is available. Existing consensus and DKG fault thresholds remain unchanged.

# Invariants

The implementation and test suite MUST establish:

1. New-format outcome construction and verification perform zero execution-state configuration reads, both for cached outcomes and when reconstructing them from dealer logs. An unavailable parent state must not prevent these DKG operations.
2. Each epoch's players and mode come from one authenticated boundary snapshot. Nodes with different execution heads, including after restart or fast sync, derive identical configuration.
3. Epoch entry waits for boundary finality and executed state. Read failures, including rotation-schedule failures, never silently change ceremony mode; retries resume initialization using the same hash.
4. Boundary configuration changes affect the following epoch, while later changes do not affect an in-flight round. Test player additions, removals, and rotation schedules before, equal to, and after the entering epoch, including rotation or deactivation in its first block and restart after that change. Configuration selection must enumerate only the boundary's active set.
5. Successful full DKG, successful resharing, and failed ceremonies preserve their existing polynomial, committee, and private-share behavior. A changed active player set must not replace the committee from a carried output after failure.
6. New artifacts round-trip at varint boundaries and existing validator limits, reject malformed output and legacy suffixes, and retain all cryptographic participant data. Pre-fork artifacts remain byte-for-byte compatible.
7. Activation before, on, and between epoch boundaries selects the correct format and next-epoch configuration without changing an in-flight transcript. Test the first new-format boundary, historical replay, and genesis activation.
8. The validator uses consistent epoch and participant information for consensus, execution, ceremony communication, startup, and historical share recovery across the transition. Test stale persisted state, missing boundary snapshots, and recovery of a ceremony on either side of activation.
