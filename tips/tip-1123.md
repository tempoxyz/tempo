# TIP-1123: Derive DKG configuration at epoch entry

## Abstract

This TIP removes unnecessary information from the on-chain DKG artifact by relying on finalized execution data. This simplifies implementation by eliminating reads of speculative execution state.

## Motivation

Let `B(E-1)` denote the boundary block (the last block) of epoch `E-1`.

The validator currently reads validator configuration at the parent of proposed `B(E-1)`: [`next_players`](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1258-L1262) and the [next full DKG epoch](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1244-L1251) populate the redundant fields for epoch `E` in the [on-chain outcome](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/dkg-onchain-artifacts/src/lib.rs#L29-L45) written into `B(E-1)`. Both proposal construction and verification depend on those reads, even though the fields repeat information already committed by execution state. A failed schedule read currently defaults to resharing.

Entering epoch `E` already requires `B(E-1)` to be finalized. Reading configuration at `B(E-1)` removes the validator's dependency on speculative execution state when producing or verifying a DKG outcome. The result is a smaller artifact and one authoritative configuration snapshot for each ceremony.

## Assumptions

1. `B(E-1)` is finalized by consensus.
2. `B(E-1)` is executed by the execution layer and its state is available.
3. Validator configuration and its decoding rules remain authoritative for active DKG players and scheduled network identity rotation.
4. This TIP does not change administrative permissions or validator eligibility rules.
5. The validator can obtain the post-state of `B(E-1)` when initializing or reconstructing epoch `E`.
6. Missing or pruned state requires synchronization or recovery of that state, not substitution of a newer snapshot.
7. All validators upgrade before activation.
8. Historical headers and genesis retain their existing encoding unless a new chain explicitly activates this TIP at genesis.

# Specification

## Epoch configuration

Let `S(B)` denote the state after executing block `B`, including its system calls. To initialize epoch `E` under this TIP, the validator MUST:

1. Authenticate the finalized boundary `B(E-1)` and its hash, and decode its DKG outcome. The outcome's `epoch` MUST equal `E`.
2. Wait until execution has made `S(B(E-1))` available. Resolve the state by the authenticated block hash, not by the current head or a height whose canonical mapping can change.
3. Read the active validators and scheduled network identity rotation epoch from ValCfgV2 in `S(B(E-1))`. Enumerate only the active set at `B(E-1)`; do not scan all active and inactive entries.
4. Derive the ordered, deduplicated player set using the existing active-validator selection and public-key decoding rules. This is the current [`next_players` selection](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/mod.rs#L201-L213) with an empty set of additional known peers, evaluated at `B(E-1)` instead of its parent.
5. Set the ceremony mode to full DKG exactly when the scheduled network identity rotation epoch in `S(B(E-1))` equals `E`; otherwise select resharing. The validator currently reads this value through [`next_full_dkg_epoch`](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/mod.rs#L215-L232).
6. Retain this configuration for epoch `E` before participating in its DKG ceremony or consensus. Do not refresh it during the epoch.

A failed configuration read MUST leave initialization pending or return an explicit error. It MUST NOT select resharing, an empty player set, or configuration from another block as a fallback. Retries MUST remain pinned to the hash of `B(E-1)`. An unusable configuration MUST prevent ceremony initialization under the existing validity constraints.

The consensus committee and DKG dealers for `E` remain determined by the preceding ceremony's outcome under the existing rules. The newly derived player set participates in the ceremony running during `E`, whose successful output becomes usable in `E+1`. These sets MUST NOT be conflated. A full ceremony continues to construct its transcript without a previous output; a reshare continues to use the previous output. Dealer selection, transcript versions, thresholds, share verification, and ceremony failure behavior otherwise remain unchanged.

If execution changes validator configuration in `B(E-1)`, those changes apply when entering epoch `E`. Configuration changes after `B(E-1)` cannot change the already initialized ceremony. This explicitly moves the sampling point from the post-state of the parent of `B(E-1)` to `S(B(E-1))`.

Equivalently, the ceremony players of epoch `E+1` are the ValCfgV2 entries marked active in the post-state of `B(E)`. Read that snapshot when entering `E+1`, before processing its first block, whose parent is `B(E)`. Reading the post-state of the first block or any later block of `E+1` is not equivalent: rotation or deactivation may already have removed entries from the active set. The ceremony mode is likewise fixed from the rotation schedule at `B(E)`.

Having `B(E-1)` available does not by itself guarantee access to `S(B(E-1))`: the existing [boundary header lookup](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1565-L1593) can succeed independently of the [state lookup](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/validators.rs#L145-L165). Validators MUST retain the derived configuration for epoch `E`, including across restart, or retain or recover `S(B(E-1))` to reconstruct it. They MUST NOT reconstruct it from a later active set.

## On-chain outcome

```rust
struct OnchainDkgOutcome {
    epoch: u64,
    output: Output<MinSig, PublicKey>,
}
```

The encoding is identical to the previous version, with the `next_players` and `is_next_full_dkg` fields omitted.

## Consumers and recovery

The validator MUST use the applicable artifact encoding when verifying proposals, initializing DKG, executing blocks, or recovering historical ceremonies. Tooling that reads boundary headers MUST use the same encoding rules. The epoch and consensus committee exposed in execution state remain unchanged.

The validator MUST use the same epoch configuration to identify ceremony participants for communication. The consensus layer continues to use the epoch's consensus committee, while the validator must also be able to communicate with ceremony players outside that committee. Address updates MUST NOT redefine the ceremony's player set.

Startup, restart, and fast sync MUST initialize epoch `E` using finalized `B(E-1)`, even when execution has advanced further. Persisted configuration is a cache and MUST be associated with `E`, the hash of `B(E-1)`, and the applicable rules. Stale or incompatible cached configuration MUST be rebuilt before replaying local ceremony state; a usable private share still requires verification against the on-chain polynomial.

Reconstructing the ceremony of a historical epoch `E` for public-dealing share recovery MUST use the configuration that governed that ceremony: legacy artifact fields in `B(E-1)` before activation, or `S(B(E-1))` after activation. This is the same epoch-initialization rule applied to a historical epoch, and may require an older snapshot of `S(B(E-1))`. Missing recovery state MUST NOT be replaced with current configuration or cause an invalid share to be accepted; the node may continue as an observer under existing rules when its current epoch configuration is available.

At genesis, use the trusted genesis block and its post-state in place of a preceding boundary when this TIP is active from genesis. Otherwise retain existing genesis initialization and historical artifact decoding.

## Hardfork activation and compatibility

The activating hardfork is not yet scheduled. Let `H` denote its configured activation condition. For each `B(E-1)`, use the chain specification and the timestamp of `B(E-1)` to determine whether `H` is active. Proposal construction MUST determine the candidate timestamp before selecting the artifact format; verification uses the timestamp committed in the header.

| Rules at `B(E-1)` | Artifact written and validated in `B(E-1)` | Configuration for epoch `E` |
| --- | --- | --- |
| Before `H` | Existing epoch, output, next players, and full-DKG flag | Existing legacy artifact fields and validation rules |
| At or after `H` | Epoch and output only | `S(B(E-1))`, once `B(E-1)` is finalized |

If `B(E-1)` is the first boundary at or after activation, it uses the new format even if epoch `E-1` began under legacy rules. The existing DKG transcript and cached configuration for `E-1` remain unchanged; the resulting reduced artifact seeds epoch `E`, which derives its configuration from `S(B(E-1))` once `B(E-1)` is finalized. Activation between `B(E-1)` and `B(E)` MUST NOT restart or reconfigure the in-flight ceremony of epoch `E`.

Codec selection MUST depend on the block's applicable hardfork rules, never on a trial decode or the node's current wall clock. Historical replay MUST preserve pre-fork encodings and validation behavior, including legacy configuration reads. The new rules MUST NOT reinterpret legacy artifacts or accept their redundant suffix after activation. Execution and consensus MUST switch their artifact decoders together.

This is a consensus change: header bytes change, and the configuration sampling point changes. It cannot be deployed as an unconditional local refactor. No migration of historical headers or new precompile storage layout is required.

# Tooling

Update boundary artifact codecs, inspectors, fixtures, and DKG test helpers to accept block hardfork context. Update full-ceremony tests for epoch `E` to inspect the configuration at `B(E-1)` and resulting ceremony behavior instead of asserting `is_next_full_dkg` in new artifacts. Preserve legacy fixtures for historical replay.

Recovery and state-pruning documentation MUST identify the snapshots of `S(B(E-1))` needed for each epoch `E` being initialized or reconstructed for historical share recovery. Operators must be able to distinguish unavailable execution state from an invalid DKG outcome. No new public transaction, contract ABI, or user command is required.

# Observability

The following structured events MUST be available; existing DKG logs may be extended to provide them:

- Epoch configuration initialized: epoch `E`, height and hash of `B(E-1)`, applicable hardfork, configuration source (`legacy_artifact` or `boundary_state`), player count, scheduled rotation epoch when read from state, and derived ceremony mode. This identifies the snapshot and rules used to start a ceremony.
- Epoch configuration unavailable or invalid: epoch `E`, height and hash of `B(E-1)`, failed operation, and error. Emit on the initial failure and changes in failure reason, with repeated retries rate-limited. This distinguishes execution lag or pruned state from invalid configuration.

Retain existing ceremony success, failure, and outcome-mismatch reporting. Never log private shares or private dealings. Success means `B(E-1)` can be proposed and verified without DKG configuration state reads, while validators agree on configuration for epoch `E` after finalizing and executing `B(E-1)`.

# Threat Model

Boundary proposers and DKG participants may be Byzantine. Verifiers still authenticate finalization, validate dealer logs, and independently check the cryptographic outcome; a proposer cannot provide an alternative player set or ceremony mode in the reduced artifact.

Validator configuration administrators retain their existing authority to select active validators and schedule rotation. `S(B(E-1))` defines the effect of authorized changes on epoch `E`. This TIP grants no new permissions.

Execution providers and local storage are trusted to serve `S(B(E-1))` matching the state root in authenticated `B(E-1)`. Lag, pruning, and stale caches are availability hazards and MUST NOT produce a different ceremony configuration. The finalized header of `B(E-1)` is insufficient until `S(B(E-1))` is available. Existing consensus and DKG fault thresholds remain unchanged.

# Invariants

The implementation and test suite MUST establish:

1. New-format outcome construction and verification perform zero execution-state configuration reads, both for cached outcomes and when reconstructing them from dealer logs. An unavailable parent state must not prevent these DKG operations.
2. The players and mode of epoch `E` come from `S(B(E-1))`. Nodes with different execution heads, including after restart or fast sync, derive identical configuration.
3. Entry into epoch `E` waits for finality of `B(E-1)` and availability of `S(B(E-1))`. Read failures, including rotation-schedule failures, never silently change ceremony mode; retries resume initialization using the hash of `B(E-1)`.
4. Configuration changes in `B(E-1)` affect epoch `E`, while later changes do not affect its in-flight round. Test player additions, removals, and rotation schedules before, equal to, and after `E`, including rotation or deactivation in its first block and restart after that change. Configuration selection must enumerate only the active set at `B(E-1)`.
5. Successful full DKG, successful resharing, and failed ceremonies preserve their existing polynomial, committee, and private-share behavior. A changed active player set must not replace the committee from a carried output after failure.
6. New artifacts round-trip at varint boundaries and existing validator limits, reject malformed output and legacy suffixes, and retain all cryptographic participant data. Pre-fork artifacts remain byte-for-byte compatible.
7. Activation before, on, and between epoch boundaries selects the correct format and next-epoch configuration without changing an in-flight transcript. Test the first new-format boundary, historical replay, and genesis activation.
8. The validator uses consistent epoch and participant information for consensus, execution, ceremony communication, startup, and historical share recovery across the transition. Test stale persisted state, missing boundary snapshots, and recovery of a ceremony on either side of activation.
