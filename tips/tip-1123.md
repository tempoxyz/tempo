# TIP-1123: Store DKG outcomes and configuration in execution state

## Abstract

Boundary block `extra_data` carries the effective epoch and public DKG output. Validators compare those bytes against their independently computed outcome before execution, allowing DKG disagreements to be reported directly. An EIP-4788-style system operation writes the same outcome to fixed execution-layer storage and snapshots the expected players from ValCfgV2 for the next ceremony. Non-boundary `extra_data` continues to carry dealer logs.

## Motivation

Consumers currently locate and decode historical boundary blocks to discover the current outcome and ceremony configuration. Keeping the outcome in boundary `extra_data` provides an explicit value for consensus verification and an execution input available during replay. Persisting it in execution state lets ordinary consumers read the current outcome without locating a boundary header.

Keeping these records in execution state gives consensus, recovery, and tooling a stable location to read. The block's state root commits to the selected outcome and the expected players. Consensus remains responsible for selecting and verifying the DKG outcome; the execution layer persists it and derives ceremony configuration from ValCfgV2.

## Assumptions

- Consensus computes the expected public DKG outcome, including the existing fallback when a ceremony fails, before executing an epoch transition.
- ValCfgV2 remains authoritative for the configured active validators and scheduled network identity rotation. Its active set can differ from the effective committee selected by DKG. The protocol relies on ValCfgV2 to enforce the registry well-formedness requirements below. Genesis setup or migration MUST establish a usable registry before this TIP can activate.
- Proposal building, verification, and replay use the outcome encoded in the boundary block. Missing or malformed boundary data, or unavailable configuration state, prevents validation or epoch initialization; it MUST NOT silently select another outcome or ceremony mode.

## Threat model

- A proposer may supply an incorrect outcome or omit the required update. Validators compare the header bytes with their independently computed outcome, and execution checks that the mandatory storage writes produce the proposed state root.
- The ValCfgV2 owner may change the configured active validators and rotation schedule. Changes made in a boundary block intentionally affect the ceremony starting in the rising epoch, but do not change the outcome already selected for that epoch or reconfigure an ongoing ceremony. Registry well-formedness is a chain-liveness assumption: an unrecoverable registry error can prevent a valid boundary block, and this failure policy is intentional.
- User transactions and contract callers MUST NOT be able to write the dedicated records. Reads from an untrusted execution provider require a storage proof against an authenticated state root.
- Failed ceremonies retain the existing consensus fallback rules. Expected players MUST NOT be mistaken for the players in a successful outcome.

# Specification

## Epoch transition

Let `B(E)` denote the last block of epoch `E`, at height `h` where `h % epoch_length == epoch_length - 1`. Let `O(E+1)` denote the public DKG outcome selected by consensus for use in epoch `E+1`.

The execution layer MUST update the dedicated state at the end of `B(E)`, after all user transactions and any system operations that modify ValCfgV2. Transactions in `B(E)` continue to observe the records for `E`; its committed post-state contains the records for `E+1`. The first block of `E+1` and subsequent non-boundary blocks retain those records unchanged.

Using the boundary's post-state is an intentional change from selecting configuration at its parent. An addition, deactivation, validator-key rotation, or network-identity rotation schedule change committed in `B(E)` MUST affect the ceremony running during `E+1`. The already selected `O(E+1)` is unchanged by those transactions. A registry change in the first block of `E+1` cannot affect that ongoing ceremony; it is eligible for the snapshot at `B(E+1)`.

This follows the post-execution timing of [TIP-1070](./tip-1070.md). The fixed locations are persistent account storage committed by the state root, not transient EVM memory. Consumers can read the records from available state without fetching the preceding boundary header. Both records name their effective epoch; the boundary's post-state already describes the rising epoch. The EL uses the existing height-and-epoch-length predicate to detect boundaries, but MUST obtain the epoch number from the CL-supplied outcome rather than calculate it from height.

## DKG outcome input

For `B(E)`, the proposer MUST place the canonical encoding of `O(E+1)` in `TempoPayloadAttributes.extra_data`, and the builder MUST copy those bytes into the block header:

```rust
struct DkgOutcome {
    epoch: u64,
    output: Output<MinSig, PublicKey>,
}

// Consensus sets outcome.epoch to E+1.
extra_data = outcome.encode();
```

For `B(E)`, consensus MUST set and verify `outcome.epoch = E+1`. Empty or malformed boundary `extra_data` is invalid. Block height determines whether `extra_data` is an outcome or a dealer log; implementations MUST NOT infer its role by trying both decoders.

The `output` is the existing public DKG `Output<MinSig, PublicKey>`, including its public polynomial and ordered participant sets. Private shares MUST NOT be included. The canonical encoding is the existing unsigned-varint `epoch` encoding followed by the existing Commonware `output` encoding, with the same decoding limits and mode version. The `next_players` and `is_next_full_dkg` fields are omitted; configuration is stored separately. Decoders MUST consume the entire value and reject malformed or non-canonical encodings.

Outcome selection uses the existing ceremony rules and dealer logs available through the parent of `B(E)`. Boundary blocks carry the outcome and no dealer log. This TIP does not change the success threshold, resharing rules, or failed-ceremony fallback.

Building, block import, and replay MUST obtain both the epoch and output from the boundary block's `extra_data`. No additional DKG outcome field is required in `TempoPayloadAttributes` or `TempoExecutionData`. Payload caching MUST distinguish builds with different boundary outcome bytes.

## Fixed storage

This TIP assigns two dedicated system-state addresses adjacent to TIP-1070's current-committee address:

```solidity
address constant DKG_OUTCOME_ADDRESS = 0xc077E00000000000000000000000000000000001;
address constant DKG_CONFIG_ADDRESS = 0xC077E00000000000000000000000000000000002;
```

The outcome record at `DKG_OUTCOME_ADDRESS` is a Solidity-layout `bytes` value rooted at slot `0`, containing the canonical encoding of `DkgOutcome`: its effective epoch followed by the full public output. These bytes MUST match the boundary header's `extra_data` exactly.

The configuration record at `DKG_CONFIG_ADDRESS` uses this layout:

| Slot | Value |
| --- | --- |
| `0` | Ceremony epoch, encoded as a zero-extended `uint64` |
| `1` | Expected players, using the Solidity storage layout of `bytes32[]` |
| `2` | Full-DKG flag, encoded as `0` or `1` |

Each update MUST replace the previous record, including clearing unused storage when a dynamic value shrinks. Implementations MUST NOT append a record per epoch. Historical values remain available only through historical execution state or authenticated snapshots.

These locations define a storage interface for node providers, `eth_getStorageAt`, and `eth_getProof`; this TIP does not introduce a public contract ABI. They are system-owned accounts with empty code and nonce `1`, written directly by the protocol hook. Ordinary EVM execution MUST NOT be able to overwrite the records or deploy code at these addresses.

An empty outcome value means the records have not yet been initialized. Readers MUST check this before interpreting the configuration record; a zero epoch or empty player array alone is not an initialization marker. Once initialized, both records MUST be present and their epochs MUST match.

## System operations

At the end of `B(E)`, the execution layer MUST perform both updates:

1. Decode and validate the outcome encoding in the boundary header's `extra_data`, then overwrite the outcome record with those exact bytes.
2. Read ValCfgV2 after the block's transactions and configuration-changing system operations, and overwrite the configuration record with `outcome.epoch`, the expected players derived from its active validators, and the full-DKG flag.

Expected players MUST use the existing Ed25519 public-key decoding and canonical ordering rules. The full-DKG flag is `1` exactly when ValCfgV2's scheduled network identity rotation epoch equals `outcome.epoch`; otherwise it is `0`. Read or decoding failures invalidate the transition. Consensus verifies the supplied epoch; the EL derives the players and ceremony mode from ValCfgV2 for that epoch.

These updates follow the [EIP-4788 system-operation model](https://eips.ethereum.org/EIPS/eip-4788#block-processing): they are protocol-controlled, absent from the transaction list, do not count against the block gas limit, and do not transfer value or apply EIP-1559 burn semantics. The protocol hook performs the direct storage writes defined above; there is no deployed writer contract or calldata interface. Both updates MUST complete successfully before calculating the block's state root; a failed update MUST invalidate the block.

Where TIP-1070 is active, its committee writer MUST decode `DkgOutcome` from the boundary's `extra_data` under this TIP's encoding rules. Its stored epoch MUST equal `outcome.epoch`, and its public keys MUST equal `outcome.output.players()` in the new outcome record. This TIP updates TIP-1070's outcome encoding while preserving its CL-supplied epoch, committee interface, and visibility timing.

### Registry validity and failure policy

The active registry MUST enumerate between `1` and `65535` distinct, decodable Ed25519 public keys, with consistent active-index references. The snapshot MUST include every active key exactly once, sorted using the existing Commonware public-key ordering; it MUST NOT depend on registry enumeration order, skip undecodable entries, or silently deduplicate keys. The rotation schedule MUST be readable as a `uint64`; any value other than `outcome.epoch`, including an unset or past epoch, selects resharing.

From activation, ValCfgV2 MUST reject mutations that violate these invariants, including a mutation that removes the last active validator. Genesis setup and migration MUST establish the invariants before activation. These are requirements on the registry, not permission for the snapshot writer to repair invalid state. Before activation, the implementation MUST establish that every subsequently available registry-writing path preserves them and that the existing registry satisfies them.

If registry execution deterministically fails, a key cannot be decoded, or an invariant is violated, the boundary block is invalid. There is no fallback to resharing, the previous player snapshot, or a filtered registry. The possible loss of chain liveness is accepted: the protocol relies on ValCfgV2 to keep the registry well formed. A local missing-state or database-access failure instead means the node cannot validate yet; it MUST recover its state and retry without treating that local failure as evidence that the proposed block is invalid.

## Verification and epoch entry

Before submitting `B(E)` for execution, each validator MUST compute its own expected `O(E+1)` using the existing DKG verification rules, including `epoch = E+1`, canonically encode it, and compare those bytes with the proposed header's `extra_data`. The comparison covers both epoch and output. A mismatch MUST reject the proposal with a distinct DKG-outcome mismatch diagnostic, including the expected and proposed outcome bytes. This check MUST also run when the execution layer has already executed the block; a cached `Valid` result does not replace consensus verification.

If the bytes match, the validator submits the proposed block through the existing `new_payload` path. The execution layer MUST write the header's outcome bytes and the ValCfgV2-derived configuration, then verify the computed state root against the proposed header. A state-root mismatch remains an execution failure; it MUST NOT be reported as a DKG-outcome disagreement. Consensus equality checks and execution validation MUST both succeed before the validator accepts the block.

After the first activated boundary, at entry into `E+1`, consensus MUST read the outcome and configuration records from the finalized execution state. Both records MUST name `E+1`. The outcome determines the effective committee and public key material; the configuration record determines the expected players and full-DKG or resharing mode for the ceremony running during `E+1`. Before that first boundary, the transition rules below preserve the current epoch's legacy configuration.

Later ValCfgV2 changes MUST NOT reconfigure that ceremony. Restart and recovery MUST use the stored configuration snapshot, rather than recomputing the expected players from the current registry. Historical configuration recovery requires execution state for the epoch being recovered, proofs against an independently authenticated state root, or replay from an authenticated checkpoint. Execution replay obtains each output directly from its boundary header; it does not need to rerun DKG to obtain the execution input. Consensus verification of that output remains separate. Header-based finalization verifiers MAY continue to read outcomes from authenticated boundary headers using the applicable encoding rules. An outcome cannot authenticate the state root used to prove that same outcome.

## Dealer logs

For non-boundary blocks, `extra_data` MUST be empty or contain a dealer log under the existing encoding, proposer/dealer identity, and signature validation rules. For boundary blocks, it MUST contain only the epoch-and-output DKG outcome specified above. Outcomes and dealer logs MUST NOT be concatenated in one header.

## Activation and compatibility

### Fork selection

`TIP1123_FORK_TIMESTAMP` is the chain-spec parameter activating these rules; a block is activated exactly when `block.timestamp >= TIP1123_FORK_TIMESTAMP`. The upgrade name and per-network timestamp are scheduling decisions, not implementation defaults. This Draft is unscheduled. Before the TIP becomes Scheduled, the upgrade decision MUST assign its `protocolVersion` and every target network's timestamp, and all clients MUST use the same chain-spec values. An unset parameter disables this TIP; implementations MUST NOT guess a timestamp or attach it implicitly to TIP-1070's hardfork.

Each boundary's own timestamp selects its outcome codec, including during historical replay. Before activation, decode the legacy artifact. After activation, decode exactly `DkgOutcome` and reject any trailing legacy fields. The caller's current hardfork or wall-clock time MUST NOT select the codec for a historical header.

### Account reservation and first write

For a non-genesis activation, the first activated block is the block whose timestamp reaches `TIP1123_FORK_TIMESTAMP` while its parent's timestamp is below it. Its pre-execution hook MUST reserve both system accounts by setting their nonce to `1`, leaving their code and storage empty and preserving any existing balance. Their pre-activation nonce MUST be zero and code and storage MUST be empty; a collision fails activation and MUST NOT be overwritten. Deployment readiness MUST check those conditions on each target network before scheduling.

There is no historical-state migration or outcome write at that hook. Both records remain uninitialized until the post-execution hook of the first activated boundary, which writes the boundary's own `DkgOutcome` and its final ValCfgV2 configuration. This matches TIP-1070's first-boundary initialization model and requires no earlier header or state lookup by the EL.

If activation occurs between boundaries, consensus MUST retain the outcome, players, and mode already selected for the ongoing epoch. It MUST NOT initialize a replacement ceremony from the current registry. Until the first activated boundary is finalized, consensus, peer discovery, and tooling MUST use the legacy epoch artifact, or the trusted genesis configuration for the initial epoch. Record decoders and tooling MUST report empty new storage as uninitialized, not interpret zeros as a valid configuration. When activation falls on a boundary, transactions in that block see uninitialized new records; the post-state contains the initialized records for the rising epoch.

### Pruning, sync, and genesis

A restarting or syncing node before the first activated boundary MUST recover the current epoch's legacy artifact using the existing pre-fork bootstrap rules. The source is the last boundary strictly before the start of that epoch, identified by the existing consensus epoch strategy, and decoded using that boundary's timestamp. If locally pruned, fetch its header and the intervening parent-linked headers from peers and verify their hashes against an independently authenticated descendant checkpoint. A checkpoint that does not authenticate that ancestry is insufficient. The initial epoch instead uses the trusted genesis configuration. Missing data pauses local initialization until it is recovered; it MUST NOT trigger a registry-derived fallback or mark an otherwise valid block invalid.

After the first activated boundary, a fast-sync checkpoint MUST include both records with proofs against its authenticated state root, or the node MUST replay from an earlier authenticated checkpoint through an activated boundary. No client needs the legacy boundary artifact to perform the new EL writes. A node MUST NOT prune the only locally available current-epoch configuration before either retaining an authenticated copy or completing the transition to the new records.

If active from genesis, the genesis allocation MUST reserve both accounts with nonce `1` and empty code and initialize their records from the chain's trusted genesis DKG outcome and ceremony configuration. Both epochs MUST match the initial consensus epoch; players and mode MUST match the genesis ceremony configuration. Genesis allocation, rather than a synthetic boundary call, establishes this state.

# Tooling

Update current-outcome consumers, peer discovery, and epoch management to read the fixed records, with the bounded legacy fallback specified for first-boundary initialization. Update consensus verification, header-based finalization verification, execution, replay, codecs, inspectors, fixtures, and DKG helpers to decode epoch-and-output boundary outcomes after activation; retain legacy fixtures for earlier blocks. No additional DKG argument is required on the executor's `new_payload` path.

Recovery and pruning documentation MUST identify the historical state or authenticated checkpoints required for each recovered epoch. Tools MUST distinguish unavailable state or consensus input from an invalid outcome.

`tempo consensus info` MUST report current dealers and ceremony players from the stored records, alongside validators currently marked active in ValCfgV2 as prospective players for the next epoch. Include their roles and current network addresses so partners can maintain firewall allowlists.

# Observability

Nodes MUST log each epoch transition with the block hash, effective epoch, outcome digest, effective committee, expected players, and ceremony mode. A DKG-outcome mismatch MUST identify the block, expected and proposed epochs, and both encoded outcome values so operators can compare the epoch and public output directly. Malformed boundary data, registry-invariant violations, deterministic registry-call failures, local unavailable state, uninitialized records, failed system writes, and state-root mismatches MUST be distinguishable from that consensus disagreement. These are node logs; the system writes do not introduce user-transaction receipts or Solidity events. Private shares MUST NOT be logged.

# Invariants

1. Every accepted activated boundary commits exactly the consensus-expected outcome and the configuration derived from that boundary's final ValCfgV2 state. Apart from genesis allocation, only activated boundaries initialize or change the records; reserving accounts at activation does not initialize them.
2. All validators use the same snapshotted players and ceremony mode throughout an epoch, including after registry changes, restart, and recovery. The first-boundary transition retains the legacy snapshot until the new records apply. Expected players remain distinct from the effective committee, including when DKG fails.
3. At every accepted post-activation boundary, the locally expected canonical outcome, header `extra_data`, and stored outcome bytes are identical, including the epoch. The configuration and TIP-1070 committee records use that same CL-supplied epoch. Building and replay produce the same state root from the same block, parent state, and chain spec, including at activation.

Tests MUST cover successful DKG, resharing, failed-ceremony fallback, malformed or missing boundary outcomes, explicit byte-mismatch diagnostics before execution and for already-executed blocks, a wrong epoch with an otherwise correct output, incorrect configuration epochs, epoch-and-output encoding, unauthorized writes, shrinking records, rejection of dealer logs in boundary headers, registry changes in and after a boundary, restart and historical recovery, and activation at genesis, on a boundary, and between boundaries. Execution tests MUST reject incorrect post-state caused by missing or incorrect storage writes through state-root validation even when the header outcome matches consensus. Where TIP-1070 is active, its committee record MUST agree with the stored output and supplied epoch.

Boundary-timing tests MUST put each of an addition, deactivation, validator-key rotation, and rotation-schedule change in `B(E)` and show its effect on the ceremony for `E+1`, while leaving `O(E+1)` unchanged. Repeat each change in the first block of `E+1` and show that the ongoing ceremony is unchanged. Registry tests MUST prove that every writing path preserves the stated invariants, then inject malformed keys, duplicate keys, invalid active indices, empty or oversized active sets, and getter failures to establish strict rejection without a fallback. Local missing-state tests MUST establish recovery and retry rather than an invalid-block verdict.

Activation tests MUST replay an actual pre-fork checkpoint and its following blocks through activation and the first activated boundary, comparing exact account storage and state roots between building, full replay, and checkpoint sync. Cover a missing local legacy header recovered through authenticated ancestry, unavailable recovery data, a post-boundary checkpoint with the new records, first-boundary registry changes, and account-address collisions. Assert that the first activated non-boundary block leaves both records uninitialized, that the first activated boundary needs no historical artifact to execute, and that historical codec selection never accepts trailing legacy fields as the new format.
