# TIP-1123: Store DKG outcomes and configuration in execution state

## Abstract

The proposer supplies its expected DKG outcome to the execution-layer builder through `TempoPayloadAttributes`. The execution layer writes that outcome to fixed storage, and validators check the resulting state against their independently computed expectation. An EIP-4788-style system operation also snapshots the expected players from ValCfgV2 for the next ceremony. Block `extra_data` carries only dealer logs, including on epoch boundaries.

## Motivation

Encoding DKG outcomes in boundary headers makes consumers locate and decode historical boundary blocks to discover the current outcome and ceremony configuration. It also makes `extra_data` serve two roles: dealer logs in ordinary blocks and outcomes in boundary blocks.

Keeping these records in execution state gives consensus, recovery, and tooling a stable location to read. The block's state root commits to the selected outcome and the expected players. Consensus remains responsible for selecting and verifying the DKG outcome; the execution layer persists it and derives ceremony configuration from ValCfgV2.

## Assumptions

- Consensus computes the expected public DKG outcome, including the existing fallback when a ceremony fails, before executing an epoch transition.
- ValCfgV2 remains authoritative for the configured active validators and scheduled network identity rotation. Its active set can differ from the effective committee selected by DKG.
- Proposal building, verification, and replay can provide the consensus input to execution. Missing input or unavailable state prevents validation or epoch initialization; it MUST NOT silently select another outcome or ceremony mode.

## Threat model

- A proposer may supply an incorrect outcome or omit the required update. Validators independently compute the expected outcome and reject a block whose resulting state differs.
- The ValCfgV2 owner may change the configured active validators and rotation schedule. These changes affect the next configuration snapshot, but do not directly change the effective committee or an ongoing ceremony.
- User transactions and contract callers MUST NOT be able to write the dedicated records. Reads from an untrusted execution provider require a storage proof against an authenticated state root.
- Failed ceremonies retain the existing consensus fallback rules. Expected players MUST NOT be mistaken for the players in a successful outcome.

# Specification

## Epoch transition

Let `B(E)` denote the last block of epoch `E`, at height `h` where `h % epoch_length == epoch_length - 1`. Let `O(E+1)` denote the public DKG outcome selected by consensus for use in epoch `E+1`.

The execution layer MUST update the dedicated state at the end of `B(E)`, after all user transactions and any system operations that modify ValCfgV2. Transactions in `B(E)` continue to observe the records for `E`; its committed post-state contains the records for `E+1`. The first block of `E+1` and subsequent non-boundary blocks retain those records unchanged.

This follows the post-execution timing of [TIP-1070](./tip-1070.md). The fixed locations are persistent account storage committed by the state root, not transient EVM memory. Consumers can read the records from available state without fetching the preceding boundary header. Reads MUST check the stored epoch: the boundary's post-state already describes the rising epoch.

## DKG outcome input

`TempoPayloadAttributes` MUST carry a dedicated `dkg_outcome` field, separate from `extra_data`:

```rust
struct DkgOutcome {
    epoch: u64,
    output: Output<MinSig, PublicKey>,
}

struct TempoPayloadAttributes {
    // Existing fields omitted.
    dkg_outcome: Option<DkgOutcome>,
}
```

For `B(E)`, the proposer MUST supply `Some(O(E+1))` with `epoch = E+1`. For non-boundary blocks this field MUST be absent. A missing boundary input, an incorrect epoch, or an input on a non-boundary block is invalid.

`output` retains the existing public DKG output, including its public polynomial and ordered participant sets. Private shares MUST NOT be included. The canonical encoding is the existing unsigned-varint `epoch` encoding followed by the existing Commonware `output` encoding, with the same decoding limits and mode version. The `next_players` and `is_next_full_dkg` fields are omitted; configuration is stored separately. Decoders MUST consume the entire value and reject malformed or non-canonical encodings.

Outcome selection uses the existing ceremony rules and dealer logs available through the parent of `B(E)`. A dealer log carried by `B(E)` MUST NOT change `O(E+1)`: both proposer and verifier must compute that outcome before executing the boundary. This TIP does not change the success threshold, resharing rules, or failed-ceremony fallback.

The same explicit consensus input MUST reach the execution path used for block import, verification, and replay. Builder attributes are not part of the block and are insufficient on their own for those paths. Execution MUST NOT recover this input by decoding `extra_data` as an outcome. Payload caching MUST distinguish builds with different DKG inputs.

## Fixed storage

This TIP defines two dedicated system-state addresses. Their numerical values remain TBD and MUST be assigned before activation:

```solidity
address constant DKG_OUTCOME_ADDRESS = TBD;
address constant DKG_CONFIG_ADDRESS = TBD;
```

The outcome record at `DKG_OUTCOME_ADDRESS` is a Solidity-layout `bytes` value rooted at slot `0`, containing the canonical encoding of `DkgOutcome` above. It stores the full public outcome, not just its hash or effective committee.

The configuration record at `DKG_CONFIG_ADDRESS` uses this layout:

| Slot | Value |
| --- | --- |
| `0` | Ceremony epoch, encoded as a zero-extended `uint64` |
| `1` | Expected players, using the Solidity storage layout of `bytes32[]` |
| `2` | Full-DKG flag, encoded as `0` or `1` |

Each update MUST replace the previous record, including clearing unused storage when a dynamic value shrinks. Implementations MUST NOT append a record per epoch. Historical values remain available only through historical execution state or authenticated snapshots.

These locations define a storage interface for node providers, `eth_getStorageAt`, and `eth_getProof`; this TIP does not introduce a public contract ABI. Ordinary EVM execution MUST NOT be able to overwrite the records.

## System operations

At the end of `B(E)`, the execution layer MUST perform both updates:

1. Overwrite the outcome record with the canonical bytes of the supplied `O(E+1)`.
2. Read ValCfgV2 after the block's transactions and configuration-changing system operations, and overwrite the configuration record with epoch `E+1`, the expected players derived from its active validators, and the full-DKG flag.

Expected players MUST use the existing Ed25519 public-key decoding and canonical ordering rules. The full-DKG flag is `1` exactly when ValCfgV2's scheduled network identity rotation epoch equals `E+1`; otherwise it is `0`. Read or decoding failures invalidate the transition. The proposer does not supply or override this configuration.

These updates follow the [EIP-4788 system-operation model](https://eips.ethereum.org/EIPS/eip-4788#block-processing): they are protocol-controlled, absent from the transaction list, do not count against the block gas limit, and do not transfer value or apply EIP-1559 burn semantics. They may be implemented as privileged system calls or equivalent direct storage writes. Both MUST complete successfully before calculating the block's state root; a missing writer or failed update MUST invalidate the block.

Where TIP-1070 is active, its committee writer MUST use the supplied `O(E+1)` instead of decoding a boundary header. Its stored epoch and public keys MUST equal the outcome epoch and `output.players()` in the new outcome record. This TIP supersedes TIP-1070's requirements to obtain and verify the outcome through `extra_data`, while preserving its committee interface and visibility timing.

## Verification and epoch entry

Before accepting `B(E)`, each validator MUST compute its own expected `O(E+1)` using the existing DKG verification rules and supply that expectation to local execution. It MUST check that the resulting outcome record matches the expected canonical bytes, that the configuration record matches the ValCfgV2 snapshot, and that the computed state root equals the proposed header's state root. Comparing against proposer-supplied attributes alone is insufficient.

At entry into `E+1`, consensus MUST read the outcome and configuration records from the finalized execution state. Both records MUST name `E+1`. The outcome determines the effective committee and public key material; the configuration record determines the expected players and full-DKG or resharing mode for the ceremony running during `E+1`.

Later ValCfgV2 changes MUST NOT reconfigure that ceremony. Restart and recovery MUST use the stored snapshot, rather than recomputing the expected players from the current registry. Historical recovery requires execution state for the epoch being recovered, or proofs for these records against an independently authenticated state root. Full replay MUST reconstruct the required consensus inputs from the ceremony history; a node without those inputs must obtain an authenticated checkpoint or stop. An outcome cannot authenticate the state root used to prove that same outcome.

## Dealer logs

After activation, `extra_data` MUST be empty or contain a dealer log under the existing dealer-log encoding and validation rules, at every block height. Boundary blocks MUST NOT encode DKG outcomes there. The existing proposer/dealer identity and signature checks also apply to boundary dealer logs.

## Activation and compatibility

The activating hardfork is TBD. A block's timestamp determines whether its execution and `extra_data` follow the legacy rules or this TIP. Historical replay MUST retain the legacy boundary-outcome decoder for pre-activation blocks only.

At the first activated block, initialize the fixed records for the ongoing epoch from its already authenticated consensus outcome and ceremony configuration before user execution. Building, verification, and replay MUST receive these records as a separate activation input, independently of the boundary-only `dkg_outcome` field. This one-time migration MUST preserve the ongoing ceremony, including its original expected players and mode; it MUST NOT resample the current ValCfgV2 registry. If the first activated block is a boundary, the normal post-execution update then writes the records for the rising epoch. If active from genesis, initialize the records in genesis state from the trusted genesis outcome and configuration.

# Tooling

Update consensus, peer discovery, epoch management, finalization verification, payload execution, and recovery to read the fixed records instead of parsing post-activation boundary outcomes. Engine adapters and replay tools must carry the explicit outcome input. Update codecs, inspectors, fixtures, and DKG helpers to apply the correct hardfork rules; retain legacy fixtures for replay.

Recovery and pruning documentation MUST identify the historical state or authenticated checkpoints required for each recovered epoch. Tools MUST distinguish unavailable state or consensus input from an invalid outcome.

`tempo consensus info` MUST report current dealers and ceremony players from the stored records, alongside validators currently marked active in ValCfgV2 as prospective players for the next epoch. Include their roles and current network addresses so partners can maintain firewall allowlists.

# Observability

Nodes MUST log each epoch transition with the block hash, effective epoch, outcome digest, effective committee, expected players, and ceremony mode. Validation failures MUST identify an outcome mismatch, configuration mismatch, state-root mismatch, missing input, or failed state access. These are node logs; the system writes do not introduce user-transaction receipts or Solidity events. Private shares MUST NOT be logged.

# Invariants

1. Every accepted boundary commits exactly the consensus-expected outcome and the configuration derived from that boundary's final ValCfgV2 state; neither record changes in non-boundary blocks except during activation initialization.
2. All validators use the same stored players and ceremony mode throughout an epoch, including after registry changes, restart, and recovery. Expected players remain distinct from the effective committee, including when DKG fails.
3. Post-activation `extra_data` is never an outcome carrier. Building, verification, and replay produce the same state root from the same consensus input and parent state.

Tests MUST cover successful DKG, resharing, failed-ceremony fallback, malformed or missing inputs, incorrect epochs and outcomes, unauthorized writes, shrinking records, boundary dealer logs, registry changes in and after a boundary, restart and historical recovery, and activation at genesis, on a boundary, and between boundaries. Where TIP-1070 is active, its committee record MUST agree with the stored outcome.
