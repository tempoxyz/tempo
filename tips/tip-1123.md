# TIP-1123: Store DKG outcomes and configuration in execution state

## Abstract

Boundary block `extra_data` carries the raw public DKG output. Validators compare those bytes against their independently computed outcome before execution, allowing DKG disagreements to be reported directly. An EIP-4788-style system operation writes the same output to fixed execution-layer storage and snapshots the expected players from ValCfgV2 for the next ceremony. Non-boundary `extra_data` continues to carry dealer logs.

## Motivation

Consumers currently locate and decode historical boundary blocks to discover the current outcome and ceremony configuration. Keeping the outcome in boundary `extra_data` provides an explicit value for consensus verification and an execution input available during replay. Persisting it in execution state lets ordinary consumers read the current outcome without locating a boundary header.

Keeping these records in execution state gives consensus, recovery, and tooling a stable location to read. The block's state root commits to the selected outcome and the expected players. Consensus remains responsible for selecting and verifying the DKG outcome; the execution layer persists it and derives ceremony configuration from ValCfgV2.

## Assumptions

- Consensus computes the expected public DKG outcome, including the existing fallback when a ceremony fails, before executing an epoch transition.
- ValCfgV2 remains authoritative for the configured active validators and scheduled network identity rotation. Its active set can differ from the effective committee selected by DKG.
- Proposal building, verification, and replay use the outcome encoded in the boundary block. Missing or malformed boundary data, or unavailable configuration state, prevents validation or epoch initialization; it MUST NOT silently select another outcome or ceremony mode.

## Threat model

- A proposer may supply an incorrect outcome or omit the required update. Validators compare the header bytes with their independently computed outcome, and execution checks that the mandatory storage writes produce the proposed state root.
- The ValCfgV2 owner may change the configured active validators and rotation schedule. These changes affect the next configuration snapshot, but do not directly change the effective committee or an ongoing ceremony.
- User transactions and contract callers MUST NOT be able to write the dedicated records. Reads from an untrusted execution provider require a storage proof against an authenticated state root.
- Failed ceremonies retain the existing consensus fallback rules. Expected players MUST NOT be mistaken for the players in a successful outcome.

# Specification

## Epoch transition

Let `B(E)` denote the last block of epoch `E`, at height `h` where `h % epoch_length == epoch_length - 1`. Let `O(E+1)` denote the public DKG outcome selected by consensus for use in epoch `E+1`.

The execution layer MUST update the dedicated state at the end of `B(E)`, after all user transactions and any system operations that modify ValCfgV2. Transactions in `B(E)` continue to observe the records for `E`; its committed post-state contains the records for `E+1`. The first block of `E+1` and subsequent non-boundary blocks retain those records unchanged.

This follows the post-execution timing of [TIP-1070](./tip-1070.md). The fixed locations are persistent account storage committed by the state root, not transient EVM memory. Consumers can read the records from available state without fetching the preceding boundary header. The outcome's effective epoch is derived from the block context: the boundary's post-state already describes the rising epoch. The configuration record's stored epoch MUST agree with that context.

## DKG outcome input

For `B(E)`, the proposer MUST place the canonical encoding of `O(E+1)` in `TempoPayloadAttributes.extra_data`, and the builder MUST copy those bytes into the block header:

```rust
// O(E+1) has type Output<MinSig, PublicKey>.
extra_data = output.encode();
```

The block context determines that this output applies to `E+1`; no epoch argument accompanies the output. Empty or malformed boundary `extra_data` is invalid. Block height determines whether `extra_data` is an outcome or a dealer log; implementations MUST NOT infer its role by trying both decoders.

The value is the existing public DKG `Output<MinSig, PublicKey>`, including its public polynomial and ordered participant sets. Private shares MUST NOT be included. The canonical encoding is the existing Commonware output encoding alone, with the same decoding limits and mode version. There is no `DkgOutcome` wrapper or epoch prefix. The `next_players` and `is_next_full_dkg` fields are omitted; configuration is stored separately. Decoders MUST consume the entire value and reject malformed or non-canonical encodings.

Outcome selection uses the existing ceremony rules and dealer logs available through the parent of `B(E)`. Boundary blocks carry the outcome and no dealer log. This TIP does not change the success threshold, resharing rules, or failed-ceremony fallback.

Building, block import, and replay MUST obtain the output from the boundary block's `extra_data`. No additional DKG outcome field is required in `TempoPayloadAttributes` or `TempoExecutionData`. Payload caching MUST distinguish builds with different boundary outcome bytes.

## Fixed storage

This TIP defines two dedicated system-state addresses. Their numerical values remain TBD and MUST be assigned before activation:

```solidity
address constant DKG_OUTCOME_ADDRESS = TBD;
address constant DKG_CONFIG_ADDRESS = TBD;
```

The outcome record at `DKG_OUTCOME_ADDRESS` is a Solidity-layout `bytes` value rooted at slot `0`, containing only the canonical encoding of `Output<MinSig, PublicKey>`. It stores the full public output, without an epoch prefix.

The configuration record at `DKG_CONFIG_ADDRESS` uses this layout:

| Slot | Value |
| --- | --- |
| `0` | Ceremony epoch, encoded as a zero-extended `uint64` |
| `1` | Expected players, using the Solidity storage layout of `bytes32[]` |
| `2` | Full-DKG flag, encoded as `0` or `1` |

Each update MUST replace the previous record, including clearing unused storage when a dynamic value shrinks. Implementations MUST NOT append a record per epoch. Historical values remain available only through historical execution state or authenticated snapshots.

These locations define a storage interface for node providers, `eth_getStorageAt`, and `eth_getProof`; this TIP does not introduce a public contract ABI. Ordinary EVM execution MUST NOT be able to overwrite the records.

## System operations

At the end of `B(E)`, the execution layer MUST perform both updates:

1. Decode and validate the raw output in the boundary header's `extra_data`, then overwrite the outcome record with those exact bytes.
2. Read ValCfgV2 after the block's transactions and configuration-changing system operations, and overwrite the configuration record with epoch `E+1`, the expected players derived from its active validators, and the full-DKG flag.

Expected players MUST use the existing Ed25519 public-key decoding and canonical ordering rules. The full-DKG flag is `1` exactly when ValCfgV2's scheduled network identity rotation epoch equals `E+1`; otherwise it is `0`. Read or decoding failures invalidate the transition. The proposer does not supply or override this configuration.

These updates follow the [EIP-4788 system-operation model](https://eips.ethereum.org/EIPS/eip-4788#block-processing): they are protocol-controlled, absent from the transaction list, do not count against the block gas limit, and do not transfer value or apply EIP-1559 burn semantics. They may be implemented as privileged system calls or equivalent direct storage writes. Both MUST complete successfully before calculating the block's state root; a missing writer or failed update MUST invalidate the block.

Where TIP-1070 is active, its committee writer MUST decode the raw `Output<MinSig, PublicKey>` from the boundary's `extra_data` under this TIP's encoding rules. Its stored epoch MUST be `E+1`, derived from the boundary block context, and its public keys MUST equal `output.players()` in the new outcome record. This TIP updates TIP-1070's outcome encoding while preserving its committee interface and visibility timing.

## Verification and epoch entry

Before submitting `B(E)` for execution, each validator MUST compute its own expected `O(E+1)` using the existing DKG verification rules, canonically encode it, and compare those bytes with the proposed header's `extra_data`. A mismatch MUST reject the proposal with a distinct DKG-outcome mismatch diagnostic, including the expected and proposed public-output bytes. This check MUST also run when the execution layer has already executed the block; a cached `Valid` result does not replace consensus verification.

If the bytes match, the validator submits the proposed block through the existing `new_payload` path. The execution layer MUST write the header's outcome bytes and the ValCfgV2-derived configuration, then verify the computed state root against the proposed header. A state-root mismatch remains an execution failure; it MUST NOT be reported as a DKG-outcome disagreement. Consensus equality checks and execution validation MUST both succeed before the validator accepts the block.

At entry into `E+1`, consensus MUST read the outcome and configuration records from the finalized execution state whose block context makes the output effective for `E+1`. The configuration record MUST name `E+1`; the outcome carries no epoch field. The outcome determines the effective committee and public key material; the configuration record determines the expected players and full-DKG or resharing mode for the ceremony running during `E+1`.

Later ValCfgV2 changes MUST NOT reconfigure that ceremony. Restart and recovery MUST use the stored configuration snapshot, rather than recomputing the expected players from the current registry. Historical configuration recovery requires execution state for the epoch being recovered, proofs against an independently authenticated state root, or replay from an authenticated checkpoint. Execution replay obtains each output directly from its boundary header; it does not need to rerun DKG to obtain the execution input. Consensus verification of that output remains separate. Header-based finalization verifiers MAY continue to read outcomes from authenticated boundary headers using the applicable encoding rules. An outcome cannot authenticate the state root used to prove that same outcome.

## Dealer logs

For non-boundary blocks, `extra_data` MUST be empty or contain a dealer log under the existing encoding, proposer/dealer identity, and signature validation rules. For boundary blocks, it MUST contain only the raw DKG output specified above. Outcomes and dealer logs MUST NOT be concatenated in one header.

## Activation and compatibility

The activating hardfork is TBD. A block's timestamp determines whether its execution and `extra_data` follow the legacy rules or this TIP. Historical replay MUST retain the legacy boundary-outcome decoder for pre-activation blocks only.

At the first activated block, initialize the fixed records for the ongoing epoch before user execution. Read its already authenticated legacy boundary artifact using the pre-activation rules: persist only its raw output in the outcome record, and use its epoch, `next_players`, and `is_next_full_dkg` for the configuration record. Building, verification, and replay MUST use the same migration source. If no preceding boundary exists, use the trusted genesis outcome and configuration. This one-time migration MUST preserve the ongoing ceremony; it MUST NOT resample the current ValCfgV2 registry. If the first activated block is a boundary, the normal post-execution update then writes the records for the rising epoch. If active from genesis, initialize the records directly in genesis state.

# Tooling

Update current-outcome consumers, peer discovery, and epoch management to read the fixed records. Update consensus verification, header-based finalization verification, execution, replay, codecs, inspectors, fixtures, and DKG helpers to decode raw boundary outputs after activation; retain legacy fixtures for earlier blocks. No additional DKG argument is required on the executor's `new_payload` path.

Recovery and pruning documentation MUST identify the historical state or authenticated checkpoints required for each recovered epoch. Tools MUST distinguish unavailable state or consensus input from an invalid outcome.

`tempo consensus info` MUST report current dealers and ceremony players from the stored records, alongside validators currently marked active in ValCfgV2 as prospective players for the next epoch. Include their roles and current network addresses so partners can maintain firewall allowlists.

# Observability

Nodes MUST log each epoch transition with the block hash, effective epoch, outcome digest, effective committee, expected players, and ceremony mode. A DKG-outcome mismatch MUST identify the block and epoch and record both expected and proposed public-output bytes so operators can compare the values directly. Malformed boundary data, configuration failures, failed system writes, and state-root mismatches MUST be distinguishable from that consensus disagreement. These are node logs; the system writes do not introduce user-transaction receipts or Solidity events. Private shares MUST NOT be logged.

# Invariants

1. Every accepted boundary commits exactly the consensus-expected outcome and the configuration derived from that boundary's final ValCfgV2 state; neither record changes in non-boundary blocks except during activation initialization.
2. All validators use the same stored players and ceremony mode throughout an epoch, including after registry changes, restart, and recovery. Expected players remain distinct from the effective committee, including when DKG fails.
3. At every accepted post-activation boundary, the locally expected canonical output, header `extra_data`, and stored output bytes are identical. Building and replay produce the same state root from the same block and parent state, with the historical migration source additionally required at activation.

Tests MUST cover successful DKG, resharing, failed-ceremony fallback, malformed or missing boundary outputs, explicit byte-mismatch diagnostics before execution and for already-executed blocks, incorrect configuration epochs, raw-output encoding without an epoch prefix, unauthorized writes, shrinking records, rejection of dealer logs in boundary headers, registry changes in and after a boundary, restart and historical recovery, and activation at genesis, on a boundary, and between boundaries. Execution tests MUST reject incorrect post-state caused by missing or incorrect storage writes through state-root validation even when the header output matches consensus. Where TIP-1070 is active, its committee record MUST agree with the stored output and block-derived epoch.
