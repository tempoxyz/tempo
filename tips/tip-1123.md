# TIP-1123: Derive DKG configuration at epoch entry

## Abstract

This TIP removes the `next_players` and `is_next_full_dkg` fields from the on-chain DKG outcome in each epoch boundary block. Nodes instead derive the next ceremony's players and mode from validator configuration in the state after the finalized boundary block. Verifying a boundary block's outcome then no longer requires the execution state of its possibly unfinalized parent.

## Motivation

Let `B(E-1)` denote the boundary block (the last block) of epoch `E-1`, and `S(B)` the state after executing block `B`.

The proposer of `B(E-1)` currently reads validator configuration at `S(parent(B(E-1)))`: [`next_players`](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1258-L1262) and the [next full DKG epoch](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1244-L1251) fill two fields of the [on-chain outcome](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/dkg-onchain-artifacts/src/lib.rs#L29-L45) that fix the players and ceremony mode for epoch `E`. Verifiers repeat both reads and reject a boundary whose fields differ, so a validator cannot vote on `B(E-1)` until its possibly unfinalized parent is executed. Deferred verification, which [TIP-1031](./tip-1031.md) prepares for, has validators notarize blocks before executing them, so this state is not generally available at vote time.

This TIP drops both fields and derives their values from `S(B(E-1))`, which nodes need only after `B(E-1)` is finalized. That state is derivable from execution and committed by `B(E-1)`'s state root. Proposers still build `B(E-1)` on its executed parent, as for any block.

Alternatives considered:

- Keep the fields, filled from an older executed block. This delays every validator-config change by an epoch and keeps a redundant check.
- Keep the fields and check them only after finalization. A finalized boundary with wrong fields could not be rejected, so nodes would have to override them from state, which is this TIP with extra bytes.

## Assumptions

1. `B(E-1)` is finalized before any node enters epoch `E`. This holds by construction, since a node enters `E` by processing the finalized `B(E-1)`.
2. Execution is deterministic: every node that executes the finalized `B(E-1)` obtains the same `S(B(E-1))`. If violated, nodes derive different configurations for `E`; see [Threat Model](#threat-model).
3. ValidatorConfigV2 ([TIP-1017](./tip-1017.md)) is initialized, and its records are append-only: deactivation is one-way, and rotation appends a deactivated copy of the old record, keeping its `addedAtHeight`, before overwriting the slot. The hardfork MUST NOT activate before V2 is initialized. If it does, the filter below reads a partially migrated record set. Any future change to the getters, their decoding, or the record lifecycle MUST be hardfork-gated by boundary timestamp.

# Specification

## Definitions

- `h(B)` and `ts(B)` are the height and timestamp of block `B`. For `E = 0`, `B(-1)` is the genesis block and `S(B(-1))` is the genesis allocation.
- The *epoch-`E` artifact* is the `OnchainDkgOutcome` in `B(E-1).extra_data`. Its `epoch` is `E`.
- `dealers(E)` is `output.players()` of the epoch-`E` artifact: the holders of shares of `B(E-1)`'s output, who deal during `E`.
- `ceremony(E)` is the DKG ceremony run during epoch `E`. Its outcome is the epoch-`(E+1)` artifact in `B(E)`.
- `players(E)` are the recipients of `ceremony(E)`. If it succeeds, they become `dealers(E+1)`.
- `mode(E)` is `full` (new network identity) or `reshare` (keeps `B(E-1)`'s public key).
- The *rotation epoch* is `getNextNetworkIdentityRotationEpoch()` of ValidatorConfigV2.
- This TIP applies to epoch `E`, and `B(E-1)` is a *post-activation boundary*, exactly when `ts(B(E-1))` is at or after the activation timestamp. Otherwise `B(E-1)` is a *legacy boundary*.

## Epoch configuration

For a post-activation boundary `B(E-1)`:

`players(E)` is the set of ed25519 public keys of all ValidatorConfigV2 records with

```
addedAtHeight <= h(B(E-1)) && (deactivatedAtHeight == 0 || deactivatedAtHeight > h(B(E-1)))
```

excluding records whose key does not decode as an ed25519 public key, de-duplicated and sorted ascending by the 32-byte key encoding. Endpoints do not affect membership. At `S(B(E-1))` this is the set returned by `getActiveValidators()`. By Assumption 3 it yields the same set at every later state, so consumers MAY evaluate it at the state of any descendant of `B(E-1)`. Every consumer (DKG manager, peer manager, CLI) MUST use this definition.

`mode(E)` is `full` if and only if `E > 0` and the rotation epoch at `S(B(E-1))` equals `E`; otherwise it is `reshare`. The rotation epoch is a single mutable slot, so `mode(E)` can be evaluated only at `S(B(E-1))`.

If `players(E)` is empty or has more than `u16::MAX` keys, `ceremony(E)` fails deterministically: dealers produce no dealings, and `B(E)` carries `B(E-1)`'s output forward, as for any failed ceremony.

For a legacy boundary, nodes MUST take `players(E)` and `mode(E)` from the `next_players` and `is_next_full_dkg` fields of the finalized artifact and MUST NOT re-derive them from execution state. Proposal and verification of legacy boundaries are unchanged: they read `S(parent(B(E-1)))` and fall back to `reshare` when the rotation-epoch read fails.

### Behaviour change

For post-activation boundaries, the configuration snapshot moves from `S(parent(B(E-1)))` to `S(B(E-1))`. Validator-config changes included in `B(E-1)` itself (`addValidator`, `deactivateValidator`, `rotateValidator`, `setNetworkIdentityRotationEpoch`) therefore apply to epoch `E` rather than `E+1`. In particular, setting the rotation epoch to `E` in `B(E-1)` triggers a full DKG in `E`. This supersedes TIP-1017 §DKG Player Selection for post-activation boundaries by moving its height bound from the parent of the boundary to the boundary itself. A failed or pending read MUST NOT default to either mode.

## Epoch entry

A node enters epoch `E` when it processes the finalized `B(E-1)`, including while catching up.

1. Consensus for `E` (engine, signing scheme, `dealers(E)`, and the node's share) starts from the epoch-`E` artifact alone and MUST NOT wait for execution.
2. The node starts its `ceremony(E)` round once `S(B(E-1))` is available, meaning its execution layer has executed the finalized `B(E-1)`. While the execution layer has not yet executed `B(E-1)`, the node waits. Waiting is not an error, and verification of epoch-`E` dealer logs waits for the round instead of rejecting. If the node processes the finalized `B(E)` while still waiting, it stops waiting and proceeds as for unavailable state below. Node startup MUST NOT block on this read, because only the running executor can produce the state.
3. The node derives `players(E)` and `mode(E)` once, persists them with its epoch-`E` DKG state, and uses the persisted values after a restart. Persisted state MUST distinguish "not yet derived" from a derived configuration.

`S(B(E-1))` is permanently unavailable if the execution layer has executed `B(E-1)` but no longer serves its state, for example because it was pruned before a cold start. The node then MUST NOT guess `mode(E)`. It does not take part in `ceremony(E)`, does not vote for epoch-`E` blocks whose verification needs the round (blocks carrying epoch-`E` dealer logs, and `B(E)`), and adopts the outcome finalized in `B(E)`. Validators SHOULD retain execution state back to the latest boundary at or below their finalized block, which is at most one epoch, so that a cold start can take part in the current ceremony.

## Share recovery

Recovering a revealed share for epoch `E` reconstructs `ceremony(E-1)`. It runs only after that ceremony succeeded. If `B(E-2)` is a post-activation boundary, the node derives the configuration from headers alone and performs no state read:

- dealers: `B(E-2).output.players()`;
- players: `B(E-1).output.players()`;
- mode: `full` if and only if the public keys of `B(E-1).output` and `B(E-2).output` differ.

If `B(E-2)` is a legacy boundary, the legacy fields apply. A recovered output that differs from `B(E-1)`'s output is discarded.

## On-chain outcome

```rust
struct OnchainDkgOutcome {
    epoch: u64,
    output: Output<MinSig, PublicKey>,
}
```

For a post-activation boundary, `B(E-1).extra_data` MUST be exactly `UInt(epoch) || output` in the commonware codec (`output` with at most `u16::MAX` participants, `ModeVersion` v0), with no trailing bytes. This is the legacy encoding without its trailing `next_players` and `is_next_full_dkg`.

Proposal verification, the DKG manager, and the execution-layer committee system call MUST apply this exact-length decode, and a post-activation boundary that fails it is invalid. Legacy boundaries keep the legacy decoding unchanged, including its tolerance of trailing bytes.

The proposer MUST fix `ts(B(E-1))` before constructing the artifact. Proposal, verification, and execution all select the format from `ts(B(E-1))`, never from its parent's timestamp.

## Execution layer

For a post-activation boundary `B(E-1)`, the [TIP-1070](./tip-1070.md) committee system call decodes `B(E-1).extra_data` with the post-activation encoding. A decode failure makes the block invalid, as before. The committee written remains `(epoch, output.players())`, which is `dealers(E)`. The system call writes only the current committee, not validator configuration, so it affects neither `players(E)` nor `mode(E)`.

## Peer set

Throughout epoch `E`, a validator's tracked peer set MUST include `dealers(E)`, `players(E)`, and the validators active at its latest finalized state. Addresses are resolved at that state through `validatorByPublicKey`, including for keys that are no longer active. For a post-activation boundary, `players(E)` is evaluated on the latest finalized state with the filter above, so a player deactivated or rotated during `E` stays connected until `E` ends. The only exception is while that state is below `S(B(E-1))`, when `players(E)` cannot be evaluated yet. The node then applies this rule to the latest epoch whose boundary state it has, extended by `dealers(E)`.

# Tooling

Boundary artifact consumers fall into three classes:

- **Output-only consumers** (finalization verifier, followers, finalized header stream, chainspec network identity, aliases, `xtask get-identity-transitions`) MAY prefix-decode `(epoch, output)` without hardfork context, which works for both encodings.
- **Validity sites** (proposal verification, DKG manager, EL committee system call) MUST select and enforce the format from `ts(B(E-1))`.
- **Consumers of players or mode** (DKG manager, peer manager, and the tools below) MUST use the legacy fields for legacy boundaries and the derivation above for post-activation boundaries.

The tools change as follows. The changes to machine-readable output are breaking.

- `tempo consensus info` MUST list `dealers(E)`, `players(E)`, and the validators active at the latest block (the candidates for `players(E+1)`), each with its roles and current addresses, so operators can maintain firewall allowlists. It evaluates `players(E)` with the filter over `validatorCount` and `validatorByIndex` at the latest block and needs no historical state. `is_next_full_dkg` becomes `ceremony_mode` (`full`, `reshare`, or `unknown`). For a post-activation boundary, the mode comes from the rotation epoch at `B(E-1)`. If the RPC cannot serve that state, the command reports `unknown` with a distinct error and never substitutes the latest state. `next_full_dkg_epoch` stays and reports the latest value. `is_dkg_player` means membership in `players(E)`.
- `tempo consensus validator` computes `is_dkg_player` the same way.
- `xtask get-dkg-outcome` prints `next_players` and `is_next_full_dkg` only for legacy boundaries.
- `xtask bootstrap-shadowfork` seeds persisted DKG state with `players(E)` and `mode(E)` derived under the rules of the patched boundary.
- Genesis tooling MUST emit the encoding that applies at the genesis timestamp. If activation is at genesis, the genesis `extra_data` uses the new encoding.
- Fixtures and test helpers take hardfork context. Legacy fixtures stay for replay, and helpers that assume parent-state timing, such as the e2e epoch-targeting helpers, apply the rules of the boundary.

Recovery documentation MUST state that a validator restored from a snapshot takes part in the current ceremony only if its execution layer holds `S(B(E-1))`.

Integrators that decode boundary `extra_data` from RPC headers MUST NOT use a legacy decoder that requires the removed fields. They can prefix-decode `(epoch, output)`, read the committee from the TIP-1070 current-committee precompile, and read players and mode from validator configuration at `B(E-1)`.

# Observability

Nodes running the DKG manager MUST emit the following. Followers emit none.

| Event | Fields | Question answered |
|-------|--------|-------------------|
| Epoch configuration fixed (info). Extends the existing "entering a new DKG ceremony" event. | `epoch`, `boundary.height`, `boundary.hash`, `rules` (`legacy`, `tip1123`), `mode` (`full`, `reshare`), `rotation_epoch` (post-activation only), `dealers`, `players` | Which configuration did this node fix for `E`, and from where? |
| Epoch configuration pending (warn) | `epoch`, `boundary.height`, `boundary.hash`, `reason` (`not_executed`, `unavailable`), `attempts` | Why has this node's round for `E` not started, and will it? |
| Boundary artifact rejected (warn in the CL; the EL's existing "failed decoding boundary block extra data as DKG outcome" block-validation error) | `height`, `hash`, `rules`, decode error | Is the artifact invalid, rather than state being unavailable? |

Nodes MUST also expose a counter of pending configuration reads by `reason`, a gauge that is 1 while waiting for epoch configuration, and a gauge of the current ceremony mode. The first event replaces the `will_be_re_dkg` log at outcome construction.

# Threat Model

- **Validators.** The BFT assumptions are unchanged. The artifact is fully determined by `ceremony(E-1)`'s outcome and checked by verifiers. A proposer influences `players(E)` and `mode(E)` only through the validator-config transactions it includes, as for any earlier block of epoch `E-1`.
- **Validator-config owner and validators.** They change players and mode only through validator-config transactions. A change included in `B(E-1)` now applies to `E`.
- **Execution layer.** Deterministic: `S(B(E-1))` is committed by the state root of the finalized `B(E-1)`.
- **Off-node consumers** (CLI, explorers). They previously read the next players from a certified header. They now trust RPC state at `B(E-1)` or verify it with a state proof against `B(E-1)`'s state root.

Under the legacy rules, verifiers checked each boundary's configuration against their own reads before finalization, so a divergent node was visible at `B(E-1)`. Under this TIP, agreement rests on deterministic execution and one shared derivation rule. A node with a divergent derivation or corrupted local state derives a different round, cannot take part in `ceremony(E)`, and detects the mismatch at `B(E)`, where its local outcome differs from the finalized one. A finalized block that fails execution is out of scope. If it is `B(E-1)`, `S(B(E-1))` never becomes available and no node starts `ceremony(E)`.

# Invariants

The implementation and test suite MUST establish:

1. All validators derive the same players and ceremony mode for epoch `E`, regardless of later configuration changes, restart, cold start, or share recovery.
2. A post-activation boundary is valid only if its `extra_data` is exactly the new encoding of `(epoch, output)`, at both the CL and the EL. For every legacy artifact, that encoding of its `(epoch, output)` is a byte prefix of its legacy encoding.
3. Hardfork activation and replay apply the rules of each boundary, and `dealers(E)`, `players(E)`, and `mode(E)` never change once `E` is entered.

Tests MUST cover:

- configuration changes in and after `B(E-1)`, including setting the rotation epoch to `E` in `B(E-1)`, and both ceremony modes;
- activation at genesis, between `ts(parent(B(E-1)))` and `ts(B(E-1))`, and between `ts(B(E-1))` and `ts(B(E))`, with a genesis-activated network keeping its genesis identity through epoch 1;
- `B(E-1)` finalized before it is executed: the round waits, then uses `S(B(E-1))`, and never falls back to `reshare`;
- cold start with missing or stale DKG state after a configuration change after `B(E-1)`, and cold start with `S(B(E-1))` unavailable;
- share recovery with legacy and post-activation ceremony boundaries;
- an empty player set;
- strict decoding at the CL and EL: after activation, a boundary with the legacy tail or trailing bytes is rejected; before activation, the new encoding is rejected;
- EL import and payload building of both encodings;
- a player of `E` deactivated or rotated during `E` remaining in the peer set;
- followers and the finalization verifier across activation.
