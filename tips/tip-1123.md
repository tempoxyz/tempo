# TIP-1123: Store DKG outcomes and configuration in execution state

## Abstract

This TIP writes the next DKG ceremony's players and rotation flag to execution state using an EIP-4788-style system operation at the end of each boundary block, following [TIP-1070](./tip-1070.md). Consensus then reads them from finalized state instead of speculative state.

## Motivation

The [DKG outcome](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/dkg-onchain-artifacts/src/lib.rs#L29-L45) in each boundary block includes the next ceremony's players and whether it rotates the network identity. Validators [read both](https://github.com/tempoxyz/tempo/blob/402e2722e7aad25b0bfe0149271287d1bf52ad2c/crates/consensus/src/dkg/manager/actor/mod.rs#L1244-L1262) from [ValCfgV2](./tip-1017.md) at the boundary block's parent, when proposing and when verifying. This has two problems:

- The parent is not yet finalized, so the reads depend on speculative state.
- A restarting node must find and decode the last boundary header to learn the current ceremony configuration.

Deriving the configuration during execution makes it a deterministic function of the block, committed by the state root. Keeping the current outcome and configuration at fixed addresses lets consensus, peer discovery, and tooling read them from the latest state.

## Assumptions

- Consensus selects the outcome for the next epoch, including the failed-ceremony fallback, from dealer logs up to the parent of the boundary block. This TIP does not change outcome selection.
- ValCfgV2 ([TIP-1017](./tip-1017.md)) is initialized, and its active validators have unique, valid Ed25519 keys.

## Threat model

- **Proposer**: controls boundary `extra_data`. As today, validators compare it with their own outcome before execution. The proposer cannot influence the configuration record, which execution derives and the state root commits.
- **ValCfgV2 owner**: registry changes up to and including the boundary block of `E` configure the ceremony running during `E+1`; later changes do not affect it. As today, a registry with no active validators makes the next boundary block invalid.
- **Users and contracts**: cannot write the records.

# Specification

Let `B(E)` be the last block of epoch `E`, at height `h` where `h % epoch_length == epoch_length - 1`, and let `O(E+1)` be the outcome consensus selects for epoch `E+1`.

## Boundary outcome

The `extra_data` of an activated `B(E)` MUST be the encoding of `O(E+1)`:

```rust
struct DkgOutcome {
    epoch: u64,                        // E+1
    output: Output<MinSig, PublicKey>, // public output, no private shares
}
```

This is the legacy `OnchainDkgOutcome` encoding without its trailing `next_players` and `is_next_full_dkg` fields. Because the new encoding is a prefix of the legacy one, decoders MUST reject trailing bytes. Validators compare the encoding, epoch included, with their locally computed `O(E+1)` before execution. Non-boundary `extra_data` is unchanged.

## Storage

```solidity
address constant DKG_OUTCOME_ADDRESS = 0xc077E00000000000000000000000000000000001;
address constant DKG_CONFIG_ADDRESS = 0xC077E00000000000000000000000000000000002;
```

The outcome record is a Solidity `bytes` value at slot `0` of `DKG_OUTCOME_ADDRESS`, holding the `extra_data` of the latest activated boundary.

The configuration record at `DKG_CONFIG_ADDRESS`:

| Slot | Value |
| --- | --- |
| `0` | `uint64 epoch`: the epoch during which the ceremony runs |
| `1` | `bytes32[] players`: Ed25519 keys in Commonware public-key order |
| `2` | `bool isFullDkg` |

Both accounts have nonce `1` and no code, and only the system operation below writes to them. Each write replaces the previous record and clears any slots a shorter value no longer uses. An empty outcome record means the records are uninitialized.

## System operation

At the end of each activated `B(E)`, after all transactions, the execution layer MUST:

1. Decode `extra_data` as `DkgOutcome` and store those bytes as the outcome record.
2. Read ValCfgV2 from the same state and store the configuration record: `epoch = outcome.epoch`, `players` from the keys of `getActiveValidators()`, and `isFullDkg = (getNextNetworkIdentityRotationEpoch() == outcome.epoch)`.

The epoch is taken from the outcome, which consensus verifies, not computed from the height. Snapshotting after the block's transactions replaces [TIP-1017's player selection](./tip-1017.md#dkg-player-selection) at the parent of `B(E)`: registry changes in `B(E)` itself apply to the ceremony in `E+1`.

As in [EIP-4788](https://eips.ethereum.org/EIPS/eip-4788#block-processing), the operation is not a transaction, uses no block gas, and transfers no value. It writes the storage directly. The block is invalid if `extra_data` does not decode, a ValCfgV2 read fails or yields an invalid key, or `players` is empty or has more than `u16::MAX` keys. There is no fallback.

The [TIP-1070](./tip-1070.md) committee system call decodes the same `DkgOutcome` and still writes `(outcome.epoch, output.players())`.

## Consensus

When it enters epoch `E+1`, consensus reads both records from finalized state; both MUST name `E+1`. The outcome record supplies the committee and public polynomial. The configuration record supplies the players and mode of the ceremony running during `E+1`. Neither is recomputed from the current registry, including after a restart. To recover a share revealed in the previous ceremony, consensus reads that ceremony's configuration record from historical state.

Peer discovery takes the committee and the ceremony players from these records, where today it uses `players` and `next_players`.

## Activation

The activating hardfork is TBD. Each boundary's timestamp selects its outcome encoding, including during replay and in header-based verifiers.

The first activated block sets the nonce of both accounts to `1`. The records stay empty until the first activated boundary writes them. Until then, consensus configures the ongoing epoch from the legacy outcome, as today.

If the hardfork is active from genesis, the genesis header uses the new encoding, and the genesis allocation contains both accounts with records for epoch `0` taken from the genesis DKG outcome and ceremony configuration.

# Tooling

Every decoder of boundary `extra_data` selects the encoding by the boundary's timestamp. This includes consensus, finalization verification, chainspec network identity, inspectors, and test helpers. Legacy fixtures remain for pre-activation blocks.

`tempo consensus info` MUST report the current dealers and the ceremony players and mode from the records. It MUST also list the validators currently active in ValCfgV2 as prospective players for the next epoch. Each entry includes its role and current network addresses, so partners can maintain firewall allowlists.

# Observability

On entering an epoch, nodes log the epoch, outcome digest, committee, ceremony players, and mode. The system operation emits no receipts or EVM events.

# Invariants

1. After every activated `B(E)`, the outcome record equals the `extra_data` of `B(E)`, which equals the outcome every honest validator computed. The configuration record is derived from ValCfgV2 in the post-transaction state of `B(E)`. The outcome, configuration, and TIP-1070 committee records all name epoch `E+1`.
2. The records change only at activated boundaries or in genesis.
3. All validators run the ceremony during an epoch with the same players and mode, regardless of later registry changes or restarts.

Tests MUST cover:

- Successful, failed, and full-DKG ceremonies.
- Each of these registry changes, made both in `B(E)` and in the first block of `E+1`: adding, deactivating, and rotating a validator, and rescheduling the network identity rotation.
- Legacy or trailing bytes in the `extra_data` of an activated boundary.
- A shrinking player set.
- A restart in the middle of an epoch.
- Activation at genesis, on a boundary, and between boundaries, including replay across activation.
