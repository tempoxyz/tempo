# TIP-1141: Scoped Policy Membership Operations

## Abstract

Add separate TIP-403 functions for adding and removing whitelist and blacklist
members. Each direction gets its own selector, so a TIP-1011 call scope can grant
an access key one direction without the other. The main use case is a hot wallet
that can whitelist users but cannot remove them, change the admin, or touch any
other policy.

## Motivation

### Use case

Issuers running a KYC-gated token add users to a whitelist as they pass
onboarding. That happens continuously and is automated, so the signing key sits
in a hot wallet. Today the hot wallet has to be the policy admin, or an access key
of the admin scoped to `modifyPolicyWhitelist`. Either way, a compromised hot
wallet can do far more than onboard users:

| Capability | Admin key lost | Current scoped key lost | Add-only key lost (this TIP) |
| --- | --- | --- | --- |
| Whitelist arbitrary addresses | yes | yes | yes |
| Remove every member (freezes all holders) | yes | yes | no |
| Transfer the admin role (permanent takeover) | yes | no | no |
| Recovery | none once the admin is transferred | root re-adds members | root removes the added addresses and revokes the key |

With an add-only key, a compromise means a bounded cleanup: the root account
revokes the key and removes the addresses the attacker added. It never means
losing the policy or freezing existing holders.

Blacklists have the mirror-image use case: an incident-response hot wallet that
can freeze addresses quickly but cannot unfreeze them. A compromise can grief
users with extra blocks, which root can undo, but cannot release a sanctioned
address.

### Why a new selector is required

`modifyPolicyWhitelist(uint64,address,bool)` and
`modifyPolicyBlacklist(uint64,address,bool)` use one selector for both
directions. TIP-1011 call scopes match target and selector, plus the recipient
for TIP-20 transfer/approve only. They cannot restrict the boolean argument, so
granting either selector grants both directions.

### Alternatives considered

1. **Admin wrapper contract.** Set the policy admin to a contract that exposes only
   `add` to the hot wallet. This works today with no hardfork, but it moves the
   policy's real interface off the precompile. Issuance tooling, explorers,
   compliance dashboards, and SDKs read `policyData().admin` and call the registry
   directly. With a wrapper they would have to recognize the wrapper, and every
   issuer would have to deploy and audit one (or depend on a shared one). Root's
   own admin actions would also have to route through it. Directional selectors
   make add-only a standard access-key configuration that existing wallets and
   tooling already understand.
2. **Argument constraints in TIP-1011.** Extend selector rules to match arbitrary
   ABI arguments, such as `bool == true`. This is more general, but it adds a
   calldata matcher to transaction validation, along with its gas bounds and
   encoding edge cases, for a case two selectors solve. It does not conflict with
   this TIP and can follow later.
3. **Per-policy operator role in TIP-403.** Let an admin delegate add-only rights
   on one policy to another address. This would also narrow the blast radius
   described under [Threat Model](#threat-model), but it needs new storage, new
   admin flows, and new events. Out of scope; a candidate for a future TIP.

### Success criteria

Issuers can run onboarding from an add-only access key, without a wrapper
contract and without exposing the admin role or member removal.

## Assumptions

1. TIP-1011 call scoping is active. A scope listing only an add selector rejects
   every other selector on the registry.
2. TIP-1022 virtual-address rejection in policy operations is active, and the new
   functions inherit it.
3. Access keys act as their account. `msg_sender` for the registry is the root
   account, so the account must be the policy admin. If it is not, calls revert
   with `Unauthorized` exactly as the legacy functions do.

## Threat Model

- **Root account / policy admin:** fully trusted. It authorizes, scopes, and
  revokes keys, and keeps sole control of `setPolicyAdmin` and removals.
- **Scoped hot-wallet key:** semi-trusted. If compromised, it can apply its one
  direction to *every* policy its account administers, including policies created
  after the key was authorized. It cannot apply the opposite direction, call the
  legacy boolean functions, change admins, or reach other targets. Issuers that
  want a narrower blast radius should put hot-wallet-managed policies under a
  dedicated admin account.
- **Policy consumers** (TIP-20 tokens, compound policies, TIP-1028 receive
  policies): see the same membership changes and events as today; their trust
  assumptions are unchanged.

# Specification

## Interface

Extend the TIP-403 registry at `0x403c000000000000000000000000000000000000`:

```solidity
/// @notice Allow an account in a whitelist policy. Caller must be its admin.
/// @dev Equivalent to modifyPolicyWhitelist(policyId, account, true).
/// @param policyId The whitelist policy to modify.
/// @param account The account to allow.
function addPolicyWhitelist(uint64 policyId, address account) external;

/// @notice Disallow an account in a whitelist policy. Caller must be its admin.
/// @dev Equivalent to modifyPolicyWhitelist(policyId, account, false).
/// @param policyId The whitelist policy to modify.
/// @param account The account to disallow.
function removePolicyWhitelist(uint64 policyId, address account) external;

/// @notice Restrict an account in a blacklist policy. Caller must be its admin.
/// @dev Equivalent to modifyPolicyBlacklist(policyId, account, true).
/// @param policyId The blacklist policy to modify.
/// @param account The account to restrict.
function addPolicyBlacklist(uint64 policyId, address account) external;

/// @notice Unrestrict an account in a blacklist policy. Caller must be its admin.
/// @dev Equivalent to modifyPolicyBlacklist(policyId, account, false).
/// @param policyId The blacklist policy to modify.
/// @param account The account to unrestrict.
function removePolicyBlacklist(uint64 policyId, address account) external;
```

| Function | Selector | Legacy equivalent |
| --- | --- | --- |
| `addPolicyWhitelist(uint64,address)` | `0x496e9631` | `modifyPolicyWhitelist(id, a, true)` |
| `removePolicyWhitelist(uint64,address)` | `0x6fbd6bc6` | `modifyPolicyWhitelist(id, a, false)` |
| `addPolicyBlacklist(uint64,address)` | `0xb796e79d` | `modifyPolicyBlacklist(id, a, true)` |
| `removePolicyBlacklist(uint64,address)` | `0xd48fa5d6` | `modifyPolicyBlacklist(id, a, false)` |

None of the functions returns a value. Storage layout and the existing functions
are unchanged.

## Semantics

Each new function MUST behave exactly like its legacy equivalent:

1. **Same checks, in the same order:** virtual-address rejection
   (`VirtualAddressNotAllowed`), policy lookup (`PolicyNotFound`), admin check
   (`Unauthorized`), then policy type (`IncompatiblePolicyType`).
2. **Same state transition:** sets the account's membership bit for that policy.
3. **Same event:** emits one `WhitelistUpdated` or `BlacklistUpdated` with the
   same fields the legacy call would emit. This includes repeated operations
   (adding an existing member still emits).

## Gas

Calldata is charged via the precompile input-cost schedule on its actual length
(32 bytes shorter than the legacy call). Storage and event gas are identical to
the legacy call.

## Activation

Before the activating hardfork, all four selectors MUST fail with the registry's
existing unknown-selector error. Historical execution is unchanged.

## Example: add-only whitelist key

Authorize a regular key through `authorizeKey` with this call scope. Expiry and
spending limits keep their existing meaning:

```json
{
  "allowAnyCalls": false,
  "allowedCalls": [
    {
      "target": "0x403c000000000000000000000000000000000000",
      "selectorRules": [
        { "selector": "0x496e9631", "recipients": [] }
      ]
    }
  ]
}
```

The selector rule MUST be explicit: per TIP-1011, `selectorRules: []` allows
every selector on the target, including `setPolicyAdmin`.

A blacklist freeze-only key uses `0xb796e79d` in the same way.

## Compatibility

- **Indexers and the transaction pool:** no change. The new functions emit the
  existing `WhitelistUpdated` / `BlacklistUpdated` events. Pool eviction on
  blacklist additions and whitelist removals is keyed off those events, so it
  keeps working.
- **Wallets and SDKs:** add the four functions to the node bindings, the
  `tempo-std` interface, and the SDK ABIs. Clients MUST NOT send them before
  activation.
- **Existing integrations:** the legacy boolean functions remain and keep working.

# Invariants

1. Each new function produces the same post-state, return data, error, and events
   as its legacy equivalent, for every input and pre-state.
2. Before activation, all four selectors revert with the unknown-selector error
   and change no state.
3. A key scoped only to `addPolicyWhitelist` can add whitelist members. Calls
   through that key to `removePolicyWhitelist`, `modifyPolicyWhitelist`,
   `setPolicyAdmin`, any blacklist function, or any other target are rejected.
   The same holds for each of the other three selectors.
4. A failed call changes no membership and emits no update event.
5. Expired or revoked keys cannot call any of the four functions.
6. The Rust bindings and the Solidity interface expose the same four signatures
   and selectors.

## Test Cases

1. For each of the four functions, run a differential test against the legacy
   equivalent covering success, repeated operation, `Unauthorized`,
   `PolicyNotFound`, `IncompatiblePolicyType` (wrong list type, compound policy),
   and virtual-address rejection.
2. Activation boundary: unknown selector before the hardfork, success after.
3. An add-only whitelist key adds a member, then fails on removal, legacy modify,
   admin change, and blacklist calls.
4. A freeze-only blacklist key restricts an address, and the pool evicts pending
   transactions from that address.
5. An add-only key applies to every policy its account administers, including
   one created after the key was authorized.
