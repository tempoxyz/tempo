# TIP-1141: Scoped Whitelist Operations

## Abstract

Add separate TIP-403 functions for adding and removing whitelist members so an
access key can be scoped to additions only.

## Motivation

`modifyPolicyWhitelist(uint64,address,bool)` uses one selector for both actions.
Access-key call scopes cannot restrict its boolean argument, so granting that
selector permits both additions and removals.

## Assumptions

TIP-1011 call scoping and TIP-1022 virtual-address checks are active. The account
using the access key must administer the policy. Activation remains TBD; T13 in
[the implementation PR](https://github.com/tempoxyz/tempo/pull/8220) is provisional.

# Specification

Extend the registry at `0x403c000000000000000000000000000000000000`:

```solidity
/// @notice Allow an account in a whitelist policy. Caller must be its admin.
/// @dev Equivalent to modifyPolicyWhitelist(policyId, account, true),
///      including its errors, check order, and WhitelistUpdated event.
/// @param policyId The whitelist policy to modify.
/// @param account The account to allow.
function addPolicyWhitelist(uint64 policyId, address account) external;

/// @notice Disallow an account in a whitelist policy. Caller must be its admin.
/// @dev Equivalent to modifyPolicyWhitelist(policyId, account, false),
///      including its errors, check order, and WhitelistUpdated event.
/// @param policyId The whitelist policy to modify.
/// @param account The account to disallow.
function removePolicyWhitelist(uint64 policyId, address account) external;
```

| Function | Selector |
| --- | --- |
| `addPolicyWhitelist(uint64,address)` | `0x496e9631` |
| `removePolicyWhitelist(uint64,address)` | `0x6fbd6bc6` |

Both functions MUST reuse the corresponding legacy mutation semantics, including
admin/type checks, virtual-address rejection, and events on repeated operations.
Neither returns a value. Storage layout and existing functions remain unchanged.
Charge actual calldata using the active input-cost schedule and retain existing
storage and event charges. Both selectors MUST return the existing unknown-selector
error before activation; historical execution remains unchanged.

## Add-Only Access Key

Configure a regular key through `authorizeKey` with this call scope; expiry and
spending-limit fields retain their existing definitions:

```json
{
  "allowAnyCalls": false,
  "allowedCalls": [
    {
      "target": "0x403c000000000000000000000000000000000000",
      "selectorRules": [
        { "selector": "0x496e9631", "recipients": [] }
      ]
    }
  ]
}
```

This permits additions to every whitelist administered by the account. It does
not restrict policy IDs or member addresses. Keep the selector rule explicit:
an empty `selectorRules` list permits every selector on the registry.

# Tooling

Add both functions to node bindings, Solidity interfaces, and SDK ABIs, with the
scope example above. Clients must wait for activation before using them.
Implementations: [Tempo #8220](https://github.com/tempoxyz/tempo/pull/8220) and
[tempo-std #157](https://github.com/tempoxyz/tempo-std/pull/157).

# Observability

Reuse `WhitelistUpdated(uint64 indexed policyId, address indexed updater,
address indexed account, bool allowed)` once per successful call, with `allowed`
set to `true` for addition and `false` for removal. Failed calls MUST leave
membership unchanged and emit no update. No new events are required.

# Threat Model

The administrator trusts the key holder to add arbitrary members to all of its
whitelists, affecting their existing token, compound-policy, and receive-policy
consumers. A compromised key can make those additions but cannot remove members
or change policy admins through the documented scope. Existing key expiry,
revocation, scope-management permissions, and fee rules remain in force.

# Invariants

Tests MUST verify activation gating, equivalence to the legacy boolean variants
(including errors and repeated-operation events), and matching Rust/Solidity ABIs.
An add-only key MUST be able to add members while removal, legacy mutations,
admin changes, blacklist mutations, and other targets are rejected. Extra calldata
MUST NOT turn an addition into a removal. Expired or revoked keys remain unusable.
