# TIP-1141: Scoped Whitelist Operations

## Abstract

This TIP adds separate TIP-403 functions for adding and removing whitelist members.
An account can authorize an access key to call only the addition function, allowing
it to maintain an allowlist without granting removal or policy-admin changes.
Both functions preserve the existing whitelist mutation checks, state, and events.

## Motivation

`modifyPolicyWhitelist(uint64,address,bool)` uses one selector for both additions
and removals. TIP-1011 call scopes can restrict the target and selector, but cannot
restrict the boolean argument. Granting that selector therefore grants both actions.

Separate selectors let issuers delegate allowlist additions with the existing
access-key authorization format. The request and implementation are tracked in
[Tempo PR #8220](https://github.com/tempoxyz/tempo/pull/8220).

Alternatives considered:

- SDK helpers around `modifyPolicyWhitelist` improve ergonomics but cannot enforce
  an add-only restriction against a key holder who submits their own calldata.
- A generic calldata restriction language would support more granular rules but
  requires changes to key authorization, storage, and validation.
- A wrapper contract could enforce additions, but would need policy administration
  delegated to it and introduce contract deployment and maintenance.

## Assumptions

- TIP-1011 target/selector call scoping and TIP-1022 virtual-address checks are
  active before this TIP activates.
- The signing account administers the whitelist being modified. Authorizing an
  access key does not make that account a policy admin.
- The owner accepts additions to every whitelist administered by the account.
  This TIP does not provide policy-ID or member-address restrictions.
- Activation requires a coordinated network upgrade under [TIP-0000](./tip-0000.md).
  The implementation PR's T13 gate is provisional; this draft does not schedule
  the proposal for T13.

# Specification

## Interface

Extend the registry at `0x403c000000000000000000000000000000000000` with the following
functions. Existing functions remain available with unchanged semantics.

```solidity
interface ITIP403WhitelistOperations {
    /// @notice Add an account to a whitelist policy.
    /// @dev Caller must be the policy admin. Equivalent to
    ///      modifyPolicyWhitelist(policyId, account, true).
    ///      Emits WhitelistUpdated even if the account is already allowed.
    ///      Reverts with VirtualAddressNotAllowed for virtual accounts,
    ///      PolicyNotFound for nonexistent policies, Unauthorized for non-admin
    ///      callers, or IncompatiblePolicyType for non-whitelist policies,
    ///      preserving the existing mutation's check order.
    /// @param policyId The whitelist policy to modify.
    /// @param account The literal account to allow.
    function addPolicyWhitelist(uint64 policyId, address account) external;

    /// @notice Remove an account from a whitelist policy.
    /// @dev Caller must be the policy admin. Equivalent to
    ///      modifyPolicyWhitelist(policyId, account, false).
    ///      Emits WhitelistUpdated even if the account is already disallowed.
    ///      Reverts with the same errors and check order as addPolicyWhitelist.
    /// @param policyId The whitelist policy to modify.
    /// @param account The literal account to disallow.
    function removePolicyWhitelist(uint64 policyId, address account) external;
}
```

| Function | Selector |
| --- | --- |
| `addPolicyWhitelist(uint64,address)` | `0x496e9631` |
| `removePolicyWhitelist(uint64,address)` | `0x6fbd6bc6` |

Neither function returns a value. Both accept ordinary ABI-encoded arguments.

## State Transitions and Checks

For a decoded call, the registry MUST use the same mutation path as
`modifyPolicyWhitelist(policyId, account, allowed)`, with `allowed` fixed to `true`
for addition and `false` for removal. Specifically, it MUST:

1. Reject virtual member addresses with `VirtualAddressNotAllowed`.
2. Load the policy using the existing policy lookup and its error semantics.
3. Require `msg.sender` to equal the policy admin, otherwise revert `Unauthorized`.
4. Require a whitelist policy, otherwise revert `IncompatiblePolicyType`.
5. Write the membership boolean and emit the existing `WhitelistUpdated` event.

An access-key transaction uses its account as the caller according to existing
transaction semantics. The key ID does not replace the policy admin check.
Repeated additions or removals succeed and emit an event. Failed calls MUST leave
membership unchanged and MUST NOT emit an update event. Static calls retain the
existing state-mutation rejection behavior.

No storage fields, policy types, policy IDs, or migration procedures are added.
Updates affect dependent tokens, compound policies, and receive policies through
their existing whitelist authorization behavior.

## Access-Key Configuration

An add-only key MUST have `allowAnyCalls = false` and exactly one call scope.
Configure the following scope on a regular access key through `authorizeKey`:

```json
{
  "allowAnyCalls": false,
  "allowedCalls": [
    {
      "target": "0x403c000000000000000000000000000000000000",
      "selectorRules": [
        { "selector": "0x496e9631", "recipients": [] }
      ]
    }
  ]
}
```

This shows the call-scope portion of the authorization. Expiry and spending-limit
fields retain their existing definitions. `recipients: []` allows arbitrary members
for the permitted selector; a nonempty recipient list is not supported for these
registry selectors. An empty `selectorRules` list would permit every selector on
the target and MUST NOT be used for an add-only key.

With this configuration, the key cannot call the removal function, either value
of `modifyPolicyWhitelist`, `setPolicyAdmin`, blacklist mutations, or other
selectors and targets. Existing key expiry, revocation, authorization-management,
and transaction fee rules remain in force. No new key privileges are introduced.

## Activation and Gas

Before activation, both selectors MUST be unavailable and return the existing
unknown-selector error. After activation, both MUST dispatch as specified. Older
blocks MUST continue to execute under their original selector set.

Use the active precompile input-cost schedule and existing whitelist mutation's
storage and event charges. The new calls encode two arguments instead of three;
charge for their actual calldata rather than requiring equal total gas to the
legacy call. No additional fixed surcharge is introduced.

# Tooling

- Add both functions to node bindings, published Solidity interfaces, and SDK ABIs.
  The Solidity declarations are proposed in
  [tempo-std PR #157](https://github.com/tempoxyz/tempo-std/pull/157).
- Provide an add-only access-key example using the scope above and describe its
  coverage of every whitelist administered by the account.
- Gate client usage on network activation. Keep the legacy mutation available for
  callers on earlier forks and callers requiring both actions.
- Add selector-dispatch and scoped-key fixtures. Rust and Solidity ABI surfaces
  MUST agree on both selectors, parameters, and empty return values.

# Observability

Both operations MUST emit the existing event once for each successful call:

```solidity
event WhitelistUpdated(
    uint64 indexed policyId,
    address indexed updater,
    address indexed account,
    bool allowed
);
```

`allowed` MUST be `true` for addition and `false` for removal. The event identifies
which policy and member changed and the caller responsible. The same event also
covers the legacy function; distinguishing entry points requires transaction
calldata or a call trace. No new event or dedicated node metric is required.

# Threat Model

- **Policy administrator:** Chooses which keys receive the add selector and remains
  responsible for the compliance consequences of their additions.
- **Access-key holder:** May be compromised or submit arbitrary calldata. Selector
  enforcement MUST prevent removal, admin changes, and calls outside the scope.
  A compromised add-only key can still add arbitrary accounts to every whitelist
  administered by its account, affecting all consumers of those policies.
- **Account authorization authority:** Can authorize, revoke, or change key scopes
  under existing rules. Granting wider scopes intentionally exceeds this TIP's
  add-only configuration; the feature does not constrain that authority.
- **Node and client implementers:** Must agree on selector activation and preserve
  existing admin checks, virtual-address rejection, and mutation atomicity.

The permission authorizes additions. It does not impose membership quotas,
compliance screening, per-policy restrictions, or restrictions on transfers other
accounts may subsequently perform after being allowed.

# Invariants

The test suite MUST establish:

1. The new selectors are rejected before activation and accepted after activation.
2. Addition and removal produce the same membership state, checks, and events as
   their corresponding legacy boolean values, including repeated operations.
3. Unauthorized callers, nonexistent policies, incompatible policy types, and
   virtual members preserve existing errors and check order without state changes
   or update events.
4. An add-only scoped key can add members and cannot remove them, call either
   legacy boolean variant, change policy admins, mutate blacklists, or call another
   target. Extra calldata cannot change addition into removal.
5. Key expiry and revocation prevent further use under existing validation rules;
   scope management retains existing authorization requirements.
6. Whitelist updates retain existing effects on direct token policies, compound
   policies, and receive policies. Historical execution and storage layout remain
   unchanged.
7. Published ABIs agree on signatures, selectors, and return values, and input,
   storage, and event gas follow the active schedules.

Success means an issuer can authorize the documented key scope and perform
allowlist additions with that key while the prohibited actions fail. Engineering,
research, security, and tooling review and upgrade scheduling remain required
before production activation.
