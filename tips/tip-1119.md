# TIP-1119: Explicit block system operations

## Abstract

Tempo selects its block system operations explicitly: the EIP-2935 history call
before transactions and the current-committee update after transactions. Ethereum
beacon-root and execution-request operations do not run after activation. Blocks
before activation retain their existing processing rules.

## Motivation

Tempo reuses Ethereum block execution code. That code schedules operations for
Ethereum consensus, including beacon roots, validator requests, and builder
requests. Upstream changes can therefore add state transitions or validation
requirements to Tempo without a Tempo protocol decision. For example,
[alloy-evm #400](https://github.com/alloy-rs/evm/pull/400) adds missing-code
validation for EIP-8282 builder contracts when Amsterdam is active. Tempo should
not need those contracts to adopt otherwise useful execution changes.

Tempo should own this selection while continuing to reuse transaction execution.
Checking whether an unwanted contract exists is insufficient: deployment at that
address could change consensus behavior. Disabling calls for all historical blocks
is also unsafe without proving equivalence for every supported chain and state.
A fork boundary preserves historical execution and makes the new rules explicit.

## Assumptions

The activation upgrade and its network timestamps remain undecided. This proposal
MUST NOT activate through an upstream Ethereum fork alone.

The existing history and committee rules remain authoritative. This proposal does
not deploy history bytecode, repair history storage, change committee selection,
or change the activation of either operation. It does not assume that excluded
contract addresses have always lacked code on deployed networks.

## Threat Model

A proposer cannot choose which system operations run. Validators derive that
selection from the agreed fork schedule and reject blocks whose resulting state
or execution commitments differ.

Contract deployment or arbitrary code at an excluded address MUST NOT cause the
executor to invoke that address as an automatic block system operation. Ordinary
transaction calls to those addresses remain subject to normal execution rules.

Client maintainers must preserve the selected operations across dependency
upgrades. Operators must agree on activation; a mismatch can split the chain.

# Specification

## Activation and compatibility

Let `A` be the timestamp assigned through the network upgrade process. Blocks
with `timestamp < A` MUST retain their existing pre- and post-execution behavior,
including Ethereum processing inherited by the legacy executor. Blocks with
`timestamp >= A` MUST use the rules below. An unscheduled chain retains legacy
behavior. No production value for `A` is proposed here.

The activation MUST participate in the chain's fork identity. Historical replay
MUST select behavior using the block timestamp, not the client's current version
or the current contents of a system-contract address.

This is a consensus change. State roots or block validity can differ when excluded
contracts contain code or legacy Ethereum validation applies. Wallet transaction
formats and contract interfaces do not change. Applications that read an excluded
contract's automatically maintained state must account for updates stopping.

## Before transactions

Nonempty withdrawals MUST remain invalid.

The executor MUST apply the existing EIP-2935 history operation when its existing
activation condition holds. For non-genesis blocks, it calls the history contract
with the parent block hash and commits its state changes. Genesis blocks skip the
call. Missing history code remains a no-op; this proposal adds no code-existence
requirement. Existing call failure handling and database error propagation remain
unchanged.

Tempo initialization and precompile deployment MUST retain their existing order
after the history operation and before transaction execution. The executor MUST
NOT perform the EIP-4788 beacon-root call or require a parent beacon root for that
call. Other header validation rules remain unchanged.

## After transactions

The executor MUST retain incentive-section gas validation. It MUST then apply the
current-committee operation under the existing activation, epoch-boundary, input,
and failure rules described by [TIP-1070](./tip-1070.md). Invalid required committee
updates remain block errors.

The executor MUST NOT parse EIP-6110 deposit requests from receipt logs or invoke
EIP-7002 withdrawal requests, EIP-7251 consolidation requests, or EIP-8282 builder
deposit and exit requests. This exclusion holds even when those addresses contain
code and when Amsterdam is active. Receipt logs remain intact.

The executor MUST return an empty execution-request list. It MUST NOT apply
Ethereum block or ommer rewards, withdrawal balance increments, or the DAO state
transition. Existing Tempo fee accounting and transaction state changes remain
unchanged. No other Ethereum block system operation is enabled by dependency or
Ethereum fork activation alone.

## Execution result

Receipts MUST retain their order, logs, success status, and cumulative transaction
gas. System operations MUST NOT add transaction receipts or consume block capacity.
Blob gas accounting remains unchanged.

When [TIP-1016](./tip-1016.md) is enabled, header gas used remains the accumulated
regular execution gas. Otherwise it remains cumulative transaction gas after
refunds. Omitting Ethereum finalization MUST NOT change either rule.

# Tooling

Clients, payload builders, replay tools, and execution proofs must use the same
activation and operation selection. No wallet or contract ABI change is required.
Custom chain operators must set activation consistently across nodes.

The activation upgrade and its chain configuration must be agreed before this TIP
is scheduled. The implementation must expose the same boundary to every consumer
of the chain specification.

# Observability

No new onchain event is required. Existing block-import errors and execution
comparisons can detect disagreement. Testnet rollout must compare state roots,
receipts, gas totals, and requests at activation, and verify history storage and
committee updates. Success means matching execution commitments across upgraded
nodes and unchanged replay results before activation.

# Invariants

- Blocks before activation retain legacy state changes and validation.
- History storage records the parent hash when enabled and deployed; genesis and
  missing-code cases retain their existing behavior.
- Excluded contracts never receive automatic calls after activation, even with
  state-changing code at every excluded address and Amsterdam enabled.
- Ethereum deposit-shaped logs remain ordinary receipt logs after activation.
- Committee updates run only at the required epoch boundary; invalid required
  updates still reject the block.
- Withdrawal rejection, incentive validation, initialization, receipts, and both
  gas-accounting modes retain their existing rules.
- Boundary tests cover the block before activation, the activation block, and a
  later block, including legacy rewards and DAO transitions on custom chains.
