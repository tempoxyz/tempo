# TIP-1119: Explicit block system calls

## Abstract

Tempo's automatic block system calls are the existing EIP-2935 history update
before transactions and the existing committee update after transactions at epoch
boundaries. This TIP excludes Ethereum beacon-root and execution-request calls.

## Motivation

Tempo delegates block initialization and finalization to Ethereum's executor,
which schedules operations for Ethereum consensus. For example,
[alloy-evm #400](https://github.com/alloy-rs/evm/pull/400) adds missing-code
validation for EIP-8282 builder contracts when Amsterdam is active. Adopting an
execution upgrade should not require Tempo to deploy Ethereum's builder contracts.

Selecting the calls explicitly prevents dependency updates from enabling unwanted
operations. Skipping a call only when its target lacks code is insufficient:
deploying code would enable the operation, and upstream validation may reject the
block before the EVM receives the call.

## Assumptions

The history contract accepts the EIP-2935 parent-hash input. The committee update
uses the epoch and ordered players from the consensus-selected DKG outcome, as
specified by [TIP-1070](./tip-1070.md). Changes to either interface or input source
require corresponding specification and fork-rule changes before rollout.

Historical replay depends on preserving each block's original processing rules,
including on custom chains with code at Ethereum system-contract addresses.

## Threat Model

A proposer or contract deployer cannot enable additional automatic system calls.
Validators apply the same fork rules regardless of code at excluded addresses.
Ordinary transaction calls to those addresses remain subject to normal EVM rules.

# Specification

## System calls

After activation, the executor MUST schedule only these automatic block-boundary
calls, subject to their existing activation conditions:

| Call | Timing | Caller | Target | Input |
| --- | --- | --- | --- | --- |
| EIP-2935 history update | Before transactions, except genesis; existing Prague gate applies | `0xfffffffffffffffffffffffffffffffffffffffe` | `0x0000F90827F1C53a10cb7A02335B175320002935` | Parent block hash as 32 raw bytes |
| Current committee update ([TIP-1070](./tip-1070.md)) | After transactions in the last block of an epoch; existing T8 gate applies | `0x0000000000000000000000000000000000000000` | `0xC077E00000000000000000000000000000000000` | ABI-encoded `setCommitteeMembers(uint64 epoch, bytes32[] publicKeys)` from the block's DKG outcome |

The executor commits the state returned by the history call. EVM invocation or
database errors abort block processing. A returned EVM revert or halt does not
itself invalidate the block. Genesis skips the call; missing history code produces
no history update. Tempo initialization and precompile deployment follow the
history call and precede transactions.

The committee call uses the epoch and player order from the DKG outcome. It runs
after incentive-section gas validation. Failure to decode the required outcome,
an EVM invocation error, or a reverted or halted committee call aborts block
processing. On success, the executor commits the returned state. Transactions
within the boundary block observe the old committee; its committed post-state
contains the new committee.

These calls do not add transactions or receipts and do not consume block gas
capacity.

## Excluded Ethereum processing

The executor MUST NOT schedule the EIP-4788 beacon-root call, EIP-7002 withdrawal
request call, EIP-7251 consolidation request call, or either EIP-8282 builder
request call. It MUST NOT require code at those targets or a beacon root for the
omitted call. These rules apply even when the targets contain code and Amsterdam
is active; other header validation remains unchanged.

EIP-6110 deposit-log parsing is also excluded. Receipt logs remain intact, and the
execution-request list is empty.

Ethereum finalization also applies block and ommer rewards, withdrawal balance
increments, and the DAO transition. Those state changes are excluded explicitly:
they implement Ethereum's proof-of-work issuance, beacon-chain withdrawals, and
DAO recovery rules. Nonempty withdrawals remain invalid.

Receipts retain their order, logs, status, and cumulative gas. Header gas used
remains regular execution gas when [TIP-1016](./tip-1016.md) is enabled and
cumulative transaction gas after refunds otherwise. Blob gas accounting is unchanged.

## Activation and compatibility

This TIP activates with the numbered Tempo upgrade that includes it. The upgrade
and network activation timestamps are TBD. Before that upgrade, historical
execution MUST retain all existing
processing and validation. Later Ethereum forks or dependency updates MUST NOT
add automatic block system calls without a Tempo protocol change.

Removing calls can change state roots or block validity when their targets contain
code or their validation rules apply. Custom chains that rely on Ethereum rewards
or the DAO transition also change behavior at activation. Applications reading
excluded system-contract state must account for automatic updates stopping.

# Tooling

Clients, payload builders, replay tools, and execution proofs must use the same
Tempo hardfork gate. Existing chain-spec upgrade configuration supplies activation.

# Observability

N/A. Existing execution diagnostics expose block-import failures and execution
commitments. At rollout, compare state roots, receipts, gas, and requests across
upgraded nodes, verify history and committee updates, and confirm unchanged replay
before activation.

# Invariants

- Test before, at, and after activation, including legacy rewards and DAO behavior.
- History records the parent hash when enabled and deployed; genesis and missing
  code retain their existing behavior.
- State-changing code at every excluded target receives no automatic call, even
  with Amsterdam active. Missing builder code cannot invalidate a block.
- Deposit-shaped logs remain ordinary receipt logs and produce no requests.
- Committee updates preserve epoch-boundary ordering and reject invalid outcomes.
- Initialization, withdrawal rejection, incentive validation, receipts, and both
  gas-accounting modes retain their existing rules.
