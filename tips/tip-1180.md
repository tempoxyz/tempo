# TIP-1180: Zone Identity

## Abstract

From T15, a new Zone predeploy, `ZoneIdentity`, records orgs, their members, and which TIP-20s each org may send to each other org. Zone execution checks every TIP-20 transfer, deposit and withdrawal against it, so several companies can share one Zone without moving funds outside paths they agreed to. An org can only restrict where funds go, not amounts or calls.

## Motivation

A Zone today restricts participants only through its portal's public account allowlist, which applies to the whole Zone. Several companies sharing one Zone need rules per company, membership kept inside the Zone, and enforcement in execution so the batch proof shows that only allowed moves happened. A sequencer that drops transactions proves nothing, misses transfers that contracts make in nested calls, and binds only an honest sequencer.

TIP-403 policies are public on Tempo and restrict who holds a token, not who pays whom. [TIP-1164](./tip-1164.md) proposes self-custodied organization accounts with policy lists, limits and an exit for members. This TIP covers custodial or operator-created accounts, whose only rule is which org may send which token to which org.

## Assumptions

- The Zone keeps the [privacy modifications](../zones/specs/spec.md#privacy-modifications) of the Zones specification. `ZoneIdentity` views follow the same account-indexed access control.
- The sequencer is trusted for liveness only.
- The portal admin may be a multisig on Tempo and never sends Zone transactions.
- Members have no exit their org cannot block: the org admin can freeze or remove them, and a removed member can only withdraw to its own address on Tempo. Zones whose members need a guaranteed exit should use TIP-1164.

# Specification

## Overview

An org is an ID with an admin. Each address is in at most one org; addresses in no org are in org 0, which has no edges unless the registrar sets them. For orgs A and B and token T, the edge says whether T may move from a member of A to a member of B. A's admin sets the outbound half, B's admin sets the inbound half, and the edge is their AND. Membership is by address, so deposit senders and withdrawal destinations on Tempo can be members too. The registrar creates endpoint orgs for them with itself as admin, so a deposit or withdrawal needs the registrar's half like any other edge, except the withdraw-to-self exit in [the check](#the-check).

| Role | Acts through | Can |
|---|---|---|
| Portal admin | `ZonePortal.setIdentityConfig` on Tempo | Set the registrar and turn enforcement on or off |
| Registrar | Zone transactions | Create orgs, replace org admins, administer org 0 |
| Org admin | Zone transactions | Add, remove and freeze its members; set its halves of edges |

## Mechanics

### Activation and configuration

At the first T15 block, the Zone deploys code at `ZoneIdentity`'s address, `0x1c00000000000000000000000000000000000003`, through the boundary deployment T15 uses for the address registry; without code, the account's storage would be cleared after each transaction that touches it. Before T15 the address has no code and no check runs.

`ZonePortal.setIdentityConfig(registrar, enforced)` is callable only by the portal admin while the portal's access-policy capability is active. It stores both values in portal slot 28, packed after `transfersEnabled`, and emits `IdentityConfigUpdated`. The Zone reads them from finalized Tempo state at its anchor. Enforcement is off until set.

### Orgs and members

The registrar creates orgs with `createOrg(admin)`, whose IDs start at 1 and increase, and replaces an org's admin with `setOrgAdmin`. Org 0's admin is always the registrar.

An org admin adds an account in no org with `addMember`. Only the account's org admin can call `removeMember`, which moves it back to org 0, so a member cannot leave to escape its org's rules. `setFrozen` blocks every move to or from a member.

### Edges

`setOutbound(fromOrg, toOrg, tokens, allowed)` requires the caller to administer `fromOrg`, and `setInbound(toOrg, fromOrg, tokens, allowed)` requires the caller to administer `toOrg`. Both orgs must exist. For each listed token, the call sets its half to `allowed`, then stores `orgs[A].edges[B][T] = orgs[A].outbound[B][T] && orgs[B].inbound[A][T]`, so the check reads one slot. Either admin can close an edge alone. Moves inside an org use the org's edge to itself. Edges are kept per token, so the number of tokens is unbounded.

### The check

With enforcement off, every move is allowed and no `ZoneIdentity` storage is read. Otherwise a move of T from `from` to `to` is allowed when neither address is frozen and either:

1. it is a withdrawal from an address in org 0 to the same address on Tempo; or
2. the edge from `org(from)` to `org(to)` allows T.

The check reads at most three Zone slots: each address's member slot, which holds its org and frozen flag, and one edge. The enforcement flag shares the Tempo slot TIP-20 already reads for `transfersEnabled`. The cost does not depend on the number of orgs, tokens or edges, or on whether the move stays inside an org.

| Operation | Pair checked | When denied |
|---|---|---|
| `transfer`, `transferWithMemo` | caller to `to` | Reverts with `OrgPolicyForbids` |
| `transferFrom`, `transferFromWithMemo` | `from`, the owner, to `to` | Reverts with `OrgPolicyForbids` |
| Deposit from Tempo | L1 sender to decrypted recipient | Bounces back to Tempo, as a failed deposit does |
| `ZoneOutbox.requestWithdrawal` | sender to L1 `to`, and sender to `zoneFallbackRecipient` when it differs | Reverts with `OrgPolicyForbids` |

The TIP-20 check runs in the token precompile after the T15 and `transfersEnabled` checks, so it also covers transfers that contracts make in nested calls. Withdrawal bounce-backs, fees and burns are not checked. A direct transfer to the outbox is denied, because the outbox is in org 0.

## Interfaces

```solidity
interface IZoneIdentity {
    /// Creates an org administered by `admin`. Registrar only.
    function createOrg(address admin) external returns (uint64 orgId);
    /// Replaces an org's admin. Registrar only. Reverts for org 0.
    function setOrgAdmin(uint64 orgId, address admin) external;

    /// Adds an account in no org to `orgId`. That org's admin only.
    function addMember(uint64 orgId, address account) external;
    /// Moves an account back to org 0. Its org's admin only.
    function removeMember(address account) external;
    /// Freezes or unfreezes a member. Its org's admin only.
    function setFrozen(address account, bool frozen) external;
    /// Sets `fromOrg`'s outbound half for each token. `fromOrg`'s admin only.
    function setOutbound(uint64 fromOrg, uint64 toOrg, address[] calldata tokens, bool allowed) external;
    /// Sets `toOrg`'s inbound half for each token. `toOrg`'s admin only.
    function setInbound(uint64 toOrg, uint64 fromOrg, address[] calldata tokens, bool allowed) external;

    function orgAdmin(uint64 orgId) external view returns (address);
    /// Visible to the account, its org's admin and the registrar.
    function orgOf(address account) external view returns (uint64 orgId, bool frozen);
    /// Visible to the admin of either org and the registrar.
    function edge(uint64 fromOrg, uint64 toOrg, address token) external view returns (bool allowed);

    event OrgCreated(uint64 indexed orgId, address admin);
    event OrgAdminUpdated(uint64 indexed orgId, address admin);
    event MemberUpdated(address indexed account, uint64 indexed orgId, bool frozen);
    event OutboundUpdated(uint64 indexed fromOrg, uint64 indexed toOrg, address indexed token, bool allowed);
    event InboundUpdated(uint64 indexed toOrg, uint64 indexed fromOrg, address indexed token, bool allowed);

    /// The caller is not the required admin, or the registrar is unset.
    error Unauthorized();
    /// `orgId` is above the highest org created.
    error UnknownOrg(uint64 orgId);
    /// A zero admin or account, or org 0 where an org is required.
    error InvalidAddress();
    /// `addMember` for an account already in an org.
    error AlreadyMember(address account);
    /// `removeMember` or `setFrozen` for an account in org 0.
    error NotMember(address account);
    /// The move fails [the check](#the-check).
    error OrgPolicyForbids(address token, address from, address to);
}

interface IZonePortal {
    /// Sets the ZoneIdentity registrar and enforcement flag. Admin only.
    function setIdentityConfig(address registrar, bool enforced) external;
    event IdentityConfigUpdated(address registrar, bool enforced);
}
```

`ZoneIdentity` storage, in field order:

| Field | Type |
|---|---|
| `org_count` | `uint64` |
| `orgs` | `mapping(uint64 => Org)`; `Org` is `{ admin: address, outbound, inbound, edges }`, each of the last three a `mapping(uint64 otherOrg => mapping(address token => bool))` |
| `members` | `mapping(address => Member)`; `Member` is `{ org: uint64, frozen: bool }` in one slot |

The portal stores `_identityRegistrar` at slot 28, offset 10, and `_identityEnforced` at slot 28, offset 30, without public getters, to keep the portal runtime under the code size limit.

# Compatibility

- **Existing Zones:** unchanged until T15 and until the portal admin enables enforcement.
- **T15 portal runtime:** adds the two packed fields and the setter; earlier storage is unchanged.
- **Integrations on an enforcing Zone:** disallowed transfers revert with `OrgPolicyForbids` and deposits from unknown senders bounce. The registrar adds deposit senders and withdrawal destinations to endpoint orgs before the portal admin enables enforcement.
- **Indexers:** mappings cannot be listed, so off-chain views of orgs, members and edges are rebuilt from `ZoneIdentity` events.
- **Zone checker:** ignores `IdentityConfigUpdated`, which does not change L1 liabilities.

# Observability

| Event | Answers |
|---|---|
| `OrgCreated`, `OrgAdminUpdated` | Which orgs exist and who administers each |
| `MemberUpdated` | An account's org and frozen state; org 0 means removed |
| `OutboundUpdated`, `InboundUpdated` | Which half of which edge changed, for which token |
| `IdentityConfigUpdated` (Tempo) | When the registrar or enforcement changed |

A denied move shows as an `OrgPolicyForbids` revert naming the token and both addresses, or as a deposit bounce-back.

# Threat Model

| Actor | Controls | Defense | If compromised |
|---|---|---|---|
| Registrar | Org creation, org admins, org 0 | Set only by the portal admin on Tempo | Can take over any org's rules by replacing its admin. Cannot move funds |
| Portal admin | Registrar and enforcement flag | Existing portal admin controls | Can turn enforcement off for the whole Zone |
| Org admin | Its members and its halves of edges | Cannot set another org's half | Can freeze or remove its members at once. Cannot open a path another org has not accepted |
| Sequencer | Ordering and liveness | Checks run in execution and are proven | Can delay transactions, not admit a disallowed move |
| Member | Its own transactions | Cannot remove itself or edit edges | None beyond its own funds |

Residual risks: the registrar, as admin of every endpoint org, can lift any org's rules; members have no exit their org cannot block, and a removed member can only withdraw to its own address; a sender can learn whether a recipient's org accepts its org by testing a transfer.

# Invariants

- With enforcement on, every TIP-20 balance change between Zone addresses other than withdrawal bounce-backs, fees and burns, every deposit credit and every withdrawal request satisfies [the check](#the-check) against the state before the move.
- An address is in at most one org.
- For every A, B and T, `orgs[A].edges[B][T] == orgs[A].outbound[B][T] && orgs[B].inbound[A][T]`.
- Only an org's admin changes its members or its halves of edges; only the registrar creates orgs or changes an org's admin.
- Before T15 execution reads neither `ZoneIdentity` storage nor the enforcement flag; with enforcement off it reads only the flag. In both cases it produces the same results as without this TIP.

Tests must cover the T14 to T15 transition with orgs configured afterwards; an edge allowing moves only once both halves are set; per-token edges; transfers, `transferFrom` by a third-party spender, deposits from allowed and unknown senders, and withdrawals to allowed and unknown destinations; freeze; removal leaving only the withdraw-to-self exit; and enforcement turned off again.
