# TIP-1180: Zone Identity

## Abstract

From T15, a new Zone predeploy, `ZoneIdentity`, records orgs, their members, and which TIP-20s each org may send to each other org. Zone execution checks every TIP-20 transfer, deposit and withdrawal against it, so several companies can share one Zone without moving funds outside paths they agreed to. An org can only restrict where funds go, not amounts or calls. An org's admin and its designated readers may read its members' account-scoped state: balances, nonces and keychain state, through precompile getters and the redacted RPC.

## Motivation

A Zone today restricts participants only through its portal's public account allowlist, which applies to the whole Zone. Several companies sharing one Zone need rules per company, membership kept inside the Zone, and enforcement in execution so the batch proof shows that only allowed moves happened. A sequencer that drops transactions proves nothing, misses transfers that contracts make in nested calls, and binds only an honest sequencer.

TIP-403 policies are public on Tempo and restrict who holds a token, not who pays whom. [TIP-1164](./tip-1164.md) proposes self-custodied organization accounts with policy lists, limits and an exit for members. This TIP covers custodial or operator-created accounts, whose only rule is which org may send which token to which org.

On a Zone, only an account can read its own state. A company running its users' accounts on a shared Zone needs to read their balances to reconcile and support them, and often a third party, such as a custodian or compliance provider, needs the same view without holding the admin key. Today that is only possible through the Zone operator, who sees everything. Running a zone per company, or routing every read through the operator, would keep this off-chain, but neither lets a company or its delegate read its users directly with a rule the Zone itself enforces.

## Assumptions

- The Zone keeps the [privacy modifications](../zones/specs/spec.md#privacy-modifications) of the Zones specification. `ZoneIdentity` views follow the same account-indexed access control.
- The sequencer is trusted for liveness only.
- The portal admin may be a multisig on Tempo and never sends Zone transactions.
- Members have no exit their org cannot block: the org admin can freeze or remove them, and a removed member can move funds only along edges the registrar sets for org 0. Zones whose members need a guaranteed exit should use TIP-1164.
- A member's state is readable by its org by design; Zones whose members must keep state from their org should not put them in orgs.
- The redacted RPC authenticates callers as the Zones specification describes.

# Specification

## Overview

An org is an ID with an admin. Each address is in at most one org; addresses in no org are in org 0, which has no edges unless the registrar sets them. An edge joins two sides. A side, `OrgKey { orgId, l1 }`, is an org's accounts on the Zone, or with `l1` set its addresses on Tempo; the Tempo side of org A is written `A|L1` below. For sides X and Y and token T, the edge says whether T may move from X to Y. X's org admin sets the outbound half, Y's org admin sets the inbound half, and a move needs both. Zone transfers use Zone-to-Zone edges, deposits use an edge from the sender's Tempo side, and withdrawals use an edge to the recipient's Tempo side, so an org can accept withdrawals to an address without accepting Zone transfers to it.

| Role | Acts through | Can |
|---|---|---|
| Portal admin | `ZonePortal.setIdentityConfig` on Tempo | Set the registrar and turn enforcement on or off |
| Registrar | Zone transactions | Create orgs, replace org admins, administer org 0 |
| Org admin | Zone transactions | Add, remove and freeze its members; set its halves of edges; designate readers of its members |
| Reader | Precompile getters, redacted RPC | Read the account-scoped state of the org's members |

## Mechanics

### Activation and configuration

At the first T15 block, the Zone deploys code at `ZoneIdentity`'s address, `0x1c00000000000000000000000000000000000003`, through the boundary deployment T15 uses for the address registry; without code, the account's storage would be cleared after each transaction that touches it. Before T15 the address has no code and no check runs.

`ZonePortal.setIdentityConfig(registrar, enforced)` is callable only by the portal admin while the portal's access-policy capability is active. It stores both values in portal slot 28, packed after `transfersEnabled`, and emits `IdentityConfigUpdated`. The Zone reads them from finalized Tempo state at its anchor. Enforcement is off until set.

### Orgs and members

The registrar creates orgs with `createOrg(admin)`, whose IDs start at 1 and increase, and replaces an org's admin with `setOrgAdmin`. Org 0's admin is always the registrar.

An org admin adds accounts with `addMembers(orgId, accounts)`; every account must be in no org and not virtual, or the call adds none. Only the account's org admin can call `removeMember`, which moves it back to org 0, so a member cannot leave to escape its org's rules. `setFrozen` blocks every move to or from a member.

### Edges

`setEdge(from, to, tokens, allowed)` sets, for each listed token, the halves of the edge the caller administers: the outbound half as `from`'s org admin and the inbound half as `to`'s. An admin of both orgs, as for an org's edge to itself, sets both in one call; a caller that administers neither is refused. Both orgs must exist, and an edge from Tempo to Tempo is refused because no move uses it. All three edges between two orgs for a token, transfer, deposit and withdrawal, share one slot of six flags. Either admin can close an edge alone. Moves inside an org use the org's edge to itself. Edges are kept per token, so the number of tokens is unbounded.

### The check

With enforcement off, every move is allowed and no `ZoneIdentity` storage is read. Otherwise a move of T from `from` to `to` is allowed when neither address is frozen and both halves of the edge below allow T:

| Move | Edge | If it does not allow T |
|---|---|---|
| Zone transfer | `org(from)` to `org(to)` | Denied |
| Deposit | `org(from)\|L1` to `org(to)` | `0\|L1` to `org(to)`, meaning any address on Tempo |
| Withdrawal | `org(from)` to `org(to)\|L1` | `org(from)` to `0\|L1`, meaning any address on Tempo |

A [TIP-1022](./tip-1022.md) virtual recipient is checked as its registered master, whose balance TIP-20 credits, using the address registry the Zone mirrors from Tempo; an unregistered one is denied, so a deposit to it bounces like any other denied deposit. Senders are checked as given. `addMembers` refuses virtual addresses.

The check reads each address's member slot, which holds its org and frozen flag, and one edge slot, plus a second edge slot when a deposit or withdrawal falls back to `0|L1`. The enforcement flag shares the Tempo slot TIP-20 already reads for `transfersEnabled`. The cost does not depend on the number of orgs, tokens or edges, or on whether the move stays inside an org.

| Operation | Pair checked | When denied |
|---|---|---|
| `transfer`, `transferWithMemo` | caller to `to` | Reverts with `OrgPolicyForbids` |
| `transferFrom`, `transferFromWithMemo` | `from`, the owner, to `to` | Reverts with `OrgPolicyForbids` |
| Deposit from Tempo | L1 sender to decrypted recipient | Bounces back to Tempo, as a failed deposit does |
| `ZoneOutbox.requestWithdrawal` | sender to L1 `to`, and sender to `zoneFallbackRecipient` when it differs | Reverts with `OrgPolicyForbids` |

The TIP-20 check runs in the token precompile after the T15 and `transfersEnabled` checks, so it also covers transfers that contracts make in nested calls. Withdrawal bounce-backs, fees and burns are not checked. A direct transfer to the outbox is denied, because the outbox is in org 0.

### Reads

The redacted RPC is the Zone's authenticated JSON-RPC, which answers account-scoped methods only for the caller's own account. This TIP adds one read rule, written `canRead(reader, account)`: true when `reader` is `account`, or when `account` is in an org other than 0 and `reader` is that org's current admin or a reader the current admin designated. Every surface below, and `ZoneIdentity.orgOf`, grants an account-scoped read by this rule; `orgOf` also answers the registrar.

An org's admin calls `setReader(orgId, reader, allowed)` to designate or remove a reader. Reader entries are stored per admin epoch: `readers[epoch][reader]`, where `setOrgAdmin` increments the org's epoch. When the registrar replaces an org's admin, the readers designated before stop counting at once, without being listed or deleted, and stay lapsed even if an earlier admin is reappointed. Setting an entry to its current value succeeds and emits `ReaderUpdated` again.

| Surface | Before | From T15 |
|---|---|---|
| Precompile getters gated by account (TIP-20 `balanceOf`, keychain, nonce, storage credits) | Caller must be an account the getter names | Same, or `canRead(caller, subject)`, where the subject is the account whose state it is |
| TIP-20 `allowance(owner, spender)` | Caller must be the owner or the spender | Same, or `canRead(caller, owner)` |
| Redacted RPC `eth_getBalance`, `eth_getTransactionCount` | `0x0` unless the authenticated caller is the account | Same, or `canRead(caller, account)` both at the requested block and at the latest block |
| Redacted RPC `eth_call`, `eth_estimateGas` at a block other than the latest or pending | Getters apply their rule | Getters apply only their rule from before T15 |

The RPC asks `ZoneIdentity.canRead` through a call from the authenticated caller, so the RPC and execution apply one rule. It evaluates the rule at the requested block, so an org cannot read a member's state from before it joined, and at the latest block, so removing a reader or replacing an admin also revokes reads of earlier blocks. A call executing at an earlier block sees only that block's readers, so the RPC runs `eth_call` and `eth_estimateGas` at earlier blocks with `canRead(reader, account)` true only when `reader` is `account`; an org reads its members' history through `eth_getBalance` and `eth_getTransactionCount`. Before T15 the call returns no data, which the RPC treats as no. The call is bounded by the same timeout as the RPC's other Tempo reads, so a slow Tempo RPC fails the request instead of stalling it.

Receipts, logs and transaction lookups in the redacted RPC are unchanged; extending them is left to a later TIP.

## Interfaces

```solidity
interface IZoneIdentity {
    /// Creates an org administered by `admin`. Registrar only.
    function createOrg(address admin) external returns (uint64 orgId);
    /// Replaces an org's admin. Registrar only. Reverts for org 0.
    function setOrgAdmin(uint64 orgId, address admin) external;

    /// Adds an account in no org to `orgId`. That org's admin only.
    function addMembers(uint64 orgId, address[] calldata accounts) external;
    /// Moves an account back to org 0. Its org's admin only.
    function removeMember(address account) external;
    /// Freezes or unfreezes a member. Its org's admin only.
    function setFrozen(address account, bool frozen) external;
    /// One side of an edge: an org's accounts on the Zone, or with `l1` its addresses on Tempo.
    struct OrgKey {
        uint64 orgId;
        bool l1;
    }

    /// Sets the halves of each token's edge from `from` to `to` that the caller administers.
    function setEdge(OrgKey from, OrgKey to, address[] calldata tokens, bool allowed) external;

    /// Designates or removes a reader of `orgId`'s members, under the org's current admin.
    /// That org's admin only. Reverts with `InvalidAddress` for org 0 or a zero `reader`.
    function setReader(uint64 orgId, address reader, bool allowed) external;
    /// Whether `canRead(msg.sender, account)` holds.
    function canRead(address account) external view returns (bool);

    function orgAdmin(uint64 orgId) external view returns (address);
    /// Visible to anyone who `canRead` the account, and the registrar.
    function orgOf(address account) external view returns (uint64 orgId, bool frozen);
    /// Visible to the admin of either org and the registrar.
    function edge(OrgKey from, OrgKey to, address token) external view returns (bool allowed);

    event OrgCreated(uint64 indexed orgId, address admin);
    event OrgAdminUpdated(uint64 indexed orgId, address admin);
    event MemberUpdated(address indexed account, uint64 indexed orgId, bool frozen);
    /// Both halves of the edge after the change.
    event EdgeUpdated(uint64 indexed fromOrg, bool fromL1, uint64 indexed toOrg, bool toL1, address indexed token, bool fromOk, bool toOk);
    event ReaderUpdated(uint64 indexed orgId, address indexed reader, bool allowed);

    /// The caller is not the required admin, or the registrar is unset.
    error Unauthorized();
    /// `orgId` is above the highest org created.
    error UnknownOrg(uint64 orgId);
    /// A zero admin or account, or org 0 where an org is required.
    error InvalidAddress();
    /// An edge from Tempo to Tempo.
    error InvalidEdge();
    /// `addMembers` for an account already in an org.
    error AlreadyMember(address account);
    /// `removeMember` or `setFrozen` for an account in org 0.
    error NotMember(address account);
    /// The move fails [the check](#the-check).
    error OrgPolicyForbids(address token, address from, address to);
}

interface IZonePortal {
    /// Sets the ZoneIdentity registrar and enforcement flag. Admin only.
    function setIdentityConfig(address registrar, bool enforced) external;
    event IdentityConfigUpdated(address registrar, bool enforced);
}
```

`ZoneIdentity` storage, in field order:

| Field | Type |
|---|---|
| `org_count` | `uint64` |
| `orgs` | `mapping(uint64 => Org)`; `Org` is `{ admin: address, edges: mapping(uint64 toOrg => mapping(address token => Edges)), adminEpoch: uint64, readers: mapping(uint64 epoch => mapping(address reader => bool)) }`; `Edges` holds the outbound and inbound halves of the transfer, deposit and withdrawal edges, six flags in one slot |
| `members` | `mapping(address => Member)`; `Member` is `{ org: uint64, frozen: bool }` in one slot |

The portal stores `_identityRegistrar` at slot 28, offset 10, and `_identityEnforced` at slot 28, offset 30, without public getters, to keep the portal runtime under the code size limit.

# Compatibility

- **Existing Zones:** unchanged until T15 and until the portal admin enables enforcement.
- **T15 portal runtime:** adds the two packed fields and the setter; earlier storage is unchanged.
- **Integrations on an enforcing Zone:** disallowed transfers revert with `OrgPolicyForbids` and deposits from unknown senders bounce. Deposit senders and withdrawal destinations need to be members of orgs with edges to the orgs they serve before the portal admin enables enforcement.
- **Members of an org:** their state becomes readable by the org's admin and readers. Wallets and integrations that assumed only the account can read it must account for that. Accounts in no org are unchanged.
- **Indexers:** mappings cannot be listed, so off-chain views of orgs, members, edges and readers are rebuilt from `ZoneIdentity` events; an `OrgAdminUpdated` lapses every reader designated before it.
- **Zone checker:** ignores `IdentityConfigUpdated`, which does not change L1 liabilities.

# Observability

| Event | Answers |
|---|---|
| `OrgCreated`, `OrgAdminUpdated` | Which orgs exist and who administers each; when every reader of an org lapsed |
| `MemberUpdated` | An account's org and frozen state; org 0 means removed |
| `EdgeUpdated` | Both halves of an edge for a token after each change |
| `ReaderUpdated` | Which reader the org's current admin designated or removed |
| `IdentityConfigUpdated` (Tempo) | When the registrar or enforcement changed |

A denied move shows as an `OrgPolicyForbids` revert naming the token and both addresses, or as a deposit bounce-back.

# Threat Model

| Actor | Controls | Defense | If compromised |
|---|---|---|---|
| Registrar | Org creation, org admins, org 0 | Set only by the portal admin on Tempo | Can take over any org's rules by replacing its admin. Cannot move funds |
| Portal admin | Registrar and enforcement flag | Existing portal admin controls | Can turn enforcement off for the whole Zone |
| Org admin | Its members, its halves of edges and its readers | Cannot set another org's half; reads only its own members, and loses that with every reader it designated when replaced | Can freeze or remove its members at once and read their state. Cannot open a path another org has not accepted |
| Reader | Nothing; reads its org's members | Removed by the admin at any time, including for earlier blocks through the RPC | Exposes members' balances, nonces and keychain state until removed |
| Sequencer | Ordering and liveness | Checks run in execution and are proven | Can delay transactions, not admit a disallowed move |
| Member | Its own transactions | Cannot remove itself or edit edges | None beyond its own funds |
| Other org's admin, or an address in no org | Nothing | `canRead` is false | No access to members' state |

Residual risks: the registrar can replace any org's admin and so lift its rules; members have no exit their org cannot block, and a removed member has none unless the registrar opens one for org 0; a sender can learn whether a recipient's org accepts its org by testing a transfer; the registrar can replace an org's admin and so gain its read access; precompile reads are priced warm or cold, so a caller that warms an org's slots first can learn from gas whether an account is in that org, which `orgOf` already reveals to its readers.

# Invariants

- With enforcement on, every TIP-20 balance change between Zone addresses other than withdrawal bounce-backs, fees and burns, every deposit credit and every withdrawal request satisfies [the check](#the-check) against the state before the move.
- An address is in at most one org.
- An edge's outbound half changes only when its sending org's admin calls `setEdge`, and its inbound half only when its receiving org's admin does.
- Only an org's admin changes its members or its halves of edges; only the registrar creates orgs or changes an org's admin.
- An account in org 0 is readable only by itself; `canRead(r, a)` is true only if `r == a`, `r` is the current admin of `a`'s org, or `r` is a reader that admin designated.
- Every surface in [Reads](#reads) grants a read exactly when its row says, and `orgOf` answers exactly those who `canRead` the account, and the registrar.
- Before T15 execution reads neither `ZoneIdentity` storage nor the enforcement flag; with enforcement off it reads only the flag. In both cases it produces the same results as without this TIP.

Tests must cover the T14 to T15 transition with orgs configured afterwards; an edge allowing moves only once both halves are set; per-token edges; transfers, `transferFrom` by a third-party spender, deposits from allowed and unknown senders, and withdrawals to allowed and unknown destinations; an address reachable by withdrawal but not by Zone transfer; the `0|L1` fallback; freeze; removal leaving no exit unless the registrar opens one; enforcement turned off again; an org's admin and a designated reader reading a member through `balanceOf` and the redacted RPC; a removed reader and a replaced admin's readers being refused, including through `eth_getBalance` and `eth_call` at a block before the removal; and another org's admin and an address in no org being refused, including for an account in org 0.
