# TIP-1180: Zone Identity

## Abstract

From T15, a Zone can run several companies in one shared zone and keep each one's money inside the paths it agreed to. A new predeploy, `ZoneIdentity`, records orgs, their members, and for each pair of orgs which TIP-20s may move between them. Zone execution checks every TIP-20 transfer, deposit and withdrawal against it, so the prover covers the check. The main limitation is that an org can only narrow where its members' funds go; it cannot limit amounts or calls.

## Motivation

A Zone today isolates participants only through its portal's public account allowlist, which applies to the whole zone. Running several companies in one zone needs three things the Zone does not have:

1. **Per-org rules.** Members of one company may pay each other and its approved off-ramps, but not another company, unless both companies agree.
2. **Private membership.** Who belongs to which org must stay inside the zone.
3. **Provable enforcement.** Off-ramps need evidence that only allowed moves happened. A sequencer that leaves transactions out of blocks gives no such evidence, misses transfers that contracts make in nested calls, and binds only an honest sequencer.

TIP-403 policies are public on Tempo and limit who holds a token, not who may pay whom. [TIP-1164](./tip-1164.md) proposes self-custodied organization accounts with policy lists, spending limits, groups and an eject path. This TIP covers a narrower case: custodial or operator-created accounts, where membership is assigned by the org admin and the only rule is which org may send which token to which org. The two can coexist; TIP-1164's richer policy could later be layered on the same org record.

## Assumptions

- The Zone keeps the [privacy modifications](../zones/specs/spec.md#privacy-modifications) of the Zones specification. `ZoneIdentity` views follow the same account-indexed access control.
- The sequencer is trusted for liveness, as the Zones specification states. Enforcement does not depend on it being honest.
- The portal admin may be a multisig contract on Tempo. It never sends Zone transactions.
- Members do not hold their own exit. A member can be frozen or removed by its org admin; a removed member can only withdraw to its own address on Tempo. Zones whose members need a guaranteed exit should use TIP-1164.

# Specification

## Overview

| Term | Meaning |
|---|---|
| Org | An ID, an admin, and its edges to other orgs. It holds no funds. |
| Member | An address assigned to exactly one org by that org's admin. |
| Org 0 | Every address in no org. Its admin is the registrar. It has no edges unless the registrar sets them. |
| Registrar | The key that creates orgs and assigns their admins. The portal admin sets it on Tempo. |
| Edge | For orgs A and B and token T, whether T may move from a member of A to a member of B. |

Authority is split across three roles:

| Role | Where it acts | Can |
|---|---|---|
| Portal admin | Tempo, `ZonePortal.setIdentityConfig` | Set the registrar and turn enforcement on or off |
| Registrar | Zone transactions | Create orgs, replace an org's admin, administer org 0 |
| Org admin | Zone transactions | Add, remove and freeze its members; set its own half of every edge it is on |

An edge needs both sides. Org A's admin sets which tokens A sends to B (outbound), and B's admin sets which tokens B accepts from A (inbound). The edge is their AND. Endpoints that are not users, such as deposit wallets and off-ramp addresses, are members of orgs the operator administers, so an exit needs the operator's half like any other edge.

## Mechanics

### Activation

At the first T15 block, the Zone deploys `ZoneIdentity` at `0x1c00000000000000000000000000000000000003` with code, through the same boundary deployment as the T15 address registry. An address without code is cleared after each transaction that touches it, which would erase the registry's storage. Before T15 the address has no code and no check runs.

### Configuration on Tempo

`ZonePortal.setIdentityConfig(registrar, enforced)` is callable only by the portal admin, and only while the portal's access-policy capability is active. It stores the registrar and the enforcement flag in portal slot 28, packed after `transfersEnabled`, and emits `IdentityConfigUpdated`. The Zone reads both values from finalized Tempo state at its anchor. Enforcement starts off, so a zone that never calls it behaves as before.

### Orgs and members

The registrar calls `createOrg(admin)`; org IDs start at 1 and increase. `setOrgAdmin` replaces an org's admin; org 0's admin is always the registrar.

An org admin calls `addMember(orgId, account)`. The account must be in no org; an address belongs to at most one org. `removeMember(account)` moves an account back to org 0 and only its org's admin may call it, so a member cannot leave to escape its org's rules. `setFrozen(account, frozen)` blocks every move to or from the account.

### Edges

`setOutbound(fromOrg, toOrg, tokens, allowed)` requires the caller to administer `fromOrg`; `setInbound(toOrg, fromOrg, tokens, allowed)` requires the caller to administer `toOrg`. Both orgs must exist. For each token, the call writes its half and then writes the stored edge as `outbound[A][B][T] && inbound[B][A][T]`, so the transfer check reads one slot instead of two. Either admin can close an edge alone by clearing its half. Moves inside one org use the edge from the org to itself. There is no limit on the number of tokens.

### The check

With enforcement off, every move is allowed and nothing is read. With enforcement on, a move of token T from `from` to `to` is allowed when:

1. Neither address is frozen.
2. It is a withdrawal from an address in org 0 to that same address on Tempo; or
3. The edge from `org(from)` to `org(to)` allows T.

The check reads at most three Zone slots (both members and one edge), plus the enforcement flag, which shares the Tempo slot TIP-20 already reads for `transfersEnabled`. The cost does not depend on the number of orgs, tokens or edges, and a move inside an org costs the same as one between orgs.

### Where it runs

| Operation | Pair checked | When denied |
|---|---|---|
| `transfer`, `transferWithMemo` | caller to `to` | Reverts with `OrgPolicyForbids` |
| `transferFrom`, `transferFromWithMemo` | `from` (the owner, not the spender) to `to` | Reverts with `OrgPolicyForbids` |
| Deposit from Tempo | L1 sender to decrypted recipient | Bounces back to Tempo, as a failed deposit does today |
| `ZoneOutbox.requestWithdrawal` | sender to L1 `to`, and sender to `zoneFallbackRecipient` when it is not the sender | Reverts with `OrgPolicyForbids` |

The TIP-20 check runs in the token precompile after the existing T15 and `transfersEnabled` checks, so transfers made by contracts in nested calls are checked too. Withdrawal bounce-backs, fees and burns are not checked. A direct transfer to the outbox address is denied, because the outbox is in org 0.

## Interfaces

```solidity
interface IZoneIdentity {
    /// Creates an org administered by `admin`. Registrar only.
    function createOrg(address admin) external returns (uint64 orgId);
    /// Replaces an org's admin. Registrar only. Reverts for org 0.
    function setOrgAdmin(uint64 orgId, address admin) external;

    /// Adds an account in no org to `orgId`. That org's admin only.
    function addMember(uint64 orgId, address account) external;
    /// Moves an account back to org 0. Its org's admin only.
    function removeMember(address account) external;
    /// Freezes or unfreezes a member. Its org's admin only.
    function setFrozen(address account, bool frozen) external;
    /// Sets `fromOrg`'s outbound half for each token. `fromOrg`'s admin only.
    function setOutbound(uint64 fromOrg, uint64 toOrg, address[] calldata tokens, bool allowed) external;
    /// Sets `toOrg`'s inbound half for each token. `toOrg`'s admin only.
    function setInbound(uint64 toOrg, uint64 fromOrg, address[] calldata tokens, bool allowed) external;

    function orgAdmin(uint64 orgId) external view returns (address);
    /// Visible to the account, its org's admin and the registrar.
    function orgOf(address account) external view returns (uint64 orgId, bool frozen);
    /// Visible to the admin of either org and the registrar.
    function edge(uint64 fromOrg, uint64 toOrg, address token) external view returns (bool allowed);

    event OrgCreated(uint64 indexed orgId, address admin);
    event OrgAdminUpdated(uint64 indexed orgId, address admin);
    event MemberUpdated(address indexed account, uint64 indexed orgId, bool frozen);
    event OutboundUpdated(uint64 indexed fromOrg, uint64 indexed toOrg, address indexed token, bool allowed);
    event InboundUpdated(uint64 indexed toOrg, uint64 indexed fromOrg, address indexed token, bool allowed);

    error Unauthorized();
    error UnknownOrg(uint64 orgId);
    error InvalidAddress();
    error AlreadyMember(address account);
    error NotMember(address account);
    error OrgPolicyForbids(address token, address from, address to);
}

interface IZonePortal {
    /// Sets the ZoneIdentity registrar and enforcement flag. Admin only.
    function setIdentityConfig(address registrar, bool enforced) external;
    event IdentityConfigUpdated(address registrar, bool enforced);
}
```

Storage of `ZoneIdentity`, in field order:

| Field | Type |
|---|---|
| `org_count` | `uint64` |
| `orgs` | `mapping(uint64 => Org)`, where `Org` is `{ admin: address, outbound, inbound, edges: mapping(uint64 => mapping(address => bool)) }` |
| `members` | `mapping(address => Member)`, where `Member` is `{ org: uint64, frozen: bool }` packed in one slot |

The portal stores `_identityRegistrar` at slot 28, offset 10, and `_identityEnforced` at slot 28, offset 30. They have no public getters, to keep the portal runtime under the code size limit.

# Compatibility

- **Existing zones:** none. Enforcement is off until the portal admin turns it on, and the predeploy only exists from T15.
- **T15 portal runtime:** the regenerated `ZonePortal` runtime adds the two packed fields and the setter. Storage before slot 28, offset 10 is unchanged.
- **Wallets and integrations on an enforcing zone:** transfers that no edge allows revert with `OrgPolicyForbids`; deposits from unknown senders bounce. Operators must add deposit senders and withdrawal destinations as members of endpoint orgs before turning enforcement on.
- **Indexers and backends:** mappings cannot be listed, so off-chain views of orgs, members and edges are rebuilt from `ZoneIdentity` events.
- **Zone checker:** ignores `IdentityConfigUpdated`, which does not change L1 liabilities.

# Observability

| Event | Answers |
|---|---|
| `OrgCreated`, `OrgAdminUpdated` | Which orgs exist and who administers each |
| `MemberUpdated` | Which org an account is in, and whether it is frozen (org 0 means removed) |
| `OutboundUpdated`, `InboundUpdated` | Which half of which edge changed, for which token |
| `IdentityConfigUpdated` (Tempo) | When the registrar or enforcement changed |

A denied move is visible as a `OrgPolicyForbids` revert naming the token and both addresses, or as a deposit bounce-back.

# Threat Model

| Actor | Controls | Defense | If compromised |
|---|---|---|---|
| Org admin | Its members and its halves of edges | Cannot set another org's half; edges need both sides | Can freeze or remove its members, and stop their transfers, at once. Cannot open a path another org has not accepted |
| Registrar | Org creation, org admins, org 0 | Set only by the portal admin on Tempo | Can replace any org's admin and so take over its rules. Cannot move funds |
| Portal admin | Registrar and enforcement flag | Existing portal admin controls | Can turn enforcement off for the whole zone |
| Sequencer | Ordering and liveness | Checks run in execution and are proven | Can delay transactions, not admit a disallowed move |
| Member | Its own transactions | Cannot remove itself or edit edges | None beyond its own funds |

Residual risks: the operator, as registrar and endpoint admin, can lift any org's rules; members have no exit the org cannot block except withdrawing to their own address after removal; a sender can learn whether a recipient's org accepts its org by testing a transfer.

# Invariants

- With enforcement on, every TIP-20 balance change between two Zone addresses, every deposit credit and every withdrawal request satisfies the check in [The check](#the-check) against the state before the move.
- An address is in at most one org.
- For every A, B and T, `edges[A][B][T] == outbound[A][B][T] && inbound[B][A][T]`.
- Only an org's admin changes its members or its halves of edges; only the registrar creates orgs or changes an org's admin.
- Before T15, and with enforcement off, zone execution reads no `ZoneIdentity` storage and its results equal those without this TIP.

Tests must cover: the T14 to T15 transition with orgs configured afterwards; an edge allowing moves only once both halves are set; per-token edges; transfers, `transferFrom` by a third-party spender, deposits from allowed and unknown senders, and withdrawals to allowed and unknown destinations; freeze; removal leaving only the withdraw-to-self exit; and enforcement turned off again.
