# TIP-1137: Remove Admin Access Keys

## Abstract

This TIP removes admin access keys ([TIP-1049](./tip-1049.md)) at T14. From T14, no key can become an admin key and only an account's root key manages its access keys. Admin keys authorized before T14 keep signing until revoked, and anyone can revoke them.

Configurable accounts ([TIP-1107](./tip-1107.md)) replace the feature: a device that would have held an admin key is added as an owner instead.

## Motivation

TIP-1049 added admin keys at T6 so a second device could manage access keys without the root key. An admin key has no spending limit, call scope or expiry. It acts alone and can authorize further admin keys.

Configurable accounts ship at T14 and cover the same use case. To give a second device full control, the user adds its key as an owner whose weight meets the approval threshold. That carries less risk than an admin key:

| Property | Admin key | Owner |
|---|---|---|
| Where it is recorded | Keychain storage, outside the account configuration | Account configuration, committed in the account leaf ([TIP-1108](./tip-1108.md)) |
| Approval | Always acts alone | Counts toward a threshold the user chooses; a 2-of-2 setup needs both devices |
| Adding more keys with the same power | Can authorize new admin keys by itself | Needs the owner quorum through `updateConfig` ([TIP-1109](./tip-1109.md)) |
| Rotation | Revoke and re-authorize per key | `updateConfig` bumps the configuration version and invalidates signatures for earlier versions |

Admin keys also bypass configurable accounts. An EOA migrated with [TIP-1113](./tip-1113.md) would keep its pre-T14 admin keys, which could spend without the owner quorum.

The feature is unused on mainnet. Between mainnet blocks 26,629,191 (T6 activation) and 43,226,357, there were zero `AdminKeyAuthorized` events and 4,961 regular key authorizations. Both admin-creation paths emit the event; pre-T6 keys have `is_admin = false`. Moderato had 256 admin keys across 101 accounts.

Alternatives considered:

- **Treat stored admin keys as revoked at T14.** Every keychain read path would need a fork-gated override, and the pool would need a T14 boundary eviction. A permissionless revoke reaches the same end state with less protocol surface, at the cost of a window until the keys are revoked.
- **Keep admin keys and exclude them from configurable accounts.** Keeps the T6 surface and needs extra rules in TIP-1111 and TIP-1113 for a feature nobody uses on mainnet.

## Assumptions

| Assumption | If violated |
|---|---|
| Configurable accounts activate at T14. | This TIP can activate alone. Multi-device key management then needs the root key until configurable accounts ship. |
| Mainnet has no admin keys at T14 activation. | Their holders lose them at T14. The root key can authorize a regular access key or migrate the account to a configurable account. |
| Tempo developers revoke all known admin keys right after T14 activation. | Unrevoked admin keys stay unrestricted signers, including on accounts migrated to configurable accounts, until someone revokes them. |

# Specification

## Overview

All rules apply from T14. Before T14, TIP-1049 applies unchanged, so T6 to T13 blocks replay exactly.

1. **Creation.** No path can set `is_admin = true` on a key.
2. **Management.** Only the root key manages access keys. A configurable parent's access keys are managed by its own owner quorum ([TIP-1111](./tip-1111.md)).
3. **Existing admin keys.** Keys stored with `is_admin = true` keep signing until revoked. Anyone can revoke them with `revokeAdminKey`.

## Creation

- `authorizeAdminKey` reverts with `UnknownFunctionSelector`.
- A transaction whose `key_authorization` has `is_admin = true` is invalid.
- Only the target account's root key may sign a `key_authorization`. A signature by an access key is invalid, whatever its stored flag.
- If `account` is present in a `key_authorization`, it must equal the target account.
- TIP-1111's admin-signed grants are removed. Only the configurable parent's own owner quorum may sign a grant.
- The transaction pool applies the same rules.

## Management

- `ensure_admin_caller` accepts only the root key. `authorizeKey`, `revokeKey`, `updateSpendingLimit`, `setAllowedCalls` and `removeAllowedCalls` revert with `UnauthorizedCaller` when the transaction is signed by an access key.
- `isAdminKey(account, keyId)` returns `keyId == account`.
- `verifyKeychainAdmin(account, hash, signature)` returns true only when the recovered signer is `account`. Its results are unchanged on mainnet, where no admin keys exist.

## Existing admin keys

Keys authorized before T14 with `is_admin = true` stay in storage without a protocol migration. They keep signing transactions with no spending limit or call scope, but have no management authority. Revoking them is up to users; Tempo developers revoke all known admin keys after T14 activation, using dataland's `stg_t6_admin_key_authorized` model.

From T14, `revokeAdminKey(account, keyId)` is callable by anyone:

- If `keys[account][keyId]` is stored with `is_admin = true`, it is revoked exactly as `revokeKey` would revoke it, and `KeyRevoked(account, keyId)` is emitted. The key ID cannot be reused.
- Otherwise, including for already revoked keys, the call reverts with `InvalidKeyId`.

The root key can still revoke its own admin keys with `revokeKey`. `updateSpendingLimit`, `setAllowedCalls` and `removeAllowedCalls` keep rejecting admin keys with `InvalidKeyId`, as under TIP-1049. The pool evicts pending transactions from a revoked admin key through its existing `KeyRevoked` handling.

## Interfaces

- `authorizeAdminKey(keyId, signatureType, witness)` is removed from dispatch.
- `revokeAdminKey(address account, address keyId)` is added to `IAccountKeychain`, dispatched from T14.
- `KeyAuthorization` keeps its optional `is_admin` and `account` RLP fields. Encodings are unchanged.
- `AuthorizedKey` keeps its `is_admin` byte. `AdminKeyAuthorized` stays in the ABI for historical logs. Indexers and decoders need no change.
- `isAdminKey` and `verifyKeychainAdmin` keep their selectors, so existing callers do not revert.

# Tooling

- SDKs (viem, tempo-go, pytempo, tempo-std) remove `authorizeAdminKey`, `is_admin` and admin-signed key authorizations for T14 chains.
- Wallets that offered admin keys add the device key as a configurable account owner instead, through account creation, `updateConfig` or TIP-1113 migration.
- After T14 activates on each network, Tempo developers run a script that calls `revokeAdminKey` for every admin key listed by dataland's `stg_t6_admin_key_authorized` model.
- The T6 upgrade docs and the AccountKeychain reference note the removal.

# Observability

No events are added. From T14, `AdminKeyAuthorized` must not appear on any network; `stg_t6_admin_key_authorized` confirms it. `KeyRevoked` events from `revokeAdminKey` track the cleanup; once every listed admin key has one, no admin key can sign.

# Threat Model

| Actor | Trust |
|---|---|
| Root key of an EOA | The only key that manages the account's access keys, as before T6. A compromised root key controls the account. |
| Owner quorum of a configurable account | Manages owners and access keys. A compromised quorum can replace the other owners. |
| Access keys | Sign within their spending limits and call scopes. They cannot manage keys. |
| Keys stored as admin before T14 | Sign without limits until revoked; no management authority. Anyone can revoke them. |

An owner whose weight meets the threshold alone has the same unrestricted authority an admin key had, plus owner rotation. Users who add a device that way accept that risk; the difference is that it is recorded in the account configuration and chosen through the threshold.

# Invariants

- Before T14, behavior matches TIP-1049, and T6 to T13 blocks replay unchanged.
- From T14, no transaction or call sets `is_admin = true` on any key.
- From T14, `revokeAdminKey` succeeds if and only if the target is a stored, unrevoked key with `is_admin = true`.
- From T14, `isAdminKey(account, keyId)` is true if and only if `keyId == account`.
- From T14, every keychain mutator rejects transactions signed by an access key.
- From T14, `verifyKeychainAdmin` returns false for every non-root signer.

Tests must cover each rule at T13 and T14, including admin keys created before T14 through both creation paths (`authorizeAdminKey` and `key_authorization` with `is_admin`), an admin-signed `key_authorization`, a stored admin key signing after T14, `revokeAdminKey` from an unrelated caller on admin, regular and revoked keys, a configurable parent, and an EOA migrated with TIP-1113 that holds an admin key.
