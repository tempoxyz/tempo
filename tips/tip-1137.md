# TIP-1137: Remove Admin Access Keys

## Abstract

From T14, the AccountKeychain no longer creates or honors admin access keys. Only an account's
root key can manage its access keys. Behavior before T14 is unchanged, so historical blocks
replay exactly as they did.

## Motivation

TIP-1049 added admin access keys at T6 so that a second device could manage keys without the
root key. Configurable accounts (TIP-1107 cluster, T14) cover that use case with an owner set and
a quorum, and they can rotate owners without changing the account address.

Admin keys are unrestricted. On a configurable account, an admin key can act for the account
without its owner quorum. Removing admin keys in the same fork that ships configurable accounts
means that combination never activates.

Admin keys have no mainnet usage. From T6 activation (block 26,629,191) to block 43,226,357,
mainnet emitted zero `AdminKeyAuthorized` events, while accounts authorized 4,961 regular access
keys. Both creation paths emit that event, and pre-T6 keys default to `is_admin = false`, so no
admin key exists in mainnet state. Moderato has 256 admin keys across 101 accounts.

## Assumptions

- Configurable accounts activate at T14. If they slip, this TIP can still activate alone, but
  multi-device key management then requires the root key until they ship.
- Nodes must replay T6–T13 blocks with TIP-1049 semantics, so all changes are hardfork-gated.
- Mainnet has no admin keys at activation. If any appear before T14, they are handled as
  described in [Existing admin keys](#existing-admin-keys).

# Specification

All rules below apply from T14. Before T14, TIP-1049 applies unchanged.

## AccountKeychain

- `authorizeAdminKey(keyId, signatureType, witness)` is unscheduled. Calls return the
  `UnknownFunctionSelector` error, as for any selector outside its schedule.
- `ensure_admin_caller` accepts only the root key. A transaction signed by any access key gets
  `UnauthorizedCaller` from `authorizeKey`, `revokeKey`, `updateSpendingLimit`,
  `setAllowedCalls` and `removeAllowedCalls`.
- `isAdminKey(account, keyId)` returns `keyId == account`.
- `AdminKeyAuthorized` is no longer emitted. The event stays in the ABI.

## Key authorizations

- The `is_admin?` and `account?` RLP fields of `KeyAuthorization` stay decodable, so encodings
  do not change.
- A transaction whose `key_authorization` has `is_admin = true` is invalid.
- A `key_authorization` must be signed by the target account's root key. An authorization signed
  by an access key is invalid, regardless of that key's stored flag.
- If `account` is present, it must equal the target account, as before.
- The transaction pool applies the same rules.

## SignatureVerifier

`verifyKeychainAdmin(account, hash, signature)` returns true only when the recovered signer is
`account`. The selector stays live so existing callers do not revert. On mainnet its results do
not change, because no admin keys exist.

## Configurable accounts

TIP-1111 allows an active admin access key to sign `key_authorization` for a configurable parent.
That clause is removed: only the parent's own owner quorum may sign it.

## Existing admin keys

Keys stored with `is_admin = true` before T14 remain in storage and are not migrated.

- They no longer satisfy any admin check.
- They remain usable for signing as unrestricted access keys, as they were before T14.
- `updateSpendingLimit`, `setAllowedCalls` and `removeAllowedCalls` continue to reject them with
  `InvalidKeyId`.
- `revokeKey` from the root key revokes them.

# Tooling

- SDKs (viem, tempo-go, pytempo, tempo-std) mark `authorizeAdminKey`, `is_admin` and
  admin-signed key authorizations as removed from T14.
- The T6 upgrade docs and the AccountKeychain reference note the T14 removal.
- The `is_admin` byte of `AuthorizedKey` and the `AdminKeyAuthorized` event stay, so indexers
  and decoders need no change.

# Observability

N/A. No events are added. After T14, `AdminKeyAuthorized` must not appear on any network, which
the existing `stg_t6_admin_key_authorized` model in dataland can confirm.

# Threat Model

- **Root key:** the only key that can manage access keys, as before T6.
- **Access keys, including previously admin ones:** are untrusted for key management. They keep
  their signing permissions.
- **Configurable account owners:** control the account only through their quorum. No single key
  can bypass it.

# Invariants

- Before T14, behavior is identical to TIP-1049, and T6–T13 blocks replay unchanged.
- From T14, no transaction or call can set `is_admin = true` on any key.
- From T14, `isAdminKey(account, keyId)` is true if and only if `keyId == account`.
- From T14, every keychain mutator rejects transactions signed by an access key.
- From T14, `verifyKeychainAdmin` returns false for every non-root signer.

Tests must cover each rule at T13 and T14, including admin keys created before T14, both
creation paths (`authorizeAdminKey` and `key_authorization` with `is_admin`), admin-signed
`key_authorization`, and a configurable parent.
