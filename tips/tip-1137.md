# TIP-1137: Remove Admin Access Keys

## Abstract

This TIP removes admin access keys ([TIP-1049](./tip-1049.md)) at T14. No new admin keys can be created, and existing ones are treated as revoked. Access-key management requires the account's unretired primitive root or its configurable owner quorum.

Devices use configurable account ownership ([TIP-1107](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1107.md)) for replacement authority.

## Motivation

TIP-1049 added admin keys at T6 for multi-device management. Each acts alone, with unrestricted spending and calls, no expiry, and authority to create more admins.

Configurable owners record that authority in the account configuration:

| Property | Admin key | Owner |
|---|---|---|
| Record | Keychain storage | Account configuration committed in the leaf ([TIP-1108](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1108.md)) |
| Approval | Acts alone | Configured weight and threshold; 2-of-2 needs both devices |
| Adding equivalent authority | Acts alone | Owner quorum through `updateConfig` ([TIP-1109](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1109.md)) |
| Rotation | Revoke and re-authorize | `updateConfig` increments the version, invalidating earlier-version signatures |

Without this TIP, [TIP-1113](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1113.md) migration would retain admin grants that spend without the owner quorum.

Mainnet blocks 26,629,191 (T6 activation) to 43,226,357 contained zero `AdminKeyAuthorized` events and 4,961 regular key authorizations. Both admin-creation paths emit the event; pre-T6 keys have `is_admin = false`. The survey found 256 admin keys across 101 Moderato accounts. Activation counts may differ.

Alternatives considered:

- **Keep stored admin keys as signers.** Leaves unrestricted spending, including after migration.
- **Exclude admin keys from configurable accounts.** Retains the T6 surface and needs extra TIP-1111 and TIP-1113 rules.

## Assumptions

| Assumption | If violated |
|---|---|
| Configurable accounts activate at T14. | This TIP can activate alone. Multi-device key management then needs the root key until configurable accounts ship. |
| Mainnet has no admin keys at T14 activation. | Their holders lose that authority at T14. The account's direct authority must authorize replacement access. |
| Moderato's admin keys can be dropped at T14. | Affected users lose access through those keys; authorize replacements before activation. |

# Specification

## Overview

All rules apply from T14. Before T14, TIP-1049 applies unchanged, so T6 to T13 blocks replay exactly.

**Direct authority** means the account's unretired primitive root or its owner quorum verified under [TIP-1114](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1114.md). A nonzero commitment retires bare root authority under [TIP-1112](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1112.md).

1. **Creation.** No path can set `is_admin = true` on a key.
2. **Management.** Only the account's direct authority manages its access keys, through direct calls or signed grants ([TIP-1111](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1111.md)).
3. **Existing admin keys.** Keys stored with `is_admin = true` are treated as revoked.

## Creation

- `authorizeAdminKey` reverts with `UnknownFunctionSelector`.
- A transaction whose `key_authorization` has `is_admin = true` is invalid.
- Only the target account's direct authority may sign a `key_authorization`. Access-key signatures are invalid regardless of the stored flag; reject `Keychain` signatures in this field.
- If `account` is present in a `key_authorization`, it must equal the target account.
- The transaction pool applies the same rules.

## Management

- `ensure_admin_caller` accepts calls authorized by the account's direct authority, including a verified owner quorum. `authorizeKey`, `revokeKey`, `updateSpendingLimit`, `setAllowedCalls` and `removeAllowedCalls` revert with `UnauthorizedCaller` when the transaction is signed by an access key.
- `isAdminKey(account, keyId)` returns true if and only if `keyId == account` and the account's call-time configuration commitment is zero. It does not authenticate owner quorums.

## SignatureVerifier

`verifyKeychainAdmin(account, hash, signature)` retains [TIP-1020](./tip-1020.md)'s signature checks and [TIP-1114](https://github.com/tempoxyz/tempo/blob/tanishk/configurable-account-tips/tips/tip-1114.md#on-chain-signature-verification)'s primitive-inner restriction:

- Decode a V2 keychain envelope with a primitive inner signature. Unsupported or malformed encodings, including a configurable (`0x05`) inner signature, revert with `InvalidFormat()`.
- Verify the primitive signature over the existing V2 signing hash. A cryptographic verification failure reverts with `InvalidSignature()`.
- After those checks pass, return `true` if the embedded account and recovered signer both equal `account`, and its call-time commitment is zero. Return `false` otherwise.

Use `verifyConfigurableAccount` to verify an owner quorum. Existing gas and system errors still apply.

## Existing admin keys

Pre-T14 admin rows stay in storage without migration. From T14, keychain views return their revoked-key result for these grants, including `verifyKeychain`, `getKey`, `getAllowedCalls`, `getRemainingLimit` and `getRemainingLimitWithPeriod`.

| Operation on a stored admin key | Result |
|---|---|
| Access-key transaction using the stored admin grant | Invalid with `KeyAlreadyRevoked` |
| `authorizeKey` with the same `keyId` | Reverts with `KeyAlreadyRevoked`; the key ID cannot be reused |
| `revokeKey` by the account's direct authority | Succeeds and writes the revoked state; this cleanup is optional |
| `updateSpendingLimit`, `setAllowedCalls`, `removeAllowedCalls` | Revert with `KeyAlreadyRevoked` |

At T14, the pool evicts pending transactions using stored admin grants.

## Interfaces

- `authorizeAdminKey(keyId, signatureType, witness)` is removed from dispatch.
- `KeyAuthorization` keeps its optional `is_admin` and `account` RLP fields. Encodings are unchanged.
- `AuthorizedKey` keeps its `is_admin` byte. `AdminKeyAuthorized` stays in the ABI for historical logs.
- `isAdminKey` and `verifyKeychainAdmin` keep their selectors. Their authority checks change as specified above; existing format and signature errors still apply.

# Compatibility

- SDKs (viem, tempo-go, pytempo, tempo-std) remove `authorizeAdminKey`, `is_admin` and admin-signed key authorizations for T14 chains.
- Wallets offer owner enrollment through creation, `updateConfig` or TIP-1113 migration.
- Before Moderato activation, use dataland's `stg_t6_admin_key_authorized` model to identify accounts needing replacement authority from their root keys.
- Existing encodings and historical event decoding remain valid. Indexers and wallets must report stored admin keys as revoked from T14.
- No mainnet admin grants are revoked if none exist at activation. Root retirement still changes helper results for configurable accounts.
- The T6 upgrade docs and the AccountKeychain reference note the removal.

# Observability

No events are added. From T14, `AdminKeyAuthorized` must not appear on any network; monitor `stg_t6_admin_key_authorized`. Use of stored admin grants yields pool rejection with `KeyAlreadyRevoked`.

# Threat Model

| Actor | Capability and trust boundary |
|---|---|
| Unretired primitive root holder | Controls the account and its grants until retirement under TIP-1112. Root compromise gives that control to the attacker. |
| Owner quorum | Can replace owners and authorize unrestricted access. Compromise of sufficient owner weight gives that control to the attacker. |
| Regular access-key holders | Act within their grants; they cannot manage keys. Owner rotation does not revoke their grants. |
| Stored admin-grant holders | Lose that grant's authority at T14 on every network, even though its row remains. |
| Clients and authority helpers | Must enforce current commitments and grant state. Recovered addresses and `keyId == account` alone do not establish root authority after retirement. |

An owner whose weight meets the threshold alone controls the account. Regular access-key grants also permit spending without fresh owner approvals; revoke unwanted grants separately under TIP-1111. Removing admin keys does not require a quorum for every payment.

# Invariants

- Before T14, behavior matches TIP-1049, and T6 to T13 blocks replay unchanged.
- From T14, no transaction or call sets `is_admin = true` on any key.
- From T14, no transaction can use a stored admin grant as access-key authority.
- From T14, `isAdminKey(account, keyId)` is true if and only if `keyId == account` and the account's call-time commitment is zero.
- From T14, every keychain mutator rejects transactions signed by an access key.
- Direct management remains available to an unretired primitive root or a verified owner quorum.
- For a valid V2 primitive signature, `verifyKeychainAdmin` returns false for a non-root or retired-root signer. Configurable inner signatures revert with `InvalidFormat()`.

Tests must cover each rule at T13 and T14, including both admin-creation paths, admin-signed grants, pool eviction, and every keychain view on a stored admin key. Include direct quorum management, helper checks after registration or migration, a forged configurable inner signature naming the parent, and a migrated account holding an admin key.
