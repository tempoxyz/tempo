# TIP-1137: Remove Admin Access Keys

## Abstract

This TIP removes admin access-key creation and key-management authority at T14. Existing admin keys retain unrestricted spending until revoked.

## Motivation

TIP-1049 added admin keys at T6 for multi-device key management. Configurable accounts replace them with owners who can rotate without changing the address. Admin keys bypass their quorum.

Between mainnet blocks 26,629,191 (T6 activation) and 43,226,357, there were zero `AdminKeyAuthorized` events and 4,961 regular key authorizations. Both admin-creation paths emit the event; pre-T6 keys have `is_admin = false`. Moderato had 256 admin keys across 101 accounts.

## Assumptions

| Assumption | If violated |
|---|---|
| Configurable accounts activate at T14. | This TIP can activate alone; multi-device key management requires the root key until configurable accounts ship. |
| Mainnet has no admin keys at activation. | [Existing admin keys](#existing-admin-keys) applies. |

# Specification

## Overview

All rules below apply from T14. Before T14, TIP-1049 remains unchanged for historical replay. Only the root key manages access keys; a configurable parent's owner quorum signs its grants. Existing admin keys retain spending access.

## AccountKeychain

- Calls to `authorizeAdminKey` return `UnknownFunctionSelector`.
- `ensure_admin_caller` accepts only the root key. Access-key transactions get `UnauthorizedCaller` from `authorizeKey`, `revokeKey`, `updateSpendingLimit`, `setAllowedCalls` and `removeAllowedCalls`.
- `isAdminKey(account, keyId)` returns `keyId == account`.

## Key authorizations

- A transaction whose `key_authorization` has `is_admin = true` is invalid.
- Only the target account's root key may sign `key_authorization`; access-key signatures are invalid regardless of the stored flag.
- If `account` is present, it must equal the target account.
- The transaction pool applies the same rules.
- TIP-1111's admin-signed grants are removed: only the configurable parent's own owner quorum may sign.

## SignatureVerifier

`verifyKeychainAdmin(account, hash, signature)` returns true only when the recovered signer is `account`. Its results are unchanged on mainnet, where no admin keys exist.

## Existing admin keys

Pre-T14 keys with `is_admin = true` remain in storage without migration.

- They fail all admin checks but remain unrestricted transaction signers.
- `updateSpendingLimit`, `setAllowedCalls` and `removeAllowedCalls` still reject them with `InvalidKeyId`.
- The root key can revoke them with `revokeKey`.

## Interfaces

- `authorizeAdminKey(keyId, signatureType, witness)` is unscheduled.
- The `is_admin?` and `account?` RLP fields of `KeyAuthorization` stay decodable; encodings are unchanged.
- The `is_admin` byte of `AuthorizedKey` stays; the `AdminKeyAuthorized` event stays in the ABI. Indexers and decoders need no change.
- The `verifyKeychainAdmin` selector stays live, so existing callers do not revert.

# Tooling

- SDKs (viem, tempo-go, pytempo, tempo-std) mark `authorizeAdminKey`, `is_admin` and admin-signed key authorizations as removed from T14.
- The T6 upgrade docs and AccountKeychain reference note the removal.

# Observability

No events are added. From T14, `AdminKeyAuthorized` must not appear on any network; dataland's `stg_t6_admin_key_authorized` model can confirm this.

# Threat Model

| Actor | Trust |
|---|---|
| Root key | The only key that can manage access keys, as before T6. |
| Access keys, including previously admin ones | Untrusted for key management. They keep their signing permissions. |
| Configurable account owners | Control the account only through their quorum. No single key can bypass it. |

# Invariants

- Before T14, behavior is identical to TIP-1049, and T6–T13 blocks replay unchanged.
- From T14, no transaction or call can set `is_admin = true` on any key.
- From T14, `isAdminKey(account, keyId)` is true if and only if `keyId == account`.
- From T14, every keychain mutator rejects transactions signed by an access key.
- From T14, `verifyKeychainAdmin` returns false for every non-root signer.

Tests must cover each rule at T13 and T14, including admin keys created before T14, both creation paths (`authorizeAdminKey` and `key_authorization` with `is_admin`), admin-signed `key_authorization`, and a configurable parent.
