# TIP-1125: Bounded Native Payment Execution

## Abstract

Native Earn and Zone operations need to call venue, engine, gateway, and verifier
contracts while executing in Tempo's payment lane. This proposal defines an EVM2
execution envelope that bounds and charges those calls, including nested calls,
reverted execution, storage work, and proof processing. Native registration alone
does not grant payment eligibility; an explicitly specified operation profile is
required. Activation remains unscheduled until the implementation, historical
replay, migration, and devnet evidence gates pass.

## Motivation

The current ZoneFactory initializes Solidity-compatible portal storage, but the
portal executes a Solidity proxy. TIP-1084 defines a native share shell with vault
callbacks and explicitly excludes those callbacks from payment classification.
Both surfaces therefore need execution and admission changes to support complete
Earn/Zone payment lifecycles without consuming the general lane.

Whitelisting only a precompile address would allow arbitrary dependent contract
execution to use the payment lane without an operation-specific bound. Removing
external calls would exclude existing yield engines and composable withdrawals.
This proposal instead uses ordinary EVM2 call frames with shared paid resources
and consensus-defined operation profiles. A profile does not certify venue
solvency or eliminate the dependent contract's trust assumptions.

## Assumptions

- EVM2 owns the transaction state journal, gas tracking, original transaction
  environment, tracing, and opcode dispatch for all production execution paths.
- Historical blocks remain executable using their original fork rules. The
  legacy executor may be removed only after differential replay and genesis sync.
- Native Earn/portal specifications define their ABIs, custody, accounting, and
  migration. This TIP defines their execution envelope and admission contract.
- Dependent contracts and proxy implementations can change and can be hostile.
  All code reachable from them executes under the same paid parent resources.
- Proof backend identity and valid fork/chain binding are specified by the Zone
  proof protocol. A development proof bypass is not production proof evidence.

## Threat Model

Users can send malformed ABI, hostile callback targets, nested batches, replayed
proofs, insufficient gas, and transactions racing activation. Dependencies can
reenter native accounts, revert after mutating state, return oversized data,
delegate to different code, create contracts, or consume their entire allowance.
Builders can misclassify transactions or underreport resources; validators must
recompute admission and accounting. Sequencers and provers cannot replace the
fork schedule or omit work from a settlement proof. Vault governance retains its
existing authority over backing and valuation and receives no metering exemption.

# Specification

## Activation and historical rules

A future hardfork activates native payment profiles. The exact fork identifier
and schedule MUST be assigned before this TIP moves to Scheduled. Before that
fork, existing TIP-1045 classification and Solidity portal/vault execution rules
apply. Earlier state roots, receipts, gas, logs, and system calls MUST NOT change.
Restart, reorg, historical RPC execution, proving, and sync select rules by the
block being executed, not the node's current wall clock or latest head.

## Operation profiles

Each admitted operation MUST specify its native identity predicate, selectors,
canonical ABI constraints, and limits on:

1. Input and returned bytes, decoded collection counts, proof bytes and proof
   count, signatures, tokens, and queued withdrawals processed.
2. Total transaction execution and state resources, maximum native child calls,
   each child's execution gas and exposed state reservoir, and EVM depth.
3. Storage allocation, log bytes/topics, proof verification, hashing, copying,
   encryption parsing, and migration work, with a consensus gas schedule.
4. Failure and recovery behavior, including the journal boundary for callbacks,
   bounce-back, refund recording, batch processing, and pending async claims.

These are consensus constants, not limits selected by vault governance. User gas
or calldata bounds may lower the allowed work but cannot raise the profile bound.
All collection iteration MUST be bounded before allocation/decoding. Every
native loop and cryptographic operation MUST consume paid gas. Native address
prefixes alone MUST NOT identify initialized portal or vault accounts.

Companion native Earn/Zone specifications MUST supply concrete profiles and
numeric limits before activation. This TIP grants no selector eligibility by
itself. Pool, builder, validator, estimator, and prover MUST use one fork-aware
classification implementation. A batch is a payment only if every call qualifies
and the complete batch fits its aggregate profile. Native payment execution is
charged to the payment budget and the total block budget; it MUST NOT silently
fall back to a general-lane transaction when a profile limit is exceeded.

## Native external calls

The native account MUST call its dependency through EVM2's existing message
execution path. The child receives:

- `msg.sender` equal to the calling native account;
- the original transaction's origin, effective gas price, chain ID, blob hashes,
  and extension context;
- the current block environment, active gas table, inspector, journal, warmness,
  access-list recorder, and state-gas accounting;
- depth equal to parent depth plus one, subject to the EVM depth limit;
- static context if either parent context or operation is static.

Default transaction environments, independent EVMs, unmetered system-call gas,
and maximum-gas storage providers MUST NOT be used for payment dependency calls.
Native protocol calls use zero native value. Dependent EVM execution otherwise
retains ordinary opcode rules, including its nested calls and creations.
EIP-7702 code resolution MUST charge both accounts and preserve the target's
storage context and caller identity; delegation MUST NOT force native dispatch.

The parent MUST pay copy and account-access overhead before executing a child,
respect cold/warm pricing, apply the active EIP-150 reduction, reserve forwarded
execution gas, and pass only the profile's allowed state reservoir. State work
may spill into the forwarded execution allowance under the active gas rules.
Unused unforwarded state resources remain owned by the parent and participate
in ordinary spill reconciliation when the child returns.

The operation maintains a transaction-local call count and non-refundable work
reservation. Before every native child call, decrement the call count and reserve
the sum of maximum forwarded execution gas and exposed reservoir. Checked
arithmetic is required. The reservation cannot be replenished by a refund,
storage restoration, caught revert, reentrancy, or a new native sub-operation.
An exhausted reservation fails before executing another dependency. This bound
is distinct from fee charging, which uses actual work under the EVM gas schedule.
The complete transaction gas limit also bounds native overhead and ordinary
descendant execution. No nested entrypoint can reset either parent budget.

Child gas MUST be settled and merged using EVM2's success/revert/halt semantics.
Executed work is paid even on revert or halt; storage refunds and reservoir
restoration follow the active fork rules. Returning or copying oversized output
fails within the defined child journal boundary; neither a successful child
write nor a refund may escape that failure. Fatal database/execution failures
abort validation and MUST NOT become a recoverable application callback failure.

Native handlers MUST release scoped storage borrows before executing a child.
Nested native calls cannot alias mutable state or bypass storage action tracking.
Reentrancy locks are journaled and unwind at the same boundary as custody changes.

## Callback and settlement boundaries

A portal or vault specification MUST distinguish ordinary child success,
application revert, exceptional halt, and fatal host error. A callback that
reverts cannot retain token movements, shares, approvals, logs, or queue writes.
If a portal records a recoverable failure and enqueues a private bounce, only
the explicitly specified outer settlement state may commit. It MUST charge the
failed child work and the bounce work and consume the withdrawal once. A failed
proof cannot advance height, queue cursors, nullifiers, or commitments.

## Migration and engine removal gates

Activation MUST preserve native account identities and historical storage.
Any conversion of backing, fee claims, pending claims, or queue state requires
a deterministic bounded migration defined by the companion specifications.
Scanning all holders, vaults, Zones, or pending claims in one activation block
is prohibited. Lazy or paged migration must prevent duplicate application and
remain correct through reorg, retry, restart, and proving.

Production must use EVM2 exclusively after the replay gate. A legacy executable
may be retained only as an external differential-test oracle, not as a node
fallback. Historical execution coverage includes all Tempo and Zone forks,
system calls, fee settlement, policy changes, and proof commitments.

# Tooling

SDKs expose the native ABIs and bounded gas/size requirements. Simulation and
estimation use the selected block's fork and identical child execution context.
Devnet tooling MUST start before activation, seed existing positions and queues,
execute the scheduled fork, then demonstrate transfer, deposit, private transfer,
withdrawal, settlement, yield, redemption, Earn spending, and failure recovery.
The implementation PRs must include reproducible commands and exact source,
binary, genesis, proof/verifier, and deployment manifests. Generated ABI and
prover compatibility checks must cover both sides of activation.

# Observability

This execution-envelope TIP adds no user event ABI. Companion specifications
retain/define the portal and vault events for their state transitions. Nodes
MUST expose transaction and aggregate operation counts, gas/resource charges,
profile-limit failures, proof/settlement lag, migration progress, and payment/
general-lane attribution. Public traces/events MUST NOT reveal encrypted Zone
recipients, private sender tags, or other private callback identifiers.

# Invariants

- No admitted dependency work has an independent, free, or resettable budget.
- Child caller, origin, static context, journal, gas, and fork remain correct.
- All required Earn/Zone payment operations consume zero general-lane resources.
- Failure cannot create unbacked shares, duplicate withdrawals, lose funds,
  advance an invalid proof cursor, or redirect a pending claim.
- All historical roots and receipts match the current execution oracle.
- Activation preserves existing balances, shares, backing, claims, and Zones.

Required evidence includes hostile/reentrant/delegated dependencies, infinite
loops, OOG, large return/revert data, static writes, state-reservoir spill/refill,
refunds, malformed inputs/proofs, and callback/settlement failure composition.
A fresh node MUST sync from genesis across activation. A mixed Earn/Zone devnet
load MUST run for at least 30 minutes after warmup, drain all queues, reconcile
backing and liabilities, and measure zero general-lane payment usage including
callbacks and settlement. Repeat with the general lane saturated and compare
against the current stack on identical hardware and workloads. Genuine accepted
proofs, receipts, lane counters, accounting snapshots, and fixed security/
correctness findings are required; mocked proofs and destination-only lane
inference cannot satisfy these gates.
