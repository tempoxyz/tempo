# TIP-1138: EVM Object Format

## Abstract

Enable EVM Object Format version 1 (EOFv1) as an opt-in contract format on
Tempo. EOF containers separate code and data, validate control flow and stack
usage before deployment, and provide structured functions, calls, and creation.
Existing legacy contracts remain supported. Activation requires a coordinated
network upgrade; this draft does not assign an upgrade or activation date.

## Motivation

Legacy EVM bytecode combines executable instructions and data, uses dynamic
jumps, and discovers many malformed-program errors only during execution.
EOF provides explicit structure and deploy-time validation, giving compilers and
execution engines stronger guarantees about control flow and stack usage.
These guarantees can support execution optimizations, but this TIP makes no
throughput claim without measurements.

Adopting a specified EOFv1 bundle gives compiler authors a defined target rather
than a Tempo-specific bytecode format. Alternatives are to retain only legacy
bytecode, adopt isolated instructions such as [TIP-1122](./tip-1122.md), or adopt
a later EOF revision with a new transaction type. Isolated instructions do not
provide container validation; a new transaction envelope is unnecessary for the
deployment path selected here.

**Proposed owner:** dankrad, subject to confirmation during review. Engineering,
research, and security reviewers and an implementation owner must be recorded
before this proposal advances under [TIP-0000](./tip-0000.md).

## Assumptions

- EOFv1 means the exact revisions below, selected from the published
  [EOF devnet-0 specification](https://notes.ethereum.org/@ethpandaops/eof-devnet-0).
  This is a proposed baseline for review, not a claim that EOF is an activated
  Ethereum feature. Later upstream revisions are not implicitly adopted.
- The activation state contains no ordinary deployed code starting with
  `0xEF00` that fails this EOF profile. Audit code in genesis allocations and
  any privileged code-writing paths before scheduling; a violation blocks
  activation until a separately reviewed resolution exists.
- Tempo's active fee, gas, nonce, authorization, precompile, and native-value
  rules remain authoritative. An execution engine supporting a different EOF
  profile cannot be enabled until it implements this profile consistently.

The selected profile uses `RETURNCONTRACT`, the `0x04` data-section marker,
EIP-663 immediate encodings, and EIP-7698 creation transactions. It does not
include EIP-7873 (`TXCREATE` / `InitcodeTransaction`), later metadata sections,
`EXTCODETYPE`, `EXTCODEADDRESS`, or `PAY`.

Enable the complete profile at one Tempo hardfork. Before activation, retain
previous bytecode and creation rules. Pool admission, payload construction,
block execution, RPC simulation, and historical replay MUST select the rules
from the applicable Tempo fork, not from an Ethereum fork name such as Osaka
or from a node-local feature flag. Revalidate pending transactions at activation.

## Containers and validation

Recognize EOF by the `0xEF00` magic and require version byte `0x01`.
Parse headers, types, code sections, optional subcontainers, and data exactly
as pinned EIP-3540 specifies. Unsupported versions, malformed headers, invalid
section lengths, invalid opcodes or immediates, invalid jump destinations,
inconsistent function types, invalid stack ranges, and invalid subcontainer
usage MUST fail validation as specified by the bundle.

Validate the full initcontainer and its subcontainers before executing externally
supplied EOF initcode. Distinguish initcontainers from deployable runtime
containers, including their termination instructions and permitted incomplete
data sections. Deployment MUST complete the runtime data section through
`RETURNCONTRACT` and enforce its declared and actual lengths. Only valid,
complete runtime containers may enter account code state.

Retain the pinned limits: 24,576 bytes for the entire deployed container,
49,152 bytes for top-level creation input including constructor arguments, and
the bundle's section, stack, and function-return-stack limits. Headers, types,
subcontainers, and data count toward size and code-deposit charges. A separate
TIP is required to raise these limits.

## Execution and legacy interoperability

Execution begins in code section zero. Use the pinned relative-jump, function,
tail-call, data access, and extended-stack instructions. Instructions prohibited
by the pinned profile, including dynamic jumps, code introspection, legacy
creation/call instructions, and `SELFDESTRUCT`, MUST be rejected by EOF validation.

`EXTCALL` and `EXTSTATICCALL` may target EOF, legacy contracts, precompiles,
or empty accounts under the active Tempo rules. `EXTDELEGATECALL` may execute
only an EOF target; a non-EOF target causes the light failure specified by the
bundle. Legacy calls, including `DELEGATECALL`, may execute EOF targets.
Resolve EIP-7702 delegations using the active Tempo rules before classifying the
effective execution code; a delegation marker is not an EOF container.
Preserve the delegated account's execution context, target warming, and charges.

Use EIP-7069 status codes: zero for success, one for revert or light failure,
and two for exceptional failure. Its return-data load/copy rules apply only
inside EOF frames; legacy frames retain their existing return-data behavior.

Legacy `EXTCODESIZE`, `EXTCODECOPY`, and `EXTCODEHASH` observe deployed EOF
code as the two bytes `0xEF00`, as specified by pinned EIP-3540. This EVM view
does not change persistent code hashing: store the full container under its
actual hash, and return the full stored bytes through `eth_getCode`.

This TIP enables EIP-663's `0xe6`, `0xe7`, and `0xe8` instructions only
in EOF code, using the pinned EIP-663 immediate encoding. If TIP-1122 is also
active, legacy code uses TIP-1122's EIP-8024 encoding. Dispatch and validation
MUST depend on the executing code format; neither encoding may leak into the
other. TIP-1122 is not a prerequisite for EOF.

## Deployment and Tempo transactions

For an otherwise valid supported transaction with an empty destination, input
starting with `0xEF00` selects the EIP-7698 path. Parse the initcontainer's
length from its header; the remaining input is constructor calldata. Include
the entire input in existing calldata, floor, and initcode-metering calculations.
Input not starting with that magic retains the legacy creation path.

Apply the same selection separately to each `Create` call in a
[TIP-0001](./tip-0001.md) transaction. Each call's `input` contains its own
initcontainer and constructor calldata. No transaction fields, signing payloads,
or transaction type bytes are added. Existing access-key restrictions on
creation and restrictions on mixing authorizations with creation still apply.

Top-level EOF creation uses Tempo's existing top-level creation address and
protocol-account nonce rules, including their batch ordering and two-dimensional
nonce handling. A user nonce key is replay protection and MUST NOT replace the
protocol-account nonce in contract address derivation. In particular, use the
same RLP-based sender/nonce address derivation as legacy top-level creation.
Successful EOF creation advances the protocol nonce exactly as the equivalent
legacy creation; failed batches preserve the existing transaction nonce rules.

Header or container validation failure is an execution failure of an otherwise
valid creation transaction/call, not a new transaction-envelope invalidity.
Charge the existing intrinsic costs, consume no initcontainer execution gas,
and deploy no code. In a Tempo batch it fails the batch and rolls back all batch
execution state and logs, retaining pre-execution effects and nonce/fee
settlement exactly as existing batch rules require. Do not make pool acceptance
of malformed EOF a different block-validity rule.

`EOFCREATE` and `RETURNCONTRACT` follow pinned EIP-7620, including constructor
calldata, auxiliary data, collision behavior, and static-context restrictions.
The `EOFCREATE` address is
`keccak256(0xff || creator || salt || keccak256(initcontainer))[12:]`,
with the creator encoded as 20 bytes and salt as 32 bytes. Constructor calldata
does not enter this hash. Legacy `CREATE` and `CREATE2` cannot deploy EOF:
an `0xEF00` initcode prefix makes them return zero before initcode execution
without incrementing the creator nonce. Legacy initcode returning runtime code
beginning with `0xEF` remains subject to the existing deployment prohibition.

## Tempo gas and fees

Use the active Tempo gas schedule for operations shared with legacy execution.
In particular, apply Tempo's creation and account-creation charges, warm/cold
access costs, memory costs, code-deposit costs, and native-value restrictions
instead of importing Ethereum's numerical prices for those operations.
The selected EOF-only instructions retain their pinned charges.

When [TIP-1016](./tip-1016.md) is active, EOF creation and code deposit use its
execution/state split, reservoir, conditional account-creation charges, and
failure refills. Charge every byte of the final container once using the active
code-deposit rate and apply the existing code-hashing charge. When it is not
active, use the then-active unsplit schedule. This TIP does not activate
TIP-1016 or alter [TIP-1060](./tip-1060.md) storage-credit behavior.

For EIP-7069 calls, after charging the caller's execution costs, forward
`g - max(floor(g / 64), 5000)` execution gas where `g` is remaining execution
gas, with the pinned 2,300 minimum-callee check. Insufficient gas takes the
specified failure path without unsigned underflow. State-gas reservoir
propagation follows the active Tempo child-frame rules; it does not count
toward these execution-gas thresholds. `EOFCREATE` uses the existing 63/64
creation forwarding rule with the same reservoir handling.

EOF does not introduce a native asset or endowment balance. Top-level nonzero
`value` is rejected as today; nonzero opcode endowments follow the active
Tempo balance and static-context rules. Stablecoin fees and sponsored
transactions settle through the existing fee manager, once per transaction.
EOF calls use the general contract-execution lane and do not acquire payment-lane
eligibility. Existing precompile policy checks apply equally from EOF callers.

# Tooling

Compilers and deployment tools need an explicit target for this pinned profile.
Publish reproducible compiler versions and deployment examples for ordinary and
Tempo transactions before testnet rollout; do not assume a generic EOF or Osaka
compiler target matches this profile. Warn that EOF callers cannot select a
per-call execution-gas limit and cannot delegate to legacy implementations.

Disassemblers, source maps, debuggers, explorers, and verification tools must
understand code-section boundaries and distinguish EVM code introspection from
the full bytes returned by `eth_getCode`. Trace frames should identify
`code_format`, `eof_version`, `code_section`, and section-relative program
counter. RPC simulation and gas estimation must use the same validation and
failure rules as block execution.

# Observability

No new consensus logs are required: application logs and receipts preserve their
existing interfaces. Nodes MUST expose diagnostic EOF validation failures with
block number (if applicable), transaction hash, batch call index (if applicable),
creation path, EOF version, failing container/section offset, and a bounded
validation-reason code. Do not log raw calldata.

Measure validation duration and failure counts by reason and creation path, and
creation success/failure counts by code format. Use bounded labels; transaction
hashes and addresses belong in diagnostic records, not metric labels. Monitor
validation cost and block execution latency during testnet rollout. Local
diagnostics MUST NOT affect consensus or turn expected failed creations into
node-fatal errors.

# Threat Model

- Transaction submitters and contract authors are untrusted. They may submit
  malformed headers, pathological nesting, invalid control flow, adversarial
  call graphs, or large constructor/auxiliary data to exhaust node resources.
- Validators and execution engines must agree on the complete pinned profile,
  Tempo adaptations, and fork selection. Divergent validation, gas charging,
  or address derivation can split consensus.
- Compilers and RPC providers are not trusted for validity. The node validates
  containers itself; cached validation must be keyed by full container bytes
  and the active validation profile, and must not bypass consensus checks.
- Existing precompiles, fee managers, and authorization mechanisms retain their
  trust boundaries. EOF entry points cannot bypass their checks.

Implement validation with bounded allocation and an explicit worklist rather
than unbounded host-stack recursion. Reject arithmetic overflows and truncated
sections deterministically. Before scheduling, benchmark adversarial valid and
invalid containers and establish acceptable validation and execution budgets
through engineering and security review.

# Invariants

1. Every stored EOF runtime container is fully valid under the activated profile;
   invalid or incomplete containers never become executable account code.
2. Legacy bytecode uses its active legacy instruction semantics. EOF additions
   do not change historical execution or reinterpret legacy data as containers.
3. All creation paths, simulations, and enabled execution backends agree on
   validity, state, code bytes, addresses, gas, and failure results.
4. Failed creation and failed batches leave no partial deployment or execution
   state; existing pre-execution and fee/nonce effects are preserved.
5. EOF does not bypass Tempo authorization, native-value, fee, state-gas,
   storage-credit, precompile, or block-budget rules.

The implementation test suite MUST cover malformed and unsupported headers;
section/count/length limits; invalid opcodes and truncated immediates; relative
jumps into immediates or across sections; stack merges and function/tail-call
boundaries; nested init/deploy containers; data completion; maximum-size
deployment; collisions; revert, static-context, and out-of-gas paths; legacy/EOF
calls and introspection; EIP-7702 resolution; both stack-immediate encodings when
TIP-1122 is active; and cold versus cached validation.

Tempo-specific cases MUST include sponsored EOF deployments, access-key
creation rejection, two-dimensional nonces, mixed creation/call batches, later
batch failure after successful deployment, pre/post-activation execution,
gas estimation, and execution/state-gas settlement and refills.

Tempo integration tests, reproducible deployment/call/verification examples,

no unexplained state/gas differences or validation failures remain and that
reviewed resource budgets hold. Activation and protocol version remain TBD
