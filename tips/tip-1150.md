# TIP-1150: Per-token Zone Withdrawal Limits

## Abstract

This TIP adds an optional withdrawal limit to each token enabled on a Zone. The
admin sets a maximum amount and a window length on the portal, and
`ZoneOutbox.requestWithdrawal` rejects any request that would take the amount
accepted in the current window above the maximum. An over-limit request reverts
before any transfer, burn, or enqueue. The limit bounds the withdrawal requests
a Zone accepts per window; it does not bound the rate at which tokens leave
Tempo escrow.

## Motivation

If many Zone accounts are compromised at once, for example through a leaked
signing service or a compromised integrator, an attacker can withdraw every
compromised balance in a few blocks. Nothing in the protocol slows this down.
`maxWithdrawalsPerBlock` limits the number of requests per block, not their
value.

A per-token value limit bounds the loss. However many accounts the attacker
controls, at most one limit of each token is accepted per window, or two across
a window boundary. The remaining funds stay on the Zone, and the operator has
time to respond, for example by pausing the portal. Limits are per token and in
raw token units because Zone tokens differ in denomination and value. Limits
are optional, and a Zone that never configures one behaves exactly as before.

Enforcing the limit when `ZonePortal.processWithdrawals` pays out would bound
tokens leaving escrow, which is a stronger guarantee. By then the user's tokens
are already burned on the Zone, so an over-limit withdrawal could only be
delayed, not rejected. The FIFO withdrawal queue would need a rule for a blocked
head, batches could be partially processed, and settlement would change.

Restoring capacity when a withdrawal bounces back would require carrying
settlement outcomes back into the limiter and attributing each one to its
original window, possibly after a configuration change. It would also let
repeatedly failing withdrawals reclaim capacity.

A rolling window removes the burst at a fixed-window boundary but needs
per-request history. Counting usage even when no limit is set would stop
re-enabling a limit from creating fresh capacity, at the cost of a storage write
on every withdrawal on every Zone. Fixed windows with accounting only for
limited tokens need one storage slot per token and no new writes on Zones that
do not opt in.

## Assumptions

- The admin is trusted. The admin can raise, lower, disable, or re-period a
  limit at any time. If the admin key is compromised, the limit provides no
  protection.
- The Zone block timestamp does not decrease and is never below the timestamp
  of the latest imported Tempo header. `TempoState` and the state transition
  function enforce this. Window membership depends on it.
- The Zone timestamp is bounded above only by honest followers, which reject
  peer blocks more than 100 ms ahead of their local clock and therefore do not
  attest to them. This TIP assumes `sequencerThreshold` cannot be met without
  honest followers. If it can, a sequencer can start new windows early.
- The Zone reads portal state at the latest finalized Tempo header it has
  imported. Configuration changes therefore take effect on the Zone after that
  delay, never before.

## Threat Model

- An attacker controlling many user accounts may have up to `withdrawalLimit`
  of each token accepted per window, and up to twice that across a window
  boundary, but cannot have more accepted. Withdrawals accepted before the
  operator responds still settle: pausing the portal stops new requests and
  delays payouts, but does not cancel accepted withdrawals.
- The admin may raise, disable, or re-period a limit, which can create fresh
  capacity, and may set a low limit. The admin cannot withhold capacity for
  longer than `MAX_WITHDRAWAL_LIMIT_PERIOD`.
- The sequencer orders transactions and so decides which requests receive a
  window's capacity. It may set the Zone timestamp ahead, but cannot start
  windows early while settlement requires honest followers.
- Any user may use up a window's shared capacity by withdrawing their own funds,
  locking out other users until rollover. Repeating this costs withdrawal fees
  and capital equal to the limit per window. The limit bounds aggregate
  acceptance; it does not guarantee access for any particular user.
- A newly enabled token is unlimited until its limit takes effect on the Zone.
  Setting both in the same Tempo block removes this gap.

# Specification

## Limit Configuration

The limit for each token is stored in the portal's existing `TokenConfig`:

```solidity
struct TokenConfig {
    bool enabled;
    bool depositsActive;
    uint128 withdrawalLimit;       // raw token units per window; 0 means no limit
    uint64 withdrawalLimitPeriod;  // window length in seconds; 0 iff withdrawalLimit is 0
}
```

The new fields occupy unused bytes of the existing slot at
`keccak256(abi.encode(token, 6))`: `enabled` at byte 0, `depositsActive` at
byte 1, `withdrawalLimit` at bytes 2-17, and `withdrawalLimitPeriod` at bytes
18-25. Existing tokens therefore read `withdrawalLimit == 0`. Because the outbox
already reads this slot to check `enabled`, reading the limit adds no Tempo
storage access and no proof data per withdrawal.

The window length is bounded:

```solidity
uint64 constant MAX_WITHDRAWAL_LIMIT_PERIOD = 7 days;
```

Seven days admits daily and weekly limits. However low a limit is set, capacity
returns at least once a week.

`setWithdrawalLimit(token, maxAmount, period)` is admin-only. It MUST revert
with `TokenNotEnabled` if the token is not enabled, as `pauseDeposits` and
`resumeDeposits` do. It MUST revert with `InvalidWithdrawalLimit` unless one of
the following holds:

```text
maxAmount == 0 && period == 0
maxAmount >  0 && 1 <= period <= MAX_WITHDRAWAL_LIMIT_PERIOD
```

The withdrawal amount counts toward the limit. The withdrawal fee does not.

### Effective configuration

The outbox reads `TokenConfig` at the state root of the latest finalized Tempo
header imported into the Zone, the same read it uses for `enabled` and the pause
expiry. A change written in Tempo block `B` applies to every Zone transaction in
the first Zone block that imports a header at or after `B`, and in every later
block. TIP-1096 header-only blocks execute no user transactions and are
unaffected.

## Usage Accounting

`ZoneOutbox` stores usage per token:

```solidity
struct WithdrawalLimitUsage {
    uint64 windowStart;  // start, in seconds, of the window `used` belongs to
    uint128 used;        // raw token units accepted in that window
}

mapping(address token => WithdrawalLimitUsage) withdrawalLimitUsage;
```

For a limit with period `p` and a Zone block with timestamp `t` in seconds:

```text
windowStart(t, p) = t - (t mod p)
```

Windows are aligned to the Unix epoch and are half-open intervals
`[windowStart, windowStart + p)`. Unused capacity does not carry over. Rollover
is lazy: the first accepted request in a new window overwrites `windowStart`,
and no action occurs at a window boundary.

## Admission

`ZoneOutbox.requestWithdrawal` applies the limit after all existing validation,
including the token-enabled check, the pause check, access and gateway policy,
and `maxWithdrawalsPerBlock`, and before any transfer or burn:

```text
(limit, period) = portal.tokenConfigs[token] at the imported Tempo header
if limit == 0:
    skip; withdrawalLimitUsage is not read or written
start     = block.timestamp - (block.timestamp mod period)
u         = withdrawalLimitUsage[token]
used      = u.windowStart == start ? u.used : 0
available = limit - min(used, limit)
if amount > available:
    revert WithdrawalLimitExceeded(token, available)
withdrawalLimitUsage[token] = (start, used + amount)
```

A request that would take `used` above `limit` MUST revert with
`WithdrawalLimitExceeded`. A request that brings `used` exactly to `limit` MUST
be accepted. A request with `amount > limit` always reverts; it is never split
or deferred to a later window.

A reverted request MUST NOT change usage, including when an enclosing call or
transaction reverts after the outbox call succeeded. Requests are evaluated in
canonical Zone transaction order, and each accepted request updates usage before
the next is checked, including multiple requests in one transaction. Only
`amount` is charged; the withdrawal fee MUST NOT be charged, whether the caller
or a separate fee payer pays it.

## Settlement and Bounce-backs

Usage is charged once, at admission. `finalizeWithdrawalBatch` and
`ZonePortal.processWithdrawals` MUST NOT read or modify usage, and the portal
applies no limit when paying out. Requests accepted in different windows MAY
settle in the same Tempo block.

When a user withdrawal fails on Tempo, the portal returns the amount to the Zone
as a withdrawal bounce-back. Processing the bounce-back, crediting the fallback
recipient, and claiming any refund MUST NOT modify usage. Capacity stays
consumed until the window rolls over, and a retry is a new request subject to
the limit.

When a deposit fails on the Zone, `ZoneInbox` returns it through
`ZoneOutbox.enqueueDepositBounceBack`, which only `ZoneInbox` can call. This
path MUST NOT read or modify usage and is exempt from the limit, so capacity
used by unrelated users cannot strand a failed deposit. The exemption depends
only on the caller being `ZoneInbox`.

## Configuration Changes

All tokens start unlimited. Because `enabled` is write-once and `enableToken`
reverts for a token that is already enabled, `enableToken` never runs on a token
that has a limit. Its assignment of the whole `TokenConfig` struct requires no
change.

A newly enabled token is unlimited until its limit takes effect on the Zone.
This applies to the initial token, which `createZone` enables, and to every
token enabled later. The admin SHOULD call `setWithdrawalLimit` in the same
Tempo block as `createZone` or `enableToken`, for example in one transaction
from an admin multisig. The Zone reads portal state at finalized block
boundaries, so it then never observes the token enabled without its limit.

When a new `withdrawalLimit` takes effect, usage is not reset. If `used` for the
current window is at or above the new limit, every request for the token
reverts until the next window. Raising the limit makes the additional capacity
available immediately.

Changing the period, disabling, and re-enabling are permitted:

- After a period change, the next request computes `start` with the new period.
  If it differs from the stored `windowStart`, `used` is treated as 0, so a
  period change MAY create fresh capacity in the current window.
- While a limit is disabled (`withdrawalLimit == 0`), usage is neither read nor
  written.
- After re-enabling, usage accepted while the limit was disabled is not
  counted. The stale `used` applies only if the stored `windowStart` equals the
  current `start`, so re-enabling MAY create fresh capacity.

No configuration change affects withdrawals the Zone has already accepted.

## Interface Changes

`IZonePortal.tokenConfig(address)` returns the extended `TokenConfig`.

`IZonePortal` adds:

```solidity
function MAX_WITHDRAWAL_LIMIT_PERIOD() external view returns (uint64);

/// Only callable by the admin. `maxAmount` of 0 disables the limit.
function setWithdrawalLimit(address token, uint128 maxAmount, uint64 period) external;
```

`IZoneOutbox` adds:

```solidity
function withdrawalLimitUsage(address token)
    external
    view
    returns (uint64 windowStart, uint128 used);

/// Returns type(uint128).max if no limit is configured.
function availableWithdrawalCapacity(address token) external view returns (uint128);
```

`availableWithdrawalCapacity` MUST return the `available` value that
`requestWithdrawal` would compute in the current Zone block.

### Events

`IZonePortal` adds:

```solidity
event WithdrawalLimitUpdated(address indexed token, uint128 maxAmount, uint64 period);
```

`setWithdrawalLimit` MUST emit `WithdrawalLimitUpdated` on success. `maxAmount`
and `period` MUST equal the values written to `TokenConfig`. No other event
signature changes.

### Errors

`IZonePortal` adds:

```solidity
error InvalidWithdrawalLimit();
```

`IZoneOutbox` adds:

```solidity
error WithdrawalLimitExceeded(address token, uint128 available);
```

`setWithdrawalLimit` reuses the existing `TokenNotEnabled` error.

## Out of Scope

This TIP does not cap tokens leaving Tempo escrow, cancel withdrawals that a
Zone has already accepted, define dynamic limits, or share a budget across
tokens. It does not change `createZone` or `CreateZoneParams`. It does not add
an abdication capability for withdrawal limits; a later TIP may let the admin
permanently give up raising or disabling them.

## Activation and Compatibility

This TIP activates through a coordinated Tempo upgrade and Zone hardfork. The
Tempo upgrade installs the new `ZonePortal` runtime, and the Zone hardfork
activates the outbox rules. Implementations MUST coordinate both activation
boundaries.

Existing tokens read `withdrawalLimit == 0` and remain unlimited until the admin
sets a limit. Withdrawals pending at activation are not charged, and
`withdrawalLimitUsage` starts empty. A Zone that never calls
`setWithdrawalLimit` executes exactly as before, with no extra state access.

`TokenConfig`, its portal storage layout, the Rust `PortalTokenConfig` mirror,
and `storage-layouts/ZonePortal.json` change together. `tokenConfig(address)`
returns a larger tuple, so offchain callers that decode the two-field return
value MUST update. Pre-activation blocks retain their active protocol-version
rules.

# Tooling

- Zone admin tooling MUST support `setWithdrawalLimit` and reading the current
  configuration and usage. Zone creation and token enablement tooling SHOULD
  set the limit in the same Tempo block as `createZone` or `enableToken`.
- SDKs and wallets SHOULD decode `WithdrawalLimitExceeded` and MAY call
  `availableWithdrawalCapacity` to warn users before they submit a request.
- The sequencer MAY drop pool transactions that would revert with
  `WithdrawalLimitExceeded`. No other sequencer change is required.
- `PortalTokenConfig` in `crates/precompiles/src/zone_factory/portal.rs`, which
  the factory and the Zone precompiles share, MUST match the extended
  `TokenConfig`, and `storage-layouts/ZonePortal.json` MUST be regenerated.

# Observability

`WithdrawalLimitUpdated` records every configuration change on Tempo. Rejected
requests revert on the Zone and emit no event, and Zone events are private, so
the sequencer SHOULD export the following metrics:

| Metric | Fields / labels | Operational question |
|---|---|---|
| `zone_withdrawal_limit_rejections_total` | `token` | Is a limit rejecting withdrawals? |
| `zone_withdrawal_limit_usage_ratio` | `token` | How close is the current window to its limit? |

Alerts SHOULD cover sustained rejections for a token, which indicate either an
attack in progress or a limit set too low for normal use.

# Invariants

| ID | Invariant | Description |
|---|---|---|
| WL1 | Bounded admission | If a token's configuration does not change during a window, the total accepted for that token in the window is at most `withdrawalLimit`. |
| WL2 | Clean revert | A reverted `requestWithdrawal` leaves usage, balances, and pending withdrawals unchanged. |
| WL3 | Single charge | Only a successful `requestWithdrawal` with `withdrawalLimit != 0` modifies `withdrawalLimitUsage`. |
| WL4 | No restoration | `finalizeWithdrawalBatch`, `processWithdrawals`, bounce-backs, refund claims, and `enqueueDepositBounceBack` never read or modify usage. |
| WL5 | Settlement unaffected | No configuration change prevents an accepted withdrawal from being batched or settled. |
| WL6 | Monotonic windows | For every token, the stored `windowStart` is at most the current Zone block timestamp. |
| WL7 | Opt-in | With `withdrawalLimit == 0`, `requestWithdrawal` behaves exactly as before activation. |
| WL8 | Historical execution | Blocks before activation produce the same results under the historical rules. |

## Test Cases

Unless stated otherwise, `withdrawalLimit` is 100 and `withdrawalLimitPeriod`
is 86,400. The test suite MUST cover:

1. **Exact limit:** with 40 used, a request for 60 is accepted and `used`
   becomes 100.
2. **One unit over:** with 40 used, a request for 61 reverts with
   `WithdrawalLimitExceeded(token, 60)` and `used` stays 40.
3. **Single request above the limit:** a request for 101 reverts.
4. **Fee excluded:** a request for 100 with a fee of 5 is accepted and `used`
   becomes 100.
5. **Enclosing revert:** a request for 30 inside a call that later reverts
   leaves `used` unchanged.
6. **Ordering:** with 50 used, requests for 40 and then 20 in one block accept
   the first and reject the second.
7. **Window boundary:** requests for 100 at `t = 86399` and 100 at `t = 86400`
   are both accepted.
8. **Bounce-back and retry:** after 60 is accepted and delivery fails, the
   bounce-back is credited and a retry of 60 in the same window reverts.
9. **Deposit refund exemption:** with 100 used, a `ZoneInbox` bounce-back of a
   500 deposit is enqueued and `used` stays 100.
10. **Lower below usage:** with 60 used, lowering the limit to 40 makes a
    request for 1 revert until the next window.
11. **Raise:** with 100 used, raising the limit to 150 lets a request for 50
    succeed.
12. **Period change:** with 100 used in the window starting at 86,400, changing
    the period to 3,600 carries usage at `t = 88200` and resets it at
    `t = 90000`.
13. **Disabled:** with no limit, a request for 1,000 is accepted and usage is
    not written.
14. **Re-enable:** with 100 used on day 1, disabling and re-enabling the limit
    with 100 on day 2 lets a request for 100 succeed.
15. **Configuration delay:** a limit set in Tempo block `B` does not apply to
    Zone requests before the Zone imports `B`.
16. **Invalid configuration:** `(100, 0)`, `(0, 60)`, and a period above
    `MAX_WITHDRAWAL_LIMIT_PERIOD` revert with `InvalidWithdrawalLimit`, and a
    period of 604,800 is accepted.
17. **Token not enabled:** `setWithdrawalLimit` for a token that is not enabled
    reverts with `TokenNotEnabled`.
18. **Same-block configuration:** `enableToken` and `setWithdrawalLimit` in one
    Tempo block leave no Zone block in which the token is enabled without its
    limit.
