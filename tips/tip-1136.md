# TIP-1136: Private Programmable Authorization (Meta)

## Abstract

A configurable account can have an owner whose authority is defined by a committed private policy evaluated in a ZK program. An owner approval proves that the policy authorized an exact transaction or scoped access-key grant, without publishing the underlying signer roster, threshold, or authentication evidence. This meta TIP defines the architecture, security requirements, and offchain witness-storage responsibilities; component specifications must fix the verifier, wire format, gas, and consensus integration before activation.

## Motivation

[TIP-1130](https://tips.sh/1130) proves that an OIDC identity authorized an access key. The same separation between private authentication evidence and public execution can support private multisigs, mixed authentication factors, organizational permissions, recovery, and agent delegation.

For example, a configurable account could have one policy owner that internally requires Google authentication, an SMS-service attestation, and a passkey signature. Observers see the policy owner and approved action, but do not need to learn the Google subject, phone number, passkey public key, or which private authorization branch succeeded.

The private data behind a commitment must remain available. A hosted authentication service can store that data and coordinate proving, but its availability and privacy responsibilities must be explicit. Witness storage is an optional product outside consensus, not a network-selected custodian.

### Alternatives considered

- Separate onchain owners are simpler and remain appropriate when the owner structure need not be private.
- A specialized private-multisig circuit minimizes initial scope; a zkVM program offers reusable authorization logic. Both need the same binding and availability guarantees.
- An MPC signer changes key custody and coordination. This proposal instead verifies execution of an explicit committed policy.
- A contract wallet can prototype the relation, but does not by itself provide native configurable-account owner support.

## Assumptions

- Configurable accounts retain their existing configuration-version, owner-weight, and quorum semantics. This is a proposed extension, not support already provided by TIP-1114.
- The selected proof system is sound and zero knowledge for the chosen deployment. A soundness failure compromises accounts relying on that verifier.
- Policy commitments use domain separation, canonical encoding, and adequate random blinding. A plain hash of a small roster can be guessed.
- External credentials have authenticated trust roots and explicit freshness/revocation semantics. Proofs do not establish real-world facts without an authenticated source.
- Users retain or can recover the committed policy and its openings. Losing all copies can make authorization impossible.

# Specification

## Scope and component boundaries

This proposal introduces a policy-owner concept within configurable accounts. It does not allocate a signature byte, select a zkVM, inherit TIP-1131's gas estimate, or activate arbitrary verifiers. A subsequent consensus specification must assign these details and reconcile signature-size, owner-count, pool-admission, and combined grant-and-use limits.

TIP-1131 currently defines fixed schemes and verifying keys. Supporting user-selected program hashes requires a new scheme or owner-approval path; an existing OIDC proof cannot be repurposed as a general program proof.

## Owner descriptor and policy

Conceptually, a policy owner is identified by:

```text
PolicyOwner = (verifierScheme, programHash, policyCommitment)
policyCommitment = Commit("tempo:private-policy:v1", canonicalPolicy, randomSalt)
```

A domain-separated owner identifier commits to the complete descriptor. The descriptor is supplied with the approval and its derived identifier must match an owner in the current configurable-account configuration. The exact identifier encoding and owner-type dispatch are reserved for the component specification.

An audited shared program can interpret a private policy containing member identities, public keys, thresholds, roles, credential issuers, and allowed delegation rules. A unique program hash may reveal the program's purpose; sharing the interpreter and keeping policy data private reduces this fingerprinting. Zero knowledge does not automatically hide timing, transaction effects, proof lengths, or authentication-provider metadata exposed by the selected scheme.

Updating a policy or program changes the owner descriptor and requires a normal configuration update authorized by the current configuration. A storage service cannot update it unilaterally. Initial owner identifiers must be derived independently of the final account address to avoid circular address derivation; approvals subsequently bind to that address.

## Approval statement

The program approves the existing configurable-account operation digest, including its account and configuration version, under an additional domain separating this approval scheme. The full statement must bind:

- verifier scheme and owner descriptor;
- chain ID and account address;
- current configuration version;
- operation kind and exact operation digest;
- applicable operation nonce and validity interval;
- any authenticated external-state references used in authorization.

For a transaction, the operation digest covers the exact transaction signing payload. For an access-key grant, it covers the exact key identifier, privileges, limits, scopes, expiry, and replay-protection fields. If a context lacks a chain binding or one-time nonce, its component specification must add them; such a context is unsupported until then. Offchain message signing is outside the initial scope.

The chain reconstructs the statement from the actual operation and current configuration. It must not accept a prover-selected digest unrelated to the operation being executed.

## Proven relation

Private inputs include the policy, commitment opening, and fresh authorization evidence. Membership paths may replace disclosure of the full roster to individual proving participants.

The program MUST establish that:

1. The private policy opens the configured commitment.
2. Every counted approval is valid under a member and credential type allowed by that policy.
3. Repeated credentials, signatures, or membership paths cannot count the same member twice.
4. The threshold and any role or delegation constraints are satisfied.
5. The evidence authorizes the exact public operation or the exact scoped delegation being approved.
6. Required expiration and authenticated external-state checks hold.

Distinct members are distinct policy identities, not necessarily distinct humans. Requiring independent people or independent providers needs an explicit policy and supporting evidence.

The output is approval of the bound statement. Private data is not included in the public output. The outer verifier MUST check both the executed program hash and the complete output commitment, including when a recursive proof wrapper is used.

## Verification and execution

The native authorization path checks canonical encoding and resource limits, resolves the active verifier, validates the current configurable-account configuration, and matches the policy-owner descriptor. It then verifies the statement, validity interval, external-state bindings, and proof. One policy-owner approval contributes only that owner's configured weight; the remaining outer quorum rules still apply.

Execution consumes the existing operation's replay protection according to that context's rules. Failed execution, fee charging, and nonce consumption must retain that context's specified semantics; this meta TIP introduces no independent nonce-consumption rule.

A configuration update invalidates proofs against the previous version. External trust-root changes must be evaluated at the operation's position in block execution. An old state root alone is insufficient evidence of current credential validity; accepted roots need an explicit currentness rule enforced outside the witness.

## Google, SMS, and passkey example

For an all-three-required policy:

| Factor | Cryptographic authority | Private checks |
| --- | --- | --- |
| Google | OIDC provider key | Token signature, issuer, audience, subject membership, times, and nonce binding to a key that approves the operation. |
| SMS | SMS verification service key | Attestation that the committed phone identity completed a challenge bound to the authorization and its expiry. |
| Passkey | Authenticator-held private key | WebAuthn signature, challenge, RP ID, allowed origin, and required user-presence/user-verification flags. |

SMS transport does not produce a publicly verifiable signature. The verification service is a trusted attester. A ZK proof can hide the phone identity, but cannot remove that trust. Ordinary OIDC authentication is also not approval of an arbitrary transaction: the token's bound ephemeral key must sign the relevant authorization, following the separation in TIP-1130.

Provider signing keys may be authenticated through the publisher mechanism proposed in TIP-1132. The issuer and publisher retain the powers described there. The generalized relation must not accept arbitrary witness-supplied provider keys.

## Per-action approvals and delegated keys

A per-action proof authorizes one exact transaction. A delegation proof authorizes installation of an access key under the existing keychain rules; subsequent transactions use that key within permissions enforced by the protocol.

A private condition checked only at key creation does not constrain future payments. A hidden vendor allowlist or private cumulative budget requires fresh per-action proofs or a separately specified enforcement mechanism. An unrestricted session key must not be described as enforcing such a policy.

Version changes invalidate outstanding policy proofs, but do not automatically revoke already-installed access keys. Delegation expiry and revocation continue to follow the keychain rules. Any desired cascading revocation must be explicitly specified and authorized.

Stateful private spending counters are deferred from the initial design. A later extension must bind old and new state commitments and serialize their consumption so two proofs cannot reuse one remaining allowance.

## Witness storage and portability

Separate durable policy data from transient approval evidence:

```text
Durable policy data + fresh approvals -> witness -> proof
```

Durable data includes policy versions, signer identities/public keys, commitment salts, membership paths, and any required private state. Fresh evidence includes tokens, attestations, and operation-bound signatures. Signing private keys should remain with their authenticators; they are not required for a signature-verification witness.

An optional hosted service, such as a Tempo authentication service, can store encrypted durable data, coordinate authentication, and run a prover. It MUST NOT be a consensus-mandated provider. SDKs must support retrieving and verifying an export independently of that service.

A portable export must identify its format version, account, configuration version, verifier scheme, program hash, policy encoding version, policy data, and commitment openings. It must contain sufficient material to reconstruct the commitment without an undocumented server-held secret. Exports are sensitive and must be encrypted for transfer and backup. They must exclude authenticator private keys and should exclude expired transient evidence.

Restore tooling must recompute the owner descriptor and compare it with current chain configuration before use. Stale exports must not silently overwrite newer state. A policy update should prepare and test a durable backup before submitting the configuration update; the chain cannot prove that an offchain backup remains available.

Encryption at rest is not privacy from a cloud prover. Ordinary cloud proving requires plaintext witness access inside that prover. Client-side proving, independently generated proofs with an appropriate aggregation relation, or distributed proving can change that boundary, but are separate implementations requiring their own analysis.

Witness recovery must not depend exclusively on successfully proving with the missing witness. Independent backup keys, alternate devices, or a separately authorized recovery route are needed to avoid this circular dependency.

## Open decisions before implementation

- Exact owner identifier, canonical policy and statement encodings, and approval signature dispatch.
- Proof system, zkVM/version, public-input encoding, setup assumptions, verifier upgrades and deactivation.
- Proof and public-input size limits, maximum approvals, verification gas, and invalid-proof admission benchmarks.
- Integration with configuration updates, access-key grants, and combined grant-and-use transactions.
- External key-registry interfaces and freshness rules.
- Versioned encrypted witness-export format and interoperable restore fixtures.

These are activation blockers. This draft does not claim implementation readiness or existing network support.

# Tooling

Wallet SDKs need policy compilation, commitment creation, authorization display, witness assembly, proof generation, and local proof verification. Users must see the exact action or delegation being approved, including limits and expiry.

Storage tooling needs encrypted backup, export/import, independent restore validation, and retention controls. A hosted prover should expose job status and bounded diagnostic codes without logging witness contents. Existing TIP-1130 integrations are useful building blocks, but do not automatically support this owner type.

# Observability

Reuse configurable-account and keychain events for configuration changes and delegation lifecycle; do not publish hidden roster or policy contents. No additional consensus event is proposed by this meta TIP. The implementation component must specify any additional event fields it requires.

Nodes should expose aggregate proof-verification latency and rejection counters by verifier scheme and failure category. Hosted services should track storage availability, restore checks, and proving latency without putting tokens, phone numbers, identity subjects, salts, or approvals in logs.

# Threat Model

- **Policy author:** can introduce an unintended approval path. Audits must cover both interpreter and policy; a proof of execution does not prove a policy is sensible.
- **Witness store:** can reveal, withhold, or lose policy data. Possession of policy data alone must not satisfy a fresh-approval requirement. Offline copies and independent recovery address availability.
- **Prover:** sees supplied witness data unless the proving design prevents it. It can withhold proofs but cannot forge missing evidence under sound verification.
- **Authentication providers and publishers:** can forge or revoke their factor's credentials within their trust scope. A threshold across factors controlled by one operator does not establish independence.
- **Frontend:** can misrepresent an action or obtain login tokens bound to its own keys. ZK does not replace trusted transaction display and consent.
- **Proof system:** soundness or verifier failure can bypass the policy. Activation requires independent review, explicit setup assumptions, and a failure-response design.
- **Network adversary:** can replay, reorder, or submit invalid proofs. Exact digest binding, current configuration checks, replay protection, and bounded verification are required.

Public transactions, account activity, authentication timing, and session keys remain observable. This proposal hides authorization evidence from chain observers; it does not provide transaction privacy or universal privacy from service operators.

# Invariants

- An approval matches exactly one current owner descriptor and the exact operation statement.
- The same private member cannot contribute more than its permitted weight.
- A valid proof cannot authorize a changed account, chain, operation, scope, expiry, or configuration version.
- A witness-supplied trust root cannot create authority absent from the configured policy and authenticated registry state.
- Stored witness data without required fresh evidence does not authorize an action.
- Policy changes require the current account quorum; hosted storage has no unilateral update right.
- Access-key execution remains bounded by actually enforced permissions.
- Export/import reconstructs the same commitment and detects stale or tampered data.

Required fixtures include valid mixed-factor approvals; duplicate-member attempts; wrong issuer/audience/origin; expired and revoked credentials; proof replay and cross-chain replay; altered grants; configuration rotation; malformed and oversized proofs; combined grant-and-use; and recovery after loss of the primary storage service. Before review completion, demonstrate a private multisig and a Google/SMS/passkey policy, measure proving and verification costs, and restore the witness data using an independent implementation.
