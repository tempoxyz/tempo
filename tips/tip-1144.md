# TIP-1144: Add ZoneOutbox to the Implicit Approval List

## Abstract

This TIP amends [TIP-1035](tip-1035.md) by adding the Zone outbox precompile (`0x1c00000000000000000000000000000000000002`) to the Implicit Approval List from T13. With this TIP activation, the Zone outbox MUST pull the withdrawing caller's funds with `system_transfer_from` instead of allowance-based `transferFrom`, so AccountKeychain spending limits apply to Zone withdrawals.

## Motivation

`ZoneOutbox.requestWithdrawal` currently pulls `amount` (plus the fee when the caller pays it) from `msg.sender` via `transferFrom`, consuming the caller's allowance to the outbox. Allowance-based `transferFrom` does not meter AccountKeychain spending limits, because TIP-20 charges an access key's limit when it creates an allowance, not when the allowance is spent.

Users normally approve the outbox from their root key, and wallets typically approve `type(uint256).max`. An access key on that account can then withdraw more than its spending limit, to any Tempo recipient, because the root-key allowance was never charged against the key. This was reported against the Zones import into this repository ([tempoxyz/tempo#8171](https://github.com/tempoxyz/tempo/pull/8171#discussion_r4212214791)).

Tempo's own precompiles that pull from `msg.sender` (TipFeeManager, StablecoinDEX, TIP20ChannelReserve) avoid this by using `system_transfer_from`, which skips the allowance and meters spending limits. The outbox cannot do the same today: from T5, `system_transfer_from` reverts with `Unauthorized` for callers not on the Implicit Approval List.

Alternatives considered:

- **Debit the caller with `transfer(msg.sender, …)` from inside the outbox.** Equivalent checks without a list change, but it moves funds on the user's behalf outside the audited TIP-1035 surface and is invisible to `isImplicitlyApproved`.
- **Charge the spending limit explicitly, then `transferFrom`.** Double-charges access keys that created the outbox allowance themselves, breaking normal access-key withdrawals.

## Assumptions

1. The Zone outbox is a precompile in the Zone node implementation, built on `tempo-precompiles`; its `system_transfer_from` calls are Rust calls, not EVM calls (TIP-1035 assumption 1).
2. No precompile is deployed at `0x1c00000000000000000000000000000000000002` on Tempo L1. Listing the address has no effect on L1 execution beyond `AddressRegistry.isImplicitlyApproved` returning `true` for it.
3. Zone chains follow Tempo hardfork activation, so the outbox switch and the list change activate together at T13.

# Specification

## List amendment

From T13, the Implicit Approval List is the TIP-1035 initial list plus:

| Address | Contract | Rationale |
|---------|----------|-----------|
| `0x1c00000000000000000000000000000000000002` | ZoneOutbox (Tempo Zones) | Withdrawals pull from `msg.sender` only; listing meters access-key spending limits and removes the redundant outbox approval |

Before T13 the list is unchanged, and `system_transfer_from` from the outbox address MUST revert with `Unauthorized`.

## ZoneOutbox withdrawals

From T13, `requestWithdrawal` MUST:

1. Pull the caller's share from `msg.sender` with `system_transfer_from(msg.sender, outbox, share)`, where `share` is `amount + fee` when `msg.sender` is the transaction fee payer and `amount` otherwise.
2. Continue to pull a distinct fee payer's fee with allowance-based `transferFrom`. The fee payer is not `msg.sender`, so the caller-only-pulls guideline does not cover it.

Before T13, withdrawals behave as before: both legs use `transferFrom`.

`approve`, `permit`, `allowance`, and `transferFrom` semantics are unchanged (TIP-1035 invariant 3). An existing allowance to the outbox is no longer consumed by the caller's leg and remains usable for the fee-payer leg.

## Eligibility

TIP-1035 guideline 1 (caller-only pulls) holds: the only `system_transfer_from` call in the outbox uses `from == msg.sender` of the current `requestWithdrawal` call. `enqueueDepositBounceBack` and `finalizeWithdrawalBatch` do not pull user funds.

# Tooling

Zone clients no longer need to `approve` the outbox before `requestWithdrawal` from T13. Clients that approve with an access key and then withdraw are charged against the key's limit twice (once at `approve`, once at withdrawal) and SHOULD drop the approve step. Integrators can branch on `AddressRegistry.isImplicitlyApproved(0x1c00…0002)`.

# Observability

N/A. `system_transfer_from` emits the standard TIP-20 `Transfer` event, and the outbox's `WithdrawalRequested` event is unchanged.

# Threat Model

- **Access-key holder**: may be compromised or exceed its delegation; MUST be bounded by its spending limit on Zone withdrawals.
- **Root key**: trusted; its allowance to the outbox MUST NOT extend any access key's spending power.
- **Fee payer**: consents to paying the fee via its own outbox allowance; out of scope for the caller-only-pulls guideline.

# Invariants

1. From T13, `isImplicitlyApproved(ZONE_OUTBOX_ADDRESS)` is `true`; before T13 it is `false`. The TIP-1035 initial list is unchanged at every hardfork.
2. From T13, a withdrawal signed by an access key reverts with `SpendingLimitExceeded` if the caller's share exceeds the key's remaining limit, regardless of the caller's allowance to the outbox.
3. From T13, a withdrawal succeeds with zero allowance to the outbox when the caller pays its own fee.
4. Pre-T13 withdrawals consume the caller's outbox allowance exactly as before.

Test coverage MUST include the T12/T13 list boundary, `system_transfer_from` from the outbox address before and after T13, spending-limit enforcement on that path, and the Zone outbox behavior on both sides of T13.
