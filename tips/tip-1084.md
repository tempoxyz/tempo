# TIP-1084: Vault-Backed TIP-20 Tokens

## Abstract

This TIP introduces a vault-backed TIP-20 subtype whose address is both a transferable native
share token and the canonical user-facing vault entrypoint. Each vault token is immutable to
one TIP-20 base asset and one vault contract.

The protocol owns the narrow token and settlement envelope: balances, allowances, transfer policy,
asset pulls, share mints and burns, bounded user entrypoints, atomic vault callbacks, and
standard events. The vault owns the economic model: valuation, fees, limits, asynchronous
claims, engine selection, venue integration, and migration. A current engine, rather than the
native token or vault, holds the venue shares.

This division gives wallets and integrations one persistent native TIP-20 address while keeping
yield products and venues outside consensus. The protocol does not assert that a registered vault
is solvent; its immutable vault remains a trusted accounting and custody authority.

## Motivation

Tempo vault shares should behave like first-class TIP-20 balances. They should be transferable,
policy-aware, indexable, usable by accounts and wallets, and eligible for the same composability as
other native tokens. Users should not need to understand whether backing currently sits in an
ERC-4626 vault, a managed meta-vault, an asynchronous RWA venue, or a future engine.

Neither a narrow ERC-4626 wrapper nor a fully enshrined yield product provides the right boundary:

- An ERC-4626 wrapper binds the native surface to one venue interface and makes the native token an
  aggregated depositor into that venue.
- Enshrining fee economics, strategy routing, reward policy, or manager execution would make
  product iteration depend on protocol upgrades.
- A normal TIP-20 plus a separate application vault preserves contract flexibility but leaves two
  user-facing addresses and cannot enforce an immutable vault relationship at the protocol
  boundary.

The vault token therefore acts as a stable shell around one contract vault. The shell
standardizes the common synchronous flow and native token semantics. The vault can replace
engines and evolve product logic without changing the user-held token or the standard integration
address.

Payment-lane eligibility is deliberately separate from vault-token registration. A native selector
that calls arbitrary vault and engine code is still general-purpose execution. This TIP makes
a later bounded payment profile possible but does not classify vault operations as payment calls.

## Assumptions

- The vault-token address is also the TIP-20 share address.
- Each vault token has one immutable TIP-20 base asset.
- Each vault token has one immutable vault contract.
- The vault may be a proxy or may internally migrate engines, but the vault address bound
  by the protocol never changes.
- The vault is trusted for valuation, solvency, fee accounting, limits, and engine selection.
- A malicious vault can misprice deposits, block exits, or use its vault-only issuance
  authority to dilute holders. Vault-token registration does not certify the vault.
- One current engine serves one vault, exposes the same base asset, and holds the venue shares.
- The vault token is non-rebasing. Yield and loss change assets redeemable per share rather than holder
  balances.
- Ordinary share transfers do not call the vault or engine.
- The protocol can make atomic EVM calls from the vault token into its vault with correct gas,
  revert, log, and journal semantics.
- A vault callback receives the original caller explicitly and authenticates the vault token
  through `msg.sender`.

## Threat Model

- **Vault token:** trusted protocol code for TIP-20 state, policy enforcement, share allowance
  handling, base-asset pulls, vault binding, callback ordering, atomicity, and event emission.
- **Vault:** trusted contract for all economic accounting. It can move backing through its
  engine and has narrowly exposed vault-only share issuance. A malicious vault can make
  the vault insolvent or dilute holders.
- **Engine:** trusted venue integration serving one vault. It holds venue shares and reports
  their value. A malicious engine or valuation source can misprice entry, exit, or fees.
- **TIP-20 administrator:** trusted for ordinary metadata, policy, and token-wide emergency roles.
  It cannot replace the vault or authorize another issuer.
- **Vault operator:** trusted according to the vault implementation. It may configure
  prospective fees, limits, emergency roles, and any vault-enabled engine migration.
- **Users and approved spenders:** may deposit, transfer, withdraw, redeem, and use advertised
  extensions subject to balances, allowances, policies, limits, capabilities, and caller bounds.
- **Payment builders:** must treat vault token calls as general transactions unless a later TIP
  defines a bounded payment-safe profile.

# Specification

## Architecture and Scope

```text
user or integration
  -> vault token / TIP-20 shares
  -> immutable vault
  -> current yield engine
  -> underlying venue

vault <-> optional fee and claim modules
```

The protocol enshrines:

- creation of a vault token TIP-20 subtype;
- one immutable base asset and vault binding;
- ordinary TIP-20 balances, allowances, permits, memos, metadata, and transfer policies;
- standard synchronous deposit, exact-withdraw, and redeem entrypoints;
- protocol-mediated base-asset pulling from the caller;
- share allowance spending, minting, and burning;
- atomic vault calls with a per-vault reentrancy lock;
- vault-only share mint and self-burn functions for nonstandard supply transitions; and
- standard vault token discovery and events.

The protocol does not enshrine:

- exchange-rate or NAV calculation;
- fee economics or recipients;
- deposit capacity or risk policy;
- asynchronous claim accounting;
- contribution or reward policy;
- engine selection, venue integration, or migration;
- swaps or multi-asset routing;
- generic manager execution; or
- payment-lane eligibility for vault-backed calls.

## Factory Interface

The TIP-20 factory is extended with a vault token creation path.

```solidity
interface ITIP20VaultFactory {
    event VaultTokenCreated(
        address indexed vaultToken,
        address indexed asset,
        address indexed vault,
        uint64 transferPolicyId,
        string name,
        string symbol,
        string currency,
        address quoteToken,
        address admin,
        bytes32 salt
    );

    function createVaultToken(
        string calldata name,
        string calldata symbol,
        string calldata currency,
        address quoteToken,
        address admin,
        uint64 transferPolicyId,
        address asset,
        address vault,
        bytes32 salt
    ) external returns (address vaultToken);

    function isVaultToken(address token) external view returns (bool);

    function getVaultTokenAddress(address sender, bytes32 salt)
        external
        pure
        returns (address vaultToken);
}
```

`createVaultToken` MUST:

1. Validate `asset` is an initialized TIP-20 token.
2. Validate `vault` is nonzero contract code.
3. Validate `admin` is nonzero.
4. Validate `transferPolicyId` under ordinary TIP-403 rules.
5. Derive and create the vault token at the deterministic factory address.
6. Validate `ITIP20VaultLogic(vault).vaultToken() == vaultToken`.
7. Validate `ITIP20VaultLogic(vault).asset() == asset`.
8. Store immutable `asset` and `vault` bindings.
9. Initialize ordinary TIP-20 metadata, policy, and administrator state.
10. Disable ordinary TIP-20 issuer-role administration for the vault token subtype.
11. Emit ordinary `TokenCreated` and then `VaultTokenCreated`.

The vault may be deployed before token creation using `getVaultTokenAddress` as its immutable
vault-token address. The complete deployment SHOULD create and bind vault modules and the
initial engine in one atomic transaction or validate every reciprocal binding before accepting
funds.

## Vault Token Interface

The base native interface is single-asset and synchronous.

```solidity
interface ITIP20VaultToken {
    function asset() external view returns (address);
    function vault() external view returns (address);

    function totalAssets() external view returns (uint256 assets);
    function convertToShares(uint256 assets) external view returns (uint256 shares);
    function convertToAssets(uint256 shares) external view returns (uint256 assets);
    function maxDeposit(address receiver) external view returns (uint256 assets);
    function maxWithdraw(address owner) external view returns (uint256 assets);
    function maxRedeem(address owner) external view returns (uint256 shares);
    function previewDeposit(uint256 assets) external view returns (uint256 shares);
    function previewWithdraw(uint256 assets) external view returns (uint256 shares);
    function previewRedeem(uint256 shares) external view returns (uint256 assets);

    function deposit(uint256 assets, address receiver, uint256 minShares)
        external
        returns (uint256 shares);

    function withdraw(uint256 assets, address receiver, address owner, uint256 maxShares)
        external
        returns (uint256 shares);

    function redeem(uint256 shares, address receiver, address owner, uint256 minAssets)
        external
        returns (uint256 assets);

    function vaultMint(address receiver, uint256 shares, bytes32 reason) external;
    function vaultBurn(uint256 shares, bytes32 reason) external;
}
```

The view functions forward to the immutable vault and propagate its return or revert data.
The protocol does not cache exchange rates or NAV. `maxDeposit`, `maxWithdraw`, and `maxRedeem`
therefore reflect vault policy and current engine conditions.

The standard user methods include explicit slippage bounds. Exact-share minting is not part of the
base interface; a later extension may add it if product demand justifies another consensus selector.

## Vault Interface

The immutable vault MUST implement:

```solidity
interface ITIP20VaultLogic {
    function vaultToken() external view returns (address);
    function asset() external view returns (address);

    function totalAssets() external view returns (uint256 assets);
    function convertToShares(uint256 assets) external view returns (uint256 shares);
    function convertToAssets(uint256 shares) external view returns (uint256 assets);
    function maxDeposit(address caller, address receiver) external view returns (uint256 assets);
    function maxWithdraw(address caller, address owner) external view returns (uint256 assets);
    function maxRedeem(address caller, address owner) external view returns (uint256 shares);
    function previewDeposit(uint256 assets) external view returns (uint256 shares);
    function previewWithdraw(uint256 assets) external view returns (uint256 shares);
    function previewRedeem(uint256 shares) external view returns (uint256 assets);

    function onDeposit(
        address caller,
        uint256 assets,
        address receiver,
        uint256 minShares
    ) external returns (uint256 shares);

    function onWithdraw(
        address caller,
        uint256 assets,
        address receiver,
        address owner,
        uint256 maxShares
    ) external returns (uint256 shares);

    function onRedeem(
        address caller,
        uint256 shares,
        address receiver,
        address owner,
        uint256 minAssets
    ) external returns (uint256 assets);
}
```

All `on*` functions MUST reject unless `msg.sender == vaultToken()`. The vault MUST treat the
explicit `caller` as the original vault-token caller. It MUST NOT derive user identity from
`tx.origin`.

The vault may expose additional direct methods for configuration, contributions, in-kind
entry, asynchronous claims, engine migration, and operations. Those methods are outside the native
base interface and are general EVM calls.

## Deposit Flow

`deposit(assets, receiver, minShares)` MUST:

1. Reject zero `assets`, zero `receiver`, or zero `minShares`.
2. Reject reentrant entry for this vault token.
3. Check that minting shares to `receiver` satisfies the current TIP-403 policy and TIP-1028
   receive policy.
4. Transfer exactly `assets` of the immutable base asset from `msg.sender` to `vault`.
5. Call `vault.onDeposit(msg.sender, assets, receiver, minShares)`.
6. Require returned `shares` to be nonzero and at least `minShares`.
7. Mint exactly `shares` to `receiver`.
8. Emit ordinary TIP-20 mint events followed by `Deposit`.
9. Clear the per-vault reentrancy lock.

The base-asset transfer and vault callback are one atomic EVM operation. If the callback or
share mint fails, the base-asset transfer MUST revert.

The protocol MAY use TIP-1035 `system_transfer_from` for step 4 only when:

- `from == msg.sender`;
- the token is the vault's immutable `asset`;
- `to == vault`; and
- the active hardfork recognizes vault tokens as an implicitly approved precompile class.

Every ordinary balance, spending-limit, and TIP-403 check on the base asset still applies.

```solidity
event Deposit(
    address indexed caller,
    address indexed receiver,
    uint256 assets,
    uint256 shares
);
```

## Withdraw and Redeem Flows

`withdraw` and `redeem` MUST:

1. Reject zero input amounts or a zero receiver or owner.
2. Reject reentrant entry for this vault token.
3. Validate the owner's share balance and burn authorization.
4. Spend ordinary share allowance when `msg.sender != owner`.
5. Lock the owner's relevant balance against transfer or another vault action for the remainder of
   the operation without changing total supply.
6. Call the corresponding vault callback.
7. Enforce `maxShares` or `minAssets` against the vault result.
8. Burn the final share amount from `owner`.
9. Emit ordinary TIP-20 burn events followed by `Withdraw`.
10. Clear the balance and reentrancy locks.

The vault transfers the base asset to `receiver` during its callback, normally through the
current engine. A failure after asset delivery, including a failed burn or policy check, MUST revert
the complete callback and asset transfer.

The owner balance remains locked and total supply remains unchanged during the vault callback.
This lets the vault checkpoint fees and value the pre-exit pool without exposing the owner to
reentrant transfer or double redemption.

```solidity
event Withdraw(
    address indexed caller,
    address indexed receiver,
    address indexed owner,
    uint256 assets,
    uint256 shares
);
```

## Vault-Only Supply Changes

Some contract-level operations legitimately change supply outside the standard synchronous user
flow. Examples include fee-share crystallization, cancellation of a burn-at-request asynchronous
claim, and in-kind entry of existing venue shares.

`vaultMint` MUST:

1. Reject unless `msg.sender == vault`.
2. Reject zero `receiver` or zero `shares`.
3. Apply ordinary shares mint and receive-policy checks to `receiver`.
4. Mint the requested shares and emit ordinary TIP-20 mint events plus `VaultMint`.

`vaultBurn` MUST:

1. Reject unless `msg.sender == vault`.
2. Burn only the vault's own shares balance.
3. Apply ordinary TIP-20 burn checks.
4. Emit ordinary TIP-20 burn events plus `VaultBurn`.

```solidity
event VaultMint(address indexed receiver, uint256 shares, bytes32 indexed reason);
event VaultBurn(uint256 shares, bytes32 indexed reason);
```

The `reason` value is for domain-specific observability and does not authorize or validate the
economic transition. Because the vault is already trusted for accounting and solvency, these
functions do not attempt to prove backing. The immutable vault binding prevents the TIP-20
administrator from adding a second issuer.

Vault-only mint and burn MAY execute during a vault callback. Other reentrant share
transfers and vault operations MUST remain blocked. Vault implementations must checkpoint fees
and perform supply-dependent calculations in an order that accounts for any vault mint.

## Vault Token Behavior

A vault token supports ordinary TIP-20 metadata, balances, transfers, approvals, permits,
memos, `quoteToken`, `currency`, logo URI, transfer policy, receive policy, and factory discovery.

Ordinary TIP-20 issuer-role administration and ordinary external `mint`, `mintWithMemo`, `burn`,
`burnWithMemo`, and `burnBlocked` paths MUST NOT create an alternative supply authority. Supply can
change only through:

- a successful native deposit, withdraw, or redeem;
- immutable-vault `vaultMint` or `vaultBurn`; or
- a future hardfork-defined vault token extension.

Ordinary transfers do not call the vault, do not change total supply, and transfer the same
pro-rata claim represented by the balance.

Vault deposit controls are vault state and are distinct from token-wide TIP-20 transfer pause
state. A vault deposit pause MUST NOT by itself block transfers or exits.

## Optional Asynchronous Extension

Asynchronous redemption is not part of the base interface. A vault may advertise a native
async extension with:

```solidity
interface ITIP20VaultTokenAsync {
    function requestRedeem(uint256 shares, address receiver, bytes calldata requestData)
        external
        returns (bytes32 requestId);

    function cancelRedeem(bytes32 requestId, uint256 minReceiverShares)
        external
        returns (uint256 receiverShares);
}
```

A request follows the same owner-balance lock and atomic callback rules as immediate redemption,
then burns shares at request time. The vault records a separate pending claim with one stored
receiver. Open claims are not part of active share supply or active NAV.

Finalization pays the stored receiver without another burn. Cancellation returns backing to the
active pool and mints a vault-calculated current-value re-entry to the same receiver through
`vaultMint`. Async methods and dynamic request data are general calls and MUST NOT be
payment-lane eligible under this TIP.

## Vault, Engine, and Venue Model

The recommended vault architecture uses one current engine:

```solidity
interface IVaultEngine {
    function supportsInterface(bytes4 interfaceId) external view returns (bool);
    function asset() external view returns (address);
    function vault() external view returns (address);
    function shareScale() external view returns (uint256 scale);
    function deposit(uint256 assets) external returns (uint256 engineShares);
    function totalShares() external view returns (uint256 engineShares);
    function totalAssets() external view returns (uint256 assets);
    function valueOf(uint256 engineShares) external view returns (uint256 assets);
}

interface IVaultEngineRedeem {
    function previewRedeem(uint256 engineShares) external view returns (uint256 assets);
    function redeem(uint256 engineShares, address receiver, uint256 minAssets)
        external
        returns (uint256 assets);
}

interface IVaultEngineExactWithdraw {
    function previewWithdraw(uint256 assets) external view returns (uint256 engineShares);
    function withdraw(uint256 assets, address receiver) external returns (uint256 engineShares);
}

interface IVaultEngineAsyncRedeem {
    function requestRedeem(uint256 engineShares, bytes calldata requestData)
        external
        returns (bytes32 requestId);
    function cancelRedeem(bytes32 requestId) external returns (uint256 engineShares);
}
```

These engine interfaces are recommended contract architecture rather than enshrined protocol ABIs.
A vault may implement another internal architecture while preserving the vault token
interface and its documented trust model.

For the recommended architecture:

- one engine serves one vault and exposes the same immutable base asset;
- the engine, not the vault or native token, holds venue shares;
- every installed engine exposes at least one usable exit capability;
- immediate exits derive asset delivery and venue-share consumption from measured balance deltas;
- active vault-token supply is backed only by active engine shares at the vault's current
  conversion anchor; and
- open asynchronous claims are separate from active supply and NAV.

## Fees, Contributions, and Migration

Fee economics are vault policy. A vault may checkpoint high-water-mark or other fees and
mint fully backed fee shares through `vaultMint`. The protocol does not define fee rates,
recipients, target returns, snapshots, or claims.

Contributions add backing without minting shares to the funder. They are direct vault methods
and do not require a native selector.

Whole-pool engine migration is vault policy. A vault may atomically move the active
position between same-asset engines while preserving vault-token supply and balances. The
protocol observes no supply change and does not select or validate the replacement engine.

Reward eligibility and distribution remain outside the vault token. Vaults and separate
reward contracts may use existing shares balances as eligibility without receiving additional
protocol roles.

## Policy Integration

The vault token's native transfer policy applies to share minting, holding, transfers, and burns under
ordinary TIP-20 and TIP-403 rules. The base asset independently enforces its own transfer policy
during deposit and withdrawal.

Vault-level policy may further restrict deposits or exits, but it cannot bypass vault-token
or base-asset policy. Customer-specific routes, conversions, and private Zone behavior
belong in separate scoped routers rather than the vault token or the vault.

## Payment Lane

This TIP does not add vault token selectors to the TIP-1045 payment call allow-list.

Although the target is a native TIP-20, deposit and exit callbacks may execute arbitrary vault,
engine, oracle, and venue code. Classifying those calls as payments without another execution bound
would allow general-purpose work to consume payment-lane capacity.

A future TIP may define a payment-safe vault profile. It must specify at least:

- the eligible native selectors and exact calldata constraints;
- a hard callback gas or execution bound;
- whether vault or engine implementations require protocol approval;
- immediate-settlement and liquidity requirements;
- allowed external call targets or another bounded execution model; and
- behavior when a vault ceases to satisfy the profile.

Vault token registration alone MUST NOT imply payment-lane eligibility.

## Non-Goals

This TIP does not:

- certify vault solvency or economic correctness;
- enshrine ERC-4626, ERC-7575, or a particular venue;
- support caller-selected deposit or withdrawal assets;
- enshrine multi-asset pricing or swap routing;
- define fixed-yield, reward, fee, or campaign modes;
- expose generic manager execution from the native token;
- make vault or engine calls payment-lane eligible;
- require synchronous-only venues; or
- define migration between different vault tokens.

# Tooling

SDKs SHOULD treat the vault token address as both the TIP-20 share address and the standard
vault action target. A deployment record SHOULD separately expose the immutable vault, current
engine, base asset, optional fee module, and advertised extensions.

Wallets and integrators SHOULD:

- use vault token discovery rather than infer vault type from selectors;
- quote through the native view methods immediately before execution;
- always supply explicit share or asset bounds;
- inspect vault and engine trust metadata independently of native registration;
- treat optional async and in-kind methods as capability-gated general calls; and
- not assume payment-lane eligibility.

Deployment tooling MUST validate the reciprocal vault-token/vault binding, base asset, zero initial
supply, transfer policy, vault code, engine binding, and every published capability before
accepting funds.

# Observability

Implementations MUST emit:

- ordinary `TokenCreated` and `VaultTokenCreated` factory events;
- ordinary TIP-20 `Transfer`, `Approval`, mint, burn, memo, policy, metadata, and pause events;
- native `Deposit` and `Withdraw` events for synchronous vault actions;
- `VaultMint` and `VaultBurn` for nonstandard vault supply changes; and
- vault-level events for fees, limits, contributions, async claims, engines, migration, and
  emergency configuration.

Indexers MUST identify a vault token through factory or registry state rather than the
presence of a particular selector alone.

# Invariants

- A vault token is an initialized TIP-20 token.
- Its base asset and vault are immutable.
- Its base asset is an initialized TIP-20 token.
- Its vault reciprocally reports the same vault token and base asset.
- The TIP-20 administrator cannot replace the vault or add another issuer.
- `totalSupply()` equals the sum of holder balances after every successful external call.
- Ordinary transfers do not call the vault and do not change total supply.
- Deposit pulls only the caller's immutable base asset and mints only after a successful vault
  callback.
- Withdraw and redeem lock the owner's balance against reentrancy and burn only after a successful
  vault callback.
- A failed asset transfer, vault callback, bound check, policy check, mint, or burn reverts the
  complete vault token operation.
- The vault is the only caller of `vaultMint` and `vaultBurn`.
- `vaultBurn` cannot burn shares directly from an arbitrary holder.
- Native registration does not imply vault solvency or payment-lane eligibility.
- Optional asynchronous claims burn shares at request time and are excluded from active supply.
- For the recommended vault architecture, the engine rather than the native token or
  vault holds venue shares.
