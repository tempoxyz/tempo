# TIP-1170: Block-Indexed Expiring Nonce Ring Positions

## Abstract

Every expiring nonce transaction ([TIP-1009](./tip-1009.md)) reads and writes one global slot, `expiringNonceRingPtr`, so any two expiring nonce transactions in a block conflict under optimistic parallel execution. This TIP defines each transaction's ring position as the pointer at block start plus the transaction's index among the block's expiring nonce transactions, and writes the pointer once, after the block's last transaction. For every valid block the post-state is identical to TIP-1009's; the change is that no transaction writes the pointer. It does not remove other shared slots a transaction may touch, such as fee accumulators.

## Motivation

TIP-1009 step 7 advances `expiringNonceRingPtr` inside each transaction. A transaction's ring position therefore depends on every earlier expiring nonce transaction in the block, and all of them write the same slot. An optimistic parallel executor must re-execute each expiring nonce transaction that read the pointer before an earlier one committed.

Measured on an experimental optimistic parallel executor (evm2), with 4,096 expiring nonce pathUSD transfers from distinct senders on an idle bare-metal 6-core/12-thread AMD EPYC 4245P (median of 20 iterations after 2 warm-up runs, two runs; every parallel result checked equal to sequential receipts and state):

| Configuration | Block time | vs. sequential |
|---|---|---|
| Sequential | 16.5 ms (~248k tx/s) | — |
| Parallel, pointer written per transaction (TIP-1009 as specified) | 2–4x slower, ~3,000 re-executions of 4,096 transactions | slower |
| Parallel (5 threads, batched commit), ring insert deferred to commit, fee counters written blind | 7.45 ms (~550k tx/s) | -55% |

The deferral in the last row reorders the TIP-1009 state transition inside one client. Each client that wants parallel execution has to reimplement it, and tracers and block access lists still record a pointer write per transaction. Tempo's node already positions transactions this way when prewarming: the payload validator and payload builder pass each transaction its index among the block's expiring nonce transactions (`expiring_nonce_idx`), and the handler temporarily sets the pointer to `ptr + index` before calling `check_and_mark_expiring_nonce` (`crates/evm/src/handler.rs`, `crates/evm/src/engine.rs`, `crates/payload/builder/src/prewarming.rs`). Action replay recomputes the ring insert per transaction for the same reason (`crates/evm/src/action_replay.rs`). This TIP makes that positioning the protocol rule.

### Alternatives considered

**(a) Block-indexed positions, pointer advanced once per block (this TIP).** A transaction's position is `(ptrStart + i) mod CAPACITY`, where `i` is its index among the block's expiring nonce transactions, which the block body fixes. The pointer is written once after the last transaction. Storage layout, gas, errors and post-state are unchanged. The cost is one post-execution state change per block.

**(b) Per-block or time-bucketed rings.**
- *Bucket by `validBefore` second* (for example `mapping(uint64 => mapping(uint32 => bytes32))` keyed by `validBefore mod (MAX_EXPIRY_SECS + 1)`). Each bucket needs a fill counter, and most transactions in a block share one or two `validBefore` values (wallets set `now + window`), so the counter conflict remains. Reusing the block index as the in-bucket index collides across blocks that use the same second. A bucket expires all at once, but EVM storage cannot drop a mapping: clearing it takes one SSTORE per entry, done either by transactions (which needs a shared cursor, reintroducing the conflict) or by a block-end sweep whose cost is unbounded and varies per block.
- *Bucket by block number* (`ring[blockNumber mod W][i]`). Entries expire by timestamp, not block number, and block spacing varies, so no fixed `W` bounds how long an entry stays live. The eviction check would still be needed. Blocks with fewer expiring nonce transactions than the bucket's previous occupant leave stale entries that something must clear.

Rejected: both change the storage layout and need a migration, and neither removes the conflict without a variable-cost sweep.

**(c) Keyed seen-set with lazy expiry, no ring.** Keep only `expiringNonceSeen[hash] = validBefore` and never evict. This has no conflicts, but every transaction leaves a dead slot permanently: about 107 bytes per transaction ([TIP-1009 benchmark](./tip-1009.md#controlled-benchmark-100k-transactions-at-5k-tps)), or 43 GB/day at 5,000 TPS and 86 GB/day at 10,000 TPS. Under [TIP-1016](./tip-1016.md) that growth would have to pay SSTORE-set state gas instead of the ephemeral `WARM_SSTORE_RESET` exemption, raising the price of every expiring nonce transaction. Lazy cleanup, such as letting a transaction delete expired hashes it names, makes gas depend on the hints a transaction carries and creates conflicts between transactions that name the same hash. Rejected.

## Assumptions

- **A1. The pointer is not observable inside a block.** The Nonce precompile exposes no getter for `expiringNonceRingPtr` (`INonce` has only `getNonce`), and contracts cannot read another account's storage. If a future precompile or opcode exposed it mid-block, the reader would see the block-start value under this TIP instead of a per-transaction value.
- **A2. Every included expiring nonce transaction inserts exactly one ring entry.** TIP-1009's checks run during nonce validation, before execution. Failing them makes the transaction invalid, which makes any block containing it invalid. An included expiring nonce transaction therefore always inserts, whether its calls succeed or revert. If a later change let an included expiring nonce transaction skip insertion, the index rule would leave gaps and stop matching TIP-1009's post-state.
- **A3. A block holds at most `CAPACITY` expiring nonce transactions.** With `CAPACITY = 3,000,000` ([TIP-1093](./tip-1093.md)) and at least 13,000 gas of replay protection per transaction, exceeding it would take more than 39 billion gas. If it were violated, positions would wrap within the block and the later transaction would hit `ExpiringNonceSetFull` against the same block's entry, exactly as under TIP-1009.
- **A4. `ptrStart < CAPACITY`.** TIP-1093 keeps the pointer in `[0, CAPACITY)`. A future fork that shrinks `CAPACITY` must define how the pointer migrates.

# Specification

## Overview

Terms:

- **Expiring nonce transaction**: a Tempo transaction (type `0x76`) with `nonceKey == uint256.max`, in a block at or after T1. System transactions and other transaction types are never expiring nonce transactions.
- **`ptrStart`**: the value of `expiringNonceRingPtr` (Nonce precompile slot 3) in the parent block's post-state.
- **`i`**: a transaction's expiring nonce index, the number of expiring nonce transactions before it in the block body. The first one has `i = 0`.
- **`n`**: the number of expiring nonce transactions in the block.
- **`CAPACITY`**, **`MAX_EXPIRY_SECS`**: the active fork's values (3,000,000 and 300 from T11, per TIP-1093).

Body order alone determines `i`, so a block's proposer fixes every transaction's ring position when it orders the body, and validators recompute them. Nobody signs or chooses an index.

## Mechanics

### Per-transaction check and insert

For an expiring nonce transaction with replay hash `H` (as defined by TIP-1009 and [TIP-1106](./tip-1106.md)), `validBefore` and index `i`, at block timestamp `now`:

1. **Expiry window.** Reject with `InvalidExpiringNonceExpiry` unless `now < validBefore <= now + MAX_EXPIRY_SECS`.
2. **Replay check.** Let `e = expiringNonceSeen[H]`. Reject with `ExpiringNonceReplay` if `e != 0 && e > now`.
3. **Position.** `P = (ptrStart + i) mod CAPACITY`. Implementations take `ptrStart` from the parent state. They MUST NOT read it from the current block's in-progress state, since that would make the result depend on execution order.
4. **Eviction check.** Let `old = expiringNonceRing[P]`. If `old != 0`: let `oe = expiringNonceSeen[old]`. Reject with `ExpiringNonceSetFull` if `oe != 0 && oe > now`. Otherwise write `expiringNonceSeen[old] = 0`.
5. **Insert.** Write `expiringNonceRing[P] = H` and `expiringNonceSeen[H] = validBefore`.

The transaction MUST NOT write `expiringNonceRingPtr`. This replaces TIP-1009 steps 3 and 7. Steps 1, 2, 4 and 5 are unchanged.

A rejection in steps 1, 2 or 4 makes the transaction invalid, as before, and a block containing it is invalid. The insert in step 5 persists if the transaction's calls revert, like a protocol nonce increment.

### Pointer advance

After the block's last transaction, including end-of-block system transactions, and before any other post-execution system call:

- If `n > 0`: write `expiringNonceRingPtr = (ptrStart + n) mod CAPACITY`.
- If `n == 0`: do nothing. The slot is neither written nor touched.

The advance is a direct state change by the protocol. It is not a transaction, consumes no block gas, emits no log and produces no receipt. In [EIP-7928](https://eips.ethereum.org/EIPS/eip-7928) block access lists it is recorded at the post-execution index (`set_post_execution_block_access_index` in `crates/evm/src/block.rs`).

### Block building

A builder counts the expiring nonce transactions it has included so far. That count is the next expiring nonce transaction's `i`. A candidate that fails steps 1, 2 or 4 is skipped and does not take an index, so the next candidate gets the same `i` and `P`. When step 4 fails because the ring is full of live entries, later candidates in the same block will usually fail it too, as under TIP-1009.

Prewarming, action replay and other speculative paths MUST use the same `P` and MUST NOT write the pointer per transaction. The existing prewarm code that saves and restores the pointer around `check_and_mark_expiring_nonce` is no longer needed.

### Gas

`EXPIRING_NONCE_GAS` stays 13,000 (`2 * COLD_SLOAD + WARM_SLOAD + 3 * WARM_SSTORE_RESET`). It does not depend on `i`, `P`, `n`, or whether step 4 finds an empty slot. TIP-1009 already left the pointer read and write out of transaction gas, so removing the per-transaction write changes no charge. The block-end write is charged to no one. [TIP-1016](./tip-1016.md)'s exemption (zero state gas for expiring nonce writes) is unchanged.

### Equivalence with TIP-1009

Under TIP-1009 the `k`-th expiring nonce transaction of a block (counting from 0) reads pointer value `(ptrStart + k) mod CAPACITY`, because each earlier one advanced it by one with the same wrap. That is `P` with `i = k`. Steps 1, 2, 4 and 5 read and write the same slots with the same values, and the final pointer is `(ptrStart + n) mod CAPACITY` under both rules. For every block valid under both rules, the post-state root is identical. The observable differences:

| Observer | TIP-1009 | This TIP |
|---|---|---|
| Block post-state, state root, receipts, logs, gas | — | Unchanged |
| Per-transaction state diff (tracers) | Includes a slot 3 write | No slot 3; it appears only in the block's post-execution changes |
| Block access list | Slot 3 written at each expiring nonce transaction's index | Slot 3 written once at the post-execution index, or not at all when `n == 0` |
| Parallel execution | Every expiring nonce transaction writes slot 3 | Expiring nonce transactions write disjoint slots |

### Activation

The rule activates at a network upgrade (TBD). Before activation, nodes apply TIP-1009 as written. The first post-activation block starts from the pointer value the last pre-activation block left. No storage migration is needed.

Activation only changes per-transaction traces and block access list contents. Tempo headers do not commit a block access list hash today (`crates/consensus/src/consensus/block.rs` rejects `block_access_list_hash`). Gating on a fork keeps every client's traces and access lists in agreement at any block height.

## Interfaces

No ABI, selector, event or error changes. The Nonce precompile's storage layout (`NONCE_PRECOMPILE_ADDRESS`) is unchanged:

```solidity
contract Nonce {
    mapping(address => mapping(uint256 => uint64)) public nonces; // slot 0
    mapping(bytes32 => uint64) public expiringNonceSeen;          // slot 1: replay hash => validBefore
    mapping(uint32 => bytes32) public expiringNonceRing;          // slot 2: position => replay hash
    uint32 public expiringNonceRingPtr;                           // slot 3: next block's ptrStart; written only by the post-block advance
}
```

Errors are unchanged and are raised as transaction-invalid during nonce validation:

```solidity
/// @notice validBefore is not in (now, now + MAX_EXPIRY_SECS].
error InvalidExpiringNonceExpiry();
/// @notice The replay hash is recorded with an expiry later than now.
error ExpiringNonceReplay();
/// @notice The entry at position (ptrStart + i) mod CAPACITY has an expiry later than now.
error ExpiringNonceSetFull();
```

Execution context: the block executor MUST pass `i` to the nonce check of each expiring nonce transaction. Tempo's `TempoTxEnv` already carries `expiring_nonce_idx`. Today the executor clears it (`set_expiring_nonce_idx(None)` in `crates/evm/src/block.rs`). Under this TIP it sets it for every expiring nonce transaction, and `check_and_mark_expiring_nonce` takes the position instead of reading and advancing the pointer.

# Compatibility

| Integration | What changes |
|---|---|
| Node execution (`crates/evm/src/handler.rs`, `crates/precompiles/src/nonce/mod.rs`) | Position comes from `ptrStart + i`. No per-transaction pointer write. The block executor adds the post-block advance. |
| Payload builder and prewarming (`crates/payload/builder`) | Count included expiring nonce transactions. Remove the pointer save/restore. |
| Action replay (`crates/evm/src/action_replay.rs`) | Records no slot 3 write per transaction. `ptrStart + i` replaces the cached `ring_ptr` / `set_next_ring_ptr` chain. |
| Block access lists | Slot 3 moves to the post-execution index. |
| Tracers (`debug_traceTransaction` prestate diff mode, `trace_replayBlockTransactions` stateDiff) | Per-transaction diffs no longer include slot 3. Tools that rebuild the pointer from per-transaction diffs must read it per block. |
| `eth_getStorageAt`, state proofs | Unchanged: they read block-level state, which is identical. |
| Transaction pool, SDKs, wallets, `is_expiring_nonce_seen` | Unchanged. Pool validation never reads the pointer. |
| `crates/state-bloat` generator | Writes the pointer directly. Check that it does not assume one write per transaction. |

Test helpers need a fork-gated fixture that executes the same block under both rules and compares state roots.

# Observability

N/A. No events are added or removed: TIP-1009 emits none for the ring, and the post-state is unchanged. Implementations SHOULD report `n` per block and the number of re-executions caused by Nonce precompile slots. After activation that count should be zero for blocks without duplicate replay hashes.

# Threat Model

**A node computes the wrong position.** The most consequential failure is a node computing a different `P` from its peers, by counting `i` differently or reading `ptrStart` from in-progress state. That yields a different post-state root, and the block is rejected. `i` is a pure function of the body and `ptrStart` of the parent state, so every honest validator computes the same values. A proposer can choose which positions transactions get by reordering the body, as it already can under TIP-1009; positions carry no value.

**Ring-filling DoS.** An attacker can submit enough live expiring nonce transactions to fill the ring, making later ones fail with `ExpiringNonceSetFull`. This is unchanged from TIP-1009 and TIP-1093: capacity is sized for 10,000 TPS over the window, and every insert pays 13,000 gas.

**Replay.** The replay check reads `expiringNonceSeen[H]`, which does not depend on position. Two transactions with the same `H` in one block still conflict: the second fails `ExpiringNonceReplay` and the block is invalid. That conflict is inherent and limited to the duplicates.

| Actor | Controls | Trusted to | Enforcing check | If wrong |
|---|---|---|---|---|
| Proposer/builder | Body order, which transactions to include | Nothing | Validators recompute `i`, `P` and the advance from the body and parent state | Block rejected |
| Transaction sender | `H`, `validBefore` | Nothing | Steps 1, 2 and 4 | Transaction invalid |
| Execution client | Scheduling, parallelism | Read `ptrStart` from the parent state, not in-progress state | State root comparison | Node forks off |

Residual risk: a client that keeps TIP-1009's per-transaction write after activation produces the same state root, so the mismatch shows only in traces and block access lists. Fork-gated differential tests guard against it. Excluded: other shared slots an expiring nonce transaction may write, such as fee token accounting, which need their own changes to become conflict-free.

# Invariants

- **I1. Post-state equivalence.** For any block valid under both rules, the post-state root under this TIP equals the one under TIP-1009.
- **I2. Distinct positions.** Within a block, every expiring nonce transaction has a distinct `P` (given A3).
- **I3. No per-transaction pointer write.** No transaction's state changes include slot 3. A block with `n > 0` writes slot 3 once, to `(ptrStart + n) mod CAPACITY`. A block with `n == 0` does not touch it.
- **I4. Bounded pointer.** `expiringNonceRingPtr < CAPACITY` after every block.
- **I5. Fixed gas.** An expiring nonce transaction's intrinsic gas does not depend on `i`, `P` or ring occupancy.
- **I6. Disjoint access.** The Nonce precompile slots an expiring nonce transaction writes are a subset of `{expiringNonceSeen[H], expiringNonceRing[P], expiringNonceSeen[old]}`, and it reads slot 3 only at its parent-state value.
- **I7. TIP-1009 E1–E7 hold**, including no replay of an unexpired `H`.

## Test cases

1. **Differential.** Randomized blocks mixing expiring nonce, 2D nonce, protocol nonce and end-of-block system transactions, executed under TIP-1009 and under this TIP from the same parent state, give equal state roots, receipts and gas (I1).
2. **Zero expiring nonce transactions.** Slot 3 is unchanged and absent from the block access list (I3).
3. **Wrap.** `ptrStart = CAPACITY - 2`, `n = 5`: positions are `CAPACITY-2, CAPACITY-1, 0, 1, 2`, and the pointer ends at `3` (I2, I4).
4. **Full ring.** Position `P` holds an entry with expiry `> now`: the transaction fails `ExpiringNonceSetFull`, a block including it is rejected, and the builder skips it and gives the same `i` to the next candidate.
5. **Expired eviction.** Position `P` holds an entry with expiry `<= now`: the old seen entry is cleared and the new one inserted.
6. **Duplicate hash in one block.** The second transaction fails `ExpiringNonceReplay`, and the block is invalid.
7. **Reverted calls.** An expiring nonce transaction whose call reverts still inserts at `P` and takes index `i`.
8. **Interleaving.** Expiring nonce transactions at body indices 0, 5 and 9 get `i = 0, 1, 2`. Other transactions, including system transactions, take no index.
9. **Gas.** Intrinsic gas is identical for `i = 0` and `i = 4,095`, and for empty and occupied positions (I5).
10. **Tracing.** Per-transaction prestate diffs omit slot 3. The block's post-execution changes include it once.
11. **Fork boundary.** The last pre-activation block writes the pointer per transaction. The first post-activation block starts from that value and writes it once.
12. **Parallel execution.** 4,096 expiring nonce transfers from distinct senders cause zero re-executions attributed to Nonce precompile slots (I6).
13. **Prewarm, replay and builder agreement.** Prewarming, action replay and canonical execution produce the same `P` for every transaction.

# Open Questions

1. **Fork gating.** The post-state is identical, so this could ship without a fork if every client switched at once. Is a fork worth it only for trace and block access list consistency?
2. **Advance placement.** On epoch boundary blocks, should the advance run before or after the current-committee system call? Neither touches the Nonce precompile, so the order only affects block access list indexing.
3. **Fee accumulators.** The measured speedup also needed fee counters written without a read. Should a companion TIP make fee accumulation conflict-free, or should that be left to clients?
