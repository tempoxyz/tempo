# TIP-1167: Zone Withdrawal Return Nonces

## Abstract

A zone withdrawal with a callback often sends funds back to the zone it came from: swap change, vault shares or redeemed assets. Today the receiving contract does this with an encrypted deposit whose recipient is chosen by whoever signed the withdrawal. This TIP lets the receiver return funds against the withdrawal's nonce instead, so they always go to the return recipient the account set when it withdrew, which an access key policy can check in plaintext. It covers returns to the source zone only.

## Motivation

Background, from the existing zone protocol:

- **Contracts.** On the zone, the **outbox** queues withdrawals and the **inbox** credits deposits arriving from Tempo. On Tempo, the **portal** (`ZonePortal`) escrows the zone's funds, processes withdrawals and keeps the **deposit queue**: a hash chain of entries the zone inbox processes in order.
- **Withdrawals.** A zone withdrawal is a call to \`ZoneOutbox.requestWithdrawal(token, to, amount, memo, gasLimit, zoneFallbackRecipient, data, revealTo)\`. When \`gasLimit > 0\`, \`to\` is a Tempo contract, the **receiver**: the sequencer calls \`processWithdrawals\` on the portal, which delivers the funds and calls the receiver's \`onWithdrawalReceived\` with \`data\` (a **callback**). \`memo\` and \`revealTo\` do not affect this TIP.

- **Fallback nonce.** When the withdrawal is requested, the outbox stores \`zoneFallbackRecipient\` on the zone under \`fallbackNonce\`, a number it assigns to each withdrawal. The withdrawal that reaches Tempo carries the nonce, not the recipient. If the callback fails, the portal queues a bounce-back deposit that names only the nonce, and the zone credits the stored recipient.

- **Closed access.** A zone in closed access mode requires every successful callback to add at least one deposit to the deposit queue, so callback value comes back to the zone.

When the callback succeeds, there is no nonce path. A receiver that sends funds back calls \`ZonePortal.deposit\` with an encrypted payload: the zone recipient and memo, encrypted to the sequencer's key. The signer writes this payload into \`data\`, and the receiver passes it on. This has two costs:

1. **Access keys can't be fully scoped.** A [TIP-1161](./tip-1161.md) policy is a contract the protocol calls before each call an access key signs; on the zone, it can check every plaintext argument of \`requestWithdrawal\`, including the fields inside \`data\`. It can't check the encrypted recipient. A key limited to one receiver can still send what comes back to any zone account.
2. **Every client builds an encrypted return payload** for the sequencer's current encryption key, even when the funds just go back to the account that withdrew.

The bounce-back path already returns funds by nonce. This TIP lets successful callbacks use it too.

Alternatives considered:

- **Check the ciphertext in the policy.** The key passes the plaintext recipient and the encryption randomness as hints, and a zone precompile re-encrypts and compares. It works, but adds a precompile and extra data to every call.
- **Encrypt on the zone.** The key passes a plaintext recipient and the zone encrypts it for the return. It needs encryption inside execution. It remains the likely route for returns to a different zone, where the nonce can't be resolved because only the source zone stores it; this TIP leaves those out.
- **A helper contract on the zone** that builds the return payload. It needs zone contract deployment rules relaxed, and the helper, not the account, becomes the caller.

## Assumptions

- **Receivers are trusted for amounts.** This TIP fixes where returned funds go, not how much comes back. Amounts are bounded by the access key's spending limits, which [TIP-1144](./tip-1144.md) applies to zone withdrawals, and the receiver's own checks, such as minimum outputs in \`data\`.
- **Returned tokens are enabled on the zone.** A receiver can only return a token the portal accepts deposits of.
- **One callback runs at a time.** \`processWithdrawals\` is non-reentrant, so the portal has at most one active receiver and return nonce at a time.
- **Activation.** Portal, outbox and inbox changes activate together at a zone hardfork. Receivers move to the new path after activation; until they do, they keep using encrypted deposits.

# Specification

## Overview

This TIP renames the fallback fields, since they are no longer used only on failure:

- **Return recipient** (\`zoneReturnRecipient\`, today \`zoneFallbackRecipient\`): the zone account that receives a withdrawal's bounce-back or returns. The account signing the withdrawal sets it, to any zone account; a policy can require it to be the account itself.
- **Return nonce** (\`returnNonce\`, today \`fallbackNonce\`): the per-withdrawal number the zone maps to the return recipient.
- **Return**: funds a receiver sends back to the source zone during a successful callback.

Lifecycle:

1. The account signs \`requestWithdrawal\` with \`to\` set to the receiver and \`zoneReturnRecipient\` set to itself. The outbox stores the recipient under a new return nonce, as today.
2. On Tempo, the portal delivers the withdrawal and records the receiver and return nonce for the duration of the callback.
3. During the callback, the receiver calls \`ZonePortal.returnToZone(token, amount)\` zero or more times. Each call queues a return that names only the nonce.
4. On the zone, the inbox resolves the nonce to the return recipient and credits it.

If the callback reverts, its returns revert with it, and the portal queues the usual bounce-back of the full amount.

No one names a recipient after step 1. A TIP-1161 policy can require \`zoneReturnRecipient\` to be the account and \`to\` to be an allowed receiver, both plaintext.

## Mechanics

### 1. Returning funds on Tempo

Before relaying a callback, the portal's \`deliverWithdrawal\` stores the withdrawal's \`to\` and return nonce, both read from the processed withdrawal, in transient storage, and clears them after the callback.

\`returnToZone(token, amount)\`:

1. Reverts with \`NoActiveCallback\` unless a callback is being delivered and \`msg.sender\` is its receiver.
2. Reverts unless \`token\` is enabled with deposits active, as for \`deposit\`.
3. Pulls \`amount\` from the receiver with \`transferFrom\`, so the receiver approves the portal first, as for \`deposit\`. It charges the zone deposit fee and reverts with \`DepositTooSmall\` if \`amount\` does not exceed it. No bounce-back fee is charged, because a return never bounces back to Tempo.
4. Queues a \`WithdrawalReturn\` entry with the token, return nonce and net amount, and emits \`WithdrawalReturned\`.

Deposit queue capacity works as for callback deposits today. The portal caps how many deposit queue entries the zone has not yet processed, and holds part of that cap back for withdrawal processing. The first deposit or return in a callback may use the held-back part; later ones count against the cap for ordinary deposits. If the queue is full, the call reverts, the callback fails and the withdrawal bounces back.

A return adds an entry to the deposit queue, so it satisfies the closed access requirement above.

Receivers can still call \`deposit\` for returns to another zone.

### 2. Crediting on the zone

The inbox handles a \`WithdrawalReturn\` entry like a bounce-back: it resolves the nonce with \`resolveReturnRecipient\` and mints the amount to the return recipient. If the mint fails, the amount is added to the recipient's pending balance, claimable as for bounce-backs today.

\`resolveReturnRecipient\` reads the stored recipient without deleting it, so one withdrawal can have several returns, such as change in one token and shares in another. A bounce-back still deletes the entry. A callback either succeeds, with any number of returns, or fails, with one bounce-back, never both.

### 3. Privacy

Returns from one callback share a nonce, so Tempo observers can tell they belong to the same withdrawal. They can tell that already, because returns happen in the same transaction as the callback. The nonce does not reveal the account. Each withdrawal gets a new nonce, and no one can return against a nonce after its callback ends, so later activity is not linked to it.

### 4. Renames

| Today | New |
|---|---|
| \`zoneFallbackRecipient\` | \`zoneReturnRecipient\` |
| \`fallbackNonce\` | \`returnNonce\` |
| \`lastFallbackNonce()\` | \`lastReturnNonce()\` |
| \`consumeFallbackRecipient(uint64)\` | \`consumeReturnRecipient(uint64)\` |

Parameter and field renames do not change the ABI. The renamed functions get new selectors; only the inbox and tooling call them.

## Interfaces

Deposit queue additions in \`IZone.sol\`:

\`\`\`solidity
enum DepositType {
    WithdrawalBounceBack,
    Deposit,
    WithdrawalReturn // Funds returned by a callback receiver
}

struct WithdrawalReturnDeposit {
    address token;       // TIP-20 token returned
    uint64 returnNonce;  // Resolves to the return recipient on the zone
    uint128 amount;      // Net amount after the deposit fee
}
\`\`\`

The entry is hashed into the deposit queue like the other types: \`keccak256(abi.encode(DepositType.WithdrawalReturn, abi.encode(entry), prevHash))\`.

\`IZonePortal\`:

\`\`\`solidity
/// @notice Return funds to the source zone of the withdrawal being delivered.
/// @dev Callable only by the active callback's receiver, during its callback.
/// @param token TIP-20 token to return; must be enabled with deposits active.
/// @param amount Amount pulled from the caller, including the deposit fee.
/// @return newCurrentDepositQueueHash The deposit queue hash after the return.
function returnToZone(address token, uint128 amount)
    external
    returns (bytes32 newCurrentDepositQueueHash);

event WithdrawalReturned(
    bytes32 indexed newCurrentDepositQueueHash,
    uint64 indexed returnNonce,
    address indexed receiver,
    address token,
    uint128 amount,
    uint128 fee,
    uint64 depositNumber
);

/// @notice No callback is active, or the caller is not its receiver.
error NoActiveCallback();
\`\`\`

\`IZoneOutbox\`:

\`\`\`solidity
/// @notice Resolve a return recipient without deleting it. Only callable by ZoneInbox.
function resolveReturnRecipient(uint64 returnNonce) external view returns (address);
\`\`\`

\`IZoneInbox\` events:

\`\`\`solidity
event WithdrawalReturnProcessed(uint64 indexed returnNonce, address indexed recipient, address token, uint128 amount);

\`\`\`

# Compatibility

| Integration | What changes |
|---|---|
| Callback receivers | Call \`returnToZone\` for same-zone returns instead of \`deposit\`. Existing receivers keep working until they switch, but their returns can't be scoped by a policy. |
| Clients | No encrypted return payload or key index to build; callback \`data\` loses its return recipient fields. |
| TIP-1161 zone withdrawal policies | Require \`zoneReturnRecipient\` to equal the account. For receivers using \`returnToZone\`, \`data\` has no recipient left to check. |
| Zone node, prover and L1 event extraction | Handle the new deposit type and \`WithdrawalReturned\` event, and the renamed outbox functions. |
| Indexers | Index \`WithdrawalReturned\` and the zone return events. |

# Observability

- \`WithdrawalReturned\` on Tempo: which withdrawal (by nonce) a return belongs to, from which receiver, and how much.
- \`WithdrawalReturnProcessed\` and \`WithdrawalReturnPending\` on the zone: whether the return was credited or is waiting to be claimed.

# Threat Model

The main attack this addresses is an access key holder, scoped to a receiver, sending what the receiver returns to an account of its choosing.

| Actor | Controls | Enforcing check | If compromised |
|---|---|---|---|
| Access key holder | Withdrawal arguments and \`data\` | TIP-1161 policy pins \`to\` and \`zoneReturnRecipient\`; the portal pays returns only by nonce | Can choose amounts and the operation within the receiver's checks and its spending limits, not where returns go |
| Receiver | What it does with the withdrawn funds | None in this TIP | Can keep funds or send them elsewhere; accounts should allow only receivers that return through \`returnToZone\` |
| Other contracts | Nothing in the withdrawal | \`NoActiveCallback\` | Can't return against another withdrawal's nonce |
| Sequencer | Deposit processing, as today | Zone proof verifies the deposit queue | Unchanged |

Residual risks: a policy sees only top-level calls on the zone, so the receiver's behavior on Tempo is trusted. Returns to another zone still use encrypted deposits.

# Invariants

- \`returnToZone\` succeeds only when called by the active callback's receiver, during that callback.
- Every return credits the return recipient stored under its nonce, or that recipient's pending balance.
- If a callback reverts, none of its returns are queued, and exactly one bounce-back of the full amount is.
- A return nonce can't be used after its callback ends.

Tests must cover: several returns in one callback, in different tokens; a return by a non-receiver; a return after the callback ends; a callback that returns and then reverts; a return in closed access mode; and a failed mint becoming a pending balance.
