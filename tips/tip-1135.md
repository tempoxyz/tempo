# TIP-1135: Configurable account authorization escalation

## Abstract

Configurable accounts can require different owner quorums depending on the value at risk. This TIP adds opt-in rules that raise the required approval weight when a transaction's gross token outflow or the account's pre-transaction token balance exceeds a configured limit. Rules are enforced by the protocol, including across batched calls, and cannot be weakened by the ordinary low-value quorum. Equal-weight owners implement M-of-N signing; weighted owners retain the authorization model proposed in TIP-1114.

## Motivation

An account should support routine payments with one signer while requiring two or more signers for larger transfers. An account holding a large balance may also need stronger authorization even for a small transfer. A wallet-only prompt does not enforce either rule against an attacker who submits transactions through another client.

For example, three equal-weight owners could require one approval for transfers up to 5,000 units of a selected USD stablecoin and two approvals above that amount. A separate balance rule could require all three approvals whenever the account holds more than 100,000 units of that token. The strongest matching rule wins.

The motivating discussion also describes a passkey with weight two and two OIDC owners with weight one each. A base threshold of two permits the passkey alone or both OIDC owners; an elevated threshold of three requires the passkey plus an OIDC owner. Weight is not a count of independent authentication factors. OIDC eligibility remains governed by the OIDC and configurable-account specifications, not this TIP.

Alternatives are a fixed high threshold, separate low-value and treasury accounts, access-key spending limits, or a smart-contract wallet. Those remain useful, but none makes the native account's owner quorum depend on its current balance and transaction outflow without changing the account model.

## Assumptions

- This is an extension of the proposed configurable-account cluster, not a description of deployed functionality. The dependency specifications are currently available in [the configurable-account TIP PR](https://github.com/tempoxyz/tempo/pull/7510). Integration must use their final approved encodings and limits.
- TIP-1114's owner configuration and configuration commitment remain unchanged. Policy state is additional authenticated protocol state in the existing native multisig precompile's storage. TIP-1108's account-leaf encoding is not extended again.
- The first version measures native TIP-20 token balances and debits. It does not value arbitrary ERC-20s, NFTs, contract-held claims, or native value in dollars.
- A token-unit threshold is not an oracle-backed dollar value. Wallets may display USD labels for a user-selected USD stablecoin, but must disclose peg and issuer risk. Values from different tokens are never added together.
- Every native TIP-20 debit path must participate in the policy checks. If this cannot be guaranteed, activation is blocked rather than shipping a calldata-only check that can be bypassed.
- Policy-enabled accounts use direct owner authorization only in this version. Existing access-key grants remain stored but cannot be used while the policy is enabled. This restriction must be shown before installation.

# Specification

## Policy state and bounds

Each account has a policy revision, initially zero, and zero or one active policy. A policy contains an `adminThreshold` and 1–16 rules. Each rule contains:

| Field | Type | Meaning |
| --- | --- | --- |
| `token` | `address` | An existing native TIP-20 token. |
| `metric` | `uint8` | `0` for transaction gross outflow; `1` for pre-transaction wallet balance. |
| `limit` | `uint256` | A strict upper boundary in the token's raw units. |
| `threshold` | `uint8` | Approval weight required when the metric is greater than `limit`. |

There are at most eight distinct rule tokens. Sort rules lexicographically by `(token, metric, limit)` and reject duplicates, invalid metrics, and non-native token addresses. Limits are unsigned integers; zero is permitted. Do not query token decimals during consensus evaluation.

Let `baseThreshold` be the current owner threshold. Every rule threshold must be greater than `baseThreshold` and at most `adminThreshold`. `adminThreshold` must be at least `baseThreshold`, at most 255, and reachable within TIP-1114's eight-signature bound. Apply the same reachability check to every rule threshold. A valid policy therefore always has a bounded quorum that can authorize every tier.

Revision increments by exactly one on every successful installation, replacement, or removal. Reject overflow. Removal keeps the revision and clears the policy; it never resets revision to zero. Policy writes use ordinary journaled storage and roll back with execution, unlike initial configurable-account registration.

## Required approval weight

For token `t`, define:

```text
B[t] = native token balance of the sending account at transaction entry,
       before fee reservation and user calls
D[t] = gross transaction outflow of that account in token t
required = max(baseThreshold,
               thresholds of all rules for which metric_value > limit)
```

Transaction entry is the transaction's position in the canonical block, not the state when a wallet signed or the transaction entered the pool. Incoming transfers in earlier transactions affect `B`; incoming transfers within this transaction do not. Refunds, incoming transfers, and transfers back to the account do not subtract from `D`.

Reserve the maximum token charge allowed by the transaction's fee fields, using the existing fee manager's conservative token-debit calculation. Include that reservation in `D` if the sender pays its own fees. It counts once, even if execution fails; replace neither the reservation with the actual fee nor subtract the refund for tier selection. A different primitive fee payer contributes no sender outflow. A policy-enabled configurable account cannot act as a separate fee payer in this version.

Then add every positive native TIP-20 debit from the sender during execution, including transfers, memo transfers, burns, and movements into DEX, fee-AMM, or channel custody. A self-transfer does not count if the native token implementation makes no balance debit. Use checked addition; overflow aborts execution. Failed subcalls roll back their debit accounting along with their state. Successful subcalls remain counted until the whole transaction commits or reverts.

Equality does not escalate: `value == limit` remains in the lower tier. When multiple tokens, metrics, or tiers match, take the maximum threshold, not the sum. Debit rules apply to the whole transaction, not independently to each batch item.

## Direct-payment and administrative lanes

The low-value lane is deliberately restricted so an unknown call cannot create authority to spend later without escalation. A transaction qualifies only when every top-level call is a direct native TIP-20 `transfer` or `transferWithMemo`, has zero native value, and targets a token present in the active policy. Reject contract creation and authorization-list delegation in this lane. Decode using the active protocol's native ABI rules; do not introduce stricter trailing-calldata rules here.

Every other transaction requires `adminThreshold`, regardless of measured outflow. This includes approvals, arbitrary contract calls, swaps, owner rotation, policy changes, access-key management, transfers of unlisted assets, and nonzero native value. It permits these operations with the strongest configured quorum rather than pretending their future exposure can be determined from calldata. Increasing or revoking an allowance uses the same administrative lane.

The lane is selected from the complete signed transaction before calls execute. An administrative transaction cannot subsequently become a low-value transaction by deleting its policy or rearranging batch calls.

Policies do not protect assets already held by external contracts, existing DEX orders, or permissions represented inside arbitrary contracts. Wallets must disclose that boundary before installation. Moving assets into those contracts requires the administrative quorum, but their later internal accounting is outside this TIP.

## Authorization witness and signing

Keep TIP-1114's three-field `0x05` witness for accounts with no active policy. After activation, add a four-field form for direct owner transactions:

```text
0x05 || rlp([account, config, signatures, [policyRevision, authorizationThreshold]])
```

`config` and primitive signature encodings remain unchanged. Use canonical RLP and reject other field counts, invalid integer widths, and trailing fields. `policyRevision` is `uint64`; `authorizationThreshold` is `uint8`.

For the extended witness, owners sign:

```text
keccak256(
  "tempo:multisig:escalation" || tx.signature_hash() || account ||
  uint64(config.version) || uint64(policyRevision) || uint8(authorizationThreshold)
)
```

Use raw ASCII for the domain, 20 bytes for the account, and fixed-width big-endian integers. The existing transaction hash binds the chain ID, nonce domain, complete call batch, gas and fee fields, and validity interval. Do not allow a fee-payer signature to contribute owner approval weight.

Require the current configuration commitment and policy revision to match at inclusion. For an enabled policy, `authorizationThreshold` must equal one of the current base, rule, or administrative thresholds. A sole-call policy replacement may also declare the proposed administrative threshold decoded from its signed calldata. Verify sorted, distinct owners and the final-signature stopping rule against this declared threshold, not against the base threshold. This allows a wallet to supply a stronger quorum in advance without TIP-1114 rejecting it as unnecessary signatures.

Before cryptographic verification, enforce the existing owner/signature bounds and require the declared threshold to cover the administrative lane, balance rules, and fee reservation. A three-field witness is invalid whenever a policy is active, even if the base quorum would otherwise suffice. A four-field witness is invalid when no policy is active. Existing no-policy signature behavior is unchanged.

During execution, recompute the outflow requirement before committing each native token debit. If it exceeds the declared threshold, abort the entire user execution. This is a protocol-level failure, not a catchable Solidity revert and not a skippable failed batch item. Roll back all user calls, policy/configuration updates, token movements, and their logs. Preserve the normal included-transaction fee and nonce effects and TIP-1114 initial-registration behavior. A failed included transaction does not charge an unperformed transfer against a later transaction.

## Preventing delegated and pull-payment bypasses

While an account's policy is enabled:

- Reject access-key transactions executed as that account, including keys granted before installation and inline grant-and-use transactions.
- Reject its use as a configurable access-key delegate or as the configurable signer of an independent signed key-authorization witness. The extended witness is transaction-only in this version.
- Allow token debits only within an included, directly owner-authorized transaction whose sender is the policy account and whose escalation checks cover that debit. Reject third-party allowance pulls, including allowances issued before policy installation. The native token hook applies even if the spender is another precompile or a contract.
- Fee collection by the protocol is permitted only through the sender reservation described above. Separate-fee-payer use by the policy account is rejected before fees are collected.
- Preserve explicit issuer-authorized burn/clawback powers and mandatory protocol transitions. Those are not owner-authorized spending and are outside this guarantee. The debit implementation must distinguish these privileged paths from ordinary `burn` and `transferFrom`; callers cannot choose a bypass flag.

Existing allowances and access-key grants are not deleted. Removing the policy can reactivate them; wallets must enumerate available grants and allowances or clearly warn if that inventory is incomplete. This TIP does not claim to enumerate permissions held by arbitrary contracts.

## Policy administration and owner rotation

Extend TIP-1109's native multisig precompile at `0xAACC000000000000000000000000000000000000`. No new precompile address is introduced.

```solidity
interface IAccountEscalation {
    struct Rule {
        address token;
        uint8 metric;
        uint256 limit;
        uint8 threshold;
    }

    /// Return revision, enabled state, admin threshold, and the canonical rules.
    /// An account without an active policy has adminThreshold zero and no rules.
    /// Reading does not register or modify a configurable account.
    function getEscalationPolicy(address account) external view returns (
        uint64 revision, bool enabled, uint8 adminThreshold, Rule[] memory rules
    );

    /// Install or replace msg.sender's policy and increment its revision.
    /// Must be the sole top-level call in a direct owner-authorized transaction.
    /// Requires expectedRevision to match and both the old administrative quorum
    /// (or base quorum if disabled) and the proposed adminThreshold to be met.
    /// Reverts for invalid rules, unsupported callers, stale state, or overflow.
    function setEscalationPolicy(
        uint64 expectedRevision, uint8 adminThreshold, Rule[] calldata rules
    ) external;

    /// Remove msg.sender's active policy without deleting grants or allowances.
    /// Must be the sole top-level call and meet the current adminThreshold.
    /// Increments revision; reverts if disabled, stale, unauthorized, or overflow.
    function removeEscalationPolicy(uint64 expectedRevision) external;

    event EscalationPolicyUpdated(
        address indexed account, uint64 revision, bool enabled,
        uint8 adminThreshold, Rule[] rules
    );

    error InvalidEscalationPolicy();
    error StalePolicyRevision();
    error PolicyRevisionOverflow();
    error UnauthorizedPolicyCaller();
    error InsufficientPolicyWeight(uint8 supplied, uint8 required);
}
```

Administration requires a protocol-created top-level call with `msg.sender == tx.origin`. A fee payer, contract callback, or access key cannot administer a policy. Check caller and sole-call constraints, expected revision, quorum, then new policy validity, in that order. Use the current owner configuration already verified by the transaction; callers do not supply a second configuration proof.

Installation uses the legacy witness, since no policy is active. For this single operation, apply TIP-1114's final-signature stopping rule at `max(baseThreshold, proposedAdminThreshold)` rather than the base threshold. Replacement uses the extended witness with declared threshold `max(oldAdminThreshold, proposedAdminThreshold)`. Decode this requirement from the signed sole-call calldata before verifying signatures. Both transitions require the existing owners to authorize the proposed administrative strength, so installation cannot accidentally make administration unreachable for the approving quorum. Actual final-signature weight may exceed the declared threshold, but cannot be supplied by extra signatures after the stopping point.

An owner/threshold update under TIP-1109 leaves the policy unchanged. Require the original transaction's administrative quorum and validate every remaining tier against the proposed owners and base threshold. Reject rotations that make a tier unreachable within eight signatures, raise the base to or above a rule threshold, or raise the base above `adminThreshold`. Changing owner weights therefore cannot silently disable a policy. Configuration changes invalidate old signatures through the existing configuration version.

After removal, subsequent transactions use the legacy witness again. The incremented policy revision ensures that removal and reinstalling an identical policy never revives an old extended witness.

## Validation, execution, and gas

Policy storage reads and writes, balance reads, hashing, primitive verification, and update logs use the existing gas schedule. Charge rule processing as a fixed bounded loop using the normal warm storage-read charge for each additional rule processed; additionally charge actual storage accesses under the normal cold/warm schedule. Decode and validate bounds before doing cryptography. Debit accounting uses the existing token operation's execution gas; it cannot invoke user code or make an external oracle call.

RPC simulation and block execution must run identical checks. Pool acceptance is advisory: cache dependencies on the policy revision, owner commitment, rule-token balances, fee-token state, and hardfork state. Revalidate at the transaction's block position and after dependency changes or reorgs. Never infer a consensus quorum from node-local pending transactions.

This TIP measures value in flight within one transaction. A user can split a payment across independent transactions below the amount threshold. Balance rules still apply, but neither rule is a rolling spending cap. Daily budgets or aggregate outstanding commitments require a separate specification with consensus-owned accounting; a mempool total cannot enforce them.

## Example policies

For a six-decimal token and three equal-weight owners:

| Condition | Raw limit | Required owners |
| --- | --- | --- |
| Base | N/A | 1 of 3 |
| Gross outflow greater than 5,000 token units | `5_000_000_000` | 2 of 3 |
| Entry balance greater than 100,000 token units | `100_000_000_000` | 3 of 3 |
| Administrative operation | N/A | 3 of 3 |

Two transfers of 3,000 units in one batch require two owners even though each transfer is below the amount limit. If the sender pays fees in that token, the fee reservation also contributes to gross outflow. A 5,000-unit transfer can therefore cross the limit when fees are included. With an entry balance of 100,001 units, even a one-unit transfer requires three owners.

For the weighted passkey/OIDC example, use base weight two, elevated weight three, and administrative weight four. That requires all configured weight for policy weakening while allowing the passkey plus either OIDC owner for elevated transfers, subject to those signer types being supported by the final dependency specifications.

# Tooling

- Wallets and SDKs must fetch policy state, simulate the complete batch, choose the declared threshold, and display token units, fee reservation, balance snapshot, selected lane, and required owners. Simulation is an estimate, not a promise that state will be unchanged at inclusion.
- Signing screens must distinguish weighted quorum from distinct-factor MFA. Two identities backed by one provider are not necessarily independent factors.
- Policy installation must display disabled access-key use, blocked allowance pulls, external-custody limitations, issuer authority, and the effect of removal. Preserve owner configuration and full policy data for recovery/debugging.
- Simulation failures must expose stable reason codes `POLICY_REVISION_MISMATCH`, `POLICY_THRESHOLD_TOO_LOW`, `POLICY_EXTERNAL_DEBIT`, and `POLICY_UNSUPPORTED_AUTHORIZATION`, with account, token where applicable, required threshold, and declared threshold. An execution escalation failure produces a failed receipt, not a valid partial payout.
- Add fixtures for legacy and extended witnesses, boundary amounts, fees, weighted owners, policy revisions, batch rollback, and every native debit path. No implementation is included in this proposal.

# Observability

Emit `EscalationPolicyUpdated` on each successful installation, replacement, or removal, with the full canonical rules and new revision. This lets indexers reconstruct policies and distinguish intentional changes from stale client state. Reverted changes emit no surviving log.

No per-transfer event is added. Existing TIP-20 transfer events and transaction witnesses identify successful payments and the declared quorum. Nodes must count authorization and execution failures by the stable reason codes above; exclude raw signatures and user identities from metric labels. Simulation/debug traces must include the evaluated revision, entry balances, fee reservation, gross debits, required weight, and supplied weight. These explain why a batch escalated without treating simulations as authoritative outcomes.

# Threat Model

- A compromised low-weight owner may authorize routine payments but cannot lower thresholds, rotate to weaker owners, approve new spenders, or bypass rules through batch splitting within one transaction. Splitting across transactions remains possible.
- Owners reaching the administrative quorum can replace or remove the policy, delegate authority, and move funds into unprotected contracts. The policy is not protection against that quorum.
- Relayers and fee payers cannot substitute a policy revision, threshold, call, or fee ceiling without invalidating owner signatures. They may delay submission until balances change; inclusion-time checks remain authoritative.
- Incoming senders can increase a wallet balance across a balance boundary and force escalation. The administrative quorum remains usable; receiving dust must not permanently lock the account. Wallets should explain this intentional balance-trigger tradeoff.
- Token issuers retain pause, blacklist, and explicit confiscation powers. Dollar stability and availability are outside the quorum mechanism.
- Contracts, allowance spenders, and access keys cannot perform ordinary native debits from a protected account without direct owner authorization. External-contract claims and prior custody arrangements are outside this guarantee.
- Validators must use deterministic, bounded evaluation against canonical state. Missing a native debit hook is a consensus/security defect, not a reason to treat that path as unmetered.

# Invariants

1. With no active policy, existing account addresses, configuration hashes, signatures, fees, and owner-update behavior remain unchanged, except for the explicit opt-in policy-installation quorum.
2. Every successful protected debit is covered by enough verified approval weight for the strongest entry-balance, fee-reservation, lane, and transaction-outflow rule.
3. Adding a successful debit or increasing an entry balance cannot reduce the required threshold. Incoming funds cannot offset earlier gross outflow.
4. Administrative changes cannot be approved by a weaker quorum than the current administrative requirement. Removed owners, stale configurations, and stale policy revisions cannot authorize new execution.
5. Every installed tier is reachable within the existing signature bound; owner rotation preserves that property or reverts.
6. A failed execution escalation check leaves no user-call state or logs, even if triggered inside a callback or a batch item that normally permits failure. Fees, nonces, and initial registration retain their normal inclusion semantics.
7. Old allowances and access keys cannot bypass an enabled policy. Removal does not imply revocation, and reinstalling never revives an old policy witness.

The test suite must cover `limit - 1`, `limit`, and `limit + 1`; multiple rules/tokens; weighted overshoot and duplicate signers; batched transfers; refunds and intra-transaction credits; reverted subcalls; amount overflow; all fee-payer combinations; native burns and privileged issuer burns; pulls through contracts and native precompiles; policy removal/reinstallation; migration and first use; concurrent nonce domains; same-block balance/policy/configuration changes; and reorg restoration. Include negative tests proving that arbitrary calls, approval-based drains, and partial-batch semantics cannot evade escalation.

Before moving beyond Draft, audit every native debit path and benchmark maximum rules, tokens, owner/signature counts, and an invalid final signature. Engineering and security review must approve the witness extension, administration transition rules, fee-reservation calculation, failure semantics, and restrictions on delegated access. Activation and a reference implementation remain unscheduled.
