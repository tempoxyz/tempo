# TIP-1117: Reprice Precompile and Opcode Gas Costs

## Abstract

This TIP changes the gas schedule for selected EVM opcodes and precompiles at
T13. The prices are calibrated from Tempo execution benchmarks toward a target
of approximately 1 GGas/s of charged work. It also removes the KZG
point-evaluation precompile because that cryptographic workload is
disproportionately expensive under its inherited gas price.

## Motivation

Gas limits bound execution only when charged gas tracks the resources consumed
by a node. Several inherited EVM prices allow substantially less than 1 GGas/s
on Tempo for arithmetic, hashing, and elliptic-curve workloads. A block filled
with those operations can therefore require much more CPU time than its gas
limit implies.

The initial benchmark analysis and candidate schedule are recorded in the
[gas-repricing study](https://gist.github.com/rakita/f39ee165c9ed093eb467ba38bf2c3ba9#candidate-gas-values).
The values below supersede those candidates. They are the final values obtained
after repeated T13 benchmark runs and are normative for this TIP.

## Assumptions

- The target node implementation and benchmark host are representative enough
  to identify operations that are materially underpriced.
- Execution time scales approximately linearly with the charged unit used by
  each gas formula over the benchmarked range.
- Existing input validation, outputs, and error behavior remain unchanged
  except for the removal of the KZG point-evaluation precompile.
- T13 is activated by the chain configuration and all nodes agree on the
  activation point.

## Threat Model

An untrusted transaction sender can select opcode sequences and precompile
inputs that maximize execution time while remaining within the block gas limit.
The repricing limits this denial-of-service vector by charging more gas for the
measured work. Incorrect or inconsistent fork activation is also in scope
because nodes using different schedules would disagree on out-of-gas results.

# Specification

## Activation

All changes in this TIP activate at T13. Before T13, the existing opcode and
precompile schedules MUST remain unchanged. At and after T13, clients MUST use
the schedules below when deciding whether execution has enough gas and when
reporting gas consumed.

Unless explicitly changed below, opcode semantics, precompile addresses, input
validation, return values, and failure behavior are unchanged.

## Opcode gas schedule

The following static opcode prices apply from T13:

| Opcode | Before T13 | T13 onward |
| --- | ---: | ---: |
| `MOD` | 5 | 40 |
| `SMOD` | 5 | 37 |
| `DIV` | 5 | 17 |
| `SDIV` | 5 | 23 |
| `ADDMOD` | 8 | 36 |
| `MULMOD` | 8 | 65 |
| `SHL` | 3 | 9 |
| `SHR` | 3 | 9 |
| `SAR` | 3 | 10 |
| `NOT` | 3 | 3 |
| `ISZERO` | 3 | 5 |
| `KECCAK256` base | 30 | 205 |
| `SELFBALANCE` | 5 | 13 |

The `NOT` candidate repricing is deliberately not adopted; its price remains 3.

For `KECCAK256`, let:

```text
words = ceil(input_length / 32)
```

The total opcode cost is:

```text
before T13: 30  + 6  * words
T13 onward: 205 + 41 * words
```

Memory-expansion charges are separate and unchanged.

## Precompile gas schedule

For the linear input-based prices in this section, let:

```text
words = ceil(input_length / 32)
```

For pairing precompiles, `k` is the number of complete encoded pairs. For
BLS12-381 MSM precompiles, `k` is the number of complete point-scalar pairs.

| Address | Precompile or parameter | Before T13 | T13 onward |
| --- | --- | ---: | ---: |
| `0x01` | `ECRECOVER` | 3,000 | 25,000 |
| `0x02` | SHA-256 | `60 + 12 * words` | `104 + 13 * words` |
| `0x04` | Identity | `15 + 3 * words` | `50 + 1 * words` |
| `0x06` | BN254 add | 150 | 750 |
| `0x07` | BN254 scalar multiplication | 6,000 | 30,000 |
| `0x08` | BN254 pairing | `45,000 + 34,000 * k` | `285,000 + 243,000 * k` |
| `0x09` | BLAKE2 F compression | `rounds` | `10 * rounds` |
| `0x0b` | BLS12-381 G1 add | 375 | 2,300 |
| `0x0c` | BLS12-381 G1 MSM base | 12,000 | 78,000 |
| `0x0d` | BLS12-381 G2 add | 600 | 3,500 |
| `0x0e` | BLS12-381 G2 MSM base | 22,500 | 143,000 |
| `0x0f` | BLS12-381 pairing | `37,700 + 32,600 * k` | `230,000 + 167,000 * k` |
| `0x10` | BLS12-381 map field element to G1 | 5,500 | 26,000 |
| `0x11` | BLS12-381 map field element to G2 | 23,800 | 95,000 |

The G1 and G2 MSM discount tables and their divisor of 1,000 are unchanged. For
either MSM operation, the gas charge remains:

```text
floor(k * T13_MSM_BASE * discount(k) / 1000)
```

`discount(k)` is the existing discount-table entry for `k`; when `k` exceeds
the table length, the last entry is used.

The Identity schedule intentionally moves cost from the per-word component to
the base component. It is therefore not a uniform multiplier of the pre-T13
schedule.

## Modular exponentiation

The modular-exponentiation precompile at `0x05` retains the Osaka input-size
limit and execution semantics but uses a Tempo-specific gas formula from T13.

Let:

```text
max_len = max(base_length, modulus_length)
```

The multiplication complexity is:

```text
if max_len <= 32:
    multiplication_complexity = 81
else:
    words = ceil(max_len / 8)
    multiplication_complexity = 2 * words * words
```

The iteration count is calculated as follows, where `exp_head` is the first
`min(exponent_length, 32)` bytes of the exponent interpreted as a big-endian
integer:

```text
if exponent_length <= 32 and exp_head == 0:
    iteration_count = 1
else if exponent_length <= 32:
    iteration_count = max(bit_length(exp_head) - 1, 1)
else:
    iteration_count = max(
        20 * (exponent_length - 32) + max(bit_length(exp_head), 1) - 1,
        1,
    )
```

The T13 gas charge is:

```text
max(500, multiplication_complexity * iteration_count)
```

For comparison, the pre-T13 Osaka formula uses a complexity of 16 when
`max_len <= 32` and an exponent-length multiplier of 16. Its minimum charge of
500 and its `2 * words * words` complexity for larger base or modulus values
are unchanged by this TIP.

## Remove KZG point evaluation

At T13, the KZG point-evaluation precompile at
`0x000000000000000000000000000000000000000A` MUST be removed from the active
precompile set. Calls to this address MUST follow ordinary EVM account-call
semantics and MUST NOT perform KZG proof verification.

Before T13, the precompile remains available at its inherited price of 50,000
gas. Historical execution is unaffected.

# Tooling

Gas estimators, debuggers, tracers, transaction simulators, and contract-testing
frameworks MUST select the schedule using the active hardfork. Tools targeting
T13 MUST stop treating address `0x0A` as a KZG precompile. No calldata or return
data encoding changes are introduced for the remaining precompiles.

# Observability

N/A. No new protocol events are required. Node operators SHOULD expose the
active hardfork and client version through existing metadata so gas-estimation
or execution disagreements can be tied to the selected schedule.

# Invariants

1. Execution before T13 uses exactly the pre-existing gas schedule and
   precompile set.
2. Every T13 node computes the same gas charge for the same opcode or valid
   precompile input.
3. Existing precompile outputs and validation errors are unchanged, except that
   address `0x0A` is no longer dispatched as a precompile.
4. BLS12-381 MSM discount tables and input-length rules are unchanged.
5. Modular-exponentiation inputs continue to enforce the Osaka size limit.
6. An operation with gas below its T13 charge fails with out-of-gas before its
   successful result can be returned.

# Security Considerations

The higher prices reduce the amount of measured CPU-intensive work that fits in
a block. The Identity schedule is not monotonically higher for every possible
input length because its base charge increases while its per-word charge
decreases; implementations must apply the complete formula rather than compare
only one component. Removing point evaluation eliminates an otherwise
underpriced cryptographic workload, but contracts that call `0x0A` must account
for the changed behavior at T13.
