# TIP-1140: Batched Zone Deposits

## Abstract

This TIP extends the existing Zone deposit interface to fund multiple recipients in a single deposit. The total amount remains public, while recipients, individual amounts, and memos are encrypted and processed within the Zone.

## Motivation

Funding multiple Zone accounts currently requires a separate deposit for each recipient, with each amount visible on Tempo. Batched deposits expose only the aggregate amount and use one portal transfer and decryption proof. Whether deposits are batched or submitted individually, the Zone mints each allocation separately to its recipient.

## Specification

### Interface and encoding

Batched deposits use the same `deposit` interface, `depositEncrypted` alias, and `DepositPayload` as single-recipient deposits. The ciphertext length identifies which format the deposit uses.

| Ciphertext length | Plaintext |
|---|---|
| `64` | Existing recipient, memo, and padding |
| `1 + 68 * N` | Version byte `0x01` followed by `N` allocations |

Each allocation contains the recipient's address, amount, and memo:

```text
recipient   20 bytes
amount      16 bytes, unsigned big-endian
memo        32 bytes
```

A batch contains between one and `MAX_BATCH_RECIPIENTS` allocations. The portal rejects ciphertext lengths that match neither format before collecting funds.

Within the Zone, the inbox checks that the version is `0x01`, recipients are nonzero, and amounts are positive. It sums the amounts using `uint256` arithmetic and verifies that the total matches the queued net amount. Allocations to the same recipient are processed in list order. Memos default to `bytes32(0)`, and batches do not support per-recipient callbacks.

### Encryption

Existing payload encryption remains unchanged.

Batches reuse secp256k1 ECDH and Chaum-Pedersen verification, with fresh ephemeral key material and a fresh nonce. HKDF retains the existing info encoding and uses the UTF-8 salt `ecies-batch-deposit-v1`.

AES-GCM additional authenticated data is the canonical `abi.encode` of:

```text
bytes32(keccak256("tempo-zone-batch-deposit-v1")),
uint256(parentChainId),
uint256(zoneChainId),
address(portal),
address(sender),
address(token),
uint128(netAmount),
uint16(N),
uint256(keyIndex),
address(tempoRefundRecipient)
```

The inbox derives this context from the authenticated deposit and Zone configuration.

### Fees and acceptance

Existing deposit checks apply. The portal transfers the gross `amount`, deducts the deposit fee, and queues the net amount in one entry.

The proposed initial fee is:

```text
batchDepositFee = N * FIXED_DEPOSIT_GAS * zoneGasRate
```

Keep `calculateDepositFee()` and add:

```solidity
function calculateDepositFee(
    uint16 allocationCount
) external view returns (uint128 fee);
```

The overload rejects zero or counts above the cap and uses checked arithmetic. The SDK submits the allocation total plus the quoted fee and authenticates the allocation total as the net amount.

If the fee changes before inclusion, authentication or sum validation fails and the net amount bounces back. The deposit fee remains paid.

A batch consumes one queue entry, deposit number, and decryption entry. Queue encoding and `DepositMade` remain unchanged.

### Execution and refunds

The inbox verifies and decrypts once, validates the entire list, then mints each allocation atomically within a bounded gas allowance. Existing token-policy checks apply to every mint.

If decryption, validation, or any mint fails, the batch credits nothing and produces one bounce-back for the entire net amount. All mint credits and logs are rolled back, and the queue advances once. There is no partial success or retry.

Reserve enough gas to record failure, enqueue the refund, and advance the queue. Existing refund fees, policy checks, and parked-refund behavior apply. Malformed queue witnesses or missing or extra decryption entries invalidate the enclosing system transaction.

## Invariants

- A successful batch cannot credit more or less than the queued net amount.
- A failed batch cannot leave any recipient credits or allocation success events.
- The credited recipients, amounts, and memos cannot differ from the authenticated list.
- Processing the same batch again cannot create additional credits or bounce-backs.
- A processed batch cannot have both credits and a bounce-back, neither outcome, or more than one bounce-back.
