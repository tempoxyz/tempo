# TIP-1140: Batched Zone Deposits

## Abstract

This TIP extends `deposit` to accept an encrypted list of recipients and amounts.
The portal locks one public total, and the Zone credits every allocation atomically.
Existing single-recipient calls retain their ABI, encryption format, and behavior.

## Motivation

Funding 100 customer balances currently requires 100 deposits with public amounts.
A batch makes this one operation and hides how the total is split. It shares the
portal transfer, queue entry, and decryption proof across allocations; ciphertext
size and recipient minting remain linear in the number of allocations.

## Assumptions

- The call's `amount` includes the deposit fee. The portal deducts it before queuing,
  as in [existing deposits](https://github.com/tempoxyz/zones/blob/24a51dd432682596c55ba82186804f7af848fc81/specs/spec.md#deposits).
- Sequencers can see the decrypted list. Public observers cannot, but can infer
  the allocation count from ciphertext length. Existing liveness, data availability,
  and verifier trust assumptions remain unchanged.
- Portal, inbox, and proof changes activate together. An old inbox cannot process
  the new format, so accepting it before coordinated activation is invalid.

# Specification

## Interface and encoding

Keep `deposit`, its `depositEncrypted` alias, `DepositPayload`, `Deposit`, and
`DepositType.Deposit` unchanged:

```solidity
function deposit(
    address token, uint128 amount, uint256 keyIndex,
    DepositPayload calldata encrypted, address tempoRefundRecipient
) external returns (bytes32 newCurrentDepositQueueHash);
```

Select the format from ciphertext length `L`:

| Length | Plaintext | Work units |
|---|---|---|
| `64` | Existing recipient, memo, and padding | `1` |
| `1 + 36 * N`, `1 <= N <= MAX_BATCH_RECIPIENTS` | `0x01` followed by `N` allocations | `N` |

Each allocation is `recipient[20 bytes] || amount[16 bytes, unsigned big-endian]`.
The formats cannot overlap because `64 != 1 + 36 * N` for integer `N`.
Reject every other ciphertext length on Tempo before collecting funds or enqueuing.
The inbox requires the batch version byte to equal `0x01`; trailing data is invalid.

Batch recipients must be nonzero and amounts must be positive. Duplicate recipients
are allowed; process them in list order. Each batch mint uses a zero memo.
Accumulate amounts in `uint256` and require their sum to equal the queued net amount.
V1 has no per-recipient memos or callbacks.

## Encryption

Legacy 64-byte payloads retain their exact key derivation and empty AES-GCM AAD.
Batch encryption reuses secp256k1 ECDH and Chaum-Pedersen verification, with fresh
ephemeral key material and nonce for each encryption. Use the existing HKDF info
encoding, but replace its salt with the UTF-8 bytes `ecies-batch-deposit-v1`.

Batch AES-GCM AAD is the canonical `abi.encode` of:

```text
bytes32(keccak256("tempo-zone-batch-deposit-v1")),
uint256(parentChainId), uint256(zoneChainId), address(portal),
address(sender), address(token), uint128(netAmount), uint16(N),
uint256(keyIndex), address(tempoRefundRecipient)
```

Derive these values from the actual deposit and Zone configuration. Do not accept
sequencer-supplied plaintext or replacement context.

## Acceptance and fees

All existing pause, token, key, sender, refund-recipient, transfer-policy, and
ephemeral-public-key checks apply. The portal takes the caller's gross `amount`,
pays the deposit fee, and queues `netAmount = amount - fee` in one entry.
The existing minimum amount check against the deposit and quoted bounce-back fees applies.

Charge `N * FIXED_DEPOSIT_GAS * zoneGasRate` for a list of `N`
allocations. Keep `calculateDepositFee()` unchanged and add
`calculateDepositFee(uint16 allocationCount) returns (uint128 fee)` for batches.
The overload rejects zero or a count above the batch cap; arithmetic is checked.
Benchmark batch execution before approving the fee schedule.

The SDK submits `sum(allocations) + quotedFee` as the gross amount and binds
`sum(allocations)` in AAD. If the fee changes before inclusion, authentication or
sum validation fails and the net deposit bounces back; the upfront fee remains paid.

Queue encoding, deposit numbering, `DepositMade`, and its net-amount semantics
remain unchanged. A batch consumes one deposit number and one decryption entry.

## Execution and refunds

The inbox verifies and decrypts once, validates the whole list, then performs all
mints inside one rollback boundary with a bounded gas allowance. Each recipient
mint uses the existing token-policy checks. If any mint fails, including the last
mint, roll back every credit and log from that operation.

Invalid encryption, invalid allocations, or a mint failure enqueue one existing
deposit bounce-back for the entire net amount. Advance the queue once, with no
partial success or retries. Reserve enough gas outside the rollback boundary to
record failure, enqueue the refund, and advance the queue.

Existing aggregate refund fees, policy checks, and parked-refund behavior apply.
Malformed queue witnesses or missing/extra decryption entries still invalidate the
enclosing system transaction rather than becoming user refunds.

## Outstanding work

Retain TIP-1096's entry limit and add the same limit in work units. Legacy deposits
and internal withdrawal bounce-backs cost one unit; list payloads cost `N`, even
when invalid or destined to fail.

Track cumulative `depositWork` and `lastProcessedDepositWork` on the portal, and
`processedDepositWork` on the inbox. Before insertion require:

```text
depositWork - lastProcessedDepositWork + entryWork <= admissionLimit
```

Ordinary admission uses `230 - 20` units. Internal withdrawal bounce-backs may use
all 230. Before processing withdrawals, require capacity for every withdrawal to
bounce back in both entries and units. Only a legacy single-recipient callback
return may consume its existing reserved slot; list payloads use ordinary capacity.

Append `prevDepositWork` and `nextDepositWork`, both `uint64`, to
`DepositQueueTransition`. The proof checks the inbox pre/post counters and derives
every increment from the authenticated queue entries. Settlement requires the
previous counter to match the portal's settled counter, rejects regression or a
next counter above `depositWork`, and commits the extended transition in the
settlement certificate. Accepted settlement alone releases portal capacity.
Each full import must finish with `processedDepositWork == depositWork` read from
its authenticated Tempo root. Header-only imports advance neither work counter.
Counter overflow rejects insertion rather than wrapping.

Set `MAX_BATCH_RECIPIENTS` no higher than 210. Its final value and the 230-unit
budget require combined worst-case execution/proving measurements before approval,
including maximum token enablements, late mint failure, and refund handling.

## Activation and compatibility

Activate through a coordinated Tempo and Zone upgrade; the protocol version is
unassigned. Before activation, only the legacy format is valid. Historical execution
and existing direct callers retain the legacy encryption, fees, checks, and events.

At activation initialize portal work counters from `depositCount` and
`lastProcessedDepositNumber`, and the inbox counter from `processedDepositNumber`.
Every pre-activation entry costs one unit, so this preserves the pending backlog.
The upgraded proof authenticates these initial values against the existing cursors.

The deposit ABI stays compatible. The extended settlement transition changes the
`submitBatch`/verifier ABI and certificate encoding; settlement tooling must upgrade
with the portal, inbox, witness, and verifier before admitting list payloads.

# Tooling

SDKs accept a list of `{to, amount}`, compute its net total, quote the fee, and encrypt
the packed list. Existing single-recipient SDK calls need no change. Payload decoders
recognize both formats, and settlement encoders include the work counters.

# Observability

Keep Tempo event signatures unchanged. `DepositMade` records one net total and
ciphertext; allocation count is derived from its length. Existing processed-deposit
cursors record inclusion, not success.

On successful list processing, emit one existing Zone-side `DepositProcessed` per
allocation with the same deposit hash, its recipient and amount, and zero memo.
Emit no such events on failure; emit the existing `DepositFailed` once. Indexers
must allow multiple allocation events for one deposit hash. Existing bounce-back
events distinguish delivered refunds from parked refunds.

# Threat Model

Senders may submit malformed or oversized lists; public length checks, work limits,
fees, and deterministic validation bound their cost. Sequencers may supply incorrect
decryption data, but cannot redirect an authenticated list or forge credits under
the existing verifier assumptions. Issuers may change policy and make one recipient
fail, causing the entire deposit to bounce back.

Tempo observers learn sender, token, gross/net totals, count, timing, and refund
recipient. The split is encrypted; this TIP adds no padding or protection against
inference from outside information.

# Invariants

- Successful credits sum exactly to the queued net amount; a failed list credits zero.
- One queue entry is consumed once and produces at most one aggregate bounce-back.
- Invalid lists cannot stall the queue or release unprocessed work capacity.
- Legacy callers retain identical payload interpretation, fee, and failure behavior.

Required coverage includes both formats and their disjoint lengths; incorrect AAD,
version, recipients, amounts, and sums; duplicates; failure on the final mint;
mixed queue ordering; reserved capacity; authenticated work transitions; and an
activation with pending legacy entries. Success requires these behavioral checks
and worst-case budget measurements.
