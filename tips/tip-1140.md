# TIP-1140: Batched Zone Deposits

## Abstract

This TIP extends the existing Zone deposit interface to fund multiple recipients in a single deposit. The total amount remains public, while recipients, individual amounts, and memos are encrypted and processed within the Zone.

## Motivation

Funding multiple Zone accounts currently requires a separate deposit for each recipient, with each amount visible on Tempo. Batched deposits expose only the aggregate amount and use one portal transfer, queue entry, and decryption proof. The Zone still mints each allocation separately.

## Specification

### Interface and encoding

Keep the existing `deposit` interface, `depositEncrypted` alias, and `DepositPayload` unchanged. Ciphertext length distinguishes the existing format from a batch:

| Ciphertext length | Plaintext |
|---|---|
| `64` | Existing recipient, memo, and padding |
| `1 + 68 * N` | Version byte `0x01` followed by `N` allocations |

Each allocation is packed as:

```text
recipient   20 bytes
amount      16 bytes, unsigned big-endian
memo        32 bytes
```

The portal requires `1 <= N <= MAX_BATCH_RECIPIENTS` and rejects all other ciphertext lengths before collecting funds.

The inbox requires version `0x01`, nonzero recipients, and positive amounts. It sums amounts in `uint256` and requires the result to equal the queued net amount. Duplicate recipients are processed in list order. Omitted memos use `bytes32(0)`. Batches have no per-recipient callbacks.

### Encryption

Existing payload encryption remains unchanged.

Batches reuse secp256k1 ECDH and Chaum-Pedersen verification, with fresh ephemeral key material and a fresh nonce. HKDF retains the existing info encoding and uses the UTF-8 salt `ecies-batch-deposit-v1`.

AES-GCM additional authenticated data is the canonical `abi.encode` of:

```text
bytes32(keccak256("tempo-zone-batch-deposit-v1")),
uint256(parentChainId),
uint256(zoneChainId),
address(portal),
address(sender),
address(token),
uint128(netAmount),
uint16(N),
uint256(keyIndex),
address(tempoRefundRecipient)
```

The inbox derives this context from the authenticated deposit and Zone configuration.

### Fees and acceptance

Existing deposit checks apply. The portal transfers the gross `amount`, deducts the deposit fee, and queues the net amount in one entry.

The proposed initial fee is:

```text
batchDepositFee = N * FIXED_DEPOSIT_GAS * zoneGasRate
```

Keep `calculateDepositFee()` and add:

```solidity
function calculateDepositFee(
    uint16 allocationCount
) external view returns (uint128 fee);
```

The overload rejects zero or counts above the cap and uses checked arithmetic. The SDK submits the allocation total plus the quoted fee and authenticates the allocation total as the net amount.

If the fee changes before inclusion, authentication or sum validation fails and the net amount bounces back. The deposit fee remains paid.

A batch consumes one queue entry, deposit number, and decryption entry. Queue encoding and `DepositMade` remain unchanged.

### Execution and refunds

The inbox verifies and decrypts once, validates the entire list, then mints each allocation atomically within a bounded gas allowance. Existing token-policy checks apply to every mint.

If decryption, validation, or any mint fails, the batch credits nothing and produces one bounce-back for the entire net amount. All mint credits and logs are rolled back, and the queue advances once. There is no partial success or retry.

Reserve enough gas to record failure, enqueue the refund, and advance the queue. Existing refund fees, policy checks, and parked-refund behavior apply. Malformed queue witnesses or missing or extra decryption entries invalidate the enclosing system transaction.

### Compatibility

Activate through a coordinated Tempo and Zone upgrade. The portal must not accept batches before the inbox and verifier support them. Existing single-recipient deposits retain their encoding, encryption, fees, and behavior.

SDKs add support for lists of `{to, amount, memo}`. On success, the Zone emits one `DepositProcessed` per allocation with the same deposit hash. On failure, it emits one `DepositFailed` and no allocation success events.

## Invariants

- **Conservation:** A successful batch credits exactly the queued net amount. A state where total credits differ from that amount must be unreachable.
- **Atomicity:** A failed batch leaves all recipient balances unchanged by its mint operation and retains no allocation success events. A state where only part of a batch is credited must be unreachable.
- **Allocation integrity:** Each credit matches the recipient, amount, and memo at the corresponding position in the authenticated list. A state with an omitted, altered, or additional allocation must be unreachable.
- **Single consumption:** A consumed queue entry cannot produce further credits or bounce-backs. A state where the same batch has been applied twice must be unreachable.
- **Refund exclusivity:** A consumed batch either succeeds or produces one bounce-back for the entire net amount. A state containing both batch credits and a bounce-back, neither outcome, or multiple bounce-backs must be unreachable.

## Validation

Required coverage includes both formats, invalid encryption and allocations, duplicate recipients, fee changes, and failure on the final mint with all earlier credits rolled back.

Compare separate deposits with batches of 1, 10, and 100 recipients. Measure Tempo gas, Zone execution gas, proving time, witness size, and successfully credited recipients per second.

Finalize the recipient cap and fee schedule from these measurements, including worst-case mint failure and refund handling.
