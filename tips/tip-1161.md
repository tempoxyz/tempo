# TIP-1161: Access Key Policy Contracts

## Abstract

This TIP lets an account attach a policy contract to an access key. Before a transaction signed by that key runs, the protocol calls the policy once per top-level call, with a fixed budget of 50,000 gas per call. If any check fails, the transaction reverts and still pays its fee. A policy sees only top-level calls. It cannot read data the call encrypts.

## Motivation

An access key is a secondary key an account authorizes to sign for it; the root key is the account's own key. [TIP-1011](./tip-1011.md) scopes an access key by target and function selector. For TIP-20 `transfer` and `approve`, it can also restrict the first argument. It cannot restrict any other argument. That gap keeps backend services on external signers with their own policy engines instead of narrowly scoped access keys. Three common cases show it.

A backend that swaps stablecoins to pathUSD on the Stablecoin DEX needs `tokenIn` limited to an allowlist, `tokenOut` fixed to pathUSD, and `minAmountOut` close to `amountIn`. A key scoped to `swapExactAmountIn` can choose all three freely.

A backend that deposits into or withdraws from an existing Earn vault needs `receiver` and `owner` to be the account. A key scoped to `deposit` or `withdraw` can send shares or assets to any address.

A backend that withdraws from a zone needs `to` and `zoneFallbackRecipient` to be the account. A key scoped to `requestWithdrawal` can withdraw the full zone balance to any address.

This TIP adds one generic hook to the protocol. Each check is ordinary contract code that can ship without a protocol upgrade. A shared library of audited policies gives wallets and integrators named permissions.

## Assumptions

- **The account owner chooses and trusts the policy.** If the policy has a bug, the key can do what the bug allows, within its TIP-1011 scopes and spending limits.
- **Policies that matter are not upgradeable.** If a policy's owner can upgrade it, that owner controls what the key can do. The protocol does not detect upgradeability.

# Specification

## Overview

A Tempo transaction is a batch of **top-level calls**; calls those make are nested calls. A **policy** is a contract implementing `IAccessKeyPolicy`. A **policy check** is one read-only call to the policy's `checkCall` for one top-level call. The check passes when `checkCall` returns its own selector. Only the account's **key manager** can set or clear a key's policy: the caller the keychain's existing `ensure_admin_caller` check accepts. That is the root key, an admin key while [TIP-1049](./tip-1049.md) admin keys exist, or, for an account with a configuration commitment, its owner quorum ([TIP-1137](./tip-1137.md)).

The lifecycle, illustrated with the stablecoin swap key from [Motivation](#motivation):

1. The account authorizes a backend access key. The TIP-1011 scope allows `swapExactAmountIn` on the Stablecoin DEX. The policy is the shared `StableSwapPolicy` described in [Reusable policies](#reusable-policies), configured for this key with an allowlist of input tokens and pathUSD as the output token.
2. The backend signs a transaction with one call: `swapExactAmountIn(USDC, pathUSD, 1000e6, 999e6)`.
3. The transaction pool admits it without running the policy. A failed check still pays its fee, so the pool does not need to filter it.
4. Before the first call executes, the protocol runs the TIP-1011 checks, then the policy check. The policy decodes the arguments, finds USDC on the allowlist and the slippage within bounds, and returns `checkCall.selector`.
5. The swap executes.

If the backend's key leaks and the attacker signs a swap to another token, the policy check in step 4 fails. The transaction reverts before any call executes, and the account pays the fee.

The policy check is the authority boundary. A key with a policy can make only the top-level calls that the TIP-1011 scopes, the spending limits and the policy all allow.

## Reusable policies

Most policies are shared contracts. A shared policy is deployed once and holds a configuration per account and key, which it looks up from the `account` and `keyId` that `checkCall` receives. An account adopts one by writing its configuration to the policy and pointing its key at it. It does not deploy anything. Only very custom rules need a new contract.

A key's policy cannot be the target of that key's own calls; see [Running a policy check](#running-a-policy-check). Otherwise a key could rewrite its own configuration, since a shared policy sees `msg.sender == account` whichever key signed.

Illustrative shared policies for the use cases in [Motivation](#motivation):

| Policy | What it checks |
|---|---|
| `StableSwapPolicy` | On Stablecoin DEX swaps, `tokenIn` is in the account's allowlist, `tokenOut` is the configured output token, and `minAmountOut` is within a configured slippage of `amountIn`. |
| `VaultReceiverPolicy` | On vault `deposit`, `withdraw` and `redeem`, `receiver` and `owner` equal the account, and the vault is in the account's allowlist. |
| `ZoneWithdrawalPolicy` | On `requestWithdrawal`, `to` and `zoneFallbackRecipient` are the account or a configured address, and `token` is in the account's allowlist. |

Zones run only predeploys and keep their own `AccountKeychain`. A zone policy such as `ZoneWithdrawalPolicy` therefore ships as a zone predeploy in a zone upgrade, and the zone keychain must implement this TIP.

## Setting a policy

- The `KeyAuthorization` gains a trailing optional `policy: address` field after `allowed_calls`. `policy = None` is omitted. When `policy` is present and `allowed_calls = None`, `allowed_calls` is encoded as `0x80`, and that encoding is canonical in this case.
- An authorization with `is_admin = true` MUST NOT carry a `policy`, as TIP-1049 already requires for limits, scopes and expiry. Otherwise an admin key could authorize an unrestricted key inside its own transaction, which no policy check sees.
- `setKeyPolicy(keyId, policy)` sets or replaces the policy of an existing key. `policy = address(0)` clears it. Only the key manager may call it; any other caller reverts with `UnauthorizedCaller`.
- The policy is stored in one slot per `(account, keyId)`. Setting it costs one `SSTORE_SET` of key-authorization intrinsic gas.
- The protocol does not check the policy's code when it is set. An address without code fails every check.

## Running a policy check

Policy checks run in the metered phase before execution that TIP-1011 defines, after its call-scope checks pass. For every transaction signed by an access key, that phase reads the key's policy slot (one cold `SLOAD`, 2,100 gas). If the key has a policy, the protocol checks each top-level call in batch order and stops at the first failure:

1. If `target` is the key's policy, the check fails.
2. Charge `POLICY_CHECK_GAS` (50,000 gas) against the transaction's gas limit.
   If the remaining gas cannot cover it, the transaction fails as out of gas, with the same effects as a failed check.
3. Make a static call to `policy.checkCall(account, keyId, callIndex, callCount, target, value, input)` with a gas limit of `POLICY_CHECK_GAS`.
4. The check passes only if the call succeeds and returns exactly 32 bytes: `IAccessKeyPolicy.checkCall.selector` followed by 28 zero bytes, as Solidity encodes a `bytes4`.

The charge is the full `POLICY_CHECK_GAS` whatever the check uses. Gas the check leaves unused is not refunded. A fixed charge makes the cost of a check independent of the policy's code, so gas estimation is exact.

50,000 gas is a proposed value for review. It is enough for ABI decoding, several storage reads and one arithmetic comparison.

## Failure

A check that reverts, runs out of gas, or returns anything else fails. One failed check fails the whole transaction:

| Effect | Result |
|---|---|
| User calls | None execute. |
| Fee | Charged for gas used, including `POLICY_CHECK_GAS` for each check up to and including the failed one. |
| Nonce | Consumed. |
| Receipt | Status 0. Receipts do not carry revert data. |
| Tracing and simulation | Error `PolicyCheckFailed(callIndex)`, where `callIndex` is the zero-based position of the failed call in the batch. |

This matches TIP-1011 call-scope failures. Because a failed check is an execution failure, not an invalid transaction, the pool and block builders never run arbitrary policy code for free.

## Interfaces

```solidity
/// @notice Implemented by access key policies.
interface IAccessKeyPolicy {
    /// @notice Decides whether an access key may make one top-level call.
    /// @dev Called with STATICCALL and a gas limit of POLICY_CHECK_GAS.
    /// @param account The account that signed through the access key.
    /// @param keyId The access key's address, as in TIP-1011.
    /// @param callIndex Zero-based position of this call in the batch.
    /// @param callCount Number of top-level calls in the batch.
    /// @param target The call's target.
    /// @param value The call's value.
    /// @param input The call's full input, including the selector.
    /// @return magic IAccessKeyPolicy.checkCall.selector to allow the call.
    function checkCall(
        address account,
        address keyId,
        uint256 callIndex,
        uint256 callCount,
        address target,
        uint256 value,
        bytes calldata input
    ) external view returns (bytes4 magic);
}

/// Additions to IAccountKeychain.
interface IAccountKeychainPolicy {
    /// @notice Emitted when a key's policy is set, replaced or cleared.
    event KeyPolicySet(address indexed account, address indexed keyId, address policy);

    /// @notice A policy check failed for the top-level call at callIndex.
    error PolicyCheckFailed(uint256 callIndex);

    /// @notice Sets, replaces or clears (policy = address(0)) a key's policy. Key manager only.
    function setKeyPolicy(address keyId, address policy) external;

    /// @notice Returns the key's policy, or address(0) if it has none.
    function getKeyPolicy(address account, address keyId) external view returns (address policy);
}
```

# Compatibility

Existing keys get no policy at activation. Every access-key transaction pays one extra cold `SLOAD` to read the policy slot; keys without a policy are otherwise unchanged.

| Integration | What changes |
|---|---|
| Wallets and SDKs | Encode the new `policy` field when authorizing a key. Show the user which policy a key has. For library policies, show its parameters. |
| Gas estimation | Add 2,100 gas for every access-key transaction, plus `POLICY_CHECK_GAS` per top-level call for keys with a policy. |
| Payment lane ([TIP-1045](./tip-1045.md)) | Lane classification is stateless and cannot see a key's policy. Gas spent on policy checks counts toward the block's `general_gas_limit`, even for a transaction classified as a payment. |
| Transaction pool | No change. It does not run policy checks. |
| Policy library | The shared policies in [Reusable policies](#reusable-policies) should ship audited and non-upgradeable alongside this TIP. Adding a Tempo policy later needs no protocol upgrade; a zone policy needs a zone upgrade. |

# Observability

`KeyPolicySet` records each policy change. A failed check leaves a receipt with status 0. Tracing or simulating the transaction returns `PolicyCheckFailed(callIndex)`, which names the call that failed, and the policy's revert data.

# Threat Model

The main attack is a leaked access key used to move funds through a call its scopes allow. With a policy, the attacker must also pass `checkCall` for every top-level call.

| Actor | Capability and trust | Boundary check and failure consequence |
|---|---|---|
| Access key holder | Signs any transaction. | TIP-1011 scopes, spending limits and the policy check. A policy bug lets the key do what the bug allows. |
| Key manager | Sets and clears policies. | Only the key manager may call `setKeyPolicy`. A compromised key manager controls the account anyway. |
| Policy owner | Can change behavior if the policy is upgradeable. | None in the protocol. An upgradeable policy's owner controls what the key can do. |
| Transaction sender (spam) | Sends transactions that fail their check. | Each failed check still pays its fee. |

Residual risks:

- A policy sees only top-level calls. If the key may call a router, the policy must judge the router call's input, not what the router later does.
- A policy cannot read encrypted arguments, such as the recipient in a zone deposit or a zone withdrawal's `data`. Scoping those needs a change to the zone contracts, outside this TIP.
- All checks run before any call executes. A later call's check therefore sees state from before the batch, and earlier calls in the same batch can change that state before the later call runs. A policy that depends on state can use `callIndex` and `callCount` to allow only single-call batches.

# Invariants

- A transaction signed by a key with a policy executes no user call unless every top-level call's check returned the success value.
- Each check charges exactly `POLICY_CHECK_GAS`.
- A failed check consumes the nonce, charges the fee and executes no user call.
- A check cannot change state.
- Only the key manager can change a key's policy.
- A key can never call its own policy.
- No admin key has a policy.

Tests must cover: a policy that reverts, returns a wrong value, returns extra bytes, exceeds `POLICY_CHECK_GAS`, or tries to write state; an address without code; a batch whose second call fails, where later checks do not run; a call whose target is the key's own policy; an admin authorization carrying a policy; a policy with no call scopes, for RLP encoding; and clearing a policy.
