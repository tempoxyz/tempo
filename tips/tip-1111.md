# TIP-1111: Configurable Account Access Keys

## Abstract

This TIP lets configurable accounts grant and receive access-key permissions. The parent account controls the funds and the grant. The delegate signs transactions within that grant's permissions, using either a primitive key or its current owner quorum.

AccountKeychain keeps the existing permissions, expiry, spending limits, and counters. Owner rotation preserves grants. Each configurable quorum uses at most eight primitive signatures; a combined grant-and-use transaction can require two quorums, plus an optional fee-payer signature.

Admin access keys can spend without limits and manage the parent's access keys. Delegates cannot change the parent's owners. A configurable delegate must sign with its own owner quorum; its access keys cannot sign for it. A primitive delegate that migrates to configurable ownership keeps its existing grants.

## Motivation

A treasury needs to give an employee or a smaller multisig limited spending access without giving it unrestricted control. Users who already rely on access keys need this capability before migrating to configurable accounts.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| [TIP-1011](./tip-1011.md) continues to define permissions and lifecycle, with grant data in AccountKeychain. | A different lifecycle could change the permissions or spending state this TIP preserves. |
| [TIP-1112](./tip-1112.md) root disablement activates with configurable accounts and migration at T14. | A migrated delegate's old root could bypass its current owners. |

# Specification

## Overview

The **parent** is the account whose funds are being accessed. The **delegate** is the key or account receiving access. A **grant** records the delegate's permissions on that parent.

A regular account's **root key** is its main signing key. A configurable account uses an **owner quorum**: owners whose combined weights meet its approval threshold. After migration, the original root key has no independent authority.

1. **Grant:** the parent authorises access using its root key or owner quorum. An active admin access key on the parent can also authorise access.
2. **Sign:** the delegate approves a transaction using its primitive key or current owner quorum.
3. **Use:** validate the delegate and grant restrictions, then execute as the parent account.

| Parent | Supported delegate |
|---|---|
| Primitive account | Primitive key or configurable account |
| Configurable account | Primitive key or configurable account |

For example, treasury A grants delegate B $100/day. B has three owners with weight one and a threshold of two. Two owners approve a $40 payment; the grant has $60 remaining for that day. A's owners do not sign the payment. If B grants laptop key C access to B's funds, C cannot use that grant to spend A's funds. B's owners must sign directly.

The grant controls what B may do; B's configuration controls who can approve it. This TIP extends native transaction authorisation. It does not add configurable delegates to the on-chain keychain verification helpers.

## Delegate eligibility

For a configurable delegate:

- Its own primitive owners must sign directly.
- Its access keys cannot sign on its behalf.
- It cannot have EVM code or EIP-7702 delegation.
- Reject a grant where the configurable delegate is the parent itself.

## Granting access

A configurable-delegate grant MUST store the delegate account's address as `key_id`. AccountKeychain identifies it with the [configurable-account key type](#interfaces).

### Authorising the grant

- Register access through the existing transaction-level `key_authorization` field.
- Direct AccountKeychain authorization selectors support configurable parents from activation.
- From activation, direct selectors retain existing caller permissions and apply the same delegate-type and self-grant checks.
- The authorization signature is a byte-encoded `TempoSignature::Primitive` or `TempoSignature::ConfigurableAccount`.
- Reject `Keychain` signatures in that field.
- Primitive authorisations keep their existing encoding and authority rules, subject to TIP-1112.
- Admin access keys cannot have spending limits, call scopes or expiry.

The signer of `key_authorization` must be the parent or an active admin access key on that parent. Either may be primitive or configurable. For an admin-signed grant, `account` must identify the parent whose funds the new key can access. The same admin must also sign the transaction carrying that grant.

A configurable signer uses its own direct owner quorum to sign:

```text
configurable_account_digest(key_authorization.signature_hash(), signer_account, config_version)
```

- The signature carries the signing account's address and full configuration, as defined in TIP-1114.
- A version-zero configurable signer registers its configuration under TIP-1114 when it authorises a grant.
- Existing expiry, replay, permission, and witness-burning checks still apply. A burned authorization witness cannot be reused.
- Non-admin delegates cannot manage the parent's keys; no delegate can rotate the parent's owners.

### Admin access keys

Existing [admin access-key permissions](./tip-1049.md) remain unchanged. An admin can spend the parent's funds without limits. It can authorise ordinary or admin keys, revoke any access key, and change ordinary keys' spending limits and call scopes on that parent. These actions need no further approval from the parent's root key or owner quorum. Admin access cannot be restricted to device onboarding or recovery.

Each key an admin authorises receives its own grant on the parent. If treasury A appoints B as an admin and B authorises C on A, C gets a separate grant. Once that grant is registered, C can use it without B's signature.

## Using access

Use the existing V2 keychain signature format:

```text
0x04 || parent_account || access_key_signature
inner_digest = keccak256(0x04 || tx.signature_hash() || parent_account)
```

- A primitive delegate signs `inner_digest` normally.
- A configurable delegate provides a TIP-1114 signature over `configurable_account_digest(inner_digest, delegate_account, delegate_config_version)`.
- Reject a keychain signature inside another keychain signature, as required by the [direct-signing rules](#delegate-eligibility).
- The recovered or named key ID must match the grant. A primitive signature must match the grant's stored type. From T14, if the key ID has a nonzero configuration commitment, the grant accepts only a configurable signature from that account's current owner quorum, whatever type it stores; its retired root is rejected under TIP-1112.
- `verifyKeychain` and `verifyKeychainAdmin` do not accept configurable delegates; see [on-chain signature verification](./tip-1114.md#on-chain-signature-verification).

### Validation and execution

1. Validate the delegate. For a primitive delegate, check its signature and authority. For a configurable delegate, check its configuration at this transaction's position in the block and verify that its primitive-owner approvals meet its threshold. A nonzero delegate configuration hash requires its current owner quorum under TIP-1112.
2. Enforce the selected grant's restrictions.
3. Execute as the parent account.

Ordinary access-key use does not need another signature from the parent's owners. A configurable delegate using its initial configuration is registered under TIP-1114 before calls execute.

## Grant and use in one transaction

- A transaction can authorize an access key and use it immediately.
- The grant signature and the transaction's outer signature are independent approvals. Both must pass validation.
- A configurable parent with code or EIP-7702 delegation is invalid.
- This TIP does not enable multisig signatures in subblocks or authorization lists.

## Owner rotation and revocation

Parent owner rotation preserves existing grants, including their permissions, expiry, limits, spending counters, and revocation state.

Only the parent's root key, current owner quorum or an active admin access key on that parent can revoke its grants. They can revoke any grant, including another admin's access or a key that another admin authorised. Revocation does not require approval from whoever authorised the key.

Revoking an admin leaves the grants it created unchanged. Revoke each unwanted grant separately.

Delegate owner rotation preserves the parent's grant, limits, and spending counters. The new owners can use the same grant. Subsequent use requires the delegate's current owner quorum; signatures under its previous configuration are invalid.

## Failure and rollback

Grant creation and initial registration follow [TIP-1114's execution boundary](./tip-1114.md#failure-behavior):

| Outcome | State effects | Next action |
|---|---|---|
| Inline grant signature or outer signature fails validation | The transaction is invalid. No registration or grant from this transaction is committed. | Correct the failed approval against the current configuration and grant state. |
| A valid, included transaction's execution reverts or halts | Initial registrations and an inline `key_authorization` persist. Grants made through precompile calls roll back with the other user-call changes. Normal fee and nonce rules apply. | Check which grant exists before retrying; a burned authorization witness cannot be reused. |

Expiry, permissions, spending accounting, and revocation retain TIP-1011's rules.

## Bounded work and gas

Count signature checks before performing cryptography.

- Each multisig quorum can contain at most eight primitive signatures.
- A transaction can contain at most two quorums: one for the grant and one for the transaction itself.
- The combined limit is sixteen primitive verifications across the outer signature and any signed key authorization.
- An optional secp256k1 fee-payer signature adds at most one more verification.

The combined verification bound remains a proposal. Confirm it with worst-case benchmarks before approval.

**Gas charges**

- Use TIP-1114's `V` cost for each multisig witness instead of that role's primitive-signature cost.
- Subtract the ordinary outer base-signature charge once. Do not subtract it from signed key authorizations.
- Keep the existing keychain processing and policy charges.
- Charge normal account access for additional delegate accounts.
- Add TIP-1114's initial registration cost for each unregistered configurable signer, once per account.
- Check total intrinsic gas and whether fees are affordable before cryptography.
- Do not add configuration SLOAD charges.

## Changes to other components

### Migration compatibility

From T14, a primitive delegate that migrates under [TIP-1113](./tip-1113.md) can use its existing grants through its current owner quorum. Its retired primitive root cannot use them. Migration preserves each grant's permissions, expiry, limits, spending counters, and revocation state; no reauthorisation is required.

## Interfaces

AccountKeychain adds `ConfigurableAccount = 3` to its key-type enum. Primitive key-type values 0, 1, and 2 MUST remain unchanged.

Before activation, key type `3` and `TempoSignature::ConfigurableAccount` key authorisations MUST remain rejected, including during historical replay.

# Tooling

- Show the parent, delegate, permissions, and owners needed to sign. Warn that admin access grants unrestricted spending and key management.
- Warn that `verifyKeychainAdmin` rejects configurable admin access-key signatures, even though those admins can authorise native transactions.
- Track configurable delegates by their current configuration.
- Recovery tooling must show active grants, including legacy and admin grants, and support [revocation per grant](#owner-rotation-and-revocation). Owner rotation or revoking an admin must not be shown as revoking other grants.
- Revalidate affected transactions after configuration changes, grant revocation, or reorgs.

# Observability

| Action | Evidence |
|---|---|
| Grant or revoke access | Existing AccountKeychain authorization, revocation, and witness events, together with the grant's current state. Events and grant state do not identify the authorising key. |
| Use access | The transaction result and existing spending accounting. The new key type identifies a configurable delegate; no per-use event is added. |
| Rotate a delegate's owners | Its current configuration commitment and TIP-1109 update events. The parent's grant and spending counters remain unchanged. |

To attribute grants, recover the authenticated signer of inline `key_authorization` or the execution authority of direct AccountKeychain calls from transaction data and traces, not merely the parent `tx.from`. Follow admin-created admins transitively. If history or attribution is incomplete, mark it unknown; tooling must not claim exhaustive cleanup.

Execution failure does not establish that an inline grant was removed. Inspect grant state using the [rollback rules](#failure-and-rollback) before preparing another authorization.

# Threat Model

Delegation limits a delegate's authority to the selected grant for one parent account.

| Actor | Trust |
| --- | --- |
| Parent's root key / owner quorum | Trusted to choose the delegate and its permissions. Compromise can create unwanted grants or revoke legitimate ones. |
| Ordinary delegates | Can spend or call within the grant's permissions, limits, and expiry. They cannot manage the parent's keys, rotate its owners, combine unrelated grants, or sign through their own access keys. |
| Admin delegates | Trusted to spend without limits and manage access-key grants. Compromise can drain funds or create additional admins. Cannot rotate the parent's owners. |
| Configurable delegate's owners | The current quorum controls use of the grant. Rotating that quorum transfers access to the new owners without resetting the parent's limits or spending counters. |
| Wallets | Trusted to show the parent, delegate, and granted permissions. Misrepresenting those fields can lead the parent to approve broader access than intended. |

Owner rotation does not revoke compromised grants. Identify and revoke unwanted keys, but do not present per-key revocation as guaranteed recovery from an active admin compromise. If exhaustive cleanup cannot be established, move remaining funds to a fresh account and stop using the compromised address; the attacker may race those transfers too.

# Invariants

- An included transaction registers every configurable signer, including a parent granting access and a delegate using it, even if execution fails.
- Only the parent's current root key, direct owner quorum or an active admin access key can manage its access-key grants.
- Ordinary access-key grants provide no key-management authority. No access-key grant provides owner-rotation authority.
- Revoking an admin key does not revoke keys it authorised.
- Parent owner rotation preserves grants, permissions, expiry, limits, spending counters, and revocation state.
- Delegate rotation preserves grant permissions.
- Delegate rotation preserves spending counters.
- Ordinary use requires only the delegate's approval, not a second parent quorum.
- The grant and validation rules apply to every supported parent/delegate combination, including version-zero accounts and combined grant-and-use transactions.
- Combined grant-and-use transactions perform at most sixteen primitive verifications across the grant and outer signatures.
- An optional secp256k1 fee-payer signature adds at most one verification.
