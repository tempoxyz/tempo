# TIP-1111: Configurable Account Access Keys

## Abstract

A configurable account can delegate limited authority to a primitive key or another configurable account. A configurable account can also serve as an access key for an existing primitive account. Owner rotation and access-key permissions remain separate.

## Motivation

A treasury can require a large quorum for unrestricted ownership while allowing an employee, or a smaller multisig, to spend within defined limits. Existing access-key users need this support before migrating to configurable accounts.

## Assumptions

[TIP-1011](./tip-1011.md) continues to own expiry, scopes, spending limits, revocation, and admin permissions. Access-key state stays in AccountKeychain; this TIP does not move it into the configuration hash. [TIP-1112](./tip-1112.md) prevents retired primitive roots from bypassing configured authority.

## Threat Model

A delegate is not an owner. Nested delegation must not create recursive validation, merge unrelated policies, or multiply the verification budget. The account trusts only its selected active access-key grant and that key's current authority.

# Specification

## Supported relationships

Both primitive and configurable accounts can grant access to primitive or configurable keys. A configurable delegate signs using its direct primitive-owner quorum, not its own access keys. Multisig-as-owner nesting remains prohibited. For configurable delegation, reject a grant to the same account and reject code-bearing or EIP-7702-delegated key accounts.

Only the grant on the account being accessed applies. For example, if treasury A grants multisig B a daily limit, B's quorum signs for A and A's grant supplies the restrictions. Access keys granted by B are not consulted.

## Granting access

At T13, add `Multisig = 3` to AccountKeychain's key-type enum; existing primitive values 0, 1, and 2 are unchanged. A multisig grant stores the delegate account address as `key_id`. It does not snapshot that account's owners: later key rotation changes who can exercise the same grant, without resetting its limits.

Registration uses existing transaction-level `key_authorization`; legacy direct authorization selectors remain disabled under TIP-1099. Its signature field becomes a byte-encoded `TempoSignature::Primitive` or `TempoSignature::Multisig`, never `Keychain`. Primitive authorizations retain their encoding and existing authority rules. A configurable parent requires its direct owner quorum over:

```text
multisig_digest(key_authorization.signature_hash(), parent_account, config_version)
```

The signature carries the parent's full TIP-1114 witness, with its account matching the authorized account. Version-zero parents can grant access without writing a commitment. Existing authorization expiry, witness-burning, replay, and permission checks still apply. No delegate, including an admin key, can rotate the parent's owners.

## Using access

Use the existing V2 keychain envelope:

```text
0x04 || parent_account || access_key_signature
inner_digest = keccak256(0x04 || tx.signature_hash() || parent_account)
```

A primitive delegate signs `inner_digest` normally. A configurable delegate supplies a TIP-1114 signature over `multisig_digest(inner_digest, delegate_account, delegate_config_version)`. Reject nested keychain envelopes. The signature type and recovered/named key ID must match the grant.

Validate the delegate against its current block-position commitment and its own primitive quorum, then enforce the selected grant's restrictions. Execute as the parent account. Do not require the parent's owner quorum for ordinary use. A primitive grant whose key ID now has a nonzero commitment cannot use the retired primitive root; the parent must explicitly authorize that account as a multisig delegate.

Authorize-and-use in one transaction remains supported. The grant signature and outer signature are independent approvals and each must validate. A configurable parent with code or delegation is invalid. Subblocks and authorization lists do not gain multisig support through this TIP.

## Bounded work and gas

Before cryptography, count primitive verifications across the outer signature, its direct owner signatures, and any signed key authorization. Each multisig quorum is limited to eight primitive signatures; at most two such quorums may be present, for a combined limit of sixteen primitive verifications. The existing optional secp256k1 fee-payer verification is additional, at most one. Never recurse into a delegate's access keys or owners' accounts.

Ordinary delegate use verifies only the delegate, at most eight signatures. The sixteen-signature limit is this draft's T13 bound for an independent grant plus use, not a change to T12's eight-signature bound. It permits an eight-signature parent to authorize an eight-signature delegate without recursive work. Benchmark the combined worst case before T13 approval.

Charge TIP-1114's `V` for each multisig witness instead of that role's primitive verification term. Subtract the ordinary outer base-signature charge only once; signed key authorizations get no subtraction. Keep existing keychain processing and policy charges, and charge normal account access for additional delegate accounts. Check total intrinsic gas and affordability before cryptography. There are no nested-owner gas terms or configuration SLOADs.

# Tooling

Show the parent, delegate, restrictions, and signing quorum separately. Follow current delegate configurations and revalidate pending transactions after parent/delegate changes, grant revocation, or reorgs. Do not claim stateless signature recovery proves an active grant.

# Observability

Retain existing AccountKeychain authorization, revocation, and witness events; the key type distinguishes configurable delegates. No new event is needed for each use. Existing limit accounting remains authoritative.

# Invariants

Test all four parent/delegate combinations, initial witnesses, authorize-and-use, owner rotation without resetting grant counters, revoked/expired keys, scopes and spending limits, aggregate limits, rejected recursion, and inability of ordinary or admin delegates to change parent ownership.
