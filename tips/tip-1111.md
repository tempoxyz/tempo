# TIP-1111: Configurable Account Access Keys

## Abstract

Configurable accounts can use access keys in both directions:

- Give a primitive key or another configurable account limited access to their funds.
- Act as an access key for an existing primitive account.

Changing owners and changing access-key permissions remain separate operations.

## Motivation

A treasury can require a large owner quorum for unrestricted control while giving an employee or a smaller multisig limited spending access.

Users who already rely on access keys need this feature before migrating to configurable accounts.

## Assumptions

- [TIP-1011](./tip-1011.md) still defines expiry, call scopes, spending limits, revocation, and admin permissions.
- Access-key data stays in AccountKeychain. It is not moved into the configuration hash.
- [TIP-1112](./tip-1112.md) prevents a retired root key from bypassing the account's configured owners.

## Threat Model

- A delegate receives only the permissions in its access-key grant. It does not become an owner.
- Using one grant must not combine it with unrelated policies.
- Delegation must not create a chain of recursive signature checks.
- Validation must check that the selected grant is active and that its delegate still controls the signing key or account.

# Specification

## Supported relationships

The **parent** is the account whose funds are being accessed. The **delegate** is the key or account receiving access.

| Parent | Supported delegate |
|---|---|
| Primitive account | Primitive key or configurable account |
| Configurable account | Primitive key or configurable account |

For a configurable delegate:

- Its own primitive owners must sign directly.
- Its access keys cannot sign on its behalf.
- It cannot have EVM code or EIP-7702 delegation.
- Reject a grant where the configurable delegate is the parent itself.

Multisigs still cannot sign as owners of other multisigs.

**Example:** Treasury A gives multisig B a daily spending limit.

- B's owners sign the transaction.
- A's grant determines how much B can spend.
- Access keys created by B are not used or checked.

## Granting access

**Identifying the delegate**

- T13 adds `Multisig = 3` to AccountKeychain's key-type enum.
- Existing primitive key-type values 0, 1, and 2 do not change.
- A multisig grant stores the delegate account's address as `key_id`.
- The grant does not store a copy of the delegate's owners.
- If the delegate rotates its owners, the new owners can use the same grant. Its spending counters and limits do not reset.

**Authorizing the grant**

- Register access through the existing transaction-level `key_authorization` field.
- The old direct authorization selectors remain disabled under TIP-1099.
- The authorization signature is a byte-encoded `TempoSignature::Primitive` or `TempoSignature::Multisig`.
- Reject `Keychain` signatures in that field.
- Primitive authorizations keep their existing encoding and authority rules.

A configurable parent needs its direct owner quorum to sign:

```text
multisig_digest(key_authorization.signature_hash(), parent_account, config_version)
```

- The signature carries the parent's full configuration, also called its witness, as defined in TIP-1114.
- The account in that signature must match the account granting access.
- A version-zero parent can grant access without storing a configuration hash.
- Existing expiry, replay, permission, and witness-burning checks still apply. A burned authorization witness cannot be reused.
- No delegate can rotate the parent's owners, even if the delegate has admin permissions.

## Using access

Use the existing V2 keychain signature format:

```text
0x04 || parent_account || access_key_signature
inner_digest = keccak256(0x04 || tx.signature_hash() || parent_account)
```

- A primitive delegate signs `inner_digest` normally.
- A configurable delegate provides a TIP-1114 signature over `multisig_digest(inner_digest, delegate_account, delegate_config_version)`.
- Reject a keychain signature inside another keychain signature.
- The signature type and the recovered or named key ID must match the grant.

**Validation and execution**

First validate the delegate:

- For a primitive delegate, check its signature and authority.
- For a configurable delegate, check its configuration at this transaction's position in the block.
- Verify that the configurable delegate's primitive-owner approvals meet its threshold.

Then enforce the selected grant's restrictions and execute as the parent account.

Ordinary access-key use does not need another signature from the parent's owners.

If a primitive delegate's key ID now has a nonzero configuration hash:

- Its retired primitive root cannot use the old grant.
- The parent must explicitly authorize that account as a multisig delegate.

**Grant and use in one transaction**

- A transaction can authorize an access key and use it immediately.
- The grant signature and the transaction's outer signature are independent approvals. Both must pass validation.
- A configurable parent with code or EIP-7702 delegation is invalid.
- This TIP does not enable multisig signatures in subblocks or authorization lists.

## Bounded work and gas

Count signature checks before performing cryptography.

- Each multisig quorum can contain at most eight primitive signatures.
- A transaction can contain at most two quorums: one for the grant and one for the transaction itself.
- The combined limit is sixteen primitive verifications across the outer signature and any signed key authorization.
- An optional secp256k1 fee-payer signature adds at most one more verification.
- Never follow a delegate's access keys or an owner's account to find another quorum.

Ordinary access-key use checks only the delegate, so it needs at most eight signatures.

The sixteen-signature limit is a proposed T13 bound for granting and using access together. It allows an eight-signature parent to authorize an eight-signature delegate. It does not change T12's limit. Benchmark this combined worst case before approving T13.

**Gas charges**

- Use TIP-1114's `V` cost for each multisig witness instead of that role's primitive-signature cost.
- Subtract the ordinary outer base-signature charge once. Do not subtract it from signed key authorizations.
- Keep the existing keychain processing and policy charges.
- Charge normal account access for additional delegate accounts.
- Check total intrinsic gas and whether fees are affordable before cryptography.
- Do not add nested-owner gas terms or configuration SLOAD charges.

# Tooling

- Show which account is being accessed, who receives access, and what restrictions apply.
- Show which owners must sign for a configurable delegate.
- Track the delegate's current configuration.
- Revalidate pending transactions after changes to the parent or delegate, grant revocation, or a reorg.
- Recovering a signer address without checking state does not prove that its grant is active.

# Observability

- Keep the existing AccountKeychain authorization, revocation, and witness events.
- The key type identifies a configurable delegate.
- No new event is needed for each use.
- Existing spending-limit accounting continues to track usage.

# Invariants

Tests must cover:

- All four parent/delegate combinations.
- Grants using an initial configuration.
- Granting and using access in one transaction.
- Owner rotation without resetting spending counters.
- Rejection of revoked and expired keys.
- Enforcement of call scopes and spending limits.
- The combined verification limit.
- Rejection of recursive delegation.
- Ordinary and admin delegates being unable to change parent ownership.
