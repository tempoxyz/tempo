# TIP-1128: Native Earn Payment Lifecycle

## Abstract

This proposal makes registered Earn adapter accounts native payment endpoints at their existing addresses. Deposits, redemption, asynchronous claims, fee-share claims, and spending from Earn execute with TIP-1125's transaction-owned EVM2 call budget in the payment lane. Share balances remain nonrebasing; venue yield and losses change the redeemable assets per share. Activation requires an audited legacy registry, historical replay, a scheduled fork, and a combined Earn and Zone devnet with zero general-lane payment usage.

## Motivation

The current Earn adapter calls TIP-20 assets and shares and a venue engine. A shell that cannot make external calls must route those operations through general EVM execution. EVM2 allows a native adapter to make paid child calls while preserving the existing adapter's custody, accounting, and asynchronous redemption semantics. TIP-1084 describes the native shell; this TIP specifies the payment state transitions and migration necessary to replace the execution path.

## Assumptions

- TIP-1125 charges all native, engine, token, policy, and callback work against one transaction reservation. Reentry and nested Zone operations cannot acquire a second reservation.
- The deployed `VaultAdapter`, its ERC-1967 proxy, engine interfaces, TIP-20 share token, and fee configuration at the activation block are the legacy source of truth. No asset, share, or venue position is silently reminted or transferred during activation.
- Each admitted engine has a registered code identity and capability set. A venue that changes implementation or asset identity is suspended until its new identity is approved.
- TIP-20 transfer policy, issuer roles, allowance, and pause state are enforced in the child token calls at execution time.

## Threat Model

An attacker can forge an adapter-looking address, deploy a proxy with matching prefix, substitute an engine, return malformed engine data, reenter through a token or engine, request the same async claim twice, or make a callback consume unbounded work. Venue assets may gain or lose value between transactions. Administrators may change fees, pause deposits, or migrate an engine. These actions must not let a payment selector bypass identity checks, resource limits, token policy, or accounting. Registered engine code is trusted only for its stated asset and capability interface, not for free execution or arbitrary payment-lane admission.

# Specification

## Fork, identity, and dispatch

Activation follows the EVM2-only execution fork and TIP-1125. Before activation, replay uses the historical adapter proxy and engine behavior. After activation, a payment call reaches native execution only when the requested address is an initialized ERC-1967 adapter proxy in the onchain Earn registry, its runtime and implementation identity match the approved manifest, its fixed asset, share token, and engine match its registration, and its share token has the adapter's exclusive issuer role. An address prefix, ABI selector, event, or factory prediction alone confers no authority.

The current `EarnFactory` emits `EarnStackDeployed` but does not store a list of adapters. Before scheduling, an activation manifest MUST enumerate deployed stacks from canonical factory receipts, reconcile each against state at the fork parent, publish a commitment and audit output, and permit bounded per-account registration with a commitment proof. Registration cannot scan historical logs while executing a block. A new native factory MUST register newly deployed stacks atomically; deployment via the old unregistered factory after activation cannot enter the payment lane. Mutable governance and emergency selectors can use the historical proxy path and general lane; a payment selector cannot fall back there after native admission fails. All transaction admission surfaces, including pool, builder, validator, RPC estimation, and prover, use the same stateful fork-aware classifier.

Native payment selectors retain the deployed ABI and events for `accrueFees`, `claimFeeShares`, `deposit`, `depositShares`, `contribute`, `redeem`, `withdrawExact`, `requestRedeemAsync`, `finalizeRedeem`, and `cancelRedeemAsync`. The new `spendFromEarn(uint256 shares,address assetReceiver,uint256 minAssets,bytes32 paymentReference)` burns the caller's Earn shares, redeems the resulting assets synchronously, transfers the asset to the receiver, and emits `EarnSpent(address indexed owner,address indexed receiver,uint256 shares,uint256 assets,bytes32 indexed paymentReference)`. The call reverts if the engine lacks synchronous redemption, if output is below `minAssets`, or if TIP-20 policy rejects the receiver. `paymentReference` is a public correlation value, not authority. A registered Zone gateway may call the same selector with shares it owns, so an Earn-to-Zone composition remains one payment transaction and one budget.

`finalizeRedeem` is admitted only from the registered engine's exact identity and approved callback selector. An arbitrary engine transaction does not receive blanket payment-lane status: an engine-specific, bounded native settlement entrypoint or narrow callback capability must be registered before its claim can be finalized in the payment lane. Its proof of completed payout, engine-to-adapter asset transfer, and adapter forwarding execute atomically. A general EVM wrapper around a native call is not sufficient to classify the whole transaction as payment-lane work.

## Vault state and synchronous operations

The adapter retains `asset`, `shareToken`, `engine`, `shareScale`, `anchorEngineShares`, `anchorSupply`, `highWaterMark`, `targetBase`, `targetStartedAt`, the current fee configuration, five fee remainders per configuration, claimable fee shares, pending claims, and all existing role and pause fields at their deployed storage slots. A native implementation MUST provide storage reads and writes equivalent to the deployed proxy at the same address. The first native payment transaction does not reset an anchor or infer a new exchange rate from total supply.

Every value-changing operation checkpoints accrued fees before changing user principal. Deposit pulls exactly `assets` from caller to adapter, approves and calls the engine, measures venue shares received, converts those shares using the current anchor, enforces `minShares` and the legacy one-basis-point conversion-loss bound, mints the resulting TIP-20 Earn shares to `receiver`, and reanchors at rest. `depositShares` pulls venue shares directly only when the engine advertises that capability and mints proportionate Earn shares. `contribute` requires positive existing share supply, adds backing without minting contributor shares, reanchors, then accrues value gained after the contribution. Deposit pause gates both deposit selectors; the other operations retain their deployed pause behavior.

`redeem` pulls and burns the caller's Earn shares, maps them to venue shares, invokes synchronous engine redemption, enforces `minAssets`, and reanchors. `withdrawExact` previews venue shares, rounds the Earn shares required upward, enforces `maxShares`, calls exact engine withdrawal, burns only the shares actually required, checks residual backing, and reanchors. `spendFromEarn` follows `redeem` accounting, then sends the received asset to `assetReceiver`; failure of any child call rolls back the burn, engine effect, token transfer, fee checkpoint, logs, and native storage writes as one EVM2 frame. A caller can spend only shares it owns or shares obtained through ordinary TIP-20 allowance transfer before entry; a gateway cannot debit a third-party Earn balance by passing that party as an argument.

## Yield and fees

Active NAV is the engine's currently redeemable assets for active venue shares. Pending redemption value is excluded. Earn token balances do not rebase on venue gain or loss. The active conversion anchor scales venue shares to outstanding Earn token supply and is restored after each operation; zero-supply reset follows deployed empty-anchor behavior.

Fees accrue on positive value above the high-water mark and the configured linear target measured over a 365-day year. The five configured recipient slots retain fractional remainders across accruals. When `0 < feeAssets < activeAssets`, newly minted fee shares equal `floor(feeAssets * supply / (activeAssets - feeAssets))`; configured allocations use the deployed rounding and give the final nonzero slot the residual. A subshare positive accrual can advance the high-water mark without minting a share. Loss alone cannot mint fees. `claimFeeShares` transfers only previously credited, already minted shares and decrements the claimable amount; it does not create new supply. Native reads, fee previews, and writes use the exact deployed integer widths and rounding directions. Fee configuration and guardian changes retain their historical authorization and are charged if invoked through native code.

## Asynchronous redemption and migration

`requestRedeemAsync` checkpoints fees, burns the caller's shares once, asks the engine for a request ID, and records receiver, requester, burned Earn shares, venue shares, request value, high-water value, target value, fee configuration ID, request time, and open status. A duplicate request ID fails. Requested venue shares leave active NAV. Engine-only `finalizeRedeem` closes the request once, decrements pending counters, forwards the engine's asset payout already held by the adapter to the stored receiver, and cannot burn again. Its optional callback failure is ignored as in the deployed adapter, but the callback still consumes paid work and remains bounded. `cancelRedeemAsync` is restricted to requester or janitor, measures venue shares returned by the engine, computes pending fees using the request's snapshotted terms and remainders, remints the caller's active shares subject to `minReceiverShares`, credits fee shares, reanchors, and closes the request once.

At activation, every open request remains associated with its original engine, recipient, fee configuration, and request ID; it is neither automatically finalized nor canceled. The activation reconciler compares each request and aggregate pending count to pre-fork state. Engine migration retains the deployed operator and guardian rules, requires no open requests, the same asset, and an approved new engine capability and code identity. It moves custody atomically, retains Earn supply, and reanchors. A deployment whose migration mode forbids operator migration cannot gain it through native dispatch.

## Resource accounting and atomicity

The adapter reserves intrinsic calldata, identity and storage reads, TIP-20 calls, policy checks, engine capability and accounting calls, fee math, writes, logs, and bounded callback work before child execution. Child EVM2 calls consume the parent transaction's remaining execution and state-work budget, including cold/warm effects, failure paths, returndata copy, and nested precompiles. Returned data and `engineData` have hard byte caps. Numeric limits and activation schedule are intentionally unspecified until measured on the mixed workload: the fork MUST publish enforceable calldata, child-call count, depth, returndata, engineData, and aggregate execution/state-work ceilings, and demonstrate failure within those limits. A failed child call cannot commit a partial mint, burn, custody transfer, pending claim, or fee credit.

# Tooling

SDKs expose typed native vault and spending calls, async request tracking, pre-fork and post-fork gas estimates, payment-lane classification, and Zone gateway composition. Migration tooling emits a deterministic activation manifest with account proofs and a per-adapter reconciliation record of asset custody, venue shares, Earn supply, anchors, fee state, and pending requests. Indexers recognize old and new receipts at the same address and correlate `EarnSpent` with the TIP-20 transfer and any Zone inbox credit. A devnet harness starts from a pre-fork snapshot, activates the fork, registers a legacy vault, and exercises sync and async redemption, yield/loss, fee claims, spending, and Zone composition.

# Observability

Existing adapter and TIP-20 events retain their deployed signatures and ordering. `EarnSpent` reports owner, receiver, burned shares, paid assets, and reference. Registration emits `NativeEarnRegistered(address indexed adapter,address indexed asset,address indexed shareToken,address engine,bytes32 manifestRoot)` to make admitted identities auditable. Receipts and metrics expose fork ID, lane, native adapter identity, aggregate child execution/state work, and nested call count; an operator can reconcile an Earn payment without treating a successful general-lane receipt as success.

# Invariants

- Adapter venue shares plus open pending venue claims equal the recorded engine custody to the extent the engine reports both; every discrepancy is explicit in the reconciliation output.
- Earn share total supply equals active user shares plus minted, unclaimed fee shares. No request can be burned, finalized, or canceled twice.
- A synchronous payout cannot exceed backing removed from the engine; an async payout cannot exceed the engine's completed claim. TIP-20 balance and supply deltas match adapter custody and event deltas.
- For each transaction, all payment selectors and their Zone/TIP-20/engine children consume one bounded payment reservation. The general-lane count for these flows is zero after activation.
- Differential tests compare the deployed Solidity adapter and native adapter across positive and negative yield, zero and tiny amounts, rounding, fee remainder carry, fee config change, pause, every redemption capability, callback failure, token policy denial, engine revert/reentry, and a fork-boundary replay from genesis. Actual activated devnet receipts, balances, proofs, and mixed-workload throughput must be published before the fork is scheduled.
