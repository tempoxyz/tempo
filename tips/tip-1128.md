# TIP-1128: Native Earn Payment Lifecycle

## Abstract

This proposal makes registered EarnVault accounts native payment endpoints at their existing addresses. Deposits, redemption, asynchronous claims, fee-share claims, and spending from Earn execute with TIP-1125's transaction-owned EVM2 call budget in the payment lane. EarnShare balances remain nonrebasing; venue yield and losses change redeemable assets per share. Activation requires an audited legacy registry, historical replay, a scheduled fork, and a combined Earn and Zone devnet with zero general-lane payment usage.

## Motivation

The current EarnVault calls TIP-20 assets and EarnShare, its separate EarnFees module, and a venue engine. A shell that cannot make external calls must route those operations through general EVM execution. EVM2 allows a native vault to make paid child calls while preserving existing custody, accounting, and asynchronous redemption semantics. TIP-1084 describes the native shell; this TIP specifies the payment state transitions and migration necessary to replace the execution path.

## Assumptions

- TIP-1125 charges all native, engine, token, policy, and callback work against one transaction reservation. Reentry and nested Zone operations cannot acquire a second reservation.
- The deployed `EarnVault`, its non-upgradeable ERC-1967 proxy, immutable `EarnFees`, engine interfaces, TIP-20 EarnShare, and fee configuration at the activation block are the legacy source of truth. No asset, share, or venue position is silently reminted or transferred during activation.
- Each admitted engine has a registered code identity and capability set. A venue that changes implementation or asset identity is suspended until its new identity is approved.
- TIP-20 transfer policy, issuer roles, allowance, and pause state are enforced in the child token calls at execution time.

## Threat Model

An attacker can forge a vault-looking address, deploy a proxy with matching prefix, substitute an engine, return malformed engine data, reenter through a token or engine, request the same async claim twice, or make a callback consume unbounded work. Venue assets may gain or lose value between transactions. Administrators may change fees, pause deposits, or migrate an engine. These actions must not let a payment selector bypass identity checks, resource limits, token policy, or accounting. Registered engine code is trusted only for its stated asset and capability interface, not for free execution or arbitrary payment-lane admission.

# Specification

## Fork, identity, and dispatch

The proposed T16 activation follows the T15 native Zone fork and TIP-1125. Before activation, replay uses the historical EarnVault proxy, EarnFees, and engine behavior. EVM2's precompile admission sees the requested address, input, and loaded bytecode, but cannot read the onchain registry before deciding whether to run bytecode or native execution. T16 therefore installs a distinct, versioned native-vault dispatcher runtime at each admitted legacy EarnVault address. The runtime is a valid EVM fallback proxy for nonpayment selectors and has a code hash that cannot be confused with the legacy ERC-1967 proxy. Native admission requires an exact dispatcher code identity, a direct `CALL` to that address, and an enumerated selector; a matching runtime alone does not confer payment-lane status. The handler then charges and verifies an initialized vault in the onchain Earn registry, its original implementation identity from the approved manifest, its asset, EarnShare, and EarnFees bindings, and the vault's live EarnShare issuer role. The mutable engine must match a separately verified registered code identity and capability set at every payment call. A forged dispatcher may reach the handler but fails registration and cannot claim the payment lane.

The current `EarnFactory` emits `EarnStackDeployed` but does not store a list of vaults. Before scheduling, an activation manifest MUST enumerate deployed stacks from canonical factory receipts, reconcile each against state at the fork parent, publish a commitment and audit output, and identify the original implementation for each vault. At the fork boundary a deterministic system transition verifies the manifest against the fork-parent accounts, replaces only listed vault runtime code with the versioned dispatcher, and stores their registration. It retains each account address, nonce, native balance, storage (including the ERC-1967 implementation slot), EarnShare supply, EarnFees state, and engine custody. The manifest and transition are consensus data; no block may scan historical receipts. Historical sync applies the replacement only at that boundary. A new native factory MUST install the dispatcher and register newly deployed stacks atomically; deployment via the old unregistered factory after activation cannot enter the payment lane. Mutable governance and emergency selectors use the dispatcher's ordinary EVM fallback and the general lane; a payment selector admitted to native execution cannot fall back to the legacy proxy after registration fails. All transaction admission surfaces, including pool, builder, validator, RPC estimation, and prover, use the same fork-aware candidate rules and verified execution marker.

The T16 schedule MAY additionally name one predeployed `NativeEarnFactory`, its exact runtime hash, governor, proxy runtime hash, immutable vault and fee implementation identities, and at most 128 initially approved engine instances and code hashes. The fork transition verifies these accounts and seeds the registry. That factory calls the native registry at `0x5aea000000000000000000000000000000000000` before `deploy` returns; failure rolls back the entire new stack. The registry admits only the scheduled factory runtime, an unregistered proxy and fee clone with exact approved code and storage bindings, a TIP-20 asset and EarnShare, the live vault issuer role, and a currently approved engine instance. It then installs both dispatcher runtimes and records their identities. The governor may approve or revoke a deployed engine instance, and may refresh a registered vault's engine identity after the vault's own migration changes its engine slot. Revoking approval suspends that engine's vault payment admission. These administrative calls use the general lane; the subsequent payments remain bounded native calls.

The native handler may execute the original immutable EarnVault implementation through a paid, bounded EVM2 `DELEGATECALL` with the vault's storage address and original caller. This preserves deployed math, fee calls, events, and authorization while charging the full child tree to one transaction budget. The dispatcher fallback delegates nonpayment selectors to the original implementation. The manifest binds the implementation code hash; changing the ERC-1967 slot or dispatcher bytecode suspends native payment admission. The legacy EarnFees account is an EIP-1167 clone, not the vault's ERC-1967 proxy. The boundary transition also verifies its clone target, writes that target into the unused ERC-1967 implementation slot at the EarnFees address, installs the dispatcher runtime there, and registers the fee account separately. The fallback then retains its existing accounting and claim ABI; native `EarnFees.claim` must check that separate registration and charge its paid child tree. A registered vault alone does not admit a fee claim.

Native payment selectors retain the deployed ABI and events for `accrueFees`, both `deposit` overloads, `depositVenueShares`, `contribute`, `absorbEngineShareSurplus`, both `redeem` overloads, both `withdrawExact` overloads, the three `requestRedeem` overloads, `finalizeRedeem`, and `cancelRedeem`. Fee recipients claim through `EarnFees.claim(address,uint256)`; that separate account and its claimable-share ledger cannot be silently folded into the vault. The new `spendFromEarn(uint256 earnShares,address receiver,uint256 minAssets,bytes32 paymentReference)` burns the caller's EarnShare, redeems synchronously to the receiver, and emits `EarnSpent(address indexed owner,address indexed receiver,bytes32 indexed paymentReference,uint256 earnShares,uint256 assets)`. It reverts if the engine lacks immediate redemption or output misses the minimum. `paymentReference` is public correlation data, never authority. A registered Zone gateway may call the selector using EarnShare it owns.

`finalizeRedeem` is admitted only from the registered engine's exact identity and approved callback selector. A Veda `solveAndForward(bytes32[],bool)` transaction enters the payment lane only through a separately registered forwarding solver. The governor calls `registerSettlementForwarder(forwarder,vault,engine,forwarderCodeHash)` after the solver is deployed and bound. The registrar verifies the vault and engine registrations, copies the forwarder's constructor-bound runtime to a deterministic empty snapshot account, installs the versioned dispatcher at the forwarder's address, and stores the code identities. Its ordinary fallback delegates to the snapshot so the solver keeps its storage, caller authorization, and other functions. The native handler admits a canonical batch of one to eight request IDs, verifies the dispatcher, snapshot and engine code, vault binding and issuer role, and calls the snapshotted `engine()` and `isAuthorizedSolver(caller)` getters before marking the transaction as payment. It then executes `solveAndForward` by paid `DELEGATECALL` with the original caller, so the solver's stock Veda solve, measured payout delta, engine forwarding, vault finalization, and failure recovery run atomically. A general EVM wrapper around a native vault call does not classify the whole transaction as payment-lane work.

## Vault state and synchronous operations

The vault retains its asset, EarnShare, EarnFees, mutable engine, managed engine shares, conversion anchors, reward-rate baseline, pending request map and count, roles, migration mode, capacity, and pause state at deployed storage slots. EarnFees separately retains fee configurations, high-water and target anchors, per-configuration remainders, recipient claims, and pending fee snapshots. Native execution MUST reproduce both deployed accounts' state transitions, or call EarnFees through paid EVM2 child frames with the correct caller. The first native payment transaction does not reset an anchor or infer an exchange rate from total supply.

Every value-changing operation checkpoints accrued fees before changing user principal. Deposit pulls `assets` from caller to vault, approves and calls the engine, measures engine shares received, converts using the current anchor, enforces `minEarnShares` and the one-basis-point conversion-loss bound, mints EarnShare to `receiver`, and reanchors. `depositVenueShares` asks only a capable current engine to pull its exact venue shares and mints proportionate EarnShare. `contribute` requires positive existing share supply, adds backing without minting contributor shares, reanchors, then accrues value gained after the contribution. Direct engine-share surplus remains quarantined until explicit bounded absorption. The configured capacity and pause gates apply to every voluntary inflow.

`redeem` pulls and burns the caller's EarnShare, maps it to engine shares, invokes immediate engine redemption, enforces `minAssets`, and reanchors. `withdrawExact` previews engine shares, rounds required EarnShare upward, enforces `maxEarnShares`, calls exact engine withdrawal, burns only shares actually required, checks residual backing, and reanchors. `spendFromEarn` follows `redeem` accounting with the engine paying `receiver` directly; failure of any child call rolls back the burn, engine effect, token transfer, fee checkpoint, logs, and native storage writes as one EVM2 frame. A caller can spend only shares it owns or obtains through ordinary allowance transfer.

## Yield and fees

Active NAV is the engine's currently redeemable assets for active venue shares. Pending redemption value is excluded. Earn token balances do not rebase on venue gain or loss. The active conversion anchor scales venue shares to outstanding Earn token supply and is restored after each operation; zero-supply reset follows deployed empty-anchor behavior.

Fees accrue on positive active value above the configured high-water and target anchors. EarnFees retains per-configuration fractional remainders and recipient claims. When `0 < feeAssets < activeAssets`, fee shares equal `floor(feeAssets * supply / (activeAssets - feeAssets))`; allocations and rounding match the deployed EarnFees exactly. Loss alone cannot mint fees. `EarnFees.claim` transfers only already minted claimable shares and decrements the claimant ledger. Native reads and writes use exact deployed widths and rounding. Fee configuration and guardian changes retain historical authorization.

## Asynchronous redemption and migration

`requestRedeem` checkpoints fees, burns the caller's shares once, asks the engine for a request ID, and stores receiver, requester, burned EarnShare, engine shares, and open status in EarnVault. EarnFees stores the request's fee snapshot and disable epoch. A duplicate ID fails. Requested engine shares leave active NAV. Engine-only `finalizeRedeem` closes once, forwards the already delivered engine payout to the stored receiver, and cannot burn again. Optional receiver callback failure is ignored, but its work is paid and bounded. `cancelRedeem` is restricted to requester or janitor, measures returned engine shares, applies EarnFees' snapshot and fee-disable rules, mints fee-aware re-entry to the stored receiver subject to `minReceiverEarnShares`, reanchors, and closes once.

At activation, every open request remains associated with its original engine, recipient, fee configuration, and request ID; it is neither automatically finalized nor canceled. The activation reconciler compares each request and aggregate pending count to pre-fork state. Engine migration retains the deployed operator and guardian rules, requires no open requests, the same asset, and an approved new engine capability and code identity. It moves custody atomically, retains Earn supply, and reanchors. A deployment whose migration mode forbids operator migration cannot gain it through native dispatch.

## Resource accounting and atomicity

The vault reserves intrinsic calldata, identity and storage reads, TIP-20 calls, policy checks, EarnFees calls, engine capability and accounting calls, fee math, writes, logs, and bounded callback work before child execution. Child EVM2 calls consume the parent transaction's remaining execution and state-work budget, including cold/warm effects, failure paths, returndata copy, and nested precompiles. The proposed T16 profile accepts at most 8,192 calldata bytes, 4,096 `engineData` bytes, and 4,096 returned bytes per native child; it reserves at most eight native child calls and 16 million aggregate execution-plus-state-work gas for a direct vault or fee transaction. One vault delegate frame receives at most 8 million execution gas and 4 million state gas; one EarnFees delegate frame receives at most 2 million execution gas and 1 million state gas. A registered settlement transaction has a 32 million transaction-owned work reservation: two getter frames each reserve 100,000 execution plus 100,000 state gas, and the forwarding-solver frame reserves 11 million execution plus 4 million state gas, leaving capacity for nested vault and fee frames. Nested EVM calls remain subject to EVM depth and the gas forwarded from those frames. These limits MUST be measured against the mixed workload and adjusted before activation if valid payments do not fit. A failed child call cannot commit a partial mint, burn, custody transfer, pending claim, or fee credit.

# Tooling

SDKs expose typed native vault and spending calls, async request tracking, pre-fork and post-fork gas estimates, payment-lane classification, and Zone gateway composition. Migration tooling emits a deterministic activation manifest with account proofs and per-vault reconciliation of custody, managed and raw engine shares, EarnShare supply, anchors, EarnFees state, and pending requests. Indexers recognize old and new receipts at the same address and correlate `EarnSpent` with TIP-20 movement and any Zone inbox credit. A devnet harness starts with pre-fork positions, activates the fork, registers a legacy vault, and exercises immediate and queued redemption, yield/loss, fee claims, spending, and Zone composition.

# Observability

Existing EarnVault, EarnFees, and TIP-20 events retain their deployed signatures and ordering. `EarnSpent` reports owner, receiver, burned EarnShare, paid assets, and reference. Factory registration emits `NativeEarnRegistered(address indexed vault,address indexed asset,address indexed earnShare,address fees,address engine,bytes32 engineCodeHash)` from the native registry address. Settlement registration emits `NativeEarnSettlementRegistered(address indexed forwarder,address indexed vault,address indexed engine,address snapshot,bytes32 forwarderCodeHash)` from the same address. The events bind new payment endpoints to their exact code identities; the legacy fork manifest is published separately. Receipts and metrics expose fork ID, lane, vault identity, aggregate child execution/state work, and nested call count.

# Invariants

- Managed engine shares plus open pending engine-share claims must reconcile to engine custody; raw surplus stays quarantined and every discrepancy is explicit in the reconciliation output.
- Earn share total supply equals active user shares plus minted, unclaimed fee shares. No request can be burned, finalized, or canceled twice.
- An immediate payout cannot exceed backing removed from the engine; a queued payout cannot exceed the engine's completed claim. TIP-20 balance and supply deltas match vault custody and event deltas.
- For each transaction, all payment selectors and their Zone/TIP-20/engine children consume one bounded payment reservation. The general-lane count for these flows is zero after activation.
- Differential tests compare the deployed Solidity EarnVault and native vault across positive and negative yield, zero and tiny amounts, rounding, fee remainder carry, fee config change, pause, every redemption capability, callback failure, token policy denial, engine revert/reentry, and fork-boundary replay from genesis. Activated devnet receipts, balances, real proofs, and mixed-workload throughput must be published before scheduling.
