# TIP-1153: Consensus Seed as PREVRANDAO

> **Implementation status.** Implementing this TIP is blocked on upstream
> commonware. Its consensus interface to the application (`Automaton`) passes
> the round, leader and parent of a proposal, but not the seed of the parent's
> round, and commonware offers no other way for the application to get that seed
> when it proposes or verifies a block. This TIP can be implemented once
> commonware exposes it.

## Abstract

This TIP makes `PREVRANDAO` return randomness by writing Tempo consensus'
threshold VRF seed into each block's `mix_hash`, hashed with `keccak256`. Each
block uses the seed from the round in which its parent was certified. The first
block of each epoch sets `mix_hash` to zero.

Validators enforce this value. Anyone with the network identity can check it
against the parent's finalization certificate.

**Safety policy.** The seed of a block's own round can leak to a Byzantine
coalition before the round resolves, so this TIP only exposes already-public
seeds and specifies commit-then-reveal guidance for contracts, following the
[commonware `bls12381_threshold::vrf` docs](https://docs.rs/commonware-consensus/2026.9.0/commonware_consensus/simplex/scheme/bls12381_threshold/vrf/index.html).

Nobody can bias the seed, but it is public before the block that uses it is
built. Applications MUST therefore commit first and bind to the randomness of a
future block.

## Motivation

Contracts on Tempo have no source of randomness: `PREVRANDAO` returns zero in
every block, because block producers always set it to zero.
Applications that need randomness, such as lotteries, sampling, raffles, games,
and randomized protocol roles, must run their own oracle or a
multi-party commit-reveal scheme.

Applications already want the consensus seed enough to extract it themselves.
The xframes "High Roller" dice game settles bets with Tempo's threshold-VRF
seed: an off-chain service reads finalization certificates from consensus, and
the
[`TempoBlockRandomness`](https://github.com/tempoxyz/xframes/blob/16750226ef1718cdd67b4e830acde67fbe58c15f/contracts/src/TempoBlockRandomness.sol)
contract checks the block's finalization and its seed with an on-chain BLS
pairing check against a group key fixed at deployment. This works, but every
application that does it:

- deploys and pays for its own BLS12-381 verifier;
- pins the network identity, so a full DKG breaks it and forces a redeploy;
- depends on someone submitting the certificates within the 8,191-block
  `blockhash` window, after which pending bets are forfeited; and
- must bind rounds to blocks safely on its own. xframes settles a bet with the
  seed of the round that included it, which the commonware documentation quoted
  below calls unsafe.

Exposing the seed through `PREVRANDAO` gives every contract the same value
for free, checked by consensus, unaffected by key changes, and with a specified
safe binding.

Tempo's consensus already computes a verifiable random value in every round.
Tempo runs Simplex with the `bls12381_threshold::vrf` scheme over `MinSig`. Every vote carries a partial signature over
the round, and every notarization, nullification, and finalization certificate
carries the recovered threshold signature, called the *seed*. Because a BLS
threshold signature over a fixed message is unique, nobody can bias the seed's
value, including the leader and any coalition below the threshold.

The seed is not secret until finalization. Commonware's documentation for the
scheme warns:

> the `f` Byzantine participants of a `3f+1` committee can recover the seed once
> any `f+1` honest participants have voted (even for conflicting proposals),
> before the round resolves and without any certificate forming. [...] It is
> **not safe** to use a round's randomness to drive execution in that same round.
> Applications [...] should employ a "commit-then-reveal" pattern and require
> users to bind to the output of randomness in advance.

This TIP follows that guidance. It never exposes the seed of a block's own round
to that block's execution. A block exposes the seed of its parent's round, which
was public before the block was proposed. The TIP also defines which future
blocks a commitment can safely bind to.

### Alternatives considered

| Alternative | Reason rejected |
| --- | --- |
| Use the seed of the block's own round | The seed is not known when the block is built. Even if execution were deferred until it was known, the leader could recover it early and pick among `f+2` outcomes, which is the front-running attack described above. |
| Also carry `σ` in a new header field | It would let a single header be checked without fetching a certificate, but `σ(r_P)` is already in the parent's finalization certificate, which followers verify anyway, and anyone who trusts a header through the hash chain already trusts its `mix_hash` because validators enforced it. Not worth a header format change and 49 bytes per block. |
| Validators release seed partials only after a height is finalized (the "instant VRF" from the commonware docs) | Requires an extra broadcast per height and changes to the consensus protocol. It can be added later; this TIP needs no new consensus messages. |
| Use the seed of the boundary block's round for the first block of an epoch | The boundary block is re-proposed until it is finalized, possibly in a later view than the one in its header, and only that finalization is stored durably. The seed of the header's round may be gone, and the finalization's seed is not recorded in any header. See [Epoch boundaries](#epoch-boundaries). |
| A randomness precompile that returns the seed of an arbitrary past block | Useful for reveals, but it is a separate interface and is out of scope here. Contracts can already prove a past block's `mix_hash` from its header and `blockhash` (see [Guidance for applications: consuming the randomness](#guidance-for-applications-consuming-the-randomness)). |

## Assumptions

- **Threshold honesty.** Fewer than `2f+1` of each epoch's `3f+1` share holders
  collude. A coalition with a quorum of shares can compute every future seed of
  that epoch. Such a coalition also breaks consensus safety, so this TIP adds no
  new trust assumption.
- **Certified parent.** An honest node proposes or verifies a block only after
  its parent is certified, by a notarization or finalization, in the parent's
  round. Every certificate carries the seed of its round, so the proposer and
  every voter have `σ`. The first block of an epoch is the exception and uses
  no seed (see [Epoch boundaries](#epoch-boundaries)).
- **Network identity per epoch.** The group public key of epoch `e` is the
  genesis network identity for `e = 0`. For later epochs it is the
  network identity recorded in the DKG outcome of the boundary block of
  `e - 1`. It stays the same across reshares and changes after a full DKG.
- **Activation.** All validators and followers MUST upgrade before the
  activating hardfork, because block verification changes. The header format
  does not change, so other header decoders are unaffected.
- **Consensus context present.** Every block after T4 carries
  `consensus_context` (TIP-1031). On a chain where this TIP activates at genesis,
  only block 1 has a parent without a context, and it is the first block of
  epoch 0.

# Specification

## Overview

Terms:

- **Round.** A Simplex `(epoch, view)` pair.
- **Parent round** of block `B`. The round in the parent header's
  `consensus_context`: `(parent.consensus_context.epoch,
  parent.consensus_context.view)`. For most blocks it equals
  `(B.epoch, B.consensus_context.parent_view)`.
- **First block of an epoch.** A block `B` whose parent `P` is genesis
  (`P.consensus_context` is `None`) or the last block of an earlier epoch
  (`P.consensus_context.epoch < B.consensus_context.epoch`). Both are
  visible from the two headers alone.
- **Seed** `σ(r)`. The BLS12-381 `MinSig` threshold signature, a G1 point, over
  round `r`, as defined by `commonware_consensus::simplex::scheme::bls12381_threshold::vrf`
  at `commonware-consensus` 2026.9.0:

  ```text
  namespace = "TEMPO" || "_SEED"            // "TEMPO_SEED"
  message   = varint(r.epoch) || varint(r.view)   // commonware's round encoding
  σ(r)      = threshold BLS signature over (namespace, message)
              under the network identity of epoch r.epoch
  ```

  The seed is the `seed_signature` in any notarization, nullification, or
  finalization certificate for `r`.

Scope: block production, block verification, and the
`PREVRANDAO` value seen by the EVM. Consensus messages, the DKG, and the leader
election are unchanged.

## Mechanics

### Activation

The rules below apply to a block `B` whose timestamp is at or after the
activating hardfork, called the fork below. A block before the fork keeps
today's rules: `mix_hash` is zero.

### Required values

The header format is unchanged. For a post-fork block `B` with parent `P`:

| `B` | `B.mix_hash` |
| --- | --- |
| First block of an epoch | `0x00…00` |
| Any other block, with `ctx = P.consensus_context` | `keccak256(σ(ctx.epoch, ctx.view))`, hashed over the 48-byte compressed G1 encoding of the seed |

The seed is hashed because its 48-byte encoding does not fit the 32-byte
`mix_hash` and is not uniformly distributed (it carries flag bits and a field
element below the BLS12-381 modulus); the hash compresses it and makes the
output look uniform. Any collision-resistant hash would do: `keccak256` is
chosen because it is the EVM's native hash and differs from the SHA-256 that
commonware's leader election applies to the same seed.

`B`'s `difficulty` stays zero, so the EVM's `PREVRANDAO` equals `B.mix_hash`.

### Epoch boundaries

The first block of an epoch has no seed it could use reliably.

Its own epoch has none yet. Each epoch's Simplex instance starts with the
previous epoch's boundary block as its genesis, at view 0. The first block's
consensus context therefore names the boundary block as its parent with
`parent_view` 0, and view 0 has no certificate. For the same reason commonware
elects the leader of view 1 round-robin instead of from a seed.

The previous epoch's seed is not reliably available either. Commonware's marshal
re-proposes the boundary block, with both inline and deferred verification, in
every later view of its epoch until a finalization for it forms. Its header
keeps its original context `(e, v_b)`, but it can be notarized again in later
views and finalized in a view `v_f ≥ v_b`, each with a different seed. Nodes
store only the finalization durably, so a node that restarted or synced may
lack `σ(e, v_b)`, and `σ(e, v_f)` is not recorded in any header.

The first block of each epoch therefore sets `mix_hash` to zero, which costs one
block in 21,600 on mainnet and testnet. No other block is affected: a block that
is not a boundary re-proposal is certified and finalized only in the round of
its own `consensus_context`.

### Block production

When the leader of round `r_B` builds on parent `P`:

1. If `B` is the first block of an epoch, set `prev_randao = 0` and stop.
2. Read the parent round `r_P` from `P.consensus_context`, and get `σ(r_P)` from
   the notarization or finalization that certified `P`.
3. Set `prev_randao = keccak256(σ(r_P))` in the payload attributes, which the
   builder writes to `mix_hash`.

If the proposer cannot get `σ(r_P)`, it MUST NOT propose. It may fetch the
certificate from peers and retry. Otherwise the view times out and is
nullified like any other missed proposal. The proposer MUST NOT fill in a
placeholder.

### Block verification

When verifying a proposal, alongside the existing `consensus_context` check, a
validator MUST reject `B` unless:

1. `B.mix_hash` matches the [Required values](#required-values) table for the
   fork state at `B`'s timestamp, where `σ(r_P)`
   is the seed of a certificate for `r_P` that the validator has verified, such
   as the one that certified `P`. Threshold BLS signatures are unique, so every
   certificate for `r_P` carries the same seed.

If `B` is not the first block of an epoch and the validator does not have a
verified certificate for `r_P`, it abstains.
It MUST NOT vote to accept or reject. This mirrors the existing handling when
DKG data is unavailable.

The execution layer cannot check `mix_hash` on its own, because it has no
certificates or epoch identities. Followers verify each block's finalization,
and `P`'s finalization certificate carries
`σ(r_P)` as its seed, so followers SHOULD check `B.mix_hash` against it. For
the first block of an epoch they check that it is zero.

Anyone else can check a block's `PREVRANDAO` the same way: verify `P`'s
finalization certificate under the network identity of `r_P.epoch`, then
compare `keccak256` of its seed signature with `B.mix_hash`. Nodes serve
finalization certificates over `consensus_getFinalization`.

### What is known, and when

Let `B` be at height `h` with parent round `r_P`. `PREVRANDAO(h) = keccak256(σ(r_P))`.

| Event | Who knows `PREVRANDAO(h)` |
| --- | --- |
| `f+1` honest votes cast in round `r_P` | A Byzantine coalition of up to `f`, while `P` (height `h-1`) is still undecided |
| `P` is notarized | Everyone. This is before `B` is proposed |
| `B` executes | Every transaction in `B` |

`PREVRANDAO` is therefore never a secret during the block that reads it. It is
safe only as the reveal of a commitment made earlier.

A seed `σ(e, v)` with `e > E` needs partial signatures from the committee of
epoch `e`. Honest members produce those only after the Simplex instance for
epoch `e` starts, and it starts only after the boundary block of epoch `e - 1`
is finalized. By induction, every block in epochs `≤ E` is finalized before any
seed of epoch `> E` can be recovered.

### Guidance for applications: consuming the randomness

This section is guidance for applications. It is not consensus behavior.

A contract commits in a transaction at height `h_c` and later reveals using
`PREVRANDAO` at a target height `h_t` fixed at commit time. The commitment is
safe only if `h_c` is finalized before anyone can learn `PREVRANDAO(h_t)`. If
the seed is known earlier, the leader of `h_c`'s round, or the leader of a later
round that can still reorganize `h_c`, can choose whether and where the commit
lands.

| Binding | Safety | Latency |
| --- | --- | --- |
| `h_t ≥ last(epoch(h_c)) + 2`, so the target's parent is in a later epoch | Guaranteed under the threshold assumption, by the epoch argument above | Up to one epoch: 21,600 blocks on mainnet and testnet |
| `h_t = h_c + k` for a small `k ≥ 2` | Probabilistic. Safe once `h_c` is finalized before round `round(h_t - 1)` collects `f+1` honest votes, so larger `k` is safer | `k` blocks |
| `h_t ≤ h_c + 1` | Unsafe. `PREVRANDAO(h_c + 1)` is the seed of `h_c`'s own round | n/a |

The first block of every epoch has `PREVRANDAO` zero. Epoch boundaries are at
fixed heights, so these blocks are known long in advance, and zero is a value
anyone can compute at commit time. A contract MUST NOT derive an outcome from a
zero `PREVRANDAO`: it MUST treat zero as "no randomness" and use `h_t + 1`
instead. Moving to `h_t + 1` only lengthens the delay, so the binding stays at
least as safe.

With this fallback, the seed of the round of an epoch's first block decides
both targets `h_t` and `h_t + 1`. Contracts SHOULD mix their own commitment or
a domain label into the value (for example
`keccak256(prevrandao, label, commitment)`) so that outcomes at the two heights
are independent. The [Threat Model](#threat-model) covers the effect on
withholding bias.

Contracts can read `PREVRANDAO` only for the block they execute in. Two reveal
patterns work:

1. **Reveal in the target block.** The reveal transaction must be included at
   exactly `h_t`. This is fragile and only suitable when a keeper is guaranteed
   to land there.
2. **Reveal by header proof.** After `h_t`, anyone submits the RLP-encoded Tempo
   header of `h_t`. The contract checks `keccak256(rlp) == blockhash(h_t)`, using
   the `BLOCKHASH` opcode for the last 256 blocks or the EIP-2935 history
   contract for the last 8,191 blocks, and then reads `mix_hash` from the header.
   The header uses Tempo's encoding (`[general_gas_limit, shared_gas_limit,
   timestamp_millis_part, inner, consensus_context?]`), not Ethereum's.

## Interfaces

- No new header fields. JSON-RPC block headers report a non-zero `mixHash`
  after the fork.
- EVM: no new opcodes or precompiles. `PREVRANDAO` (0x44) returns `mix_hash`, as
  it does today.

# Compatibility

| Integration | What changes |
| --- | --- |
| Header encoding and hashing | Unchanged. Header decoders, including the RPC types and the zone precompiles that decode Tempo headers (TIP-1096), need no update. |
| Contracts reading `PREVRANDAO` / `block.prevrandao` / `block.difficulty` | Values become non-zero and change every block. Contracts that assumed a zero value, for example as a sentinel, change behavior. Contracts using it as a secret are unsafe, as on Ethereum. See [Guidance for applications: consuming the randomness](#guidance-for-applications-consuming-the-randomness). |
| Payload building | Payload attributes get the seed from consensus and set `prev_randao`. Builds that do not come from consensus, such as dev mode, have no seed and must stay pre-fork or use a test identity. |
| Deferred verification (T14) | No interaction beyond the header check. Blocks notarized optimistically are still checked before certification. |
| Zones | Zone blocks keep `mix_hash = 0`. Zones can read Tempo randomness from imported Tempo headers. |
| Block explorers and indexers | `mixHash` becomes non-zero. No other change. |
| Devnets and e2e tests | Test networks already run the threshold scheme, so seeds exist. Test helpers that build headers by hand must set `mix_hash` for post-fork heights. |

# Observability

N/A for on-chain events: the header already exposes `mixHash`.

Nodes SHOULD export:

- A counter of proposals skipped because `σ(r_P)` was unavailable.
- A counter of verifications that abstained because no verified certificate for
  the parent round was available.
- A counter of blocks rejected for a `mix_hash` mismatch, with
  the proposer logged.

A rising skip or abstain count points to certificate retention or fetch problems,
not to Byzantine behavior.

# Threat Model

The most consequential attack is a **Byzantine leader who learns a seed early
and front-runs a naive consumer.** A contract that settles a bet with
`PREVRANDAO` at the commit height, or at the next height, gives the leader of
round `r` a free option. Once `f+1` honest votes are in, the leader knows
`σ(r)`, which is `PREVRANDAO` of the next height. It can then choose among up to
`f+1` candidate blocks, or nullification, to decide which commits land at that
height. The protocol cannot prevent this. Applications must bind to a future
height as described in [Guidance for applications: consuming the randomness](#guidance-for-applications-consuming-the-randomness).

| Actor | Controls | Trusted to | Enforcing check | Consequence of failure |
| --- | --- | --- | --- | --- |
| Leader of `r_B` | Contents of `B`, including `mix_hash` | Nothing about `σ` | Verification step 1. `σ(r_P)` is unique, so the leader has no choice | A wrong `mix_hash` is rejected and the view is nullified |
| Byzantine leader of `r` | Whether round `r` produces a certified block or a nullification | Nothing | None. This is inherent to Simplex | **Withholding bias.** After learning `σ(r)`, it can force a nullification so that `σ(r)` is never used as `PREVRANDAO`. That height then gets a seed from a later round that the leader does not yet know. This is a one-bit bias per Byzantine-led round, comparable to RANDAO's last-revealer bias. Consecutive Byzantine leaders get more options |
| Leader of view 1 of an epoch | Whether the round of the epoch's first block is certified or nullified | Nothing | None. This is inherent to Simplex | **Predictable withholding bias.** View 1's leader is chosen round-robin, so it is known as soon as the epoch's committee is, instead of shortly before its round. Its round's seed is `PREVRANDAO` of the epoch's second block and, through the fallback, of the first. The bias is still one bit, but it covers two target heights, and bets can be placed against a leader known in advance |
| Coalition of up to `f` validators | Their shares | Not to reach threshold | Threshold `2f+1` | Learns `σ(r)` early, as above, but cannot change it |
| Coalition of `2f+1` or more shares | All seeds of the epoch | — | None | Predicts every seed of the epoch. Consensus safety is already lost |
| Transaction senders and searchers | Transaction ordering bids | Nothing | None | Everyone knows `PREVRANDAO(h)` once the parent is notarized and can simulate against it |
| Contract developers | How randomness is consumed | To follow commit-then-reveal | Documentation only | Same-block or next-block use is exploitable, as above. A contract that accepts a zero `PREVRANDAO` at the first block of an epoch gives anyone an outcome they can compute at commit time |

Excluded: randomness that stays secret at execution time, which would need the
"instant VRF" or timelock encryption, and bias resistance beyond the withholding
bias above.

# Invariants

1. **Pre-fork.** Pre-fork blocks have `mix_hash == 0`.
2. **Value.** For every post-fork block `B` with parent `P` that is not the
   first block of an epoch, `B.mix_hash == keccak256(σ(P.ctx.epoch, P.ctx.view))`,
   where `σ` is the threshold signature under namespace
   `TEMPO_SEED` and the network identity of `P.ctx.epoch`.
3. **Epoch boundary.** The first block of every post-fork epoch has
   `mix_hash == 0`.
4. **Encoding.** The header format and pre-fork header hashes are unchanged.
5. **EVM.** `PREVRANDAO` executed in `B` returns `B.mix_hash`.

### Test coverage

- Verification rejects: a non-zero `mix_hash` before the fork, a zero
  `mix_hash` after it, and `mix_hash` derived from the wrong round (for example
  `B`'s own round, or `(e, parent_view)` when it differs from the parent
  header's round) or from a seed under the wrong epoch identity.
- Verification rejects a non-zero `mix_hash` in the first block of an epoch.
- An e2e test across an epoch boundary, including one where the boundary block is
  re-proposed and finalized in a later view: the first block of epoch `e + 1`
  has `mix_hash` zero, and the second carries the seed of the first block's
  round in epoch `e + 1`, including after a full DKG that changes the identity.
- An e2e test with nullified views: the block after a nullification uses the seed
  of its actual parent's round, not of the nullified view.
- Fork activation: the first post-fork block on a running chain carries a seed;
  block 1 on a chain with the fork at genesis carries none.
- An EVM test that `PREVRANDAO` returns `mix_hash`.
