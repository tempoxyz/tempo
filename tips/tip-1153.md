# TIP-1153: Consensus Seed as PREVRANDAO

## Abstract

Every Tempo block's `mix_hash`, and therefore the EVM `PREVRANDAO` opcode, is
today the constant zero. This TIP sets `mix_hash` of each block to
`keccak256(σ)`, where `σ` is the threshold-VRF seed that Tempo's consensus
already produces for the round in which the block's parent was certified, and
appends `σ` to the header so anyone holding the network identity can verify it.
The seed is unbiasable but is known before the block that uses it is built, and a
Byzantine coalition can learn it before the parent is finalized, so applications
MUST use a commit-then-reveal pattern and bind to the randomness of a future
block.

## Motivation

Contracts on Tempo have no source of randomness: `PREVRANDAO` returns zero in
every block (`TempoPayloadAttributes::new` hard-codes `prev_randao: B256::ZERO`).
Applications that need randomness, such as lotteries, sampling, raffles, games,
and randomized protocol roles, must run their own oracle or a
multi-party commit-reveal scheme.

Applications already want the consensus seed enough to extract it themselves.
The xframes "High Roller" dice game settles bets with Tempo's threshold-VRF
seed: an off-chain service reads finalization certificates from consensus, and
the
[`TempoBlockRandomness`](https://github.com/tempoxyz/xframes/blob/16750226ef1718cdd67b4e830acde67fbe58c15f/contracts/src/TempoBlockRandomness.sol)
contract checks the block's finalization and its seed with an on-chain BLS
pairing check against a group key fixed at deployment. This works, but every
application that does it:

- deploys and pays for its own BLS12-381 verifier;
- pins the network identity, so a full DKG breaks it and forces a redeploy;
- depends on someone submitting the certificates within the 8,191-block
  `blockhash` window, after which pending bets are forfeited; and
- must bind rounds to blocks safely on its own. xframes settles a bet with the
  seed of the round that included it, which the commonware documentation quoted
  below calls unsafe.

Exposing the seed through `PREVRANDAO` gives every contract the same value
for free, checked by consensus, unaffected by key changes, and with a specified
safe binding.

Tempo's consensus already computes a verifiable random value in every round.
Tempo runs Simplex with the `bls12381_threshold::vrf` scheme over `MinSig`
(see `crates/consensus/src/alias.rs`). Every vote carries a partial signature over
the round, and every notarization, nullification, and finalization certificate
carries the recovered threshold signature, called the *seed*. Because a BLS
threshold signature over a fixed message is unique, nobody can bias the seed's
value, including the leader and any coalition below the threshold.

The seed is not secret until finalization. Commonware's documentation for the
scheme warns:

> the `f` Byzantine participants of a `3f+1` committee can recover the seed once
> any `f+1` honest participants have voted (even for conflicting proposals),
> before the round resolves and without any certificate forming. [...] It is
> **not safe** to use a round's randomness to drive execution in that same round.
> Applications [...] should employ a "commit-then-reveal" pattern and require
> users to bind to the output of randomness in advance.

This TIP follows that guidance. It never exposes the seed of a block's own round
to that block's execution. A block exposes the seed of its parent's round, which
was public before the block was proposed. The TIP also defines which future
blocks a commitment can safely bind to.

### Alternatives considered

| Alternative | Reason rejected |
| --- | --- |
| Use the seed of the block's own round | The seed is not known when the block is built. Even if execution were deferred until it was known, the leader could recover it early and pick among `f+2` outcomes, which is the front-running attack described above. |
| Set `mix_hash = keccak256(σ)` without carrying `σ` in the header | Only nodes that hold the parent's certificate could check `mix_hash`. Followers, zones that import Tempo headers, and light clients would have to trust it. Carrying `σ` costs 49 bytes per block and makes the value verifiable from the header chain and the network identity alone. |
| Validators release seed partials only after a height is finalized (the "instant VRF" from the commonware docs) | Requires an extra broadcast per height and changes to the consensus protocol. It can be added later; this TIP needs no new consensus messages. |
| A randomness precompile that returns the seed of an arbitrary past block | Useful for reveals, but it is a separate interface and is out of scope here. Contracts can already prove a past block's `mix_hash` from its header and `blockhash` (see [Consuming the randomness](#consuming-the-randomness)). |

## Assumptions

- **Threshold honesty.** Fewer than `2f+1` of each epoch's `3f+1` share holders
  collude. A coalition with a quorum of shares can compute every future seed of
  that epoch. Such a coalition also breaks consensus safety, so this TIP adds no
  new trust assumption.
- **Certified parent.** An honest node proposes or verifies a block only after
  its parent is certified, by a notarization or finalization, in the parent's
  round. The first block of an epoch builds on the previous epoch's boundary
  block, which is finalized before the new epoch's Simplex instance starts
  (`Floor::Genesis(boundary_digest)` in
  `crates/consensus/src/epoch/manager/actor.rs`). Every certificate carries the
  seed of its round, so the proposer and every voter have `σ`.
- **Network identity per epoch.** The group public key of epoch `e` is the
  genesis network identity for `e = 0`. For later epochs it is the
  `network_identity` of the `OnchainDkgOutcome` in the boundary block of
  `e - 1`. It stays the same across reshares and changes after a full DKG.
- **Activation.** All validators, followers, RPC nodes, and zone nodes that
  decode Tempo headers MUST upgrade before the activating hardfork, because the
  header gains a field.
- **Consensus context present.** Every block after T4 carries
  `consensus_context` (TIP-1031). On a chain where this TIP activates at genesis,
  only block 1 has a parent without a context.

# Specification

## Overview

Terms:

- **Round.** A Simplex `(epoch, view)` pair.
- **Parent round** of block `B`. The round in the parent header's
  `consensus_context`: `(parent.consensus_context.epoch,
  parent.consensus_context.view)`. For most blocks it equals
  `(B.epoch, B.consensus_context.parent_view)`. For the first block of an epoch
  it is the round in which the previous epoch's boundary block was certified,
  not the new epoch's view 0.
- **Seed** `σ(r)`. The BLS12-381 `MinSig` threshold signature, a G1 point, over
  round `r`, as defined by `commonware_consensus::simplex::scheme::bls12381_threshold::vrf`
  at `commonware-consensus` 2026.9.0:

  ```text
  namespace = "TEMPO" || "_SEED"            // "TEMPO_SEED"
  message   = varint(r.epoch) || varint(r.view)   // commonware `Round::encode`
  σ(r)      = threshold BLS signature over (namespace, message)
              under the network identity of epoch r.epoch
  ```

  The seed is the `seed_signature` in any notarization, nullification, or
  finalization certificate for `r`.

Scope: block production, block verification, the header encoding, and the
`PREVRANDAO` value seen by the EVM. Consensus messages, the DKG, and the leader
election are unchanged.

```diagram
 round r_P                         round r_B (r_B > r_P)
┌────────────────────────┐        ┌───────────────────────────────────┐
│ block P certified       │        │ block B                           │
│ certificate carries     │──σ────▶│ parent_seed = σ(r_P)              │
│ σ(r_P)                  │        │ mix_hash    = keccak256(σ(r_P))   │
└────────────────────────┘        │ PREVRANDAO  = mix_hash            │
                                  └───────────────────────────────────┘
                                  votes in r_B leak σ(r_B), which only
                                  B's child exposes to execution
```

## Mechanics

### Activation

The rules below apply to a block `B` whose timestamp is at or after the
activating hardfork, called the fork below. A block before the fork keeps
today's rules: `mix_hash` is zero and the header has no `parent_seed`.

### Header field

`TempoHeader` gains a trailing optional field after `consensus_context`:

```rust
#[rlp(trailing(no_gaps))]
pub struct TempoHeader {
    pub general_gas_limit: u64,
    pub shared_gas_limit: u64,
    pub timestamp_millis_part: u64,
    pub inner: Header,
    pub consensus_context: Option<TempoConsensusContext>,
    /// Threshold-VRF seed of the parent block's round. `None` before the fork
    /// and when the parent has no consensus context.
    pub parent_seed: Option<ParentSeed>,
}
```

`ParentSeed` is the 48-byte compressed G1 encoding of `σ`, the commonware
`MinSig::Signature` encoding. It is RLP-encoded as a 48-byte string (49 bytes)
and as fixed bytes in `Compact`, and serialized in JSON as `parentSeed`, a
`0x`-prefixed hex string. Decoding MUST reject bytes that are not the canonical
compressed encoding of a G1 point in the prime-order subgroup. Canonical
encoding matters because the bytes are hashed into both `mix_hash` and the block
hash.

When `parent_seed` is `None`, it is omitted from the RLP stream. Pre-fork headers
encode and hash exactly as before. `no_gaps` means `parent_seed` can be `Some`
only if `consensus_context` is `Some`, which every post-fork block satisfies.

### Required values

For a post-fork block `B` with parent `P`:

| `P.consensus_context` | `B.parent_seed` | `B.mix_hash` |
| --- | --- | --- |
| `Some(ctx)` | `Some(σ(ctx.epoch, ctx.view))` | `keccak256(parent_seed)`, hashed over the 48 encoded bytes |
| `None` (only `P` = genesis) | `None` | `0x00…00` |

`B.inner.difficulty` stays zero, so the EVM's `PREVRANDAO` (`block_env.prevrandao`)
equals `B.mix_hash`.

### Block production

When the leader of round `r_B` builds on parent `P`:

1. Read the parent round `r_P` from `P.consensus_context`.
2. Get `σ(r_P)` from a certificate for `r_P`: the notarization or finalization
   that certified `P`. For the first block of an epoch, this is the boundary
   block's finalization in the previous epoch.
3. Set `prev_randao = keccak256(σ(r_P))` in `TempoPayloadAttributes`, which the
   builder writes to `mix_hash`, and set `parent_seed = σ(r_P)` in the header.

If the proposer cannot get `σ(r_P)`, it MUST NOT propose. It may fetch the
certificate through marshal and retry. Otherwise the view times out and is
nullified like any other missed proposal. The proposer MUST NOT fill in a
placeholder.

### Block verification

In `Automaton::verify`, next to the existing `consensus_context` check in
`verify_header`, a validator MUST reject `B` unless:

1. `B.parent_seed` and `B.mix_hash` match the [Required values](#required-values)
   table for the fork state at `B`'s timestamp and for `P.consensus_context`.
2. If `B.parent_seed` is `Some(σ)`, `σ` is a valid signature over `r_P` under
   the network identity of epoch `r_P.epoch`. Because threshold BLS signatures
   are unique, a validator MAY instead check that `σ` equals the seed in a
   certificate for `r_P` that it has already verified. The two checks are
   equivalent.

If the validator does not have the identity of epoch `r_P.epoch` or a verified
certificate for `r_P`, it abstains. It MUST NOT vote to accept or reject. This
mirrors the existing handling when DKG data is unavailable.

The execution layer's stateless header validation MUST check the fork-gated
presence of `parent_seed` and that `mix_hash == keccak256(parent_seed)`, or zero
when `parent_seed` is `None`. It MAY skip the BLS check because it has no epoch
identities. Followers that verify finalizations with `FinalizationVerifier`
already track per-epoch identities and SHOULD also verify `σ`.

### What is known, and when

Let `B` be at height `h` with parent round `r_P`. `PREVRANDAO(h) = keccak256(σ(r_P))`.

| Event | Who knows `PREVRANDAO(h)` |
| --- | --- |
| `f+1` honest votes cast in round `r_P` | A Byzantine coalition of up to `f`, while `P` (height `h-1`) is still undecided |
| `P` is notarized | Everyone. This is before `B` is proposed |
| `B` executes | Every transaction in `B` |

`PREVRANDAO` is therefore never a secret during the block that reads it. It is
safe only as the reveal of a commitment made earlier.

A seed `σ(e, v)` with `e > E` needs partial signatures from the committee of
epoch `e`. Honest members produce those only after the Simplex instance for
epoch `e` starts, and it starts only after the boundary block of epoch `e - 1`
is finalized. By induction, every block in epochs `≤ E` is finalized before any
seed of epoch `> E` can be recovered.

### Consuming the randomness

This section is guidance for applications. It is not consensus behavior.

A contract commits in a transaction at height `h_c` and later reveals using
`PREVRANDAO` at a target height `h_t` fixed at commit time. The commitment is
safe only if `h_c` is finalized before anyone can learn `PREVRANDAO(h_t)`. If
the seed is known earlier, the leader of `h_c`'s round, or the leader of a later
round that can still reorganize `h_c`, can choose whether and where the commit
lands.

| Binding | Safety | Latency |
| --- | --- | --- |
| `h_t ≥ last(epoch(h_c)) + 2`, so the target's parent is in a later epoch | Guaranteed under the threshold assumption, by the epoch argument above | Up to one epoch: 21,600 blocks on mainnet and testnet |
| `h_t = h_c + k` for a small `k ≥ 2` | Probabilistic. Safe once `h_c` is finalized before round `round(h_t - 1)` collects `f+1` honest votes, so larger `k` is safer | `k` blocks |
| `h_t ≤ h_c + 1` | Unsafe. `PREVRANDAO(h_c + 1)` is the seed of `h_c`'s own round | n/a |

The first block of epoch `E + 1` is excluded from the guaranteed row. Its parent
is the boundary block of epoch `E`, so its `PREVRANDAO` is a seed of epoch `E`
that can leak before that boundary is finalized.

Contracts can read `PREVRANDAO` only for the block they execute in. Two reveal
patterns work:

1. **Reveal in the target block.** The reveal transaction must be included at
   exactly `h_t`. This is fragile and only suitable when a keeper is guaranteed
   to land there.
2. **Reveal by header proof.** After `h_t`, anyone submits the RLP-encoded Tempo
   header of `h_t`. The contract checks `keccak256(rlp) == blockhash(h_t)`, using
   the `BLOCKHASH` opcode for the last 256 blocks or the EIP-2935 history
   contract for the last 8,191 blocks, and then reads `mix_hash` from the header.
   The header uses Tempo's encoding (`[general_gas_limit, shared_gas_limit,
   timestamp_millis_part, inner, consensus_context?, parent_seed?]`), not
   Ethereum's.

## Interfaces

- `TempoHeader.parent_seed: Option<ParentSeed>`. `ParentSeed` is 48 bytes; see
  [Header field](#header-field).
- JSON-RPC block headers gain `parentSeed` after the fork, and `mixHash`
  becomes non-zero.
- EVM: no new opcodes or precompiles. `PREVRANDAO` (0x44) returns `mix_hash`, as
  it does today.

# Compatibility

| Integration | What changes |
| --- | --- |
| Header encoding and hashing | Post-fork headers carry a trailing 49-byte RLP field. Pre-fork hashes do not change. Everything that decodes `TempoHeader` must upgrade before the fork: nodes, the alloy RPC types in `crates/alloy`, and `TempoHeader::decode` in zone precompiles (`crates/zones/precompiles/src/tempo_state.rs`, TIP-1096). |
| Contracts reading `PREVRANDAO` / `block.prevrandao` / `block.difficulty` | Values become non-zero and change every block. Contracts that assumed a zero value, for example as a sentinel, change behavior. Contracts using it as a secret are unsafe, as on Ethereum. See [Consuming the randomness](#consuming-the-randomness). |
| Payload building | `TempoPayloadAttributes` gets the seed from consensus and sets `prev_randao` and `parent_seed`. Builds that do not come from consensus, such as dev mode, have no seed and must stay pre-fork or use a test identity. |
| Deferred verification (T14) | No interaction beyond the header check. Blocks notarized optimistically are still checked before certification. |
| Zones | Zone blocks keep `mix_hash = 0` (`crates/zones/node/src/consensus.rs`). Zones can read Tempo randomness from imported Tempo headers. |
| Block explorers and indexers | Display `parentSeed`. No other change. |
| Devnets and e2e tests | Test networks already run the threshold scheme, so seeds exist. Test helpers that build headers by hand must set `parent_seed` and `mix_hash` for post-fork heights. |

# Observability

N/A for on-chain events: the header already exposes `parentSeed` and `mixHash`.

Nodes SHOULD export:

- A counter of proposals skipped because `σ(r_P)` was unavailable.
- A counter of verifications that abstained because the seed or epoch identity
  was unavailable.
- A counter of blocks rejected for a `parent_seed` or `mix_hash` mismatch, with
  the proposer logged.

A rising skip or abstain count points to certificate retention or fetch problems,
not to Byzantine behavior.

# Threat Model

The most consequential attack is a **Byzantine leader who learns a seed early
and front-runs a naive consumer.** A contract that settles a bet with
`PREVRANDAO` at the commit height, or at the next height, gives the leader of
round `r` a free option. Once `f+1` honest votes are in, the leader knows
`σ(r)`, which is `PREVRANDAO` of the next height. It can then choose among up to
`f+1` candidate blocks, or nullification, to decide which commits land at that
height. The protocol cannot prevent this. Applications must bind to a future
height as described in [Consuming the randomness](#consuming-the-randomness).

| Actor | Controls | Trusted to | Enforcing check | Consequence of failure |
| --- | --- | --- | --- | --- |
| Leader of `r_B` | Contents of `B`, `parent_seed` | Nothing about `σ` | Verification step 2. `σ(r_P)` is unique, so the leader has no choice | A forged or substituted seed is rejected and the view is nullified |
| Byzantine leader of `r` | Whether round `r` produces a certified block or a nullification | Nothing | None. This is inherent to Simplex | **Withholding bias.** After learning `σ(r)`, it can force a nullification so that `σ(r)` is never used as `PREVRANDAO`. That height then gets a seed from a later round that the leader does not yet know. This is a one-bit bias per Byzantine-led round, comparable to RANDAO's last-revealer bias. Consecutive Byzantine leaders get more options |
| Coalition of up to `f` validators | Their shares | Not to reach threshold | Threshold `2f+1` | Learns `σ(r)` early, as above, but cannot change it |
| Coalition of `2f+1` or more shares | All seeds of the epoch | — | None | Predicts every seed of the epoch. Consensus safety is already lost |
| Transaction senders and searchers | Transaction ordering bids | Nothing | None | Everyone knows `PREVRANDAO(h)` once the parent is notarized and can simulate against it |
| Contract developers | How randomness is consumed | To follow commit-then-reveal | Documentation only | Same-block or next-block use is exploitable, as above |

Excluded: randomness that stays secret at execution time, which would need the
"instant VRF" or timelock encryption, and bias resistance beyond the withholding
bias above.

# Invariants

1. **Presence.** For every post-fork block `B` with parent `P`,
   `B.parent_seed.is_some() == P.consensus_context.is_some()`. Pre-fork blocks
   have `parent_seed == None` and `mix_hash == 0`.
2. **Binding.** `B.mix_hash == keccak256(B.parent_seed)` when `parent_seed` is
   `Some`, and zero otherwise.
3. **Validity.** `B.parent_seed` is the threshold signature over the parent
   round `(P.ctx.epoch, P.ctx.view)` under namespace `TEMPO_SEED` and the
   network identity of `P.ctx.epoch`.
4. **Epoch boundary.** For the first block of an epoch, the parent round is the
   boundary block's round in the previous epoch, never `(e, 0)`.
5. **Encoding.** Pre-fork header hashes are unchanged. `parent_seed` round-trips
   through RLP, `Compact`, and serde. Non-canonical or off-subgroup G1 bytes fail
   decoding.
6. **EVM.** `PREVRANDAO` executed in `B` returns `B.mix_hash`.

### Test coverage

- Header RLP, `Compact`, and serde round-trips with and without `parent_seed`,
  and a pre-fork header hash fixture that does not change.
- Decoding rejects 48-byte strings that are not canonical, not on the curve, or
  not in the subgroup.
- Verification rejects: a missing seed after the fork, a seed present before the
  fork, the seed of the wrong round (for example `B`'s own round, or
  `(e, parent_view)` when it differs from the parent header's round), a seed
  under the wrong epoch identity, and `mix_hash` not equal to
  `keccak256(parent_seed)`.
- An e2e test across an epoch boundary: the first block of epoch `e + 1` carries
  the boundary block's seed from epoch `e` and verifies, including after a full
  DKG that changes the identity.
- An e2e test with nullified views: the block after a nullification uses the seed
  of its actual parent's round, not of the nullified view.
- Fork activation: the first post-fork block on a running chain carries a seed;
  block 1 on a chain with the fork at genesis carries none.
- An EVM test that `PREVRANDAO` returns `mix_hash`.
