# TIP-1112: EOA Root-Key Disablement

## Abstract

This TIP disables an account's bare primitive root authority once its configuration commitment becomes nonzero. From T14, protocol checks use that commitment to reject the old root as an independent authority. No separate retirement flag is stored.

The account instead acts through its current owner configuration or an authorised access key. A retired root can remain an explicit owner, contributing only its configured weight inside a valid multisig witness. Root disablement does not revoke access-key grants.

The check covers transaction roles and protocol precompiles, including previously signed permits and channel vouchers submitted after disablement. Pure signature recovery remains unchanged. Applications that infer authority from a recovered address need their own check. Disablement neither adds a post-quantum signature scheme nor changes root authority on other chains.

## Motivation

An old root key must not bypass an account's configured owners. Existing accounts need to retire that independent authority when they migrate. Post-quantum account protection also requires a suitable signature scheme beyond this TIP.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| [TIP-1108](./tip-1108.md) prevents execution from clearing a nonzero commitment. | Clearing the commitment could restore bare root authority. |
| This TIP activates with configurable accounts and [TIP-1113](./tip-1113.md) migration at T14. | A migration without root disablement would leave the old root able to bypass the new owners. |

# Specification

## Overview

**Bare root authority** means accepting a primitive key as controlling the account at its own address, without a configuration witness. A commitment check distinguishes that authority from an explicit owner's approval.

| Signature role | Effect of a nonzero commitment |
|---|---|
| Bare primitive root | Cannot authorise protocol actions independently. |
| Root listed as an owner | Contributes its configured weight inside a valid multisig witness. |
| Access key acting for a parent | Checks the signing delegate's key ID, not the parent's commitment. |
| Pure signature recovery | Still recovers the signer; does not establish account authority. |

For example, an account migrates to a 1-of-1 configuration that retains its original key at weight one and threshold one. That key can approve a transaction inside the version-one multisig witness. Its bare signature no longer authorises a transaction or a protocol permit.

These rules cover protocol authority. They do not add multisig formats to permits or vouchers, or guarantee that applications recognise root retirement.

## Authority check

Once this TIP activates, read the recovered primitive address's account-leaf commitment before accepting it as direct authority.

- If the commitment is zero, preserve existing primitive-signature behavior.
- If it is nonzero, reject bare root authority with `RootKeyRetired(account)`.

Apply this check to every primitive-authority role:

- Direct transaction senders.
- Signers of key authorizations.
- Fee payers.
- Access-key identities.

For an access key, check the key ID supplying the signature. Do not apply this check to the parent account whose funds it accesses. A configurable parent may use active delegates under TIP-1111.

Check EIP-7702 and Tempo authorization-list authorities before changing delegation.

- Skip an ineligible entry where the existing authorization-list rules require skipping.
- That entry must never install or remove delegation for the retired account.
- Existing skipped keychain entries remain skipped.

## Explicit owner signatures

A retired root key may still be explicitly listed as an owner.

- It signs inside a valid multisig witness.
- Its signature follows TIP-1114 and contributes only its configured weight.

Do not apply the bare-root check to these owner approvals. They prove an owner's approval with its configured weight.

A configurable account can pay its own normal transaction fees. It cannot sign as a separate primitive fee payer. This TIP does not add multisig fee-payer signatures.

## State ordering and permanence

Use the commitment at the transaction's position in the block.

- Migration authenticates before storing the commitment. After successful migration, later transactions cannot reuse the old root authority.
- If migration execution fails, its commitment and event revert under [TIP-1113](./tip-1113.md#installing-the-configuration). The original root authority remains unchanged; normal fee and nonce rules still apply.
- Pending transactions must be revalidated after commitment changes or reorgs. A cached zero is not proof of current authority.

[TIP-1114](./tip-1114.md#initial-use) stores the initial commitment before the first included transaction's calls execute, outside the execution rollback checkpoint.

- Root-key disablement applies during those calls and persists even if execution reverts or halts.
- Already registered configurable accounts become subject to root-key disablement when this TIP activates.
- An address that has only received funds is not yet registered. Its zero commitment does not disable root authority.

Existing access-key grants remain subject to TIP-1111. Root disablement does not revoke them.

Reads follow the normal account-access schedule.

- An already loaded commitment adds no separate read or surcharge.
- This TIP writes no state.

## Changes to other components

### Protocol precompiles

Once this TIP activates, every protocol precompile must apply the same check before treating a primitive signature or an implicit root-key match as account authority.

- TIP-20 `permit` checks the owner's commitment before granting an allowance.
- Channel vouchers check the commitment of the expected signer. This is the payer when no separate signer is set, otherwise the channel's authorized signer.
- `verifyKeychain` and `verifyKeychainAdmin` check the primitive signing key's commitment before accepting its authority.
- `isAdminKey` and internal admin checks must not treat `key_id == account` as implicit root authority when that account has a nonzero commitment.

Use the commitment at the time of the call, including changes made earlier in the same transaction.

- Operations that rely on retired root authority revert with `RootKeyRetired(account)` before changing state.
- Boolean authority checks return `false` for retired root authority.
- These rules also apply to signatures created before the root was disabled and submitted later by a relayer.

These checks also apply to [TIP-1137](https://github.com/tempoxyz/tempo/pull/8204)'s root-only helpers. A signer or key ID matching the account is insufficient once its root authority is retired.

Calls made by an account through an authenticated transaction still use its `msg.sender` authority. A nonzero commitment does not block those calls.

Pure signature checks remain unchanged, including `ecrecover` and TIP-1020 `recover` and `verify`. They prove who signed, not whether that signer currently controls an account. A protocol precompile using their result as authority must perform the commitment check itself.

Listing a retired root key as an owner does not make its bare signature valid for permits or vouchers.

### Applications and tooling

Root-key disablement is guaranteed only at the protocol level.

- Libraries, wallets, and dapps are not guaranteed to recognize that an EOA root key has been disabled.
- Permit2 and other dapps that use `ecrecover` need a separate check for root-key disablement before accepting the recovered address as account authority.
- Without that check, they may still accept signatures from the disabled key.

# Tooling

Distinguish retired-root errors from invalid signatures. A zero commitment does not by itself identify an ordinary EOA.

# Observability

No new event. Initial registration is visible in included transactions and account state, even if execution fails. Updates and migration have their own events. Validation errors should identify the retired account and authority role.

# Threat Model

The old root key may remain known or become compromised. Disablement must cover every protocol role through which that key could act independently.

It does not change offchain signatures or recovery on other chains.

# Invariants

- Initial registration leaves a nonzero commitment even if execution fails.
- Failed migration does not disable the original root authority.
- An account with a nonzero commitment has no bare root authority from T14.
- A retired root may contribute its configured weight as an explicit owner.
- Access-key authority checks apply to the signing delegate's key ID.
- A configurable parent's nonzero commitment does not itself reject an active delegate.
- Later transactions in the same block cannot reuse retired root authority in any protocol role.
- Skipped authorisation-list entries cannot install or remove delegation for the retired account.
- Permits, channel vouchers, and keychain authority checks use the commitment at call time, including changes earlier in the transaction.
- Relaying a signature created before disablement does not restore its authority.
