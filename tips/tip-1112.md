# TIP-1112: EOA Root-Key Disablement

## Abstract

Once an account stores a nonzero configuration commitment, its original key can no longer authorize actions on its own. This is called disabling the bare root key.

The account must instead use:

- Its current owner configuration.
- An explicitly authorized access key.

## Motivation

An old root key must not bypass the account's configured owners.

Disabling it allows existing accounts to migrate safely to configurable ownership. It is also a prerequisite for future post-quantum account protection.

## Assumptions

- [TIP-1108](./tip-1108.md) stores the configuration commitment in the account leaf.
- Once set, that commitment cannot be cleared.
- There is no separate disable flag or toggle API.

A newly derived account starts with a zero commitment, so this rule does not yet disable its root key. Its owners can establish a commitment with an ordinary TIP-1109 update, even if they keep the same owners.

## Threat Model

The old root key may still exist or become compromised.

- Its holder must not bypass the owners by signing as a fee payer, access key, or authorization-list authority.
- This TIP governs authority on Tempo. It does not change arbitrary offchain signatures or recovery wallets on other chains.

# Specification

## Authority check

From T13, read the recovered primitive address's account-leaf commitment before accepting it as direct authority.

- If the commitment is zero, preserve existing primitive-signature behavior.
- If it is nonzero, reject bare root authority with `RootKeyRetired(account)`.

Apply this check to every primitive-authority role:

- Direct transaction senders.
- Signers of key authorizations.
- Fee payers.
- Access-key identities.

For an access key, check the key ID supplying the signature. Do not apply this check to the parent account whose funds it accesses. A configurable parent may use active delegates under TIP-1111.

Check EIP-7702 and Tempo authorization-list authorities before changing delegation.

- Skip an ineligible entry where the existing authorization-list rules require skipping.
- That entry must never install or remove delegation for the retired account.
- Existing skipped keychain entries remain skipped.
- Every new primitive-authority path must also perform this check.

## Explicit owner signatures

A retired root key may still be explicitly listed as an owner.

- It signs inside a valid multisig witness.
- Its signature is bound to the configurable account, configuration version, and operation.
- It contributes only its configured weight.

Do not apply the bare-root check to these owner approvals. They prove an owner's approval, rather than granting the key independent authority over the account.

A configurable account can pay its own normal transaction fees. It cannot sign as a separate primitive fee payer. This TIP does not add multisig fee-payer signatures.

## State ordering and permanence

Use the commitment at the transaction's position in the block.

- A migration transaction uses the authority valid before migration.
- Later transactions cannot reuse that account's old root authority.
- Revalidate affected pending transactions after a commitment change or reorg.
- A cached zero commitment is not enough to establish current authority.

Root disablement is permanent once the commitment is nonzero.

- Rotation may add the original key as an explicit owner.
- Rotation cannot restore bare root signatures.
- Existing access-key grants are not automatically revoked. They still require a valid delegate signature and must obey TIP-1111.

Reads follow the normal account-access gas schedule.

- An already loaded commitment adds no separate storage read or surcharge.
- A newly accessed authority account incurs ordinary account-access gas.
- This TIP does not write configuration state.

# Tooling

- Distinguish a retired root key from an invalid signature.
- Do not treat a zero commitment as proof that an address is an ordinary EOA.
- Use owner-quorum signing after a commitment is created.
- Explain that disablement alone does not make the supported signing algorithms post-quantum secure.

# Observability

There is no new transition event. Configuration and migration events identify when a nonzero commitment is stored.

Validation errors should identify the retired account and the authority role it tried to use.

# Invariants

- Check every primitive-authority role, including keychain parent and delegate handling.
- Allow a retired root to approve as an explicitly listed owner.
- Preserve authorization-list skipping and self-funded transactions.
- Test same-block ordering and restoration after reorgs.
- Preserve zero-commitment behavior.
- Change no signature format or account behavior before T13.
