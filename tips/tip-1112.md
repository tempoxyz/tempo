# TIP-1112: EOA Root-Key Disablement

## Abstract

Once an account stores a nonzero configuration commitment, its original key can no longer authorize actions on its own. This is called disabling the bare root key.

The account must instead use:

- Its current owner configuration.
- An explicitly authorized access key.

## Motivation

An old root key must not bypass the account's configured owners.

Disabling it allows existing accounts to migrate safely to configurable ownership. It is also a prerequisite for future post-quantum account protection.

## Assumptions

[TIP-1108](./tip-1108.md) prevents a nonzero commitment from being cleared. This makes root disablement permanent without a separate flag or toggle.

## Threat Model

The old root key may remain known or become compromised. Disablement must cover every protocol role through which that key could act independently.

It does not change offchain signatures or recovery on other chains.

# Specification

## Authority check

From T13, read the recovered primitive address's account-leaf commitment before accepting it as direct authority.

- If the commitment is zero, preserve existing primitive-signature behavior.
- If it is nonzero, reject bare root authority with `RootKeyRetired(account)`.

Apply this check to every primitive-authority role:

- Direct transaction senders.
- Signers of key authorizations.
- Fee payers.
- Access-key identities.

For an access key, check the key ID supplying the signature. Do not apply this check to the parent account whose funds it accesses. A configurable parent may use active delegates under TIP-1111.

Check EIP-7702 and Tempo authorization-list authorities before changing delegation.

- Skip an ineligible entry where the existing authorization-list rules require skipping.
- That entry must never install or remove delegation for the retired account.
- Existing skipped keychain entries remain skipped.

## Explicit owner signatures

A retired root key may still be explicitly listed as an owner.

- It signs inside a valid multisig witness.
- Its signature follows TIP-1114 and contributes only its configured weight.

Do not apply the bare-root check to these owner approvals. They prove an owner's approval, rather than granting the key independent authority over the account.

A configurable account can pay its own normal transaction fees. It cannot sign as a separate primitive fee payer. This TIP does not add multisig fee-payer signatures.

## State ordering and permanence

Use the commitment at the transaction's position in the block.

- Migration authenticates before storing the commitment. Later transactions cannot reuse the old root authority.
- Pending transactions must be revalidated after commitment changes or reorgs. A cached zero is not proof of current authority.

A newly derived account starts with a zero commitment, so its root is not yet disabled. Its owners can establish a commitment through TIP-1109, even with unchanged owners.

Existing access-key grants remain subject to TIP-1111. Root disablement does not revoke them.

Reads follow the normal account-access schedule.

- An already loaded commitment adds no separate read or surcharge.
- This TIP writes no state.

# Tooling

Distinguish retired-root errors from invalid signatures. A zero commitment does not by itself identify an ordinary EOA.

# Observability

No new event. Configuration and migration events identify commitment creation. Validation errors should identify the retired account and authority role.

# Invariants

- A retired root may contribute as an explicit owner, but cannot act independently.
- Check the delegate identity rather than rejecting its configurable parent.
- Test same-block disablement across all authority roles, including skipped authorization-list entries.
