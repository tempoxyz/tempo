# TIP-1112: EOA Root-Key Disablement

## Abstract

An account with a nonzero configuration commitment can no longer act through its bare primitive root key. Its authority comes from the current owner configuration or an explicitly authorized access key.

## Motivation

Without protocol enforcement, an old root key could bypass the configured owners. Disablement enables safe in-place migration and is a prerequisite for future post-quantum account protection.

## Assumptions

[TIP-1108](./tip-1108.md) provides an authenticated commitment that cannot be cleared. This TIP introduces no independent disable flag or toggle API. Initial counterfactual accounts with zero commitment are not marked disabled; their quorum can make an ordinary TIP-1109 update, even with unchanged owners, to establish a commitment.

## Threat Model

The old key may still exist or become compromised. Its holder must not bypass configuration by acting as a fee payer, delegate, or authorization-list authority. This rule governs protocol authority, not arbitrary offchain signatures or another chain's recovery wallet.

# Specification

## Authority check

From T12, before accepting a recovered primitive address as direct authority, read its account-leaf commitment. Zero preserves existing primitive behavior; nonzero rejects bare root authority with `RootKeyRetired(account)`.

Apply this check to direct transaction senders, primitive signed-key authorizers, primitive fee payers, and primitive access-key identities. For access keys, check the key ID supplying the signature, not the parent whose funds it accesses. A configurable parent is allowed to use active delegates under TIP-1111.

Apply the same check to EIP-7702 and Tempo authorization-list authorities before any delegation mutation. An ineligible entry is skipped where the existing authorization-list rules require skipping; it must never install or remove delegation for that account. Existing skipped keychain entries remain skipped. No new primitive-authority path may omit the check.

## Explicit owner signatures

A retired primitive key may still sign as an explicitly listed owner inside a valid multisig witness. That signature is bound to the configurable account, its version, and the operation; it contributes only its configured weight. Do not apply the bare-root check recursively to primitive owner approvals, which authenticate keys rather than granting independent account authority.

A configurable account can still pay its own normal transaction fees. It cannot act as a separate primitive-signed fee payer; this TIP does not add multisig fee-payer signatures.

## State ordering and permanence

Validate against the commitment at the transaction's block position. An upgrade transaction authenticates under pre-upgrade authority, but later transactions cannot reuse its old root authority. Revalidate all affected pending authority roles after a commitment change or reorg; a cached zero is not sufficient proof.

Once nonzero, the commitment cannot return to zero. Rotation may explicitly add the original key as an owner but cannot re-enable bare root signatures. Access-key grants are not automatically revoked; each still needs a valid delegate signature and must obey TIP-1111.

Reads use the normal account-access schedule. A commitment already present in the loaded account adds no separate storage read or surcharge; newly accessed authority accounts incur ordinary account-access gas. No configuration is written by this TIP.

# Tooling

Distinguish a retired root from an invalid signature. A zero commitment does not prove an address is an ordinary EOA. Wallets must use owner-quorum signing after commitment creation and explain that disablement alone does not make currently supported signing algorithms post-quantum secure.

# Observability

No new transition event: configuration and migration events identify nonzero commitments. Validation errors should identify the retired account and authority role.

# Invariants

Test every primitive-authority role, explicit root-as-owner, both keychain parent and delegate roles, delegation-list skipping, self-funded transactions, same-block ordering, reorg restoration, and zero-commitment compatibility. No signature format or existing account changes before T12.
