# TIP-1112: EOA Root-Key Disablement

## Abstract

This TIP rejects bare primitive root authority when the account's configuration commitment is nonzero. From T14, protocol consumers check that commitment; no separate retirement flag is stored.

Account actions use the current owner configuration or an active access grant. A retired root can contribute its configured weight inside a valid owner witness. Ordinary access grants survive; TIP-1137 separately revokes pre-T14 admin grants.

Checks apply at use, including to previously signed permits. [Funded-channel vouchers](#protocol-precompiles) stay redeemable. Pure signature recovery and foreign-chain authority remain unchanged; applications using recovery need their own authority check. Post-quantum signature schemes are outside this TIP.

## Motivation

Migration needs this rule so the original key cannot bypass the installed owner quorum.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| [TIP-1108](./tip-1108.md) prevents execution from clearing a nonzero commitment. | Clearing the commitment could restore bare root authority. |
| This TIP activates with configurable accounts and [TIP-1113](./tip-1113.md) migration at T14. | A migration without root disablement would leave the old root able to bypass the new owners. |

# Specification

## Overview

**Bare root authority** means accepting a primitive key as controlling the account at its own address, without a configuration witness. Root retirement starts when the commitment becomes nonzero: through EOA migration or a derived account's first registration.

Later owner rotations replace a nonzero commitment with another nonzero value. They invalidate old configurations and versions under TIP-1114; they do not retire each removed owner's primitive key. This TIP closes the separate bare-root authorization path. Without it, a migrated EOA's original key could bypass the installed quorum.

| Signature role | Effect of a nonzero commitment |
|---|---|
| Bare primitive root | Rejected as independent protocol authority, except settlement against previously funded channel deposits. |
| Root listed as an owner | Contributes its configured weight inside a valid multisig witness. |
| Access key acting for a parent | Checks the signing delegate's key ID, not the parent's commitment. |
| Pure signature recovery | Still recovers the signer; does not establish account authority. |

For example, an account migrates to a 1-of-1 configuration that retains its original key at weight one and threshold one. That key can approve a transaction inside the version-one multisig witness. Its bare signature no longer authorises a transaction or a protocol permit.

These rules cover protocol authority. They do not add multisig formats to permits or vouchers, or guarantee that applications recognise root retirement.

## Authority check

Once this TIP activates, read the recovered primitive address's account-leaf commitment before accepting it as direct authority, with the funded-channel exception below.

- If the commitment is zero, preserve existing primitive-signature behavior.
- If it is nonzero, reject bare root authority with `RootKeyRetired(account)`.

Apply this check according to the authority context:

| Context | Commitment checked | State used | Result for retired root authority |
|---|---|---|---|
| Direct sender, key-authorization signer, or separate fee payer | Recovered primitive signing address | At the transaction's position in the block | Reject with `RootKeyRetired(account)`. |
| Access-key signature | Signing delegate's key ID | At the transaction's position in the block | Reject with `RootKeyRetired(account)`. |
| EIP-7702 or Tempo authorization-list entry | Entry's authority | Before changing delegation | Skip where the existing list rules require skipping; never install or remove delegation for the retired account. |
| Protocol operation using primitive authority | The signer required by that operation | At call time, including earlier changes in the transaction | Revert with `RootKeyRetired(account)` before changing state. |
| Boolean authority helper | The primitive signing key or implicit root-key identity | At call time, including earlier changes in the transaction | Return `false`. |
| Settlement of funded channel vouchers | No retirement check | Ordinary channel state | Retirement does not invalidate a voucher; other settlement checks still apply. |

For an access key, check the key ID supplying the signature. Do not apply this check to the parent account whose funds it accesses. A configurable parent may use active delegates under TIP-1111.

Existing skipped keychain authorization-list entries remain skipped.

## Explicit owner signatures

A retired root may sign as an explicit owner inside a valid TIP-1114 witness, contributing only its configured weight. Do not apply the bare-root check to these owner approvals.

A configurable account can pay its own normal transaction fees. It cannot sign as a separate primitive fee payer. This TIP does not add multisig fee-payer signatures.

## State ordering and permanence

- Migration authenticates before storing the commitment. After successful migration, later transactions cannot authenticate with its bare root signature.
- If migration execution fails, its commitment and event revert under [TIP-1113](./tip-1113.md#installing-the-configuration). The original root authority remains unchanged; normal fee and nonce rules still apply.
- Pending transactions must be revalidated after commitment changes or reorgs. A cached zero is not proof of current authority.

[TIP-1114](./tip-1114.md#onboarding) stores the initial commitment before the first included transaction's calls execute, outside the execution rollback checkpoint.

- Root-key disablement applies during those calls and persists even if execution reverts or halts.
- Already registered configurable accounts become subject to root-key disablement when this TIP activates.
- An address that has only received funds is not yet registered. Its zero commitment does not disable root authority.

Ordinary access-key grants remain subject to TIP-1111. Root disablement does not revoke them; TIP-1137's admin-grant revocation applies independently.

Reads follow the normal account-access schedule.

- An already loaded commitment adds no separate read or surcharge.
- This TIP writes no state.

## Changes to other components

### Protocol precompiles

Once this TIP activates, protocol precompiles must check retirement before treating a primitive signature or implicit root-key match as account authority. Funded-channel settlement is the explicit exception.

- TIP-20 `permit` checks the owner's commitment before granting an allowance.
- Channel `open` and nonzero `topUp` reject a retired voucher signer: the separate authorized signer, or the payer if none is set. Settlement preserves claims against existing deposits to the fixed payee, so migration cannot void the payee's vouchers.
- `verifyKeychain` and `verifyKeychainAdmin` check the primitive signing key's commitment before accepting its authority.
- `isAdminKey` and internal admin checks must not treat `key_id == account` as implicit root authority when that account has a nonzero commitment.

These call-time checks also reject signatures created before retirement, except channel vouchers.

Calls made by an account through an authenticated transaction still use its `msg.sender` authority. A nonzero commitment does not block those calls.

Pure signature checks (`ecrecover` and TIP-1020 `recover` and `verify`) remain unchanged. Protocol consumers must check the recovered signer's commitment before granting bare-root authority.

Listing a retired root key as an owner does not make its bare signature valid for permits, or for opening or topping up a channel.

# Compatibility

### Token approvals

TIP-20 rejects a retired root's `permit`; Phase 1 adds no quorum permit format. A configurable account can instead authorise an `approve(spender, amount)` transaction, optionally batched with the application call. The application must support direct approvals; this does not make a Permit2-signature-only flow compatible.

[Permit2](https://github.com/Uniswap/permit2/blob/cc56ad0f3439c502c246fc5cfcc3db92bb8b7219/src/libraries/SignatureVerification.sol) and similar applications enforce their own signature rules. If they use primitive recovery without checking retirement, the old key can still spend standing token allowances through them. Accepting native quorum signatures requires [TIP-1114's stateful verifier](./tip-1114.md#on-chain-signature-verification).

### Wallets and other authority domains

- Wallets and libraries must distinguish `RootKeyRetired` from an invalid signature. Signatures created before retirement do not remain valid merely because they were signed earlier.
- Prompt users to close channels whose voucher signer was retired, especially if that key may be compromised. Previously funded vouchers remain redeemable to the fixed payee; channels using that signer cannot be opened or topped up with a nonzero amount.
- Tempo retirement does not update application authentication caches, foreign-chain authority or Zone state. A migrated EOA's original key still controls its address on other chains and Zones; moving to a new Tempo quorum does not secure those balances.
- A zero commitment can describe an ordinary account or an unregistered derived account. Do not infer the account type from zero alone.

# Observability

No new event is added. Read the commitment at the selected state to determine whether bare root authority is retired.

- Initial registration is visible in the included transaction's witness and account state, even if execution fails.
- Migration emits `AccountUpgraded`; later owner updates emit `ConfigurableAccountConfigUpdated`. A reverted migration leaves the original root authority unchanged.
- Validation errors should identify the retired account and authority role. Pure signature recovery does not establish that authority.

# Threat Model

This TIP protects protocol authority even when the retired root is known to an attacker. Cryptographic recovery still succeeds; the consumer must enforce retirement before granting authority.

| Actor | Capability and trust boundary |
|---|---|
| Retired-root holder | Can still sign cryptographically. Current-commitment checks reject independent root authority except [funded-channel settlement](#protocol-precompiles). Explicit owner approvals contribute only their configured weight. |
| Protocol clients / precompiles | Trusted to check the correct primitive signer, including implicit root matches, at the specified state boundary. Missing a role or using a cached zero lets that role bypass the current quorum. |
| Application / authentication verifier | Controls its own acceptance rule. Pure recovery proves who signed, not current account authority; omitting retirement can let the old key use application permissions or standing allowances. |
| Relayer | Can submit a signature collected before retirement. Transaction-position or call-time checks reject it after retirement, except channel settlement; signature creation time grants no exemption. |
| Channel payer, payee and voucher signer | Migration cannot cancel the payee's claim against an existing deposit. Settlement keeps checking the channel's fixed signer and payee without checking retirement. A compromised retired signer can authorise vouchers against that deposit, but cannot redirect its payee or increase it. |
| Zone / foreign-chain verifier | Uses its own state and does not import this commitment rule. The old EOA key retains authority there; this TIP supplies no synchronization or foreign-chain revocation. |

Requiring channels to close before migration would need a per-signer index and delay migration. Preserved settlement instead leaves existing deposits exposed to their original signer until closed.

# Invariants

- Initial registration leaves a nonzero commitment even if execution fails.
- Failed migration does not disable the original root authority.
- From T14, a nonzero commitment rejects bare root authority except funded-channel settlement under the specified rules.
- A retired root may contribute its configured weight as an explicit owner.
- Access-key authority checks apply to the signing delegate's key ID.
- A configurable parent's nonzero commitment does not itself reject an active delegate.
- Later transactions in the same block cannot reuse retired root authority outside the funded-channel settlement exception.
- Skipped authorisation-list entries cannot install or remove delegation for the retired account.
- Permits, channel `open` and nonzero `topUp`, and keychain authority checks use the commitment at call time, including changes earlier in the transaction.
- Voucher settlement does not depend on the signer's commitment, and a retired signer's channel deposit cannot increase.
- Relaying a signature created before disablement does not restore its authority, except for channel vouchers.
