# TIP-1061: Configurable Accounts

## Abstract

Configurable accounts can change who controls them and their configuration without changing their identity. They support multisig control, recovery, key rotation, and permissioned access (via access keys) while remaining the same Tempo account to applications and counterparties.

## Motivation

Keys change. Account identity should not. A team should be able to change its members or control policy without replacing the account, and a lost or compromised key should not require moving assets to a new address.

Today, these needs typically require a contract wallet or external account abstraction system. Configurable accounts make them part of Tempo's account keychain model, giving wallets and applications one consistent way to serve individuals, teams, treasuries, validators, and institutions.

# Specification

## Types and Limits

```rust
/// Tempo signature type byte for configurable account signatures.
pub const SIGNATURE_TYPE_CONFIGURABLE_ACCOUNT: u8 = 0x05;

/// Domain prefix for configurable account owner approvals.
pub const CONFIGURABLE_ACCOUNT_SIGNATURE_DOMAIN: &[u8] = b"tempo:configurable-account";

/// Maximum number of owners in an account configuration.
pub const MAX_CONFIGURABLE_ACCOUNT_OWNERS: usize = 255;

/// Maximum threshold for one account configuration.
pub const MAX_CONFIGURABLE_ACCOUNT_THRESHOLD: u8 = 8;

/// Maximum number of owner approvals in one configurable account signature.
pub const MAX_CONFIGURABLE_ACCOUNT_SIGNATURES: usize =
    MAX_CONFIGURABLE_ACCOUNT_THRESHOLD as usize;

/// Maximum number of configurable account signatures in one nested authorization path.
pub const MAX_CONFIGURABLE_ACCOUNT_NESTING_DEPTH: usize = 2;

/// Maximum encoded byte length of one owner approval.
pub const MAX_CONFIGURABLE_ACCOUNT_OWNER_SIGNATURE_BYTES: usize =
    1 + MAX_WEBAUTHN_SIGNATURE_LENGTH;

/// Weighted owner in an account configuration.
pub struct ConfigurableAccountOwner {
    /// Address recovered from a primitive approval or named by a nested account approval.
    pub owner: Address,

    /// Nonzero weight contributed by this owner.
    pub weight: u8,
}

/// Initial owner configuration used to derive and bootstrap an account.
pub struct ConfigurableAccountInit {
    /// Caller-chosen value that permits distinct accounts with otherwise identical configurations.
    pub salt: B256,

    /// Minimum total owner weight required for authorization.
    pub threshold: u8,

    /// Strictly ascending weighted owners.
    pub owners: Vec<ConfigurableAccountOwner>,
}

/// Signature payload for a configurable account.
pub enum ConfigurableAccountSignature {
    /// Carries the initial configuration that derives the account.
    Bootstrap {
        /// Initial owner configuration.
        init: ConfigurableAccountInit,

        /// Ordered primitive or nested configurable account approvals.
        signatures: Vec<TempoSignature>,
    },

    /// Carries the account directly.
    Initialized {
        /// Account authorized by the owner approvals.
        account: Address,

        /// Ordered primitive or nested configurable account approvals.
        signatures: Vec<TempoSignature>,
    },
}
```

`MAX_CONFIGURABLE_ACCOUNT_OWNERS` bounds the stored owner set. Transaction validation is instead bounded by the threshold, submitted signature count, nesting depth, and per-approval byte limit. A top-level signature has depth 1, so depth 2 permits one initialized configurable account owner beneath it.

An owner configuration is valid when it has 1 through 255 strictly ascending, unique, nonzero owner addresses; every weight is nonzero; total weight is at most 255; and `1 <= threshold <= min(8, total_weight)`.

Each submitted owner approval:

- MUST be a `TempoSignature::Primitive` or `TempoSignature::ConfigurableAccount`.
- MUST NOT be a `TempoSignature::Keychain`.

## Signature Encoding

Signature type `0x05` has two canonical wire shapes:

- `bootstrap` derives and initializes a new account from its initial owner configuration.
- `initialized` authorizes an existing configurable account.

Each item in `signatures` is the existing byte encoding of a `TempoSignature`.

Decoders MUST reject trailing fields, malformed owner approvals, signatures beyond the limits above, and nested signatures deeper than `MAX_CONFIGURABLE_ACCOUNT_NESTING_DEPTH`.

Before T11, `TempoSignature::ConfigurableAccount` is invalid. At and after T11, `0x05` selects the encoding below.

### Bootstrap

```text
0x05 || rlp([init, signatures])

init  = rlp([salt, threshold, owners])
owner = rlp([owner, weight])
```

Only a top-level transaction bootstrap MAY use this encoding. The signature derives its account from `init`, binding the owner configuration to its approvals through the account included in `configurable_account_digest`.

### Initialized

```text
0x05 || rlp([account, signatures])
```

The initialized encoding carries the account directly. Nested owner approvals, account keychain signatures, and key authorization signatures MUST use this encoding.

## Account Identity

The initial configuration derives the account:

```text
account = address(keccak256(
  "tempo:configurable-account" ||
  salt ||
  uint8(threshold) ||
  uint8(owners.len()) ||
  owners[0].owner || uint8(owners[0].weight) ||
  ...
)[12:32])
```

The domain is the exact ASCII byte string shown. Every integer is one fixed-width byte, and the preimage is raw concatenation rather than RLP or ABI encoding. The chain ID is absent, so the same initial configuration derives the same address on every Tempo chain.

The derived address MUST be nonzero and outside Tempo's virtual-address and active precompile namespaces, including TIP-20 addresses. A different salt permits the same owners and threshold to derive another account.

The salt is used only for initial identity. Configuration updates replace the current threshold and owners without changing the account address.

## Authorization

Owners approve:

```text
configurable_account_digest = keccak256(
  "tempo:configurable-account" ||
  inner_digest ||
  account
)
```

For a direct transaction, `inner_digest` is `tx.signature_hash()`. If `parent_account` and `child_account` are initialized configurable accounts, and the child is an owner of the parent, a transaction is signed as follows:

```text
// Build a transaction from the parent configurable account.
tx = transaction(
  from = parent_account,
  calls = [...]
)

// Bind the transaction to the parent configurable account.
parent_digest = configurable_account_digest(
  tx.signature_hash(),
  parent_account
)

// Bind the parent approval to the child configurable account.
child_digest = configurable_account_digest(
  parent_digest,
  child_account
)

alice_signature = sign(alice_key, child_digest)
bob_signature   = sign(bob_key, child_digest)

// Use the child's configurable account signature as a parent owner approval.
child_approval =
  0x05 || rlp([
    child_account,
    [alice_signature, bob_signature]
  ])

// Attach the parent's configurable account signature.
tx.signature =
  0x05 || rlp([
    parent_account,
    [child_approval]
  ])
```

Primitive owners of the parent sign `parent_digest`; owners of the child sign `child_digest`. The account binding prevents an approval from being reused for another configurable account or as an ordinary primitive signature.

Validation processes approvals in strictly ascending recovered-owner order. Each owner must exist in the applicable initial or stored configuration. Validation accumulates current weights and succeeds exactly when the final submitted approval reaches quorum. Missing quorum, duplicate or unsorted owners, a cycle, or any approval after quorum makes the signature invalid.

Sender recovery follows these requirements:

- Stateless recovery MUST validate the signature shape and return the claimed account or the account derived from `init`.
- Stateless recovery MUST NOT treat owner membership or quorum as proven.
- Stateful validation MUST complete before the account is treated as an authorized sender.

## Transaction Execution

### Bootstrap

A bootstrap transaction:

- MUST use the bootstrap signature encoding.
- MUST target a derived account without a configurable account header.
- MAY target an account with a balance or existing protocol, 2D, or expiring nonce state when the transaction satisfies the selected nonce mode.
- MUST target an account with empty code and no EIP-7702 delegation.

The examples below assume `alice_address < bob_address`, each owner has weight 1, and the threshold is 2.

```text
// Define the initial owner configuration.
init = configurable_account_init(
  salt = salt,
  threshold = 2,
  owners = [
    [alice_address, 1],
    [bob_address, 1]
  ]
)

// Derive the new configurable account.
account = derive_configurable_account(init)

// Build the account's first transaction.
tx = transaction(
  from = account,
  calls = [...]
)

// Sign the account-bound transaction digest.
digest = configurable_account_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

// Attach the bootstrap signature containing the initial configuration.
tx.signature =
  0x05 || rlp([
    init,
    [alice_signature, bob_signature]
  ])
```

After the initial configuration and approvals validate, the protocol stores the account header, ordered owner rows, direct owner-weight rows, and emits `ConfigurableAccountInitialized`. These writes and normal nonce consumption are transaction-level effects. They remain committed if later EVM calls revert. Failed bootstrap validation writes nothing and consumes no nonce.

`updateAccountConfig` MUST reject the account bootstrapped earlier in the same transaction.

### Initialized

Every later direct transaction MUST use the initialized signature encoding and the configuration in state after all earlier transactions in the block.

A direct configurable account transaction executes with `tx.from`, `tx.origin`, and top-level `msg.sender` equal to the configurable account. It is authorized once for the full `tx.calls` batch. A successful owner update affects later transactions, not later calls in the already-authorized batch.

Configurable accounts cannot contain code or EIP-7702 delegation code and cannot appear as authorities in `tempo_authorization_list`. Bare configurable account signatures are invalid inside that list. The secp256k1-only fee-payer field cannot directly represent a configurable account; sponsored configurable account transactions use an ordinary fee payer and retain existing signing-hash behavior.

Transaction pools:

- MAY use stateless recovery for indexing.
- MUST revalidate pending direct and nested authorizations when an owner configuration they depend on changes.

## Storage

The configurable account precompile stores:

```text
accounts[account] = packed { threshold: u8, owner_count: u8 }
owners[account][index] = packed { owner: Address, weight: u8 }
owner_weights[account][owner] = weight
```

The header is both the account marker and the current quorum. `{0, 0}` is uninitialized; a header with only one zero field is invalid. Ordered rows support enumeration, while `owner_weights` lets authorization read only submitted owners. Replacing a configuration MUST clear stale ordered rows and lookup rows.

## Configurable Account Precompile

The precompile is deployed at `0xAACC000000000000000000000000000000000000` from T11.

```solidity
interface IConfigurableAccount {
    struct ConfigurableAccountOwner {
        address owner;
        uint8 weight;
    }

    struct AccountConfig {
        uint8 threshold;
        ConfigurableAccountOwner[] owners;
    }

    /// Returns whether account has a complete configurable account header.
    /// Reverts with InvalidConfig for a partial header.
    function isConfigurableAccount(address account) external view returns (bool);

    /// Returns account's current configuration.
    /// Reverts with NotConfigurableAccount or InvalidConfig.
    function getAccountConfig(
        address account
    ) external view returns (AccountConfig memory);

    /// Replaces msg.sender's current configuration.
    /// Requires direct current-quorum authorization and a top-level batch call.
    function updateAccountConfig(
        uint8 threshold,
        ConfigurableAccountOwner[] calldata owners
    ) external;

    event ConfigurableAccountInitialized(address indexed account);
    event AccountConfigUpdated(
        address indexed account,
        uint8 threshold,
        ConfigurableAccountOwner[] owners
    );

    error NotConfigurableAccount();
    error InvalidAccount();
    error InvalidConfig();
    error InvalidThreshold();
    error InvalidOwner();
    error InvalidWeight();
    error TooManyOwners();
    error DuplicateOwner();
    error InvalidOwnerOrder();
    error AccountAlreadyInitialized();
    error UnauthorizedCaller();
    error SameTransactionUpdateNotAllowed();
}
```

`updateAccountConfig` requires `msg.sender == tx.origin`, a zero account keychain transaction key, a complete existing account header, and an owner configuration that satisfies the limits above. It rejects nested `CALL`, `STATICCALL`, `DELEGATECALL`, and `CALLCODE`, and rejects an account initialized earlier in the same transaction. It accepts no separate authorization signature because the direct outer configurable account signature supplies current-quorum authority.

## Account Keychain

The account keychain signature-type enum gains one value without changing the existing values:

```solidity
enum SignatureType {
    Secp256k1, // 0
    P256,      // 1
    WebAuthn,  // 2
    ConfigurableAccount // 3
}
```

Where the account keychain currently accepts a primitive access key or key authorization signature, it:

- MUST accept either a primitive signature or a `ConfigurableAccountSignature` with the initialized encoding.
- MUST NOT accept a recursive `KeychainSignature` in those inner positions.

### Access Keys on Configurable Accounts

A configurable account may own ordinary or admin access keys. Its quorum may register them through an account keychain precompile call in a direct configurable account transaction or through transaction-level `key_authorization`, including during bootstrap. Existing expiry, spending-limit, call-scope, witness, admin, revocation, and event rules apply unchanged.

When the target account's owner quorum signs `key_authorization`, `SignedKeyAuthorization.signature` uses the initialized encoding with an account equal to the target account, and its owner approvals authorize:

```text
configurable_account_digest(key_authorization.signature_hash(), account)
```

Key authorization follows these requirements:

- The authorization MUST include an `account` equal to the target account.
- During bootstrap, validation MUST verify the nested signature against the outer signature's initial configuration.
- The nested signature MUST NOT include another `init`.
- The protocol MUST validate both bootstrap and key authorization before either takes effect.

An initialized configurable account used as an admin access key may sign `key_authorization` for its parent account under the existing admin-key rules. In that case, the authorization's `account` is the parent account and the signature's account is the configurable account access key. Same-transaction authorize-and-use is allowed after initialization when the outer account keychain signature uses the key being authorized.

An active access key for a configurable account uses the existing V2 account keychain envelope:

```text
0x04 || user_address || access_key_signature
```

`user_address` is the configurable account. The access key signs the existing V2 account keychain digest, and the transaction executes as `user_address` under the key's stored restrictions. This path does not re-run the parent account's owner quorum because the quorum delegated authority when it registered the key.

### Configurable Accounts as Access Keys

Any account, including another configurable account, MAY register a configurable account as an access key. The registration:

- MUST target an initialized configurable account.
- MUST use `key_type = ConfigurableAccount`.
- MUST use the configurable account as `key_id`.
- MUST omit `init` from the account keychain inner signature.

For a V2 account keychain transaction, owners of the access key configurable account authorize:

```text
keychain_digest = keccak256(0x04 || tx.signature_hash() || user_address)
configurable_account_digest(keychain_digest, key_id)
```

Validation uses the access key account's current owner configuration at the transaction's block position, then applies the parent account's stored access key status, type, expiry, limits, scopes, and admin flag. A configurable account used as an admin access key may perform TIP-1049 admin operations under the same signer-equals-transaction-key rules as a primitive admin key.

Verification follows these requirements:

- `verifyKeychain` and `verifyKeychainAdmin` MUST accept the initialized configurable account inner signature and perform the same stateful configurable account and account keychain checks.
- The stateless TIP-1020 `recover` and `verify` methods MUST reject a bare `TempoSignature::ConfigurableAccount`.

No access key, including an admin or configurable account access key, may call `updateAccountConfig` for its parent account. Only a direct outer `TempoSignature::ConfigurableAccount` with a zero account keychain transaction key may replace that account's owner set.

## Gas

Configurable account authorization is charged as regular intrinsic gas. Define a full primitive approval cost as 3,000 gas for secp256k1, 8,000 gas for P256, and `8,000 + calldata_gas(webauthn_data)` for WebAuthn.

```text
node(signature) =
    2,100
  + 2,100 * signature.signatures.len()
  + sum(full_primitive_cost(owner) or node(nested_owner))

direct_configurable_account_surcharge = node(outer_signature) - 3,000
```

The subtraction occurs once because ordinary Tempo intrinsic gas already prices one secp256k1 transaction signature. It does not occur for nested configurable account nodes or a configurable account key authorization sidecar. A configurable account wrapped by the account keychain pays the existing 3,000 gas account keychain validation surcharge plus `node(inner) - 3,000`.

A 1-of-1 secp256k1 configurable account therefore adds 4,200 gas; a 2-of-2 adds 9,300 gas. Direct configurable account authorization does not add the account keychain's 900 gas processing buffer.

Bootstrap additionally creates `1 + 2 * owners.len()` persistent slots: one packed header, one ordered row per owner, and one direct weight row per owner. It pays the active SSTORE regular and state gas for those slots plus a 1,500 gas event buffer. Precompile reads and updates use the active precompile storage schedule.

## Observability

| Event | Purpose |
| --- | --- |
| `ConfigurableAccountInitialized(account)` | Identifies the transaction that established configurable account state. |
| `AccountConfigUpdated(account, threshold, owners)` | Reconstructs owner and threshold rotation. |

Account keychain operations continue to emit the existing key authorization, admin authorization, revocation, restriction, and witness events, including when either the parent or access key is a configurable account.

## Examples

These examples show the canonical signing flows and the main authorization edge cases.

### Basic

An initialized 2-of-2 configurable account signs an ordinary transaction with both owner approvals.

```text
// Build a later transaction from the initialized account.
tx = transaction(
  from = account,
  calls = [...]
)

// Sign the account-bound transaction digest.
digest = configurable_account_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

// Attach the initialized signature containing the account address.
tx.signature =
  0x05 || rlp([
    account,
    [alice_signature, bob_signature]
  ])
```

### Fee Sponsorship

Fee sponsorship supports either signing order because the owners and fee payer sign separate digests.

Owners sign first:

```text
// Mark the transaction as sponsored before the owners sign.
tx = transaction(
  from = account,
  calls = [...],
  fee_payer_signature = placeholder
)

// Sign the sender digest, which omits the fee token.
digest = configurable_account_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

tx.signature =
  0x05 || rlp([
    account,
    [alice_signature, bob_signature]
  ])

// Select the fee token and authorize payment for this account.
tx.fee_token = fee_token
fee_payer_digest = tx.fee_payer_signature_hash(account)
tx.fee_payer_signature = sign_secp256k1(fee_payer_key, fee_payer_digest)
```

The fee payer signs first:

```text
// Build the transaction with the fee token selected.
tx = transaction(
  from = account,
  calls = [...],
  fee_token = fee_token
)

// Authorize payment for the known configurable account.
fee_payer_digest = tx.fee_payer_signature_hash(account)
tx.fee_payer_signature = sign_secp256k1(fee_payer_key, fee_payer_digest)

// Sign the sender digest after sponsorship is attached.
digest = configurable_account_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

tx.signature =
  0x05 || rlp([
    account,
    [alice_signature, bob_signature]
  ])
```

### Weighted Quorum

Owner weights determine which ordered approvals satisfy the threshold and when an extra approval is invalid.

Assume `alice_address < bob_address < carol_address`:

```text
threshold = 3
owners = [
  [alice_address, 2],
  [bob_address, 1],
  [carol_address, 1]
]

digest = configurable_account_digest(tx.signature_hash(), account)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)
carol_signature = sign(carol_key, digest)

// Valid: the final approval reaches the threshold.
signatures = [alice_signature, bob_signature]
signatures = [alice_signature, carol_signature]

// Invalid: the total weight is below the threshold.
signatures = [bob_signature, carol_signature]

// Invalid: Bob reaches the threshold before Carol's extra approval.
signatures = [alice_signature, bob_signature, carol_signature]
```

### Bootstrap with Key Authorization

A bootstrap transaction may initialize the configurable account and register an access key, but the access key cannot sign that bootstrap transaction.

```text
// Define and derive the new configurable account.
init = configurable_account_init(
  salt = salt,
  threshold = 2,
  owners = [
    [alice_address, 1],
    [bob_address, 1]
  ]
)

account = derive_configurable_account(init)

// Authorize a primitive access key for the new account.
authorization = key_authorization(
  chain_id = chain_id,
  account = account,
  key_type = Secp256k1,
  key_id = access_key_address
)

authorization_digest = configurable_account_digest(
  authorization.signature_hash(),
  account
)

authorization_signature =
  0x05 || rlp([
    account,
    [
      sign(alice_key, authorization_digest),
      sign(bob_key, authorization_digest)
    ]
  ])

// Include the signed key authorization in the bootstrap transaction.
tx = transaction(
  from = account,
  calls = [...],
  key_authorization = signed_key_authorization(
    authorization,
    authorization_signature
  )
)

// Authorize the complete transaction with the bootstrap encoding.
digest = configurable_account_digest(
  tx.signature_hash(),
  account
)

tx.signature =
  0x05 || rlp([
    init,
    [
      sign(alice_key, digest),
      sign(bob_key, digest)
    ]
  ])
```

After validation, the account is initialized and `access_key_address` is active. The access key may sign a later account keychain transaction for the configurable account.

### Configuration Rotation

The current quorum authorizes an owner update, which preserves the account address and applies to later transactions.

Assume Alice and Bob are both required. They replace themselves with Carol:

```text
// Build a top-level owner update.
rotate_tx = transaction(
  from = account,
  calls = [
    updateAccountConfig(
      threshold = 1,
      owners = [[carol_address, 1]]
    )
  ]
)

// The current owners authorize the update.
rotate_digest = configurable_account_digest(
  rotate_tx.signature_hash(),
  account
)

rotate_tx.signature =
  0x05 || rlp([
    account,
    [
      sign(alice_key, rotate_digest),
      sign(bob_key, rotate_digest)
    ]
  ])

execute(rotate_tx)

// The next transaction uses Carol and keeps the same account address.
next_tx = transaction(
  from = account,
  calls = [...]
)

next_digest = configurable_account_digest(
  next_tx.signature_hash(),
  account
)

next_tx.signature =
  0x05 || rlp([
    account,
    [sign(carol_key, next_digest)]
  ])
```

## Backwards Compatibility

This TIP adds no transaction field. Existing primitive, account keychain, key authorization, fee-payer, and authorization-list encodings retain their current field positions. Signature type values 0 through 2 are unchanged; value 3 is newly valid for configurable accounts used as access keys.

Transactions that do not use configurable accounts remain byte-identical. Configurable account signatures are rejected before T11. Existing EOAs are not upgraded in place; moving assets or application state to a derived configurable account uses existing application flows.

## Invariants

1. A bootstrap signature derives exactly one eligible account from its initial owner set; later updates never change that address.
2. Bootstrap uses `rlp([init, signatures])`; every other configurable account signature context uses `rlp([account, signatures])`.
3. Every accepted approval path is cycle-free, within depth and size limits, strictly ordered, and ends exactly at the current weighted quorum.
4. Consensus authorization uses the owner configuration in state at the transaction's block position. Pools revalidate direct and nested dependencies after rotation.
5. A configurable account never has EVM code, delegation code, or direct fee-payer authority.
6. Access keys may act for a configurable account, and initialized configurable accounts may act as access keys, but no access key path may replace a configurable account's owner set.
7. Bootstrap config and nonce writes survive later call reverts; failed bootstrap validation changes no state.
8. Intrinsic gas prices every submitted primitive or nested approval and every bootstrap storage row.
