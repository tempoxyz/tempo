# TIP-1061: Native Multisig Accounts

## Abstract

This TIP adds native multisig accounts. An account address is derived from an initial weighted owner configuration and a caller-chosen salt. Transactions are authorized against the current configuration by primitive or nested multisig approvals whose weights meet the threshold.

## Motivation

Teams, treasuries, validators, and institutions need stable accounts whose funds and configuration cannot be controlled by one key. Contract wallets provide this model, but they require deployment and make account behavior depend on contract code.

Native validation provides the core weighted-threshold model without a wallet contract. Integration with the account keychain keeps the existing delegation model available when a quorum intentionally grants narrower or administrative authority to another key.

# Specification

## Types and Limits

```rust
/// Tempo signature type byte for native multisig signatures.
pub const SIGNATURE_TYPE_MULTISIG: u8 = 0x05;

/// Domain prefix for native multisig owner approvals.
pub const MULTISIG_SIGNATURE_DOMAIN: &[u8] = b"tempo:multisig:signature";

/// Maximum number of owners in a native multisig configuration.
pub const MAX_MULTISIG_OWNERS: usize = 255;

/// Maximum threshold for one native multisig configuration.
pub const MAX_MULTISIG_THRESHOLD: u8 = 8;

/// Maximum number of owner approvals in one multisig signature.
pub const MAX_MULTISIG_SIGNATURES: usize = MAX_MULTISIG_THRESHOLD as usize;

/// Maximum number of multisig signatures in one nested authorization path.
pub const MAX_MULTISIG_NESTING_DEPTH: usize = 2;

/// Maximum encoded byte length of one owner approval.
pub const MAX_MULTISIG_OWNER_SIGNATURE_BYTES: usize = 1 + MAX_WEBAUTHN_SIGNATURE_LENGTH;

/// Weighted owner in a native multisig configuration.
pub struct MultisigOwner {
    /// Address recovered from a primitive approval or named by a nested multisig approval.
    pub owner: Address,

    /// Nonzero weight contributed by this owner.
    pub weight: u8,
}

/// Initial configuration used to derive and bootstrap a native multisig account.
pub struct InitMultisig {
    /// Caller-chosen value that permits distinct accounts with otherwise identical configurations.
    pub salt: B256,

    /// Minimum total owner weight required for authorization.
    pub threshold: u8,

    /// Strictly ascending weighted owners.
    pub owners: Vec<MultisigOwner>,
}

/// Native multisig signature payload.
pub enum MultisigSignature {
    /// Carries the initial configuration that derives the account.
    Bootstrap {
        /// Initial account configuration.
        init: InitMultisig,

        /// Ordered primitive or nested multisig owner approvals.
        signatures: Vec<TempoSignature>,
    },

    /// Carries the account directly.
    Initialized {
        /// Account authorized by the owner approvals.
        account: Address,

        /// Ordered primitive or nested multisig owner approvals.
        signatures: Vec<TempoSignature>,
    },
}
```

`MAX_MULTISIG_OWNERS` bounds stored configuration size. Transaction validation is instead bounded by the threshold, submitted signature count, nesting depth, and per-approval byte limit. A top-level signature has depth 1, so depth 2 permits one initialized multisig owner beneath it.

A configuration is valid when it has 1 through 255 strictly ascending, unique, nonzero owner addresses; every weight is nonzero; total weight is at most 255; and `1 <= threshold <= min(8, total_weight)`.

Each submitted owner approval:

- MUST be a `TempoSignature::Primitive` or `TempoSignature::Multisig`.
- MUST NOT be a `TempoSignature::Keychain`.

## Signature Encoding

Signature type `0x05` has two canonical wire shapes:

- `bootstrap` derives and initializes a new multisig account from its initial configuration.
- `initialized` authorizes an existing multisig account.

Each item in `signatures` is the existing byte encoding of a `TempoSignature`.

Decoders MUST reject trailing fields, malformed owner approvals, signatures beyond the limits above, and nested signatures deeper than `MAX_MULTISIG_NESTING_DEPTH`.

Before T11, `TempoSignature::Multisig` is invalid. At and after T11, `0x05` selects the encoding below.

### Bootstrap

```text
0x05 || rlp([init, signatures])

init  = rlp([salt, threshold, owners])
owner = rlp([owner, weight])
```

Only a top-level transaction bootstrap MAY use this encoding. The signature derives its account from `init`, binding the configuration to its approvals through the account included in `multisig_digest`.

### Initialized

```text
0x05 || rlp([account, signatures])
```

The initialized encoding carries the account directly. Nested owner approvals, account keychain signatures, and key authorization signatures MUST use this encoding.

## Account Identity

The initial configuration derives the account:

```text
account = address(keccak256(
  "tempo:multisig:account" ||
  salt ||
  uint8(threshold) ||
  uint8(owners.len()) ||
  owners[0].owner || uint8(owners[0].weight) ||
  ...
)[12:32])
```

The domain is the exact ASCII byte string shown. Every integer is one fixed-width byte, and the preimage is raw concatenation rather than RLP or ABI encoding. The chain ID is absent, so the same initial configuration derives the same address on every Tempo chain.

The derived address MUST be nonzero and outside Tempo's virtual-address and active precompile namespaces, including TIP-20 addresses. A different salt permits the same owners and threshold to derive another account.

The salt is used only for initial identity. Configuration updates replace the current threshold and owners without changing the account address.

## Authorization

Owners approve:

```text
multisig_digest = keccak256(
  "tempo:multisig:signature" ||
  inner_digest ||
  account
)
```

For a direct transaction, `inner_digest` is `tx.signature_hash()`. If `parent_account` and `child_account` are initialized multisigs, and the child is an owner of the parent, a transaction is signed as follows:

```text
// Build a transaction from the parent multisig.
tx = transaction(
  from = parent_account,
  calls = [...]
)

// Bind the transaction to the parent multisig.
parent_digest = multisig_digest(
  tx.signature_hash(),
  parent_account
)

// Bind the parent approval to the child multisig.
child_digest = multisig_digest(
  parent_digest,
  child_account
)

alice_signature = sign(alice_key, child_digest)
bob_signature   = sign(bob_key, child_digest)

// Use the child multisig signature as a parent owner approval.
child_approval =
  0x05 || rlp([
    child_account,
    [alice_signature, bob_signature]
  ])

// Attach the parent multisig signature.
tx.signature =
  0x05 || rlp([
    parent_account,
    [child_approval]
  ])
```

Primitive owners of the parent sign `parent_digest`; owners of the child sign `child_digest`. The account binding prevents an approval from being reused for another multisig or as an ordinary primitive signature.

Validation processes approvals in strictly ascending recovered-owner order. Each owner must exist in the applicable initial or stored configuration. Validation accumulates current weights and succeeds exactly when the final submitted approval reaches quorum. Missing quorum, duplicate or unsorted owners, a cycle, or any approval after quorum makes the signature invalid.

Sender recovery follows these requirements:

- Stateless recovery MUST validate the signature shape and return the claimed account or the account derived from `init`.
- Stateless recovery MUST NOT treat owner membership or quorum as proven.
- Stateful validation MUST complete before the account is treated as an authorized sender.

## Transaction Execution

### Bootstrap

A bootstrap transaction:

- MUST use the bootstrap signature encoding.
- MUST target a derived account without a native multisig header.
- MAY target an account with a balance or existing protocol, 2D, or expiring nonce state when the transaction satisfies the selected nonce mode.
- MUST target an account with empty code and no EIP-7702 delegation.

The examples below assume `alice_address < bob_address`, each owner has weight 1, and the threshold is 2.

```text
// Define the initial owner configuration.
init = multisig_init(
  salt = salt,
  threshold = 2,
  owners = [
    [alice_address, 1],
    [bob_address, 1]
  ]
)

// Derive the new multisig account.
account = derive_multisig_account(init)

// Build the account's first transaction.
tx = transaction(
  from = account,
  calls = [...]
)

// Sign the account-bound transaction digest.
digest = multisig_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

// Attach the bootstrap signature containing the initial configuration.
tx.signature =
  0x05 || rlp([
    init,
    [alice_signature, bob_signature]
  ])
```

After the initial configuration and approvals validate, the protocol stores the account header, ordered owner rows, direct owner-weight rows, and emits `MultisigInitialized`. These writes and normal nonce consumption are transaction-level effects. They remain committed if later EVM calls revert. Failed bootstrap validation writes nothing and consumes no nonce.

`updateMultisigConfig` MUST reject the account bootstrapped earlier in the same transaction.

### Initialized

Every later direct transaction MUST use the initialized signature encoding and the configuration in state after all earlier transactions in the block.

A direct multisig transaction executes with `tx.from`, `tx.origin`, and top-level `msg.sender` equal to the native multisig account. It is authorized once for the full `tx.calls` batch. A successful configuration update affects later transactions, not later calls in the already-authorized batch.

Native multisig accounts cannot contain code or EIP-7702 delegation code and cannot appear as authorities in `tempo_authorization_list`. Bare multisig signatures are invalid inside that list. The secp256k1-only fee-payer field cannot directly represent a native multisig; sponsored multisig transactions use an ordinary fee payer and retain existing signing-hash behavior.

Transaction pools:

- MAY use stateless recovery for indexing.
- MUST revalidate pending direct and nested multisig authorizations when any depended-on configuration changes.

## Storage

The native multisig precompile stores:

```text
accounts[account] = packed { threshold: u8, owner_count: u8 }
owners[account][index] = packed { owner: Address, weight: u8 }
owner_weights[account][owner] = weight
```

The header is both the account marker and the current quorum. `{0, 0}` is uninitialized; a header with only one zero field is invalid. Ordered rows support enumeration, while `owner_weights` lets authorization read only submitted owners. Replacing a configuration MUST clear stale ordered rows and lookup rows.

## Native Multisig Precompile

The precompile is deployed at `0xAACC000000000000000000000000000000000000` from T11.

```solidity
interface INativeMultisig {
    struct MultisigOwner {
        address owner;
        uint8 weight;
    }

    struct MultisigConfig {
        uint8 threshold;
        MultisigOwner[] owners;
    }

    /// Returns whether account has a complete native multisig header.
    /// Reverts with InvalidConfig for a partial header.
    function isMultisigAccount(address account) external view returns (bool);

    /// Returns account's current configuration.
    /// Reverts with NotMultisigAccount or InvalidConfig.
    function getMultisigConfig(
        address account
    ) external view returns (MultisigConfig memory);

    /// Replaces msg.sender's current configuration.
    /// Requires direct current-quorum authorization and a top-level batch call.
    function updateMultisigConfig(
        uint8 threshold,
        MultisigOwner[] calldata owners
    ) external;

    event MultisigInitialized(address indexed account);
    event MultisigConfigUpdated(
        address indexed account,
        uint8 threshold,
        MultisigOwner[] owners
    );

    error NotMultisigAccount();
    error InvalidAccount();
    error InvalidConfig();
    error InvalidThreshold();
    error InvalidOwner();
    error InvalidWeight();
    error TooManyOwners();
    error DuplicateOwner();
    error InvalidOwnerOrder();
    error AccountAlreadyInitialized();
    error UnauthorizedCaller();
    error SameTransactionUpdateNotAllowed();
}
```

`updateMultisigConfig` requires `msg.sender == tx.origin`, a zero account keychain transaction key, a complete existing native multisig header, and a configuration that satisfies the limits above. It rejects nested `CALL`, `STATICCALL`, `DELEGATECALL`, and `CALLCODE`, and rejects an account initialized earlier in the same transaction. It accepts no separate authorization signature because the direct outer multisig signature supplies current-quorum authority.

## Account Keychain

The account keychain signature-type enum gains one value without changing the existing values:

```solidity
enum SignatureType {
    Secp256k1, // 0
    P256,      // 1
    WebAuthn,  // 2
    Multisig   // 3
}
```

Where the account keychain currently accepts a primitive access key or key authorization signature, it:

- MUST accept either a primitive signature or a `MultisigSignature` with the initialized encoding.
- MUST NOT accept a recursive `KeychainSignature` in those inner positions.

### Access Keys on Multisig Accounts

A native multisig account may own ordinary or admin access keys. Its quorum may register them through an account keychain precompile call in a direct multisig transaction or through transaction-level `key_authorization`, including during bootstrap. Existing expiry, spending-limit, call-scope, witness, admin, revocation, and event rules apply unchanged.

When the target account's multisig quorum signs `key_authorization`, `SignedKeyAuthorization.signature` uses the initialized multisig encoding with an account equal to the target account, and its owner approvals authorize:

```text
multisig_digest(key_authorization.signature_hash(), account)
```

Key authorization follows these requirements:

- The authorization MUST include an `account` equal to the target account.
- During bootstrap, validation MUST verify the nested signature against the outer signature's initial configuration.
- The nested signature MUST NOT include another `init`.
- The protocol MUST validate both bootstrap and key authorization before either takes effect.

An initialized multisig admin access key may sign `key_authorization` for its parent account under the existing admin-key rules. In that case, the authorization's `account` is the parent account and the signature's account is the multisig access key. Same-transaction authorize-and-use is allowed after initialization when the outer account keychain signature uses the key being authorized.

An active access key for a native multisig account uses the existing V2 account keychain envelope:

```text
0x04 || user_address || access_key_signature
```

`user_address` is the native multisig account. The access key signs the existing V2 account keychain digest, and the transaction executes as `user_address` under the key's stored restrictions. This path does not re-run the parent account's owner quorum because the quorum delegated authority when it registered the key.

### Multisig Access Keys

Any account, including another native multisig, MAY register a native multisig as an access key. The registration:

- MUST target an initialized native multisig.
- MUST use `key_type = Multisig`.
- MUST use the multisig account as `key_id`.
- MUST omit `init` from the account keychain inner signature.

For a V2 account keychain transaction, owners of the access key multisig authorize:

```text
keychain_digest = keccak256(0x04 || tx.signature_hash() || user_address)
multisig_digest(keychain_digest, key_id)
```

Validation uses the access key multisig's current configuration at the transaction's block position, then applies the parent account's stored access key status, type, expiry, limits, scopes, and admin flag. A multisig admin access key may perform TIP-1049 admin operations under the same signer-equals-transaction-key rules as a primitive admin key.

Verification follows these requirements:

- `verifyKeychain` and `verifyKeychainAdmin` MUST accept the initialized multisig inner signature and perform the same stateful multisig and account keychain checks.
- The stateless TIP-1020 `recover` and `verify` methods MUST reject a bare `TempoSignature::Multisig`.

No access key, including an admin or multisig access key, may call `updateMultisigConfig` for its parent account. Only a direct outer `TempoSignature::Multisig` with a zero account keychain transaction key may replace that account's owner set.

## Gas

Native multisig verification is charged as regular intrinsic gas. Define a full primitive approval cost as 3,000 gas for secp256k1, 8,000 gas for P256, and `8,000 + calldata_gas(webauthn_data)` for WebAuthn.

```text
node(signature) =
    2,100
  + 2,100 * signature.signatures.len()
  + sum(full_primitive_cost(owner) or node(nested_owner))

direct_multisig_surcharge = node(outer_signature) - 3,000
```

The subtraction occurs once because ordinary Tempo intrinsic gas already prices one secp256k1 transaction signature. It does not occur for nested multisig nodes or a multisig key authorization sidecar. A multisig wrapped by the account keychain pays the existing 3,000 gas account keychain validation surcharge plus `node(inner) - 3,000`.

A 1-of-1 secp256k1 native multisig therefore adds 4,200 gas; a 2-of-2 adds 9,300 gas. Direct multisig authorization does not add the account keychain's 900 gas processing buffer.

Bootstrap additionally creates `1 + 2 * owners.len()` persistent slots: one packed header, one ordered row per owner, and one direct weight row per owner. It pays the active SSTORE regular and state gas for those slots plus a 1,500 gas event buffer. Precompile reads and updates use the active precompile storage schedule.

## Observability

| Event | Purpose |
| --- | --- |
| `MultisigInitialized(account)` | Identifies the transaction that established native multisig state. |
| `MultisigConfigUpdated(account, threshold, owners)` | Reconstructs owner and threshold rotation. |

Account keychain operations continue to emit the existing key authorization, admin authorization, revocation, restriction, and witness events, including when either the parent or access key is a multisig.

## Examples

These examples show the canonical signing flows and the main authorization edge cases.

### Basic

An initialized 2-of-2 multisig signs an ordinary transaction with both owner approvals.

```text
// Build a later transaction from the initialized account.
tx = transaction(
  from = account,
  calls = [...]
)

// Sign the account-bound transaction digest.
digest = multisig_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

// Attach the initialized signature containing the account address.
tx.signature =
  0x05 || rlp([
    account,
    [alice_signature, bob_signature]
  ])
```

### Fee Sponsorship

Fee sponsorship supports either signing order because the owners and fee payer sign separate digests.

Owners sign first:

```text
// Mark the transaction as sponsored before the owners sign.
tx = transaction(
  from = account,
  calls = [...],
  fee_payer_signature = placeholder
)

// Sign the sender digest, which omits the fee token.
digest = multisig_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

tx.signature =
  0x05 || rlp([
    account,
    [alice_signature, bob_signature]
  ])

// Select the fee token and authorize payment for this account.
tx.fee_token = fee_token
fee_payer_digest = tx.fee_payer_signature_hash(account)
tx.fee_payer_signature = sign_secp256k1(fee_payer_key, fee_payer_digest)
```

The fee payer signs first:

```text
// Build the transaction with the fee token selected.
tx = transaction(
  from = account,
  calls = [...],
  fee_token = fee_token
)

// Authorize payment for the known multisig account.
fee_payer_digest = tx.fee_payer_signature_hash(account)
tx.fee_payer_signature = sign_secp256k1(fee_payer_key, fee_payer_digest)

// Sign the sender digest after sponsorship is attached.
digest = multisig_digest(
  tx.signature_hash(),
  account
)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)

tx.signature =
  0x05 || rlp([
    account,
    [alice_signature, bob_signature]
  ])
```

### Weighted Quorum

Owner weights determine which ordered approvals satisfy the threshold and when an extra approval is invalid.

Assume `alice_address < bob_address < carol_address`:

```text
threshold = 3
owners = [
  [alice_address, 2],
  [bob_address, 1],
  [carol_address, 1]
]

digest = multisig_digest(tx.signature_hash(), account)

alice_signature = sign(alice_key, digest)
bob_signature   = sign(bob_key, digest)
carol_signature = sign(carol_key, digest)

// Valid: the final approval reaches the threshold.
signatures = [alice_signature, bob_signature]
signatures = [alice_signature, carol_signature]

// Invalid: the total weight is below the threshold.
signatures = [bob_signature, carol_signature]

// Invalid: Bob reaches the threshold before Carol's extra approval.
signatures = [alice_signature, bob_signature, carol_signature]
```

### Bootstrap with Key Authorization

A bootstrap transaction may initialize the multisig and register an access key, but the access key cannot sign that bootstrap transaction.

```text
// Define and derive the new multisig account.
init = multisig_init(
  salt = salt,
  threshold = 2,
  owners = [
    [alice_address, 1],
    [bob_address, 1]
  ]
)

account = derive_multisig_account(init)

// Authorize a primitive access key for the new account.
authorization = key_authorization(
  chain_id = chain_id,
  account = account,
  key_type = Secp256k1,
  key_id = access_key_address
)

authorization_digest = multisig_digest(
  authorization.signature_hash(),
  account
)

authorization_signature =
  0x05 || rlp([
    account,
    [
      sign(alice_key, authorization_digest),
      sign(bob_key, authorization_digest)
    ]
  ])

// Include the signed key authorization in the bootstrap transaction.
tx = transaction(
  from = account,
  calls = [...],
  key_authorization = signed_key_authorization(
    authorization,
    authorization_signature
  )
)

// Authorize the complete transaction with the bootstrap encoding.
digest = multisig_digest(
  tx.signature_hash(),
  account
)

tx.signature =
  0x05 || rlp([
    init,
    [
      sign(alice_key, digest),
      sign(bob_key, digest)
    ]
  ])
```

After validation, the account is initialized and `access_key_address` is active. The access key may sign a later account keychain transaction for the multisig account.

### Configuration Rotation

The current quorum authorizes a configuration update, which preserves the account address and applies to later transactions.

Assume the current configuration requires both Alice and Bob. They authorize a new configuration whose only owner is Carol:

```text
// Build a top-level configuration update.
rotate_tx = transaction(
  from = account,
  calls = [
    updateMultisigConfig(
      threshold = 1,
      owners = [[carol_address, 1]]
    )
  ]
)

// The current owner configuration authorizes the update.
rotate_digest = multisig_digest(
  rotate_tx.signature_hash(),
  account
)

rotate_tx.signature =
  0x05 || rlp([
    account,
    [
      sign(alice_key, rotate_digest),
      sign(bob_key, rotate_digest)
    ]
  ])

execute(rotate_tx)

// The next transaction uses Carol and keeps the same account address.
next_tx = transaction(
  from = account,
  calls = [...]
)

next_digest = multisig_digest(
  next_tx.signature_hash(),
  account
)

next_tx.signature =
  0x05 || rlp([
    account,
    [sign(carol_key, next_digest)]
  ])
```

## Backwards Compatibility

This TIP adds no transaction field. Existing primitive, account keychain, key authorization, fee-payer, and authorization-list encodings retain their current field positions. Signature type values 0 through 2 are unchanged; value 3 is newly valid for multisig access keys.

Non-multisig transactions remain byte-identical. Native multisig signatures are rejected before T11. Existing EOAs are not upgraded in place; moving assets or application state to a derived multisig uses existing application flows.

## Invariants

1. A bootstrap signature derives exactly one eligible account from its initial configuration; later configuration changes never change that address.
2. Bootstrap uses `rlp([init, signatures])`; every other multisig context uses `rlp([account, signatures])`.
3. Every accepted approval path is cycle-free, within depth and size limits, strictly ordered, and ends exactly at the current weighted quorum.
4. Consensus authorization uses the configuration in state at the transaction's block position. Pools revalidate direct and nested dependencies after rotation.
5. A native multisig account never has EVM code, delegation code, or direct fee-payer authority.
6. Access keys may act as a multisig account, and initialized multisigs may act as access keys, but no access key path may replace a native multisig owner set.
7. Bootstrap config and nonce writes survive later call reverts; failed bootstrap validation changes no state.
8. Intrinsic gas prices every submitted primitive or nested approval and every bootstrap storage row.
