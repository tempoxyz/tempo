# TIP-1157: SLH-DSA-SHA2-256s Access Keys

## Abstract

Add SLH-DSA-SHA2-256s as a native Tempo primitive signature, usable as an access key and as a configurable-account owner approval. Specify one cryptographic profile, canonical wire format, key identity, and integration with existing authorization rules. This is an algorithm-enablement proposal; existing 160-bit owner identities and 256-bit digests do not acquire the primitive's full security margin.

## Motivation

SLH-DSA-SHA2-256s supplies a standardized, category-5 stateless hash-based signature that can complement P-521 and ML-DSA-87 without relying on lattice hardness. The small-signature parameter set reduces bandwidth relative to the corresponding fast-signing variant, at the cost of slower signing. Stateful schemes add key-state coordination and reuse hazards; the SHAKE and other SLH-DSA parameter sets are separate profiles.

The prerequisite account and signature interfaces are [TIP-1004](./tip-1004.md), [TIP-1020](./tip-1020.md), [TIP-1049](./tip-1049.md), the [configurable-account TIP cluster](https://github.com/tempoxyz/tempo/pull/7510), and [removal of admin access keys](https://github.com/tempoxyz/tempo/pull/8204). This proposal preserves their policy and authority boundaries. Implementing this only in a contract or off-chain signer would not make it a native access-key type.

The three algorithm drafts are TIP-1155 (P-521), TIP-1156 (ML-DSA-87), and TIP-1157 (SLH-DSA-SHA2-256s). Each can be reviewed independently; requiring all three algorithms in one account policy requires all three to be enabled.

## Assumptions

- Activation occurs at an explicitly scheduled, unreleased Tempo hardfork after configurable accounts and removal of admin access keys. No fork number or date is assigned by this draft.
- The normative algorithm is [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf), August 2024 edition. Algorithm standardization does not establish an implementation's audit or FIPS validation status.
- Existing account, chain, nonce, configuration-version, grant, expiry, revocation, call-scope, and spending-limit checks remain necessary. A valid primitive signature alone confers no access to another account.
- Existing address-sized owner commitments and transaction hashing remain trusted. Full-width key commitments and stronger transaction commitments require separate proposals if the application requires stronger end-to-end guarantees.

# Specification

## Overview

After activation, add `SlhDsaSha2256s` to the native primitive signature family. An account authorizes the resulting key ID using the existing access-key lifecycle. A configurable account can instead include that key ID as an owner and require its approval through the existing weighted threshold.

Native primitive verification also becomes available in existing direct-root and signed-key-authorization contexts that accept primitive signatures. It does not restore a disabled root or grant admin authority to an access key. Fee-payer signatures and EIP-7702 authorization tuples retain their existing secp256k1 formats. No recursive keychain or configurable-account owner signature is introduced.

## Mechanics

### Effective digest and domain separation

Let `D` be the effective 32-byte digest supplied by the existing enclosing protocol. A direct primitive signature uses the existing transaction or authorization digest. A V2 keychain signature uses `keccak256(0x04 || inner_digest || account)`, with `inner_digest` 32 bytes and `account` 20 bytes. A configurable-account owner approval uses `keccak256(ASCII("tempo:configurable-account:signature") || inner_digest || account || uint64_be(config_version))`. Apply the enclosing digest transformation once, then the algorithm profile below once.

The signature-verifier precompile's `hash` argument is already `D` for primitive verification. Its keychain helpers receive the inner hash and apply the existing V2 transformation before primitive verification. The new algorithm MUST NOT be accepted inside legacy `0x03` keychain envelopes.

### Cryptographic profile

Use the pure external `SLH-DSA.Verify` interface from FIPS 205 with parameter set SLH-DSA-SHA2-256s, message `D` (exactly 32 bytes), and context `ASCII("tempo:slh-dsa-sha2-256s:v1")` (26 bytes). Context encoding and the pure-mode prefix are applied by the external interface exactly once. Do not use HashSLH-DSA, a caller-selected context, a pre-standard SPHINCS+ variant, or an internal entrypoint accepting a caller-computed message representative.

The primitive encoding is `0x08 || PK || SIG`. `PK` is the standard 64-byte `PK.seed || PK.root` encoding (32 bytes each); `SIG` is the standard 29,792-byte SLH-DSA-SHA2-256s signature. The total is `1 + 64 + 29792 = 29857` bytes. Use the entire public key for identity.

Apply the exact standard parameter set, SHA2 instantiations, address encodings, message processing, FORS, WOTS+, and hypertree verification. Accept only when the reconstructed root equals `PK.root` under the standard verification procedure. Reject alternate parameter sets, truncated proofs, extra bytes, and library-specific encodings. There is no recovery bit, persistent signing counter, or on-chain per-signature key state. Signers may use any standard-permitted randomness mode; validators only verify the resulting signature.

### Key identity and authorization

For this new type only, derive `keyId = last20(keccak256(ASCII("tempo:signature-key:v1") || 0x08 || PK))`. `ASCII` denotes the literal bytes without a terminating NUL or length prefix; `0x08` is one byte, and `last20` takes the final 20 digest bytes in their existing order. `PK` is the canonical public-key encoding defined above. The algorithm byte separates new signature families; existing key-ID derivations are unchanged.

Assign key-type value `6` to `SlhDsaSha2256s` in the AccountKeychain ABI, stored signature type, and primitive/signed-authorization type identifiers. This is distinct from primitive wire tag `0x08`. Values 0 through 3 retain their existing meanings; the companion proposals reserve 4/P521, 5/MlDsa87, and 6/SlhDsaSha2256s. These allocations MUST remain stable even if the proposals activate in a different order: an allocated but inactive type is rejected, never reassigned or treated as a placeholder granting another algorithm's authority.

Register the derived ID through the currently supported `authorizeKey` overloads or signed key authorization, using the new key type and existing restrictions. Existing authorization authority and rollback rules apply. On use, verify the primitive, derive its key ID, and require the active stored grant's type to match `6`. An address match alone is insufficient for an access-key grant. Expired, revoked, restricted, retired-root, or otherwise unauthorized keys fail under the existing account rules. This TIP adds no storage fields, changes no nonce consumption, and creates no exception to existing transaction failure semantics.

### Configurable-account approvals

An owner approval may carry this primitive in the existing `0x05` configurable-account envelope. Keep the configuration commitment, owner ordering, duplicate rejection, weight arithmetic, and excess-approval rejection unchanged. Preserve the limits of 48 owners and eight submitted approvals; do not count an approval before successful primitive verification. Owner entries remain address/weight pairs, with the residual identity-binding limitations described below.

A policy with three distinct owners, weights one each, and threshold three requires all three approvals. With all three companion algorithms enabled, one owner can use each family. Each signs its algorithm-specific processing of the same enclosing configurable-account digest. Adding three independent access-key grants does not implement a 3-of-3 policy: any permitted grant is usable independently. Delegating unrestricted transaction authority from a 3-of-3 account to one access key also permits that key to act without collecting the three owner signatures.

### Bounds and activation

The new primitive has exactly 29,857 bytes, including its tag. Validate the enclosing container length, tag, exact per-type length, and applicable fork before allocating algorithm-sized working buffers or invoking cryptography. Preserve the existing length-first interpretation of untagged 65-byte secp256k1 signatures, regardless of their first byte. All length, allocation-size, and gas arithmetic MUST be checked; an overflow is invalid input, never wrapping or truncation.

Before activation, every consensus validation and precompile path rejects this type. After activation, replace any shared 2,049-byte owner-approval bound with type-aware bounds that admit exactly 29,857 bytes for this algorithm and retain each older type's existing bound. A container-level ceiling may be the maximum bound of active types; it does not relax per-type validation. Keep unrelated transaction, block, owner-count, and proof-count limits in force; they may still exclude an otherwise correctly encoded oversized transaction.

Update all containing encoders and decoders, including configurable-account witnesses, signed key authorizations, RPC transport, database codecs, and signature-verifier dispatch. For the verifier's four existing methods, an adequate common ABI ceiling is `4 + 4*32 + ceil32(L + 21)`, where `L` is the largest active primitive length and `ceil32(x) = 32 * ceil(x/32)`. The 21 bytes accommodate the V2 keychain tag and account; individual methods must still accept only their proper envelope. Unknown tags, inactive tags, malformed RLP/ABI, and trailing primitive bytes are rejected. Preserve historical validation on replay; cached verification success cannot bypass the fork or account-state checks.

### Gas and resource accounting

Reserve `G_SLH_DSA_SHA2_256S` for one complete verification, including algorithm-specific hashing, public-key validation, and key-ID derivation. Its numeric value is deliberately unresolved in this Draft and MUST be fixed by benchmark evidence before Ready for Consideration. It MUST be at least the existing 3,000-gas secp256k1 baseline and cover worst-case invalid as well as valid inputs on supported validator hardware.

For a new primitive carried in a transaction signature rather than EVM calldata, additionally charge `4 * tokens(primitive_bytes)`, where each zero byte contributes one token and each nonzero byte four tokens, including the algorithm tag and embedded public key. This uses the existing standard calldata token price to account for the new signature's bandwidth. The additional intrinsic gas for a direct primitive is `G_SLH_DSA_SHA2_256S + 4 * tokens(primitive_bytes) - 3000`; a V2 keychain signature also pays its existing keychain overhead. A configurable-account transaction signature sums each approval's full verification and applicable byte cost, subtracts the existing 3,000-gas baseline only once for the transaction, and preserves existing configuration overheads. Older algorithms retain their current accounting. No approval becomes free when quorum is reached.

Precompile calls retain their existing calldata/input and state-access charges and add `G_SLH_DSA_SHA2_256S` for each primitive verification actually attempted; do not add the transaction-signature byte surcharge to bytes already supplied as precompile calldata. Charge the verification amount before cryptographic work, including on cryptographically invalid inputs. Malformed encodings can fail during bounded parsing without attempting verification. Insufficient gas fails under the enclosing transaction or precompile's existing rules, with no new refund or state mutation.

## Interfaces

No new function selector, event, or storage layout is introduced. Existing `authorizeKey` signatures remain ABI-compatible (`SignatureType` is encoded as `uint8`); clients must add the new value `6` without reinterpreting old values. Existing `KeyInfo.signatureType` and `KeyAuthorized.signatureType` expose that same value. `InvalidSignatureType()` rejects inactive types, and `SignatureTypeMismatch(uint8 expected,uint8 actual)` continues to report stored-versus-presented access-key type mismatches.

At the existing SignatureVerifier precompile (`0x5165300000000000000000000000000000000000`), the following interface semantics extend to this algorithm:

| Existing method | Parameters, result, and failure behavior |
| --- | --- |
| `recover(bytes32 hash, bytes signature) -> address signer` | `hash` is `D`; `signature` is the primitive encoding above. Verify first, then return the derived key ID. Embedded-key verification is used; the public key is not recovered from a PQ/ECDSA recovery bit. Invalid format reverts `InvalidFormat()`; invalid cryptography reverts `InvalidSignature()`. |
| `verify(address signer, bytes32 hash, bytes signature) -> bool` | Same primitive verification and errors; return whether the derived ID equals `signer`. A valid signature for another ID returns false. |
| `verifyKeychain(address account, bytes32 hash, bytes signature) -> bool` | `hash` is the inner digest; `signature` must be a V2 keychain envelope. Preserve existing embedded-account, active grant, type, and retired-root checks. A policy mismatch returns false; malformed or cryptographically invalid input retains the existing revert behavior. |
| `verifyKeychainAdmin(address account, bytes32 hash, bytes signature) -> bool` | Same envelope and verification rules, retaining the existing root/admin authority checks. This TIP does not make a regular access key an admin. |

All four remain view operations, retain current out-of-gas behavior, and write no state. Configurable-account verification remains in its existing interface; `recover` and `verify` do not accept a `0x05` wrapper. The existing function declarations, events, and errors are specified in the pinned [AccountKeychain interface](https://github.com/tempoxyz/tempo/blob/584d54f743e456b88cdb0c9844ed1e63153af360/crates/contracts/src/precompiles/account_keychain.rs) and [SignatureVerifier interface](https://github.com/tempoxyz/tempo/blob/584d54f743e456b88cdb0c9844ed1e63153af360/crates/contracts/src/precompiles/signature_verifier.rs); only type support and bounds change here.

# Compatibility

Existing keys and signatures require no migration. Adoption requires updated validators before activation and updated SDK signing, public-key derivation, ABI enum handling, signature serialization, hardware-wallet adapters, RPC size handling, estimation, and transaction-pool validation. Support in a general-purpose crypto library does not establish support in a wallet or hardware signer; no partner compatibility is asserted by this proposal.

The existing [primitive format](https://github.com/tempoxyz/tempo/blob/584d54f743e456b88cdb0c9844ed1e63153af360/crates/primitives/src/transaction/tt_signature.rs), [configurable-account format](https://github.com/tempoxyz/tempo/blob/584d54f743e456b88cdb0c9844ed1e63153af360/crates/primitives/src/transaction/configurable_account/mod.rs), and [precompile size guard](https://github.com/tempoxyz/tempo/blob/584d54f743e456b88cdb0c9844ed1e63153af360/crates/precompiles/src/signature_verifier/dispatch.rs) identify integration points, rather than evidence that this new algorithm is already implemented. Existing JSON shapes for other algorithms remain unchanged; raw signature byte round trips MUST preserve the new canonical encoding. New structured SDK/RPC representations, if exposed, must agree on field names and hex encodings before rollout.

The consensus profile is backend-independent. Before implementation approval, select and pin a verifier, identify the exact audited version and algorithm scope where an audit is claimed, and review the Tempo adapter, parsing, domain handling, dependency changes, and supported build targets. A library-wide audit or FIPS certificate does not automatically cover this exact integration. This draft makes no unaudited dependency an implicit protocol requirement.

# Observability

No new events are required. Existing `KeyAuthorized(account, publicKey, signatureType, expiry)` records a grant with `signatureType = 6`; `KeyRevoked` and existing spending-limit/call-scope events retain their current meanings. Rejected verification has no success event or new persistent state. Existing RPC validation errors and precompile revert data distinguish malformed input, invalid signatures, inactive types, and unauthorized grants where those interfaces already expose the distinction.

Before testnet, publish gas-estimation and payload-size guidance and measure verification time, signature bytes, and rejection volume by algorithm. Success means supported wallets can authorize, use, and revoke this key under existing restrictions, configurable-account quorum remains enforced, and measured resource costs fit the approved gas schedule and existing transport limits.

# Threat Model

An attacker who compromises a permitted standalone access key can perform all actions within its grant. Algorithm diversity protects an account only when its actual authorization policy requires the independent signatures; it does not protect an unrestricted single-key delegation.

Large proofs can consume bandwidth, allocation capacity, and verifier time before a transaction is included. Hash-based security does not remove risks from key compromise, incorrect domain/address handling, or a shared backend. Stateless signing avoids leaf-state reuse coordination, but private keys still require secure generation and custody.

Untrusted transaction senders control every byte, including embedded public keys, tags, contexts implied by the selected profile, and container lengths. Validators trust only the fixed profile, bounded canonical parsing, fork selection, and verified enclosing account policy. There is no algorithm fallback on failure. Backend or adapter disagreement can split consensus, so verification must be deterministic across supported platforms.

The 160-bit key ID remains a truncated commitment, and configurable-account owner records do not separately commit to an algorithm or full public key. Domain separation prevents ordinary cross-profile reuse but does not eliminate key-ID preimage/collision attacks. Existing 256-bit transaction, configuration, and account-binding digests remain shared dependencies: a collision or binding failure there can undermine all three approvals. Hashing `D` inside a stronger signature does not recover information already lost before `D`. This proposal therefore makes no claim of full 256-bit end-to-end security or complete post-quantum account security. A bunker design requiring those properties must strengthen those commitments and review every recovery, migration, upgrade, and delegation path before relying on the combined policy.

# Invariants

- Every accepted new primitive has the exact tag, length, canonical public key, fixed message/context processing, and successful verification specified here.
- The key ID is computed from that verified public key and algorithm tag; access-key use also matches the stored type and all existing grant restrictions.
- A new primitive or grant is unusable before its activation, regardless of cache state or whether a companion algorithm is active.
- Configurable-account approvals remain distinct, ordered, bounded, and tied to the account and current configuration version; a three-owner unit-weight threshold of three cannot succeed with two approvals.
- Old signature validity, key-ID derivation, storage representation, gas rules, and authority boundaries remain unchanged outside this TIP's explicitly gated changes.
- Bounded malformed input cannot trigger unmetered cryptographic work; all attempted verifications are charged and no arithmetic wraps.

# Open Decisions Before Ready for Consideration

Assign a human TIP owner; complete engineering, security, and compatibility review; pin the verifier and adapter review scope; fix `G_SLH_DSA_SHA2_256S` from reproducible valid/invalid-input benchmarks; and schedule the activation hardfork. Confirm signer latency and the effect of 29,857-byte primitives on RPCs, gossip, transaction pools, blocks, and configurable-account witness transport without increasing unrelated protocol limits. Confirm the stable type allocations with the companion drafts and decide whether the intended bunker deployment requires prerequisite full-width commitment proposals. These unresolved decisions prevent this Draft from being treated as an activation-ready specification.
