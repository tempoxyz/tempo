# TIP-1143: Chunked Contract Bytecode

## Abstract

Divide deployed contract bytecode into independently executable 24 KiB chunks, with at most 40 chunks (960 KiB) per contract. Existing contracts fit in one chunk and retain their account encoding and bytecode database records; only newly deployed multi-chunk contracts need chunk metadata. Execution loads chunks on demand and journals transaction-local chunk warmth. At a 1 Ggas/s calibration target, this draft retains a provisional cold price of 28,680 gas and a warm price of 1,000 gas, subject to measurement at the new chunk size.

Multi-chunk deployment validation prohibits instructions and sequential execution from crossing a chunk boundary. Existing single-chunk bytecode keeps legacy execution semantics, including zero padding for a truncated final PUSH. No database backfill or activation-time state migration is required.

## Motivation

Loading and analyzing a complete contract makes execution I/O depend on code a transaction never executes. Chunking bounds each database read, permits sparse code access, and retains the existing global code hash and externally visible bytes.

[EIP-6800](https://eips.ethereum.org/EIPS/eip-6800) and [EIP-7864](https://eips.ethereum.org/EIPS/eip-7864) commit code in smaller units for authenticated state. [EIP-7907](https://eips.ethereum.org/EIPS/eip-7907) prices code loading and journals code warmth. This TIP uses a 24 KiB unit matching the existing deployed-code limit and stores an ordered chunk-hash vector only for multi-chunk contracts.

Retaining full-code loading avoids the deployment restrictions but keeps I/O proportional to complete code size. Smaller chunks can reduce unused payload reads at the cost of more committed hashes and lookups. The 24 KiB design preserves existing storage while permitting larger contracts. Its boundary restrictions apply only to multi-chunk code. Measurements from the earlier 12 KiB design do not establish savings or pricing for this design.

## Assumptions

- Pre-activation runtime bytecode is at most 24 KiB, so every existing contract fits in one chunk. Activation must confirm this invariant for the target network, including genesis allocations; an oversized legacy allocation needs a separately specified compatibility rule, not a silent rewrite.
- Initcode remains resident input and is not chunked. The runtime limit rises to 960 KiB, and the initcode limit rises with it as specified below. Transaction, block, and gas limits still constrain deployability.
- Tempo/Reth authenticates bytecode when ingesting or reconstructing state and supplies validated bytes to EVM2. Execution trusts that provider boundary and does not rehash every chunk access.
- The account-extension layout must be reconciled with other extensions scheduled for the same fork, including configurable accounts. Version `1` below is a draft encoding, not an independently reserved format tag. Existing account extensions must not be overwritten to add chunk metadata.

# Specification

## Constants

```text
CODE_CHUNK_SIZE         = 24 * 1024 = 24576
MAX_CODE_CHUNKS         = 40
MAX_CODE_SIZE           = CODE_CHUNK_SIZE * MAX_CODE_CHUNKS = 983040
MAX_INITCODE_SIZE       = 2 * MAX_CODE_SIZE = 1966080
COLD_CODE_CHUNK_GAS     = 28680
WARM_CODE_CHUNK_GAS     = 1000
ACCOUNT_FORMAT_VERSION = 1
```

All arithmetic that determines indices, byte ranges, or gas MUST be checked. At activation, all creation paths, including creation transactions, AA creation calls, CREATE, and CREATE2, use these runtime and initcode limits. Existing initcode metering, code-deposit charges, and other deployment checks remain. The limits do not guarantee that every permitted code size fits within the active gas or transaction-size budget.

## Deployment validation and chunk construction

Let `code` be the original deployed bytes and `L = code.len()`. Creation MUST reject `L > MAX_CODE_SIZE` through the existing oversized-runtime failure path. Empty code has no chunks. Nonempty code has `N = ceil(L / CODE_CHUNK_SIZE)` chunks, with `1 <= N <= 40` and valid indices `0..N-1`. Original payload `i` is:

```text
code[i * CODE_CHUNK_SIZE .. min((i + 1) * CODE_CHUNK_SIZE, L)]
```

For `L <= CODE_CHUNK_SIZE`, retain existing deployment validation, legacy bytecode analysis, and end-of-code padding. In particular, this TIP adds no terminal STOP requirement and does not reject a final truncated PUSH in single-chunk code. This applies to both existing and newly deployed single-chunk contracts.

For `L > CODE_CHUNK_SIZE`, creation MUST additionally reject deployed code when either condition holds:

1. A PUSH1 through PUSH32 immediate crosses a chunk boundary or extends beyond `L`.
2. A non-final chunk's last original byte is not a decoded STOP opcode (`0x00`). A zero byte belonging to a PUSH immediate does not satisfy this rule.

Multi-chunk validation scans all original bytes from offset zero, including unreachable bytes, advancing over PUSH immediates before checking opcode boundaries. These rules guarantee that every chunk starts at an opcode boundary and that execution cannot fall through into the next chunk. They are not retroactively applied to single-chunk code.

For execution, analyze each multi-chunk payload as independent legacy bytecode with a synthetic trailing STOP and the interpreter's normal analysis padding. Single-chunk code uses its existing legacy analysis. Synthetic bytes are not part of `L`, `code_hash`, chunk payloads, RPC output, or deployment gas.

Define:

```text
code_hash       = keccak256(code)
chunk_hash[i]   = keccak256(original_payload[i])
```

Concatenating all original payloads MUST reproduce exactly `L` bytes whose Keccak hash is `code_hash`. For a nonempty single-chunk contract, `chunk_hash[0] == code_hash`; this identity allows its existing bytecode database record to serve directly as chunk zero.

## Account commitment and Reth representation

Accounts without chunk metadata retain their existing encoding. An empty code hash identifies empty code; otherwise, the existing bytecode record is a single chunk of at most 24 KiB. No `code_size` or chunk-hash vector is backfilled into these accounts. Newly deployed code of at most 24 KiB uses this same representation.

Only multi-chunk contracts commit to `code_hash`, `code_size`, and an ordered `chunk_hashes` vector. The chunk count is derived from `code_size`; it is not stored separately. In this draft, Tempo stores these fields in Reth's chain-specific account extension, a fifth RLP string in the trie account, with this payload:

```text
format_version: u8 = 1
code_size:      u32 big-endian
chunk_hashes:   N consecutive B256 values
```

A chunk-metadata payload is valid only when `24576 < code_size <= 983040` and `N = ceil(code_size / 24576)`, giving `2 <= N <= 40`. Its length MUST equal `5 + 32 * N`, at most 1,285 bytes. Unknown versions, out-of-range sizes, mismatched lengths, and mismatched hash counts are invalid. Empty and single-chunk code MUST NOT use this payload. Absence of chunk metadata MUST NOT be interpreted as `code_size == 0`; the existing account code hash determines whether a legacy bytecode lookup is needed.

Reth Compact encoding preserves existing account records without chunk metadata and carries the extension for new multi-chunk accounts. Conversion among Reth `Account`, trie `TrieAccount`, and EVM account information MUST preserve which representation is present. Creating, replacing, clearing, reverting, or snapshotting code MUST update the code hash and optional chunk metadata atomically. Replacing multi-chunk code with single-chunk or empty code removes chunk metadata while preserving unrelated account fields.

For multi-chunk code, EXTCODESIZE reads the committed `code_size` without loading payloads. For single-chunk code, its size is obtained from the existing bytecode record via the metered chunk-zero access path; a cached size does not bypass logical chunk gas or warmth. Empty code needs no bytecode read. EXTCODEHASH retains its existing result. Global PC and jump offsets remain offsets into complete original code.

## Database interface

The required database operation is:

```rust
fn get_code_chunk_by_hash(
    &mut self,
    code_hash: &B256,
    index: u32,
) -> Result<Option<CodeChunk>, Self::Error>;
```

Typed, erased, cached, counted, and asynchronous adapters MUST preserve this contract. For a nonempty account without chunk metadata, index zero reads the existing bytecode record keyed by `code_hash` directly. This is a bounded one-chunk read, not a multi-chunk full-code fallback, and requires no new persistent index entry. Its returned length determines the in-memory code size. Higher indices return `None` without I/O. Empty code requires no read.

For multi-chunk code, the caller checks `index < ceil(code_size / CODE_CHUNK_SIZE)` using committed metadata. Out-of-range requests return `None` without chunk I/O or warmth changes. In-range requests return a payload of the exact derived length. The provider must support direct chunk reads without fetching complete multi-chunk code. Any new lookup index mapping `(code_hash, index)` to a payload is populated only when multi-chunk code is deployed or ingested during synchronization; existing bytecode rows need no rewrite or backfill. Account metadata, payloads, and required lookup entries must become visible atomically.

EVM2 validates creation output. Tempo/Reth validates imported chunks against their committed hashes at the ingestion boundary and checks full-code reconstruction when complete code is available. Execution does not rehash a fetched chunk. Missing in-range data, invalid lengths, or detected corruption are node errors, never empty code or an EVM halt. A provider must not substitute a whole-code record when a required multi-chunk payload is missing.

Full-code access remains available for RPC, synchronization, and index verification. It returns the original single-chunk record or reconstructs multi-chunk code. Consensus execution MUST NOT reconstruct complete multi-chunk code to satisfy a chunk request.

## Journaled account and caches

The EVM journaled account contains:

```text
code_size: Option<u32>
code_chunks: HashMap<u32, { bytecode: Bytecode, is_warm: bool }>
```

`code_size` is known from metadata for multi-chunk code and is zero for empty code. For nonempty single-chunk code it is initially unknown and becomes known after the first chunk-zero read. Unknown MUST NOT be treated as empty. `code_chunks` stores only the analyzed chunks that execution has requested, including execution-only padding. Loading account metadata does not itself load chunk zero. The bytecode type MUST NOT hold a lazily initialized vector of all chunks: an absent map entry is the source of truth that the chunk has not been loaded for this journaled account. A newly created account retains validated creation output but constructs and inserts only the requested chunk on first access.

Warmth belongs to the resolved code-owner account and chunk index, not the calling account or storage context. Two addresses with identical bytecode share immutable bytes but do not share warmth. The journaled map is tied to the account's current `code_hash`; replacing or clearing code MUST invalidate the map, and reverting that change MUST restore the previous code identity and warmth.

Each loaded map entry carries its transaction-local `is_warm` flag. Maintain one additional immutable structure:

- An immutable byte cache keyed by `(code_hash, chunk_index)`, shared across addresses and retained across reverts and transaction resets.

After a successful cold read, insert the account entry with `is_warm = true`, or set an existing cold entry to warm, and append `CodeChunkWarmed` to the revert journal. Revert undoes only warmth changes recorded since that checkpoint and retains immutable bytes. Chunks already warm when the checkpoint was opened remain warm. Transaction reset discards the journaled account and therefore all warmth. Failed reads, skipped reads, and out-of-range requests do not insert or warm a chunk. A hit in the immutable byte cache still counts as a cold account-chunk access when the account entry is absent or cold, so physical cache residency never changes gas.

## Interpreter behavior

Call and transaction entry resolve the code owner, read account metadata, and load chunk zero when code is nonempty. For the single-chunk representation, this read also resolves `code_size` before executing instructions. Precompile dispatch does not load a runtime chunk. Initcode remains resident input and is not chunked; its PC, CODESIZE, and CODECOPY continue to refer to that input.

For a taken JUMP or JUMPI with global target `t`:

1. Reject `t >= code_size` as an invalid jump without chunk I/O.
2. Compute `index = t / CODE_CHUNK_SIZE` and `local = t % CODE_CHUNK_SIZE`.
3. If `index` differs from the active chunk, reserve the applicable cold or warm gas, fetch the chunk, and update warmth.
4. Validate `local` against that chunk's jump table.
5. Replace the interpreter's owned bytecode and bytecode view, then set its local program counter to `local`.

An invalid in-range destination still pays for its destination chunk because validation requires reading it. An untaken JUMPI does not read its target. Same-chunk jumps use the active analysis. For multi-chunk code, the boundary validator requires the final decoded opcode of every non-final payload to be STOP; a zero byte used as PUSH immediate data does not satisfy this rule. Sequential execution therefore cannot enter another chunk and the interpreter dispatch loop requires no boundary branch.

`PC` returns `active_chunk_index * CODE_CHUNK_SIZE + local_pc`. `CODESIZE` returns resolved `code_size`, excluding synthetic STOP. CODECOPY and multi-chunk EXTCODECOPY require every original payload intersecting their clipped source range and charge each required chunk at its cold or warm rate before fetching any of them. For source offset `s` and length `n`, the required set is empty when `n == 0` or `s >= code_size`. Otherwise, let `end = s + min(n, code_size - s)`; required indices run from `s / CODE_CHUNK_SIZE` through `(end - 1) / CODE_CHUNK_SIZE`, inclusive. Compare the original EVM-width operands before narrowing them to host indices. Normal memory-expansion, copy charges, and exceptional-halt rules still apply. Bytes beyond `code_size` remain zero and do not require a chunk; synthetic STOP bytes MUST NOT be copied.

For EXTCODECOPY of nonempty single-chunk code, require chunk zero exactly when the copy length is nonzero and the source offset is below `CODE_CHUNK_SIZE`. This read resolves the size if it is unknown. Charge that chunk once for the operation even if the source is beyond the actual code length. A zero-length copy or source offset at or above `CODE_CHUNK_SIZE` needs no chunk. Apply this rule even when the size or bytes are cached so cache residency cannot change gas. Existing account-access and memory charges still apply.

## Gas accounting

The incremental charge is:

```text
chunk_gas(cold, warm) = 28680 * |unique(cold)| + 1000 * |unique(warm)|
```

Every cold chunk costs 28,680 gas, including a short final chunk. Every warm chunk request costs 1,000 gas. Requests occur on nonempty call entry, cross-chunk jumps, and the size/copy reads described above. Each operation charges a required chunk at most once. Executing another opcode or jumping within the active chunk does not incur another chunk charge. Existing opcode, account-access, memory, copy, call, and deployment charges remain.

The complete incremental cost for one operation MUST be checked and reserved before its first chunk I/O. If it is unaffordable, execution halts before fetching or warming any chunk. Database failure is a node execution error. REVERT does not refund spent gas but does revert chunk warmth through the normal checkpoint journal.

The requested calibration target is one billion gas per second. The retained 28,680 cold price assigns 28.68 microseconds to lookup, reading, constructing, and analyzing one 24 KiB chunk. It was proposed for the earlier 12 KiB design and must be remeasured; doubling the payload size does not establish that the same price is sufficient. The 1,000 warm price assigns one microsecond to the account-map lookup, jump-table access, and active-chunk switch. These values are consensus constants for the draft and should be checked against the persistent Tempo provider before activation. For multi-chunk accounts, they do not price the enlarged account proof containing up to `32 * 40 = 1280` hash bytes; that metadata is loaded with the account and must be covered by account/state-access pricing. Single-chunk accounts have no new proof fields.

The charge occurs before a CALL's 63/64 child-gas calculation when chunk zero is needed to resolve code. Cross-chunk jumps spend gas in the executing child frame. Chunked frames execute in the interpreter until compiled engines implement identical loading and gas ordering.

## Compatibility and activation

The full code hash, contract addresses, RPC bytecode, storage, and opcode offsets remain unchanged. Existing accounts and bytecode records retain their exact persisted representation. Activation does not rewrite account leaves, recompute a replacement state root, split existing bytecode rows, or require a database backfill. Subsequent multi-chunk deployments use the new encoding through ordinary state transitions.

The TIP still requires a coordinated hardfork for the larger code and initcode limits, multi-chunk validation, optional account metadata, and gas rules. Added gas can change transaction success, GAS, estimates, and call forwarding even for existing contracts. Single-chunk bytecode retains legacy validation and padding, so no pre-activation code rewrite is needed.

Before activation, clients MUST:

1. Confirm the target network's existing code fits the 24 KiB single-chunk representation, including genesis allocations, and verify execution against an unchanged pre-fork database.
2. Support both representations in execution, persistence, synchronization, proofs, and RPC, including nodes restored from pre-fork snapshots.
3. Differentially replay chunked interpreter execution against an unchunked reference with the same fork rules, including failed calls and reverts, and verify that untouched account encodings remain byte-for-byte identical across activation. Compiled engines remain deferred.
4. Measure 24 KiB cold database latency, account-proof growth for up to 40 chunks, cache memory, and Tempo transaction gas deltas. Agree on the final chunk tariff and any multi-chunk account-metadata tariff before scheduling the fork.
5. Activate code-size limits, deployment validation, account decoding, database reads, interpreter behavior, and gas rules together.

Historical pre-activation execution retains the old code-size limits and gas behavior. No eager loading or persistent conversion of existing code is part of activation.

## Reference implementation and measurements

The earlier 12 KiB EVM2 prototype on `rakita/bytecode-chunking` includes:

- validated 12 KiB chunks with synthetic STOP;
- `code_size` and a per-account map of loaded bytecode chunks with individual warm flags;
- typed, erased, cached, counted, and async chunk database reads;
- rollback-aware chunk warmth and persistent byte caching;
- lazy chunk-zero loading for calls and transaction entry;
- cross-chunk JUMP/JUMPI loading with global PC and code size;
- creation-time PUSH and STOP-boundary validation;
- range-based `CODECOPY` and `EXTCODECOPY` loading with aggregate pre-I/O gas reservation;
- EIP-3607 and EIP-7702 validation using code size and, only when needed, chunk zero;
- checked 28,680-gas cold and 1,000-gas warm tariffs.

Chunked frames currently bypass compiled JIT/AOT execution and use the interpreter. Compiled cache keys and builtins require chunk-index-aware loading and identical gas behavior before compiled execution can be enabled.

The earlier Tempo prototype uses Reth's account extension to encode `code_size` and all ordered chunk hashes for nonempty code. It must be updated to encode only multi-chunk metadata, distinguish absent metadata from empty code, and enforce the 40-chunk limit; it does not yet implement this migration-free representation. Tests cover extension validation, Compact persistence, trie commitment changes, chunk construction, cross-chunk jumps, cold/warm gas, skipped reads, cache retention, and rollback.

The coverage experiment replayed Ethereum blocks 25,347,446–25,347,455 (2,279 transactions). At 12 KiB, block-local full code totaled 29,955,810 bytes and touched original payload totaled 29,493,944 bytes, a 1.54% reduction. Execution touched 3,963 of 4,053 chunks. Transaction-local full code totaled 66,668,187 bytes versus 65,950,134 payload bytes, a 1.08% reduction. Those figures describe the earlier 12 KiB experiment, not this 24 KiB design. They are coverage observations, not lazy database I/O or Tempo gas results, and do not justify activation pricing.

The revised draft still requires the 24 KiB/40-chunk implementation, persistent provider integration without backfill, single-chunk compatibility and broader conformance coverage, and Tempo replay measurement before it is activation-ready. JIT and AOT support is deferred; clients must route chunked frames through the interpreter until compiled engines implement the same on-demand loading and gas rules.

# Tooling

- Compiler and assembler tooling targeting multi-chunk contracts must enforce the 40-chunk limit and identify PUSH instructions spanning a 24 KiB boundary and non-final chunks without a terminal STOP opcode. Inserting padding changes byte offsets and code hashes, so tools must regenerate jump destinations, source maps, and deployment artifacts; validators must never insert padding into submitted code.
- Compatibility tooling must verify execution and persistence using an unchanged pre-fork database and snapshots. No migration command or backfill is required. Deployment tools must expose the 960 KiB runtime and 1,920 KiB initcode limits alongside the active gas and transaction-size budgets.
- RPC bytecode responses and code hashes retain their existing bytes. Debuggers and traces must report global PCs, and proof tooling must support the versioned account extension. Gas estimators must apply the same fork rules and logical warmth as execution.
- Replay tooling must compare chunked interpreter results, gas, logs, state roots, and rollback behavior with the unchunked reference, using cold and populated physical caches. Reports must distinguish payload coverage from actual database reads.

# Observability

No new on-chain events are required: chunk reads are execution details and MUST NOT emit EVM logs. Clients must provide these local diagnostics, independently of consensus execution:

- An activation compatibility report containing the pre-fork block/hash, code-size bound checked, and legacy account/bytecode persistence results, to demonstrate that activation needs no data rewrite.
- A chunk-read failure diagnostic containing the block/transaction context when available, code hash, chunk index, expected length, and failure reason. Such a failure remains a node error.
- Aggregate counters for logical cold chunk accesses, physical cache hits/misses, bytes fetched, and read latency, to measure the workload used to calibrate pricing. Address and code-hash labels must not be used on aggregate metrics.

# Threat Model

- Contract authors and callers are untrusted. They can target boundaries, invalid destinations, many code owners, and repeated reverts to maximize I/O. Clients MUST charge before I/O and use checked arithmetic.
- EVM2 validates bytecode when it is created. Tempo/Reth persists and retrieves the resulting chunks without corruption, so execution trusts fetched payloads and does not rehash them. Imported code must satisfy the same code-hash and chunk-metadata invariants at the provider boundary. The complete-code hash remains an invariant for reconstruction.
- Validators must agree on the active account format, gas schedule, and fork boundary. Activation must preserve the pre-fork state without a migration root. Local caches and speculative execution must not influence consensus gas or warmth.
- Submitted runtime code is untrusted until EVM2 creation validation succeeds. Multi-chunk boundary validation covers unreachable bytes as well as executed instructions; single-chunk code retains legacy validation. Persisted validated chunks are trusted thereafter.

# Invariants

1. Runtime code never exceeds `40 * 24576 = 983040` bytes; multi-chunk metadata contains exactly `ceil(code_size / 24576)` hashes, between 2 and 40.
2. Each multi-chunk payload has the derived length and matches its account-committed hash; ingestion establishes this invariant before execution.
3. Concatenated original payloads have `code_size` bytes and hash to `code_hash`; a single-chunk payload hashes directly to the existing code hash.
4. In multi-chunk code, no PUSH immediate crosses a boundary or deployed-code end. Single-chunk code retains legacy end-of-code padding.
5. Every non-final original payload ends in a decoded STOP opcode; synthetic STOP and analysis padding never appear in original bytes.
6. Chunk gas depends on logical warmth, never physical cache residency, including when a single-chunk code size has already been cached.
7. Insufficient gas causes no chunk fetch or warmth mutation for the failing operation.
8. Revert restores warmth and optional account metadata while retaining immutable cached bytes.
9. Missing or invalid in-range data is a node error, never an EVM result.
10. Interpreter, async execution, RPC, and proof tooling agree on original bytes and global offsets; JIT and AOT remain disabled for chunked frames.
11. Existing account and bytecode records require no rewrite or backfill; absence of chunk metadata is distinct from empty code.

## Required test cases and success criteria

Before scheduling, tests MUST cover empty code; lengths `24575`, `24576`, and `24577`; exactly 40 chunks (`983040` bytes); a short 40th chunk; and rejection at `983041` bytes. Test the initcode limit at `1966080` and `1966081` bytes through all creation paths. Test every PUSH immediate width at chunk boundaries and code end, including legacy single-chunk truncated PUSH behavior and rejection of a boundary zero that is PUSH data in multi-chunk code. Include taken, untaken, invalid, and same-chunk jumps and global PC behavior.

Copy tests MUST include zero length, out-of-range and maximal source offsets, boundary-spanning ranges, short final chunks, and out-of-gas before the first chunk read. Exercise unknown and cached single-chunk sizes with identical logical gas and warmth, including a source offset below 24 KiB but beyond the actual code end.

Warmth tests MUST cover two owners with identical code, nested success and revert, a chunk already warm before a reverted checkpoint, transitions between multi-chunk, single-chunk, and empty code with rollback, and transaction reset with a populated immutable cache. Missing and wrong-length chunks MUST fail as node errors; corrupted imported chunks MUST be rejected at ingestion. Encoding tests MUST cover unknown versions, sizes outside the multi-chunk range, more than 40 hashes, invalid hash counts, persistence round trips, and the full-code hash invariant.

Compatibility tests MUST open an unchanged pre-fork database, load chunk zero from the original bytecode record, and verify that untouched account RLP, Compact records, bytecode rows, and state commitments are unchanged by activation. Repeat with a pre-fork snapshot synchronized through post-fork multi-chunk deployments. New single-chunk deployments MUST use the original representation.

Activation requires zero unexplained execution or gas differences against unchunked reference execution using the same fork rules, identical results with cold and populated physical caches, and demonstrated operation without database backfill or state migration. Chunked frames must remain interpreter-only until compiled engines satisfy the same requirements. The owner must publish Tempo replay measurements and obtain engineering, research, and security approval under [TIP-0000](./tip-0000.md); this draft remains unscheduled until the unresolved semantics and pricing are settled.
