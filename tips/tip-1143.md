# TIP-1143: Chunked Contract Bytecode

## Abstract

Allow contracts to contain up to 40 code chunks while loading only the chunks an operation needs. Each prepared chunk stores at most 24 KiB, including fixed padding, a generated STOP or relative jump, and a one-byte start offset. The client prepares chunks at deployment or ingestion, so compilers do not need to place instructions at chunk boundaries. Account extensions contain either the ordered chunk hashes or an EIP-7702 delegation address; execution charges 28,680 gas for a cold chunk request and 1,000 gas for a warm request.

## Motivation

The goal is to support bytecode roughly 40 times larger than the existing 24 KiB limit without requiring every execution to load and analyze the entire contract. A transaction that executes only two chunks should pay for and load those chunks, even if the contract contains 40.

[EIP-6800](https://eips.ethereum.org/EIPS/eip-6800) and [EIP-7864](https://eips.ethereum.org/EIPS/eip-7864) provide related work on committing code in smaller units. [EIP-7907](https://eips.ethereum.org/EIPS/eip-7907) provides related work on code-loading prices and journaled code warmth. This proposal uses a bounded 24 KiB stored chunk and an ordered vector of hashes in the account.

The earlier draft required compilers to prevent crossing PUSH instructions and place STOP at each boundary. This draft removes those deployment restrictions. The client copies crossing immediate bytes into padding and appends a stack-neutral transfer. Logical code offsets stay unchanged, so ordinary absolute jump destinations do not need relocation.

## Assumptions

- Existing ordinary runtime code is at most 24 KiB, including genesis allocations. An oversized historical allocation needs an explicit compatibility rule before activation.
- Initcode stays resident and is not split. Runtime chunks are prepared from the bytes returned by successful creation. Gas and transaction-size limits still constrain deployment.
- The provider authenticates stored code and account metadata at ingestion. Execution trusts that boundary and does not rehash every chunk request.
- Account extensions are authoritative for code type. Clients must coordinate the type tags and their container with other account extensions scheduled for the same fork.
- Existing delegation records must be made available as account metadata before the new execution path is used. The historical-state and persistence policy for that conversion remains an activation dependency, described below.
- This is an unscheduled draft. The current EVM2 implementation uses the interpreter; the latest format is not yet a claim of completed Reth/Tempo integration.

# Specification

## Constants and terminology

```text
MAX_STORED_CHUNK_SIZE    = 24 * 1024 = 24576
LEGACY_CODE_CHUNK_SIZE   = 24 * 1024 = 24576
CHUNK_PADDING_SIZE      = 32
CODE_CHUNK_SIZE          = 24576 - 36 = 24540
MAX_CODE_CHUNKS          = 40
MAX_CODE_SIZE            = 24540 * 40 = 981600
MAX_INITCODE_SIZE        = 1966080
COLD_CODE_CHUNK_GAS      = 28680
WARM_CODE_CHUNK_GAS      = 1000
RJUMP_GAS               = 2
RJUMPI_GAS              = 4
CHUNK_EXTENSION_TYPE    = 1
DELEGATION_EXTENSION_TYPE = 2
```

`CODE_CHUNK_SIZE` is the logical payload stride. The 36 reserved bytes cover 32 bytes of padding, a three-byte RJUMP, and a one-byte offset. STOP needs only one byte, so a full payload with a STOP tail occupies 24,574 stored bytes. A full payload with an RJUMP tail occupies exactly 24,576 bytes.

The runtime limit is 981,600 logical bytes, approximately 39.94 times the legacy limit. The initcode limit stays at the previously selected 1,966,080 bytes; it is not recalculated as twice the smaller logical runtime limit.

**Logical code** means the complete runtime bytes returned by creation, before adding chunk fields. **Payload** means one contiguous slice of those bytes. **Stored chunk** means payload plus fixed padding, tail, and offset. **Safety padding** means extra memory added by an interpreter for safe immediate reads; it is not part of a stored chunk.

The limits apply to creation transactions, AA creation paths, CREATE, and CREATE2. Existing validation, initcode metering, code-deposit charges, and gas limits still apply. Arithmetic for lengths, indices, displacements, and aggregate gas MUST avoid overflow.

## Code representation and commitments

For logical code `code` of length `L`:

- `L == 0`: empty code; no chunks or code extension.
- `0 < L <= CODE_CHUNK_SIZE`: use the ordinary legacy bytecode record, without generated fields.
- `CODE_CHUNK_SIZE < L <= MAX_CODE_SIZE`: use extension type 1 and prepare `ceil(L / CODE_CHUNK_SIZE)` chunks.
- `L > MAX_CODE_SIZE`: reject creation through the oversized-runtime failure path.

Existing ordinary records up to `LEGACY_CODE_CHUNK_SIZE` remain ordinary records even when their length exceeds the new payload stride. The account representation selects the loading path; length alone MUST NOT reinterpret an old record as chunked code.

For a prepared chunk at index `i`:

```text
start          = i * CODE_CHUNK_SIZE
payload_len    = min(CODE_CHUNK_SIZE, L - start)
payload[i]     = code[start .. start + payload_len]
code_hash      = keccak256(code)
chunk_hash[i]  = keccak256(stored_chunk[i])
```

Chunk hashes commit to all stored fields, including copied immediate bytes, unused padding, the generated tail, and the start-offset byte. They do not hash only the logical payload. The complete account code hash remains the hash of logical code. Concatenating the payloads, excluding appended fields, MUST recover exactly `L` bytes and that hash.

Prepared buffers are the canonical stored and executed chunks. No second original-byte buffer is needed inside each chunk. CODESIZE, CODECOPY, EXTCODECOPY, code-deposit accounting, and RPC bytecode continue to use logical code. Generated fields do not increase logical size or code-deposit gas. CREATE2 continues to hash the original resident initcode under its existing address rule.

## Stored chunk format

```text
| code payload: at most 24540 bytes | padding: exactly 32 bytes | STOP or RJUMP | start offset: 1 byte |
```

| Field | Meaning |
| --- | --- |
| Code payload | Original logical bytes, including any leading immediate data copied into the preceding chunk. |
| Padding | Completes a crossing or truncated immediate, then provides executable instructions to reach the tail. |
| Tail | STOP if no following logical instruction remains; otherwise RJUMP to the next chunk. |
| Start offset | Number of leading payload bytes belonging to the preceding chunk's instruction, from 0 through 32. |

The first chunk has start offset zero. A short final chunk may consist entirely of leading immediate data; its offset then equals its payload length. Leading data bytes MUST remain unchanged. No `0xae` marker or replacement JUMPDEST is written over them.

The stored start offset is data, not an executable instruction. The unconditional RJUMP or STOP tail prevents normal fallthrough into it, and destination checks exclude it from jumps. Only a prepared chunk selected through account metadata uses this format; a similar suffix in an ordinary contract does not establish a chunk type.

## Splitting and preparation

Preparation runs when code is created or ingested, before publication. It scans the complete logical byte stream, including unreachable bytes, and uses these instruction widths:

| Opcode | Width including immediate |
| --- | --- |
| PUSH1 through PUSH32 | `1 + immediate width` |
| RJUMP and RJUMPI | 3 bytes |
| DUPN, SWAPN, EXCHANGE (`0xe6`–`0xe8`) | 2 bytes |
| Other opcodes, including PUSH0 | 1 byte |

The width scan is deterministic and uses these widths even for an invalid immediate encoding. It is separate from JUMPDEST analysis and does not make a disabled or invalid instruction executable. See the compatibility limitation below for alternative entries through invalid-immediate sequences.

For each payload `[start, end)`:

1. Find the first instruction boundary at or after `start` using the complete-code scan. The start offset is the number of bytes from `start` to that boundary, capped at `end` for a data-only final payload.
2. Starting at that boundary, scan until the next instruction boundary `q` is at or after `end`. For a data-only final payload, use `q = end`.
3. Copy the payload unchanged. Let `k = q - end`, where `0 <= k <= 32`.
4. Put the next `k` logical immediate bytes in the beginning of the padding. When the final instruction extends beyond `L`, fill the missing immediate bytes with zero.
5. Fill the remaining `32 - k` padding bytes as defined below.
6. Append RJUMP if `q < L`; otherwise append STOP. A PUSH that consumes all remaining logical bytes therefore ends with STOP, even if some of those bytes occupy a separate data-only final payload.
7. Append the one-byte start offset, authenticate the resulting buffer, and store it with the account's ordered commitments.

Crossing immediates are copied, not removed from the following payload. Their logical positions and copy results remain unchanged. The interpreter executes the copy in the preceding chunk, then skips the original leading data when entering the successor through the generated transfer. A truncated final PUSH keeps the usual zero-filled value.

### Crossing unused padding

Let `r = 32 - k` be the number of unused padding bytes:

- `r == 0`: no additional instruction is needed before the tail.
- `1 <= r <= 3`: write `r` JUMPDEST opcodes.
- `r >= 4`: write RJUMP and its two-byte encoded displacement `r - 4`, then `r - 4` zero filler bytes, then JUMPDEST. The local jump lands on that final JUMPDEST immediately before the tail.

The padding jump uses physical positions inside the active stored buffer and MUST pass its jump-table check. It does not load another chunk. The filler bytes are skipped. This adds `min(r, 3)` gas: either up to three JUMPDESTs, or a two-gas RJUMP and one-gas JUMPDEST. It neither consumes nor adds stack values.

There is no chunk-size branch in the ordinary opcode-dispatch loop. Padding and tails are executable instructions. The relative-jump handler distinguishes a jump inside generated padding from an ordinary logical jump and the final transfer.

### Final transfer

The tail starts at local position `payload_len + 32`. If it transfers, its stored bytes are:

```text
RJUMP -35 = e0 5a 38
```

The displacement cancels the 32-byte padding and three-byte instruction. Its logical destination is the beginning of the next payload. After loading that chunk, execution advances to its start offset, landing on its first actual instruction.

This authenticated final RJUMP is the only jump that does not require JUMPDEST at its destination. Its identity comes from the validated chunk layout and tail position, not from matching opcode bytes. An identical RJUMP in the original payload follows ordinary destination checks. The transfer costs 2 gas plus the next chunk's cold or warm tariff.

### Example: PUSH2 crosses a boundary

Suppose logical positions `CODE_CHUNK_SIZE - 1`, `CODE_CHUNK_SIZE`, and `CODE_CHUNK_SIZE + 1` contain `PUSH2 0x12 0x34`, followed by POP and STOP.

```text
chunk 0 payload:  ... PUSH2
chunk 0 padding:  12 34 | RJUMP +26 | 26 zero bytes | JUMPDEST
chunk 0 tail:     RJUMP -35
chunk 0 offset:   00

chunk 1 payload:  12 34 POP STOP
chunk 1 padding:  RJUMP +28 | 28 zero bytes | JUMPDEST
chunk 1 tail:     STOP
chunk 1 offset:   02
```

PUSH2 reads `0x1234` from chunk 0's padding. The padding jump reaches its JUMPDEST, then the final transfer loads chunk 1 and starts at local offset 2, executing POP. CODECOPY still reads `0x12 0x34` directly from chunk 1. The original STOP prevents execution of chunk 1's appended padding in this example.

## RJUMP and RJUMPI

The names and opcode assignments follow [EIP-4200](https://eips.ethereum.org/EIPS/eip-4200), but this TIP does not adopt EOF containers, EOF validation, or its signed 16-bit immediate format. Ordinary destinations require JUMPDEST.

| Opcode | Byte | Immediate | Stack effect | Base gas |
| --- | --- | --- | --- | --- |
| RJUMP | `0xe0` | Two encoded offset bytes | None | 2 |
| RJUMPI | `0xe1` | Two encoded offset bytes | Pops one condition | 4 |

Before TIP activation both opcodes remain unknown. After activation they are available in ordinary runtime code, prepared runtime chunks, and resident initcode. Other opcode activations remain controlled by their own fork rules. This TIP does not introduce RJUMPV.

### Relative-offset encoding

Each offset byte uses the allowed alphabet of the DUPN/SWAPN immediate encoding in [EIP-8024](https://eips.ethereum.org/EIPS/eip-8024). Allowed bytes are `0x00..0x5a` and `0x80..0xff`. Bytes `0x5b..0x7f` are invalid, so valid offset bytes contain neither JUMPDEST nor PUSH1–PUSH32.

Decode the two bytes in high-digit, low-digit order:

```text
digit(x) = ((x + 145) mod 256) - 17       // 0 through 218
value    = 219 * digit(high) + digit(low) // 0 through 47960
offset   = value if value <= 23980 else value - 47961
```

The signed displacement range is `-23980..23980`, not the full signed 16-bit range. To encode, add 47,961 to a negative offset, split the result into two base-219 digits, and encode each digit as `(digit + 128) mod 256`.

Examples are `80 80` for zero, `80 81` for +1, `5a 58` for -3, and `5a 38` for -35. A truncated resident immediate reads zero bytes past the end, as supplied by ordinary interpreter safety padding; those bytes still go through this decoder.

### Execution and failures

For an ordinary RJUMP at logical position `p`, compute `target = p + 3 + offset`. Reject arithmetic overflow, a negative target, or `target >= code_size` before destination chunk I/O. Resolve and load an in-range destination as for JUMP, then require JUMPDEST.

RJUMPI pops one condition. If nonzero, it takes the same checked relative branch. If zero, it advances three bytes without validating the destination or charging, loading, or warming its target chunk. Invalid immediate encoding fails on either path. Stack underflow, invalid encoding, invalid destinations, and insufficient gas follow exceptional-halt rules.

An untaken RJUMPI whose operand crosses a payload boundary reads the completed operand from padding. It then executes the remaining padding and final transfer as normal fallthrough. That transfer can load the following chunk even though the conditional branch itself did not.

## Jump analysis and existing opcodes

For each prepared chunk, analysis begins after the leading-data offset. Leading immediate data is never a valid destination, even when a byte equals `0x5b`. Within the logical payload, retain the existing PUSH-only jump analysis: skip PUSH data and mark other JUMPDEST bytes. The preparation width scan and this legacy jump analysis are deliberately distinct.

Generated padding JUMPDESTs are marked for the local padding jump. Ordinary logical jumps cannot address those appended positions: global addressing resolves positions beyond a full payload into the next chunk. The transfer and trailer are not ordinary jump destinations.

For JUMP, taken JUMPI, ordinary RJUMP, and taken RJUMPI in chunked runtime code:

1. Check the global destination against logical code size.
2. Compute `index = target / CODE_CHUNK_SIZE` and `local = target % CODE_CHUNK_SIZE`.
3. If `index` differs from the active chunk, reserve its tariff, load it, and mark it warm.
4. Check `local` against its payload jump table, excluding leading data and appended fields.
5. Activate its bytecode and jump to `local`.

An invalid in-range destination in another chunk still incurs the read and its charge before jump validation. A same-chunk jump uses the current analysis and incurs no chunk charge. Untaken JUMPI does not inspect its target. Ordinary legacy code and resident initcode use their own whole-buffer positions rather than the new payload stride.

| Existing operation | Behavior under this TIP |
| --- | --- |
| PUSH1–PUSH32 | Reads contiguous immediate bytes; preparation completes crossings and zero-fills missing final values. |
| DUPN/SWAPN/EXCHANGE | Preparation copies a crossing operand; the opcode's own activation, operand validation, and stack rules still apply. |
| JUMP/JUMPI | Keeps absolute logical destinations; taken cross-chunk branches load on demand. |
| PC | Returns `chunk_index * CODE_CHUNK_SIZE + local_pc` for original payload instructions. |
| CODESIZE | Returns logical runtime size, or resident initcode size; excludes appended fields. |
| CODECOPY | Copies original payload bytes from each requested chunk; never copies generated fields. |
| EXTCODESIZE | Reads size from chunk metadata, returns 23 for inline delegation, or meters a legacy chunk-zero read. |
| EXTCODEHASH | Returns the existing account code hash under the existing empty/nonexistent-account rules; no chunk read. |
| EXTCODECOPY | Copies the addressed account's logical code or synthesized delegation marker; does not follow delegation. |
| CALL/CALLCODE/DELEGATECALL/STATICCALL | Resolves code owner, meters entry chunk zero, then uses normal call semantics. |
| CREATE/CREATE2 | Executes resident initcode, validates logical output, prepares chunks, and publishes code and extension atomically. |
| GAS | Includes added chunk, padding, and transfer charges; gas-sensitive behavior may change. |
| STOP/RETURN/REVERT/INVALID and other halts | Keep their existing behavior; an original halt does not execute appended padding or the tail. |
| Storage, memory, logs, return data | Keep existing semantics and charges; loading a code chunk emits no EVM log. |

### Copy ranges

For CODECOPY and EXTCODECOPY of a chunked account, let `s` be the source offset and `n` the requested length. There are no required chunks when `n == 0` or `s >= code_size`. Otherwise:

```text
end   = s + min(n, code_size - s)
first = s / CODE_CHUNK_SIZE
last  = (end - 1) / CODE_CHUNK_SIZE
```

Reserve the aggregate charge for all indices `first..last` before reading any of them. Charge each index once per copy operation, including the active chunk if it is part of the range. Repeated copies pay warm charges after the first successful access. Copy directly from payload positions, including unchanged leading data. A copy MUST NOT fetch the preceding chunk to reconstruct those bytes.

Bytes past logical code end are zero-filled. Normal memory expansion, copy gas, and exceptional-halt rules apply before the operation completes. Large EVM-width offsets must not wrap when converted to host indices.

For EXTCODECOPY of a nonempty ordinary account, request chunk zero when `n != 0` and `s < LEGACY_CODE_CHUNK_SIZE`, even if `s` is beyond the actual code length or that length is already cached. The fixed 24 KiB threshold makes gas independent of size-cache residency. CODECOPY in an executing ordinary runtime frame already knows its exact size and clips to that size. Empty code, zero-length copies, and legacy external offsets at or above 24 KiB need no chunk read.

## Account extensions and EIP-7702

The account's extension is the sole source of code type. No `get_code_kind_by_hash` lookup or code-payload inspection is needed to discover it. The ordinary account `code_hash` field remains present for every representation.

| Extension | Encoded bytes | Meaning |
| --- | --- | --- |
| Absent/empty | Empty byte string | Ordinary code; the account hash distinguishes empty from nonempty code. |
| Type 1 | `01 || code_size_be_u32 || chunk_hash[0] || ... || chunk_hash[N-1]` | Prepared multi-chunk runtime code. |
| Type 2 | `02 || target_address_20_bytes` | EIP-7702 delegation with the target directly in the account. |

The two nonempty types are alternatives, not simultaneous fields. Type 1 is valid only for `24540 < code_size <= 981600` and exactly `ceil(code_size / 24540)` hashes, between 2 and 40. Its encoded length is `5 + 32*N`, at most 1,285 bytes. Type 2 has exactly 21 bytes and a nonzero target. Unknown tags, malformed lengths, extra bytes, invalid sizes, or invalid hash counts MUST be rejected. An absent extension is not an encoded `00` byte and does not imply empty code.

For type 2:

```text
logical_code = 0xef0100 || target_address
code_size    = 23
code_hash    = keccak256(logical_code)
```

The account hash MUST agree with the target's marker. The target does not also need a chunk-hash vector or a stored marker payload. The client can synthesize the marker for copy/RPC operations. EXTCODESIZE returns 23, EXTCODEHASH returns its marker hash, and EXTCODECOPY returns marker bytes without chunk I/O or a chunk tariff.

Execution follows one delegation hop under [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702). Resolving the target directly from the account requires no marker load and no extra chunk gas. Existing authorization, account-access, and delegation-target charges still apply; executing the resolved target's nonempty ordinary or chunked code pays its normal chunk-zero tariff. Warmth belongs to that resolved code-owner address, including for DELEGATECALL and CALLCODE, independently of the storage context.

A target that is itself delegated is not followed recursively. Its own marker is synthesized and passed through the existing one-hop execution behavior. Delegation to a precompile address retains the existing EIP-7702 treatment rather than automatically dispatching the native precompile.

Installing a valid nonzero delegation sets type 2 and the marker hash atomically. Clearing delegation through the existing zero-target authorization operation restores empty code and an empty extension; zero is not a stored type-2 target. EIP-3607 sender checks and authorization eligibility inspect account metadata without reading chunk zero. Authorization ordering, nonce handling, refunds, and persistence across execution failure remain governed by the existing authorization rules and Tempo hooks.

Reth account persistence, trie encoding, historical snapshots, and EVM account conversion MUST preserve the selected extension. In the proposed trie representation it is a chain-specific fifth RLP string; the enclosing format and Compact codec must support both types. Replacing chunked code with ordinary code, delegation, or empty code replaces the code extension and invalidates account-local chunk state. Other account fields and unrelated extensions must be preserved.

## Loading, gas schedule, and ordering

Chunk gas is additional to ordinary opcode, account-access, memory, copy, call, and creation charges:

```text
chunk_gas = 28680 * number_of_cold_required_chunks
          +  1000 * number_of_warm_required_chunks
```

A short final chunk pays the same tariff as a full chunk. These are draft consensus constants pending persistent-provider calibration.

| Operation | Required chunk requests |
| --- | --- |
| Nonempty runtime transaction/call entry | Chunk zero of the resolved code owner. |
| Taken jump to another chunk | Destination chunk, cold or warm. |
| Generated final RJUMP | Next chunk, cold or warm. |
| Same-chunk jump or ordinary sequential opcode | None. |
| Generated padding jump | None; only its opcode gas and JUMPDEST gas. |
| Untaken JUMPI/RJUMPI | None for the branch target; subsequent fallthrough may request a chunk. |
| CODECOPY / chunked EXTCODECOPY | Every unique chunk in the clipped source range. |
| EXTCODESIZE of ordinary nonempty code | Chunk zero on every operation, even if its bytes or size are cached. |
| EXTCODESIZE of type 1 / EXTCODEHASH | None; account metadata is sufficient. |
| Delegation marker inspection or copying | None; type 2 provides the target. |
| Empty account, native precompile dispatch, resident initcode | No runtime chunk request. |

For each operation, determine the required set and reserve its complete chunk tariff before its first chunk fetch or warmth change. An unaffordable request halts out of gas without fetching or warming any of that operation's required chunks. Ordinary account loading or memory work that precedes the chunk operation follows its existing ordering; the rule is about chunk I/O and warmth.

Successful requests load and warm chunks, then execution performs destination validation or copying. A later invalid jump may therefore follow a charged chunk read. A provider failure is a node error, not an EVM exceptional halt. Native empty-code handling must never be used to hide a missing required chunk.

At CALL-family entry, reserve chunk zero after normal account/delegation costs and before the 63/64 child-gas calculation. The charge reduces gas available for forwarding. Cross-chunk jumps, generated transfers, and copies during execution spend gas in the current frame. At transaction entry, the resolved runtime's chunk-zero charge is reserved from the transaction execution budget before its first instruction. Initcode has no runtime-chunk tariff; its normal word metering and CREATE2 hashing remain.

The generated transfer is a separate operation from the preceding padding jump. Its two-gas opcode charge precedes its destination chunk tariff. Insufficient transfer gas does not read the successor. REVERT does not refund spent chunk or padding gas.

### Warmth, snapshots, and caches

Consensus warmth is keyed by `(resolved code-owner address, chunk index)` within the current code identity. It is independent of ordinary account warmth, access-list entries, and physical cache residency. Two addresses with equal code hashes may share immutable bytes and analysis but not chunk warmth. Two delegators resolving to the same target share that target's chunk warmth.

The journaled account keeps its resolved logical size and a map of requested chunks. Each entry contains one analyzed bytecode and its warm flag. No eager vector of every analyzed chunk is required. Account metadata loading alone does not load or warm chunk zero.

Loading and warming are distinct operations, like storage access. A chunk-loading handle can check bounds and retrieve bytes without changing warmth. The execution path first reserves gas, loads the required bytes, then explicitly warms the handle and journals a cold-to-warm transition. Skipped, failed, and out-of-range requests do not warm chunks.

Revert restores warmth to its checkpoint state. A chunk warm before a checkpoint stays warm after reverting it; a chunk first warmed inside that checkpoint becomes cold. Immutable bytes and analysis may remain cached. Transaction reset clears logical chunk warmth even if the bytes stay resident. Code replacement invalidates the account-local map; account snapshot restoration restores the previous code identity and warmth together. Handle drop needs no independent scan of old account-change journal entries.

A warm request still costs 1,000 gas. Reusing the active chunk for ordinary execution or a same-chunk jump is not a new request. Copy operations explicitly request their source chunks and therefore pay the warm tariff even for an already active source chunk.

### Pricing rationale

At the proposed one-billion-gas-per-second target, 28,680 gas corresponds to 28.68 microseconds and 1,000 gas to one microsecond. The cold price was originally proposed for a 12 KiB experiment and must be measured again for the current stored format. Neither that old experiment nor the byte limit establishes adequate pricing.

Account reads also carry up to 1,280 bytes of chunk hashes. The account-proof and metadata cost is separate from payload loading and must be reviewed under account/state-access pricing. Padding increases stored bytes but currently has no separate storage-deposit charge; executed padding and transfers do have the opcode charges specified above.

## Provider and client responsibilities

The provider must support direct reads of a prepared chunk by logical code hash and index:

```rust
fn get_code_chunk_by_hash(
    &mut self,
    code_hash: &B256,
    index: u32,
) -> Result<Option<CodeChunk>, Self::Error>;
```

A `CodeChunk` wraps a bytecode buffer with its own jump analysis. Code size and type belong to account metadata, while the requested index belongs to the load/frame context. No separate persisted `PreparedCodeChunk` record is required. The client derives payload length, tail position, and start offset from that context and the validated stored bytes.

Typed, erased, cached, counted, and asynchronous adapters must preserve missing-data and error behavior. An out-of-range index returns no chunk without payload I/O or warmth changes. Ordinary accounts use the existing whole-record lookup as a bounded legacy chunk-zero read; do not split an old 24 KiB record using the smaller payload stride. Delegated accounts synthesize marker bytes from type 2.

For type 1, the provider returns the exact stored buffer. Creation/ingestion validates the payload length, 32-byte padding construction, tail, start-offset bounds, and ordered commitments, including agreement between adjacent chunks' copied immediate data. When complete logical code is available, verify its global hash and deterministic preparation. Execution may validate local shape and account context but does not rehash every request.

Missing required data, malformed lengths, invalid preparation, and detected corruption are node errors. Rejected cached entries must be evicted through all adapter layers so a repaired provider can be retried. A whole-code record in a cache MUST NOT silently substitute for a missing required prepared chunk.

Creation and synchronization publish the account extension, chunk commitments, buffers, and any `(code_hash, index)` lookup entries atomically. Preparing and storing every buffer does not make every chunk transaction-warm. Full logical code may be retained or reconstructed for RPC and synchronization; execution MUST NOT fetch the whole multi-chunk contract to satisfy one chunk request.

## Compatibility and remaining decisions

Ordinary pre-fork account and bytecode records remain usable without splitting or backfilling them. New ordinary deployments up to 24,540 bytes use the same representation. Historical execution retains its original fork limits and gas schedule. Activation must coordinate code limits, both new opcodes, preparation, account extensions, providers, and tariffs.

The logical hash, code-copy results, and original instruction positions are preserved by ordinary boundary preparation. Added gas changes GAS, estimates, call forwarding, and potentially execution success. Instructions `0xe0` and `0xe1` also gain new behavior at activation. Tools and replay reports must distinguish these intended differences from bugs.

Two compatibility issues require explicit resolution before scheduling:

1. **Historical delegation metadata.** Existing databases may store only an EIP-7702 marker under a code hash. Such a record cannot provide the target directly from the account without prior work. Clients must specify an authenticated ingestion/conversion or auxiliary-index strategy that supplies type-2 account information, preserves historical state roots, and defines when the new extension enters the trie. The current EVM2 path expects normalized account metadata and has no execution-time code-kind fallback. Therefore, this draft does not claim that historical delegation already works without conversion or extra provider work.
2. **Alternative instruction entries.** The preparation scan recognizes immediate widths, while legacy jump analysis skips only PUSH data. Invalid immediate sequences can therefore admit another valid JUMPDEST entry whose following PUSH crosses a boundary differently from the linear scan. The current EVM2 buffer is immutable and uses the canonical start offset; it does not reprepare code for that alternate path. Such paths can consume generated padding and behave differently. Exact behavior for these cases must be reviewed before claiming compatibility for every possible byte sequence; compilers are not required to repair them.

The general design does not require compiler boundary placement. These remaining cases and metadata activation must be settled in the protocol and clients, rather than delegated to compiler authors.

## Reference implementation and measurements

The current EVM2 draft is [implementation PR #574](https://github.com/alloy-rs/evm2/pull/574), with [tests in PR #575](https://github.com/alloy-rs/evm2/pull/575) stacked on its branch. # Tooling

- Compilers may emit ordinary bytecode without aligning instructions or inserting terminal STOPs at payload boundaries. Assemblers opting into RJUMP/RJUMPI must use this TIP's immediate encoding and JUMPDEST rules.
- Deployment tools should expose the 981,600-byte logical runtime limit, the independent 1,966,080-byte initcode limit, and existing gas and transaction-size constraints.
- RPC returns logical code. Debuggers report original global PCs and hide generated padding/tail steps, while gas accounting still includes those steps. Disassemblers inspecting stored chunks must show appended fields separately from logical payload.
- Providers, snapshots, proofs, and account codecs must support both extension types. Account metadata and code identity must survive serialization, rollback, and restart.
- Gas estimators must use the same logical chunk warmth and charge ordering as execution. Replay tools must compare logical results, gas, logs, state roots, and rollback with cold and populated physical caches.
- JIT/AOT must remain disabled for TIP-enabled execution until they implement equivalent preparation, target checks, loading, and gas behavior.

# Observability

No new on-chain event is emitted for a chunk read. Clients should expose local diagnostics independently of consensus behavior:

- Failed required reads: block/transaction context when available, code hash, chunk index, expected layout or length, and failure reason. The operation remains a node error.
- Aggregate counts of logical cold/warm requests, physical cache hits/misses, bytes read, read latency, and analysis time. Do not attach unbounded account-address or code-hash labels to metrics.
- Activation reports covering ordinary legacy records, delegated-account normalization, historical snapshots, account-proof growth, and provider gas calibration.

These metrics describe behavior; they do not require extra consensus state such as per-account chunk statistics.

# Threat Model

Contract authors and callers can deliberately cross boundaries, target invalid destinations, jump among many chunks, copy large ranges, and repeatedly revert. Clients must use checked arithmetic, reserve gas before chunk I/O, preserve warmth journals, and bound every stored buffer.

Stored data becomes trusted only after creation or ingestion validates its commitments and preparation. A forged trailer must not make PUSH data a valid destination, and matching RJUMP bytes must not grant the final-tail exception to original code. A malformed or missing provider record must not be interpreted as an empty contract.

Account type and marker hashes are authenticated account data. Guessing delegation from arbitrary code prefixes or trusting a bytecode cache's remembered kind can select the wrong execution path. Replacing code must also replace its type and invalidate account-local chunk state.

Physical caches, asynchronous suspension, tracing, and speculative execution must not change consensus warmth, gas, or output. Larger hash vectors and prepared buffers increase proof and storage costs that must be measured before activation.

# Invariants

1. Logical runtime size is at most 981,600 bytes. Type 1 has exactly `ceil(code_size / 24540)` ordered hashes, between 2 and 40.
2. Every prepared buffer has one payload, exactly 32 padding bytes, one STOP or three-byte RJUMP tail, and one offset byte, totaling at most 24 KiB.
3. Chunk hashes commit to complete stored buffers; concatenated payloads recover logical code and its account hash.
4. Leading immediate bytes remain unchanged. The offset identifies them, and the payload jump table excludes them.
5. Crossing immediates have their continuation in the preceding padding. Final missing immediate bytes are zero-filled.
6. Only the authenticated final transfer may bypass JUMPDEST checking. Padding jumps are checked locally; all ordinary taken jumps validate logical destinations.
7. Generated transfers preserve the stack and enter the successor at its start offset. A data-only final chunk is not fetched by fallthrough when no logical instruction remains.
8. Copies return logical payload bytes without appended fields or predecessor reconstruction. Metadata-only operations do not read chunks.
9. Chunk gas follows owner/index warmth, never physical residency. An unaffordable chunk operation fetches and warms none of its required chunks.
10. Revert restores code identity, extension, and logical warmth; immutable bytes may remain cached. Transaction reset clears warmth.
11. Type 2 directly supplies its delegation address and marker hash. No marker read or chunk tariff is needed merely to resolve or inspect delegation.
12. Missing or invalid required provider data is a node error. Interpreter and async adapters agree on loading and error ordering.

## Required tests and success criteria

- **Limits and layout:** empty code; payload lengths 24,539, 24,540, and 24,541; unchanged legacy lengths 24,575 and 24,576; 981,600 bytes; a short 40th chunk; rejection at 981,601. Test initcode at 1,966,080 and 1,966,081 through every creation path. Verify exact stored lengths and full-buffer hashes.
- **Preparation:** all PUSH widths and every crossing position; truncated final values; offsets 0 through 32; data-only final chunks; crossing relative/stack-opcode immediates; all unused-padding lengths 0 through 32; full-stack fallthrough; malformed padding, tails, and trailers. Preserve the documented alternative-entry cases as explicit compatibility tests.
- **Jumps:** taken/untaken JUMPI and RJUMPI; forward/backward and same/cross-chunk jumps; invalid bounds; invalid JUMPDEST and leading `0x5b` data; every encoded relative displacement and forbidden immediate byte; out-of-gas loops; ordinary end-of-payload RJUMPs matching generated-tail bytes. Test pre-activation unknown-opcode behavior and resident initcode.
- **Copies and metadata:** zero length, out-of-range/maximal offsets, multiple boundaries, leading data, final zero fill, active-source warm charging, absent predecessors, and aggregate out-of-gas before any read. Ordinary EXTCODESIZE/EXTCODECOPY must charge identically with unknown and cached sizes. Chunked size/hash and delegation inspection need no payload reads.
- **Gas and state:** cold/warm budget edges, small final chunks, padding and transfer gas, call forwarding, two owners with equal hashes, multiple delegators to one owner, nested calls/reverts, warmth before a checkpoint, code-type replacement with rollback, and transaction reset with retained bytes.
- **Accounts and providers:** both extension encodings, invalid tags/lengths/targets/hash counts, marker-hash agreement, creation and authorization transitions, one-hop delegation, native precompile cases, historical delegation normalization, atomic publication, snapshot/Compact/trie round trips, missing/corrupt data, cache eviction/retry, and async suspension without duplicate charging.

Before scheduling, settle the compatibility decisions above and verify execution on historical state and new deployments with the same fork rules. Replay must account explicitly for intended chunk/padding gas differences and show identical results across physical-cache states and interpreter backends. Publish persistent-provider measurements, proof/storage growth, Tempo gas effects, and the delegation conversion policy.
