# TIP-1145: TIP-20 Payment Storage Optimization

## Abstract

This proposal reduces TIP-20 payment reads through flat token-specific TIP-403 policies, packed memberships, and packed token control and supply. Token policies lose sharing, increasing state and requiring token admins to maintain their own lists. Generic TIP-403 policies remain reusable. T14 converts pathUSD automatically, while other existing tokens and receivers opt in.

## Motivation

Authorization currently follows policy IDs, compound references, metadata, and memberships. Flat role modes remove that indirection. Packing modes with pause saves another payment read, while supply/cap and quote/currency packing reduce mint and metadata reads.

[Current usage](#token-issuer-policies) mainly exercises allow-all and simple policies. Allow-all already skips policy metadata, but benefits from control packing. [Receive filters](#address-level-receive-policies) have limited adoption. Adoption estimates migration scope and state growth, while activity weights expected gains. Benchmarks MUST still cover compound policies, both receive filters, blocked delivery, and fresh allocations.

# Specification

## Policy Model

Each token-specific policy is permanently keyed by its token address, with independent sender, transfer-recipient, and mint-recipient rules. Receivers have token and sender filters. Generic TIP-403 policies retain their existing semantics and immutable types.

| Value | Mode | Allow? |
|---|---|---|
| `0` | `ALLOW` | `true` |
| `1` | `DENY` | `false` |
| `2` | `WHITELIST` | `m` |
| `3` | `BLACKLIST` | `!m` |

`m` is membership in the checked list, defaulting to `false`. Token filters check token addresses, other rules check accounts. Mode changes MUST preserve lists without copying, clearing, or enumerating them.

| ABI value | `AuthRole` | Membership mask |
|---|---|---|
| `0` | `SENDER` | `0b001` |
| `1` | `RECIPIENT` | `0b010` |
| `2` | `MINT_RECIPIENT` | `0b100` |
| `3` | `TRANSFER` | `0b011` |
| `4` | `ALL` | `0b111` |

Queries require every selected rule to allow the same account, checking sender, recipient, then mint recipient and stopping on rejection. ABI values MUST map to masks. `ALL` edits all three issuer lists together.

## Storage

### TIP-403

Roots `0..4` retain generic policies and legacy state. New entries use standard Solidity mapping layout, one word each. Receive configurations reuse the first word of the legacy `receivePolicies[receiver]` entry at root `3`, so a single read serves both layouts:

| Root | Entry | Fields, low to high |
|---|---|---|
| `5` | `tokenPolicies[token]` | `uint8 isSet`, sender mode, recipient mode, mint-recipient mode |
| `6` | `tokenUserFlags[token][account]` | Bits `0..2`: sender, recipient, mint recipient. Bit `3`: receiver's token membership |
| `3` | `receivePolicies[receiver]`, first word | `uint8 kind`, token mode, sender mode, `uint8 recoveryMode`, `address thirdPartyRecoveryAuthority` |
| `7` | `receiveSenderMembers[receiver][sender]` | `bool member` |

The legacy word stores `bool hasReceivePolicy` in its first byte, so `kind` is `0` (unconfigured) or `1` (legacy). `kind == 2` selects the new layout and overwrites the legacy word. The legacy recovery-address word is no longer read.

Modes occupy one byte. Flags and booleans encode `0`/`1`, unused bits MUST be zero. Registration uses only the TIP-20 prefix and `isSet == 1`. Prepared issuer policies leave `isSet == 0`. Future-token receive preferences neither register nor deploy tokens.

Recovery modes are `0` originator, `1` receiver, `2` third party. The stored address MUST be zero except in mode `2`. Receivers unconfigured in both layouts allow all with originator recovery. Membership edits do not activate policies.

### TIP-20

| Slot | Packed use |
|---|---|
| `4` | External currency when inline bytes are zero |
| `6`, `7`, `13` | Obsolete quote, staged quote/ID, and cap words, cleared on activation |
| `8` | Packed supply and cap |
| `12` | Packed control, replacing pause |
| Others | Unchanged, including balances at root `9` |

Existing roots and unrelated fields MUST retain their locations. The legacy ID already shares slot `7` with the staged quote.

```solidity
struct TokenControl { // slot 12
    uint8 flags; // bit 1: paused, bit 2: packed layout
    uint8 modes;
    uint64 quoteId;
    uint64 nextQuoteId;
    bytes14 currency;
}

struct SupplyState { // slot 8
    uint128 totalSupply; // bits 0..127
    uint128 supplyCap;   // bits 128..255
}
```
Legacy slot-`12` words are exactly `0`/`1`. Public versions are `0 = LEGACY`, `1 = PACKED`. Malformed encodings MUST revert. Transfers already read pause, so layout detection adds no separate read. Supply/cap getters widen to `uint256`, and mutations preserve the other half. Balances, allowances, amounts, and public arguments remain `uint256`.

Quote IDs are eight-byte suffixes restored with the TIP-20 prefix `0x20C000000000000000000000`. Zero identifies pathUSD. For pathUSD itself, both IDs MUST be zero and getters return `address(0)`. Creation sets quotes equally, staging changes only the staged ID, completion only the active ID. Existing authority, USD, cycle, and pathUSD checks remain unchanged. Undeployed metadata retains its defaults.

Currency is inline when its exact UTF-8 bytes are nonempty, contain no NUL, and fit fourteen bytes. Right-pad with zeros and clear slot `4`. Otherwise, zero the inline field and retain the complete external string and payload. The getter removes padding or reads that string, without normalization or truncation. Packed USD checks compare inline bytes with padded `"USD"`, without an external read.

## Interface

TIP-403 adds:

```solidity
enum PolicyMode { ALLOW, DENY, WHITELIST, BLACKLIST }
enum AuthRole { SENDER, RECIPIENT, MINT_RECIPIENT, TRANSFER, ALL }
enum MembershipKind { ISSUER, RECEIVE_TOKEN, RECEIVE_SENDER }

error InvalidToken();
error InvalidPolicyMode();
error InvalidAuthRole();
error AddressReserved();
error TokenPolicyIdsUnsupported();
error ReceivePolicyIdsUnsupported();

function tokenPolicy(address token) external view returns (
    bool isSet, PolicyMode senderMode, PolicyMode recipientMode, PolicyMode mintRecipientMode
);
function tokenUserFlags(address token, address account) external view returns (uint8 flags);
function isTokenAuthorized(address token, address account, AuthRole role) external view returns (bool authorized);
function setTokenPolicyModes(address token, PolicyMode senderMode, PolicyMode recipientMode, PolicyMode mintRecipientMode) external;
function addTokenMembers(address token, address[] calldata accounts, AuthRole role) external;
function removeTokenMembers(address token, address[] calldata accounts, AuthRole role) external;
function receiveConfig(address receiver) external view returns (
    bool hasReceivePolicy, PolicyMode tokenMode, PolicyMode senderMode, address recoveryAuthority
);
function setReceiveConfig(PolicyMode tokenMode, PolicyMode senderMode, address recoveryAuthority) external;
function addReceiveTokens(address[] calldata tokens) external;
function removeReceiveTokens(address[] calldata tokens) external;
function addReceiveSenders(address[] calldata senders) external;
function removeReceiveSenders(address[] calldata senders) external;
function receiveSenderMembership(address receiver, address sender) external view returns (bool member);

event TransferPolicyUpdated(address indexed token, PolicyMode senderMode, PolicyMode recipientMode, PolicyMode mintRecipientMode);
event ReceivePolicyUpdated(address indexed receiver, PolicyMode tokenMode, PolicyMode senderMode, address recoveryAuthority);
event PolicyMembershipUpdated(MembershipKind kind, address indexed owner, address indexed account, AuthRole role, bool isMember);
```

- Token arguments MUST have the TIP-20 prefix, otherwise revert `InvalidToken`. Issuer setters require deployment, `isTokenAuthorized` requires registration. Raw membership queries and receive-token lists support future tokens. Views read only TIP-403 state and expose prepared configurations.
- Issuer setters require the token's current `DEFAULT_ADMIN_ROLE` (`bytes32(0)`), otherwise revert `Unauthorized`. Receive setters modify only `msg.sender`. Virtual callers revert `VirtualAddressNotAllowed`, ReceivePolicyGuard callers revert `AddressReserved`.
- Issuer members and receive senders MUST NOT be virtual addresses, otherwise revert `VirtualAddressNotAllowed`. Invalid mode/role encodings revert `InvalidPolicyMode`/`InvalidAuthRole`.
- Public recovery authority is zero for originator recovery, the receiver for receiver recovery, or a third party. Virtual addresses and protocol precompiles revert `InvalidRecoveryAuthority`.

Add/remove batches write membership `true`/`false`, preserving unrelated bits. Lists remain editable in every mode. Validate caller and applicable token/role once, even for empty batches. Process entries in calldata order, including duplicates and no-ops. Empty batches make no member writes. Normal gas limits apply, without a separate batch limit.

TIP-20 adds `transferPolicy()`, returning sender, recipient, and mint-recipient modes.

## Execution

TIP-403 remains canonical. Mode setters MUST atomically synchronize changed modes into packed token control. Legacy tokens receive no cache writes. Memberships, receive settings, registry authorization views, and zone policy witnesses remain registry-only.

Token-specific policies always use the packed layout. Packed tokens obtain pause, layout, and issuer modes from slot `12`, while legacy tokens retain legacy authorization without consulting `tokenPolicies`. List modes read account flags, `ALLOW`/`DENY` skip them. Checks SHOULD reuse decoded configuration and flags.

| Operation | Issuer checks | Receive-filter sender |
|---|---|---|
| Transfers, including memo, allowance, system variants | Sender for `from`, then recipient for resolved destination | `from` |
| `mint`, `mintWithMemo` | Mint recipient for resolved destination | `msg.sender` |
| Protocol fee deposit | Sender for payer | No receive check |

After issuer and applicable allowance/spending checks, receive evaluation loads the receiver's configuration word. Unless `kind == 2`, use the legacy receive path. Otherwise, check token membership at bit `3`, then the receiver/sender entry. Constant modes skip memberships. Token rejection has priority. `validateReceivePolicy` returns `(true, NONE)` or `(false, TOKEN_FILTER/RECEIVE_POLICY)`.

Other checks, ordering, errors, and exemptions MUST remain unchanged, including [TIP-1022](./tip-1022.md) virtual resolution and [TIP-1028](./tip-1028.md) blocked delivery, receipts, and claims. Mint checks the `uint256` sum and cap before narrowing. Cap updates check current supply, then the existing maximum. Burns retain underflow checks. Metadata remains readable while paused.

Getters/setters decode the actual layout, preserve unrelated fields, and never convert implicitly. Mint reads packed supply/cap at slot `8`. Unchanged balance, allowance, permit, reward, refund, and AMM settlement paths acquire no layout probe. Fee routing can reuse quotes, but settlement MUST use its cached route. Validator payout benefits through ordinary transfers.

TIP-1060 applies to whole-word transitions with existing fee exceptions, without credits for individual fields. Replay MUST validate layout dependencies and re-decode after activation, including within the same transaction. Exact-word dependencies and balance `Sinc`/`Sdec` remain unchanged, though packing can increase conflicts.

### Read Savings

Counts are distinct cold storage keys, not gas or physical reads. A successful transfer with a previously compound issuer policy and both new receive lists reads:

| Read group | Today | This proposal |
|---|---:|---:|
| Pause / packed control | 1 | 1 |
| Policy binding, compound metadata/references, leaf metadata | 5 | 0 |
| Sender/recipient memberships or flags | 2 | 2 |
| Separate receive-token membership | 1 | 0 |
| Receiver configuration and sender membership | 2 | 2 |
| Sender/recipient balances | 2 | 2 |
| **Total** | **13** | **7** |

Packing adds one saved payment read and two saved mint reads beyond flat policies. Shared configuration words let unconfigured and legacy receivers keep a single configuration read. Legacy tokens keep legacy authorization without an extra registration read. Blocked delivery saves the separate recovery-address read, with guard/receipt work counted separately. Burn/refunds gain no policy-read savings. The [appendix](#successful-workloads) covers other workloads and counting assumptions.

### Writes and State Growth

| Update | Current TIP403 words | New TIP403 words |  |
|---|---:|---:|---:|
| All issuer modes across `T` tokens | - | `T` |  |
| Issuer members across `T` tokens | `N` to `3 × N` | `T × N` |
| Receive-token or sender members across `R` receivers | `N` | `R × N` |
| One receiver configuration | 2 | 1 |  |

`N` is list entries, `T` tokens and `R` receivers sharing a policy today. Counts exclude creation/activation and assume the same update across participants. Packed mode caches add a token write only when changed. Current issuer lists need one word per entry for simple policies, up to three for distinct compound leaves. New flags preserve unrelated bits with a read-modify-write. Modes need no membership fanout.

Transfers retain two balance writes, mint/burn retain supply and balance write counts, and pause/quote/cap changes update one packed word. Packing reclaims obsolete token fields, while independent registry lists grow with adoption and membership counts. Overlap saves membership keys, but sharing losses increase maintenance. Retained legacy state is not reclaimed.

## Creation, Migration, and Compatibility

New native tokens MUST atomically initialize packed storage and three `ALLOW` modes, preserving prepared receive-token bits. Only pathUSD may have a null quote. Other quotes MUST be deployed TIP-20s, otherwise revert `InvalidQuoteToken`.

### pathUSD at T14

Before the first T14 block's transactions, the protocol MUST convert pathUSD if it is deployed, still legacy, uses policy ID `0` or `1`, and its values fit [the packed layout](#token-storage-conversion). Otherwise leave it unchanged. If T14 is active at genesis, run this step before the first post-genesis block's transactions.

ID `0` becomes three `DENY` modes. ID `1` becomes three `ALLOW` modes. Register these modes and convert storage atomically, replacing prepared modes and clearing the old generic binding. No admin call is needed.

### Admin and Receiver Opt-In

Tokens not converted at T14 and receivers MAY stay legacy indefinitely.

For admin opt-in, token admins MUST prepare equivalent modes and memberships with the normal setters, leaving `isSet == 0`. Calling `changeTransferPolicyId(type(uint64).max)` under `DEFAULT_ADMIN_ROLE` atomically sets `isSet = 1`, preserving the prepared policy, clears the obsolete generic binding, and converts the token to the packed layout. The reserved ID MUST NOT be allocated to generic policies. Repeating it is a no-op, other IDs after activation revert `TokenPolicyIdsUnsupported`. Token-specific policies cannot be shared, replaced, or switched back to legacy.

Receivers prepare lists, then `setReceiveConfig` atomically activates modes and recovery. `kind == 2` permanently selects the new layout, including `ALLOW`/`ALLOW`. Legacy policy edits continue to govern users until they switch.

| Existing APIs | After activation |
|---|---|
| `transferPolicyId()`, `tokenTransferPolicyId(address)` | Reserved ID for token-specific policies, legacy behavior otherwise |
| `migrateTransferPolicyIds(address[])` | Copies legacy bindings, skipping token-specific tokens. Does not activate policies |
| `receivePolicy(address)`, `setReceivePolicy(uint64,uint64,address)` | Legacy behavior until receiver opt-in, then revert `ReceivePolicyIdsUnsupported` |

`validateReceivePolicy` retains its selector/result encoding. Historical execution retains its original interpretation, and legacy state remains stored.

### Token Storage Conversion

Both migration paths use this conversion without external callbacks or membership scans:

1. Read journal-state currency, quotes, supply, cap, pause, and the selected modes. Non-pathUSD null or undeployed quotes revert `InvalidQuoteToken`, supply or cap above 128 bits revert `SupplyCapExceeded`.
2. Build packed words, preserving external currency unless it fits inline. Clear slots `6`, `7`, `13`, and slot `4` only for inline currency. Write supply at `8`, then control at `12` last, skipping unchanged writes.

Admin opt-in pays normal gas and uses TIP-1060 credit accounting. The T14 conversion runs outside user execution with no gas or credit changes. Malformed control words are unreachable and halt as fatal errors.

# Tooling and Dependencies

SDKs and zones MUST adopt the new policy interfaces. Zone tokens keep the legacy layout. At T14, an active mirrored token-specific policy resolves to the reserved ID when no generic binding exists, including for previously enabled zone tokens. Without either policy, the legacy local policy ID applies. Zone policy proofs remain TIP-403-only, while token roles, balances, and pause need separate proofs. Storage/historical decoders MUST use the fork and actual token version.

Tools MUST check that pathUSD can convert before scheduling T14. Migration tools MUST reconstruct legacy lists from events, reconcile edits, and show differences before admin opt-in. They SHOULD compare logical values and simulate activation, including its storage conversion. Coverage never determines consensus.

Tests/benchmarks MUST cover mixed/historical layouts, all modes/roles, compound and receive lists, malformed encodings, activation rollback, quote/currency/supply boundaries, blocked delivery, fresh allocations, fees, and replay. Report cold/warm loads, writes, gas, credits, state growth, conversion cost, and re-execution.

# Observability

Configuration setters emit `TransferPolicyUpdated`/`ReceivePolicyUpdated` once per successful call, including no-ops. Membership setters emit `PolicyMembershipUpdated` per entry in calldata order, including duplicates/no-ops. Empty batches emit none. Add/remove uses `isMember = true`/`false`.

For `ISSUER`, `owner` is the token, `account` its member, and `role` the requested ABI role. For `RECEIVE_TOKEN`/`RECEIVE_SENDER`, `owner` is the receiver, `account` the token/sender, and `role` MUST be `SENDER`. Kind values follow declaration order.

Creation emits three `ALLOW` modes. User-triggered policy activation MUST emit `TransferPolicyUpdated` with the active modes. Activation's storage conversion emits no further events. The T14 conversion creates no receipts or logs. Legacy receive setters keep their old event signature. Other events remain unchanged.

Pool maintenance MUST revalidate on affected policy events, role changes, admin activation, and T14. Generic-policy events affect only users still on legacy paths. Clients SHOULD expose migration failures/gas, coverage, cache mismatches, changed words, and replay invalidations.

# Threat Model

- Token admins and receivers control their respective policies. Role checks and packed updates enforce field isolation.
- Native clients derive packed values from canonical state and synchronize caches atomically.
- Registry consumers use canonical TIP-403 state without relying on indexers or token caches.

# Invariants

For equivalent policies, payment outcomes, ordering, errors, and exemptions MUST remain unchanged, including virtual resolution, blocked delivery, receipts, and claims.

- Legacy authorization remains active until admin opt-in or pathUSD conversion at T14. Generic policies and historical execution retain their behavior.
- Storage conversion preserves exact logical token values, account code, unrelated roots, balances, roles, allowances, nonces, and receipts.
- Cached modes equal canonical registry modes, and updates preserve unrelated fields. Failed calls leave no state, credit, or event changes.
- Replay validates the layout it decoded and preserves balance-delta behavior.
