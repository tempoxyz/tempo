# TIP-1181: Timelocked Owners for Configurable Accounts

## Abstract

This TIP lets a configurable account give any owner an activation delay. A delayed owner's approvals don't count toward a quorum until the owner has publicly requested activation and the delay has passed. During the delay, owners whose weights reach a new `cancel_threshold` can cancel the request. Delayed owners give configurable accounts recovery keys that can't act by surprise, and escape paths from co-signers that stop responding, without smart contract wallets or offchain enclaves. The main limitation is that the delay protects an account only if someone able to cancel is watching.

## Motivation

[TIP-1107](./tip-1107.md) makes every owner act immediately. Its threat model lists "timelocks or dead-man switches" as a planned follow-up and notes that until then "a recovery provider is an ordinary owner with full authority". Three common setups need a delay:

1. **Recovery without surprise.** A user wants a recovery key or provider that can replace a lost passkey. With immediate owners, whoever holds the recovery key can take the account at any moment. Users want the recovery to be visible for days first, so they can stop it if they still hold the passkey.
2. **Co-signer escape.** An account can require a co-signing service, such as a transaction-screening service, as an owner so that a stolen user key can't move funds alone. If the co-signer goes offline, shuts down or refuses valid transactions, the user needs a way to continue without it. That way must not work right away, or a thief holding the user's key would use it to skip the co-signer.
3. **Dead-man switch.** An heir or a company's backup quorum should gain authority only after the primary owners have been inactive for some time.

The alternatives each fall short:

| Alternative | Problem |
|---|---|
| Pre-signed transactions with `valid_after` on a reserved 2D nonce lane | They count time but can't express "this owner gains weight". Any owner update cancels them, so they must be re-signed after every rotation, and they can't name a passkey that doesn't exist yet. |
| An enclave or offchain service that adds its signature after a delay | Moves trust to the enclave vendor and its operator, and needs a separate liveness oracle. |
| A smart contract wallet with a timelock module | Loses native account features such as access keys and fee sponsorship. |

## Assumptions

- Block timestamps follow Tempo's consensus rules and can't be moved far from real time. A delay is only as precise as those bounds.
- Owners who can cancel watch for activation requests, directly or through a wallet or monitoring service. If no one watches, a delay just postpones a takeover.
- Builders and the transaction pool don't censor cancellation transactions for the whole delay. Delays should be days, not minutes.
- TIP-1107, TIP-1111 and TIP-1113 are active. Accounts whose configuration has no delayed owner behave exactly as under those TIPs.

# Specification

## Overview

**Terms.** These add to the terms in [TIP-1107](./tip-1107.md#overview).

| Term | Meaning |
|---|---|
| Delay | An owner's activation delay in seconds. Zero means the owner is immediate, as in TIP-1107. |
| Immediate owner | An owner with delay zero. |
| Delayed owner | An owner with a nonzero delay. |
| Activation request | A delayed owner's signed request to start its delay, recorded onchain. |
| Active | A delayed owner is active when its activation request was recorded for the current configuration version and its delay has passed. |
| Cancel threshold | The weight that approvals must reach to cancel an activation request. A new configuration field. |
| Canceller set | Approvals from owners other than the target, each immediate or active, whose weights add up to at least the cancel threshold. |

**Who can do what.**

| Operation | Authority |
|---|---|
| Request activation | The delayed owner alone, by signature. Anyone can submit it. |
| Cancel or deactivate | A canceller set, by signature, or the account's own quorum by direct call. Anyone can submit it. |
| Approve as part of a quorum | Immediate owners always. Delayed owners only while active. |
| Change delays or the cancel threshold | An owner update, signed by a quorum counting only immediate and active owners. |

**Lifecycle.** Alice's account requires a co-signing service and has a timelocked recovery key:

| Owner | Weight | Delay |
|---|---|---|
| Alice's passkey | 3 | 0 |
| Co-signer service | 2 | 0 |
| Recovery key | 3 | 7 days |

Threshold 5, cancel threshold 3.

| Approvals | Weight | Result |
|---|---|---|
| Passkey + co-signer | 5 | Valid. The normal path. |
| Passkey alone | 3 | Invalid. A stolen passkey can't move funds. |
| Co-signer alone | 2 | Invalid. The co-signer can't move funds or cancel requests. |
| Passkey + recovery, recovery not active | 3 | Invalid. |
| Passkey + recovery, recovery active | 6 | Valid. Escape when the co-signer is gone. |
| Co-signer + recovery, recovery active | 5 | Valid. Replaces a lost passkey. |

1. **Co-signer disappears.** Alice signs an activation request with her recovery key, and a sponsor submits it. The request is public and its timer starts.
2. **Seven days pass.** Nobody cancels. The recovery key is now active. Alice signs with passkey and recovery key and removes the co-signer with an owner update. The update bumps the version, which ends every activation, including the recovery key's.
3. **Alternative: a thief has the recovery key.** The thief requests activation. Alice's wallet sees `OwnerActivationRequested` and Alice cancels with her passkey alone (weight 3 meets the cancel threshold). The thief can request again only by signing again, and Alice can rotate the recovery key with passkey + co-signer.
4. **Alternative: Alice lost her passkey.** She requests activation of the recovery key. After seven days, recovery key + co-signer replace the passkey. If a colluding co-signer and a thief with the recovery key tried the same, Alice could cancel with her passkey during those seven days.

## Mechanics

### Configuration

This TIP adds two fields to TIP-1107's [configuration](./tip-1107.md#configuration):

- Each owner gains `delay`, a uint32 number of seconds.
- The configuration gains `cancel_threshold`, a uint8.

A configuration MUST satisfy TIP-1107's rules and all of these:

- Each delay is at most `MAX_OWNER_DELAY = 31,536,000` (365 days).
- If no owner has a delay, `cancel_threshold` is 0.
- If any owner has a delay, `cancel_threshold` is between 1 and `threshold`.
- If any owner has a delay, the eight largest immediate-owner weights add up to at least `cancel_threshold`, so that the immediate owners alone can always cancel.

TIP-1107's rule that the eight largest weights reach the threshold applies to all owners, delayed or not. A configuration whose immediate owners can't reach the threshold is valid. Such an account can act only after a delayed owner activates.

### Encoding

A configuration with no delayed owner is encoded, hashed and derived exactly as in TIP-1107. Existing accounts and signatures are unchanged.

A configuration with at least one delayed owner uses the extended form:

```text
config = [salt, version, threshold, owners, cancel_threshold]
owner  = [address, weight]           // delay 0
owner  = [address, weight, delay]    // delay > 0
```

RLP MUST be canonical. The fifth configuration field MUST be present if and only if an owner has a delay. An owner's third field MUST be present if and only if its delay is nonzero.

The extended form uses new domain strings for the commitment and the derived address. Every owner contributes its delay, zero included:

```text
commitment = keccak256(
  "tempo:configurable-account:config-v2" || salt || uint64(version) ||
  uint8(threshold) || uint8(cancel_threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || uint32(owner[0].delay) || ...
)

account = last20(keccak256(
  "tempo:configurable-account:account-v2" || salt || uint8(threshold) ||
  uint8(cancel_threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || uint32(owner[0].delay) || ...
))
```

Separate domains mean no configuration hashes the same in both forms. An account can switch between forms through an owner update. A new account whose version-0 configuration has a delayed owner derives its address with the v2 formula.

### Activation state

The configurable-account precompile stores one record per (account, delayed owner):

```text
activation[account][owner] = {
  version:      uint64,   // configuration version the request was made under
  activates_at: uint64,   // unix seconds; 0 = no pending or active request
  nonce:        uint64,   // incremented by every request and cancellation
}
```

A delayed owner is **active** for an account at a block when all of these hold:

1. The owner is in the account's current configuration with a nonzero delay.
2. `activation.version` equals the current configuration version.
3. `activation.activates_at` is nonzero and at most the block timestamp.

An owner update ends every activation, because the version changes. Records are never deleted. `nonce` keeps old signed requests and cancellations from being replayed.

### Requesting activation

`requestActivation(account, current, owner, signature)` may be called by anyone, from any transaction. The precompile:

1. Checks `current` against the account's commitment, and reverts with `InvalidConfig` if it doesn't match or the account isn't registered.
2. Requires `owner` to be a delayed owner in `current` (`NotDelayedOwner`).
3. Requires that no request is pending or active for this version: `activation.version != current.version` or `activation.activates_at == 0` (`ActivationExists`).
4. Recovers the signer of `signature`, a primitive secp256k1, P256 or WebAuthn signature, over the digest below, and requires it to equal `owner` (`InvalidSignature`):
   ```text
   activation_digest = keccak256(
     "tempo:configurable-account:activate" || uint64(chain_id) || account || owner ||
     uint64(current.version) || uint64(activation.nonce)
   )
   ```
5. Writes `version = current.version`, `activates_at = block.timestamp + delay` and `nonce = nonce + 1`.
6. Emits `OwnerActivationRequested`.

The owner signs a digest rather than sending a transaction, so a recovery key with no funds, or a P256 key, can request activation through any sponsor. The digest binds the chain, account, version and nonce, so a request can't be replayed after a cancellation, an owner update or on another chain.

### Cancelling and deactivating

`cancelActivation(account, current, owner, approvals)` may be called by anyone. It cancels a pending request or deactivates an active owner. The precompile:

1. Checks `current` against the commitment (`InvalidConfig`), and requires `owner` to be a delayed owner in it (`NotDelayedOwner`).
2. Requires `activation.version == current.version` and `activation.activates_at != 0` (`NoActivation`).
3. Authorizes the cancellation in one of two ways:
   - **Direct.** If `approvals` is empty, `msg.sender` must be `account`, and the call must be a top-level call of a transaction with `msg.sender == tx.origin`. The transaction's own quorum authorizes it. Access keys can't cancel.
   - **Canceller set.** Otherwise `approvals` is an RLP list of 1 to 8 primitive signatures over the digest below. Signers MUST be in strictly ascending address order and MUST be owners in `current`, and none may be `owner`. Each signer MUST be immediate or active. Their weights MUST reach `cancel_threshold`, with TIP-1107's minimality rule: the total minus the smallest weight MUST be below `cancel_threshold`. Failures revert with `InvalidCancellation`.
     ```text
     cancel_digest = keccak256(
       "tempo:configurable-account:cancel" || uint64(chain_id) || account || owner ||
       uint64(current.version) || uint64(activation.nonce)
     )
     ```
4. Writes `activates_at = 0` and `nonce = nonce + 1`, and emits `OwnerActivationCancelled`.

### Authorization changes

TIP-1107's [authorization](./tip-1107.md#authorization) step 1 (quorum) is unchanged and ignores delays. Step 2 (configuration) adds a check after the commitment matches:

- For every approval whose owner has a nonzero delay in the configuration, that owner MUST be active at the transaction's position in the block.

The rule applies wherever TIP-1107 runs step 2:

- transaction outer signatures,
- TIP-1111 grants signed by a configurable parent, and configurable delegates using a grant,
- owner updates, whose quorum is the transaction's,
- `verifyConfigurableAccount` and ERC-1271 `isValidSignature`, which return `false` when a delayed approval is not active, as for a commitment mismatch.

Signatures don't change. A wallet can collect a delayed owner's approval before it activates, but the transaction is valid only once it does.

### Registration

An unregistered account can't have an active delayed owner, since activation needs a commitment. Its first transaction MUST be authorized by immediate owners. `requestActivation` and `cancelActivation` on an unregistered account revert with `InvalidConfig`.

### Zones

[TIP-1154](./tip-1154.md) mirrors commitments, not activation records. Until a later TIP mirrors activation state, zones MUST reject any configurable-account signature that contains an approval from a delayed owner. Zones reject `requestActivation` and `cancelActivation`.

### Transaction pool

Besides TIP-1107's commitment rule, clients MUST revalidate or evict pending transactions whose authorization relies on a delayed owner when that owner's activation record changes, including through a reorg. The pool MUST reject a transaction whose delayed approval isn't active at the pool's current head, and need not queue it until activation.

### Gas

- Each approval from a delayed owner adds one cold storage read (2,100 gas) to the authorization cost `V`, charged as intrinsic gas.
- `requestActivation` charges precompile input costs, `configuration_proof_cost`, the approval cost (3,000 secp256k1, 8,000 P256 or WebAuthn), and the record write: TIP-1000's new state element cost the first time a record is written for (account, owner), otherwise 5,000. It also charges its event's log cost.
- `cancelActivation` charges the same, with one approval cost per canceller signature, plus a 5,000 write and its event's log cost.

## Interfaces

Added to the configurable-account precompile at `0xAACC000000000000000000000000000000000000`:

```solidity
interface IConfigurableAccountTimelock {
    struct ConfigurableAccountOwnerV2 {
        address owner;
        uint8 weight;
        uint32 delay; // seconds; 0 = immediate
    }

    struct ConfigurableAccountConfigV2 {
        bytes32 salt;
        uint64 version;
        uint8 threshold;
        uint8 cancelThreshold; // 0 when no owner has a delay
        ConfigurableAccountOwnerV2[] owners;
    }

    /// @notice Replaces msg.sender's configuration, allowing delayed owners.
    /// @dev Same authority and rules as updateConfig in TIP-1107. `current` may be in either form.
    function updateConfigV2(
        ConfigurableAccountConfigV2 calldata current,
        uint8 threshold,
        uint8 cancelThreshold,
        ConfigurableAccountOwnerV2[] calldata owners
    ) external;

    /// @notice Starts `owner`'s activation delay.
    /// @param signature The owner's primitive signature over activation_digest.
    /// @return activatesAt When the owner becomes active.
    function requestActivation(
        address account,
        ConfigurableAccountConfigV2 calldata current,
        address owner,
        bytes calldata signature
    ) external returns (uint64 activatesAt);

    /// @notice Cancels a pending activation or deactivates an active owner.
    /// @param approvals Empty when called by the account itself, else an RLP list of
    ///        primitive signatures over cancel_digest from a canceller set.
    function cancelActivation(
        address account,
        ConfigurableAccountConfigV2 calldata current,
        address owner,
        bytes calldata approvals
    ) external;

    /// @notice Returns an owner's activation record and whether it is active now.
    function getActivation(address account, address owner)
        external view returns (uint64 version, uint64 activatesAt, uint64 nonce, bool active);

    event OwnerActivationRequested(
        address indexed account, address indexed owner, uint64 version, uint64 activatesAt, uint64 nonce
    );
    event OwnerActivationCancelled(
        address indexed account, address indexed owner, uint64 version, uint64 nonce, bool wasActive
    );
    /// Emitted with ConfigurableAccountConfigUpdated when the new configuration has a delayed owner.
    event ConfigurableAccountTimelockConfigured(
        address indexed account, uint64 version, uint8 cancelThreshold, uint32[] delays
    );

    error InvalidDelay();
    error InvalidCancelThreshold();
    error NotDelayedOwner();
    error ActivationExists();
    error NoActivation();
    error InvalidCancellation();
    error InvalidSignature();
}
```

`deriveAccount` gains a v2 overload taking `cancelThreshold` and `ConfigurableAccountOwnerV2[]`. Configuration errors follow TIP-1107's order, with `InvalidDelay` and `InvalidCancelThreshold` checked after `InvalidThreshold`.

# Compatibility

| Integration | What changes |
|---|---|
| Accounts without delayed owners | Nothing. Encoding, hashes, gas and behavior match TIP-1107. |
| Wallets and SDKs | Encode the extended configuration and v2 hashes. Show each owner's delay and whether it is active. Watch `OwnerActivationRequested` for the user's accounts and offer one-tap cancellation. |
| Signature checkers (ERC-1271, `verifyConfigurableAccount`) | The same signature can be invalid before activation and valid after. Callers that cache results must recheck. |
| Indexers | Parse the three new events. An account's effective authority depends on its activation records as well as its configuration. |
| Zones | Delayed-owner approvals are rejected until a follow-up TIP mirrors activation state ([Zones](#zones)). |
| Payment channels | Unchanged. Vouchers still use an ordinary `authorizedSigner` (TIP-1107 [Supported contexts](./tip-1107.md#supported-contexts)). |

# Observability

- `OwnerActivationRequested` answers "is someone trying to gain authority over this account, and when will they have it?". Monitoring services SHOULD alert every canceller when it fires.
- `OwnerActivationCancelled` answers "who stopped it?" and, with `wasActive`, whether an active owner was removed.
- `ConfigurableAccountTimelockConfigured` records delays and the cancel threshold alongside each configuration update.
- `getActivation` lets wallets and RPC users read the current state.

# Threat Model

The most consequential attack is a **delayed owner's key stolen while nobody is watching**. The thief requests activation and, after the delay, acts with whatever weight the configuration gives that owner together with any other keys they hold. The design limits this by making the request public and cancellable. Configurations SHOULD NOT give one delayed owner weight equal to the threshold, so a stolen delayed key still needs another owner.

| Actor | Controls | Trust | Enforcing check | Failure consequence |
|---|---|---|---|---|
| Delayed owner | Its key; can request activation | Trusted to act only after the delay | Activation record, delay, canceller veto | If unwatched, a stolen key gains authority after the delay |
| Canceller set | Can cancel or deactivate | Trusted not to block recovery forever | Weight at least `cancel_threshold`, excludes the target | A malicious canceller set can veto activation forever; configure so that a co-signer service alone can't reach `cancel_threshold` |
| Immediate quorum | All account actions | Fully trusted, as in TIP-1107 | TIP-1107 authorization | Takes over the account |
| Builders and the pool | Inclusion order | Not trusted to be timely | Long delays | Censoring cancellations for the whole delay lets an activation complete |
| Relayer or sponsor | Submits requests and cancellations | No authority | Signatures bind account, version, nonce and chain | Can delay but not forge or replay |
| Block proposer | Timestamp within consensus bounds | Bounded | Consensus timestamp rules | Shifts activation by at most the timestamp tolerance |

Residual risks:

- **Dormant accounts.** A delay protects only owners who notice the request. Wallets should push notifications and accounts should have more than one canceller.
- **Deactivation race.** An active delayed owner can act in the same block in which a canceller set deactivates it. Ordering decides which lands first.
- **Griefing.** A delayed owner can keep requesting activation, forcing cancellers to keep cancelling. Each request needs the owner's own signature, and cancellers with a quorum can remove the owner with an owner update.

Out of scope: rate limits or partial authority for delayed owners, delays on access-key grants, and mirroring activation state to zones.

# Invariants

- A configuration with no delayed owner has the same encoding, commitment, derived address and authorization result as under TIP-1107.
- An approval from a delayed owner contributes to a valid quorum only when its activation record has the current version and `0 < activates_at <= block.timestamp`.
- `activates_at` is written only by `requestActivation`, as `block.timestamp + delay` for the owner's delay in the current configuration, and cleared only by `cancelActivation`.
- Every owner update ends every pending and active activation of that account.
- An activation request or cancellation signature is accepted at most once, and never under another version, chain or account.
- A delayed owner can never cancel its own activation, and a canceller set always excludes the target.
- If any owner has a delay, the immediate owners alone can reach `cancel_threshold`.
- No access-key signature can request activation, cancel it or authorize an owner update.

Tests MUST cover: the v1/v2 hash split and switching forms through an owner update; requests and cancellations at the delay boundary (`activates_at == block.timestamp`); replay of a request after a cancellation and after an owner update; a canceller set including an active delayed owner and excluding the target; transaction pool eviction after a cancellation and after a reorg that removes a request; TIP-1111 grants signed with an active delayed owner; `verifyConfigurableAccount` changing from `false` to `true` across activation; and rejection of delayed-owner approvals on zones.
