# TIP-1108: Account Configuration Commitments

## Abstract

Tempo stores a configurable account's configuration hash in its account leaf. The account leaf is the record for that account in the state trie.

- Signatures and events carry the complete owner configuration.
- The chain stores its hash instead of a separate array of owners.
- This hash is also called the configuration commitment.

## Motivation

Keeping the hash with the account avoids a separate precompile-storage lookup during authorization.

It also prepares for root-key disablement. The chain can check the account's configuration while reading the account itself.

Starting with a separate precompile-storage mapping would require migrating this security-sensitive state later.

## Assumptions

[TIP-1114](./tip-1114.md) defines valid configurations. The commitment is a protocol field in the account leaf.

## Threat Model

Losing a stored commitment could restore old authority. Account deletion and state restoration must preserve the configuration rules below.

# Specification

## Commitment

```text
config_hash = keccak256(
  "tempo:multisig:config" || salt || uint64(version) ||
  uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
```

Build the hash input as follows:

- Encode the domain string as raw ASCII.
- Encode the salt as 32 bytes and each address as 20 bytes.
- Use fixed-width, big-endian integers. Their widths are shown in the formula.
- Include owners in sorted address order.
- Do not add RLP encoding, ABI padding, or a chain ID.

A stored configuration must have a version above zero. Its hash must also be nonzero.

## Account leaf

The account leaf uses one of two encodings:

```text
config_hash == 0: rlp([nonce, balance, storageRoot, codeHash])
config_hash != 0: rlp([nonce, balance, storageRoot, codeHash, config_hash])
```

- A zero hash uses the existing four-field encoding. Do not append a fifth field containing zero.
- A nonzero hash adds a fifth field containing exactly 32 bytes.
- Reject malformed encodings and any extra fields.
- Before T12, only the four-field encoding is valid.
- Existing accounts keep their encoding when T12 activates. No bulk migration is needed.

**What the hash means**

- Zero means no configuration has been stored. This can be an ordinary account or a new multisig using its initial configuration.
- A nonzero hash identifies the account's current configuration.
- Once stored, the hash must never be cleared.
- An account with a nonzero hash must not be deleted as empty, even if its other fields would allow deletion.

**Where the hash must be preserved**

The hash is part of the account's authenticated state. Every representation of that state must carry the same value:

- State roots and account proofs.
- Execution witnesses and block access lists used for execution.
- Snapshots and state synchronization.
- Historical reexecution, rollback, and reorgs.

## Access and updates

- [TIP-1109](./tip-1109.md) and [TIP-1113](./tip-1113.md) are the only ways to write the hash.
- Ordinary storage writes, contract creation, delegation, and account clearing cannot overwrite it.
- Changes must roll back if their enclosing call or transaction reverts.

**Gas**

- Reading the hash from an account that is already loaded adds no separate SLOAD charge.
- Explicit reads through the precompile use the normal warm/cold account-access charges.
- Writing a hash costs 20,000 gas if the previous value is zero.
- Replacing a nonzero hash costs 5,000 gas.
- Hashing, calldata, events, and ordinary precompile costs are charged separately.
- There is no clearing refund.

# Tooling

- Account-proof readers must understand the optional fifth field.
- The TIP-1109 getter lets callers read the hash without decoding a proof.
- Historical reads must use the encoding that was active at the requested block.

# Observability

No additional event. TIP-1109 and TIP-1113 emit the full configuration when they write the commitment.

# Invariants

- Accounts without a commitment keep byte-identical legacy encodings and state roots.
- Emptying an account never clears its commitment.
- Test commitment preservation through synchronization, historical replay, rollback, and reorgs.
