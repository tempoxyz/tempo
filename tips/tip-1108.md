# TIP-1108: Account Configuration Commitments

## Abstract

This TIP adds a 32-byte configuration commitment to the account leaf. The commitment identifies the account's current owners, weights, threshold, salt, and version. It is included in the state root and account proofs.

Unregistered accounts keep their existing four-field encoding. Registration adds a tagged fifth field. Owner updates and in-place migration write the same field, making the current configuration available whenever the account is loaded.

The commitment cannot be cleared by execution or account deletion. Initial registration survives transaction execution failure; owner updates and migration follow execution rollback. This TIP defines storage, write costs, and account RPC responses. TIP-1114 defines which configurations are valid and how their owners authorise transactions.

## Motivation

Authorisation and root disablement need the current configuration whenever an account is loaded. Keeping its hash in precompile storage would require a separate storage read.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| [TIP-1114](./tip-1114.md) validates configurations before they are committed. | The leaf could authenticate a configuration that cannot authorise transactions. |
| Clients treat the commitment as a protocol field in the account leaf. | State roots, proofs, and restored state could disagree about the account's authority. |

# Specification

## Overview

The **configuration commitment** is the hash of an account's full configuration. Zero means no configuration is registered; a nonzero value identifies the current configuration. An address that has only received funds may still have a zero commitment.

The three write operations have different rollback boundaries:

| Operation | Configuration written | Rollback behaviour |
|---|---|---|
| [Initial registration](./tip-1114.md#initial-use) | Version zero, before calls in the first included transaction the account authorises. | Persists even if execution reverts or halts. |
| [Owner update](./tip-1109.md#update-rules) | The next version of the current configuration. | Rolls back with the enclosing call or transaction execution. |
| [Migration](./tip-1113.md#installing-the-configuration) | Version one, replacing the existing account's primitive authority. | Rolls back with the enclosing call or transaction execution. |

For example, an account's first transaction registers version zero, updates to version one, then fails in a later call. Version zero remains registered; the version-one update rolls back.

This TIP covers the account field and its external representation. Signature validation, owner updates, and migration are defined by the linked component TIPs.

## Commitment

```text
config_hash = keccak256(
  "tempo:multisig:config" || salt || uint64(version) ||
  uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
```

Build the hash input as follows:

1. Encode the domain string as raw ASCII.
2. Encode the salt as 32 bytes and each address as 20 bytes.
3. Use fixed-width, big-endian integers with the widths shown in the formula.
4. Include owners in sorted address order.
5. Concatenate the fields without Recursive Length Prefix (RLP) encoding, ABI padding, or a chain ID, then hash them.

A stored configuration hash MUST be nonzero.

## Access and updates

Only initial registration, owner updates, and migration may write the hash, under the component rules linked in the [Overview](#overview).

Ordinary storage writes, contract creation, delegation, and account clearing MUST NOT overwrite or clear it. Rolling back an owner update MUST preserve any initial registration from the same transaction.

## Account state

An account with a nonzero hash MUST NOT be deleted as empty, even if its other fields would allow deletion.

It also counts as nonempty for Ethereum Virtual Machine (EVM) execution. If it has no code, `EXTCODEHASH` returns `keccak256("")` rather than zero. `CALL` and `SELFDESTRUCT` do not charge for creating a new account when such an account is the recipient.

The hash is part of the account's authenticated state. State roots, account proofs, execution witnesses, and snapshots MUST preserve it. Historical reexecution, rollback, and reorgs MUST restore the value for the selected state.

## Gas

- Reading the hash from an account that is already loaded adds no separate SLOAD charge.
- Explicit reads through the precompile use the normal warm/cold account-access charges.
- Writing a hash costs 20,000 gas if the previous value is zero.
- Replacing a nonzero hash costs 5,000 gas.
- These charges cover the account-leaf field write, with no additional storage-slot creation charge.
- Account creation is priced separately. A registration that creates an account also pays TIP-1000's new-account cost, as specified in TIP-1114.
- Configuration-hash writes neither consume nor mint storage credits.
- Hashing, calldata, events, and ordinary precompile costs are charged separately.
- There is no clearing refund.

## Changes to other components

### JSON-RPC

Request parameters and existing response fields are unchanged. All values below refer to the state selected by the request, including historical reads.

#### Account responses

`eth_getAccount` and `eth_getAccountInfo` expose the configuration commitment through an optional `extension` field in their account response object:

- For a nonzero `config_hash`, `extension` is the fifth field, `0x00 || config_hash`, encoded as `0x` followed by exactly 66 hexadecimal digits (33 bytes of JSON-RPC `DATA`).
- For a zero `config_hash`, omit `extension`.

Missing-account behavior is unchanged. An account with a nonzero commitment is not missing, even if its balance, nonce, and code are otherwise empty.

Where `debug_accountAt` and `debug_accountInfoAt` are exposed, their account objects follow the same extension rules at the requested transaction boundary.

#### Account proofs

`eth_getProof` and, where exposed, `eth_getMultiProof` encode account leaves with their extensions in the proof nodes. Proof summary fields remain unchanged and do not include a separate `extension` field.

## Interfaces

### Account leaf

The account leaf uses one of two encodings:

```text
config_hash == 0: rlp([nonce, balance, storageRoot, codeHash])
config_hash != 0: rlp([nonce, balance, storageRoot, codeHash, 0x00 || config_hash])
```

- A zero hash uses the existing four-field encoding. Do not append a fifth field containing zero.
- A nonzero hash adds a fifth field containing exactly 33 bytes: the format tag `0x00` followed by the hash.
- The tag identifies the field's layout. It is not the configuration version. Reject any other tag.
- Reject malformed encodings and any extra fields.
- Before activation, only the four-field encoding is valid.
- Existing accounts keep their encoding when this TIP activates. No bulk migration is needed.

# Tooling

- Callers of `eth_getProof` and `eth_getMultiProof` RPC methods must understand the optional fifth field.
- The TIP-1109 getter lets callers read the hash without decoding a proof.
- A nonzero hash identifies a registered configurable account for contracts and analytics.
- Historical reads must use the encoding that was active at the requested block.

# Observability

Initial registration is recorded by the included transaction and its configuration witness, regardless of execution success.

# Threat Model

The commitment protects the account's current authority through execution and state restoration.

| Actor | Trust |
| --- | --- |
| Owners / transaction callers | Can write the commitment only through authorised registration, owner updates, or migration. Ordinary calls cannot clear it to restore old authority. |
| Execution clients | Trusted to preserve the commitment in account encoding, deletion checks, snapshots, replay, and reorgs. Losing it could restore old authority or produce an incorrect state root. |
| RPC / proof providers | Can withhold data or return stale state. Account proofs authenticate the commitment only against the state root the reader checks; they do not establish that the state is current. |

The hash commits to a configuration but does not recover it. Losing the full configuration can prevent owner authorisation until it is recovered from transaction witnesses or update events.

# Invariants

- Accounts without a commitment keep byte-identical legacy encodings and state roots.
- After an included configurable-account transaction, the hash is nonzero, including at version zero and after execution failure.
- Emptying an account never clears its commitment.
- Snapshots, historical replay, rollback, and reorgs preserve the commitment for the selected state.
