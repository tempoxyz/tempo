# TIP-1108: Account Configuration Commitments

## Abstract

This TIP stores a 32-byte configuration commitment in the account leaf, authenticated by state roots and account proofs.

Unregistered accounts keep four-field encoding; registration, rotation and migration write a tagged fifth field.

Execution and account deletion cannot clear it. Initial registration survives execution failure; updates and migration follow execution rollback. This TIP defines storage, gas and RPC representation; TIP-1114 defines valid configurations and owner authorisation.

## Motivation

Owner authorization needs the current configuration. The account leaf supplies its commitment without a separate precompile-storage read. AccountKeychain retains access-key grants, permissions and spending state.

## Assumptions

[TIP-1114](./tip-1114.md) validates configurations before they are committed; otherwise, the leaf could authenticate a configuration that cannot authorise transactions.

# Specification

## Overview

The **configuration commitment** is the full configuration's hash. Zero means unregistered; nonzero identifies the current configuration. Funding alone does not register an account.

The three write operations have different rollback boundaries:

| Operation | Configuration written | Rollback behaviour |
|---|---|---|
| [Initial registration](./tip-1114.md#onboarding) | Version zero, before calls in its first included authorised transaction. | Persists if execution reverts or halts. |
| [Owner update](./tip-1109.md#update-rules) | Next configuration version. | Rolls back with the enclosing call or transaction execution. |
| [Migration](./tip-1113.md#installing-the-configuration) | Version one, replacing primitive authority. | Rolls back with the enclosing call or transaction execution. |

See [TIP-1109](./tip-1109.md#overview) for a failed-batch example.

## Commitment

```text
config_hash = keccak256(
  "tempo:configurable-account:config" || salt || uint64(version) ||
  uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
```

Build the hash input as follows:

1. Encode the domain string as raw ASCII.
2. Encode the salt as 32 bytes and each address as 20 bytes.
3. Use the formula's fixed-width, big-endian integers.
4. Include owners in sorted address order.
5. Concatenate the fields without Recursive Length Prefix (RLP) encoding, ABI padding, or a chain ID, then hash them.

A stored configuration hash MUST be nonzero.

## Access and updates

Only the [Overview](#overview) operations may write the hash, under their linked component rules.

Ordinary storage writes, contract creation, delegation, and account clearing MUST NOT overwrite or clear it. Rolling back an owner update MUST preserve any initial registration from the same transaction.

## Account state

An account with a nonzero hash MUST NOT be deleted as empty, even if its other fields would allow deletion.

For Ethereum Virtual Machine (EVM) execution it also counts as nonempty: `CALL` and `SELFDESTRUCT` charge no new-account cost when it is the recipient. Registration and migration also install TIP-1114's [account code marker](./tip-1114.md#account-code), so its `codeHash` is `keccak256(0xef)`.

State roots, account proofs, execution witnesses, journals and snapshots MUST preserve the hash. Historical reexecution, rollback and reorgs MUST restore its value for the selected state.

## Gas

- Reading an already-loaded account's hash adds no SLOAD charge; explicit precompile reads pay normal warm/cold account-access charges.
- Writing from zero costs 250,000 gas, the same as creating an account (TIP-1000), because the hash is permanent account state. Writing from nonzero costs 5,000 execution gas and no state gas. There is no additional storage-slot creation charge.
- Registration that creates an account also pays TIP-1000's new-account cost under TIP-1114.
- Configuration-hash writes neither consume nor mint storage credits.
- Hashing, calldata, events, and ordinary precompile costs are charged separately.
- There is no clearing refund.

## Changes to other components

### JSON-RPC

Request parameters and existing response fields are unchanged. Values use the request's selected state, including historical reads.

#### Account responses

`eth_getAccount` and `eth_getAccountInfo` add an optional account-response field, `extension`:

- For nonzero `config_hash`, return `0x00 || config_hash` as `0x` followed by exactly 66 hexadecimal digits (33 bytes of JSON-RPC `DATA`).
- For zero, omit `extension`.

Missing-account behavior is unchanged. A nonzero commitment makes the account present even with empty balance, nonce and code.

Where exposed, `debug_accountAt` and `debug_accountInfoAt` use these rules at the requested transaction boundary.

#### Account proofs

`eth_getProof` and, where exposed, `eth_getMultiProof` include extensions in their account-leaf proof nodes. Summary fields remain unchanged, without a separate `extension`.

## Interfaces

### Account leaf

The account leaf uses one of two encodings:

```text
config_hash == 0: rlp([nonce, balance, storageRoot, codeHash])
config_hash != 0: rlp([nonce, balance, storageRoot, codeHash, 0x00 || config_hash])
```

- Zero uses the existing four fields; never append a zero fifth field.
- Nonzero adds a 33-byte fifth field: tag `0x00` followed by the hash.
- The tag identifies layout, not configuration version. Reject any other tag.
- Reject malformed encodings and extra fields.
- Before activation, only the four-field encoding is valid.
- Activation leaves existing encodings unchanged, without bulk migration.

# Compatibility

- Proof consumers must decode the optional fifth field; the TIP-1109 getter exposes the hash without proof decoding.
- A nonzero hash identifies a registered configurable account for contracts and analytics.
- Historical reads must use the encoding that was active at the requested block.

# Observability

| Operation | Evidence |
|---|---|
| Initial registration | Version-zero `ConfigurableAccountConfigUpdated` carries the full configuration, as does the included transaction's witness; write and event survive execution failure. |
| Owner update | `ConfigurableAccountConfigUpdated` carries the full configuration; update and event roll back together on failure. |
| Migration | `AccountUpgraded` carries the configuration and commitment; write and event roll back together on failure. |

Match witness or event configurations to the selected state's commitment from the [getter](./tip-1109.md#interfaces), RPC or proof. Earlier events do not establish current authority.

# Threat Model

Deleting the commitment makes later reads return zero. A migrated account could then accept its original key without the current quorum's approval.

| Actor | Trust boundary |
|---|---|
| Owners / transaction callers | Only authorised [write operations](#access-and-updates) may change the commitment. Ordinary calls, storage writes and clearing cannot overwrite/delete it to bypass ownership checks. |
| RPC / proof provider | Can withhold or return stale data. Readers must verify proofs against their selected canonical root; an old proof does not establish current authority. |

# Invariants

- Unchanged accounts without a commitment keep byte-identical legacy account leaves.
- After an included configurable-account transaction, the hash is nonzero, including at version zero and after execution failure.
- Emptying an account never clears its commitment.
- Snapshots, historical replay, rollback, and reorgs preserve the commitment for the selected state.
