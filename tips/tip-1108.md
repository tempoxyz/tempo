# TIP-1108: Account Configuration Commitments

## Abstract

This TIP adds a 32-byte configuration hash to the account leaf for configurable accounts. The hash commits to the account's owners, weights, approval threshold, salt, and version. Accounts without a registered configuration retain their existing encoding.

## Motivation

Owner rotation changes an account's authority without changing its address. Validation therefore needs a stored commitment to the current owners and approval threshold.

Keeping the hash in the account leaf, the account's record in the state trie, makes it available when the node loads the account. This avoids a separate precompile-storage lookup during authorisation and supports future root-key disablement without migrating authorisation state.

## Assumptions

[TIP-1114](./tip-1114.md) defines valid configurations and initial registration. Initial registration must complete before transaction calls execute, so those calls see the registered hash.

# Specification

## Configuration commitment

The configuration hash, or configuration commitment, is computed as follows:

```text
config_hash = keccak256(
  "tempo:multisig:config" || salt || uint64(version) ||
  uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
```

Build the hash input as follows:

- Encode the domain string as raw ASCII.
- Encode the salt as 32 bytes and each address as 20 bytes.
- Use fixed-width, big-endian integers. Their widths are shown in the formula.
- Include owners in sorted address order.
- Do not add RLP encoding, ABI padding, or a chain ID.

A stored configuration hash must be nonzero. The full configuration is carried in authorisation witnesses and configuration-change events; the account leaf stores only its hash.

## Account leaf encoding

The account leaf uses one of two encodings:

```text
config_hash == 0: rlp([nonce, balance, storageRoot, codeHash])
config_hash != 0: rlp([nonce, balance, storageRoot, codeHash, config_hash])
```

- A zero hash uses the existing four-field encoding. Do not append a fifth field containing zero.
- A nonzero hash adds a fifth field containing exactly 32 bytes.
- Reject malformed encodings and any extra fields.
- Before T12, only the four-field encoding is valid.
- Existing accounts keep their encoding when T12 activates. No bulk migration is needed.

## Registration and updates

Before registration, an account has a zero configuration hash. Registration stores a nonzero hash identifying the account's current configuration.

Only the following operations may write the hash:

| Operation | Configuration written | Rollback behaviour |
|---|---|---|
| [Initial registration](./tip-1114.md#initial-use) | Version zero, when the account first authorises an included transaction. No owner update is required. | Persists even if execution reverts or halts. |
| [Owner update](./tip-1109.md#update-rules) | A positive version replacing the current configuration. | Rolls back if the enclosing call or transaction execution reverts. |
| [Migration](./tip-1113.md) | A positive version registering an existing account's configuration. | Rolls back if the enclosing call or transaction execution reverts. |

Initial registration under TIP-1114 requires a valid, included transaction. Reverting subsequent owner updates preserves that version-zero registration.

## Account existence and state preservation

An account with a nonzero hash must not be deleted as empty, even if its other fields would allow deletion. It also counts as nonempty for EVM execution. If it has no code, `EXTCODEHASH` returns `keccak256("")` rather than zero. `CALL` and `SELFDESTRUCT` do not charge for creating a new account when such an account is the recipient.

The hash is part of the account's authenticated state. Every representation of that state must carry the same value:

- State roots and account proofs.
- Execution witnesses.
- Snapshots.
- Historical reexecution, rollback, and reorgs.

## Gas accounting

| Operation | Charge |
|---|---|
| Read from an already loaded account | No separate `SLOAD` charge. |
| Explicit read through the precompile | Normal warm/cold account-access charges. |
| Write a hash when the previous value is zero | 20,000 gas. |
| Replace a nonzero hash | 5,000 gas. |

The write charges cover the account-leaf field, with no additional storage-slot creation charge. Configuration-hash writes neither consume nor mint storage credits, and there is no clearing refund. Hashing, calldata, events, and ordinary precompile costs are charged separately.

## JSON-RPC

Request parameters and existing response fields are unchanged. All values below refer to the state selected by the request, including historical reads.

### Account responses

`eth_getAccount` and `eth_getAccountInfo` expose the configuration hash through an optional `extension` field in their account response object:

- For a nonzero `config_hash`, `extension` is the hash itself, encoded as `0x` followed by exactly 64 hexadecimal digits (32 bytes of JSON-RPC `DATA`).
- For a zero `config_hash`, omit `extension`.

Missing-account behaviour is unchanged. An account with a nonzero hash is not missing, even if its balance, nonce, and code are otherwise empty.

Where `debug_accountAt` and `debug_accountInfoAt` are exposed, their account objects follow the same extension rules at the requested transaction boundary.

### Account proofs

`eth_getProof` and, where exposed, `eth_getMultiProof` encode account leaves with their extensions in the proof nodes. Proof summary fields remain unchanged and do not include a separate `extension` field.

# Tooling

- Libraries and applications that decode account leaves from `eth_getProof` or `eth_getMultiProof` must support the optional fifth field.
- Client snapshot and execution-witness tooling must also preserve it.
- Historical reads must use the encoding active at the requested block.
- Contracts can read the hash through [`getConfigCommitment(address)`](./tip-1109.md#interface) without decoding a proof.
- Contracts and analytics can use a nonzero hash to identify a registered configurable account.

# Observability

- This TIP introduces no new events.
- Initial registration is recorded by the included transaction and its configuration witness, regardless of execution success.
- Owner updates and migration emit events recording the new configuration.
- The stored hash identifies the current configuration but does not reveal its owners or threshold without the matching configuration.

# Threat Model

Clearing a rotated account's hash by accident could make validation accept its initial configuration again. Initial owners meeting that configuration's approval threshold could regain control, including removed owners.

Deletion, rollback, and restoration must preserve the hash for the selected state. A reorg may restore an earlier configuration, or zero if it removes the registration from canonical history.

# Invariants

- Accounts with a zero configuration hash keep the legacy four-field encoding byte for byte.
- Adding support for the configuration hash alone leaves the state root unchanged.
- Every configurable account that authorised an included transaction retains a nonzero hash, including at version zero.
- Version-zero initial registration survives execution reverts and halts.
- Execution and account clearing preserve a nonzero hash after initial registration or successful migration.
- Reverting an owner update preserves any initial registration from the same transaction.
- All representations of an account at the same block or execution boundary carry the same configuration hash.
