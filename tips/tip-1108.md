# TIP-1108: Account Configuration Commitments

## Abstract

Tempo stores a configurable account's configuration hash in its account leaf. The account leaf is the record for that account in the state trie.

- Signatures and events carry the complete owner configuration.
- The chain stores its hash instead of a separate array of owners.
- This hash is also called the configuration commitment.

## Motivation

Keeping the hash with the account avoids a separate precompile-storage lookup during authorization.

It also prepares for root-key disablement. The chain can check the account's configuration while reading the account itself.

Starting with a separate precompile-storage mapping would require migrating this security-sensitive state later.

## Assumptions

[TIP-1114](./tip-1114.md) defines valid configurations. The commitment is a protocol field in the account leaf.

## Threat Model

Losing a stored commitment could restore old authority. Account deletion and state restoration must preserve the configuration rules below.

# Specification

## Commitment

```text
config_hash = keccak256(
  "tempo:multisig:config" || salt || uint64(version) ||
  uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
```

Build the hash input as follows:

- Encode the domain string as raw ASCII.
- Encode the salt as 32 bytes and each address as 20 bytes.
- Use fixed-width, big-endian integers. Their widths are shown in the formula.
- Include owners in sorted address order.
- Do not add RLP encoding, ABI padding, or a chain ID.

A stored configuration hash must be nonzero. Version zero is stored on first use. Owner updates and migration store positive versions.

## Account leaf

The account leaf uses one of two encodings:

```text
config_hash == 0: rlp([nonce, balance, storageRoot, codeHash])
config_hash != 0: rlp([nonce, balance, storageRoot, codeHash, config_hash])
```

- A zero hash uses the existing four-field encoding. Do not append a fifth field containing zero.
- A nonzero hash adds a fifth field containing exactly 32 bytes.
- Reject malformed encodings and any extra fields.
- Before T12, only the four-field encoding is valid.
- Existing accounts keep their encoding when T12 activates. No bulk migration is needed.

**What the hash means**

- Zero means no configuration has been registered. An address that has only received funds may still have a zero hash.
- The first successful transaction authorized by a configurable account leaves a nonzero hash, even without an owner update.
- A nonzero hash identifies the account's current configuration.
- Once stored, the hash must never be cleared.
- An account with a nonzero hash must not be deleted as empty, even if its other fields would allow deletion.

**Where the hash must be preserved**

The hash is part of the account's authenticated state. Every representation of that state must carry the same value:

- State roots and account proofs.
- Execution witnesses and block access lists used for execution.
- Snapshots and state synchronization.
- Historical reexecution, rollback, and reorgs.

## Access and updates

- [TIP-1114](./tip-1114.md) writes the initial hash when an account first authorizes a transaction.
- [TIP-1109](./tip-1109.md) replaces it on owner updates. [TIP-1113](./tip-1113.md) writes it on migration.
- These are the only ways to write the hash.
- Ordinary storage writes, contract creation, delegation, and account clearing cannot overwrite it.
- Changes must roll back if their enclosing call or transaction reverts.

**Gas**

- Reading the hash from an account that is already loaded adds no separate SLOAD charge.
- Explicit reads through the precompile use the normal warm/cold account-access charges.
- Writing a hash costs 20,000 gas if the previous value is zero.
- Replacing a nonzero hash costs 5,000 gas.
- These charges cover the account-leaf field write, with no additional storage-slot creation charge.
- Configuration-hash writes neither consume nor mint storage credits.
- Hashing, calldata, events, and ordinary precompile costs are charged separately.
- There is no clearing refund.

## JSON-RPC

Request parameters and existing response fields are unchanged. All values below refer to the state selected by the request, including historical reads.

### Account responses

`eth_getAccount` and `eth_getAccountInfo` expose the configuration commitment through an optional `extension` field in their account response object:

- For a nonzero `config_hash`, `extension` is the hash itself, encoded as `0x` followed by exactly 64 hexadecimal digits (32 bytes of JSON-RPC `DATA`).
- For a zero `config_hash`, omit `extension`.

Missing-account behavior is unchanged. An account with a nonzero commitment is not missing, even if its balance, nonce, and code are otherwise empty.

Where `debug_accountAt` and `debug_accountInfoAt` are exposed, their account objects follow the same extension rules at the requested transaction boundary.

### Account proofs

`eth_getProof` and, where exposed, `eth_getMultiProof` support accounts with configuration commitments. They must return proofs for extended accounts, without rejecting them or stripping the commitment. Both methods retain their existing response schemas: the extension is carried in the authenticated account leaf rather than a separate JSON `extension` field.

Each `accountProof` contains the trie nodes authenticating the complete account leaf, including the fifth field when present. `eth_getMultiProof` applies the same rules to every returned account proof, including requests mixing accounts with and without commitments and missing accounts. Storage proofs and the existing balance, nonce, code-hash, and storage-root summary fields are unchanged.

Proof verifiers must authenticate the full leaf against the selected block's state root and decode it using the account-leaf rules above. Reconstructing a four-field leaf from the response summary fields is insufficient for an account with a commitment. An absence proof has no account commitment; a proof of an account with only a nonzero commitment is an inclusion proof, not an absence proof.

Tools reconstructing account state from either proof method must recover the commitment from the authenticated leaf and preserve it alongside the ordinary account fields. They must verify inclusion for the requested address before treating a leaf's fifth field as that account's commitment; an absence proof can contain a leaf belonging to another account.

### Compatibility

Clients that ignore unknown account-response fields can continue using the existing fields. Proof verifiers that assume every account leaf has four fields must be updated before verifying extended accounts. RPC-backed execution and state-reconstruction tools must use an extension-aware endpoint; a legacy endpoint can omit a stored commitment, so an absent JSON field alone is not evidence of endpoint support.

# Tooling

- Account-proof readers must understand the optional fifth field.
- The TIP-1109 getter lets callers read the hash without decoding a proof.
- A nonzero hash identifies a registered configurable account for contracts and analytics.
- Historical reads must use the encoding that was active at the requested block.

# Observability

Initial registration is recorded by the successful transaction and its configuration witness. TIP-1109 and TIP-1113 emit events for updates and migration.

# Invariants

- Accounts without a commitment keep byte-identical legacy encodings and state roots.
- After a successful configurable-account transaction, the hash is nonzero, including at version zero.
- Emptying an account never clears its commitment.
- Test commitment preservation through synchronization, historical replay, rollback, and reorgs.
