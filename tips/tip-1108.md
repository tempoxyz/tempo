# TIP-1108: Account Configuration Commitments

## Abstract

Tempo stores a configurable account's current configuration hash in its account leaf. Signatures and events carry the complete configuration; the chain does not store owner arrays.

## Motivation

Keeping the commitment with the account avoids a separate precompile-storage lookup during authorization and prepares for root-key disablement. Putting it in a separate mapping now would require a sensitive migration later.

## Assumptions

[TIP-1114](./tip-1114.md) defines valid configurations. The commitment is a consensus field, not ordinary EVM storage. Account proofs and execution must agree on its value.

## Threat Model

Transaction data, storage writes, nonce choices, and delegation cannot set or hide this field. Only authorized configuration transitions can change it. Losing it during state clearing, synchronization, or a reorg would restore stale authority.

# Specification

## Commitment

```text
config_hash = keccak256(
  "tempo:multisig:config" || salt || uint64(version) ||
  uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
```

Use raw ASCII, 32-byte salt, 20-byte addresses, fixed-width big-endian integers, and the sorted owner order. There is no RLP, ABI padding, or chain ID in this preimage. A persisted commitment must have a positive version and a nonzero hash.

## Account leaf

```text
config_hash == 0: rlp([nonce, balance, storageRoot, codeHash])
config_hash != 0: rlp([nonce, balance, storageRoot, codeHash, config_hash])
```

The fifth field is exactly 32 bytes. An explicit zero fifth field, extra fields, or malformed encodings are invalid. Before T12, only the legacy four-field encoding is valid. At T12, existing accounts are unchanged; no bulk migration is required.

Zero means no persisted configuration. It does not distinguish an ordinary account from an uninitialized counterfactual multisig. A nonzero value binds the current configuration and must never be cleared. An account with a nonzero commitment is not empty even if its balance, nonce, storage, and code would otherwise permit deletion.

The field participates in state roots, proofs, execution witnesses, snapshots, synchronization, reexecution, rollback, and any block access-list representation used for execution. Those paths must preserve and authenticate exactly the same value. Future leaf extensions require their own specification.

## Access and updates

[TIP-1109](./tip-1109.md) and [TIP-1113](./tip-1113.md) are the only writers. Ordinary storage operations, contract creation, delegation, and account clearing cannot overwrite the field. Writes are journaled and reverted with their enclosing call or transaction.

Reading the commitment as part of an already-loaded account adds no separate SLOAD charge. Explicit precompile reads use the ordinary warm/cold account-access schedule. A write costs 20,000 gas when replacing zero and 5,000 otherwise, in addition to hashing, calldata, events, and ordinary precompile costs; it grants no clearing refund. This is a protocol field write, not an SSTORE to a hidden mapping.

# Tooling

Account-proof consumers must accept the optional fifth field. The TIP-1109 getter exposes the commitment without requiring callers to decode a proof. Historical reads use the encoding active at that block.

# Observability

No storage-specific event. The authorized writer emits a configuration or migration event containing enough data to reconstruct the commitment.

# Invariants

Test byte-identical legacy accounts and roots, nonzero commitment proofs, malformed leaf rejection, rollback/reorgs, state synchronization, historical replay, and preservation through account-emptying paths. Ordinary EVM storage cannot alter account authority.
