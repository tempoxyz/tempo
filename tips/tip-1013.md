# TIP-1013: Chunked Contract Bytecode

## Abstract

Divide deployed contract bytecode into independently executable 12 KiB chunks. Each account commits to the complete code size and an ordered hash for every chunk. Execution loads the initial chunk without loading complete bytecode, loads another chunk when a taken jump crosses a boundary, and journals transaction-local chunk warmth. A cold chunk costs 2,868 gas in this draft; a warm chunk has no additional charge.

Deployment validation prohibits instructions and sequential execution from crossing a chunk boundary. Every executable chunk has a synthetic trailing STOP, so the existing interpreter dispatch loop can execute one chunk at a time without a fallthrough hook.

## Motivation

Loading and analyzing a complete contract makes execution I/O depend on code a transaction never executes. Chunking bounds each database read, permits sparse code access, and retains the existing global code hash and externally visible bytes.

[EIP-6800](https://eips.ethereum.org/EIPS/eip-6800) and [EIP-7864](https://eips.ethereum.org/EIPS/eip-7864) commit code in smaller units for authenticated state. [EIP-7907](https://eips.ethereum.org/EIPS/eip-7907) prices code loading and journals code warmth. This TIP uses a Tempo-specific 12 KiB unit and stores an ordered chunk-hash vector in the account leaf.

## Specification

### Constants

```text
CODE_CHUNK_SIZE       = 12 * 1024 = 12288
COLD_CHUNK_BASE_GAS   = 2100
GAS_PER_CODE_WORD     = 2
COLD_CODE_CHUNK_GAS   = 2100 + 2 * (12288 / 32) = 2868
WARM_CODE_CHUNK_GAS   = 0
ACCOUNT_FORMAT_VERSION = 1
```

All arithmetic that determines indices, byte ranges, or gas MUST be checked.

### Deployment validation and chunk construction

Let `code` be the original deployed bytes and `L = code.len()`. Empty code has no chunks. Nonempty code has `N = ceil(L / CODE_CHUNK_SIZE)` chunks. Original payload `i` is:

```text
code[i * CODE_CHUNK_SIZE .. min((i + 1) * CODE_CHUNK_SIZE, L)]
```

Creation MUST reject deployed code when either condition holds:

1. A PUSH1 through PUSH32 immediate crosses a chunk boundary or extends beyond `L`.
2. A non-final chunk's last original byte is not STOP.

These rules guarantee that every chunk starts at an opcode boundary and that execution cannot fall through into the next chunk. They intentionally constrain newly deployed code. An activation migration MUST validate existing code and cannot activate while incompatible code exists unless a separate transition rule is specified.

For execution, append one synthetic STOP byte to every payload and analyze that byte sequence as independent legacy bytecode. The synthetic byte is not part of `L`, `code_hash`, a chunk payload, RPC output, or deployment gas. Appending it even when the payload already ends in STOP keeps construction uniform and provides normal final-code padding.

Define:

```text
code_hash       = keccak256(code)
chunk_hash[i]   = keccak256(original_payload[i])
```

Concatenating all original payloads MUST reproduce exactly `L` bytes whose Keccak hash is `code_hash`.

### Account commitment and Reth representation

A nonempty-code account commits to `code_hash`, `code_size`, and the ordered `chunk_hashes` vector. The chunk count is derived from `code_size`; it is not stored separately.

Tempo stores the new fields in Reth's chain-specific account extension. A nonempty extension is the fifth RLP string in the trie account. Its payload is:

```text
format_version: u8 = 1
code_size:      u32 big-endian
chunk_hashes:   N consecutive B256 values
```

The payload length MUST equal `5 + 32 * ceil(code_size / 12288)`. A zero `code_size` uses the empty account extension and no chunk hashes, preserving the canonical four-field empty-code leaf. Unknown versions, zero-size nonempty extensions, mismatched lengths, and mismatched hash counts are invalid.

Reth Compact account encoding carries the same opaque extension after the legacy account fields. Conversion among Reth `Account`, trie `TrieAccount`, and EVM account information MUST preserve the extension. Creating, replacing, clearing, reverting, snapshotting, or migrating code MUST update the complete tuple atomically:

```text
(code_hash, code_size, chunk_hashes)
```

`EXTCODESIZE` reads `code_size` without loading bytecode. `EXTCODEHASH` retains its existing result. The global `PC` and jump offsets remain offsets into complete original code.

### Database interface

The required database operation is:

```rust
fn get_code_chunk_by_hash(
    &mut self,
    code_hash: &B256,
    index: u32,
) -> Result<Option<CodeChunk>, Self::Error>;
```

Typed, erased, cached, counted, and asynchronous adapters MUST preserve this contract. No default implementation may fetch complete code.

The caller first checks `index < ceil(code_size / CODE_CHUNK_SIZE)`. An out-of-range request returns `None` without chunk I/O or warmth changes. An in-range request MUST return a payload of the exact derived length, and its hash MUST equal `chunk_hashes[index]`. A missing or mismatched in-range chunk is a database or state-validation error, never empty code, STOP, or an EVM halt.

Full-code access remains available for RPC, synchronization, migration, and index verification. Consensus execution after activation MUST not fall back to it.

### Journaled account and caches

The EVM journaled account contains:

```text
code_size: u32
code_chunks: HashMap<u32, { bytecode: Bytecode, is_warm: bool }>
```

`code_chunks` stores only the independently executable chunks that execution has requested, including their synthetic STOP. Loading account metadata does not load chunk zero or complete bytecode. The bytecode type MUST NOT hold a lazily initialized vector of all chunks: an absent map entry is the source of truth that the chunk has not been loaded for this journaled account. A newly created account retains validated creation output but constructs and inserts only the requested chunk on first access.

Each loaded map entry carries its transaction-local `is_warm` flag. Maintain one additional immutable structure:

- An immutable byte cache keyed by `(code_hash, chunk_index)`, shared across addresses and retained across reverts and transaction resets.

After a successful cold read, insert the account entry with `is_warm = true`, or set an existing cold entry to warm, and append `CodeChunkWarmed` to the revert journal. Revert resets the entry's flag and retains its bytes. Transaction reset discards the journaled account and therefore all warmth. Failed reads, skipped reads, and out-of-range requests do not insert or warm a chunk. A hit in the immutable byte cache still counts as a cold account-chunk access when the account entry is absent or cold, so physical cache residency never changes gas.

### Interpreter behavior

Call and transaction entry resolve the code owner, read account metadata, and load chunk zero when code is nonempty. Initcode remains resident input and is not chunked.

For a taken JUMP or JUMPI with global target `t`:

1. Reject `t >= code_size` as an invalid jump without chunk I/O.
2. Compute `index = t / CODE_CHUNK_SIZE` and `local = t % CODE_CHUNK_SIZE`.
3. If `index` differs from the active chunk, reserve cold gas when necessary, fetch the chunk, verify its account-committed hash, and update warmth.
4. Validate `local` against that chunk's jump table.
5. Replace the interpreter's owned bytecode and bytecode view, then set its local program counter to `local`.

An invalid in-range destination still pays for a cold destination chunk because validation requires reading it. An untaken JUMPI does not read its target. Same-chunk jumps use the active analysis. Since a valid non-final payload ends in STOP, sequential execution cannot enter another chunk and the interpreter dispatch loop requires no boundary branch.

`PC` returns `active_chunk_index * CODE_CHUNK_SIZE + local_pc`. `CODESIZE` returns account `code_size`, excluding synthetic STOP. CODECOPY and EXTCODECOPY require every original payload intersecting their clipped source range and charge each newly cold chunk before fetching any of them. Bytes beyond `code_size` remain zero and do not require a chunk.

### Gas accounting

The incremental charge is:

```text
chunk_gas(required, warm) = 2868 * |unique(required) \\ warm|
```

Every cold chunk costs 2,868 gas, including a short final chunk. A warm chunk adds zero. Existing opcode, account-access, memory, copy, call, and deployment charges remain.

The complete incremental cost for one operation MUST be checked and reserved before its first cold chunk I/O. If it is unaffordable, execution halts before fetching or warming any chunk. Database failure is a node execution error. REVERT does not refund spent gas but does revert chunk warmth through the normal checkpoint journal.

The proposed 2,868 consists of the existing 2,100 cold-read reference plus 384 32-byte words at 2 gas each. It prices a fixed 12 KiB payload read. It does not price the enlarged account proof containing `32 * N` hash bytes. That metadata is authenticated when the account is loaded and should be covered by account/state-access pricing rather than charged again per chunk. Activation therefore depends on measuring both costs and either confirming the existing account charge covers the larger leaf or adding a separate size-dependent account-metadata tariff.

The charge occurs before a CALL's 63/64 child-gas calculation when chunk zero is needed to resolve code. Cross-chunk jumps spend gas in the executing child frame. Gas ordering MUST be identical in the interpreter and compiled engines.

## Compatibility and activation

The full code hash, contract addresses, RPC bytecode, storage, and opcode offsets remain unchanged. Account RLP and state roots change. New validation rules can reject runtime bytecode that was formerly valid, and added gas can change transaction success, `GAS`, estimates, and call forwarding. The TIP therefore requires a coordinated hardfork and deterministic state migration.

Before activation, clients MUST:

1. Scan all existing code, validate the boundary rules, and build payloads and hashes.
2. Write the versioned account extensions and recompute the state commitment.
3. Differentially replay interpreter and compiled execution, including failed calls and reverts.
4. Measure cold database latency, account-proof growth, cache memory, and Tempo transaction gas deltas.
5. Activate account encoding, database reads, interpreter behavior, and gas rules together.

Historical pre-activation execution retains the old account format and full-code behavior.

## Reference implementation and measurements

The draft EVM2 implementation on `rakita/bytecode-chunking` includes:

- validated 12 KiB chunks with synthetic STOP;
- `code_size` and a per-account map of loaded bytecode chunks with individual warm flags;
- typed, erased, cached, counted, and async chunk database reads;
- rollback-aware chunk warmth and persistent byte caching;
- lazy chunk-zero loading for calls and transaction entry;
- cross-chunk JUMP/JUMPI loading with global PC and code size;
- creation-time PUSH and STOP-boundary validation; and
- a checked 2,868-gas cold tariff.

The Tempo draft uses Reth's account extension to encode `code_size` and all ordered chunk hashes. Tests cover extension validation, Compact persistence, trie commitment changes, chunk construction, cross-chunk jumps, cold/warm gas, skipped reads, cache retention, and rollback.

The coverage experiment replayed Ethereum blocks 25,347,446–25,347,455 (2,279 transactions). At 12 KiB, block-local full code totaled 29,955,810 bytes and touched original payload totaled 29,493,944 bytes, a 1.54% reduction. Execution touched 3,963 of 4,053 chunks. Transaction-local full code totaled 66,668,187 bytes versus 65,950,134 payload bytes, a 1.08% reduction. Those figures are coverage observations, not lazy database I/O or Tempo gas results, and do not justify activation pricing.

The current draft still requires chunk-backed CODECOPY/EXTCODECOPY, EIP-7702 conformance coverage, JIT/AOT parity, persistent provider integration, migration tooling, and Tempo replay measurement before it is activation-ready.

## Invariants

1. The account hash vector length equals `ceil(code_size / 12288)`.
2. Each payload has the derived length and matches its account-committed hash.
3. Concatenated payloads have `code_size` bytes and hash to `code_hash`.
4. No PUSH immediate crosses a boundary or deployed-code end.
5. Every non-final original payload ends in STOP; every executable chunk has a synthetic final STOP.
6. Cold gas depends on logical warmth, never physical cache residency.
7. Insufficient gas causes no chunk fetch or warmth mutation.
8. Revert restores warmth and account metadata while retaining immutable cached bytes.
9. Missing or corrupt in-range data is a node error, never an EVM result.
10. Interpreter, JIT, AOT, async execution, RPC, and proof tooling agree on original bytes and global offsets.

## Security considerations

Contract authors can target boundaries, invalid destinations, many code owners, and repeated reverts to maximize I/O. Implementations MUST charge before I/O, use checked arithmetic, validate every fetched payload against the account hash vector, and keep transaction warmth separate from shared caches. Peers and witnesses are untrusted; the account-committed per-chunk hash authenticates a partial payload, while the complete-code hash remains the invariant for migration and full-code verification.
