# TIP-1013: Chunked Contract Bytecode

## Abstract

Divide deployed contract bytecode into 12 KiB chunks and charge for the chunks an execution actually reads. Add the code hash and byte length to each account's consensus metadata, derive the chunk count from that length, extend the database interface to fetch individual chunks, and journal transaction-local chunk warmth while retaining fetched bytes across reverted calls. This draft proposes an incremental charge of 2,868 gas per cold chunk; activation and pricing calibration are pending.

## Motivation

Fetching and analyzing complete contracts makes execution cost depend on code that a transaction never reads. Chunking bounds each read and lets clients fetch, cache, and analyze only the necessary regions. A 12 KiB payload keeps the number of database lookups and bookkeeping entries small, at the cost of fetching more unused bytes than finer chunking.

[EIP-6800](https://eips.ethereum.org/EIPS/eip-6800) and [EIP-7864](https://eips.ethereum.org/EIPS/eip-7864) describe fine-grained code chunking for authenticated state trees. This proposal uses their idea of recording leading PUSH data, but does not adopt their tree layouts or chunk size. [EIP-7907](https://eips.ethereum.org/EIPS/eip-7907) prices code loading and journals code warmth; this draft instead meters individual 12 KiB reads. Its 2 gas per 32-byte word informs the proposed byte component, while the fixed read component requires independent calibration.

Alternatives are retaining whole-code loads and pricing by total code size, or using much smaller chunks. The former charges for unread code; the latter reduces byte coverage but increases lookup, metadata, and access-tracking costs. Neither the contract-size limit nor the initcode-size limit changes in this TIP.

## Assumptions

- Activation occurs at a coordinated protocol upgrade. Existing execution and gas rules remain in effect beforehand.
- Full deployed code remains identified by its existing Keccak code hash. Externally visible code bytes do not change. Adding `code_size` to account metadata changes the state commitment at activation.
- The account's `code_size` is the consensus-authoritative byte length. The chunk count and index bound are derived as `ceil(code_size / C)`. Nodes MUST construct and validate chunk records from complete code whose hash and length match the account before activation. A missing in-range record is a database error, never empty code or an EVM out-of-gas result.
- A code hash is an immutable content identity. The same `(code_hash, index)` MUST resolve to identical bytes and boundary metadata across accounts and forks.
- Partial network witnesses cannot be authenticated by a whole-code Keccak hash alone. This TIP does not introduce a partial-code proof format: untrusted full code MUST be verified before indexing. Stateless witnesses still require complete code unless a separate commitment proposal is adopted.
- The draft tariff is a candidate, not a measured equivalence between gas and I/O. Scheduling requires Tempo workload and adversarial storage benchmarks, as described below.

# Specification

## Chunk layout

Let `C = 12 * 1024 = 12288` and `L` be the original bytecode length. Empty code has zero chunks; other code has `ceil(L / C)` chunks. Chunk `i` contains original bytes `[i*C, min((i+1)*C, L))`. The final chunk is unpadded. Execution's virtual STOP and truncated PUSH zero-padding MUST NOT be persisted, hashed, or treated as additional chunks.

Each record is `leading_push_data: u8 || payload`. The marker is in `[0, 32]` and counts initial bytes consumed by a PUSH instruction beginning in the preceding chunk. The first marker is zero. A truncated final chunk may have a marker greater than its payload length. Calculate markers by scanning original instructions in order, advancing one byte plus the immediate width for PUSH1 through PUSH32, and one byte for other opcodes.

For JUMPDEST validation, begin instruction scanning at `leading_push_data` within the destination chunk. A byte is a valid destination only if it is in range, is at an instruction boundary, and equals JUMPDEST. Cache per-chunk analysis after its first use. Metadata MUST be generated from verified complete code, not accepted on structural validation alone.

## Account metadata

Extend the consensus account record with `code_size: u32` alongside `code_hash`. Abstractly, the account code identity becomes:

```text
(code_hash, code_size)
```

The other existing account fields are unchanged. Empty code MUST use `KECCAK256_EMPTY` and a size of zero. Nonempty code MUST record its exact original byte length. A nonempty code hash with size zero, an empty code hash with nonzero size, or a size that disagrees with verified code is invalid state.

Derive `code_chunk_count = ceil(code_size / C)`, with zero chunks when `code_size == 0`. An execution request with `index >= code_chunk_count` is out of range and MUST return no chunk without performing chunk database I/O or changing warmth. A request with `index < code_chunk_count` is in range and MUST produce a valid chunk; absence is a database failure. `EXTCODESIZE`, PC bounds, and copy-range clipping use `code_size` directly without fetching bytecode. Every chunk except the last MUST have payload length `C`; the final payload MUST have length `code_size - (code_chunk_count - 1) * C`.

Creating or replacing code MUST update `code_hash` and `code_size` atomically. Reverting that state transition restores both fields. An EIP-7702 designator records its exact 23-byte size when present. Account deletion and any operation that clears code restore the empty hash and zero size according to existing account-lifecycle rules.

## Database and execution interfaces

The required database operation is:

```rust
fn get_code_chunk_by_hash(
    &mut self,
    code_hash: &B256,
    index: u32,
) -> Result<Option<CodeChunk>, Self::Error>;
```

`Some` returns exactly one indexed record. The caller MUST derive the chunk count from the account's `code_size` and compare `index` with it first. `None` is valid only for an out-of-range index or empty code; an implementation SHOULD answer that case before calling this method. Unknown nonempty code, missing in-range records, malformed data, and I/O failures MUST return errors. Typed, erased, cached, counted, and asynchronous database adapters MUST preserve this contract. Async adapters take an owned hash and yield during I/O. There is no default implementation that fetches complete code.

The account's `code_size` determines exact length and which chunk indices exist. `EXTCODESIZE` uses this field, and `EXTCODEHASH` uses the account code hash. Existing full-code APIs remain necessary for `eth_getCode`, synchronization, code hashing, and verification.

An in-memory backend with complete resident bytecode MAY derive and cache its chunks locally. A persistent backend MUST fetch the selected chunk without first loading other chunks or complete bytecode. New deployments MUST install the account's hash/size pair, payloads, and boundary markers atomically with code availability. The activation transition MUST populate `code_size` for every existing account from code verified against its hash and update the state commitment. The transition is invalid if code is unavailable or the derived metadata is inconsistent. Historical pre-activation reads use the old account format and old execution rules; post-activation reads use the hash/size pair from the requested state. Pruning follows the existing code-retention policy.

The journal-facing operation returns the chunk and whether this access was cold. In the EVM2 prototype it is `State::load_code_chunk(address, index, skip_cold_load)`. It resolves the account's current code hash and size, including uncommitted code replacement, derives the chunk count, and performs the bound check before chunk I/O. When `skip_cold_load` is true, cold in-range nonempty code returns `ColdLoadSkipped` before chunk I/O or warmth mutation; account metadata may already have been read. The caller handles account-access gas, delegation resolution, byte-range validation, and gas reservation.

## Cache and journal

Maintain two distinct structures:

- A byte cache keyed by `(code_hash, chunk_index)`, shared across addresses and retained across call reverts and transaction resets.
- A warm set keyed by `(code_address, code_hash, chunk_index)`, initially empty for each transaction. This address is the owner of the code being read; for DELEGATECALL it is not the storage-context address.

After an authorized successful cold read, insert its key into the warm set and append `CodeChunkWarmed` to the revert journal. Repeated warm reads do not append entries. Reverting a call removes keys inserted since its checkpoint but retains cached bytes. A caller-warmed chunk remains warm when an inner call that reused it reverts. Successful child-call warmth persists into the parent. Transaction reset clears all chunk warmth, irrespective of cached bytes; access lists and account warmth do not prewarm code chunks.

Failed fetches, skipped cold loads, and out-of-range queries MUST NOT warm chunks. Cache hits MUST NOT change consensus gas: a logically cold access still pays the cold tariff. A new code hash or size at the same address has independent account state, and rollback restores both previous values. Snapshots MUST preserve the byte cache, warm set, and journal together. A detached committed state diff excludes these access-tracking fields; cache bytes are not consensus writes.

## Gas function

Define the incremental code-read tariff:

```text
CHUNK_BYTES       = 12288
COLD_CHUNK_BASE    = 2100
GAS_PER_CODE_WORD = 2
COLD_CHUNK_COST    = 2100 + 2 * ceil(CHUNK_BYTES / 32) = 2868
WARM_CHUNK_COST    = 0

chunk_gas(required, warm) = 2868 * |unique(required) \\ warm|
```

`required` and `warm` contain the complete address/hash/index keys. Multiplication and range arithmetic MUST be checked; a cost exceeding remaining gas is out of gas. Every cold chunk costs 2,868, including a short final chunk. This fixed capacity charge makes the cost known before chunk I/O. No initial 24 KiB allowance applies. The charge is additional to existing account-access, opcode, copying, memory-expansion, call, and deployment gas; none is replaced by this function.

For a byte range `(offset, size)`, require no chunks if `size == 0` or `offset >= L`. Otherwise intersect the range with `[0, L)` using nonwrapping arithmetic; require indices from `floor(offset/C)` through `floor((min(offset+size,L)-1)/C)`. Deduplicate before charging. Out-of-code copy bytes and truncated PUSH operands are virtual zeros and have no chunk charge.

Before fetching any cold chunk for one access, reserve the total incremental gas for that access and only then fetch and warm its chunks. Insufficient gas halts the current frame before those fetches or warmth changes. Database failure aborts execution as a node error. Gas already spent is not refunded by REVERT; warmth follows the checkpoint rules above.

## Execution access points

Existing stack, opcode, and fork validity checks retain their order. Once the opcode byte is available, existing opcode gas and memory checks occur before additional operand/source/destination chunk I/O.

| Operation | Required reads and charging frame |
|---|---|
| Opcode fetch | The current PC's chunk, charged to the executing frame before fetching. A PC beyond code length produces virtual STOP without a chunk read. |
| PUSH1–PUSH32 | Immediate bytes intersecting original code, charged to the executing frame after base opcode gas and before reading operands. This may cross one chunk boundary. |
| Taken JUMP / JUMPI | In-range destination chunk, charged before destination validation, even if it proves invalid. Untaken JUMPI and out-of-range targets do not read destination code. |
| CODECOPY | Source range in the current code after normal memory/copy gas checks, charged to the executing frame. |
| EXTCODECOPY | Source range of the addressed account after normal account/memory/copy gas checks, charged to the caller. EIP-7702 designators are copied as stored; this opcode does not follow delegation. |
| CALL family / transaction entry | Resolve the executing code owner normally. The first opcode fetch charges the new execution frame. Internal-call forwarding and the 63/64 calculation retain their current rules; a child's chunk out-of-gas failure follows normal child failure handling. |
| EIP-7702 resolution | Reading a nonempty designator requires its chunk in the resolving frame, then ordinary target-account access rules apply. Target executable bytes are charged when read in the execution frame. Top-level resolution uses transaction execution gas; failure prevents execution and rolls back execution-phase changes. |

Initcode is already supplied by the transaction or caller memory and is exempt from deployed-code chunk charges. CODECOPY and instruction reads within initcode are likewise exempt. Returning deployed runtime code retains existing deposit charges and creates the index; it does not automatically warm runtime chunks. Native precompiles do not read deployed bytecode and incur no chunk charge. Code-size limits, initcode limits, and existing delegation validity rules remain unchanged.

Activation MUST gate all read points together. JIT/AOT paths MUST charge the same logical reads as the interpreter; compiling or prefetching extra bytes cannot warm or charge them. A full-code compilation path that still reads complete code cannot claim the I/O bound of lazy chunk execution.

## Compatibility and rollout

The code hash, storage keys, deployment addresses, opcode outputs, and RPC code bytes remain unchanged. Account encoding and state roots change because accounts commit to `code_size`. Additional gas can change transaction success, gas estimation, GAS opcode results, and CALL forwarding behavior indirectly through gas already consumed. The proposal therefore requires a hardfork, a deterministic account migration, and updated gas estimation, transaction simulation, proof tooling, and conformance fixtures.

Roll out in stages: build the local index and database/journal APIs; implement and differentially test lazy interpreter and compiled execution; shadow replay Tempo workloads; calibrate and approve the tariff; then activate all consensus changes at the scheduled fork. Replaying pre-fork blocks MUST retain their original gas schedule. Do not combine this TIP with a code-size-limit increase without separate review.

## Reference implementation and measurements

The experimental EVM2 branch `rakita/bytecode-chunking` implements the 12 KiB codec, required typed/erased/async database reads, cache, read counters, journaled warmth, snapshots, and a checked `code_chunk_gas` helper. Unit tests cover boundaries, rollback, transaction reset, code replacement, absent/failed/skipped reads, and async suspension.

The current interpreter still executes resident full bytecode under the existing gas schedule. Its inspector estimates touched chunks; the new loader and tariff are not yet wired into every execution access point. The prototype's account type does not yet contain the consensus code size described here. Account encoding and migration, lazy interpreter/JIT dispatch, fork gating, and complete delegation tracing remain required before activation. This draft does not represent a completed consensus implementation.

The accompanying EVM2 measurements use Ethereum blocks 25,347,446–25,347,455 (2,279 transactions), not a Tempo workload. Results compare baseline transaction outcomes and receipt roots under unchanged gas. Coverage counts retained reads even from reverted execution and deduplicates by code address/hash/index within each block; it is not physical disk I/O or a proof-size measurement. Initcode and delegation-resolution reads are excluded. Full state-root comparison is not enabled.

At 12 KiB, the sum of block-local full code is 29,955,810 bytes versus 29,497,907 payload bytes (including markers, excluding proofs), a **1.53% reduction**. Execution touches 3,963 of 4,053 chunks. Transaction-local totals are 66,668,187 full-code bytes versus 65,958,266 payload bytes (1.06% reduction). On an Apple M5 Max with rustc 1.98.1 and packed dispatch, seven interleaved samples give median replay times of 97.347 ms without inspection and 180.645 ms with coverage inspection; this is instrumentation overhead, not a lazy-loading speedup.

The 12 KiB result and reproducible commands are recorded in the implementation's `measurements/bytecode-chunks/README.md`. Scheduling requires cold/warm persistent-DB latency distributions, bytes actually read, sparse large-code execution, boundary jumps, repeated reverts, memory overhead, and Tempo replay gas/success deltas. The tariff MUST bound worst-case read throughput under the block gas budget. Engineering, research, security, and tooling review remain pending under TIP-0000.

# Tooling

Clients expose separate full-code and chunk-read counters. Database implementers add the required chunk method to typed, erased, and async backends; deployment/import/sync tooling builds and verifies the code index and the account's code size. State inspection and proof tooling must decode the post-activation account field. RPC consumers keep the existing full-code interface. Gas estimators and simulators must select the active fork and maintain journaled warmth across calls.

The EVM2 `bytecode_chunks` and `bytecode_chunks_mainnet` examples produce coverage CSVs and separate timing output. Fixtures MUST cover zero-length ranges, short final chunks, all PUSH widths across boundaries, invalid jumps into PUSH data, copy overflow, duplicate keys, nested reverts, new deployments, code replacement, delegation, precompiles, and compiled execution parity. Benchmarks MUST distinguish tracing overhead from an actual chunk-backed execution measurement.

# Observability

No new on-chain events are emitted. Clients MUST export aggregate counters for chunk requests, physical backend reads, byte-cache hits, bytes returned, and full-code reads, with no per-address metric labels. These distinguish logical demand from cache and I/O behavior.

Clients MUST emit a structured `code_chunk_database_error` diagnostic on a failed chunk fetch, with block/transaction context when available, code hash, declared code size, derived chunk count, requested index, and error category. It answers whether validation failed because of inconsistent account metadata, missing/malformed code, or a storage failure. Per-request latency histograms and total cached bytes SHOULD be exported to identify regressions and memory growth. Consensus warmth and gas MUST never depend on these metrics or on cache eviction.

# Threat Model

- Contract authors and transaction senders are adversarial. They can target chunk boundaries, invalid jump targets, many code owners, repeated reverts, and truncated ranges to maximize I/O or exploit accounting errors. Charge before I/O and use checked arithmetic.
- Database providers are trusted to return code verified against its hash, account code size, and correct boundary metadata. Corrupt bytes or metadata can alter execution; fail validation rather than substitute STOP, empty code, or a benign miss.
- Network peers are untrusted. Individually plausible chunks do not prove membership in the whole-code hash. Verify complete code before populating the trusted index.
- Client implementations and compiled engines must enforce identical logical reads, checkpoint behavior, and gas ordering. Shared caches and concurrent execution are optimizations and cannot share transaction warmth.

# Invariants

1. Concatenating exactly `ceil(code_size / 12288)` payloads yields `code_size` bytes whose hash matches `code_hash`; empty code has size and chunk count zero.
2. Chunk-local JUMPDEST validation equals whole-code instruction analysis at every byte offset.
3. Cold gas is determined by logical address/hash/index warmth, never cache residency, prefetch, or timing.
4. An insufficient gas reservation performs no chunk fetch or new warmth insertion for that access.
5. Revert restores warmth to the checkpoint while preserving fetched bytes and outer-scope warmth.
6. `index >= ceil(code_size / 12288)` performs no chunk I/O; failed/skipped reads do not warm, and missing data below the bound is a node error rather than an EVM result.
7. Changing code updates hash and size atomically and cannot expose stale bytes; reverting replacement restores both fields.
8. Snapshot/restore preserves cache, journal, and warmth consistently; transaction reset removes all warmth.
9. Interpreter, JIT, AOT, and async execution agree on gas, output, logs, state, and access order at activation.
10. Database reads of existing deployed code are bounded by charged chunk demand; complete-code fallback in the lazy execution path is prohibited.
