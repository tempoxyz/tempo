# TIP-1122: Adopt EIPs 7954, 7976, 8024, and 7997

## Abstract

This TIP aligns Tempo with proposed Ethereum execution-layer changes so developers
can use a shared set of EVM capabilities and deployment conventions across both
chains. It adopts EIPs 7954, 7976, 8024, and 7997, with adaptations for Tempo's
transaction batching and gas accounting.

## Motivation

Keeping Tempo aligned with Ethereum reduces differences that application,
compiler, and deployment-tool authors need to support. This TIP includes:

- [EIP-7954: Increase Maximum Contract Size](https://eips.ethereum.org/EIPS/eip-7954)
  — raises runtime code to 64 KiB and initcode to 128 KiB, allowing larger contracts.
- [EIP-7976: Increase Calldata Floor Cost](https://eips.ethereum.org/EIPS/eip-7976)
  — raises the floor to 64 gas per byte, increasing the cost of data-heavy traffic.
- [EIP-8024: Backward compatible SWAPN, DUPN, EXCHANGE](https://eips.ethereum.org/EIPS/eip-8024)
  — adds stack operations that simplify compiler-generated code and deeper stack access.
- [EIP-7997: Deterministic Factory Contract](https://eips.ethereum.org/EIPS/eip-7997)
  — guarantees the canonical CREATE2 factory used for deployments at the same
  address across chains. Tempo already includes this factory in its genesis allocations.

# Specification

## EIP-7954: Increase Maximum Contract Size

Set the maximum deployed runtime code size to **65,536 bytes** (`0x10000`) and
the maximum initcode size to **131,072 bytes** (`0x20000`). These limits replace
24,576 and 49,152 bytes, respectively; equality with a limit is permitted.

Apply the limits to ordinary contract-creation transactions, every creation call
in a Tempo transaction, and internal `CREATE`/`CREATE2`. Preserve existing failure
semantics for oversized code and initcode. Tempo's creation, code-deposit, initcode
metering, and state-gas charges remain unchanged. In particular, a larger allowed
size does not guarantee deployment within the transaction's gas budget.

### Denial-of-service analysis for Tempo

**Loading existing code.** The main risk is the size-dependent work behind a
size-independent account-access charge. As described in
[EIP-170](https://eips.ethereum.org/EIPS/eip-170), reading and preparing code can
scale with code length even when the called contract does little execution.
Increasing the limit from 24 KiB to 64 KiB permits **2.67 times as many code bytes
per maximum-size code load**, without increasing the call's account-access charge.
This is a byte-volume comparison, not a measured execution-time multiplier.

An attacker can deploy many contracts with distinct code hashes, each returning
immediately, then call different contracts across transactions and blocks to
pressure the code cache and database. Repeated calls to one cached contract do
not represent this workload. Tempo's high-throughput design makes aggregate code
reads, cache churn, and validator processing latency relevant even when the
contracts execute very few instructions. Upfront deployment fees do not meter
these later reads.

**Deployment and state growth.** Tempo's
[current gas schedules](../crates/revm/src/gas_params.rs) distinguish the
[TIP-1000](./tip-1000.md) schedule from the separately gated
[TIP-1016](./tip-1016.md) execution/state split:

| Code-deposit component | 24 KiB runtime | 64 KiB runtime |
| --- | ---: | ---: |
| TIP-1000: 1,000 gas/byte | 24,576,000 | 65,536,000 |
| TIP-1016: 200 execution gas/byte | 4,915,200 | 13,107,200 |
| TIP-1016: 2,300 state gas/byte | 56,524,800 | 150,732,800 |

These figures exclude fixed creation costs, transaction overhead, initcode
execution, and hashing. Under TIP-1000, code deposit consumes the ordinary gas
budget; the 64 KiB limit can therefore exceed what a transaction's active gas cap
allows. With TIP-1016 enabled, state gas is paid by the sender but does not count
against block execution capacity. Its higher total fee is an economic deterrent,
not a bound on the validator's work per block. The remaining execution charge
still scales with deployed bytes. This TIP does not enable TIP-1016 or change
these prices.

**Initcode and calldata.** The larger initcode limit increases the maximum input
that creation must process. Initcode metering, memory expansion, execution gas,
and CREATE2 hashing charges continue to apply. EIP-7976 charges for top-level
input bytes, but does not price subsequent reads of deployed code or runtime
bytes generated by compact initcode. It therefore does not eliminate the
large-code attack above. Reverting creation workloads also need consideration:
execution and hashing work can be repeated without leaving permanent code behind.

The unresolved question is whether existing access and execution prices cover
these workloads within Tempo's block-processing budget. Evaluate 24 KiB versus
64 KiB contracts with distinct code hashes, warm and cold caches, sustained
cache-evicting access, successful and reverting creation, and 128 KiB initcode.
Measure full-block execution and persistence latency under the gas schedule
selected for inclusion. If those workloads exceed the supported validator budget,
code-access repricing or retaining the current limit is needed before adoption;
Ethereum's proposed limit alone is not evidence of safety for Tempo.

## EIP-7976: Increase Calldata Floor Cost

Replace the EIP-7623 floor with:

```text
calldata_floor_gas = 21_000 + 64 * calldata_length
```

Zero and nonzero bytes count equally toward this floor. Ordinary calldata pricing
remains 4 gas per zero byte and 16 per nonzero byte. The transaction gas limit
MUST cover both its intrinsic gas and its calldata floor.

For an Ethereum transaction, `calldata_length` is the transaction input length,
including initcode for a creation transaction. For a Tempo transaction
([TIP-0001](./tip-0001.md)), it is the sum of `call.input.len()` over **all encoded
top-level calls**, including creation calls and calls not reached during execution.
Apply the 21,000 base once per transaction, not once per call. Nested EVM calls do
not add bytes to this count. Signature material, authorization lists, access lists,
and envelope metadata retain their existing charges and are not added to the floor.

Replace the existing floor in admission and final gas accounting while preserving
Tempo's active creation, authorization, and refund rules. If the execution/state
split in [TIP-1016](./tip-1016.md) is enabled, use this value for
`calldata_floor_gas_cost` in its execution-gas cap, settlement, and block accounting;
state gas remains separate. Apply the floor after execution-gas refunds, preserving
[TIP-1060](./tip-1060.md) where active. Adopting the new floor does not enable
TIP-1016 or import Ethereum's refund cap and creation prices.

Pool admission, payload construction, block validation, and RPC simulation MUST
use the same active formula. Pending transactions must be revalidated against it
at activation. Existing protocol system-transaction exemptions remain unchanged.

## EIP-8024: Backward compatible SWAPN, DUPN, EXCHANGE

Enable `DUPN` (`0xe6`), `SWAPN` (`0xe7`), and `EXCHANGE` (`0xe8`) in EVM bytecode,
each costing **3 gas**. Each opcode consumes one immediate byte, decoded exactly
as specified by
[EIP-8024](https://github.com/ethereum/EIPs/blob/24c0edb17b82cb65f26d29f03e084637ec2ae2d4/EIPS/eip-8024.md),
including its invalid immediate ranges and zero-padding at end of code.

Adopt the specified stack effects and exceptional failures, preserving the
1,024-item stack limit and existing jump-destination analysis. No EOF container
or bytecode version is required. Before activation these bytes retain their
previous invalid-opcode behavior when executed. Existing bytecode is not rewritten.

## EIP-7997: Deterministic Factory Predeploy

Require the canonical factory at
`0x4e59b44847b379578588920cA78FbF26c0B4956C`, with the exact runtime bytecode in
[EIP-7997](https://github.com/ethereum/EIPs/blob/24c0edb17b82cb65f26d29f03e084637ec2ae2d4/EIPS/eip-7997.md)
and a nonzero nonce. This is an ordinary EVM contract, not a precompile.

Tempo already defines this address and runtime in
[`tempo-contracts`](../crates/contracts/src/lib.rs), and the
[`dev`](../crates/chainspec/src/genesis/dev.json),
[`presto`](../crates/chainspec/src/genesis/presto.json), and
[`moderato`](../crates/chainspec/src/genesis/moderato.json) allocations contain it
with nonce 1. Preserve existing deployed state. New genesis configurations MUST
include the canonical code with nonce 1. Clients MUST NOT introduce a
factory-existence check at the fork boundary or an automatic repair transition.

Calls supply a 32-byte salt followed by initcode, without a function selector.
The factory uses `CREATE2` and returns a successful deployment address as exactly
20 unpadded bytes; creation failure reverts with empty return data. The bytecode
remains authoritative for all edge cases. Tempo's existing restrictions on native
value transfer continue to apply.

# Compatibility

The size limits, calldata pricing, and new opcodes require a coordinated network
upgrade. Historical execution retains its previous rules. Existing contracts keep
their code and jump destinations; execution of the newly assigned opcode bytes
changes from exceptional failure to the specified stack operations.

Data-heavy transactions may need higher gas limits after the change. Larger
contracts remain subject to Tempo's active gas budget and creation restrictions.
The canonical factory's existing code, nonce, balance, and storage are preserved;
its inclusion adds no state transition on networks that already satisfy EIP-7997.
A network missing the factory requires a separately specified deployment or
remediation, not an automatic overwrite at the upgrade boundary.
