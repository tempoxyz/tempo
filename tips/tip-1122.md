# TIP-1122: Adopt EIPs 7954, 7976, 8024, and 7997

## Abstract

This TIP adopts four Ethereum improvements for Tempo: larger contract and initcode
limits, a higher calldata gas floor, additional stack instructions, and guaranteed
availability of the canonical deterministic deployment factory. It specifies how
these changes interact with Tempo transactions and gas accounting. The factory
already appears in Tempo's checked-in genesis allocations; its inclusion is a
compatibility requirement rather than a new deployment on those networks.

## Motivation

Larger contracts and deeper stack access reduce constraints on application and
compiler authors. A higher calldata floor limits how cheaply data-heavy
transactions can consume block bandwidth, while a shared deployment factory
supports applications that use the same contract addresses across chains.

Adopting the upstream specifications avoids maintaining Tempo-specific alternatives
for these features. Keeping the existing limits and opcodes would preserve current
tooling constraints; choosing a different factory would lose compatibility with
existing deterministic deployment tools.

## Assumptions

- The prerequisites of the adopted EIPs are already supported: EIP-170,
  EIP-3860, EIP-7623, and EIP-1014.
- Nodes agree on a scheduled Tempo activation point. Until scheduling, this TIP
  does not assign a protocol version or change any network configuration.
- The four upstream EIPs are in Review. The revisions pinned below are normative;
  subsequent upstream edits require an explicit update and review of this TIP.
- Before scheduling, verify the factory code and nonce on each target network.
  A mismatch requires a separately specified remediation before that network can
  claim compliance; this TIP does not authorize overwriting an existing account.

## Threat Model

Transaction senders are untrusted and may maximize calldata, deployed code, or
stack-operation workloads within the gas limits. Validators must enforce the
same limits and prices regardless of local pool policy or compiler behavior.

Factory callers are permissionless. Applications must not rely on exclusive use
of a salt or on environment-dependent initialization being protected from
front-running. Node operators coordinate activation; inconsistent rules can cause
consensus disagreement.

# Specification

## Activation and upstream references

Activate the changes together at the Tempo upgrade assigned to this TIP. Historical
execution MUST retain its original rules. This TIP adopts only the four EIPs
listed here, not an entire Ethereum hardfork.

The normative upstream specifications are pinned to Ethereum EIPs revision
`24c0edb17b82cb65f26d29f03e084637ec2ae2d4`:

| EIP-7976 | [Increase Calldata Floor Cost](https://github.com/ethereum/EIPs/blob/24c0edb17b82cb65f26d29f03e084637ec2ae2d4/EIPS/eip-7976.md) |

The Tempo adaptations below govern transaction batching, existing gas schedules,
and factory availability. All other semantics of the adopted features follow the
pinned specifications.

## EIP-7954: Increase Maximum Contract Size

Set the maximum deployed runtime code size to **65,536 bytes** (`0x10000`) and
the maximum initcode size to **131,072 bytes** (`0x20000`). These limits replace
24,576 and 49,152 bytes, respectively; equality with a limit is permitted.

Apply the limits to ordinary contract-creation transactions, every creation call
in a Tempo transaction, and internal `CREATE`/`CREATE2`. Preserve existing failure
semantics for oversized code and initcode. Tempo's creation, code-deposit, initcode
metering, and state-gas charges remain unchanged. In particular, a larger allowed
size does not guarantee deployment within the transaction's gas budget.

## EIP-7976: Increase Calldata Floor Cost

Replace the EIP-7623 floor with:

```text
calldata_floor_gas = 21_000 + 64 * calldata_length
```

Zero and nonzero bytes count equally toward this floor. Ordinary calldata pricing
remains 4 gas per zero byte and 16 per nonzero byte. The transaction gas limit
MUST cover both its intrinsic gas and its calldata floor.

For an Ethereum transaction, `calldata_length` is the transaction input length,
including initcode for a creation transaction. For a Tempo transaction
([TIP-0001](./tip-0001.md)), it is the sum of `call.input.len()` over **all encoded
top-level calls**, including creation calls and calls not reached during execution.
Apply the 21,000 base once per transaction, not once per call. Nested EVM calls do
not add bytes to this count. Signature material, authorization lists, access lists,
and envelope metadata retain their existing charges and are not added to the floor.

Use this value wherever Tempo currently applies `calldata_floor_gas_cost` in
[TIP-1016](./tip-1016.md): admission, the execution-gas cap, settlement, and the
transaction's contribution to block execution gas. Keep state gas separate and
apply the floor after execution-gas refunds. Preserve the refund rules of
[TIP-1060](./tip-1060.md); do not import Ethereum's refund cap or replace Tempo's
creation and authorization charges with the illustrative Ethereum formula.

Pool admission, payload construction, block validation, and RPC simulation MUST
use the same active formula. Pending transactions must be revalidated against it
at activation. Existing protocol system-transaction exemptions remain unchanged.

## EIP-8024: Backward compatible SWAPN, DUPN, EXCHANGE

Enable `DUPN` (`0xe6`), `SWAPN` (`0xe7`), and `EXCHANGE` (`0xe8`) in EVM bytecode,
each costing **3 gas**. Each opcode consumes one immediate byte, decoded exactly
as specified by the pinned EIP, including its invalid immediate ranges and
zero-padding at end of code.

Adopt the specified stack effects and exceptional failures, preserving the
1,024-item stack limit and existing jump-destination analysis. No EOF container
or bytecode version is required. Before activation these bytes retain their
previous invalid-opcode behavior when executed. Existing bytecode is not rewritten.

## EIP-7997: Deterministic Factory Predeploy

Require the canonical factory at
`0x4e59b44847b379578588920cA78FbF26c0B4956C`, with the exact runtime bytecode in the
pinned EIP and a nonzero nonce. This is an ordinary EVM contract, not a precompile.

Tempo already defines this address and runtime in
[`tempo-contracts`](../crates/contracts/src/lib.rs), and the
[`dev`](../crates/chainspec/src/genesis/dev.json),
[`presto`](../crates/chainspec/src/genesis/presto.json), and
[`moderato`](../crates/chainspec/src/genesis/moderato.json) allocations contain it
with nonce 1. Preserve existing deployed state. New genesis configurations MUST
include the canonical code with nonce 1. Clients MUST NOT introduce a
factory-existence check at the fork boundary or an automatic repair transition.

Calls supply a 32-byte salt followed by initcode, without a function selector.
The factory uses `CREATE2` and returns a successful deployment address as exactly
20 unpadded bytes; creation failure reverts with empty return data. The bytecode
remains authoritative for all edge cases. Tempo's existing restrictions on native
value transfer continue to apply.

# Tooling

Update gas estimation, transaction simulation, and SDK gas calculations for the
new floor and size limits. Wallets should re-estimate pending transactions around
activation. Compiler targets, assemblers, disassemblers, and tracers must recognize
the EIP-8024 encoding before emitting or interpreting the new instructions.

Deployment tooling can retain the canonical factory address and raw calldata
interface. No new RPC method, transaction field, or Solidity precompile interface
is required. Add activation-aware execution fixtures and genesis checks to the
existing client test suites.

# Observability

N/A for new on-chain events: these changes add no event-emitting interface.
Existing receipts, execution traces, gas-estimation errors, and code/nonce queries
provide transaction diagnostics and factory verification. Existing block-size,
gas-usage, and execution-latency telemetry should be used to assess the effects
of larger contracts and the higher floor during testnet rollout.

# Invariants

1. **Historical replay:** pre-activation blocks preserve their state roots,
   receipts, and gas accounting. All execution and admission paths switch at the
   same configured activation point.
2. **Size enforcement:** test runtime sizes 24,576, 24,577, 65,536, and 65,537,
   and initcode sizes 49,152, 49,153, 131,072, and 131,073, across activation.
   Cover ordinary creation, Tempo batch creation, `CREATE`, and `CREATE2`,
   including insufficient gas and rollback after failed creation.
3. **Floor enforcement:** equal-length zero, nonzero, and mixed inputs have the
   same floor. Test gas limits immediately below, at, and above it; computation
   above the floor; refunds below it; and state-gas separation. Test mixed Tempo
   batches, early reverts, sponsorship, and every supported signature type.
4. **Stack correctness:** run the pinned EIP-8024 vectors and cover all immediate
   bytes, stack underflow/overflow, insufficient gas, and truncated instructions.
   Jump-destination sets must remain identical across activation for any bytecode.
5. **Factory compatibility:** verify canonical code and nonzero nonce for each
   target network, nonce 1 in new genesis allocations, deterministic addresses,
   short input, repeated deployment collisions, and failed initialization. Check
   that activation does not reset the factory's nonce, code, balance, or storage.

Before scheduling, publish passing conformance results and benchmark worst-case
large-code deployment/access and data-heavy blocks on supported validator hardware.
Review their execution, propagation, and state-growth impact against the target
network's block budget. Engineering, security, and tooling review follow
[TIP-0000](./tip-0000.md); upstream changes or failed readiness checks require
revising the draft before approval and activation.
