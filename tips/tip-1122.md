# TIP-1122: Adopt EIPs 7954, 7976, and 8024

## Abstract

This TIP aligns Tempo with proposed Ethereum execution-layer changes so developers
can use a shared set of EVM capabilities across both chains. It adopts EIPs 7954,
7976, and 8024, with adaptations for Tempo's transaction batching and gas accounting.

## Motivation

Keeping Tempo aligned with Ethereum reduces differences that application,
compiler, and deployment-tool authors need to support. This TIP includes:

- [EIP-7954: Increase Maximum Contract Size](https://eips.ethereum.org/EIPS/eip-7954)
  — raises runtime code to 64 KiB and initcode to 128 KiB, allowing larger contracts.
- [EIP-7976: Increase Calldata Floor Cost](https://eips.ethereum.org/EIPS/eip-7976)
  — raises the floor to 64 gas per byte, increasing the cost of data-heavy traffic.
- [EIP-8024: Backward compatible SWAPN, DUPN, EXCHANGE](https://eips.ethereum.org/EIPS/eip-8024)
  — adds stack operations that simplify compiler-generated code and deeper stack access.

# Specification

## EIP-7954: Increase Maximum Contract Size

Set the maximum deployed runtime code size to **65,536 bytes** (`0x10000`) and
the maximum initcode size to **131,072 bytes** (`0x20000`). These limits replace
24,576 and 49,152 bytes, respectively; equality with a limit is permitted.

Apply the limits to ordinary contract-creation transactions, every creation call
in a Tempo transaction, and internal `CREATE`/`CREATE2`. Preserve existing failure
semantics for oversized code and initcode. Tempo's creation, code-deposit, initcode
metering, and state-gas charges remain unchanged. In particular, a larger allowed
size does not guarantee deployment within the transaction's gas budget.

## EIP-7976: Increase Calldata Floor Cost

Replace the EIP-7623 floor with:

```text
calldata_floor_gas = 21_000 + 64 * calldata_length
```

Zero and nonzero bytes count equally toward this floor. Ordinary calldata pricing
remains 4 gas per zero byte and 16 per nonzero byte. The transaction gas limit
MUST cover both its intrinsic gas and its calldata floor.

For an Ethereum transaction, `calldata_length` is the transaction input length,
including initcode for a creation transaction. For a Tempo transaction
([TIP-0001](./tip-0001.md)), it is the sum of `call.input.len()` over **all encoded
top-level calls**, including creation calls and calls not reached during execution.
Apply the 21,000 base once per transaction, not once per call. Nested EVM calls do
not add bytes to this count. Signature material, authorization lists, access lists,
and envelope metadata retain their existing charges and are not added to the floor.

Replace the existing floor in admission and final gas accounting while preserving
Tempo's active creation, authorization, and refund rules. If the execution/state
split in [TIP-1016](./tip-1016.md) is enabled, use this value for
`calldata_floor_gas_cost` in its execution-gas cap, settlement, and block accounting;
state gas remains separate. Apply the floor after execution-gas refunds, preserving
[TIP-1060](./tip-1060.md) where active. Adopting the new floor does not enable
TIP-1016 or import Ethereum's refund cap and creation prices.

Pool admission, payload construction, block validation, and RPC simulation MUST
use the same active formula. Pending transactions must be revalidated against it
at activation. Existing protocol system-transaction exemptions remain unchanged.

## EIP-8024: Backward compatible SWAPN, DUPN, EXCHANGE

Enable `DUPN` (`0xe6`), `SWAPN` (`0xe7`), and `EXCHANGE` (`0xe8`) in EVM bytecode,
each costing **3 gas**. Each opcode consumes one immediate byte, decoded exactly
as specified by
[EIP-8024](https://github.com/ethereum/EIPs/blob/24c0edb17b82cb65f26d29f03e084637ec2ae2d4/EIPS/eip-8024.md),
including its invalid immediate ranges and zero-padding at end of code.

Adopt the specified stack effects and exceptional failures, preserving the
1,024-item stack limit and existing jump-destination analysis. No EOF container
or bytecode version is required. Before activation these bytes retain their
previous invalid-opcode behavior when executed. Existing bytecode is not rewritten.

# Compatibility

The size limits, calldata pricing, and new opcodes require a coordinated network
upgrade. Historical execution retains its previous rules. Existing contracts keep
their code and jump destinations; execution of the newly assigned opcode bytes
changes from exceptional failure to the specified stack operations.

Data-heavy transactions may need higher gas limits after the change. Larger
contracts remain subject to Tempo's active gas budget and creation restrictions.
