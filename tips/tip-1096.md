# TIP-1096: Multi-block Tempo Imports for Zones

## Abstract

This TIP allows every non-genesis Zone block to import an ordered, nonempty range
of consecutive Tempo headers. Header continuity is checked across the entire
range, while only the final header becomes the Zone's new Tempo checkpoint and
supplies state for Tempo reads performed in that Zone block.

The import and deposit processing are atomic. A Zone block must process the
complete deposit queue visible at the final imported Tempo state root, and the
Tempo-side queue is bounded by outstanding deposits so that catch-up remains
within the Zone system transaction's gas budget.

## Motivation

A Zone may produce blocks less frequently than Tempo or pause temporarily. If a
Zone block can import only one Tempo header, the Zone must produce one block per
missed Tempo block before it can use current Tempo state. Its externally visible
state, deposits, token policies, and leadership can remain stale throughout that
catch-up period.

Importing a consecutive range lets a Zone advance directly to a recent Tempo
checkpoint in one block without weakening the parent-hash chain that authenticates
the checkpoint. Intermediate headers prove ancestry; the final header alone
defines the state snapshot used by Zone execution.

Using only the final state root means deposit processing must also be defined at
that snapshot. Requiring exact queue-head equality avoids accepting a partial
deposit prefix whose relationship to the final queue head is not checked during
execution. Bounding outstanding deposits, rather than deposits appended per
Tempo block, keeps the required all-or-nothing processing bounded even while a
Zone is offline.

## Assumptions

- A Zone can authenticate Tempo header ancestry and Tempo state proofs in its
  batch proof.
- Each portal exposes a monotonic deposit count, its last processed deposit
  number, its current deposit queue hash, and the Zone leadership configuration.
- The maximum outstanding deposit count is calibrated against the gas available
  to the Zone's opening `advanceTempo` system transaction.
- A Zone block has exactly one beneficiary and therefore cannot span two Tempo
  leadership epochs in one import range.
- The activation updates Zone execution, proving, verification, and the canonical
  Tempo-side Zone runtimes atomically. Implementations using the old single-header
  ABI are not compatible after activation.

If header or queue continuity cannot be proven, the complete Zone block is
invalid. If the configured queue bound no longer fits within the system gas
budget, liveness is not guaranteed and the bound must be changed by a later TIP.

## Threat Model

- **Zone sequencer.** May choose which consecutive headers to import and may delay
  a Zone, but cannot skip Tempo ancestry, omit deposits visible at the final root,
  cross a leadership transition, or bind reads to an intermediate root.
- **Depositor.** May continuously fill the public portion of a portal's queue but
  cannot exceed the outstanding-deposit cap or consume capacity reserved for
  withdrawal bounce-backs.
- **Withdrawal submitter.** May submit a batch in which every withdrawal could
  fail, but must reserve enough queue capacity for every possible bounce-back.
- **Batch prover.** May supply malformed headers, incomplete state witnesses, or
  reads for the wrong Zone block or Tempo checkpoint. The proof must reject all
  such inputs rather than substitute zero or another state root.
- **Tempo reorganization.** Is out of scope after the imported checkpoint has the
  finality required by the existing Zones protocol.

# Specification

## Zone Block Input

The single optional `tempo_header_rlp` field is replaced by:

```rust
pub tempo_header_rlps: Vec<Vec<u8>>
```

The canonical Zone genesis block MUST contain an empty vector. Every non-genesis
Zone block MUST contain at least one header and MUST execute exactly one
`advanceTempo` system transaction as its first transaction. A missing, repeated,
reverted, or halted `advanceTempo` call makes the containing Zone block invalid;
it MUST NOT be committed as a block with a failed system-transaction receipt.

Each item is the canonical RLP encoding of a Tempo header:

```text
rlp([general_gas_limit, shared_gas_limit, timestamp_millis_part, inner])
```

where `inner` is the Ethereum-compatible header defined by the active Tempo
protocol version. The header hash is Tempo's canonical hash of this encoding.

## Header Range Validation

Let `(storedHash, storedNumber)` be the Zone's current Tempo checkpoint. For a
non-bootstrap import, the first header MUST have:

```text
header[0].parent_hash == storedHash
header[0].number      == storedNumber + 1
```

For every later header `i`:

```text
header[i].parent_hash == hash(header[i - 1])
header[i].number      == header[i - 1].number + 1
```

Malformed headers, an empty array, a number gap, a duplicate number, or a parent
hash mismatch MUST revert `advanceTempo` and invalidate the Zone block.

After all headers validate, the Zone MUST set its Tempo checkpoint hash and
number to the hash and number of the final header. `TempoBlockFinalized` MUST be
emitted once for the final header and MUST contain its hash, number, and state
root. Intermediate headers MUST NOT create intermediate checkpoints or emit
separate finalization events.

For the first import after Zone genesis, the stored hash is zero and ordinary
parent continuity is unavailable. The batch proof MUST instead prove against the
final imported state root that the portal exists and its sequencer configuration
is nonempty. This proves that the imported range is not entirely before portal
creation. The final checkpoint is then installed as above.

## Tempo State Reads

Only the final imported header's state root is active during the containing Zone
block. Every Tempo state read performed by `advanceTempo` or a later user
transaction in that block MUST be proven against that root. This includes portal
queue state, token enablement state, TIP-403 policy resolution, and Zone
leadership state.

An intermediate header authenticates ancestry only. No deposit, policy, or other
state read may be evaluated against an intermediate header's state root.

Each witnessed Tempo read MUST identify the Zone block index, final imported
Tempo block number, account, storage slot, and value. Missing witness data, a
checkpoint mismatch, or an invalid trie proof MUST be an error and MUST NOT
default to zero.

## Leadership Boundary

After binding the final root, execution reads the portal's leader and
`leaderActivationTempoBlock`. If the first imported header precedes the activation
block and the final imported header is at or after it, the range crosses a leader
transition and the Zone block MUST be rejected.

Otherwise, the complete range belongs to one leadership epoch and the Zone block
beneficiary MUST equal the leader read from the final root. An operator must split
a catch-up range at every leadership transition.

## Atomic Deposit Processing

`advanceTempo` uses this ABI:

```solidity
function advanceTempo(
    bytes[] calldata headers,
    QueuedDeposit[] calldata deposits,
    DecryptionData[] calldata decryptions,
    EnabledToken[] calldata enabledTokens
) external;
```

It first validates and installs the final Tempo checkpoint, then activates tokens
and processes deposits oldest-first using only the final imported state root. The
reconstructed queue hash MUST equal the portal's `currentDepositQueueHash` at
that root. The call MUST revert on any mismatch, including when the supplied
deposits form only a valid prefix of the final queue.

The revert is atomic across header import, token activation, deposit mints,
decryption handling, bounce-backs, events, and all other side effects of the
system transaction. A successful call therefore processes every pending deposit
through the final-root queue head or processes none of them.

## Outstanding Deposit Capacity

Each portal replaces its per-Tempo-block deposit limit with:

```solidity
uint64 public constant MAX_UNPROCESSED_DEPOSITS = 230;
uint64 public constant WITHDRAWAL_BOUNCEBACK_RESERVE = 20;
```

Before appending an item, the portal computes:

```text
unprocessed = depositCount - lastProcessedDepositNumber
```

An ordinary user deposit MUST be rejected when `unprocessed` has reached
`MAX_UNPROCESSED_DEPOSITS - WITHDRAWAL_BOUNCEBACK_RESERVE`. A withdrawal
bounce-back MUST be rejected when `unprocessed` has reached
`MAX_UNPROCESSED_DEPOSITS`.

Before processing a withdrawal batch, the portal MUST conservatively assume that
every withdrawal fails and produces a bounce-back. With:

```text
remainingCapacity = MAX_UNPROCESSED_DEPOSITS - unprocessed
```

the call MUST reject `withdrawals.length > remainingCapacity` before processing
any withdrawal. A failed call MUST leave the withdrawal and deposit queues
unchanged.

The 20 reserved entries are sufficient for one maximum-size withdrawal batch
under the existing Zones limits. The value 230 is the measured upper bound for
processing the worst-case queue within the buffered 200,000,000 gas ceiling.

## Interface Changes

`ITempoState` changes from a single header to an array:

```solidity
function finalizeTempo(bytes[] calldata headers) external;
```

`finalizeTempo` MUST accept calls only from `ZoneInbox`, reject an empty array,
validate the complete range, store only the final hash and number, and emit only
the final-header event.

`IZonePortal.MAX_DEPOSITS_PER_TEMPO_BLOCK()` is replaced by
`MAX_UNPROCESSED_DEPOSITS()`. Implementations MUST expose distinct errors for a
full deposit queue and for a withdrawal batch that exceeds remaining capacity.

## Activation and Compatibility

The protocol version that schedules this TIP MUST update the canonical
`ZonePortal`, `ZoneInbox`, and `TempoState` runtimes together with the batch proof
and verifier rules. Existing Zone checkpoint and queue state are retained; no
per-Zone state migration is required.

The calldata ABI and Zone block witness format are not backward compatible.
Sequencers, provers, RPC encoders, test fixtures, and block decoders MUST switch
at the same activation boundary. Pre-activation Zone blocks continue to use the
single-header rules of their active protocol version.

# Invariants

- Every non-genesis Zone block imports one or more Tempo headers exactly once and
  as its first transaction.
- Imported header numbers and parent hashes form one consecutive chain beginning
  at the previously stored checkpoint.
- The stored checkpoint and `TempoBlockFinalized` event refer only to the final
  imported header.
- All Tempo reads in a Zone block use the final imported header's state root.
- An imported range never crosses a Zone leader activation boundary, and the
  beneficiary is the leader for the range's single epoch.
- A successful `advanceTempo` processes deposits through exactly the queue head
  visible at the final root; partial prefixes are rejected atomically.
- `depositCount - lastProcessedDepositNumber` never exceeds
  `MAX_UNPROCESSED_DEPOSITS`.
- Public deposits cannot consume the withdrawal bounce-back reserve.
- A withdrawal batch is accepted only if every withdrawal could bounce without
  exceeding the outstanding-deposit cap.
- A failed system transaction changes no checkpoint, queue, token, balance,
  receipt, or event state and invalidates its containing Zone block.

Critical tests MUST cover one-header and multi-header imports, empty and malformed
arrays, number gaps, parent-hash mismatches, bootstrap imports, leadership
boundary splits, final-root-only reads, exact and partial queue processing,
capacity boundaries for deposits and withdrawals, worst-case bounce-backs, and
full rollback after each failure class.
