# TIP-1096: Multi-block Tempo Imports for Zones

## Abstract

This TIP lets a non-genesis Zone block import an ordered, nonempty range of
consecutive Tempo headers. It defines two block modes:

1. a header-only recovery block that advances the Zone's Tempo checkpoint and
   performs no other execution; and
2. a full block that advances the checkpoint, processes every pending deposit
   and token enablement against the final imported Tempo state root, and may then
   execute user transactions and finalize a withdrawal batch.

Header-only blocks let a Zone recover from a long interruption without obtaining
historical recipient-specific Tempo state proofs. Pending deposits and token
enablements remain globally bounded and are processed atomically by a final full
block at a recent checkpoint.

## Motivation

A Zone may produce blocks less frequently than Tempo or stop temporarily. If a
Zone block can import only one Tempo header, the Zone must produce one block per
missed Tempo block before it can use current Tempo state.

A single multi-header call is not sufficient for arbitrarily long interruptions:
header decoding and validation consume gas linearly, and pending deposits and
token enablements share the same system-transaction budget. Splitting recovery
into ordinary full blocks would require historical Tempo state proofs at every
split point. Some of those proof keys depend on decrypted deposit recipients, so
an independent historical-proof service could not discover them without access
to sequencer secrets.

Header-only recovery blocks solve this downtime case. They authenticate and
store only header ancestry and cannot execute user-visible work. The final full
block processes the globally bounded backlog against its final, recent state
root, where the sequencer can discover and request all required proofs on demand.

# Specification

## Header Range

A header-only import contains between 1 and
`MAX_TEMPO_HEADERS_PER_ZONE_BLOCK` headers, inclusive. A full import contains
exactly one header.

```solidity
uint64 constant MAX_TEMPO_HEADERS_PER_ZONE_BLOCK = 1024;
```

Each item is the canonical RLP encoding of a Tempo header:

```text
rlp([general_gas_limit, shared_gas_limit, timestamp_millis_part, inner])
```

where `inner` is the Ethereum-compatible header defined by the active Tempo
protocol version.

Let `(storedHash, storedNumber)` be the Zone's current Tempo checkpoint. The
first imported header MUST satisfy:

```text
header[0].parent_hash == storedHash
header[0].number      == storedNumber + 1
```

Every later header `i` MUST satisfy:

```text
header[i].parent_hash == hash(header[i - 1])
header[i].number      == header[i - 1].number + 1
```

After validation, the Zone stores the hash and number of the final header as its
single Tempo checkpoint. Intermediate headers authenticate ancestry only and do
not create separately readable checkpoints. `TempoBlockFinalized` is emitted
once for the final header and contains its hash, number, and state root.

An empty or oversized array, malformed encoding, number gap, duplicate number,
or parent-hash mismatch invalidates the Zone block.

## Block Modes

The canonical Zone genesis block contains no Tempo system transaction. Every
non-genesis Zone block MUST begin with exactly one of the following system calls.

### Header-only recovery block

```solidity
function advanceTempoHeaders(bytes[] calldata headers) external;
```

`advanceTempoHeaders` validates the header range and advances only
`TempoState.tempoBlockHash` and `TempoState.tempoBlockNumber`. A block beginning
with this call:

- MUST contain no other system or user transaction;
- MUST NOT read Tempo account or storage state;
- MUST NOT process deposits or token enablements;
- MUST NOT change the processed deposit or enablement cursors;
- MUST NOT execute or finalize withdrawals.

The block may cross deposits, token enablements, sequencer-set changes, and
leadership changes because it performs no operation governed by that historical
state. Its beneficiary is not checked against the historical or final-root
leader. It MUST still be authorized as part of the batch by the versioned
sequencer-set settlement certificate.

There is no separate pending checkpoint. A successor continues from the single
checkpoint installed by the latest header-only block and may import a newer
consecutive range.

### Full block

```solidity
function advanceTempo(
    bytes calldata header,
    QueuedDeposit[] calldata deposits,
    DecryptionData[] calldata decryptions,
    EnabledToken[] calldata enabledTokens
) external;
```

The call validates and installs its single header, processes all pending token
enablements and deposits, and binds every Tempo state read in the containing Zone
block to that header's state root. After `advanceTempo` succeeds, the block
may execute user transactions. If it is the final block of a batch, it MUST end
with the existing `finalizeWithdrawalBatch` system transaction.

The full block's beneficiary MUST equal the portal's `leader` proven at the
header's root. Historical leaders and leadership transitions crossed by
preceding header-only blocks are irrelevant because those blocks are
leader-neutral and the full block performs all application work at its own root.
No `leaderTransitionHash` is introduced.

## Batch Settlement

Settlement behavior is derived from the block sequence proven by the batch; it
is not supplied as a separate mode. The proof exposes the resulting
`nextWithdrawalBatchIndex`, and the versioned sequencer-set settlement
certificate binds that index together with the existing batch outputs.

The verifier accepts exactly two shapes:

- a checkpoint batch containing only header-only recovery blocks, for which
  `nextWithdrawalBatchIndex == ZonePortal.withdrawalBatchIndex`; or
- an operational batch ending in a full block, for which
  `nextWithdrawalBatchIndex == ZonePortal.withdrawalBatchIndex + 1`.

Any other block shape or resulting index is invalid.

### Checkpoint settlement

A checkpoint batch contains only header-only recovery blocks and may therefore
end with `advanceTempoHeaders`. Its proof commits the resulting Zone block hash
and Tempo checkpoint, but MUST prove that:

- the processed deposit hash and number are unchanged;
- the processed token-enablement hash and count are unchanged;
- `ZoneOutbox.lastBatch` is unchanged; and
- the submitted withdrawal queue hash is zero.

After accepting a checkpoint settlement, `ZonePortal` updates its settled Zone
block hash, `lastSyncedTempoBlockNumber`, and Zone height. It MUST NOT increment
`withdrawalBatchIndex`, enqueue a withdrawal root, or change either processed
cursor. This keeps the portal and `ZoneOutbox.lastBatch` synchronized across any
number of checkpoint settlements.

The proof's deposit and token-enablement transitions MUST be identity
transitions. Their previous values are authenticated from the previously settled
Zone state, and their numeric cursors MUST equal the portal's corresponding
processed cursors. The proof MUST expose the unchanged
`ZoneOutbox.lastBatch.withdrawalBatchIndex` as `nextWithdrawalBatchIndex`.

### Operational settlement

An operational batch ends in a full block. Header-only recovery blocks may
precede it. The final full block MUST end with the existing
`finalizeWithdrawalBatch` system transaction, including an empty finalization
when there are no withdrawals. The portal then applies the deposit and token
enablement transitions and advances the withdrawal batch exactly as under the
existing settlement rules. The proof exposes the incremented
`ZoneOutbox.lastBatch.withdrawalBatchIndex` as `nextWithdrawalBatchIndex`.

These two derived paths let a long recovery settle authenticated header progress
in bounded chunks. A successor can resume from the latest settled checkpoint,
while only an operational settlement needs recipient-specific Tempo state proofs
and decryption data.

## Bootstrap

`advanceTempoHeaders` MUST NOT be used while the stored Tempo checkpoint hash is
zero. The first non-genesis block after canonical Zone genesis MUST be a full
block.

For that first import, ordinary parent continuity is unavailable. The batch proof
MUST prove against the final imported state root that the portal exists and has a
nonempty sequencer configuration. The proof then installs the final header as the
initial Tempo checkpoint and processes all portal work visible at that root.

## Final-root Tempo Reads

Only a full block may perform Tempo state reads. Every read made by
`advanceTempo`, a later user transaction, or the final withdrawal system
transaction MUST be proven against that block's final imported state root.

This includes, as applicable:

- the portal's deposit queue head;
- its token-enablement sequence and processed bounds;
- encryption-key slots used by encrypted deposits;
- TIP-20 registry and TIP-403 policy state;
- the final-root leader; and
- every other account or storage key reached by Zone execution.

Intermediate headers and header-only blocks require no MPT state proofs. Each
witnessed read MUST identify the Zone block index, final imported Tempo block
number, account, derived storage slot, and value. Missing witness data, a block
number mismatch, or an invalid trie proof is an error.

## Atomic Deposit Processing

In a full block, `advanceTempo` starts from the Zone's processed deposit queue
hash and processes supplied deposits oldest-first. Every policy decision and
encryption-key read uses the final imported Tempo root, including for deposits
enqueued before a preceding header-only block.

The reconstructed queue hash MUST equal the portal's
`currentDepositQueueHash` at the final root. A valid prefix is insufficient. A
mismatch reverts the complete system transaction, including the new checkpoint,
token activations, deposit mints, bounce-backs, events, and every other side
effect.

## Outstanding Deposit Capacity

Each portal enforces:

```solidity
uint64 constant MAX_UNPROCESSED_DEPOSITS = 230;
uint64 constant WITHDRAWAL_BOUNCEBACK_RESERVE = 20;
```

Before appending an item, the portal computes:

```text
unprocessed = depositCount - lastProcessedDepositNumber
```

An ordinary deposit is rejected when `unprocessed` has reached
`MAX_UNPROCESSED_DEPOSITS - WITHDRAWAL_BOUNCEBACK_RESERVE`. A withdrawal
bounce-back is rejected when `unprocessed` has reached
`MAX_UNPROCESSED_DEPOSITS`.

Before processing a withdrawal batch, the portal conservatively assumes that
every withdrawal fails and produces a bounce-back. With:

```text
remainingCapacity = MAX_UNPROCESSED_DEPOSITS - unprocessed
```

the call rejects `withdrawals.length > remainingCapacity` before processing any
withdrawal. A failed call leaves both queues unchanged.

The value 230 is the measured upper bound for processing the worst-case deposit
queue within 200,000,000 gas. The 20 reserved entries cover one maximum-size
withdrawal batch under the existing Zones limits.

The header, deposit, and token bounds are not independent gas allowances. The
combined worst case of one imported header,
`MAX_UNPROCESSED_DEPOSITS` deposits, and
`MAX_UNPROCESSED_TOKEN_ENABLEMENTS` token enablements MUST fit within the full
block's 225,000,000 gas ceiling. The measured worst case of 230 deposits and 8
maximum-metadata enablements uses 214,832,282 gas. Recovery remains live at that
combination because the sequencer can use header-only blocks until exactly one
header remains for the full block.

## Outstanding Token Enablement Capacity

Token enablement changes from a per-Tempo-block limit to a global outstanding
limit:

```solidity
uint64 constant MAX_UNPROCESSED_TOKEN_ENABLEMENTS = 8;
```

The portal maintains:

```text
enabledTokenCount
lastProcessedEnabledTokenCount
```

Before enabling a token, it requires:

```text
enabledTokenCount - lastProcessedEnabledTokenCount
    < MAX_UNPROCESSED_TOKEN_ENABLEMENTS
```

The existing append-only `_enabledTokens` array defines canonical enablement
order. A full `advanceTempo` MUST process the complete unprocessed suffix visible
at its final root. The proof verifies the supplied token addresses against that
array in order and verifies the metadata and policy state used for Zone token
initialization against the same root.

The Zone stores `processedEnabledTokenCount`. A full block starts at that Zone
count, not at the portal's last-settled count, and processes every array entry up
to `enabledTokenCount` at the final root. This prevents replay when several full
blocks execute before their containing batch is submitted.

The batch proof exposes the transition from the previously settled count to the
final Zone count. It requires the previous count to equal the portal's
`lastProcessedEnabledTokenCount`, and `submitBatch` updates the portal count only
after accepting the proof. A header-only block advances neither count. Skipping,
reordering, replaying, or partially processing that suffix is invalid.

Existing portals initialize `lastProcessedEnabledTokenCount` at activation to
the number of tokens already confirmed by their latest accepted Zone state. The
activation procedure MUST derive or configure this value consistently with each
Zone's state; it MUST NOT reopen already processed enablements or mark an
unprocessed token as processed.

## Interface and Proof Changes

`IZoneInbox` adds:

```solidity
function advanceTempoHeaders(bytes[] calldata headers) external;
```

`IZoneInbox.advanceTempo(bytes calldata header, ...)` remains single-header.

`ITempoState.finalizeTempo(bytes[] calldata headers)` validates a bounded range,
stores only its final hash and number, and emits only its final-header event. It
is callable only through the authorized Zone system path. `advanceTempoHeaders`
passes its complete range to `finalizeTempo`; `advanceTempo` passes a one-element
array. An empty or oversized array reverts before changing the checkpoint.

`IZonePortal.MAX_DEPOSITS_PER_TEMPO_BLOCK()` is replaced by
`MAX_UNPROCESSED_DEPOSITS()`. The portal additionally exposes
`MAX_UNPROCESSED_TOKEN_ENABLEMENTS()` and
`lastProcessedEnabledTokenCount()`.

The Zone block witness identifies whether its opening system transaction is
header-only or full. The batch proof enforces the corresponding block-shape
rules, final-root read rules, deposit transition, token-enablement count
transition, final leader check, and derived settlement behavior.
`ZonePortal.submitBatch` and its settlement attestation add
`nextWithdrawalBatchIndex`. A checkpoint settlement requires the current index
and leaves withdrawal and processed-cursor state unchanged; an operational
settlement requires the next index and applies the existing transitions.

## Activation and Compatibility

The activation updates `ZonePortal`, `ZoneInbox`, `TempoState`, the Zone block
witness, state-transition function, and verifier atomically.
Existing Zone checkpoint and deposit state are retained. Token-enablement cursors
are initialized as specified above.

The existing `IZoneInbox.advanceTempo(bytes,...)` ABI remains unchanged.
`IZoneInbox.advanceTempoHeaders(bytes[])` is new, and
`ITempoState.finalizeTempo(bytes)` is replaced by
`ITempoState.finalizeTempo(bytes[])`. The block witness, settlement proof
statement, settlement attestation, and portal storage also change. Sequencers,
provers, verifiers, RPC encoders, block decoders, and canonical runtimes MUST
switch at the same activation boundary. Pre-activation blocks retain their
active protocol-version rules.

# Tooling

Payload builders and block decoders MUST represent the opening Tempo system
transaction as an explicit header-only or full variant. Inferring the mode from
empty deposit arrays is invalid because a full block may legitimately process no
deposits or token enablements.

During recovery, the sequencer MUST:

1. reserve one finalized Tempo header for the next full block;
2. split every earlier consecutive header into bounded header-only blocks;
3. optionally prove and submit one or more checkpoint batches;
4. collect the complete deposit and token-enablement suffix since the last full
   block; and
5. decrypt deposits and obtain Tempo state proofs only for the single header
   imported by the full block.

Follower validation, RPC block extraction, fixtures, and proof-input encoders
MUST decode both Inbox selectors and enforce their distinct block shapes. Prover
tooling MUST support identity deposit and token transitions for checkpoint
settlements and MUST omit Tempo MPT witness nodes when a checkpoint batch
performs no Tempo reads.

Operator tooling SHOULD report the settled Tempo checkpoint separately from the
last operational checkpoint at which deposits, enablements, and withdrawals were
processed. Recovery status SHOULD include the number of pending headers,
deposits, and token enablements and the remaining capacity for each bounded
sequence.

# Observability

`TempoBlockFinalized(bytes32 blockHash, uint64 blockNumber, bytes32 stateRoot)`
continues to be emitted once per `finalizeTempo` call and refers only to the final
header in its array. Intermediate headers do not emit events. An observer can
distinguish header-only and full blocks from the opening Inbox transaction
selector.

The existing `ZonePortal.BatchSubmitted.withdrawalBatchIndex` field remains
unchanged for a checkpoint settlement and increments for an operational
settlement. Together with the processed cursors and final Tempo block number,
this identifies whether a submission only advanced header ancestry or also
processed cross-domain work. No separate settlement-mode event field is needed.

The portal MUST expose `lastProcessedEnabledTokenCount` alongside the existing
deposit and withdrawal cursors. Implementations SHOULD alert when either
outstanding-work count approaches its global cap, when recovery repeatedly
submits checkpoint batches without an operational settlement.

# Invariants

- Every non-genesis Zone block begins with exactly one bounded Tempo header
  import whose first header extends the stored checkpoint.
- Header hashes and numbers form one consecutive chain across and within Zone
  blocks.
- A header-only block changes only the Tempo checkpoint and contains no other
  transaction or Tempo state read.
- A checkpoint batch contains only header-only blocks and changes no deposit,
  token-enablement, or withdrawal state.
- An operational batch ends in a full block and advances the withdrawal batch.
- `nextWithdrawalBatchIndex` equals the current portal index for a checkpoint
  batch and exactly the next index for an operational batch.
- Only a full block is checked against the final-root leader, and all application
  execution in that block uses the same final imported Tempo root.
- A successful full block processes exactly the complete pending deposit queue
  and token-enablement suffix visible at its final root.
- Public deposits cannot consume the withdrawal bounce-back reserve.
- Outstanding deposits never exceed `MAX_UNPROCESSED_DEPOSITS`.
- Outstanding token enablements never exceed
  `MAX_UNPROCESSED_TOKEN_ENABLEMENTS`.
- A failed system transaction changes no checkpoint, cursor, queue, token,
  balance, receipt, or event state and invalidates its containing Zone block.

Critical tests MUST cover header-only and full block shapes, empty and oversized
arrays, continuity failures across block boundaries, bootstrap restrictions,
leadership changes crossed by header-only blocks, final-root leader rejection,
exact and partial pending-work processing, both global capacity boundaries,
worst-case combined header and pending-work gas, missing Tempo reads, settlement
of checkpoint batches, rejection of mixed checkpoint batches, repeated
checkpoint settlements without withdrawal-index drift, forged or skipped next
withdrawal indices, and full rollback after each failure class.
