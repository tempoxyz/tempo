# TIP-1114: Native Multisig Accounts

## Abstract

A native multisig account is controlled by a weighted owner quorum. Its address stays fixed when its owners change. A 1-of-1 configuration provides ordinary key rotation using the same rules as a larger multisig.

This TIP defines signatures and transaction authorization. [TIP-1108](./tip-1108.md) stores the configuration hash, [TIP-1109](./tip-1109.md) changes owners, and [TIP-1110](./tip-1110.md) derives the address.

## Motivation

Users should not need to move funds or application permissions when replacing a key. Native authorization also lets the account pay its own transaction fees without a separate executor.

## Assumptions

The account has no EVM code or EIP-7702 delegation. Primitive signatures follow Tempo's existing secp256k1, P256, and WebAuthn rules. Hash collisions and discovery of a primitive key for a counterfactual address are outside the T12 security model; [TIP-1112](./tip-1112.md) later rejects bare root authority for nonzero commitments.

## Threat Model

Submitters can supply malformed witnesses, stale owners, duplicate signatures, or an invalid final signature. Validation must bound both parsing and cryptographic work before accepting authority. A valid encoding or recovered address alone is not proof of authorization.

# Specification

## Configuration and limits

A configuration contains `salt: bytes32`, `version: uint64`, `threshold: uint8`, and a list of `(owner: address, weight: uint8)` pairs.

- There are 1–48 unique, nonzero owners, sorted by ascending address. Each weight is nonzero and their sum is at most 255.
- The threshold is 1–8 and must not exceed the total owner weight. A signature carries 1–8 primitive owner signatures. These are separate limits: an account may have more than eight owners.
- Owners sign as primitive keys. Nested multisig and keychain owner signatures are rejected, in both T12 and T13.
- Each primitive signature uses its existing encoding and size limit; an encoded owner signature is at most 2,049 bytes.
- Version zero denotes the initial derived configuration. Positive versions denote committed configurations. An initial configuration cannot name its derived account as an owner. Positive versions may name the account's primitive root as an explicit owner, as needed for migration.

The threshold cap of eight is this draft's literal interpretation of the review decision. It replaces the old draft's 255 threshold, not its 48-owner limit. Review must confirm this interpretation and benchmark the eight-signature worst case, including rejection on the final signature.

## Encoding and signing

```text
signature = 0x05 || rlp([account, config, signatures])
config    = [salt, version, threshold, owners]
owner     = [address, weight]
multisig_digest(inner_digest, account, version) = keccak256("tempo:multisig:signature" || inner_digest || account || uint64(version))
```

`signatures` is a list of byte strings containing primitive Tempo signatures. Integers in the digest are fixed-width big-endian; the domain is raw ASCII and the address is 20 bytes. For a direct transaction, `inner_digest` is its existing transaction signing hash. [TIP-1111](./tip-1111.md) defines T13 delegation contexts.

Use canonical RLP and reject trailing fields, invalid lengths, and limit violations before verification. Exactly 65 signature bytes always decode as secp256k1, regardless of their first byte. Type `0x05` is rejected before T12.

## Authorization

1. Reject an account with EVM code or EIP-7702 delegation. Read its configuration hash at the transaction's position in the block.
2. If zero, require version zero and the TIP-1110 derivation to equal `account`. If nonzero, require a positive version and an exact TIP-1108 commitment match.
3. Verify owner signatures over `digest`. Recovered owners must appear in strictly ascending order and belong to the supplied configuration.
4. Sum their weights. The final signature must reach threshold; reject insufficient quorum and any signature after threshold is reached.

State-independent recovery may validate the shape and return `account`, but consensus must perform all four steps. Balance, storage, and a nonzero transaction nonce do not prevent initial authorization. Initial use writes no configuration state and may repeat until the first update.

## Transaction behavior

The account is `tx.from`, `tx.origin`, and the top-level `msg.sender`. One quorum authorizes the complete call batch. Existing nonce, fee-token, sponsorship, and transaction signing rules apply. A fee payer supplies the existing secp256k1 sponsorship signature and gains no account authority.

In T12, multisig signatures are allowed only as the outer signature. Reject them in subblocks, authorization lists, access-key envelopes, and signed key authorizations. A directly multisig-signed T12 transaction must not carry `key_authorization`. Keychain transactions with a nonzero-commitment parent are also rejected before T13. Bare multisig signatures remain unsupported by stateless TIP-1020 `recover` and `verify`.

Primitive authorization-list entries retain existing behavior; keychain-signed entries retain their existing skip behavior. No new transaction fields are added. Non-multisig transactions retain their existing encoding. T13 changes only the contexts explicitly enabled by TIP-1111 and the root-authority checks in TIP-1112.

## Gas and validation cost

Define `K(n) = 30 + 6 * ceil(n / 32)` and let `calldata_gas` use the active calldata schedule. Multisig verification cost is:

```text
V(signature, inner_digest) =
    calldata_gas(rlp(account) || rlp(config))
  + configuration_proof_hash_cost
  + K(84)
  + sum(primitive_signature_cost)
```

The digest preimage is 84 bytes. For version zero, the proof hash cost is `K(56 + 21 * owner_count) + K(85)` for TIP-1110 derivation; otherwise it is `K(63 + 21 * owner_count)` for the commitment. Primitive costs are 3,000 for secp256k1, 8,000 for P256, and 8,000 plus the existing WebAuthn-data calldata charge for WebAuthn.

Add `V - 3,000` to ordinary intrinsic gas, subtracting the already-included base signature cost exactly once. There is no separate precompile storage read and no keychain processing buffer for direct authorization. Compute intrinsic gas and check fee affordability before owner cryptography. Gas charging does not replace the unpaid-work limits.

# Tooling

SDKs must build witnesses, collect ordered signatures, and reconstruct configurations from initial signatures and update events. Pools must revalidate affected transactions after commitment changes or reorgs. RPC simulation must use the same stateful authorization rules and report the state against which it simulated.

# Observability

No new event for initial use: its signature carries the initial configuration. Owner changes emit the event in TIP-1109. The hash alone cannot reconstruct an owner list.

# Invariants

Test stable sender identity, 1-of-1 and weighted quorum, exact bounds, duplicate/unsorted/extra signatures, rejected nesting, stale configurations, replay across accounts and versions, sponsorship, pre-activation rejection, same-block rotation, and reorg revalidation. Invalid witnesses never authorize spending.
