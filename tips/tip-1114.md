# TIP-1114: Native Multisig Accounts

## Abstract

A native multisig account has a set of owners. Each owner has a weight, and approvals must meet the account's threshold.

- The address stays the same when owners change.
- A 1-of-1 account uses the same rules with just one owner.

This TIP defines signatures and transaction authorization. The other components define:

- [TIP-1108](./tip-1108.md): storing the configuration hash.
- [TIP-1109](./tip-1109.md): changing owners.
- [TIP-1110](./tip-1110.md): deriving the address.

## Motivation

Users should not need to move funds or application permissions when replacing a key. Native authorization also lets the account pay its own transaction fees without a separate executor.

## Assumptions

- The account has no EVM code or EIP-7702 delegation.
- Owners use Tempo's existing secp256k1, P256, or WebAuthn signatures.
- T12 assumes no hash collisions and no discovery of a primitive private key for a derived account address.
- [TIP-1112](./tip-1112.md) adds bare root-key rejection for accounts with nonzero commitments in T13.

## Threat Model

A submitted signature may contain:

- Malformed data.
- An outdated owner configuration.
- Duplicate owner signatures.
- An invalid signature at the end of the list.

Validation must bound parsing and cryptographic work. Correct encoding or a recovered address alone does not prove authority to spend.

# Specification

## Configuration and limits

A configuration contains:

| Field | Type | Meaning |
| --- | --- | --- |
| `salt` | `bytes32` | A fixed value used in address derivation and configuration hashing. |
| `version` | `uint64` | Zero for the initial configuration. Updates use increasing positive versions. |
| `threshold` | `uint8` | The total approval weight needed to authorize an operation. |
| `owners` | List of `(address, uint8 weight)` | The keys that can approve and the weight of each approval. |

### Owners and approvals

- An account has 1–48 owners.
- Owner addresses must be nonzero, unique, and sorted in ascending order.
- Each owner has a nonzero weight.
- The sum of all owner weights must be at most 255.
- The threshold must be 1–8 and cannot exceed the total owner weight.
- A signature contains 1–8 primitive owner signatures.

The owner limit and signature limit are separate. An account can have more than eight owners, but an operation uses at most eight signatures.

Owners sign using primitive keys.

- Nested multisig and keychain owner signatures are rejected in both T12 and T13.
- Each primitive signature keeps its existing encoding and size limit.
- An encoded owner signature is at most 2,049 bytes.

### Configuration versions

- Version zero is the initial configuration used to derive the address.
- Positive versions are configurations whose hashes have been stored in the account leaf.
- The initial configuration cannot list its derived account address as an owner.
- A positive-version configuration may explicitly list the account's primitive root as an owner. This supports migration with the existing key.

### Draft review point

The threshold cap of eight is this draft's literal interpretation of the review decision.

- It replaces the old draft's threshold cap of 255.
- The 48-owner limit remains.
- Review must confirm this interpretation.
- Benchmarks must cover eight signatures, including an invalid final signature.

## Encoding and signing

```text
signature = 0x05 || rlp([account, config, signatures])
config    = [salt, version, threshold, owners]
owner     = [address, weight]
multisig_digest(inner_digest, account, version) = keccak256("tempo:multisig:signature" || inner_digest || account || uint64(version))
```

- `signatures` is a list of byte strings containing primitive Tempo signatures.
- Encode integers in the digest as fixed-width big-endian values.
- Encode the domain as raw ASCII and the account address as 20 bytes.
- For a direct transaction, `inner_digest` is the existing transaction signing hash.
- [TIP-1111](./tip-1111.md) defines the T13 delegation signing contexts.

Before verifying signatures:

- Require canonical RLP.
- Reject trailing fields, invalid lengths, and limit violations.
- Decode an exactly 65-byte signature as secp256k1, regardless of its first byte.
- Reject signature type `0x05` before T12.

## Authorization

### Check the account and configuration

Reject accounts with EVM code or EIP-7702 delegation. Read the configuration hash at the transaction's position in the block.

If the stored hash is zero:

- Require configuration version zero.
- Derive the address using TIP-1110 and require it to equal `account`.

If the stored hash is nonzero:

- Require a positive configuration version.
- Require the TIP-1108 configuration hash to match the stored commitment exactly.

### Check the owner approvals

- Verify each owner signature over `multisig_digest`.
- Require recovered owner addresses in strictly ascending order.
- Require each signer to belong to the supplied configuration.
- Add the signers' weights.
- The final signature must reach the threshold.
- Reject insufficient approval weight or any signature after the threshold is reached.

### Initial use

An account can use its initial configuration even if it already has a balance, storage, or a nonzero transaction nonce.

Initial authorization writes no configuration state. It may repeat until the first configuration update.

State-independent recovery may check the signature's shape and return `account`. Consensus must still perform all account, configuration, and approval checks above.

## Transaction behavior

### Sender and fees

- The account is `tx.from`, `tx.origin`, and the top-level `msg.sender`.
- One owner quorum authorizes the complete call batch.
- Existing nonce, fee-token, sponsorship, and transaction signing rules apply.
- A separate fee payer uses the existing secp256k1 sponsorship signature.
- Sponsoring fees gives no authority over the account.

### Supported signature contexts

In T12, multisig signatures are allowed only as the outer transaction signature.

Reject them in:

- Subblocks.
- Authorization lists.
- Access-key envelopes.
- Signed key authorizations.

Additional restrictions:

- A directly multisig-signed T12 transaction must not carry `key_authorization`.
- Before T13, reject keychain transactions whose parent has a nonzero configuration commitment.
- Stateless TIP-1020 `recover` and `verify` do not support bare multisig signatures.

Primitive authorization-list entries keep their existing behavior. Keychain-signed entries keep their existing skip behavior.

No new transaction fields are added. Non-multisig transactions keep their existing encoding.

T13 adds only the signature contexts defined in TIP-1111 and root-authority checks defined in TIP-1112.

## Gas and validation cost

Use `K(n) = 30 + 6 * ceil(n / 32)` for hashing `n` bytes. Use the active calldata schedule for `calldata_gas`.

Multisig verification costs:

```text
V(signature, inner_digest) =
    calldata_gas(rlp(account) || rlp(config))
  + configuration_proof_hash_cost
  + K(84)
  + sum(primitive_signature_cost)
```

The signing digest has an 84-byte preimage.

The configuration proof cost depends on the version:

- Version zero: `K(56 + 21 * owner_count) + K(85)` for TIP-1110 address derivation.
- Positive versions: `K(63 + 21 * owner_count)` for the configuration commitment.

Primitive signature costs are:

| Signature | Gas |
| --- | --- |
| secp256k1 | 3,000 |
| P256 | 8,000 |
| WebAuthn | 8,000 plus the existing WebAuthn-data calldata charge |

Add `V - 3,000` to ordinary intrinsic gas. The subtraction removes the base signature cost already included in ordinary gas, exactly once.

- Direct authorization adds no separate precompile storage read or keychain processing buffer.
- Compute intrinsic gas and check fee affordability before verifying owner signatures.
- Gas charging does not replace the limits on unpaid validation work.

# Tooling

SDKs must:

- Build witnesses containing the configuration and approvals.
- Collect signatures in owner-address order.
- Reconstruct configurations from initial signatures and update events.

Transaction pools must revalidate affected transactions after commitment changes or reorgs.

RPC simulation must use the same stateful authorization rules. It must report the state used for simulation.

# Observability

- Initial use emits no new event. Its signature carries the initial configuration.
- Owner changes emit the TIP-1109 event.
- The configuration hash alone cannot reconstruct the owner list.

# Invariants

- Keep the sender address stable through owner changes.
- Support 1-of-1 and weighted approvals.
- Enforce every owner, threshold, size, and signature limit.
- Reject duplicate, unsorted, extra, or nested signatures.
- Reject outdated configurations and replay across accounts or versions.
- Preserve sponsorship behavior.
- Reject multisig signatures before activation.
- Test same-block rotation and reorg revalidation.
- Never authorize spending with an invalid witness.
