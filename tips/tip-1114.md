# TIP-1114: Native Multisig Accounts

## Abstract

This TIP adds native accounts with weighted owners and a stable address. An account has 1–48 owners, and each operation uses at most eight primitive signatures whose combined weight reaches its threshold. A 1-of-1 account follows the same rules.

Owners sign a witness containing the account's full configuration. The protocol checks that witness against the account-leaf commitment. First use registers the initial configuration before transaction calls execute, even when their execution later fails. Subsequent owner changes preserve the address.

This TIP defines transaction authorisation and stateful on-chain signature verification. Owners use existing secp256k1, P256, or WebAuthn signatures; recursive multisig owners are excluded. TIP-1108 defines commitment storage, TIP-1109 defines owner updates, and TIP-1110 defines address derivation. TIP-1111 extends the mechanism to access-key grants and use.

## Motivation

Users need to replace keys without moving funds or application permissions. They also need the account to pay its own transaction fees without a separate executor.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| Owners use Tempo's existing secp256k1, P256, or WebAuthn signature schemes. | A new owner scheme would need separate encoding, verification, and cost rules. |
| An attacker cannot discover a primitive private key for an unregistered derived account address. | Before registration, a zero commitment does not retire that primitive root's authority. |

# Specification

## Overview

A **configuration** contains a fixed salt, a version, an approval threshold, and weighted owner addresses. A **quorum** is a set of owner approvals whose weights reach the threshold. Each signature witness carries the configuration and the primitive owner signatures.

| Stage | Authority and state |
|---|---|
| Derive an address | TIP-1110 derives it from the initial configuration; nothing is registered yet. |
| First included transaction | Validate the initial quorum and register version zero before calls execute. |
| Later transaction | Match the stored commitment and validate the current quorum. |
| Owner update | TIP-1109 replaces the configuration at the same address. |
| On-chain verification | Check current authority without registering or changing the account. |

For example, three owners in address order have weights 2, 1, and 1, with threshold 3. The first two signatures contribute 3 and authorise the operation. The last two contribute only 2 and fail. The first included transaction registers this configuration at version zero even if its execution later reverts.

Native authorisation covers direct transactions and TIP-1111 access-key flows. It does not add multisig signatures to subblocks, authorisation lists, or separate fee-payer signatures. The related TIPs define storage, rotation, and address recovery.

## Configuration and limits

### Owners and approvals

- An account has 1–48 owners.
- Owner addresses must be nonzero, unique, and sorted in ascending order.
- Each owner has a nonzero weight.
- The sum of all owner weights must be at most 255.
- The threshold must be 1–255 and must be reachable with at most eight owners: the sum of the eight largest owner weights (or all owners if fewer than eight) must meet the threshold.
- A signature contains 1–8 primitive owner signatures.

The owner limit and signature limit are separate. An account can have more than eight owners, but an operation uses at most eight signatures.

Owners sign using primitive keys.

- Nested multisig and keychain owner signatures are rejected.
- Each primitive signature keeps its existing encoding and size limit.
- An encoded owner signature is at most 2,049 bytes.

### Configuration versions

- Version zero is the initial configuration used to derive the address.
- First use stores the version-zero hash. Positive versions represent later updates or migration.
- The initial configuration cannot list its derived account address as an owner.
- A positive-version configuration may explicitly list the account's primitive root as an owner. This supports migration with the existing key.

## Encoding and signing

Encode a multisig signature as the `0x05` prefix followed by a Recursive Length Prefix (RLP) list containing the account, configuration, and owner signatures.

```text
signature = 0x05 || rlp([account, config, signatures])
config    = [salt, version, threshold, owners]
owner     = [address, weight]
multisig_digest(inner_digest, account, version) = keccak256("tempo:multisig:signature" || inner_digest || account || uint64(version))
```

- `signatures` is a list of byte strings containing primitive Tempo signatures.
- Encode integers in the digest as fixed-width big-endian values.
- Encode the domain as raw ASCII and the account address as 20 bytes.
- For a direct transaction, `inner_digest` is the existing transaction signing hash.
- [TIP-1111](./tip-1111.md) defines the delegation signing contexts.

Before verifying signatures:

- Require canonical RLP encoding.
- Reject trailing fields, invalid lengths, and limit violations.
- Decode an exactly 65-byte signature as secp256k1, regardless of its first byte.
- Reject signature type `0x05` before activation.

## Authorization

### Check the account and configuration

Reject accounts with EVM code or EIP-7702 delegation. Read the configuration hash at the transaction's position in the block.

If the stored hash is zero:

- Require configuration version zero.
- Derive the address using TIP-1110 and require it to equal `account`.
- Compute the TIP-1108 configuration hash and reject a zero result.

If the stored hash is nonzero:

- Accept version zero or a positive version.
- Require the TIP-1108 configuration hash to match the stored commitment exactly.

### Check the owner approvals

- Verify each owner signature over `multisig_digest`.
- Require recovered owner addresses in strictly ascending order.
- Require each signer to belong to the supplied configuration.
- Add the signers' weights.
- The final signature must reach the threshold.
- Reject insufficient approval weight or any signature after the threshold is reached.

### Initial use

An account can use its initial configuration even if it already has a balance, storage, or a nonzero transaction nonce.

After all transaction validation and authorization checks pass and fee collection succeeds, register each configurable account whose commitment is still zero:

- Write its version-zero configuration hash before executing any transaction calls, outside the execution rollback checkpoint.
- Precompiles and the TIP-1109 getter see the nonzero hash during those calls.
- Keep the initial registration even if a subcall or the entire transaction execution reverts or halts. The registration has been authorized and its write cost paid through intrinsic gas. Normal fee and nonce rules still apply.
- A later owner update may replace the initial hash in the same transaction. That update follows ordinary execution rollback rules: if execution rolls it back, restore the initial hash rather than zero. It must never clear the hash.

After an included transaction, every configurable account that authorized it has a nonzero commitment, regardless of execution success. This includes configurable parents signing key authorizations and configurable delegates signing access-key transactions.

Receiving funds or deriving an address does not register the account. Simulation applies registration only to its temporary state.

A transaction rejected as invalid does not register any account. An account that has not yet authorized an included transaction may still have a zero hash.

State-independent recovery may check the signature's shape and return `account`. Consensus must still perform all account, configuration, and approval checks above.

### Failure behavior

For a valid, included transaction whose execution reverts or halts:

| Change | Result |
|---|---|
| Initial multisig registration | Persists |
| Owner/threshold update | Rolls back, including its event |

Access keys use the same rollback boundary: an inline `key_authorization` persists, but a grant made through a precompile call rolls back.

For a worked example with an owner update, see [TIP-1109's Overview](./tip-1109.md#overview).

A failed batch rolls back all user-call changes, including earlier successful calls. A transaction rejected as invalid commits none of these changes.

## On-chain signature verification

From activation, [TIP-1020](./tip-1020.md)'s `SignatureVerifier` precompile exposes `verifyMultisig(account, hash, signature)`. It checks a multisig signature without changing state. The full interface is [below](#interfaces).

- Accept the `0x05` signature format, with owners signing `multisig_digest(hash, account, config.version)`.
- Apply the authorization rules above against state at call time. For an unregistered account, verify against the supplied initial configuration and require it to derive the account's address. Verification does not register the account.
- Return `false` for an embedded-account or stored-commitment mismatch, address-derivation failure, or an account with code or EIP-7702 delegation. Otherwise, return `true` after successful verification.
- Revert with `InvalidFormat()` for encoding/configuration errors and `InvalidSignature()` for owner-approval errors.
- Charge standard precompile input and account-access costs plus `V(signature, hash)`, without the transaction's 3,000-gas subtraction or registration write charge.

TIP-1049's `verifyKeychain` and `verifyKeychainAdmin` accept only primitive inner signatures. They revert with `InvalidFormat()` for a V2 keychain signature whose inner signature uses the `0x05` format. Shape-only recovery would otherwise let a forged signature naming the parent pass the root-key check. [TIP-1137](https://github.com/tempoxyz/tempo/pull/8204) makes `verifyKeychainAdmin` root-only, subject to TIP-1112's root-retirement check.

## Gas and validation cost

Use `K(n) = 30 + 6 * ceil(n / 32)` for hashing `n` bytes. Use the active calldata schedule for `calldata_gas`.

Multisig verification costs:

```text
V(signature, inner_digest) =
    calldata_gas(rlp(account) || rlp(config))
  + configuration_proof_hash_cost
  + K(84)
  + sum(primitive_signature_cost)
```

The configuration proof cost depends on whether the account is registered:

- Zero stored hash: `K(56 + 21 * owner_count) + K(85)` for address derivation, plus `K(63 + 21 * owner_count)` for the initial commitment.
- Nonzero stored hash: `K(63 + 21 * owner_count)` to check the commitment, including version zero.

Add TIP-1108's zero-to-nonzero write cost to intrinsic gas for each account being registered. Charge the write once per account, even if it appears in more than one authorization role.

If an account being registered is empty (zero nonce, zero balance, no code), registration creates it. Also charge TIP-1000's new-account cost for that account, including its state-gas portion. Skip this charge only when the account is the transaction sender and another TIP-1000 charge already pays for creating it:

- With `nonce_key == 0`, the `nonce == 0` charge pays for the protocol nonce write that creates the account.
- With a 2D or expiring nonce, a first-call `CREATE` from a sender with account nonce zero already pays TIP-1000's new-account cost.

With a 2D nonce key, the `nonce == 0` charge pays for the new nonce-key slot, not the account, so registration still charges the new-account cost.

Primitive signature costs are:

| Signature | Gas |
| --- | --- |
| secp256k1 | 3,000 |
| P256 | 8,000 |
| WebAuthn | 8,000 plus the existing WebAuthn-data calldata charge |

Add `V - 3,000` to ordinary intrinsic gas. The subtraction removes the base signature cost already included in ordinary gas, exactly once.

- Direct authorization adds no separate precompile storage read or keychain processing buffer.
- Compute intrinsic gas and check fee affordability before verifying owner signatures.
- Gas charging does not replace the limits on unpaid validation work.

## Changes to other components

### Sender and fees

- The account is `tx.from`, `tx.origin`, and the top-level `msg.sender`.
- One owner quorum authorizes the complete call batch.
- Existing nonce, fee-token, sponsorship, and transaction signing rules apply.
- A separate fee payer uses the existing secp256k1 sponsorship signature.
- Sponsoring fees gives no authority over the account.

### Supported signature contexts

From activation, multisig signatures are supported in:

- Outer transaction signatures.
- Access-key envelopes under TIP-1111.
- Signed key authorizations under TIP-1111.

A transaction may grant access and use it immediately. TIP-1111 defines the combined verification limit.

Reject multisig signatures in subblocks and authorization lists. Stateless TIP-1020 `recover` and `verify` do not support bare multisig signatures.

Primitive authorisation-list entries retain their existing encoding and apply TIP-1112's root-authority checks. Keychain-signed entries keep their existing skip behaviour.

No new transaction fields are added. Non-multisig transactions keep their existing encoding.

The root-authority checks defined in [TIP-1112](./tip-1112.md) apply from T14, together with native multisig authorisation.

## Interfaces

### Configuration fields

The configuration encodes `salt`, `version`, `threshold`, and `owners` in that order. Each owner encodes an address followed by its weight. The signature encoding is defined under [Encoding and signing](#encoding-and-signing).

| Field | Type | Meaning |
| --- | --- | --- |
| `salt` | `bytes32` | A fixed value used in address derivation and configuration hashing. |
| `version` | `uint64` | Zero for the initial configuration. Updates use increasing positive versions. |
| `threshold` | `uint8` | The total approval weight needed to authorize an operation. |
| `owners` | List of `(address, uint8 weight)` | The keys that can approve and the weight of each approval. |

### Signature verifier

```solidity
function verifyMultisig(
    address account,
    bytes32 hash,
    bytes calldata signature
) external view returns (bool);
```

# Rationale

## Signature limits

- **Limit:** At most 8 signatures per quorum. Weights and thresholds may exceed 8, provided the threshold is reachable with 8 or fewer signatures.
- **Direct transaction:** P256/WebAuthn verification costs 8,000 gas per signature: **8 × 8,000 = 64,000 gas**. A secp256k1 fee-payer signature adds 3,000, totaling **67,000 gas**.
- **Grant and use an access key:** The parent signs the grant and the delegate signs the transaction. Two full quorums plus a fee payer cost **16 × 8,000 + 3,000 = 131,000 gas**.

Invalid transactions pay no fees, so the signature cap bounds unpaid verification work. These costs exclude configuration processing, hashing, and WebAuthn-data charges.

Before approval, benchmark direct and combined grant-and-use transactions at these limits, including maximum owner counts, maximum-size WebAuthn signatures, an optional fee payer, and an invalid final signature. Compare each primitive signature type and the configurable 1-of-1 case with an ordinary account.

# Tooling

- Before account creation, wallets should verify that the proposed owners can produce valid signatures meeting the approval threshold.
- SDKs build witnesses with the full configuration and signatures in owner-address order.
- Wallets and SDKs must support independent signing and collection of owner signatures, so owners do not need to be online together. Each approval binds the transaction signing hash, account address, and configuration version. Changes to those values require fresh signatures. Before submission, tooling must combine the signatures and recheck the current configuration, nonce, and validity window.
- Recover configurations from initial signatures and update events.
- Pools revalidate affected transactions after commitment changes or reorgs.
- RPC simulation uses the same stateful authorization rules and reports the state used.

# Observability

Initial registration emits no new event. An included transaction carries the initial configuration in its authorization witness and stores its hash, even if execution fails. Later changes are recorded by TIP-1109.

# Threat Model

Invalid transactions can consume verification work without paying fees. Parsing and signature limits must apply before cryptography, including when only the final signature is invalid.

# Invariants

- Signatures cannot be replayed across accounts or configuration versions.
- Every included transaction authorized by a configurable account leaves that account with a nonzero hash, regardless of execution success.
- An existing balance, storage, or nonce does not prevent initial registration.
- Initial registration survives reverted subcalls and reverted or halted execution.
- Invalid transactions do not register accounts.
- Rolling back an owner update in the first transaction restores the initial hash, not zero.
- Registration persists for configurable parents and delegates even if execution fails.
- Registration charges the applicable TIP-1000 new-account cost exactly once, including its state-gas portion, for senders under every nonce type (including a first 2D nonce key and a first-call `CREATE`) and for delegates.
- Initial registration is visible before the first call, including an owner update in the first transaction.
- The final owner signature reaches the approval threshold.
- No owner signatures are accepted after the threshold is reached.
- Signature counts and sizes remain bounded even when the final signature is invalid.
- Thresholds above eight are valid only when at most eight owners can reach them, including during creation, updates, and migration.
- A later transaction in the same block validates against the configuration left by an earlier rotation.
- `verifyMultisig` checks the configuration at call time without writing state, including for unregistered accounts and under `STATICCALL`.
- `verifyMultisig` follows the specified false/revert cases and cannot succeed without sufficient gas.
- `verifyKeychain` and `verifyKeychainAdmin` reject multisig inner signatures with `InvalidFormat()`, including one naming the parent account.
