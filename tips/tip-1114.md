# TIP-1114: Configurable Account Type

## Abstract

This TIP adds configurable accounts with a stable address and 1–48 weighted owners. Each quorum uses at most eight primitive signatures meeting the threshold, including for 1-of-1 accounts.

Witnesses carry the configuration and approvals bound to the operation, account and configuration version. First use registers before calls execute; registration survives execution failure.

This TIP defines transaction and stateful message verification using secp256k1, P256 or WebAuthn. TIP-1108 stores commitments, TIP-1109 updates owners, TIP-1110 derives addresses, and TIP-1111 covers access-key flows. Nested multisig owners are excluded.

## Motivation

Users need to replace keys without moving funds or application permissions. They also need the account to pay its own transaction fees without a separate executor.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| Owners use Tempo's existing secp256k1, P256, or WebAuthn signature schemes. | A new owner scheme would need separate encoding, verification, and cost rules. |
| An attacker cannot discover a primitive private key for an unregistered derived account address. | Before registration, a zero commitment does not retire that primitive root's authority. |

# Specification

## Overview

A **configuration** contains a fixed salt, a version, an approval threshold, and weighted owner addresses. A **quorum** is a set of owner approvals whose weights reach the threshold. Each signature witness carries the configuration and the primitive owner signatures.

1. **Derive:** TIP-1110 derives the address from the initial configuration; nothing is registered yet.
2. **Sign:** collect owner approvals over the transaction, account, and configuration version.
3. **Validate and register:** check the current quorum. First use registers version zero before calls execute; later transactions must match the stored commitment.
4. **Execute:** run the calls as the account. TIP-1109 can replace its configuration at the same address; execution failure rolls back call changes but preserves initial registration.

On-chain signature verification checks current authority without registering or changing the account.

For example, three owners in address order have weights 2, 1, and 1, with threshold 3. The first two signatures contribute 3 and authorise the operation. The last two contribute only 2 and fail.

Configurable account authorisation covers direct transactions and TIP-1111 access-key flows. It does not add multisig signatures to subblocks, authorisation lists, or separate fee-payer signatures.

## Configuration and limits

### Owners and approvals

- An account has 1–48 owners.
- Owner addresses must be nonzero, unique, and sorted in ascending order.
- Each owner has a nonzero weight.
- The sum of all owner weights must be at most 255.
- The threshold must be 1–255 and must be reachable with at most eight owners: the sum of the eight largest owner weights (or all owners if fewer than eight) must meet the threshold.
- A signature contains 1–8 primitive owner signatures.

Owner count may exceed eight; each quorum still uses at most eight signatures.

Owners sign using primitive keys.

- Nested multisig and keychain owner signatures are rejected.
- Each primitive signature keeps its existing encoding and size limit.
- An encoded owner signature is at most 2,049 bytes.

### Configuration versions

- Version zero is the initial configuration used to derive the address.
- First use stores the version-zero hash. Positive versions represent later updates or migration.
- The initial configuration cannot list its derived account address as an owner.
- A positive-version configuration may explicitly list the account's primitive root as an owner. This supports migration with the existing key.

## Encoding and signing

Encode a multisig signature as the `0x05` prefix followed by a Recursive Length Prefix (RLP) list containing the account, configuration, and owner signatures.

```text
signature = 0x05 || rlp([account, config, signatures])
config    = [salt, version, threshold, owners]
owner     = [address, weight]
configurable_account_digest(inner_digest, account, version) = keccak256("tempo:configurable-account:signature" || inner_digest || account || uint64(version))
```

- `signatures` is a list of byte strings containing primitive Tempo signatures.
- Encode integers in the digest as fixed-width big-endian values.
- Encode the domain as raw ASCII and the account address as 20 bytes.
- For a direct transaction, `inner_digest` is the existing transaction signing hash.
- [TIP-1111](./tip-1111.md) defines the delegation signing contexts.

Before verifying signatures:

- Require canonical RLP encoding.
- Reject trailing fields, invalid lengths, and limit violations.
- Decode an exactly 65-byte signature as secp256k1, regardless of its first byte.
- Reject signature type `0x05` before activation.

## Authorization

### Check the account and configuration

Reject accounts with EVM code or EIP-7702 delegation. Read the configuration hash at the transaction's position in the block.

If the stored hash is zero:

- Require configuration version zero.
- Derive the address using TIP-1110 and require it to equal `account`.
- Compute the TIP-1108 configuration hash and reject a zero result.

If the stored hash is nonzero:

- Accept version zero or a positive version.
- Require the TIP-1108 configuration hash to match the stored commitment exactly.

### Check the owner approvals

- Verify each owner signature over `configurable_account_digest`.
- Require recovered owner addresses in strictly ascending order.
- Require each signer to belong to the supplied configuration.
- Add the signers' weights.
- The final signature must reach the threshold.
- Reject insufficient approval weight or any signature after the threshold is reached.

### Onboarding

An account can use its initial configuration even if it already has a balance, storage, or a nonzero transaction nonce.

After transaction validation and authorization checks pass and fee collection succeeds, register every configurable signer whose commitment is zero. This includes parents signing key authorizations and delegates signing access-key transactions.

- Write its version-zero hash before transaction calls, outside their execution rollback checkpoint. Precompiles and the TIP-1109 getter see it during those calls.
- Registration survives reverted subcalls and reverted or halted execution. Its write cost is paid through intrinsic gas.
- Owner updates in those calls follow execution rollback. Reverting an update restores the initial hash, never zero.

Receiving funds or deriving an address does not register the account. Read-only verification does not register it either. Simulation registers only in temporary state. Invalid transactions do not register accounts; see [Failure behavior](#failure-behavior).

`recover_signer` checks shape and returns the claimed `account`, as for keychain signatures. It does not authenticate the caller. Non-consensus consumers, including Zone RPC authentication, must check current authority: keychain grants, configurable quorums and TIP-1112 retirement.

### Failure behavior

| Outcome | Any initial registration | Inline `key_authorization` | User-call changes |
|---|---|---|---|
| Transaction rejected as invalid | Not committed | Not committed | Not executed or committed |
| Valid, included transaction completes successfully | Persists | Persists | Successful effects remain |
| Valid, included transaction's execution reverts or halts | Persists | Persists | All changes roll back, including earlier successful calls, owner/threshold updates and their events, and grants made through precompile calls |

Normal transaction fee and nonce rules still apply to included transactions.

For a worked example with an owner update, see [TIP-1109's Overview](./tip-1109.md#overview).

## On-chain signature verification

From activation, [TIP-1020](./tip-1020.md)'s `SignatureVerifier` precompile exposes the read-only `verifyConfigurableAccount(account, hash, signature)` [interface](#interfaces).

- Accept the `0x05` signature format, with owners signing `configurable_account_digest(hash, account, config.version)`.
- Apply the authorization rules above against state at call time. For an unregistered account, verify against the supplied initial configuration and require it to derive the account's address. Verification does not register the account.
- Charge standard precompile input and account-access costs plus `V(signature, hash)`, without the transaction's 3,000-gas subtraction or registration write charge.

| Verification outcome | Result |
|---|---|
| Embedded-account or stored-commitment mismatch, address-derivation failure, or account with code or EIP-7702 delegation | Return `false`. |
| Encoding or configuration error | Revert with `InvalidFormat()`. |
| Owner-approval error | Revert with `InvalidSignature()`. |
| Successful verification | Return `true`. |

`verifyKeychain` and `verifyKeychainAdmin` accept only primitive inner signatures. They revert with `InvalidFormat()` for a V2 keychain signature whose inner signature uses the `0x05` format. Shape-only recovery would otherwise let a forged signature naming the parent pass the root-key check. `verifyKeychainAdmin` is root-only, subject to [root-key disablement](./tip-1112.md).

From T14, both helpers return `false` when an access-key signature's primitive type differs from the grant's stored key type. Before T14, they do not compare these types.

## Gas and validation cost

Use `K(n) = 30 + 6 * ceil(n / 32)` for hashing `n` bytes. Use the active calldata schedule for `calldata_gas`.

Multisig verification costs:

```text
V(signature, inner_digest) =
    calldata_gas(rlp(account) || rlp(config))
  + configuration_proof_hash_cost
  + K(96)
  + sum(primitive_signature_cost)
```

The configuration proof cost depends on whether the account is registered:

- Zero stored hash: `K(68 + 21 * owner_count)` for address derivation, plus `K(75 + 21 * owner_count)` for the initial commitment.
- Nonzero stored hash: `K(75 + 21 * owner_count)` to check the commitment, including version zero.

The fixed input lengths include the raw ASCII domains: 36 bytes for the signature domain, 34 bytes for account derivation, and 33 bytes for the configuration commitment. Each owner adds a 20-byte address and a one-byte weight.

Add TIP-1108's zero-to-nonzero write cost to intrinsic gas for each account being registered. Charge the write once per account, even if it appears in more than one authorization role.

If an account being registered is empty (zero nonce, zero balance, no code), registration creates it. Also charge TIP-1000's new-account cost for that account, including its state-gas portion. Skip this charge only when the account is the transaction sender and another TIP-1000 charge already pays for creating it:

- With `nonce_key == 0`, the `nonce == 0` charge pays for the protocol nonce write that creates the account.
- With a 2D or expiring nonce, a first-call `CREATE` from a sender with account nonce zero already pays TIP-1000's new-account cost.

With a 2D nonce key, the `nonce == 0` charge pays for the new nonce-key slot, not the account, so registration still charges the new-account cost.

Primitive signature costs are:

| Signature | Gas |
| --- | --- |
| secp256k1 | 3,000 |
| P256 | 8,000 |
| WebAuthn | 8,000 plus the existing WebAuthn-data calldata charge |

Add `V - 3,000` to ordinary intrinsic gas. The subtraction removes the base signature cost already included in ordinary gas, exactly once.

- Direct authorization adds no separate precompile storage read or keychain processing buffer.
- Compute intrinsic gas and check fee affordability before verifying owner signatures.
- Gas charging does not replace the limits on unpaid validation work.

## Changes to other components

### Sender and fees

- For a direct owner-authorised transaction, the configurable account is `tx.from`, `tx.origin`, and the top-level `msg.sender`; its quorum authorizes the complete call batch.
- When a configurable account acts as an access key, the parent remains the sender and caller; the delegate's quorum supplies authority under TIP-1111.
- Existing nonce, fee-token, sponsorship, and transaction signing rules apply.
- A separate fee payer uses the existing secp256k1 sponsorship signature.
- Sponsoring fees gives no authority over the account.

### Supported signature contexts

From activation, multisig signatures are supported in:

- Outer transaction signatures.
- Access-key envelopes under TIP-1111.
- Signed key authorizations under TIP-1111.

A transaction may grant access and use it immediately. TIP-1111 defines the combined verification limit.

Reject multisig signatures in subblocks. EIP-7702 authorisation-list entries with multisig (`0x05`) signatures, directly or inside a V2 keychain envelope, invalidate the transaction both before and after T14. Stateless TIP-1020 `recover` and `verify` do not support bare multisig signatures.

Primitive authorisation-list entries retain their existing encoding and apply TIP-1112's root-authority checks. Keychain-signed entries with primitive inner signatures keep their existing skip behaviour.

**Payment channels (MPP).** A configurable account can fund a payment channel, but it cannot sign the channel's vouchers itself. When opening the channel, it must name a regular single-key signer (`authorizedSigner`) to sign vouchers. That signer stays in charge of the channel until the channel closes, even if the account later changes its owners. To use a different signer, close the channel and open a new one.

No new transaction fields are added. Non-multisig transactions keep their existing encoding.

The root-authority checks defined in [TIP-1112](./tip-1112.md) apply from T14, together with configurable account authorisation.

### Zones

Configurable accounts are blocked on zones for now. A zone keeps its own copy of account state, so owner changes and migrations on Tempo never reach it. On a zone, an account would still trust its initial owners, even after they were rotated out on Tempo.

Until a separate TIP syncs account configurations from Tempo to zones:

- Zones reject the `0x05` signature format in every context, configurable delegates, and key authorisations signed by a configurable parent.
- Zones reject `updateConfig` ([TIP-1109](./tip-1109.md)) and `upgradeAccount` ([TIP-1113](./tip-1113.md)).
- Newly derived accounts cannot access zone funds; migrated accounts retain their old root's authority there. Wallets must not deposit to zones for configurable accounts.

## Interfaces

### Configuration fields

The configuration encodes `salt`, `version`, `threshold`, and `owners` in that order. Each owner encodes an address followed by its weight. The signature encoding is defined under [Encoding and signing](#encoding-and-signing).

| Field | Type | Meaning |
| --- | --- | --- |
| `salt` | `bytes32` | A fixed value used in address derivation and configuration hashing. |
| `version` | `uint64` | Zero for the initial configuration. Updates use increasing positive versions. |
| `threshold` | `uint8` | The total approval weight needed to authorize an operation. |
| `owners` | List of `(address, uint8 weight)` | The keys that can approve and the weight of each approval. |

### Signature verifier

```solidity
function verifyConfigurableAccount(
    address account,
    bytes32 hash,
    bytes calldata signature
) external view returns (bool);
```

# Rationale

## Signature limits

- **Direct transaction:** P256/WebAuthn verification costs 8,000 gas per signature: **8 × 8,000 = 64,000 gas**. A secp256k1 fee-payer signature adds 3,000, totaling **67,000 gas**.
- **Grant and use an access key:** The parent signs the grant and the delegate signs the transaction. Two full quorums plus a fee payer cost **16 × 8,000 + 3,000 = 131,000 gas**.

Invalid transactions pay no fees, so the signature cap bounds unpaid verification work. These costs exclude configuration processing, hashing, and WebAuthn-data charges.

Before approval, benchmark direct and combined grant-and-use transactions at these limits, including maximum owner counts, maximum-size WebAuthn signatures, an optional fee payer, and an invalid final signature. Compare each primitive signature type and the configurable 1-of-1 case with an ordinary account.

# Compatibility

- Before account creation, wallets should verify that the proposed owners can produce valid signatures meeting the approval threshold.
- SDKs build witnesses with the full configuration and signatures in owner-address order.
- Wallets and SDKs must support independent signing and collection of owner signatures, so owners do not need to be online together. Each approval binds the transaction signing hash, account address, and configuration version. Changes to those values require fresh signatures. Before submission, tooling must combine the signatures and recheck the current configuration, nonce, and validity window.
- Recover configurations from initial signatures and update events; match them to the commitment at the selected state.
- Applications using `verifyConfigurableAccount` remain responsible for the message's application domain, intended chain scope and replay protection in `hash`. The verifier proves current approval of that hash; it does not define the action or consume an application nonce.
- Pools revalidate affected transactions after commitment changes or reorgs.
- RPC simulation uses the same stateful authorization rules and reports the state used.

# Observability

Initial registration emits no new event.

| Stage | Evidence |
|---|---|
| Address derived or funded | No registration occurs. Derivation or receipt of funds alone does not establish a nonzero commitment. |
| Initial transaction included | Its authorization witness carries the initial configuration, and account state stores the hash. Execution failure does not undo registration. |
| Owners updated | TIP-1109's `ConfigurableAccountConfigUpdated` records the new configuration. A failed batch leaves no update event. |
| Signature verified onchain | The verifier returns or reverts as specified above; it writes no state and does not register the account. |

Match the supplied configuration to the commitment at the selected state. A transaction's execution status alone does not identify whether initial registration occurred.

# Threat Model

The critical boundary is an untrusted witness's claimed address versus current authority. Shape-only recovery must not authorise an operation; current-state and quorum checks must succeed first.

| Actor | Capability and trust boundary |
|---|---|
| Owners / recovery providers | A current quorum approves the entire call batch, including ownership changes. Weight checks block a below-threshold set; compromise or collusion of a quorum gives account control. |
| Wallet | Presents the operation and proposed owners. Signature verification proves approval of the signed bytes, not that the display was accurate or replacement keys are usable. |
| Signature collector / relayer / fee payer | Can collect or withhold approvals, delay submission or pay fees. Operation, account and version binding prevents altering what owners signed; these roles confer no owner authority. |
| Public submitter | Controls wrapper bytes, claimed account, configuration and approvals. Parsing/configuration bounds precede cryptography; state matching and recovered-owner weight checks reject forged or stale authority. Limits bound work per attempt, including an invalid final signature. |
| Protocol client / stateful verifier | Trusted to check current commitments and quorum approvals separately for every operation-specific signing role before privileged effects. Registration stays outside the user-call rollback checkpoint; owner updates stay inside it. |
| Application / offchain authenticator | Chooses which message authorises which action. It must use stateful authority verification and enforce its message/replay policy; accepting a claimed address or old configuration can bypass the account's current quorum. |
| Wallet / configuration provider | Must retain or recover the full configuration matching the commitment. The onchain hash proves a supplied configuration but cannot reconstruct it; unavailable data can block authorisation even with enough keys. |

Per-transaction limits do not prevent repeated invalid submissions. Verification cannot protect a quorum that approves a harmful call or restore lost keys. The unknown-root assumption for unregistered derived accounts remains under [Assumptions](#assumptions).

# Invariants

- Signatures cannot be replayed across accounts or configuration versions.
- Every included transaction authorized by a configurable account leaves that account with a nonzero hash, regardless of execution success.
- An existing balance, storage, or nonce does not prevent initial registration.
- Initial registration survives reverted subcalls and reverted or halted execution.
- Invalid transactions do not register accounts.
- Rolling back an owner update in the first transaction restores the initial hash, not zero.
- Registration persists for configurable parents and delegates even if execution fails.
- Registration charges the applicable TIP-1000 new-account cost exactly once, including its state-gas portion, for senders under every nonce type (including a first 2D nonce key and a first-call `CREATE`) and for delegates.
- Initial registration is visible before the first call, including an owner update in the first transaction.
- The final owner signature reaches the approval threshold.
- No owner signatures are accepted after the threshold is reached.
- Signature counts and sizes remain bounded even when the final signature is invalid.
- Thresholds above eight are valid only when at most eight owners can reach them, including during creation, updates, and migration.
- A later transaction in the same block validates against the configuration left by an earlier rotation.
- `verifyConfigurableAccount` checks the configuration at call time without writing state, including for unregistered accounts and under `STATICCALL`.
- `verifyConfigurableAccount` follows the specified false/revert cases and cannot succeed without sufficient gas.
- `verifyKeychain` and `verifyKeychainAdmin` reject multisig inner signatures with `InvalidFormat()`, including one naming the parent account.
