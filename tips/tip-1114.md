# TIP-1114: Configurable Account Type

## Abstract

This TIP adds stable-address accounts with 1–48 weighted owners. A quorum meets the threshold with at most eight primitive signatures, including for 1-of-1 accounts.

Witnesses carry the configuration and approvals bound to the operation, account and configuration version. First use registers before calls execute; registration survives execution failure.

This TIP defines transaction and stateful message verification using secp256k1, P256 or WebAuthn. TIP-1108 stores commitments, TIP-1109 updates owners, TIP-1110 derives addresses, and TIP-1111 covers access-key flows. Owner approvals cannot use nested configurable-account signatures.

## Motivation

Users need to replace keys without moving funds or application permissions, and pay transaction fees without a separate executor.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| Owners use Tempo's existing secp256k1, P256, or WebAuthn signature schemes. | A new owner scheme would need separate encoding, verification, and cost rules. |
| An attacker cannot discover a primitive private key for an unregistered derived account address. | Before registration, a zero commitment does not retire that primitive root's authority. |

# Specification

## Overview

A **configuration** contains a fixed salt, version, threshold and weighted owner addresses. A **quorum** comprises owner approvals whose weights reach the threshold. A witness carries the configuration and primitive approvals.

1. **Derive:** TIP-1110 derives an address from the initial configuration without registering it.
2. **Sign:** collect approvals bound to the transaction, account and version.
3. **Validate and register:** check current authority; first use registers version zero before calls, and later transactions must match the stored commitment.
4. **Execute:** run calls as the account, including TIP-1109 updates. Failure rolls back call changes but preserves registration.

On-chain signature verification checks current authority without registering or changing the account.

For owners ordered by address with weights 2, 1, 1 and threshold 3, the first two signatures authorise the operation; the last two fail.

This covers direct transactions and TIP-1111 access-key flows; [other signature contexts](#supported-signature-contexts) retain their restrictions.

## Configuration and limits

### Owners and approvals

- An account has 1–48 owners.
- Owner addresses must be nonzero, unique, and sorted in ascending order.
- Each owner has a nonzero weight.
- The sum of all owner weights must be at most 255.
- The threshold must be 1–255 and must be reachable with at most eight owners: the sum of the eight largest owner weights (or all owners if fewer than eight) must meet the threshold.
- A signature contains 1–8 primitive owner signatures.

- Configurable-account and keychain signatures are rejected as owner approvals.
- Primitive signatures retain their existing encoding and size limits; each encoded owner signature is at most 2,049 bytes.

### Configuration versions

- Version zero derives the address and is stored at first use; positive versions represent updates or migration.
- The initial configuration cannot list its derived address as an owner. Positive versions may explicitly list the account's primitive root, supporting migration with the existing key.

## Encoding and signing

A configurable-account signature prefixes a Recursive Length Prefix (RLP) list of account, configuration and owner signatures with `0x05`:

```text
signature = 0x05 || rlp([account, config, signatures])
config    = [salt, version, threshold, owners]
owner     = [address, weight]
configurable_account_digest(inner_digest, account, version) = keccak256("tempo:configurable-account:signature" || inner_digest || account || uint64(version))
```

- `signatures` contains primitive Tempo signatures as byte strings.
- The digest uses fixed-width big-endian integers, a raw ASCII domain and a 20-byte account address.
- `inner_digest` is the existing transaction signing hash for direct transactions; [TIP-1111](./tip-1111.md) defines delegation contexts.

Before verifying signatures:

- Require canonical RLP; reject trailing fields, invalid lengths and limit violations.
- Decode an exactly 65-byte signature as secp256k1, regardless of its first byte.
- Reject signature type `0x05` before activation.

## Authorization

Check the current commitment and owner quorum separately for every configurable signing role before accepting its authority.

### Check the account and configuration

Reject accounts with EVM code or EIP-7702 delegation. Read the configuration hash at the transaction's position in the block.

| Stored hash | Required configuration check |
|---|---|
| Zero | Require version zero, then derive its TIP-1110 address and require equality with `account`. Compute its TIP-1108 hash and reject zero. |
| Nonzero | Accept version zero or positive; require its TIP-1108 hash to match the stored commitment exactly. |

### Check the owner approvals

- Verify each owner signature over `configurable_account_digest`.
- Require recovered addresses in strictly ascending order and membership in the supplied configuration; add their weights.
- The final signature must reach the threshold. Reject insufficient weight or any signature after reaching it.

These checks read no state. Nodes may run them during sender recovery and cache the result, as keychain recovery verifies its inner signature and caches the key ID.

### Onboarding

Existing balance, storage or a nonzero transaction nonce does not prevent initial registration.

After transaction validation, authorization and fee collection succeed, register every configurable signer with a zero commitment, including parents signing key authorizations and delegates signing access-key transactions.

Write its version-zero hash before calls, outside their execution rollback checkpoint, visible to precompiles and the TIP-1109 getter. Intrinsic gas pays for the write. [Failure behavior](#failure-behavior) preserves registration through reverted subcalls or reverted/halted execution; rolling back an owner update restores the initial hash, never zero.

Funding, derivation and read-only verification do not register accounts; simulation registers only in temporary state. Invalid transactions follow [Failure behavior](#failure-behavior).

`recover_signer` verifies the owner quorum against the embedded configuration and returns `account`. That configuration remains a claim until it matches the stored commitment or initial derivation. Non-consensus consumers, including Zone RPC authentication, must check configurable commitments, current keychain grants and TIP-1112 retirement.

### Failure behavior

| Outcome | Any initial registration | Inline `key_authorization` | User-call changes |
|---|---|---|---|
| Transaction rejected as invalid | Not committed | Not committed | Not executed or committed |
| Valid, included transaction completes successfully | Persists | Persists | Successful effects remain |
| Valid, included transaction's execution reverts or halts | Persists | Persists | All changes roll back, including earlier successful calls, owner/threshold updates and their events, and grants made through precompile calls |

Included transactions follow normal fee and nonce rules. See [TIP-1109](./tip-1109.md#overview) for a failed-batch example.

## On-chain signature verification

From activation, [TIP-1020](./tip-1020.md)'s `SignatureVerifier` precompile exposes the read-only `verifyConfigurableAccount(account, hash, signature)` [interface](#interfaces).

- Accept the `0x05` signature format, with owners signing `configurable_account_digest(hash, account, config.version)`.
- Apply [Authorization](#authorization) against call-time state, including initial-configuration derivation for unregistered accounts. Do not register the account.
- Charge standard precompile input and account-access costs plus `V(signature, hash)`, without the transaction's 3,000-gas subtraction or registration write charge.

| Verification outcome | Result |
|---|---|
| Embedded-account or stored-commitment mismatch, address-derivation failure, or account with code or EIP-7702 delegation | Return `false`. |
| Encoding or configuration error | Revert with `InvalidFormat()`. |
| Owner-approval error | Revert with `InvalidSignature()`. |
| Successful verification | Return `true`. |

`verifyKeychain` and `verifyKeychainAdmin` accept only primitive inner signatures; a V2 keychain envelope with inner `0x05` reverts with `InvalidFormat()`. Recovery does not check the delegate's commitment, so an unregistered configuration could otherwise pass the root-key check. `verifyKeychainAdmin` is root-only, subject to [root-key disablement](./tip-1112.md).

From T14, both helpers return `false` when an access-key signature's primitive type differs from the grant's stored key type. Before T14, they do not compare these types.

## Gas and validation cost

Use `K(n) = 30 + 6 * ceil(n / 32)` for hashing `n` bytes. Use the active calldata schedule for `calldata_gas`.

Configurable-account verification costs:

```text
V(signature, inner_digest) =
    calldata_gas(rlp(account) || rlp(config))
  + configuration_proof_hash_cost
  + K(96)
  + sum(primitive_signature_cost)
```

The configuration proof cost depends on whether the account is registered:

- Zero stored hash: `K(68 + 21 * owner_count)` for address derivation, plus `K(75 + 21 * owner_count)` for the initial commitment.
- Nonzero stored hash: `K(75 + 21 * owner_count)` to check the commitment, including version zero.

Input lengths include raw ASCII domains: 36 bytes for signatures, 34 for derivation, 33 for commitments. Each owner adds a 20-byte address and one-byte weight.

Add TIP-1108's zero-to-nonzero write cost to intrinsic gas once per account being registered, deduplicating authorization roles.

Registering an empty account (zero nonce, zero balance, no code) also charges TIP-1000's new-account cost, including state gas. Skip it only for the transaction sender when another TIP-1000 charge already pays for its creation:

- With `nonce_key == 0`, the `nonce == 0` charge pays for the protocol nonce write that creates the account.
- With a 2D or expiring nonce, a first-call `CREATE` from a sender with account nonce zero already pays TIP-1000's new-account cost.

With a 2D nonce key, the `nonce == 0` charge pays for the new nonce-key slot, not the account, so registration still charges the new-account cost.

Primitive signature costs are:

| Signature | Gas |
| --- | --- |
| secp256k1 | 3,000 |
| P256 | 8,000 |
| WebAuthn | 8,000 plus the existing WebAuthn-data calldata charge |

Add `V - 3,000` to ordinary intrinsic gas, subtracting its included base signature cost exactly once.

- Direct authorization adds no separate precompile storage read or keychain processing buffer.
- Gas charging does not replace the limits on unpaid validation work.

## Changes to other components

### Sender and fees

- For direct transactions, the configurable account is `tx.from`, `tx.origin` and top-level `msg.sender`; its quorum authorizes the complete batch.
- For configurable access keys, the parent remains sender and caller; the delegate's quorum supplies TIP-1111 authority.
- Existing nonce, fee-token, sponsorship, and transaction signing rules apply.
- A separate fee payer uses the existing secp256k1 sponsorship signature.
- Sponsoring fees gives no authority over the account.

### Supported signature contexts

From activation, configurable-account signatures support outer transactions, TIP-1111 access-key envelopes and signed key authorizations. A transaction may grant and immediately use access under TIP-1111's combined verification limit.

Reject configurable-account signatures in subblocks. EIP-7702 authorisation-list entries with configurable-account (`0x05`) signatures, directly or inside a V2 keychain envelope, invalidate the transaction both before and after T14. Stateless TIP-1020 `recover` and `verify` do not support standalone `0x05` signatures.

Primitive authorisation-list entries retain their existing encoding and apply TIP-1112's root-authority checks. Keychain-signed entries with primitive inner signatures keep their existing skip behaviour.

**Payment channels (MPP).** A configurable account may fund channels but cannot sign vouchers itself. It must name a primitive `authorizedSigner` at opening. Owner rotation does not replace that signer; changing it requires closing and reopening the channel.

No new transaction fields are added. Transactions without configurable-account signatures keep their existing encoding.

The root-authority checks defined in [TIP-1112](./tip-1112.md) apply from T14, together with configurable account authorisation.

### Zones

Zones keep separate account state and receive no Tempo owner updates or migrations; enabling configurable signatures there could admit approvals from superseded owners.

Until a separate TIP syncs account configurations from Tempo to zones:

- Zones reject the `0x05` signature format in every context, configurable delegates, and key authorisations signed by a configurable parent.
- Zones reject `updateConfig` ([TIP-1109](./tip-1109.md)) and `upgradeAccount` ([TIP-1113](./tip-1113.md)).
- Newly derived accounts cannot access zone funds; migrated accounts retain their old root's authority there. Wallets must not deposit to zones for configurable accounts.

## Interfaces

### Configuration fields

Encode `salt`, `version`, `threshold`, then `owners`; each owner encodes address then weight. See [Encoding and signing](#encoding-and-signing).

| Field | Type | Meaning |
| --- | --- | --- |
| `salt` | `bytes32` | Fixed input to derivation and configuration hashing. |
| `version` | `uint64` | Initially zero; updates use increasing positive versions. |
| `threshold` | `uint8` | Required approval weight. |
| `owners` | List of `(address, uint8 weight)` | Approving keys and their weights. |

### Signature verifier

```solidity
function verifyConfigurableAccount(
    address account,
    bytes32 hash,
    bytes calldata signature
) external view returns (bool);
```

# Rationale

## Signature limits

- **Direct transaction:** eight P256/WebAuthn signatures cost **8 × 8,000 = 64,000 gas**; a secp256k1 fee payer adds 3,000, totaling **67,000 gas**.
- **Grant and use:** parent and delegate quorums sign grant and transaction, respectively; with a fee payer, **16 × 8,000 + 3,000 = 131,000 gas**.

Invalid transactions pay no fees, so the signature cap bounds unpaid verification work. These costs exclude configuration processing, hashing, and WebAuthn-data charges.

# Compatibility

- Before creation, wallets should verify that proposed owners can sign a valid quorum.
- SDKs build witnesses with the full configuration and signatures in owner-address order.
- Wallets and SDKs must support independent, asynchronous signing and collection. Changing [signed values](#encoding-and-signing) requires fresh approvals. Before submission, combine signatures and recheck current configuration, nonce and validity window.
- Recover configurations from initial signatures and update events; match them to the commitment at the selected state.
- Applications using `verifyConfigurableAccount` remain responsible for application domain, intended chain scope and replay protection in `hash`. The verifier proves current approval; it neither defines actions nor consumes application nonces.
- Pools revalidate affected transactions after commitment changes or reorgs.
- RPC simulation uses the same stateful authorization rules and reports the state used.

# Observability

Initial registration emits no new event.

| Stage | Evidence |
|---|---|
| Address derived or funded | No registration; see [Onboarding](#onboarding). |
| Initial transaction included | Witness carries the configuration; state stores its hash despite execution failure. |
| Owners updated | TIP-1109's `ConfigurableAccountConfigUpdated` records the configuration; failed batches leave no update event. |
| Signature verified onchain | [Return/revert result](#on-chain-signature-verification) only; no state change or registration. |

Match configurations to the selected state's commitment; execution status alone does not identify registration.

# Threat Model

| Actor | Trust boundary |
|---|---|
| Owners / recovery providers | A current quorum controls spending and owner changes, including the full batch. Compromise or collusion at the threshold gives account control. |
| Wallet / configuration provider | Presents operations and owner changes, and retains full configurations. Signed bytes do not guarantee an accurate display, and a stored commitment cannot reconstruct an unavailable configuration. |
| Signature collectors / relayers / fee payers | Can delay or withhold approvals and submission, but cannot change signed operations, account or version; fee sponsorship grants no owner authority. |
| Public submitters | Can submit invalid witnesses without paying fees. Signature count and size limits bound verification work per attempt, but not repeated invalid submissions. |

# Invariants

- Signatures cannot be replayed across accounts or configuration versions.
- Every included transaction authorized by a configurable account leaves that account with a nonzero hash, regardless of execution success.
- An existing balance, storage, or nonce does not prevent initial registration.
- Initial registration survives reverted subcalls and reverted or halted execution.
- Invalid transactions do not register accounts.
- Rolling back an owner update in the first transaction restores the initial hash, not zero.
- Registration persists for configurable parents and delegates even if execution fails.
- When registration creates a new account, charge TIP-1000's new-account cost, including its state-gas portion, exactly once.
- Initial registration is visible before the first call, including an owner update in the first transaction.
- The final owner signature reaches the approval threshold.
- No owner signatures are accepted after the threshold is reached.
- Signature counts and sizes remain bounded even when the final signature is invalid.
- Thresholds above eight are valid only when at most eight owners can reach them, including during creation, updates, and migration.
- A later transaction in the same block validates against the configuration left by an earlier rotation.
- `verifyConfigurableAccount` checks the configuration at call time without writing state, including for unregistered accounts and under `STATICCALL`.
- `verifyConfigurableAccount` follows the specified false/revert cases and cannot succeed without sufficient gas.
- `verifyKeychain` and `verifyKeychainAdmin` reject configurable-account inner signatures with `InvalidFormat()`, including one naming the parent account.
