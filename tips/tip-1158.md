# TIP-1158: T15 Hardfork Meta TIP

## Abstract

The proposed T15 hardfork lets static-only payment calls carry up to 32 bytes
after their ABI-encoded arguments and still qualify for the payment lane. It
also makes the DKG outcome a boundary block carries a block validity rule,
checked by execution against the parent state, and rejects trailing bytes after
the DKG data (dealer logs and the boundary block's outcome) in a block's
extra data.

## Motivation

Collect the T15 upgrade scope and implementation links in one place for review.

---

# Changes

These changes activate at T15; pre-T15 behavior is unchanged.

## 1. Allow trailing bytes in payment calls

**PR**: [#8850](https://github.com/tempoxyz/tempo/pull/8850) · **Author**: @klkvr

Amends [TIP-1045](./tip-1045.md): calldata for a static-only payment call MAY
carry up to 32 arbitrary bytes after its ABI-encoded arguments. Integrators
append fixed-size tags, such as attribution IDs, to TIP-20 transfers. Since
[TIP-1116](./tip-1116.md) these calls execute again, but they are classified as
general transactions.

The trailing bytes are not interpreted and do not change which allow-list entry
matches. Calls with more than 32 trailing bytes do not match any entry. Entries
with dynamic types (TIP20ChannelReserve `settle` and `close`) are unchanged
and remain bounded by the 2048-byte calldata limit.

## 2. Check the boundary block's DKG outcome in execution

**PR**: [#8995](https://github.com/tempoxyz/tempo/pull/8995) · **Author**: @SuperFluffy

The last block of each epoch (the boundary block) carries the DKG outcome for
the next epoch in its `extra_data`. Consensus now supplies only the DKG
ceremony output. The payload builder fills in `epoch`, `next_players` and
`is_next_full_dkg` from ValidatorConfigV2 in the parent state, then writes the
full `OnchainDkgOutcome` to `extra_data`.

From T15, the block executor decodes the `extra_data` of a boundary block as an
`OnchainDkgOutcome`. A block is invalid if the decode fails or if any of these
fields differ from what the parent state gives:

- `epoch` MUST be the next epoch.
- `next_players` MUST be the active ValidatorConfigV2 validators. Validators
  whose public key, ingress or egress does not decode are skipped, and each
  public key counts once.
- `is_next_full_dkg` MUST be true exactly when the next epoch is
  ValidatorConfigV2's next full DKG epoch.

Execution reads ValidatorConfigV2 from the backing database. These reads are not
part of the block's state or access list. The outcome MUST take up all of
`extra_data` (see [change 3](#3-reject-trailing-bytes-in-dkg-extra-data)).
The check is skipped when ValidatorConfigV2 is not initialized in the parent
state. Consensus compares only the ceremony output. Before T15,
verifying validators compare the whole outcome against the parent state, as
before.

## 3. Reject trailing bytes in DKG extra data

**PR**: [#9310](https://github.com/tempoxyz/tempo/pull/9310) · **Author**: @SuperFluffy

A block's `extra_data` carries either a signed DKG dealer log or, in the
boundary block, the `OnchainDkgOutcome` for the next epoch. Before T15,
decoders read these values and ignore any bytes after them.

From T15, decided by the block's timestamp, these values MUST take up all of
`extra_data`:

- A proposal whose dealer log has trailing bytes fails verification. When the DKG manager reads dealer logs from notarized or finalized
  blocks, it ignores such a log, so the dealer does not count for the
  ceremony.
- A boundary block whose outcome has trailing bytes fails consensus
  verification. Execution also rejects it when checking the outcome against
  the parent state (change 2), whenever ValidatorConfigV2 is initialized.

The committee system call still reads the outcome without this check. Blocks
before T15 are unaffected.
