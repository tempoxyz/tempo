# TIP-1158: T15 Hardfork Meta TIP

## Abstract

T15 lets static-only payment calls carry up to 32 trailing bytes and stay in
the payment lane, makes the boundary block's DKG outcome a block validity rule
checked against the parent state, rejects trailing bytes after DKG data in a
block's extra data, and disables ValidatorConfig V1 and the V1 to V2 migration.
This meta TIP specifies these protocol changes.

## Motivation

Collect the T15 upgrade scope and implementation links in one place for review.

# Additional protocol changes

These changes are not covered by an individual T15 TIP. They are proposed behind
T15; pre-T15 execution rules are preserved.

## 1. Allow trailing bytes in payment calls

**PR**: [#8850](https://github.com/tempoxyz/tempo/pull/8850) · **Author**: @klkvr

Amends [TIP-1045](./tip-1045.md): from T15, a static-only payment call MAY carry
up to 32 arbitrary bytes after its ABI-encoded arguments and still qualify for
the payment lane. Integrators append fixed-size tags, such as attribution IDs,
to TIP-20 transfers; since [TIP-1116](./tip-1116.md) these calls execute, but as
general transactions. The trailing bytes are not interpreted and do not change
which allow-list entry matches. A call with more than 32 trailing bytes matches
no entry. Entries with dynamic types (TIP20ChannelReserve `settle` and
`close`) are unchanged and remain bounded by the 2048-byte calldata limit.

## 2. Check the boundary block's DKG outcome in execution

**PR**: [#8995](https://github.com/tempoxyz/tempo/pull/8995) · **Author**: @SuperFluffy

The last block of each epoch (the boundary block) carries the next epoch's
`OnchainDkgOutcome` in its `extra_data`. Consensus supplies only the DKG
ceremony output; the payload builder fills in `epoch`, `next_players` and
`is_next_full_dkg` from ValidatorConfigV2 in the parent state.

From T15, the block executor decodes a boundary block's `extra_data` as an
`OnchainDkgOutcome` and rejects the block if decoding fails or any field
differs from the parent state:

- `epoch` MUST be the next epoch.
- `next_players` MUST be the active ValidatorConfigV2 validators, skipping
  those whose public key, ingress or egress does not decode and counting each
  public key once.
- `is_next_full_dkg` MUST be true exactly when the next epoch is
  ValidatorConfigV2's next full DKG epoch.

The outcome MUST fill all of `extra_data`
([change 3](#3-reject-trailing-bytes-in-dkg-extra-data)). ValidatorConfigV2 is
read from the backing database, and these reads are not part of the block's
state or access list. The check is skipped when ValidatorConfigV2 is not
initialized in the parent state. Consensus compares only the ceremony output.
Before T15, verifying validators compare the whole outcome against the parent
state.

## 3. Reject trailing bytes in DKG extra data

**PR**: [#9310](https://github.com/tempoxyz/tempo/pull/9310) · **Author**: @SuperFluffy

A block's `extra_data` carries a signed DKG dealer log or, in the boundary
block, the next epoch's `OnchainDkgOutcome`. Before T15, decoders ignore any
bytes after these values. From T15, decided by the block's timestamp, the value
MUST fill all of `extra_data`:

- A proposal whose dealer log has trailing bytes fails verification. The DKG
  manager ignores such a log in notarized or finalized blocks, so its dealer
  does not count for the ceremony.
- A boundary block whose outcome has trailing bytes fails consensus
  verification. Execution also rejects it in the change 2 check whenever
  ValidatorConfigV2 is initialized.

The committee system call still reads the outcome without this check.

## 4. Disable ValidatorConfig V1 and the V1 to V2 migration

**PR**: [#9350](https://github.com/tempoxyz/tempo/pull/9350) · **Author**: @SuperFluffy

From T15, every selector of the ValidatorConfig (V1) precompile, including its
views, reverts with `UnknownFunctionSelector(bytes4)`, as do
`migrateValidator` and `initializeIfMigrated` on ValidatorConfigV2
([TIP-1017](./tip-1017.md)). All other ValidatorConfigV2 functions are
unchanged.

Once ValidatorConfigV2 is initialized, as on mainnet and Moderato, consensus,
DKG and fee-recipient lookups read only V2, so V1 writes have no effect and the
migration calls already revert with `AlreadyInitialized`. Pre-T15 behavior is
preserved, so historical blocks replay unchanged. Tooling that still uses V1,
such as `xtask generate-add-peer`, must use ValidatorConfigV2 on networks at
T15 or later.
