# TIP-1154: Configurable Accounts on Zones

## Abstract

This TIP lets a [configurable account](./tip-1107.md) use the same address and owners on every zone as on Tempo, by keeping a copy of each account's configuration commitment in zone state. Original-key retirement and code checks read only that copy, and Tempo is read only to verify an owner (`0x05`) signature, metered like a cold account access. Tempo appends each migration (`upgradeAccount`, which makes an account configurable and retires its original key) to a hash-chained list for 250,000 extra gas, and a zone must apply every migration its anchor includes before any user transaction, so a sequencer can delay a migration but not skip one. The main limitation: a zone sees a Tempo change only once its anchor, the Tempo block it reads state at, includes it, and nothing bounds that lag.

## Motivation

A configurable account on Tempo should work on every zone at the same address, so users keep one account across Tempo and its zones. A zone needs the account's commitment for three things: rejecting the retired original key, showing the account code marker to contracts such as Permit2, and verifying owner signatures.

One alternative is for a zone to read the commitment from Tempo at its anchor on every account load, as it does for TIP-403 policies. Unlike policies, which are per token, commitments are per account, so almost every zone transaction would depend on Tempo. Even a plain EOA would need a proof that its commitment is zero, since any address may have been migrated on Tempo. The sequencer can cache these reads, but the prover cannot: the witness grows by one Tempo account proof per distinct account per anchor. Invalid transactions and fresh addresses would also force unmetered Tempo reads.

This TIP avoids that cost by keeping a copy of the commitment in each zone's own state, so original-key retirement and code checks read only that copy. Zone state still needs proofs, but they are proofs of the zone's own, smaller state that the witness already carries. Only accounts whose owners actually sign (with a `0x05` signature) pay for a Tempo read.

A separate address namespace for zone accounts would avoid all of these costs, because a zone account would never depend on Tempo state. However, it was rejected because each user would hold a different account on Tempo and on every zone, with its own address to share and its own owners to manage.

## Assumptions

- Zones already read Tempo state at a finalized, proven Tempo block (the anchor, kept by the `TempoState` precompile), as they do for TIP-403 policies and token enablements. Without it, no zone could check a Tempo commitment.
- An account's Tempo commitment never returns to zero once set ([TIP-1107](./tip-1107.md#commitment-storage), [TIP-1113](./tip-1113.md#ordering-and-permanence)). If it could, a nonzero zone copy could outlive the Tempo commitment it copies.
- Every commitment that goes from zero to nonzero on Tempo does so through a TIP-1113 migration, which emits `AccountUpgraded` and rolls back with its event on failure. There is no first-use registration ([TIP-1107](./tip-1107.md)). Any other zero-to-nonzero path would bypass the migration list and leave the original key live on zones.
- In normal operation a zone's anchor trails Tempo by about one block. Larger lag means the sequencer or its Tempo connection is failing, and every Tempo change, not only these, reaches the zone late.
- This TIP activates together with the other T14 configurable account components.

# Specification

## Overview

### Terms

- **Tempo** is the L1. A **zone** is a chain that settles to Tempo and is run by a **sequencer**, which builds zone blocks, and a **prover**, which proves each batch of zone blocks against Tempo.
- **Anchor**: the finalized Tempo block a zone currently reads Tempo state at. The sequencer advances it with the `advanceTempo` system call (which also processes deposits) or `advanceTempoHeaders` (which only moves the anchor).
- **Configurable account**: an account authorized by a set of owners and a threshold ([TIP-1107](./tip-1107.md)) rather than by one private key.
- **Commitment**: the hash of a configurable account's current configuration, stored on Tempo as an optional fifth field in its account leaf ([TIP-1107](./tip-1107.md#commitment-storage)). A zero commitment means the account is not configurable.
- **`0x05` signature**: the signature type a configurable account's owners sign with. It names the configuration it uses, which must hash to the account's commitment.
- **Migration**: `upgradeAccount` ([TIP-1113](./tip-1113.md)), which gives an account its first configuration at the same address. It is the only way an account becomes configurable, including keyless accounts ([TIP-1107](./tip-1107.md)). **Rotation**: `updateConfig`, which changes a configured account's owners.
- **Original-key retirement**: once an account's commitment is nonzero, a plain (primitive) signature from its original private key no longer authorizes it (TIP-1113).
- **Account code marker**: the one-byte code `0xef` a configured account has, so contracts that check for code, such as Permit2, treat it as a contract and call ERC-1271 instead of trusting `ecrecover`.
- **Zone copy**: the zone's own copy of an account's commitment, in the zone account leaf.
- **Migration list**: an append-only, hash-chained list of every migration on Tempo.

### Lifecycle

This example is illustrative. The rules are in [Mechanics](#mechanics).

1. **Migrate on Tempo.** Bob's EOA holds funds on Tempo and on zone Z. Bob calls `upgradeAccount` on Tempo. Tempo stores his commitment and appends `(Bob, commitment)` to the migration list.
2. **Apply on the zone.** Z's sequencer advances the anchor past that Tempo block with `advanceTempo` and supplies Bob's entry. Z checks the entry against the list's hash on Tempo, writes Bob's zone copy and installs the code marker. Z can't run a user transaction at that anchor until it has done this.
3. **Use the account.** Bob's original key is now rejected on Z, using only the zone copy. Bob's owners sign a `0x05` transfer on Z. Z reads Bob's commitment from Tempo at the anchor, charges for the read and checks the signature against it.
4. **Rotate.** Bob's owners rotate on Tempo. Once Z's anchor includes the rotation, `0x05` signatures on Z are checked against the new commitment. Bob's zone copy picks up the new commitment on his next `0x05` transaction on Z.

If Z's sequencer stops advancing the anchor before step 2, Bob's original key stays live on Z. This is the critical boundary: the anchor decides when a Tempo change takes effect on a zone ([Threat Model](#threat-model)).

### Where each check reads

| Operation | Tempo | Zone under this TIP |
|---|---|---|
| Original-key retirement (TIP-1113), account code marker | Uses the local commitment | Uses the zone copy |
| Authorize with `0x05` (direct, access key, key authorization) | Checked against the local commitment | Checked against Tempo's commitment at the anchor (metered). The result is written into the zone copy. |
| `upgradeAccount` | Writes the commitment and appends to the migration list | Reverts. Applied from the migration list by `advanceTempo`. |
| `updateConfig` | Allowed | Reverts. The new commitment reaches the zone copy on the account's next `0x05` transaction there. |

Tempo stays the only chain that writes commitments. Access keys stay per zone ([Access keys](#access-keys)).

## Mechanics

### Migration list on Tempo

Each successful `upgradeAccount` appends `(account, commitment)` to the migration list in the configurable account precompile. It stores:

- `migrationCount`: the number of entries
- `migrationHeads[i]`: the running hash after `i` entries, where `migrationHeads[0] = 0` and `migrationHeads[i+1] = keccak256(migrationHeads[i] ‖ account ‖ commitment)`

The append rolls back with a failed migration, together with its `AccountUpgraded` event. So the list's entries are exactly the `account` and `commitment` of the `AccountUpgraded` events in Tempo log order, and the sequencer rebuilds them from those events. Each account appears at most once, since it can migrate only once.

Each append writes one new `migrationHeads` slot and updates `migrationCount`. `upgradeAccount` charges for both on top of its [TIP-1113 cost](./tip-1113.md): TIP-1000's new state element cost (250,000 gas) for the head, and an ordinary nonzero-to-nonzero storage write for the count.

### Applying migrations on a zone

The `ZoneInbox` precompile keeps `processedMigrationCount` and `processedMigrationHead`, both starting at zero. `advanceTempo` takes, as input from the sequencer, the next `n` entries after the zone's processed position (`n` may be zero):

1. Fold the supplied entries onto `processedMigrationHead`, giving head `h` after `processedMigrationCount + n` entries.
2. Read `migrationHeads[processedMigrationCount + n]` from Tempo at the new anchor and require it to equal `h`, or revert with `MigrationHeadMismatch()`.
3. Write each entry's commitment into that account's zone copy and set the account code marker ([Zone copy](#zone-copy)).
4. Store the new count and `h` as the processed position.

Every zone applies every entry, including accounts that never use that zone, because an unapplied migration would leave the account's retired key live there. The sequencer chooses `n`, so a backlog drains over several `advanceTempo` calls, each in its own block. A zone created after T14 starts with such a backlog: the list is global, so the zone's genesis anchor already includes every migration since T14.

**Completeness.** A zone block MUST NOT contain a user transaction while `processedMigrationCount` is below Tempo's `migrationCount` at the anchor. A block that does is invalid. This also covers anchors advanced by `advanceTempoHeaders`, which applies no entries. So every migration included by the anchor is in the zone copy before any transaction uses that anchor.

**Gas.** Applying entries is a system operation outside the block gas limit and the inbox gas budget, so it never reduces the room for deposits. Each account is applied at most once. Each entry already paid at least 500,000 gas on Tempo (250,000 for the commitment under TIP-1113 and 250,000 for its list head), so Tempo's gas limit bounds the entries per Tempo block.

**Fork boundary.** `advanceTempo` calls in zone blocks before T14 keep their current signature and selector. From T14, `advanceTempo` takes the trailing `Migration[]` argument. Executors, followers, provers and witness decoders accept the form that matches the block's timestamp.

### Zone copy

Zone account leaves accept the optional [TIP-1107](./tip-1107.md#commitment-storage) fifth field, with the same encoding rules as Tempo: tag `0x00`, nonzero hash and no extra fields. An account whose copy is nonzero has the [account code marker](./tip-1107.md#account-code) (`0xef`) as its code. If it already has other code on the zone, it keeps that code and fails authorization as under TIP-1107.

The copy is written only by:

1. `advanceTempo` applying migration list entries ([Applying migrations on a zone](#applying-migrations-on-a-zone)).
2. Transaction authorization, after a `0x05` verification reads a commitment from Tempo that differs from a nonzero copy ([Verifying `0x05` signatures](#verifying-0x05-signatures)). This carries rotations into the copy.

No zone transaction can write it otherwise. `updateConfig` ([TIP-1107](./tip-1107.md#owner-updates)) and `upgradeAccount` ([TIP-1113](./tip-1113.md)) revert on zones.

These read only the copy and never Tempo:

- the TIP-1113 [retirement check](./tip-1113.md#retirement-check): a primitive signature from an address with a nonzero copy is rejected as a retired original key
- authorization's code-hash check, `EXTCODESIZE`, `EXTCODEHASH`, `EXTCODECOPY` and dispatch of calls to the account. Permit2 and other verifiers that check for code therefore call ERC-1271 instead of trusting the retired original key. The ERC-1271 call itself verifies the `0x05` signature against Tempo, so a removed owner can't sign through a stale copy.
- `getConfigCommitment`, which returns the zone copy
- transaction pool and RPC checks of the above

### Verifying `0x05` signatures

Every `0x05` verification on a zone reads the account's commitment from Tempo at the anchor (one account proof). It applies the [TIP-1107 authorization](./tip-1107.md#authorization) rules against that commitment, exactly as on Tempo. A zero commitment at the anchor fails verification.

Each read is charged like a cold account access. Transaction authorization reads once per configurable signer, at most twice per transaction: the outer signer and, when a transaction creates and uses an access-key grant at once, the `key_authorization` parent ([TIP-1111](./tip-1111.md#grant-and-use-in-one-transaction)). Fee payers can't sign with `0x05` ([TIP-1107](./tip-1107.md#supported-contexts)). ERC-1271 `isValidSignature`, `verifyConfigurableAccount` and keychain checks during execution each read and are metered the same way.

If transaction authorization reads a commitment that differs from a nonzero zone copy, the transaction writes it into the copy. Like TIP-1107 state written during authorization, the write happens before any call runs and persists if the calls revert. Verifications during execution never write.

Because verification always checks Tempo, an owner removed by `updateConfig` loses `0x05` authority on a zone once its anchor includes the rotation, even before the copy is updated.

If Tempo state at the anchor can't be read, execution fails closed: the sequencer stops building rather than treating the commitment as zero.

### Access keys

Access keys stay per zone, exactly as on Tempo ([TIP-1111](./tip-1111.md)): a configurable account can grant and use keys on a zone, and an owner rotation does not revoke grants. Users who rotate after a compromise must revoke each zone's grants on that zone.

### Transaction pool

Pool admission of a primitive-key transaction reads only the zone copy. Admission of a `0x05` transaction runs every zone-local check first (encoding, owner signatures and threshold, nonce, fee balance). Only then does it do one Tempo read per `0x05` signer. A transaction that fails at that read is rejected from the pool and pays nothing, like any invalid transaction. The read costs the sequencer one Tempo account lookup, and pools SHOULD rate-limit such failures per sender.

When the anchor advances, the pool:

- drops pending primitive-key transactions from accounts the newly applied migration entries retired, using the zone copy
- revalidates pending `0x05` transactions with a fresh Tempo read, only for accounts whose commitment changed between the old and new anchor. The `ConfigurableAccountConfigUpdated` and `AccountUpgraded` events on Tempo in that range identify them. Both events roll back with the change they report, so they find every change.

### Zone RPC

- Authorization tokens accept `0x05` signatures, checked against Tempo's commitment at the zone's current anchor.
- Tokens signed by a retired original key are rejected, using the zone copy.
- Open sessions are rechecked when the anchor advances, only for accounts whose commitment changed in that range, found as in [Transaction pool](#transaction-pool). A session is dropped when the commitment no longer authorizes it, as revoked keychain keys are today.
- `eth_getAccount` on a zone returns the zone copy as its `extension`.

### Forced exits

The forced-exit authorization (`crates/zones/exithatch`) accepts `0x05` signatures for the account under the same rules. It rejects a primitive signature from an address with a nonzero zone copy.

### Proving

- The zone copy is zone state, so retirement, marker and `EXTCODE*` reads are covered by the zone's own state witness.
- Each `advanceTempo` adds storage proofs for `migrationHeads[processedMigrationCount + n]` and `migrationCount` at the anchor.
- Each `0x05` verification adds one Tempo account proof for that account at that anchor.

A missing or invalid proof invalidates the batch.

## Interfaces

On Tempo, the configurable account precompile adds:

```solidity
/// @notice Number of successful migrations since T14.
/// @return count The migration list's length.
function migrationCount() external view returns (uint64 count);

/// @notice Running hash of the migration list after `count` entries.
/// @param count The number of entries, at most `migrationCount()`.
/// @return head `migrationHeads[count]`, which is zero for `count == 0`.
/// Reverts with InvalidMigrationIndex() if `count` exceeds `migrationCount()`.
function migrationHeads(uint64 count) external view returns (bytes32 head);
```

On zones, `ZoneInbox` adds:

```solidity
struct Migration {
    address account;
    bytes32 commitment;
}

/// @notice Number of migration list entries this zone has applied.
function processedMigrationCount() external view returns (uint64);

/// @notice Running hash after the applied entries. It equals Tempo's `migrationHeads(processedMigrationCount())`.
function processedMigrationHead() external view returns (bytes32);

/// @notice The supplied entries don't extend the processed position to Tempo's head at the anchor.
error MigrationHeadMismatch();
```

From T14, `advanceTempo` takes a trailing `Migration[] calldata migrations` argument.

# Compatibility

| Integration | What changes |
|---|---|
| Wallets and SDKs | Build `0x05` witnesses for zones as for Tempo, using the configuration valid at the zone's anchor. After a migration or rotation, wait for the zone to import it before relying on it there. Read the current configuration from Tempo at the zone's anchor: the zone's `getConfigCommitment` can lag a rotation until the account's next `0x05` transaction there. |
| Migrated accounts | The original key loses authority on a zone once `advanceTempo` applies the migration. Funds stay at the same address under the account's owners. |
| Keyless accounts | Exist on a zone once the zone applies their Tempo migration. Funds sent to the address on a zone before then are subject to the same counterfactual-funding risks as on Tempo ([TIP-1107](./tip-1107.md)). |
| Zone operators | The sequencer supplies migration entries with each `advanceTempo`, rebuilt from Tempo's `AccountUpgraded` events. The Tempo state reader must serve account reads (`eth_getAccount` at a block). |
| Prover | Tempo witnesses add two storage proofs per anchor, plus one account proof per `0x05` verification. |
| Zone nodes | Decode `advanceTempo` by block timestamp: the current form before T14, the form with migrations from T14 ([Fork boundary](#applying-migrations-on-a-zone)). |
| Zone genesis | A zone created after T14 starts at processed count zero and drains the backlog through `advanceTempo` before accepting user transactions. |
| Tempo | `upgradeAccount` costs 250,000 gas more, plus one storage write, for the migration list. |

# Observability

Tempo's configurable account precompile emits `ConfigurableAccountConfigUpdated` and `AccountUpgraded` as before. Its `migrationCount` and `migrationHeads` show the migration list. Zones expose their position through `processedMigrationCount` and `processedMigrationHead`. An operator compares `processedMigrationCount` with Tempo's `migrationCount` at the anchor to see how far behind the zone is.

# Threat Model

The most consequential attack is a stale anchor. A removed owner, or a retired original key, keeps authority on a zone until the zone's anchor includes the rotation or migration. A sequencer that stops advancing the anchor stretches that window. The completeness rule then applies a migration before any transaction at that anchor. The sequencer is trusted for liveness, and nothing forces it to advance its anchor. In normal operation the anchor trails Tempo by about one block.

| Actor | Capability and trust | Boundary check and failure consequence |
|---|---|---|
| Sequencer | Chooses when to advance the anchor and supplies migration entries. Trusted for liveness. | Can't fake a commitment or skip a migration: `0x05` reads are checked against the anchor's state root, and migration entries against `migrationHeads` at the anchor. It can delay rotations and migrations by not advancing the anchor. |
| Removed owner / retired original key | Holds a key that Tempo no longer accepts. | Keeps zone authority until the zone's anchor includes the rotation or migration. |
| Access key holder | Holds a per-zone grant. | Not revoked by an owner rotation on any chain. Users must revoke it on each zone. |
| Transaction sender | Submits transactions to the zone pool. | Primitive-key transactions read only zone state, and every `0x05` read in an included transaction is charged. An invalid `0x05` transaction can cost the sequencer one Tempo read at admission, after every local check passed, as invalid transactions already cost unpaid signature checks. |
| Tempo user | Can migrate any account it controls. | Each migration pays for its list entry, so growing the list, which every zone must apply, costs at least 500,000 gas per entry. |
| Depositor | Can send funds to any address. | Those funds are usable by the account's current owners. |

Residual risk: staleness is unbounded. A later change could cap how far a zone's anchor may lag before it rejects owner- or root-signed transactions.

# Invariants

- Before any user transaction at an anchor, every migration in Tempo's list at that anchor is in the zone copy.
- A nonzero zone copy equals a commitment that Tempo held for that address at some anchor no later than the current one.
- A primitive signature from an address whose zone copy is nonzero never authorizes a zone action, except where TIP-1113 allows it on Tempo.
- Every `0x05` verification on a zone checks against Tempo's commitment at the transaction's anchor, and fails if it is zero.
- A batch is not provable if it applied migration entries that don't hash to Tempo's `migrationHeads`, or used a commitment read without a valid Tempo account proof.
