# TIP-1154: Configurable Accounts on Zones

## Abstract

Zones accept configurable-account signatures by reading each account's [configuration commitment](./tip-1107.md#commitment-storage) from Tempo at the zone's current Tempo block. Tempo stays the only chain that writes commitments; zones never register, update or migrate accounts. The zone prover checks every commitment read against that Tempo block's state root. The main limitation is lag: a zone applies an owner rotation only once it imports the Tempo block that contains it.

## Motivation

A configurable account on Tempo should work on every zone at the same address, so users keep one account across Tempo and its zones. Owner changes made on Tempo carry over to each zone, with nothing to register or update per zone.

## Assumptions

- Zones already read Tempo state at a finalized, proven Tempo block (the **anchor**, kept by the `TempoState` precompile), as they do for TIP-403 policies. This TIP adds one more kind of read through that same path.
- Address derivation ([TIP-1107](./tip-1107.md#address-derivation)) hashes only the initial configuration, with no chain ID, so a derived address is the same on Tempo and its zones.
- This TIP activates together with the other T14 configurable account components.

# Specification

## Overview

On a zone, an account's **commitment** is the value of Tempo's TIP-1107 commitment for that address at the zone's anchor. Zone state never stores it.

| Operation | Tempo | Zone under this TIP |
|---|---|---|
| Authorize with `0x05` (direct, access key, key authorization) | Allowed | Allowed, checked against Tempo's commitment at the anchor |
| Initial registration | Writes the version-zero hash | No write; an unregistered account is checked by derivation, exactly as on Tempo |
| `updateConfig`, `upgradeAccount` | Allowed | Rejected |
| Original-key retirement (TIP-1113) | Uses the local commitment | Uses Tempo's commitment at the anchor |

Owners rotate keys and migrate accounts only on Tempo. Zones apply those changes once their anchor reaches the Tempo block that contains them.

## Mechanics

### Reading the commitment

1. Every read of an account's commitment during zone execution returns Tempo's commitment for that address at the anchor. This includes transaction authorization, TIP-1113 retirement checks, `verifyConfigurableAccount`, `getConfigCommitment`, TIP-20 `permit`, keychain and channel checks.
2. Zones read Tempo only for an address that can hold a commitment: an address eligible as a TIP-1107 account (not zero, virtual, a precompile or a zone portal) whose zone code is empty. Other addresses have no commitment on the zone, and loading them reads nothing from Tempo.
3. The commitment is read when execution first loads the account, so it is priced by the account access that loads it (see [Gas](#gas)).
4. The anchor is fixed for each transaction, as it is for TIP-403 reads. A transaction after `advanceTempo` in the same zone block sees the new anchor. A commitment read before `advanceTempo` advances the anchor makes the advancement fail.
5. If Tempo state at the anchor can't be read, execution fails closed: the sequencer stops building rather than treating the commitment as zero.

With this, the [TIP-1107 authorization](./tip-1107.md#authorization) rules and the [TIP-1113 retirement](./tip-1113.md#retirement-check) rules apply on zones without changes:

- An account unregistered on Tempo validates a version-zero configuration by derivation.
- A registered or migrated account must match Tempo's commitment.
- A primitive signature from an address with a nonzero commitment is rejected as a retired root.

### Account code

An account whose Tempo commitment at the anchor is nonzero has the [account code marker](./tip-1107.md#account-code) (`0xef`) as its code on the zone, read from Tempo like the commitment and never written to zone state. When such an account changes on the zone, for example when its nonce advances, the zone stores it with its local code and no commitment. Authorization's code-hash check, `EXTCODESIZE`, `EXTCODEHASH`, `EXTCODECOPY`, calls to the account and ERC-1271 then behave as on Tempo, so Permit2 and other verifiers that check for code reject the retired original key. Zone accounts otherwise keep their local code; an account with other code or EIP-7702 delegation on the zone fails authorization as under TIP-1107.

### No writes on zones

- Zones skip initial registration and do not charge its intrinsic gas (the TIP-1107 registration cost or TIP-1000 new-account cost).
- Calls to `updateConfig` ([TIP-1107](./tip-1107.md#owner-updates)) and `upgradeAccount` ([TIP-1113](./tip-1113.md)) revert on zones.
- Zone account leaves keep the four-field encoding and their local code. A state transition that would write a commitment or the account marker into zone state is invalid.

### Gas

Every Tempo read that zone execution makes for a transaction is paid for by that transaction:

- The sender's commitment read costs 2,600 gas of intrinsic gas, the [EIP-2929](https://eips.ethereum.org/EIPS/eip-2929) cold account access cost. The sender is warm by default, so without this charge its read would be free. The charge applies to every transaction at T14, whatever its signature.
- Every other read happens when execution first loads the account, which the account access already charges: cold access for `EXTCODE*`, `BALANCE` and calls, and the role account charges of TIP-1107 authorization for the fee payer, key authorization signer and access key.
- Initial registration happens only on Tempo. Zones charge none of its gas (the TIP-1107 registration cost or the TIP-1000 new-account cost).

### Access keys

Access keys stay per-zone, exactly as on Tempo ([TIP-1111](./tip-1111.md)): a configurable account can grant and use keys on a zone, and an owner rotation does not revoke grants. Users who rotate after a compromise must revoke each zone's grants on that zone.

### Proving

The prover's Tempo witness includes an account proof for each address whose commitment execution read, at each anchor used. Account-leaf decoding accepts the optional [TIP-1107](./tip-1107.md#commitment-storage) fifth field with the same rules as Tempo: tag `0x00`, nonzero hash, and no extra fields. A missing or invalid proof invalidates the batch.

### Zone RPC

- Authorization tokens accept `0x05` signatures, checked with both [TIP-1107 authorization](./tip-1107.md#authorization) steps against the [commitment index](#commitment-index) at the zone's current anchor. The check is a local lookup, with no Tempo read, so derived and migrated accounts reach zone RPC before they grant an access key there.
- Primitive-key tokens apply the [TIP-1113 retirement check](./tip-1113.md#retirement-check) against the [commitment index](#commitment-index), as [TIP-1107](./tip-1107.md#authorization) requires of RPC logins: a token signed by a retired original key is rejected. The check is a local lookup, with no Tempo read.
- Open sessions are rechecked against the index when the anchor advances, and dropped once the account's commitment no longer authorizes the token's signer (a removed owner, or a retired original key), as revoked keychain keys are today.
- `eth_getAccount` on a zone returns no `extension`. Wallets read the commitment from `getConfigCommitment` on the zone, or from Tempo at the zone's anchor.

### Transaction pool

When the anchor advances, the pool revalidates pending transactions whose signing accounts have a commitment that changed at that anchor. Only TIP-1107 owner updates and TIP-1113 migrations change zone authority. Both emit events from the configurable account precompile.

Initial registration changes the stored value but not the authority, since the version-zero configuration is accepted either way. However, gas differs between registered and unregistered accounts ([TIP-1107 gas](./tip-1107.md#gas)), so any cached commitment MUST be exact at the anchor. A cache MAY reuse a commitment read at an earlier anchor, including zero, only if no Tempo block in between changed it, as the [commitment index](#commitment-index) tracks.

### Commitment index

Every zone node keeps an index of Tempo commitments, built from the Tempo blocks it imports. For each address with a nonzero commitment, it records every change with the Tempo block number that made it. Each block changes a commitment only in these ways:

- Registration: an included transaction carrying a configurable-account signature for an account with no entry. Registration persists through failed execution and emits no event, so the index reads it from the transaction, not its receipt. The entry's value is the hash of the configuration in the signature.
- Owner update: `ConfigurableAccountConfigUpdated`, which rolls back with its transaction.
- Migration: `AccountUpgraded`, which rolls back with its transaction.

A read at anchor N returns the address's latest change at or before block N, or zero if it has none. Every read uses the anchor of the zone block being executed, not the newest Tempo block the node imported, so historical `eth_call`, re-execution after a restart and follower replay read the same values the original execution did. Because the index is keyed by Tempo block, zone state and the index never need to roll back together.

Anchors are finalized, so the index never handles Tempo reorgs. Configurable accounts start at T14, so a zone created later builds its index from the Tempo blocks since T14. A node MAY prune changes older than the oldest anchor it serves; a read at an older anchor then falls back to Tempo state at that anchor.

Execution, the transaction pool, RPC simulation and RPC authorization read commitments from the index, with no Tempo round trip. The pool and RPC authorization read at the zone's current anchor. It does not replace proofs: the prover still fetches an account proof for each commitment execution read.

### Forced exits

The forced-exit authorization (`crates/zones/exithatch`) accepts `0x05` signatures for the account under the same rules, and rejects a primitive signature from a retired original key.

## Interfaces

No new interfaces, and no change on Tempo. Zones reuse TIP-1107's `getConfigCommitment` and `verifyConfigurableAccount`.

# Compatibility

| Integration | What changes |
|---|---|
| Wallets and SDKs | Build `0x05` witnesses for zones as for Tempo, using the configuration valid at the zone's anchor. After a rotation, wait for the zone to import it before using the new configuration there. |
| Migrated accounts | The original key loses authority on a zone once it imports the migration. Funds stay at the same address under the account's owners. |
| Derived accounts | Can receive and move funds on zones from first use, with the same address as on Tempo. |
| Zone operators | Nodes keep a [commitment index](#commitment-index) from the Tempo blocks they import. The prover's Tempo state reader must serve account proofs (`eth_getProof` at a block) in addition to storage proofs. |
| Transactions on zones | Every transaction pays 2,600 gas more for its sender's commitment read. |
| Prover | Tempo witnesses grow by one account proof per distinct authorizing account and anchor in a batch. Measure this before scheduling. |

# Observability

Zones add no new state transitions and no events. A [commitment index](#commitment-index) follows Tempo's commitment changes from transactions carrying configurable-account signatures (registration) and from `ConfigurableAccountConfigUpdated` and `AccountUpgraded` events.

# Threat Model

The most consequential risk is a stale anchor. A removed owner, or a retired original key, keeps authority on a zone until the zone imports the rotation. The sequencer is trusted for liveness, and nothing forces it to advance its anchor.

| Actor | Trust boundary |
|---|---|
| Sequencer | Cannot fake a commitment: the prover checks every read against the anchor's state root. It can delay rotations by not advancing the anchor. |
| Removed owner / retired original key | Keeps zone authority until the zone's anchor includes the rotation. |
| Access keys | Not revoked by an owner rotation on any chain. They must be revoked on each zone. |
| Depositors | Can still send funds to any address. Those funds are now usable by the account's current owners. |
| Transaction senders | Pay for every commitment their transaction's execution reads. Gas bounds the number of reads, and the commitment index serves them without Tempo round trips. Each read still adds an account proof to the witness. |
| RPC callers | `eth_call`, `eth_estimateGas` and pool admission run zone execution or checks that no transaction pays for. They read commitments from the [commitment index](#commitment-index), so they cause no Tempo round trip and no proof. |
| Retired original key | Loses zone RPC access once the zone's anchor includes the migration or rotation; open sessions drop at that anchor. |

Residual risk: staleness is unbounded. A later change could cap how far a zone's anchor may lag before it rejects owner- or root-signed transactions.

# Invariants

- For any zone transaction, every commitment read equals Tempo's commitment for that address at the transaction's anchor.
- Zone state never stores a commitment, and no zone transaction changes one.
- A primitive signature from an address whose Tempo commitment at the anchor is nonzero never authorizes a zone action, except where TIP-1113 allows it on Tempo.
- An unregistered derived account on a zone accepts only its version-zero configuration.
- A batch whose execution read a commitment without a valid Tempo account proof is not provable.
