# TIP-1154: Configurable Accounts on Zones

## Abstract

Configurable accounts use weighted owners and a signing threshold to authorize actions. This TIP lets zones accept their signatures by reading each account's [configuration commitment](./tip-1107.md#commitment-storage) from Tempo at the zone's current Tempo block. Tempo stays the only chain that writes commitments; zones never register, update or migrate accounts. The zone prover checks every commitment read against that Tempo block's state root. The main limitation is lag: a zone applies an owner rotation only once it imports the Tempo block that contains it.

## Motivation

A configurable account on Tempo should work on every zone at the same address, so users keep one account across Tempo and its zones. Owner changes made on Tempo carry over to each zone, with nothing to register or update per zone.

## Assumptions

- Zones already read Tempo state at a finalized, proven Tempo block (the **anchor**, kept by the `TempoState` precompile), as they do for TIP-403 policies. This TIP adds one more kind of read through that same path.
- Address derivation ([TIP-1107](./tip-1107.md#address-derivation)) hashes only the initial configuration, with no chain ID, so a derived address is the same on Tempo and its zones.
- This TIP activates together with the other T14 configurable account components.

# Specification

## Overview

Zones read each account's configuration commitment from Tempo at their anchor; they do not store it locally. This hash identifies the account's configuration and determines signature authorization, original-key retirement and the exposed account code.

Owners register accounts, rotate keys and migrate accounts on Tempo. Zones apply those changes when their anchor reaches the corresponding Tempo block.

## Mechanics

### Reading Tempo state

Each transaction uses one anchor for all its Tempo reads, as it does for TIP-403 policies. A transaction after `advanceTempo` in the same zone block sees the new anchor.

When execution first loads an account, it reads the account's commitment from Tempo at that anchor. Only eligible TIP-1107 accounts with empty zone code or an EIP-7702 delegation need this read. The zero address, virtual addresses, precompiles, zone system contracts and the zone portal are ineligible. Contract creation is disabled on zones; every other address with zone code is a TIP-20 token or system contract and has no commitment. Loading those accounts reads nothing from Tempo.

This anchored commitment is used throughout execution: transaction authorization, TIP-1113 retirement checks, `verifyConfigurableAccount`, `getConfigCommitment`, TIP-20 `permit`, keychain and channel checks. If Tempo state at the anchor can't be read, the sequencer stops building. It never substitutes a zero commitment.

### Transaction authorization

Zones accept `0x05` configurable-account signatures for direct authorization, access keys and key authorizations. The [TIP-1107 authorization](./tip-1107.md#authorization) and [TIP-1113 retirement](./tip-1113.md#retirement-check) rules apply unchanged:

- An account unregistered on Tempo validates its initial, version-zero configuration by checking that it derives the account's address.
- A registered or migrated account must match Tempo's commitment.
- A primitive signature from an address with a nonzero commitment is rejected as a retired root.

### Transaction execution

The commitment also determines the code that execution sees. A nonzero Tempo commitment exposes the [account code marker](./tip-1107.md#account-code), `0xef`, on the zone. The marker is read from Tempo like the commitment, never written to zone state. Authorization's code-hash check, `EXTCODESIZE`, `EXTCODEHASH`, `EXTCODECOPY`, calls to the account and ERC-1271 then behave as on Tempo. Permit2 and other verifiers that check for code reject the retired original key. Other accounts retain their local code; accounts with other code or EIP-7702 delegation on the zone fail authorization as under TIP-1107.

Execution can change the account's local state, such as its nonce, but stores the account with its local code and no commitment. A transition that writes a commitment or account marker into zone state is invalid. The persisted account layout is described in [Interfaces](#interfaces).

Unlike Tempo, which writes the version-zero hash on initial registration, zones skip initial registration and its intrinsic gas charges (TIP-1107 registration and TIP-1000 new-account costs). Calls to `updateConfig` ([TIP-1107](./tip-1107.md#owner-updates)) and `upgradeAccount` ([TIP-1113](./tip-1113.md)) revert on zones. Transactions instead pay for their commitment reads through account-access gas:

- Every zone transaction at T14 pays 2,600 extra intrinsic gas for its sender's read, whatever its signature. This is the [EIP-2929](https://eips.ethereum.org/EIPS/eip-2929) cold account access cost; the sender is otherwise warm by default.
- Other authority accounts (separate fee payer, key-authorization signer, access key) each pay one account access under [TIP-1107](./tip-1107.md#gas), covering their reads.
- Other reads are covered when execution loads the account: an EIP-2929 cold access for `EXTCODE*`, `BALANCE` and calls, or the 2,400 intrinsic gas per access-list address. The transaction's `to` and coinbase are warm by default, so at most two commitment reads lack a cold-access payment.

### Batch verification

To prove the resulting batch, the prover includes a Tempo account proof for every address whose commitment execution read, at each anchor used. It decodes Tempo account leaves using the layout in [Interfaces](#interfaces). A missing or invalid proof invalidates the batch.

### Owner changes

An owner update or migration on Tempo takes effect on a zone when its anchor advances to include it. Whenever the anchor advances, the pool revalidates pending transactions whose signing accounts have a commitment that changed at that anchor. Only TIP-1107 owner updates and TIP-1113 migrations change zone authority; both emit events from the configurable account precompile.

Initial registration changes the stored value but not the authority, since the version-zero configuration is accepted either way. However, gas differs between registered and unregistered accounts ([TIP-1107 gas](./tip-1107.md#gas)), so any cached commitment MUST be exact at the anchor.

Access-key grants do not follow owner changes across chains. They stay per-zone, exactly as on Tempo ([TIP-1111](./tip-1111.md)): a configurable account can grant and use keys on a zone, and an owner rotation does not revoke grants. Users who rotate after a compromise must revoke each zone's grants on that zone.

## Interfaces

No new interfaces. Zones reuse TIP-1107's `getConfigCommitment` and `verifyConfigurableAccount`.

Zone account leaves keep the four-field encoding (`nonce`, `balance`, `storageRoot`, `codeHash`) and their local code. Tempo account-leaf decoding accepts the optional [TIP-1107](./tip-1107.md#commitment-storage) fifth field: tag `0x00`, nonzero hash, and no extra fields.

# Compatibility

Zone RPC authorization tokens accept `0x05` signatures against Tempo's commitment at the zone's current anchor. Tokens signed by a retired original key are rejected. Keychain tokens also apply the [TIP-1113](./tip-1113.md#retirement-check) retirement check to the signing key ID: an ordinary signature from a key ID with a nonzero commitment is rejected. Open RPC sessions are rechecked when the anchor advances and dropped if the commitment no longer authorizes them, as revoked keychain keys are today.

`eth_getAccount` on a zone returns no `extension`. Wallets read the commitment through the zone's `getConfigCommitment`, or from Tempo at the zone's anchor.

| Integration | What changes |
|---|---|
| Wallets and SDKs | Build `0x05` witnesses for zones as for Tempo, using the configuration valid at the zone's anchor. After a rotation, wait for the zone to import it before using the new configuration there. |
| Migrated accounts | The original key loses authority on a zone once it imports the migration. Funds stay at the same address under the account's owners. |
| Derived accounts | Can receive and move funds on zones from first use, with the same address as on Tempo. |
| Zone operators | The Tempo state reader must serve account reads (`eth_getAccount` at a block) in addition to storage reads. |
| Transactions on zones | Every transaction pays 2,600 more intrinsic gas for its sender's commitment read. |
| Prover | Tempo witnesses grow by one account proof per distinct authorizing account and anchor in a batch. Measure this before scheduling. |
| Forced exits | The forced-exit authorization (`crates/zones/exithatch`) accepts `0x05` signatures for the account under the [transaction authorization rules](#transaction-authorization), and rejects a primitive signature from a retired original key. |

# Observability

No new events. Owner updates and migrations are observed through the configurable account precompile's `ConfigurableAccountConfigUpdated` and `AccountUpgraded` events on Tempo. Initial registration emits no event: zones observe it from the transaction's configurable-account signature and confirm it with the Tempo account proof at the anchor. Zones add no new state transitions.

# Threat Model

The most consequential risk is a stale anchor. A removed owner, or a retired original key, keeps authority on a zone until the zone imports the rotation. The sequencer is trusted for liveness, and nothing forces it to advance its anchor.

| Actor | Trust boundary |
|---|---|
| Sequencer | Cannot fake a commitment: the prover checks every read against the anchor's state root. It can delay rotations by not advancing the anchor. |
| Removed owner / retired original key | Keeps zone authority until the zone's anchor includes the rotation. |
| Access keys | Not revoked by an owner rotation on any chain. They must be revoked on each zone. |
| Depositors | Can still send funds to any address. Those funds are now usable by the account's current owners. |
| Transaction senders | Pay for the commitment reads their transaction makes, except at most two (`to` and the coinbase), which are warm by default. Gas bounds the number of reads, not their latency: each read missing from the sequencer's cache waits for one Tempo round trip. |
| RPC callers | Zone RPC authorization, `eth_call`, `eth_estimateGas` and pool admission read commitments that no transaction pays for. Zone RPC MUST rate-limit these per authorization token. |

Residual risk: staleness is unbounded. A later change could cap how far a zone's anchor may lag before it rejects owner- or root-signed transactions.

# Invariants

- For any zone transaction, every commitment read equals Tempo's commitment for that address at the transaction's anchor.
- Zone state never stores a commitment, and no zone transaction changes one.
- A primitive signature from an address whose Tempo commitment at the anchor is nonzero never authorizes a zone action, except where TIP-1113 allows it on Tempo.
- An unregistered derived account on a zone accepts only its version-zero configuration.
- A batch whose execution read a commitment without a valid Tempo account proof is not provable.
