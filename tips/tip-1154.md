# TIP-1154: Configurable Accounts on Zones

## Abstract

Each zone keeps a copy of every account's [configuration commitment](./tip-1107.md#commitment-storage) in its own state. Original-key retirement, the account code marker, `EXTCODE*` and transaction pool checks read only that copy. Tempo is read only to verify a `0x05` signature, at most twice per transaction and metered. Tempo records every account whose commitment becomes nonzero in an append-only **activation list**. `advanceTempo` must apply every entry up to its new anchor, so a sequencer can delay a migration but never skip one. Tempo stays the only chain that writes commitments.

## Terms

- **Tempo** is the L1. A **zone** is a chain that settles to Tempo and is run by a **sequencer**, which builds zone blocks, and a **prover**, which proves each batch of zone blocks against Tempo.
- **Configurable account**: an account authorized by a set of owners and a threshold ([TIP-1107](./tip-1107.md)) rather than by one private key. Its **commitment** is the hash of its current configuration, stored on Tempo as an optional fifth field in its account leaf. A zero commitment means the account is not configurable.
- **`0x05` signature**: the signature type a configurable account's owners sign with. It names the configuration it uses, which must hash to the account's commitment.
- **Registration**: the first time Tempo writes a commitment for an account whose address was derived from its first configuration (TIP-1107).
- **Migration**: `upgradeAccount` ([TIP-1113](./tip-1113.md)), which gives an existing key-controlled account a configuration at the same address. `updateConfig` rotates a configured account's owners.
- **Original-key retirement**: once an account's commitment is nonzero, a plain (primitive) signature from its original private key no longer authorizes it (TIP-1113).
- **Account code marker**: the one-byte code `0xef` a configured account has, so contracts that check for code, such as Permit2, treat it as a contract and call ERC-1271 instead of trusting `ecrecover`.
- **Anchor**: the finalized Tempo block a zone currently reads Tempo state at. The sequencer advances it with the `advanceTempo` system call (which also processes deposits) or `advanceTempoHeaders` (which only moves the anchor).

## Motivation

A configurable account on Tempo should work on every zone at the same address, so users keep one account across Tempo and its zones.

Reading the commitment from Tempo on every account load would make almost every zone transaction depend on Tempo, including plain EOAs: any address may have been migrated on Tempo, so each would need a proof that its commitment is zero. The sequencer can cache values, but the prover can't: the witness would need a Tempo account proof per distinct account per anchor, and invalid transactions and fresh addresses would force unmetered Tempo reads for free. A zone copy keeps those checks local, so only accounts that actually sign with `0x05` pay for a Tempo read.

## Assumptions

- Zones already read Tempo state at a finalized, proven Tempo block (the **anchor**, kept by the `TempoState` precompile), as they do for TIP-403 policies and token enablements.
- An account's Tempo commitment never returns to zero once set ([TIP-1107](./tip-1107.md#commitment-storage), [TIP-1113](./tip-1113.md#ordering-and-permanence)).
- Address derivation ([TIP-1107](./tip-1107.md#address-derivation)) hashes only the initial configuration, with no chain ID, so a derived address is the same on Tempo and its zones. If derivation and first-use registration are removed ([#8788](https://github.com/tempoxyz/tempo/pull/8788)), every activation is a TIP-1113 migration and this TIP needs no other change.
- This TIP activates together with the other T14 configurable account components.

# Specification

## Overview

| Operation | Tempo | Zone under this TIP |
|---|---|---|
| Original-key retirement (TIP-1113), account code marker | Uses the local commitment | Uses the zone copy |
| Authorize with `0x05` (direct, access key, key authorization) | Checked against the local commitment | Checked against Tempo's commitment at the anchor (metered); the result is written into the zone copy |
| Initial registration, `upgradeAccount` | Writes the commitment and appends to the activation list | No local write; applied from the activation list by `advanceTempo` |
| `updateConfig` | Allowed | Rejected; the new commitment reaches the zone copy on the account's next `0x05` transaction there |

## Mechanics

### Zone copy

Zone account leaves accept the optional [TIP-1107](./tip-1107.md#commitment-storage) fifth field, with the same encoding rules as Tempo: tag `0x00`, nonzero hash and no extra fields. An account whose copy is nonzero has the [account code marker](./tip-1107.md#account-code) (`0xef`) as its code, unless it already has other code on the zone, in which case it keeps that code and fails authorization as under TIP-1107.

The copy is written only by:

1. `advanceTempo` applying activation list entries ([Activation list](#activation-list)).
2. Transaction authorization, after a `0x05` verification reads a nonzero commitment from Tempo that differs from the copy (including a zero copy) ([Verifying `0x05` signatures](#verifying-0x05-signatures)).

No zone transaction can write it otherwise. `updateConfig` ([TIP-1107](./tip-1107.md#owner-updates)) and `upgradeAccount` ([TIP-1113](./tip-1113.md)) revert on zones, and zones skip initial registration and its intrinsic gas.

These read only the copy and never Tempo:

- the TIP-1113 [retirement check](./tip-1113.md#retirement-check): a primitive signature from an address with a nonzero copy is rejected as a retired root
- authorization's code-hash check, `EXTCODESIZE`, `EXTCODEHASH`, `EXTCODECOPY` and dispatch of calls to the account, so Permit2 and other verifiers that check for code call ERC-1271 instead of trusting the retired original key. The ERC-1271 call itself verifies the `0x05` signature against Tempo, as below, so a removed owner can't sign through a stale copy.
- `getConfigCommitment`, which returns the zone copy
- transaction pool and RPC checks of the above

### Activation list

On Tempo, the configurable account precompile appends `(account, commitment)` to the activation list each time an account's commitment goes from zero to nonzero: TIP-1107 initial registration and TIP-1113 `upgradeAccount`. It stores:

- `activationCount`: the number of entries
- `activationHeads[i]`: the running hash after `i` entries, where `activationHeads[0] = 0` and `activationHeads[i+1] = keccak256(activationHeads[i] ‖ account ‖ commitment)`

Each account appears at most once, since its commitment never returns to zero.

On a zone, the `ZoneInbox` precompile keeps `processedActivationCount` and `processedActivationHead`, both starting at zero. `advanceTempo` takes, as input from the sequencer, the entries added to Tempo's list since the zone's processed position:

1. Fold the supplied entries onto `processedActivationHead`, giving head `h` after `n` entries.
2. Read `activationHeads[n]` from Tempo at the new anchor and require it to equal `h`.
3. Write each entry's commitment into that account's zone copy and set the account code marker as above.
4. Store `n` and `h` as the processed position.

`advanceTempoActivations(entries)` applies the next entries the same way at the current anchor, without advancing it. The sequencer uses it to catch up on a large backlog in several calls. A zone created after T14 starts with such a backlog: the list is global, so the zone's genesis anchor already includes every activation since T14, none of which the new zone has applied yet.

**Completeness.** A zone block MUST NOT contain a user transaction while `processedActivationCount` is below Tempo's `activationCount` at the anchor. A block that does is invalid. This also covers anchors advanced by `advanceTempoHeaders`, which applies no entries. So every activation included by the anchor is in the zone copy before any transaction uses that anchor.

**Gas.** Applying entries is a system operation outside the block gas limit and the inbox gas budget. Each account is applied at most once, and on Tempo each activation already pays for a commitment write, so Tempo's gas limit bounds the entries per Tempo block.

### Verifying `0x05` signatures

Every `0x05` verification on a zone reads the account's commitment from Tempo at the anchor (one account proof) and applies the [TIP-1107 authorization](./tip-1107.md#authorization) rules against it, exactly as on Tempo:

- An account unregistered on Tempo validates a version-zero configuration by derivation.
- A registered or migrated account must match Tempo's commitment.

Each read is charged like a cold account access. Transaction authorization reads once per configurable signer, at most twice per transaction: the outer signer and, when a transaction creates and uses an access-key grant at once, the `key_authorization` parent ([TIP-1111](./tip-1111.md#grant-and-use-in-one-transaction)). Fee payers can't sign with `0x05` ([TIP-1107](./tip-1107.md#supported-contexts)). ERC-1271 `isValidSignature`, `verifyConfigurableAccount` and keychain checks during execution each read and are metered the same way.

If transaction authorization reads a nonzero commitment that differs from the zone copy, the transaction writes it into the copy and sets the account code marker. A derived account that is unregistered on Tempo writes nothing: it reaches the copy through the activation list once Tempo registers it. Verifications during execution never write.

Because verification always checks Tempo, an owner removed by `updateConfig` loses `0x05` authority on a zone once its anchor includes the rotation, even before the copy is updated.

If Tempo state at the anchor can't be read, execution fails closed: the sequencer stops building rather than treating the commitment as zero.

### Access keys

Access keys stay per-zone, exactly as on Tempo ([TIP-1111](./tip-1111.md)): a configurable account can grant and use keys on a zone, and an owner rotation does not revoke grants. Users who rotate after a compromise must revoke each zone's grants on that zone.

### Proving

- The zone copy is zone state, so retirement, marker and `EXTCODE*` reads are covered by the zone's own state witness.
- Each `advanceTempo` and `advanceTempoActivations` adds storage proofs for `activationHeads[n]` and `activationCount` at the anchor.
- Each `0x05` verification adds one Tempo account proof for that account at that anchor.

A missing or invalid proof invalidates the batch.

### Zone RPC

- Authorization tokens accept `0x05` signatures, checked against Tempo's commitment at the zone's current anchor.
- Tokens signed by a retired original key are rejected, using the zone copy.
- Open sessions are rechecked when the anchor advances, and dropped when the commitment no longer authorizes them, as revoked keychain keys are today.
- `eth_getAccount` on a zone returns the zone copy as its `extension`.

### Transaction pool

When the anchor advances, the pool:

- drops pending primitive-key transactions from accounts the new activation entries retired, using the zone copy
- revalidates pending `0x05` transactions from accounts whose commitment changed at that anchor (`ConfigurableAccountConfigUpdated` and `AccountUpgraded` events on Tempo), with a fresh Tempo read

Pool admission of a primitive-key transaction reads only the zone copy. Admission of a `0x05` transaction does one Tempo read per `0x05` signer.

### Forced exits

The forced-exit authorization (`crates/zones/exithatch`) accepts `0x05` signatures for the account under the same rules, and rejects a primitive signature from an address with a nonzero zone copy.

## Interfaces

On Tempo, the configurable account precompile adds:

```solidity
/// Number of accounts whose commitment has gone from zero to nonzero.
function activationCount() external view returns (uint64);

/// Running hash of the activation list after `count` entries.
function activationHeads(uint64 count) external view returns (bytes32);
```

On zones, `ZoneInbox` adds:

```solidity
struct Activation {
    address account;
    bytes32 commitment;
}

function processedActivationCount() external view returns (uint64);
function processedActivationHead() external view returns (bytes32);

/// Apply activation entries at the current anchor without advancing it. Sequencer only.
function advanceTempoActivations(Activation[] calldata activations) external;
```

`advanceTempo` takes a trailing `Activation[] calldata activations` argument.

# Compatibility

| Integration | What changes |
|---|---|
| Wallets and SDKs | Build `0x05` witnesses for zones as for Tempo, using the configuration valid at the zone's anchor. After a rotation, wait for the zone to import it before using the new configuration there. Read the current configuration from Tempo at the zone's anchor: the zone's `getConfigCommitment` can lag a rotation until the account's next `0x05` transaction there. |
| Migrated accounts | The original key loses authority on a zone once `advanceTempo` applies the migration. Funds stay at the same address under the account's owners. |
| Derived accounts | Can receive and move funds on zones from first use, with the same address as on Tempo. The code marker appears on a zone once the zone applies the Tempo registration. |
| Zone operators | The sequencer supplies activation entries with each `advanceTempo`, from the configurable account precompile on Tempo. The Tempo state reader must serve account reads (`eth_getAccount` at a block). |
| Prover | Tempo witnesses add two storage proofs per anchor, plus one account proof per `0x05` verification. |
| Zone genesis | A zone created after T14 starts at processed count zero and catches up with `advanceTempoActivations` before accepting user transactions. |

# Observability

Tempo's configurable account precompile emits `ConfigurableAccountConfigUpdated` and `AccountUpgraded` as before. Its `activationCount` and `activationHeads` show the activation list. Zones expose their position through `processedActivationCount` and `processedActivationHead`, and an operator can compare `processedActivationCount` with Tempo's `activationCount` at the anchor to see how far behind it is.

# Threat Model

The most consequential risk is a stale anchor. A removed owner, or a retired original key, keeps authority on a zone until the zone's anchor includes the rotation or migration (the completeness rule then applies a migration before any transaction at that anchor). The sequencer is trusted for liveness, and nothing forces it to advance its anchor.

| Actor | Trust boundary |
|---|---|
| Sequencer | Cannot fake a commitment or skip an activation: `0x05` reads are checked against the anchor's state root, and activation entries against `activationHeads` at the anchor. It can delay rotations and migrations by not advancing the anchor. |
| Removed owner / retired original key | Keeps zone authority until the zone's anchor includes the rotation or migration. |
| Access keys | Not revoked by an owner rotation on any chain. They must be revoked on each zone. |
| Transaction senders | Can't force unmetered Tempo reads: primitive-key and invalid transactions read only zone state, and each `0x05` read is charged. |
| Depositors | Can still send funds to any address. Those funds are usable by the account's current owners. |

Residual risk: staleness is unbounded. A later change could cap how far a zone's anchor may lag before it rejects owner- or root-signed transactions.

# Invariants

- Before any user transaction at an anchor, every activation in Tempo's list at that anchor is in the zone copy.
- A nonzero zone copy equals a commitment that Tempo held for that address at some anchor no later than the current one.
- A primitive signature from an address whose zone copy is nonzero never authorizes a zone action, except where TIP-1113 allows it on Tempo.
- Every `0x05` verification on a zone checks against Tempo's commitment at the transaction's anchor.
- An unregistered derived account on a zone accepts only its version-zero configuration.
- A batch is not provable if it applied activation entries that don't hash to Tempo's `activationHeads`, or used a commitment read without a valid Tempo account proof.
