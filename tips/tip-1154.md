# TIP-1154: Configurable Accounts on Zones

## Abstract

Zones accept configurable-account signatures by reading each account's [configuration commitment](./tip-1107.md#commitment-storage) from Tempo at the zone's current Tempo block. Tempo stays the only chain that writes commitments; zones never register, update or migrate accounts. The zone prover checks every commitment read against that Tempo block's state root. The main limitation is lag: a zone applies an owner rotation only once it imports the Tempo block that contains it.

## Motivation

A configurable account on Tempo should work on every zone at the same address, so users keep one account across Tempo and its zones. Owner changes made on Tempo carry over to each zone, with nothing to register or update per zone.

## Assumptions

- Zones already read Tempo state at a finalized, proven Tempo block (the **anchor**, kept by the `TempoState` precompile), as they do for TIP-403 policies. This TIP adds one more kind of read through that same path.
- Address derivation ([TIP-1107](./tip-1107.md#address-derivation)) hashes only the initial configuration, with no chain ID, so a derived address is the same on Tempo and its zones.
- This TIP activates together with the other T14 configurable account components.

# Specification

## Overview

On a zone, an account's **commitment** means its [TIP-1107 configuration commitment](./tip-1107.md#commitment-storage): the configuration hash in the fifth field of the account's leaf in Tempo's state trie, read at the zone's anchor. A zero commitment means the account is unregistered. Zone state never stores a commitment.

| Operation | Tempo | Zone under this TIP |
|---|---|---|
| Authorize with `0x05` (direct, access key, key authorization) | Allowed | Allowed, checked against Tempo's commitment at the anchor |
| Initial registration | Writes the version-zero hash and retires the [colliding key](./tip-1107.md#address-derivation) | No write; an unregistered account is checked by derivation, exactly as on Tempo. The colliding key is retired on the zone only once the account registers on Tempo and the anchor includes it |
| `updateConfig`, `upgradeAccount` | Allowed | Revert with `UnsupportedOnZone()` |
| Original-key retirement (TIP-1113) | Uses the local commitment | Uses Tempo's commitment at the anchor |

Owners register, rotate keys and migrate accounts only on Tempo. Zones apply those changes once their anchor reaches the Tempo block that contains them. An account used only on a zone keeps its colliding key live there until it registers on Tempo; users who want the key retired on a zone register on Tempo first.

## Mechanics

### Reading the commitment

1. Every read of an account's commitment during zone execution returns Tempo's commitment for that address at the anchor. This includes transaction authorization, TIP-1113 retirement checks, `verifyConfigurableAccount`, `getConfigCommitment`, TIP-20 `permit`, keychain and channel checks.
2. Zones read Tempo only for an **eligible** address: one whose zone code is empty or an EIP-7702 delegation and that isn't zero, a virtual address, an address with the TIP-20 prefix (`0x20C0` followed by ten zero bytes) or the ZonePortal prefix (`0x5AD0` followed by ten zero bytes), a precompile active on the zone, or a zone system contract. Eligibility depends only on the address and zone state, never on Tempo state, so every zone node charges the same gas; it excludes everything TIP-1107 excludes, since an address with either prefix can never be a configurable account. Contract creation is disabled on zones, so every other address with zone code is a TIP-20 token or system contract and has no commitment; loading it reads nothing from Tempo.
3. The commitment is read when execution first loads the account in a transaction, and is priced as described in [Gas](#gas).
4. The anchor is fixed for each transaction, as it is for TIP-403 reads. Every transaction in a zone block reads Tempo at the anchor set by that block's opening [`advanceTempo`](../zones/specs/spec.md#block-structure) system transaction (a block has exactly one).
5. If Tempo state at the anchor can't be read, execution fails closed: the sequencer stops building rather than treating the commitment as zero.

With this, the [TIP-1107 authorization](./tip-1107.md#authorization) rules and the [TIP-1113 retirement](./tip-1113.md#retirement-check) rules apply on zones without changes:

- An account unregistered on Tempo validates a version-zero configuration by derivation.
- A registered or migrated account must match Tempo's commitment.
- A primitive signature from an address with a nonzero commitment is rejected as a retired root.

### Sequencer commitment index

The sequencer MUST answer commitment reads without a Tempo round trip on the block-building path. It keeps an index of every nonzero commitment on Tempo up to its anchor, updated each time the anchor advances from the configurable account precompile's events in the newly imported Tempo blocks: `ConfigurableAccountConfigUpdated` (including the version-zero event registration emits) and `AccountUpgraded`. Every commitment write emits one of them under the same rollback rules as the write: registration and its event persist when the transaction's calls revert, while a reverted owner update or migration leaves neither. Anchors are finalized, so the index never handles a Tempo reorg. An eligible address missing from the index has a zero commitment. The index is versioned by anchor: it can answer a lookup at any anchor still served by zone RPC (for example by keeping each anchor's changes), so a simulation of an older zone block reads commitments at that block's anchor, not the current one. The index is a cache: the prover still checks every read against a Tempo account proof (see [Proving](#proving)).

### Account code

An eligible account whose Tempo commitment at the anchor is nonzero has the [account code marker](./tip-1107.md#account-code) (`0xef`) as its code on the zone, read from Tempo like the commitment and never written to zone state. When such an account changes on the zone, for example when its nonce advances, the zone stores it with its local code and no commitment. Authorization's code-hash check, `EXTCODESIZE`, `EXTCODEHASH`, `EXTCODECOPY`, calls to the account and ERC-1271 then behave as on Tempo, so Permit2 and other verifiers that check for code reject the retired original key.

The marker replaces a local EIP-7702 delegation too. An account that delegated on a zone and later registers or migrates on Tempo has the marker as its code there once the anchor includes the change, so its owners can authorize with `0x05` and its zone funds stay usable. The delegation stays in the zone leaf but is never executed, and since commitments never return to zero, this is permanent. Authorization-list entries for the account are skipped under TIP-1113's retirement check, so nothing needs to clear the delegation.

### No writes on zones

- Zones skip initial registration and do not charge its intrinsic gas (the TIP-1107 registration cost or TIP-1000 new-account cost).
- The configurable account precompile is active on zones for its read functions (`getConfigCommitment`, `verifyConfigurableAccount`). Calls to `updateConfig` ([TIP-1107](./tip-1107.md#owner-updates)) and `upgradeAccount` ([TIP-1113](./tip-1113.md)) explicitly revert with `UnsupportedOnZone()`.
- Zone account leaves keep the four-field encoding and their local code. A state transition that would write a commitment or the account marker into zone state is invalid.

### Gas

Each commitment read costs `TEMPO_READ_GAS` (8,000) on top of the account's [EIP-2929](https://eips.ethereum.org/EIPS/eip-2929) access cost, because each one adds a Tempo account proof to the batch witness.

- **Sender.** Intrinsic gas adds 2,600 (the cold access the sender skips, since it is warm by default) plus `TEMPO_READ_GAS`, 10,600 in total. It applies to every zone transaction at T14, whatever its signature.
- **Other authority accounts** (separate fee payer, key-authorization signer, access key). [TIP-1107](./tip-1107.md#gas) charges one account access each; intrinsic gas adds `TEMPO_READ_GAS` for each eligible one.
- **`to`.** When the transaction's `to` is eligible, intrinsic gas adds `TEMPO_READ_GAS`, even though `to` is warm by default.
- **Execution.** The first load of any other eligible account in a transaction (`EXTCODE*`, `BALANCE`, calls, or an access-list entry) charges `TEMPO_READ_GAS` on top of its cold or access-list cost. Later loads in the same transaction are warm and charge nothing extra.
- **Coinbase.** The coinbase is warm by default, but when it is eligible, the first load of it in a transaction (`EXTCODE*`, `BALANCE`, a call, or an access-list entry) charges `TEMPO_READ_GAS` and observes its commitment like any other account. Crediting fees to it reads no commitment.
- **Exempt.** System transactions (`advanceTempo`, `advanceTempoHeaders`, `finalizeWithdrawalBatch`), which pay no gas and make no commitment reads.

`TEMPO_READ_GAS` keeps a batch's Tempo witness inside the prover's budget when every block is filled with reads of fresh addresses. A Tempo account proof is about 2.6 KB. A batch has 120 zone blocks of 30M gas each, and the witness limit is about 1.1 GB, so a block can carry at most about 3,500 reads, which needs at least about 8,500 gas per read. The cheapest read is an access-list entry at 2,400 + `TEMPO_READ_GAS` = 10,400 gas, so a 30M block carries at most about 2,880 reads, about 0.9 GB per batch, leaving about 18% of the limit for the rest of the witness. The value assumes today's Tempo state size: each 10× growth in Tempo accounts adds about 0.45 KB per proof, and the constant should be revisited with it.

### Access keys

Access keys stay per-zone, exactly as on Tempo ([TIP-1111](./tip-1111.md)): a configurable account can grant and use keys on a zone, and an owner rotation does not revoke grants. Users who rotate after a compromise must revoke each zone's grants on that zone.

### Proving

The prover's Tempo witness includes an account proof for each address whose commitment execution read, at each anchor used; for an unregistered address it proves the leaf has no fifth field, or that the account doesn't exist. Account-leaf decoding accepts the optional [TIP-1107](./tip-1107.md#commitment-storage) fifth field with the same rules as Tempo: tag `0x00`, nonzero hash, and no extra fields. A missing or invalid proof invalidates the batch.

Witness size grows with distinct eligible accounts read × anchors. The first proof of an account is about 2.6 KB, and the same account at another anchor in the batch adds about 0.45 KB, since most trie nodes are shared. A 60-second batch with 6,000 distinct senders adds about 16 MB; reaching the 1.1 GB limit would take about 400,000 distinct senders in one batch, which [Gas](#gas) prices out. Fetching 1,000 proofs from a Tempo node takes about 200 ms.

### Zone RPC

- Authorization tokens accept `0x05` signatures, checked against Tempo's commitment at the zone's current anchor.
- Tokens signed by a retired original key are rejected. Keychain tokens apply the [TIP-1113](./tip-1113.md#retirement-check) check to the signing key ID too: an ordinary signature from a key ID with a nonzero commitment is rejected.
- Open sessions are rechecked when the anchor advances, and dropped when the commitment no longer authorizes them, as revoked keychain keys are today.
- Zone RPC reads commitments from the sequencer's [commitment index](#sequencer-commitment-index) at the anchor of the zone block it executes against, never with a Tempo round trip per request. It rate-limits token authentication, `eth_call` and `eth_estimateGas` per connection and per source IP before reading any commitment, since authorization tokens cost nothing to mint.
- `eth_getAccount` on a zone returns no `extension`. Wallets read the commitment from `getConfigCommitment` on the zone, or from Tempo at the zone's anchor.

### Transaction pool

When the anchor advances, the pool revalidates pending transactions whose signing accounts' commitments changed at the new anchor, taking the changed accounts from the [commitment index](#sequencer-commitment-index) update. Three changes affect zone authority:

- A TIP-1107 owner update replaces the accepted configuration.
- A TIP-1113 migration retires the original key.
- An initial registration retires the colliding key. It emits `ConfigurableAccountConfigUpdated` at version zero.

Gas also differs between registered and unregistered accounts ([TIP-1107 gas](./tip-1107.md#gas)), so a cached commitment MUST be exact at the anchor.

### Forced exits

Forced exits aren't enabled on zones. When they are, their authorization MUST accept `0x05` signatures and reject a retired original key under the rules above, reading Tempo's commitment at the zone's anchor, not Tempo's latest state.

## Interfaces

Zones reuse TIP-1107's `getConfigCommitment` and `verifyConfigurableAccount`. The configurable account precompile adds one error, used only on zones:

```solidity
error UnsupportedOnZone();
```

## Rationale

Zones could instead keep their own copy of each commitment and read Tempo only for `0x05` verification. That makes plain EOA transactions cheaper to prove while most senders are EOAs, but the saving disappears as configurable accounts become the norm, because every configurable-account transaction still needs a Tempo proof. A copy also adds permanent zone state that grows with Tempo's accounts, a migration list on Tempo, and new `advanceTempo` rules, none of which can be removed later. Witnesses are ephemeral and can be compressed. Reading from Tempo can still move to a copy later; a copy couldn't move back.

# Compatibility

| Integration | What changes |
|---|---|
| Wallets and SDKs | Build `0x05` witnesses for zones as for Tempo, using the configuration valid at the zone's anchor. After a rotation, wait for the zone to import it before using the new configuration there. |
| Migrated accounts | The original key loses authority on a zone once it imports the migration. Funds stay at the same address under the account's owners, including accounts that had an EIP-7702 delegation on the zone. |
| Derived accounts | Can receive and move funds on zones from first use, with the same address as on Tempo. Until the account registers on Tempo and the zone imports that block, its colliding key also controls the address on the zone. |
| Zone operators | The Tempo state reader must serve account proofs at a block in addition to storage reads, and the sequencer keeps the [commitment index](#sequencer-commitment-index). |
| Transactions on zones | Every transaction pays 10,600 more intrinsic gas for its sender's commitment read, and `TEMPO_READ_GAS` for each other eligible account it reads. |
| Prover | Tempo witnesses grow by about 2.6 KB per distinct eligible account read, plus about 0.45 KB for each further anchor it is read at, bounded per block by `TEMPO_READ_GAS` (see [Proving](#proving)). |

# Observability

No new events. Every commitment change on Tempo is observed through the configurable account precompile's events: `ConfigurableAccountConfigUpdated` for initial registration (at version zero, persisting when the transaction's calls revert) and owner updates, and `AccountUpgraded` for migrations. The Tempo account proof at the anchor confirms each read. Zones add no new state transitions.

# Threat Model

The most consequential risk is a stale anchor. A removed owner, or a retired original key, keeps authority on a zone until the zone imports the rotation. Every full zone block imports exactly one child of the previous Tempo block and can't skip ancestry, so the anchor can fall behind only while the sequencer stalls the zone. Proving doesn't force freshness: reads are checked against the anchor's state root, not Tempo's latest. After a stall, the sequencer can keep the lag instead of catching up.

| Actor | Trust boundary |
|---|---|
| Sequencer | Cannot fake a commitment: the prover checks every read against the anchor's state root. It can delay rotations only by stalling the zone, then keeping the lag. |
| Removed owner / retired original key | Keeps zone authority until the zone's anchor includes the rotation. |
| Colliding key of a derived account | Controls the address on a zone until the account registers on Tempo and the zone's anchor includes it, including through Permit2. |
| Access keys | Not revoked by an owner rotation on any chain. They must be revoked on each zone. |
| Depositors | Can still send funds to any address. Those funds are now usable by the account's current owners. |
| Transaction senders | Pay `TEMPO_READ_GAS` for every commitment read their transaction makes, including reads of the coinbase. The index removes Tempo round trips from block building, so reads cost witness size, not sequencer latency. |
| RPC callers | Zone RPC authorization, `eth_call`, `eth_estimateGas` and pool admission read commitments that no transaction pays for. They read only the index, and are rate-limited per connection and source IP. |

Residual risk: a stall can leave a zone's anchor arbitrarily stale. A later change could cap how far a zone's anchor may lag before it rejects owner- or root-signed transactions.

# Invariants

- For any zone transaction, every commitment read equals Tempo's configuration commitment for that address at the transaction's anchor.
- Zone state never stores a configuration commitment or the account marker, and no zone transaction changes one.
- A primitive signature from an address whose Tempo commitment at the anchor is nonzero never authorizes a zone action, except where TIP-1113 allows it on Tempo.
- An eligible account whose Tempo commitment at the anchor is nonzero has the account marker as its code on the zone, whatever its local code.
- An unregistered derived account on a zone accepts only its version-zero configuration.
- A batch whose execution read a commitment without a valid Tempo account proof is not provable.
