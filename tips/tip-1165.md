# TIP-1165: Pre-Authorized Access Key Signatures

## Abstract

An access key signature verifies today only after a transaction registers the access key in the AccountKeychain. This TIP defines a **pre-authorized signature**: a keychain signature and the signed `key_authorization` for its access key, joined in one byte string that ends with the 32-byte magic `0x1165…1165`. A verifier accepts it if the access key is active onchain, or if the `key_authorization` would still register the access key at the block it verifies against.

The rule is an offchain convention. It changes no consensus rule, and the onchain `verifyKeychain` does not accept the format.

## Motivation

A wallet commonly returns a signed `key_authorization` to an app without sending a transaction. The first transaction that the access key signs carries the `key_authorization` and registers the access key. Until then the AccountKeychain holds no record of the access key, so [`verifyKeychain`](./tip-1020.md) returns false for every message that it signs.

Apps hit this gap whenever a signature is needed before a transaction:

- **Payment proofs.** A server asks a client to prove control of an account before it serves a paid resource. The client holds only an access key. The proof fails until the client spends gas on an unrelated transaction to register the access key.
- **Sign-in.** A server verifies a signed challenge from a session's access key. [TIP-1053](./tip-1053.md) covers one challenge through the witness. Later challenges in the same session have no path.
- **Offchain orders and intents.** A verifier checks a signed message that settles later, in the transaction that also registers the access key.

In each case the root key has already approved the access key, with a signature that anyone can check. The verifier only lacks a standard way to receive that approval and a standard rule for when to accept it.

Ethereum solved the same shape of problem for undeployed contract accounts with ERC-6492, and for undelegated EOAs with ERC-8010. Both append data and a magic suffix to the signature. This TIP does the same for an unregistered access key.

Alternatives considered:

- **A new signature type byte.** A type such as `0x06` puts an offchain-only format in the ID space of transaction signatures. Nodes must then reject it explicitly.
- **A new `SignatureVerifier` function.** It is the right home for onchain verification, but it needs a hardfork, and offchain verifiers gain nothing from it. It can follow in a separate TIP and reuse this encoding.
- **Register first.** The app sends a transaction before the first signature. It costs gas and a confirmation for a step that the user does not see as a transaction.

## Assumptions

- The verifier reads chain state through a node that it trusts, at a reference block of its choice. A stale or dishonest node can hide a revocation or a burned witness.
- A result holds for the reference block only. It is not a promise that the access key registers later, as a `verifyKeychain` result is not a promise that the access key stays active.
- The signed message carries its own replay protection and domain separation, as with any other signature.
- The `key_authorization` checks in [Verification](#verification) mirror the transaction path. A hardfork that changes those checks changes the verification rule with it. An implementation that falls behind accepts or refuses signatures that the chain does not.

# Specification

## Overview

| Term | Meaning |
|---|---|
| Account | The address that the signature claims to sign for. |
| Access key | The key identified by `key_id` in the `key_authorization`. |
| Keychain signature | A V2 keychain signature, `0x04 ‖ user_address ‖ inner_signature`, as in the Tempo Transaction specification. |
| Signed key authorization | `rlp([key_authorization, signature])`, as in the `key_authorization` field of a Tempo Transaction. |
| Pre-authorized signature | The encoding in [Encoding](#encoding). |
| Reference block | The block whose state and timestamp the verifier uses. |

A pre-authorized signature is valid for `(account, hash)` if and only if one of these holds at the reference block:

1. **Registered.** The keychain signature passes `verifyKeychain(account, hash, keychain_signature)`.
2. **Registrable.** The keychain signature is a correct signature by the access key, and a transaction from the account that carries the signed key authorization would pass every `key_authorization` check.

The format is for verifiers of signed messages. It is never a transaction signature, and a node must not accept it as one.

## Encoding

```
pre_authorized_signature = rlp([keychain_signature, signed_key_authorization]) ‖ magic

keychain_signature        = 0x04 ‖ account ‖ inner_signature
signed_key_authorization  = rlp([key_authorization, signature])
key_authorization         = rlp([chain_id, key_type, key_id, expiry?, limits?, allowed_calls?, witness?, is_admin?, account?])
magic                     = 0x1165116511651165116511651165116511651165116511651165116511651165
```

- `magic` is the TIP number, `0x1165`, repeated 16 times.
- `keychain_signature` is an RLP byte string. Its inner signature signs `keccak256(0x04 ‖ hash ‖ account)`, as for any V2 keychain signature.
- `signed_key_authorization` is a nested RLP list, not a byte string. Its bytes equal the `key_authorization` field of the transaction that registers the access key.
- The outer list has exactly two items. The RLP must be canonical, with no bytes between the list and `magic`.

The signer wraps the same keychain signature that it produces without this TIP. Once the access key is registered, the signer should return the plain keychain signature.

### Example

## Verification

Inputs are `account`, `hash`, `signature`, and a reference block. The default reference block is the latest block. The result is a boolean. Every failure, including a decode failure, returns false.

1. If the last 32 bytes of `signature` do not equal `magic`, the signature is not pre-authorized. Verify it as before this TIP.
2. Remove `magic`. RLP-decode the rest into `keychain_signature` and `signed_key_authorization`, under the rules in [Encoding](#encoding).
3. Call `verifyKeychain(account, hash, keychain_signature)` at the reference block. If it returns true, return true. The signed key authorization is not consulted.
4. Check the keychain signature:
   - Its type is `0x04`, and its `user_address` equals `account`.
   - Its inner signature is a primitive signature: secp256k1, P256, or WebAuthn.
   - The key recovered from the inner signature over `keccak256(0x04 ‖ hash ‖ account)` equals `key_id`.
   - The type of the inner signature equals `key_type`.
5. Check the signed key authorization as the transaction path checks it for a transaction from `account`:
   - `chain_id` equals the chain ID.
   - `key_id` is not the zero address.
   - `account`, if present, equals the account.
   - `is_admin` is not set.
   - `expiry`, if present, is greater than the timestamp of the reference block.
   - `signature` is a valid root signature for the account over `digest = keccak256(rlp(key_authorization))`:
     - For a primitive signature, `verify(account, digest, signature)` returns true and `isAdminKey(account, account)` returns true. The second call fails for a root key that a configuration commitment retired.
     - For a configurable account signature, `verifyConfigurableAccount(account, digest, signature)` returns true.
6. Check the state of the AccountKeychain:
   - `getKey(account, key_id)` returns `keyId == address(0)` and `isRevoked == false`. The access key was never registered and never revoked.
   - If `witness` is present, `isKeyAuthorizationWitnessBurned(account, witness)` returns false.
7. Return true.

Steps 3 to 6 read state at one reference block. A verifier can batch the reads in one call.

A verifier applies its own policy after step 7. The decoded `key_authorization` gives it the expiry, limits, and call scopes of the access key, and the witness. On the registered path, the verifier reads them from the AccountKeychain instead.

### Why registration state matters

Step 6 is what makes the result track the chain. Each row is a state in which the signed key authorization can no longer register the access key.

| State | Transaction path | Result |
|---|---|---|
| Access key registered and active | n/a | True, at step 3 |
| Access key registered and expired | `KeyAlreadyExists` | False |
| Access key revoked | `KeyAlreadyRevoked` | False |
| Witness burned | Witness check fails | False |
| Authorization expired | `expiry` check fails | False |
| Root key retired by a configuration commitment | Signer check fails | False |

## Invalidation

An account that wants to stop a pre-authorized signature before registration has two tools:

- Burn the witness with `burnKeyAuthorizationWitness` ([TIP-1053](./tip-1053.md)). It applies only to an authorization that has a witness.
- Register the access key, then revoke it with `revokeKey`. `revokeKey` reverts with `KeyNotFound` for an access key that was never registered.

Wallets should include a `witness` and an `expiry` in every `key_authorization` that an app may use before registration.

## Scope limits

- A configurable account as the access key (inner signature type `0x05`) is out of scope. A later TIP can extend step 4.
- A V1 keychain signature (`0x03`) is never valid in this format.
- A `key_authorization` signed by an admin access key is never valid, including on networks before [TIP-1137](./tip-1137.md) activates.
- Onchain verification is out of scope. A contract that calls `verifyKeychain` or `isValidSignature` with a pre-authorized signature gets a failure.

## Interfaces

This TIP adds no precompile function, event, error, or storage. A verifier uses these existing views:

| Precompile | Function | Step |
|---|---|---|
| SignatureVerifier | `verifyKeychain(address account, bytes32 hash, bytes signature)` | 3 |
| SignatureVerifier | `recover(bytes32 hash, bytes signature)` | 4 |
| SignatureVerifier | `verify(address signer, bytes32 hash, bytes signature)` | 5 |
| AccountKeychain | `isAdminKey(address account, address keyId)` | 5 |
| SignatureVerifier | `verifyConfigurableAccount(address account, bytes32 hash, bytes signature)` | 5 |
| AccountKeychain | `getKey(address account, address keyId)` | 6 |
| AccountKeychain | `isKeyAuthorizationWitnessBurned(address account, bytes32 witness)` | 6 |

A verifier may recover primitive signatures locally instead of calling `recover` and `verify`.

# Compatibility

No node, transaction, or precompile behavior changes. Adoption is in signers and verifiers.

| Integration | What changes |
|---|---|
| Signers (Viem and `ox` access key accounts) | Return a pre-authorized signature from message and typed data signing while the account holds an unregistered signed key authorization. Return the plain keychain signature after registration. |
| Offchain verifiers (Viem `verifyHash`, `verifyMessage`, `verifyTypedData`) | Detect `magic` and run [Verification](#verification). The Tempo check runs before the ERC-6492 and ERC-8010 checks, whose magic values differ. |
| Servers that verify proofs from access keys | Accept a pre-authorized signature where they accept a keychain signature today. |
| Verifiers without this TIP | Fail to parse the signature and return false. The failure is closed. |
| Contracts | No change. See [Scope limits](#scope-limits). |

The `ox` signature envelope has its own internal magic suffix, `0x77` repeated 32 times, which `ox` removes before a signature leaves the library. It is unrelated to this format and never appears inside it.

A plain keychain signature cannot be mistaken for a pre-authorized signature. A secp256k1 or P256 inner signature ends in a recovery or pre-hash byte. A WebAuthn inner signature ends in a public key coordinate, which equals `magic` with negligible probability.

# Observability

N/A. Verification is offchain and emits nothing. Registration of the access key emits the existing `KeyAuthorized` event, and a burned witness emits the existing `KeyAuthorizationWitnessBurned` event.

# Threat Model

The most consequential attack is a signature accepted for an access key that the account has tried to stop. Before registration the account cannot call `revokeKey`, so the window stays open until the authorization expires, its witness is burned, or the account registers and revokes the access key. See [Invalidation](#invalidation).

| Actor | Controls | Enforcing check | Consequence of failure |
|---|---|---|---|
| Holder of the access key | The access key and the signed key authorization | Steps 4 and 5: the root key signed the authorization for this access key, chain, and account | None beyond the authority that the root key granted. The holder can already register the access key with one transaction and then pass `verifyKeychain`. |
| Holder of only the signed key authorization, such as a past verifier | A public approval | Step 4: the inner signature must come from the access key | None. Only a transaction from the root key or from the access key itself can register the authorization. |
| Holder of a stopped access key | An access key that was revoked or whose witness was burned | Step 6 | The verifier accepts a signature that the chain refuses. |
| Node behind the verifier | The state that the verifier reads | None. See Assumptions. | A hidden revocation or burned witness. |

Residual risks:

- **No limits on messages.** Spending limits and call scopes bind transactions, not signed messages. This matches `verifyKeychain`. A verifier that needs a narrower grant reads the limits and scopes from the decoded authorization and applies its own policy.
- **Disclosure.** The verifier learns the expiry, limits, call scopes, and witness of the access key before they are onchain.
- **Divergence.** A verifier that omits a check in step 5 or 6 accepts a signature that can never register. Implementations must cover every row of the table in [Why registration state matters](#why-registration-state-matters).
- **Size.** A signed key authorization with many call scopes is large. A verifier should bound the signature length before it decodes.

# Invariants

- A signature that does not end in `magic` verifies exactly as before this TIP.
- A pre-authorized signature is valid only if the root key, or the owner quorum, of the account signed a `key_authorization` for the key that signed the message.
- If verification returns true on the registrable path at a block, a transaction from the account that carries the same signed key authorization passes every `key_authorization` check in the next block, unless that block's timestamp reaches `expiry` or an earlier transaction in it changes the AccountKeychain state of the account.
- If the access key is revoked, expired in the AccountKeychain, or bound to a burned witness, verification returns false.
- A pre-authorized signature for one account, chain, or hash is invalid for any other.
- Decoding never accepts trailing bytes, a non-canonical RLP encoding, or a list with more or fewer than two items.
- A node rejects a transaction whose signature is a pre-authorized signature.

Test cases must cover: each row of the registration state table; each primitive key type; a `key_type` that differs from the inner signature type; a `user_address`, `account` field, or `chain_id` mismatch; an authorization signed by a key other than the root; a configurable account as the root; the registered path with an unrelated authorization attached; and the example vector above.
