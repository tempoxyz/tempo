# TIP-1147: Top-of-Block Operator Lane

## Abstract

This TIP adds a privileged lane for a small set of registered operators. An operator connects to
the validators as an authenticated commonware peer, learns who leads each round the moment the
leader starts proposing, and streams signed transactions directly to that leader. The leader
executes them first in its block, after start-of-block system work and before any pool
transaction. Each maker holds one slot per block, and a newer transaction replaces the older one.

Nothing changes in consensus or execution rules. The lane is a proposer policy configured per
validator.

## Motivation

Market makers on Tempo quote continuously. What they need from the chain is simple: the latest
quote (or cancel) lands first in the next block, and stale quotes never land.

Today they cannot get that:

- The builder orders the pool by effective tip. Position is whatever you outbid, until someone
  outbids you.
- Replacing a pending transaction requires a fee bump. A maker re-quoting fifty times a second
  ratchets its own fees up.
- The pool gossips. Every quote is visible to every peer and to anyone watching the mempool, and
  any validator can include a stale one.
- The leader is not known far in advance. The VRF leader of view `v` is derived from the
  certificate of view `v-1`, so the earliest anyone can know it is when that certificate exists.

Faster delivery alone does not fix this. Getting to the leader first reserves nothing if the
builder still sorts by tip. Position has to be an explicit builder policy, and the transactions
have to bypass the pool to get it.

## Assumptions

- Operators are few, known, and contractually accountable. The registry owner decides who they are.
- The registry is an ordinary contract. Validators only read it; no execution rule depends on it.
- The leader honors the lane. Other validators do not check block order, so a leader can ignore or
  reorder the lane without being slashed. This TIP does not change that.
- Makers sign their own transactions. An operator relays and orders them; it cannot forge them.
- Commonware may drop messages. Every submission is acknowledged at the application layer.

# Specification

## Roles

| Role | What it is |
|---|---|
| Operator | Holder of an ed25519 key listed in the registry contract. Connects as a secondary peer. |
| Maker | The recovered signer of a lane transaction. One slot per maker and nonce key per block. |
| Leader | The validator proposing the current round. Opens the lane and builds the block. |

## Registry

The registry is `TopOfBlockRegistry`, a plain Solidity contract with an OpenZeppelin-style
`Ownable` owner. Not a precompile.

```solidity
struct Operator {
    bytes32 publicKey;      // ed25519 consensus identity
    string  ip;             // IP the operator connects from
    uint64  expiresAt;      // unix seconds; 0 never expires
    uint32  maxTxsPerBlock;
    uint64  maxGasPerBlock;
}

uint64 public windowMs;                                     // 0 disables the lane
function operators() external view returns (Operator[] memory);
function setOperator(Operator calldata operator) external;  // onlyOwner, upsert by publicKey
function removeOperator(bytes32 publicKey) external;        // onlyOwner
function setWindowMs(uint64 windowMs) external;             // onlyOwner
```

Every change emits an event: `OperatorSet`, `OperatorRemoved`, `WindowSet`, `OwnershipTransferred`.

Validators started with `--consensus.top-of-block-registry <ADDRESS>` read `windowMs()` and
`operators()` with a static call against their latest finalized block, every time the peer manager
reads the validator set. Every validator therefore sees the same operators and window at the same
height. If a read fails, the previous registry stays in effect.

Listed operators are added to the secondary peer set, excluding keys that are already primary.
Secondary peers may connect inbound; validators never dial them. An expired operator stays a peer
but every submission is refused. Entries with an invalid key or IP are skipped.

A leader opens its lane only if `windowMs` is non-zero and at least one operator is active, so an
empty registry costs nothing. Without the flag, nothing in this TIP is active and the channel is not
registered.

## Channel

Channel `6`, quota 2048 messages per second per peer, size-limited like every other consensus
channel.

| Message | Direction | Fields |
|---|---|---|
| `Submit` | operator → leader | `epoch`, `view`, `id`, `txs: [(tx, seq, expires_at_ms)]` (≤ 1024 txs, ≤ 128 KiB each) |
| `Ack` | leader → operator | `epoch`, `view`, `id`, `status`, `accepted`, `replaced`, `rejected`, `since_open_us` |

`status` is `Ok`, `NotOpen` (round already passed, or too many rounds pending), `Closed` (builder
already took the lane), or `Unauthorized`. Messages use commonware codec with a one-byte tag.

There is no leader announcement. Validators already broadcast their consensus certificates to every
connected peer, operators included. The operator verifies them against the epoch's DKG outcome
(read from the boundary block's `extraData`) and runs the same elector the validators run: the
leader of view `v + 1` comes from the VRF seed of any certificate of view `v`. Notarization,
nullification, and finalization of a view sign the same seed, so the first one to arrive is enough.
The operator knows the leader exactly when the validators do, and nothing on the channel can lie
about it.

The first view of an epoch has no previous certificate in that epoch. Operators skip it in v1;
that block is built from the pool.

There is no build report either. The leader broadcasts its proposed block to every connected peer,
operators included; its header's consensus context names the round and proposer. The operator
reads the lane back from the block's leading transactions it streamed. That is the actual
proposal, not a claim about it, and it is what the operator uses to clear landed slots and advance
maker nonces before the block finalizes.

## Round

```text
leader of v                              operator
  │── certificate(v-1) ─────────────────────▶│ (every validator broadcasts it)
  │                                          │ verify, elect leader(v)
  │◀──────────────────── Submit{v, txs} ─────│ flush latest tx of every maker
  │── Ack ──────────────────────────────────▶│
  │ propose(v, parent)                       │
  │── open lane(v, window) ──────────────────│ (keeps what already arrived)
  │◀──────────────────── Submit{v, txs} ─────│ stream each new tx immediately
  │   ...                                    │
  │ builder: system txs                      │
  │ builder: take lane (waits for window)    │
  │── Ack{Closed} ──────────────────────────▶│ stop streaming to this leader
  │ builder: lane txs, then pool             │
  │── proposed block (broadcast) ───────────▶│ read the lane prefix, clear landed slots
```

The operator and the leader learn about view `v` from the same certificate, so the first flush
usually lands before the leader starts proposing. The leader opens the lane when it starts
building, before the parent finishes executing and before the payload job starts; the window runs
from there.

## Lane

- A validator keeps submissions for rounds it has not opened yet, up to 4 rounds, and discards
  rounds earlier than the last one it opened. Opening a round keeps what already arrived for it.
- A submission is refused for a round earlier than the last opened one, or after the builder takes
  the lane.
- The slot key is `(signer, nonce_key)`. A maker quotes several markets independently by using a
  nonce key per market; Ethereum transaction types use nonce key `0`.
- Every submitted transaction carries a replacement `seq`. It replaces the slot's transaction only
  if its `seq` is strictly higher, so the latest quote wins regardless of arrival order. The slot
  keeps its position. Slots are ordered by when they were first filled in the round.
- Every submitted transaction may carry `expires_at_ms`. The builder drops it unless the block's
  timestamp is earlier. For Tempo transactions, `valid_before` enforces the same at execution.
- A slot belongs to the operator that filled it. Another operator's transaction for that slot is
  rejected.
- `max_txs_per_block` bounds an operator's slots. `max_gas_per_block` bounds the sum of gas limits
  over its slots, replacements included.
- Transactions that fail to decode or recover, or do not raise their slot's `seq`, are counted as
  `rejected` and dropped.

## Builder

1. Apply pre-execution changes (start-of-block system work).
2. Start pool prewarming.
3. Take the lane for `(epoch, view)` from the payload attributes' consensus context. This blocks
   until `window_ms` after the lane opened. The wait is recorded as idle time, so it does not count
   as validation work.
4. Execute lane transactions in slot order. They bypass prewarming and parallel planning, so their
   order is the same in every builder mode, and they are not subject to the build-time budget.
5. Fill from the pool as today.

A lane transaction that is invalid at execution time (stale nonce, insufficient fee token balance,
over the block gas limit) is skipped. It is never handed to the pool. An empty, late, or
fully-invalid lane builds an ordinary block. Rebuilding the same round takes nothing: the lane is
taken once.

## Activation and Compatibility

No hardfork. The registry is deployed with an ordinary transaction, and blocks with a lane prefix are
ordinary blocks that verify on every node. Validators without the flag neither open lanes nor
register the channel, so a partially configured network is fine: operators simply get no lane in
rounds led by unconfigured validators.

## Alternatives Considered

- **Pool with a high tip.** Position is not reserved, replacement needs fee bumps, and quotes gossip
  to everyone. Rejected.
- **Broadcast to every validator.** Removes the need to know the leader, at five times the
  bandwidth, and lets non-leaders see and leak flow they will never include. Rejected for v1.
- **Consensus-enforced prefix.** Validators would reject blocks that drop or reorder the lane. That
  needs the lane commitment in the block and a verification rule. Deferred until the policy proves
  out.
- **Local configuration file.** Each validator keeps its own copy, so validators can disagree on who
  is an operator, and every change needs a restart. Rejected.
- **Registry precompile, or operators in `ValidatorConfigV2`.** A canonical protocol address, at the
  cost of a hardfork. Deferred; nodes would only change where they read from.
- **Auction.** The end state for allocating the right. Deferred; it can sit behind the registry
  owner.

# Tooling

- `tempo node --consensus.top-of-block-registry <ADDRESS>` enables the lane.
- `tempo-xtask generate-localnet --top-of-block-operator <KEY>@<IP>` deploys the registry in genesis,
  owned by the first generated account, and writes its address next to the genesis.
- `tempo_consensus::top_of_block::start_operator_network` gives operators a ready connection, the
  channel, and the certificate and proposal streams; `leader::EpochLeaders` verifies a certificate
  and elects the next leader; `decode_proposal` reads a broadcast block; `wire` exposes the message
  types. Operators must ping at the validators' `--consensus.wait-before-peers-reping` (50s by
  default): each side stops reading a connection while the other pings more often than half its
  own period, so a mismatch delays every submission behind the pings.
- `tempo-tob-operator` serves `tempo_sendTobTransaction(rawTx, { seq?, expiresAt? })` over
  JSON-RPC. It returns the slot, sequence, and the validator the transaction was streamed to, and
  refuses stale and expired submissions. Without `seq`, the slot's next sequence is used.
- `tempo-tob-operator` is also a reference operator: it signs quotes for N makers at a configurable
  rate, streams them to each leader, sends high-tip public traffic as a control, verifies each block
  through another validator's RPC, and serves a dashboard.

# Observability

The `Built payload` log line carries `top_of_block_taken`, `top_of_block_included`, and
`top_of_block_wait`. Before testnet, these MUST also be metrics:

| Metric | Question it answers |
|---|---|
| lane transactions taken / included per block | Is the lane being used, and are operators sending valid transactions? |
| lane wait per block | How much build time does the window cost? |
| submissions by `status` per operator | Are operators late, unauthorized, or sending to non-leaders? |
| `since_open_us` of the first submission per round | How fast does flow reach the leader? |

# Threat Model

- **Registry owner.** Decides who gets the privilege and on what limits. Should be a multisig or
  governance contract on public networks. Changes take effect at the next finalized block.
- **Operator.** Authenticated, bounded by its limits, and able to see the public mempool. It can
  front-run public transactions it observes, because its lane executes first. That is the privilege
  being granted. Who gets it, and on what terms, is a governance decision outside this TIP.
- **Leader.** Can ignore, reorder, or leak the lane. Unenforced in v1. The broadcast proposal and the
  dashboard's RPC check make deviations visible, not impossible. It cannot misdirect flow: operators
  elect leaders from verified certificates, not from anything a validator claims.
- **Other validators.** Receive no lane traffic. They do receive the operator as a secondary peer,
  and their `Recipients::All` consensus broadcasts reach it; that is extra outbound bandwidth, not
  extra authority. The operator relies on that: the certificates are how it learns the leader.
- **Makers.** A maker can only be ordered by the operator that opened its slot in the round.
- **Public users.** Pay the window: up to `window_ms` less pool execution time in blocks proposed by
  configured validators, under a full pool.

# Invariants

- Lane transactions are the first non-system transactions of a block built with an open lane.
- At most one lane transaction per slot `(signer, nonce_key)` per block.
- A slot's transaction is only ever replaced by one with a higher `seq`.
- No lane transaction executes in a block whose timestamp is at or past its `expires_at_ms`.
- A lane is taken at most once per round, and only by a build for that round.
- Submissions from unregistered or expired keys never reach the lane.
- An empty or invalid lane never prevents block production.
- Without a registry, block building is unchanged.

## Test Cases

- The highest `seq` wins a slot and keeps its first position; a lower `seq` arriving later is
  rejected.
- A submission expiring at or before the block timestamp is dropped.
- Operators are read from the registry contract at the finalized block.
- Submissions for a round earlier than the last opened one, or after the lane is taken, are
  refused. Submissions ahead of the round are kept and survive opening it.
- Every certificate of a view elects the same next leader; a certificate from another DKG or
  epoch is rejected.
- Per-operator slot and gas limits; a maker's slot cannot be taken over by another operator.
- Operators become secondary peers, and never displace a primary peer.
- Expired operators are refused.
- Devnet, 5 validators, 20 makers at 1,000 tx/s total, 20 tx/s public traffic tipping 30 gwei:
  100 of 100 consecutive blocks carried 20 lane transactions at index 0–19, with all 1,058 public
  transactions after them. The same 0-tip transactions sent through the mempool landed last.
