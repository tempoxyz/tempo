# TIP-1110: Account Address Derivation and Cross-Chain Recovery

## Abstract

This TIP defines how native configurable account addresses are derived using CREATE2. The configuration chosen at account creation, together with the canonical factory and wallet artifacts, determines the address. The address stays the same when owners change. This derivation also allows a recovery wallet to be deployed at the same address on supported EVM chains to retrieve assets sent there.

## Motivation

Configurable accounts need deterministic address derivation so wallets can compute an account's address before registration. Users can receive funds at this address during onboarding and keep it as owners and approval thresholds change.

Using CREATE2 also supports recovery of assets mistakenly sent to the same address on another supported EVM chain. Address derivation and recovery belong in one TIP because the factory and wallet creation code determine the address; changing either can change the addresses users receive.

## Assumptions

- The owner configuration follows [TIP-1114](./tip-1114.md).
- The canonical recovery contracts below remain the baseline while a smaller proxy design is reviewed. Final artifacts must be settled before T12.
- Recovery depends on the expected Safe Singleton Factory and recovery contracts being available on the destination chain.

# Specification

## Address derivation

First, combine the initial configuration into a salt. Then use that salt in the CREATE2 address formula.

```text
account_salt = keccak256(
  "tempo:multisig:account" || salt || uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
account = last20(keccak256(0xff || factory || account_salt || wallet_init_code_hash))
```

Encode the inputs as follows:

- Use raw ASCII for the domain string.
- Use 32 bytes for the salt and 20 bytes for each address.
- Use one byte for each integer shown as `uint8`.
- Include owners in sorted address order.
- Do not include a chain ID or add ABI/RLP encoding.

Reject a derived address if it is zero or belongs to a reserved namespace:

- Virtual addresses.
- Active precompiles.
- TIP-20 contracts.
- ZonePortal contracts.

Owner rotation preserves the original address and recovery salt.

## Factory activation

### Deployment salt

- Choose a fresh, random 32-byte deployment salt. This is separate from each account's salt.
- Keep it private until T12 activation is finalised on every Tempo network using the factory address.
- Do not publish the salt or deploy the factory on another chain before then. Deployment reveals the salt.
- The T12 hardfork code commits to the derived factory address. It does not need the secret salt.
- After activation, publish the salt so anyone can deploy the recovery factory on other chains.

### Factory reservation on Tempo

At T12 activation, before accepting native signatures, block deployment at the committed factory address:

- Set the recovery factory address's code to `0xEF`.
- Set its nonce to at least one, preserving any higher nonce.
- Replace any existing code at that address, but preserve its balance and storage.

Do not deploy the recovery factory runtime on Tempo. Safe's Singleton Factory may still be used for unrelated deployments.

## Recovery behaviour

### Wallet deployment

- After the salt is published, anyone may deploy the recovery factory on other chains through Safe's Singleton Factory.
- The recovery factory deploys each wallet with CREATE2.
- Deployment must also bind the wallet to `account_salt` in the same transaction.
- Only the factory can initialise its wallet, and initialisation can happen only once.

### Recovery authority

Cross-chain recovery uses the configuration that originally derived the account address. Its owners are referred to below as the initial owners.

- The wallet checks the supplied initial configuration against its stored salt.
- Owner rotation on Tempo does not change cross-chain recovery authority. Removed initial owners retain that authority; replacement owners do not inherit it.
- Only direct initial secp256k1 owners contribute to the recovery threshold.
- This baseline does not support P256, WebAuthn, or nested multisig signatures.
- If the supported initial owners cannot reach the threshold, baseline recovery is unavailable.

### Recovery signatures

A signature approves the full recovery operation. Its signed message includes:

- A domain specific to recovery.
- The destination chain and wallet address.
- The account salt and wallet nonce.
- The complete set of requested transfers.

The wallet requires:

- Distinct owners in sorted order.
- Enough weight to reach the threshold on the final signature.
- No signatures after the threshold has been reached.
- Low-`s` secp256k1 signatures, encoded as 65 bytes with `v` equal to 27 or 28.
- At most 48 owners and eight signatures.

### Allowed transfers

- Send native value with empty calldata.
- Transfer ERC-20, ERC-721, and ERC-1155 assets.
- Reject approvals and arbitrary calls.
- Apply the token checks and safe NFT receiver behaviour defined by the canonical contracts below.

These checks limit the wallet's interface. They cannot guarantee what a target contract does. Even a native-value transfer can run the recipient's contract code.

The exact ABI, signed-message encoding, transfer checks, nonce handling, and events are defined by the [canonical recovery contracts](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/src/TempoMultisigRecovery.sol).

The [artifact generator](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/gen_recovery_init_code_hash.sh) records the baseline compiler inputs and code hashes. Its public zero salt and derived factory address are superseded by the TBD values below. Changing the contract artifacts requires revisiting address derivation before activation.

# Tooling

- Verify the deployed runtime and wallet creation-code hashes against the canonical artifacts before offering recovery.
- Retain the initial configuration and check that its secp256k1 owners can meet the threshold.
- Show recovery eligibility separately from current Tempo ownership.
- Accounts migrated under TIP-1113 do not gain CREATE2 recovery.

# Observability

- Use recovery events and receipts on the destination chain, as defined by the canonical contracts.

# Threat Model

Cross-chain recovery uses the initial secp256k1 owners and approval threshold, independently of later Tempo ownership or governance changes. Removed initial owners retain recovery authority; replacement owners do not inherit it. Losing enough initial keys to fall below the threshold makes recovery unavailable, even while the account remains usable on Tempo.

Preventing deployment on Tempo before T12 depends on keeping the factory deployment salt private until activation.

# Invariants

- Address derivation matches the canonical factory and wallet artifacts.
- The factory address is reserved on Tempo before native signatures are accepted.
- Only the factory can initialise a recovery wallet.
- Each recovery wallet can be initialised only once.
- Recovery signatures are valid only for the signed destination chain, wallet address, account salt, wallet nonce, and transfer set.
- Recovery signatures cannot be reused after their wallet nonce has been consumed.
- Initial secp256k1 owners retain cross-chain recovery authority after removal on Tempo.
- Owners added by rotation on Tempo do not gain cross-chain recovery authority.
- Cross-chain recovery requires initial secp256k1 owners whose combined weight meets the original approval threshold.
- Cross-chain recovery does not restore removed owners' authority on Tempo.
