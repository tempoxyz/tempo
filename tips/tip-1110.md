# TIP-1110: Account Address Derivation and Cross-Chain Recovery

## Abstract

A native account uses a CREATE2-compatible address. Its initial owners can deploy a recovery wallet at that address on another supported EVM chain to recover accidentally sent assets.

## Motivation

A new address scheme should not make mistaken cross-chain transfers permanently inaccessible. Derivation and recovery belong together because changing the factory or wallet creation code changes account addresses.

## Assumptions

The configuration follows [TIP-1114](./tip-1114.md). This draft retains the existing immutable recovery wallet as its baseline. Whether a smaller deployable proxy should replace it remains a design-review question; the artifacts and resulting addresses must be settled before T12 activation.

Recovery requires the expected Safe Singleton Factory and canonical recovery artifacts on the destination chain. There is no recovery guarantee if those prerequisites are absent or differ.

## Threat Model

Initial owners retain recovery authority forever on other chains, even after removal on Tempo. Replacement owners acquire no such authority. The recovery wallet is not proof of current Tempo ownership and must not be used as synchronized cross-chain governance.

# Specification

## Address derivation

```text
account_salt = keccak256(
  "tempo:multisig:account" || salt || uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
account = last20(keccak256(0xff || factory || account_salt || wallet_init_code_hash))
```

Use raw ASCII, 32-byte salt, 20-byte addresses, one-byte integers, and sorted owners. There is no chain ID or ABI/RLP encoding in the preimage. Reject zero addresses and addresses in virtual, active-precompile, TIP-20, or ZonePortal namespaces. Rotation never changes the original address or recovery salt.

On Tempo, T12 reserves the recovery factory address with code `0xEF` and nonce at least one before accepting native signatures. Replace any existing code there while preserving balance, storage, and a higher nonce. Do not install the recovery factory runtime on Tempo; the Safe Singleton Factory can remain available for unrelated uses.

## Recovery behavior

Anyone may deploy the dedicated factory through Safe's Singleton Factory using the deployment salt below. The dedicated factory deploys the wallet with CREATE2 and atomically binds `account_salt`; only that factory can initialize its wallet, exactly once.

The wallet verifies the supplied initial configuration against that bound salt. Only direct initial secp256k1 owners contribute recovery weight. P256, WebAuthn, and nested multisigs are unsupported by this baseline; a configuration without a sufficient direct secp256k1 quorum has no baseline recovery.

Recovery signatures bind the destination chain, wallet, salt, wallet nonce, and complete transfer set under a recovery-specific domain. Require sorted distinct owners, sufficient weight on the final signature, no extra signatures, low-`s`, and 65-byte signatures with `v` of 27 or 28. The wallet supports at most 48 owners and eight signatures.

The wallet can send native value with empty calldata and transfer ERC-20, ERC-721, and ERC-1155 assets. It cannot approve spending or make arbitrary calls. Token targets must have code; NFT calls must name the wallet as sender and use canonical ABI with matching batch-array lengths. Failed or malformed token returns revert recovery. Receiver callbacks accept safe NFT transfers. These interface restrictions do not prove target-contract semantics: even receiving native value can execute contract code.

The exact recovery ABI, signature preimage, transfer validation, nonce handling, and events are defined by the canonical [recovery contracts](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/src/TempoMultisigRecovery.sol). Their behavior is part of this baseline, not a second account-authorization mechanism on Tempo. The [artifact generator](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/gen_recovery_init_code_hash.sh) fixes the compiler/build inputs and verifies the constants below; a change requires a new derivation decision before activation.

# Tooling

Before advertising recovery, verify the singleton/factory runtime hashes and wallet creation-code hash, and check the initial secp256k1 quorum. Explain that key rotation on Tempo does not rotate recovery authority. Wallets must preserve the initial configuration as well as the current one. Accounts migrated in place by TIP-1113 do not acquire CREATE2 recovery.

# Observability

Recovery uses destination-chain contract events and receipts. Tempo owner-update events do not alter recovery authority.

# Invariants

Test identical derivation across chains, permissionless deployment, factory reservation on Tempo, initialization protection, cross-chain/nonce replay rejection, token-call validation, unsupported signer types, and removed initial owners retaining only destination-chain recovery authority.
