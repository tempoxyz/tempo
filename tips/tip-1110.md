# TIP-1110: Account Address Derivation and Cross-Chain Recovery

## Abstract

This TIP derives a configurable account's address by hashing its initial configuration. Derivation needs no deployed contracts, on Tempo or elsewhere.

A derived address has no private key, so assets sent to it on another chain cannot be recovered. Users who want cross-chain recovery should instead create an EOA and migrate it in place under [TIP-1113](./tip-1113.md). The EOA key then controls the same address on other EVM chains, while [TIP-1112](./tip-1112.md) retires it on Tempo.

## Motivation

New configurable accounts need an address before their configuration is registered. The address must be bound to the initial configuration so that only its owners can register it.

A hash of the configuration is enough. Supporting cross-chain recovery for derived addresses would require deploying and maintaining factory and wallet contracts on every destination chain. EOA migration already gives an address that a primitive key controls on every EVM chain, without new contracts.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| The owner configuration follows [TIP-1114](./tip-1114.md). | Derivation and authorization can disagree about the account's owners or threshold. |
| An attacker cannot find a primitive private key whose address equals a derived account address. | That key could act as the account's root before registration. |

# Specification

## Address derivation

Hash the initial configuration and take the last 20 bytes:

```text
account = last20(keccak256(
  "tempo:configurable-account:account" || salt || uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
))
```

Encode the inputs as follows:

- Use raw ASCII for the domain string.
- Use 32 bytes for the salt and 20 bytes for each address.
- Use one byte for each integer shown as `uint8`.
- Include owners in sorted address order.
- Do not include a chain ID or add ABI/RLP encoding.

Reject a derived address if it is zero or belongs to a reserved namespace:

- Virtual addresses.
- Active precompiles.
- TIP-20 contracts.
- ZonePortal contracts.

Owner rotation never changes the address.

## Cross-chain recovery

A derived address exists only on Tempo. No key or contract controls it on other chains, so assets sent there are lost.

For accounts that need cross-chain recovery, tooling should create the account from a fresh EOA key instead:

1. Generate a fresh secp256k1 key. Its address is the account address.
2. Have that key sign a TIP-1113 `upgradeAccount` transaction installing the user's real owners. The key should not be one of them. Fee sponsorship allows this before the account is funded.
3. Keep the key as a recovery credential, or discard it if the user does not want cross-chain recovery.

After migration:

- **On Tempo**, TIP-1112 retires the EOA key. The user's funds are controlled only by the configured owners, so losing or leaking the EOA key does not put them at risk.
- **On other EVM chains**, the EOA key still controls the same address. If assets are sent there by mistake, the key holder can move them out with an ordinary transaction.

Tooling should treat the EOA key as a recovery-only credential:

- Migrate immediately after generating the key, before the address receives funds or is shared.
- Do not use the address on other chains. Recover mistaken transfers and move them elsewhere.
- Do not sign anything else with the EOA key. Applications that check signatures with `ecrecover` may still accept it as the account; see [TIP-1112](./tip-1112.md).
- If the key is discarded, show that the account has no cross-chain recovery, as for a derived address.

Accounts with several owners can use the same flow, with the EOA key held by whoever is responsible for cross-chain recovery.

# Tooling

- Use the EOA migration flow above for accounts that may receive cross-chain transfers by mistake.
- Warn users of derived accounts that assets sent to the address on another chain cannot be recovered.
- Show whether an account has a recovery key and who holds it, separately from its current Tempo owners.

# Threat Model

| Actor | Trust |
| --- | --- |
| EOA recovery key holder | Controls the address on every other EVM chain, including after the configured owners change on Tempo. Has no authority on Tempo after migration. |
| Address collision finder | Must find a primitive key or configuration whose address matches another account's, at roughly 2^80 work. Same bound as other 160-bit Ethereum addresses. |

Contracts on Tempo must not treat messages from the same address on another chain as approval by the Tempo account.

# Invariants

- Derivation is deterministic, chain-independent, and rejects zero and reserved addresses.
- Owner rotation never changes the address.
- A migrated account's EOA key has no authority on Tempo, but still controls the address on other chains.
