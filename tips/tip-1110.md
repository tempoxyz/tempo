# TIP-1110: Account Address Derivation and Cross-Chain Recovery

## Abstract

This TIP derives configurable account addresses with CREATE2. On other EVM chains, the same address is a minimal beacon proxy.

If assets are accidentally sent to that address on another supported chain, its initial owners can deploy the proxy and retrieve them. Tempo can upgrade the recovery logic for every account at once through a shared beacon. Each account's owners can pin an implementation of their choice to opt out of later upgrades.

The beacon deploys an audited default implementation, so every chain has working recovery and pinning as soon as the beacon exists. It accepts initial owners using any primitive Tempo signature type: secp256k1, P256 or WebAuthn. Owner rotation on Tempo does not change that authority. The beacon owner can change the default only after a fixed delay, which gives owners time to pin before an upgrade takes effect.

## Motivation

The new address scheme should let users recover mistaken cross-chain transfers.

Address derivation and recovery belong in one TIP. The factory and proxy creation code determine the address, so changing either changes the addresses users receive.

Fixed recovery bytecode cannot be fixed or extended after activation. For example, it cannot add P256 or WebAuthn recovery. Per-account upgrades would require every user to act on every chain, and most addresses are never deployed. A beacon lets one upgrade reach every account. A per-account pin keeps each account's owners in control of the code at their address.

The beacon owner is fixed in the address derivation and cannot be retired on chains where the beacon is not yet deployed. A built-in default implementation and a fixed upgrade delay bound that trust: a lost owner key leaves accounts on working code, and a compromised one can only schedule changes in public, which owners can avoid by pinning.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| The owner configuration follows [TIP-1114](./tip-1114.md). | Derivation and authorization can disagree about the account's owners or threshold. |
| The account proxy, beacon, default implementation, factory, beacon owner address and upgrade delay are part of address derivation and must be final before activation. | Changing them can change account addresses. |
| Later implementations are outside address derivation and may be published after activation. | Binding them into derivation would prevent replacing the default at the same address. |
| The default implementation's recovery and pin logic is correct. | It is the only implementation that can be active without passing the upgrade delay. A flaw affects every unpinned account until a delayed upgrade replaces it. |
| The Safe Singleton Factory, recovery factory and beacon are available on the destination chain. | Recovery is unavailable until the required contracts are deployed. The beacon deploys the default implementation itself. |

# Specification

## Overview

1. **Derive on Tempo:** the initial owner configuration, factory, and proxy creation code determine the configurable account address.
2. **Deploy on a destination chain:** anyone can use the recovery factory to deploy the proxy at that address. Deployment requires no owner signature.
3. **Select the implementation:** the proxy uses its pinned implementation, or the beacon's default when unpinned. Owners can authorise pinning or unpinning.
4. **Recover assets:** eligible initial owners approve the requested transfers under the selected implementation. Tempo owner rotation does not change this recovery authority.

### Contracts

Recovery on a destination chain uses four contracts:

| Contract | Instances | Upgradeable | Role |
| --- | --- | --- | --- |
| Account proxy | One per account | No | Holds the account's assets and storage. Delegates every call to the pinned or beacon implementation. |
| Recovery beacon | One per chain | Owner can schedule a new implementation, effective after `UPGRADE_DELAY` | Stores the default implementation and any scheduled change. |
| Recovery implementation | One per version | No, replaced by publishing a new version | Holds the recovery and pin logic. The beacon deploys the default version. |
| Recovery factory | One per chain | No | Deploys account proxies with CREATE2. |

The factory, beacon and every later implementation are deployed through Safe's Singleton Factory, each with one published salt and identical init code on every chain. The beacon's constructor deploys the default implementation with `CREATE`. Each contract therefore has the same address on every chain.

## Address derivation

First, combine the initial configuration into a salt. Then use that salt in the CREATE2 address formula.

```text
account_salt = keccak256(
  "tempo:configurable-account:account" || salt || uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
account = last20(keccak256(0xff || factory || account_salt || ACCOUNT_PROXY_INIT_CODE_HASH))
```

Encode the inputs as follows:

- Use raw ASCII for the domain string.
- Use 32 bytes for the salt and 20 bytes for each address.
- Use one byte for each integer shown as `uint8`.
- Include owners in sorted address order.
- Do not include a chain ID or add ABI/RLP encoding.

`ACCOUNT_PROXY_INIT_CODE_HASH` is the hash of the account proxy's creation code. The creation code is identical for every account. It takes no constructor arguments and embeds the beacon address as a constant.

Reject a derived address if it is zero or belongs to a reserved namespace:

- Virtual addresses.
- Active precompiles.
- TIP-20 contracts.
- ZonePortal contracts.

Owner rotation never changes the original address or recovery salt.

**Keep the factory deployment salt private**

- Choose a fresh, random 32-byte deployment salt. This is separate from each account's salt.
- Keep it private until activation is finalized on every Tempo network using the factory address.
- Do not publish the salt or deploy the factory on another chain before then. Deployment reveals the salt.
- The activation code commits to the derived factory address. It does not need the secret salt.
- After activation, publish the salt so anyone can deploy the recovery factory on other chains.

**Reserve the factory address on Tempo**

At activation, before accepting native signatures, block deployment at the committed factory address:

- Set the recovery factory address's code to `0xEF`.
- Set its nonce to at least one, preserving any higher nonce.
- Replace any existing code at that address, but preserve its balance and storage.

Do not deploy the recovery factory, beacon or implementation runtime on Tempo. Safe's Singleton Factory may still be used for unrelated deployments.

## Recovery factory

- `deploy(account_salt)` deploys the account proxy with CREATE2 using the constant creation code. It returns the existing address if code is already there.
- `deployAndCall(account_salt, data)` deploys the proxy if needed and then calls it with `data`. One transaction can deploy and pin, or deploy and recover.
- Anyone may call either function. Deployment requires no signature, because the proxy holds no account-specific state until owners act.
- The factory has no owner or initialization step.

## Account proxy

The proxy has no logic of its own. On each call it does the following:

1. If calldata is empty, accept any native value and stop without calling anything else. Plain transfers, including those limited to a 2,300 gas stipend, then always succeed.
2. Read the implementation address from `PIN_SLOT`.
3. If `PIN_SLOT` is zero, read the implementation from `RECOVERY_BEACON.implementation()` with a static call.
4. Revert if the resulting address is zero.
5. `delegatecall` the implementation with the full calldata and value. Return or revert with its return data.

Requirements:

- The beacon address is a constant in the runtime code. It is not read from storage.
- The proxy has no constructor logic and does not call the beacon at deployment. A proxy can be deployed before the beacon exists on that chain.
- The proxy defines [three reserved storage slots](#reserved-storage-slots). Only an implementation running through the proxy can write them.
- Compile the proxy, beacon and factory for the `paris` EVM version, so they run on chains without `PUSH0`. The canonical artifacts record the exact compiler inputs and the pinned OpenZeppelin and Solady releases.

**Prior art and alternatives**

- OpenZeppelin's `BeaconProxy` and Solady's minimal beacon proxy (`LibClone`) always use the beacon and have no per-account override. OpenZeppelin's `BeaconProxy` also requires the beacon and its implementation to have code at construction, which would prevent deploying a proxy before the beacon exists on that chain.
- Solady's `EIP7702Proxy` uses the same lookup order: a per-account ERC-1967 slot first, then a shared upgradeable default. Pairing an ERC-1167 clone with it would avoid new proxy code, but it is not used here:
  - It uses transient storage and executes `TLOAD` for every unpinned account, so it only runs on chains with Cancun.
  - The clone always delegates, so plain transfers with a 2,300 gas stipend fail once the account is deployed.
  - It has no admin events and no check that a new implementation has code.
  - It is designed for EIP-7702 delegations, not CREATE2 contracts.

## Recovery beacon

The beacon takes no constructor arguments. Its constructor:

- Deploys the default implementation with `CREATE` from creation code embedded in the beacon, and sets it as the current implementation. Whenever the beacon exists on a chain, the default implementation exists too.
- Sets the owner to `RECOVERY_BEACON_OWNER`, a constant.

**Delayed upgrades**

- `scheduleUpgrade(impl)` is callable only by the owner. It requires `impl` to have code, records it as the pending implementation with an effective time of `block.timestamp + UPGRADE_DELAY`, and emits `UpgradeScheduled`. A pending change that has already taken effect becomes the current one first. Scheduling again replaces a change that has not yet taken effect and restarts the delay.
- `cancelUpgrade()` is callable only by the owner. It clears a pending implementation that has not yet taken effect and emits `UpgradeCancelled`.
- `implementation()` returns the pending implementation once its effective time has passed, and the current one otherwise. No further transaction is needed for an upgrade to take effect.
- The delay applies to every change, including the first upgrade on a chain. There is no way to upgrade immediately.

**Delayed ownership transfers**

- `scheduleOwnershipTransfer(newOwner)` and `cancelOwnershipTransfer()` follow the same owner-only, delay and cancellation rules, and emit `OwnershipTransferScheduled` and `OwnershipTransferCancelled`.
- `owner()` returns the pending owner once its effective time has passed.
- The owner cannot be set to zero, so upgrades can never be disabled permanently on a chain.

Without the delay on transfers, a leaked owner key could take ownership on a new chain at once and lock Tempo out of future upgrades there.

**Choosing `UPGRADE_DELAY`**

`UPGRADE_DELAY` is 14 days. It must be long enough for wallets and watchers to notice a scheduled change on every chain where an account holds assets and submit pre-signed pin messages, including over weekends and holidays. Upgrades are rare and recovery is not time-critical, so a long delay costs little. The delay also applies to fixes; owners worried about a flaw in the current implementation can pin a corrected one without waiting.

## Recovery implementation

**Binding to the account**

An implementation has no constructor state and no immutables other than constants. It identifies its account by recomputing the address:

```text
address(this) == last20(keccak256(0xff || RECOVERY_FACTORY || deriveAccountSalt(init) || ACCOUNT_PROXY_INIT_CODE_HASH))
```

Every signed operation supplies the initial configuration and must pass this check. The proxy does not store `account_salt`, and no factory-only initialization is needed.

**Storage**

- The nonce and pin nonce live in the proxy's reserved slots. Moving between implementations never resets them, so earlier signatures cannot be replayed.
- All other state uses ERC-7201 namespaced storage. Published implementations must not reuse each other's namespaces for different layouts.

**Who can recover**

The default implementation applies these authority rules:

- The supplied initial configuration must bind to the account as above.
- Owner rotation on Tempo does not change cross-chain recovery authority. Removed initial owners retain that authority; replacement owners do not inherit it.
- Every direct initial owner contributes to the recovery threshold, whether it signs with secp256k1, P256 or WebAuthn. These are all of Tempo's primitive signature types, so any initial configuration that can sign on Tempo can also recover and pin on other chains.
- It does not support nested multisig signatures. Later implementations may add signature types that Tempo adds after activation, without changing addresses. Owners that need such a type cannot recover or pin until an implementation supporting it takes effect.

**Verifying P256 and WebAuthn**

Other chains may lack Tempo's signature verifier. The default implementation verifies P256 signatures, including those inside WebAuthn assertions, with the P256 precompile at `0x100` ([EIP-7951](https://eips.ethereum.org/EIPS/eip-7951)) when the chain provides one. Otherwise it uses an embedded Solidity verifier. Both paths must accept exactly the same signatures.

A Solidity P256 check costs roughly 200,000–350,000 gas, against about 3,000 for secp256k1. With at most eight signatures, the worst case stays within a single transaction on chains without the precompile. Recovery and pinning are rare, so this cost is acceptable.

**Recovery signatures**

A signature approves the full recovery operation. Its signed message includes:

- The raw ASCII domain `tempo:configurable-account:recovery`.
- The destination chain and account address.
- The account salt and recovery nonce.
- The complete set of requested transfers.

The implementation requires:

- Distinct owners in sorted order.
- Enough weight to reach the threshold on the final signature.
- No signatures after the threshold has been reached.
- Owner signatures in [TIP-1020](./tip-1020.md)'s primitive encodings, with the same validity checks and owner-address derivation as TIP-1020 `recover`. secp256k1 signatures must be low-`s` with `v` equal to 27 or 28.
- At most 48 owners and eight signatures.

**Allowed transfers**

- Send native value with empty calldata.
- Transfer ERC-20, ERC-721, and ERC-1155 assets.
- Reject approvals and arbitrary calls.
- Apply the token checks and safe NFT receiver behavior defined by the canonical contracts below.

These checks limit the account's interface. They cannot guarantee what a target contract does. Even a native-value transfer can run the recipient's contract code.

## Pinning an implementation

The account's owners can opt out of beacon upgrades. Every published implementation must support two signed operations:

- `pin(impl)` writes `impl` into `PIN_SLOT`. `impl` can be any address with code, and its code hash must equal the signed code hash. The beacon no longer affects the account.
- `unpin()` clears `PIN_SLOT`. The account follows the beacon again.

The signed message for both operations includes:

- The raw ASCII domain `tempo:configurable-account:pin`.
- The account address and account salt.
- The pin nonce.
- The target implementation and its code hash, or zero for both for `unpin`.

It does not include a chain ID. Owners can sign one pin message and anyone can submit it on every chain, for example with `deployAndCall`. The pin nonce increments on every pin or unpin, so an old message cannot be replayed after the owners change their choice. The code hash ensures the message installs the same code on every chain, even where the target address holds different code.

Pin and unpin use the same signature rules and threshold as recovery. Because the default implementation supports every Tempo signature type, any account's initial owners can pin on any chain where the beacon is deployed.

Pins are not limited to implementations published through the beacon. The initial owners own the address on other chains, as with a Safe whose owners can run arbitrary code through `delegatecall`.

## Canonical artifacts

The exact ABI, signed-message encodings, transfer checks and events are defined by the canonical recovery contracts. The [baseline recovery contracts](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/src/TempoMultisigRecovery.sol) supply the recovery logic for the default implementation. They need these changes: the configurable-account domains defined above, no constructor state or `initialize`, address-based binding, reserved slots, pin operations, and P256 and WebAuthn owner signatures. The result is the default implementation, and its creation code is embedded in the beacon. The canonical ABI names the initial-configuration tuple `InitConfigurableAccount`.

The [artifact generator](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/gen_recovery_init_code_hash.sh) must be updated for the proxy, beacon and factory. Its recorded baseline hashes are superseded.

## Interfaces

### Proxy contract

The proxy extends OpenZeppelin's `Proxy`, which supplies the `fallback` and `delegatecall` logic. The only new code is the implementation lookup and the empty-calldata `receive`:

```solidity
import { Proxy } from "@openzeppelin/contracts/proxy/Proxy.sol";
import { IBeacon } from "@openzeppelin/contracts/proxy/beacon/IBeacon.sol";

contract TempoAccountProxy is Proxy {
    address internal constant BEACON = RECOVERY_BEACON;
    bytes32 internal constant PIN_SLOT = bytes32(uint256(keccak256("tempo.recovery.pin")) - 1);

    receive() external payable { }

    function _implementation() internal view override returns (address impl) {
        bytes32 slot = PIN_SLOT;
        assembly { impl := sload(slot) }
        if (impl == address(0)) impl = IBeacon(BEACON).implementation();
        if (impl == address(0)) revert();
    }
}
```

### Beacon contract

```solidity
interface ITempoRecoveryBeacon {
    event UpgradeScheduled(address indexed implementation, uint64 effectiveAt);
    event UpgradeCancelled(address indexed implementation);
    event OwnershipTransferScheduled(address indexed newOwner, uint64 effectiveAt);
    event OwnershipTransferCancelled(address indexed newOwner);

    /// Pending implementation once effective, otherwise the current one. Never zero.
    function implementation() external view returns (address);
    /// Pending owner once effective, otherwise the current one.
    function owner() external view returns (address);

    function scheduleUpgrade(address implementation) external;
    function cancelUpgrade() external;
    function scheduleOwnershipTransfer(address newOwner) external;
    function cancelOwnershipTransfer() external;
}
```

# Tooling

- Verify the runtime hashes of the factory, beacon and implementation, and the proxy creation-code hash, against the canonical artifacts before offering recovery.
- Retain the initial configuration and check that the current implementation's supported signers can meet the threshold.
- Show recovery eligibility separately from current Tempo ownership.
- Show whether an account follows the beacon or is pinned, and to which implementation.
- Offer a chain-independent pin signature at account creation for users who do not want automatic upgrades.
- Watch `UpgradeScheduled` and `OwnershipTransferScheduled` on every chain where an account holds assets. For users who opt in, hold a pre-signed pin to the default implementation and submit it before an unwanted change takes effect.

Accounts migrated under TIP-1113 do not gain CREATE2 recovery.

# Observability

| Stage | Evidence |
|---|---|
| Beacon implementation or owner changed | `UpgradeScheduled` and `OwnershipTransferScheduled` record each change and its effective time; the matching `Cancelled` events record withdrawals. `implementation()` and `owner()` return the values in effect at the queried state. |
| Proxy deployed | The factory's deployment event records the account salt and address. Deployment alone does not establish that a recovery implementation is available. |
| Implementation pinned or unpinned | The implementation's pin event records the pinned address, or zero on unpin. `PIN_SLOT` determines whether the proxy uses that address or follows the beacon. |
| Assets recovered | The implementation emits the recovery events defined by its canonical contracts. |

Check implementation selection at the state used for recovery. A proxy on a chain without the beacon accepts empty-calldata native transfers but cannot process a recovery call. The [canonical artifacts](#canonical-artifacts) define the exact event and signed-message encodings.

# Threat Model

Recovery protects assets on destination chains under the initial owner configuration and that chain's beacon or pinned implementation.

| Actor | Trust |
| --- | --- |
| Initial recovery quorum | Retains authority after removal on Tempo; replacement owners do not inherit it. Eligible initial owners meeting the original threshold can pin any code and have full control of the address on other chains. |
| Beacon owner | Trusted with every unpinned account on its chain, including accounts not yet deployed. It can only schedule changes, which take effect after `UPGRADE_DELAY`. A compromised owner key can schedule a malicious implementation on any chain, including chains where the beacon is not yet deployed; unpinned accounts that do not pin within the delay can lose their assets. Tempo, holding the same key, can cancel such a change within the delay, though not prevent it being scheduled again. A lost key leaves every chain on its current implementation. Pinned accounts are unaffected. |
| Default implementation | Trusted to implement recovery and pinning correctly. It is the only implementation that can be active without passing the upgrade delay, and its code is fixed in address derivation. |
| Pin-message relayers | Can submit a chain-independent pin message on any chain whose pin nonce has not advanced past it. Replacing a pin requires submitting the new message on every chain where the old one could still be replayed. |
| Deployment maintainers | Trusted to keep the factory deployment salt private until activation. Revealing it early removes the protection against deploying the factory on Tempo before the address is reserved. |

The recovery implementation does not track current Tempo ownership or synchronise governance across chains. Contracts on Tempo must not treat messages from the same address on another chain as approval by the current Tempo account.

Pinning protects an account only if it happens before a harmful beacon upgrade takes effect. The delay guarantees that window. Once a malicious implementation is in effect it can pin accounts to itself or move their assets, so harm to accounts that did not pin may be irreversible. A flawed pinned implementation stays in use until the owners unpin or pin another version; the beacon owner cannot move pinned accounts.

`RECOVERY_BEACON_OWNER` can be transferred on each chain, but never retired on chains where the beacon is not yet deployed, because the beacon's creation code fixes it as the initial owner.

The proxy, beacon, default implementation and factory cannot be fixed after activation without changing addresses. The proxy, beacon and factory must be minimal, and all four must be reviewed before activation.

# Invariants

- Test address derivation against the canonical artifacts and the factory reservation on Tempo.
- Test that the proxy accepts empty-calldata transfers with a 2,300 gas stipend and reverts when no implementation is set.
- Test that the beacon cannot change the implementation of a pinned account.
- Test that deploying the beacon deploys the default implementation and that `implementation()` returns it.
- Test that a scheduled upgrade or ownership transfer has no effect before `UPGRADE_DELAY` elapses, takes effect without a further transaction afterwards, and can be cancelled before then.
- Test that the owner cannot be set to zero and that no path changes the implementation without the delay.
- Test recovery and pinning with secp256k1, P256 and WebAuthn owners, both with and without a P256 precompile at `0x100`, and that both verification paths accept the same signatures.
- Test that pins reject addresses without code or with a code hash other than the signed one, and that unpinning restores beacon resolution.
- Test that nonces survive moving between implementations, that recovery messages cannot be replayed, and that pin messages cannot be replayed once the pin nonce has advanced.
- Test that an implementation binds only to the configuration that derives its proxy's address.
- Removed initial owners retain recovery authority without regaining authority on Tempo.
