# TIP-1110: Account Address Derivation and Cross-Chain Recovery

## Abstract

A native account uses a CREATE2-compatible address.

If assets are accidentally sent to that address on another supported EVM chain, its initial owners can deploy a recovery wallet there and retrieve them.

## Motivation

The new address scheme should let users recover mistaken cross-chain transfers.

Address derivation and recovery belong in one TIP. The factory and wallet creation code determine the address, so changing either can change the addresses users receive.

## Assumptions

- The owner configuration follows [TIP-1114](./tip-1114.md).
- This draft keeps the existing immutable recovery wallet as its baseline.
- Replacing that wallet with a smaller deployable proxy is still under review.
- The final contracts and resulting addresses must be settled before T12 activation.
- The destination chain must have the expected Safe Singleton Factory and recovery contracts. Missing or different contracts mean this TIP cannot guarantee recovery.

## Threat Model

- The initial owners retain recovery authority on other chains, even if they are removed on Tempo.
- Replacement owners do not gain recovery authority automatically.
- A recovery wallet does not prove who currently owns the Tempo account.
- Applications must not treat the wallet as a way to keep governance synchronized across chains.

# Specification

## Address derivation

First, combine the initial configuration into a salt. Then use that salt in the CREATE2 address formula.

```text
account_salt = keccak256(
  "tempo:multisig:account" || salt || uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
account = last20(keccak256(0xff || factory || account_salt || wallet_init_code_hash))
```

Encode the inputs as follows:

- Use raw ASCII for the domain string.
- Use 32 bytes for the salt and 20 bytes for each address.
- Use one byte for each integer shown as `uint8`.
- Include owners in sorted address order.
- Do not include a chain ID or add ABI/RLP encoding.

Reject a derived address if it is zero or belongs to a reserved namespace:

- Virtual addresses.
- Active precompiles.
- TIP-20 contracts.
- ZonePortal contracts.

Owner rotation never changes the original address or recovery salt.

**Reserve the factory address on Tempo**

Before T12 accepts native signatures:

- Set the recovery factory address's code to `0xEF`.
- Set its nonce to at least one, preserving any higher nonce.
- Replace any existing code at that address, but preserve its balance and storage.

Do not deploy the recovery factory runtime on Tempo. Safe's Singleton Factory may still be used for unrelated deployments.

## Recovery behavior

**Deploying the wallet**

- Anyone may deploy the recovery factory through Safe's Singleton Factory, using the deployment salt below.
- The recovery factory deploys each wallet with CREATE2.
- Deployment must also bind the wallet to `account_salt` in the same transaction.
- Only the factory can initialize its wallet, and initialization can happen only once.

**Who can recover**

- The wallet checks the supplied initial configuration against its stored salt.
- Only direct initial secp256k1 owners contribute to the recovery threshold.
- This baseline does not support P256, WebAuthn, or nested multisig signatures.
- If the supported initial owners cannot reach the threshold, baseline recovery is unavailable.

**Recovery signatures**

A signature approves the full recovery operation. Its signed message includes:

- A domain specific to recovery.
- The destination chain and wallet address.
- The account salt and wallet nonce.
- The complete set of requested transfers.

The wallet requires:

- Distinct owners in sorted order.
- Enough weight to reach the threshold on the final signature.
- No signatures after the threshold has been reached.
- Low-`s` secp256k1 signatures, encoded as 65 bytes with `v` equal to 27 or 28.
- At most 48 owners and eight signatures.

**Allowed transfers**

- Send native value with empty calldata.
- Transfer ERC-20, ERC-721, and ERC-1155 assets.
- Reject approvals and arbitrary calls.
- Require token targets to have deployed code.
- Require NFT calls to name the recovery wallet as the sender.
- Require canonical NFT call encoding and matching batch-array lengths.
- Revert recovery if a token call fails or returns a malformed result.
- Support receiver callbacks for safe NFT transfers.

These checks limit the wallet's interface. They cannot guarantee what a target contract does. Even a native-value transfer can run the recipient's contract code.

The exact ABI, signed-message encoding, transfer checks, nonce handling, and events are defined by the [canonical recovery contracts](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/src/TempoMultisigRecovery.sol).

The [artifact generator](https://github.com/tempoxyz/tempo/blob/53b0bb32dad143c24e8e9612d612053899efc7ad/tips/verify/gen_recovery_init_code_hash.sh) fixes the compiler inputs and checks the constants below. Changing these artifacts requires revisiting address derivation before activation.

These contracts define the recovery baseline. They do not authorize transactions on Tempo.

# Tooling

Before offering recovery, tooling must:

- Check the singleton and recovery factory runtime hashes.
- Check the wallet creation-code hash.
- Check that the initial secp256k1 owners can reach the threshold.
- Explain that rotating keys on Tempo does not rotate recovery owners.

Wallets must keep the initial configuration as well as the current one.

Accounts migrated in place under TIP-1113 do not gain CREATE2 recovery.

# Observability

- Recovery is recorded in events and receipts on the destination chain.
- Owner-update events on Tempo do not change recovery authority.

# Invariants

Tests must cover:

- The same inputs deriving the same address on every supported chain.
- Permissionless factory and wallet deployment.
- The recovery factory address being reserved on Tempo.
- Wallet initialization being allowed only once and only by its factory.
- Rejection of signatures replayed on another chain or with another nonce.
- Token-call validation.
- Rejection of unsupported signer types.
- Removed initial owners retaining recovery authority on the destination chain, without regaining authority on Tempo.
