# TIP-1175: Separate Account and Bytecode Load Pricing

## Abstract

Loading a contract is one or two database lookups: the account, and its
bytecode if it has any. [TIP-1174](./tip-1174.md) charges a code-loading access
only the account read. This TIP adds a code component, charged only when the
account has code, and a code-hash declaration so clients can fetch bytecode by
hash in parallel with the account instead of after it.

This is component 2 of the [TIP-1139](./tip-1139.md) state access program.

## Motivation

An address without code needs one lookup, a contract two, and the second can
only start once the first returns the code hash. A single price either
overcharges calls to accounts without code or undercharges calls to contracts.
Splitting the charge prices each case by the work it causes. Declaring the code
hash lets clients start both lookups at once, so a declared contract call costs
one round trip.

A cold contract call is the most expensive state access: on 10 validators with
~100 GB of state, distinct 24,576-byte contracts and node memory capped at
16 GB, a serial cold call took ~160 µs at the median and up to ~380 µs
([`state-call-*`](../contrib/bench/txgen/presets/state-call-dependent-disk.yml)
presets), against ~70 µs for a cold storage read. With only TIP-1174's 5,000
account read, a block of four serial 10M-gas transactions of cold calls takes
~1.1 s against a ~0.5 s block time; at 10,000 it takes ~0.6 s, matching
TIP-1174's worst case for reads.

### Alternatives considered

- **A code flag instead of a code hash:** the client learns the code hash only
  from the account lookup, so each declared contract still costs two serial
  lookups, or clients must store bytecode per account as well as by hash.
- **Keep one combined price:** simple, but prices accounts without code and
  contracts the same.

## Assumptions

- [TIP-1174](./tip-1174.md) activates in the same hardfork. Without this TIP,
  TIP-1174 prices a cold contract call at the account read alone, which
  benchmarks show is underpriced.
- Code-hash declarations need [TIP-1176](./tip-1176.md). This TIP can activate
  without it, in which case only prewarming, deployment, and legacy access list
  entries make code warm.

# Specification

## 1. Code warmth

Code warmth is tracked per address and code hash. An address is code-warm for a
hash if it is prewarmed, its code was deployed in this transaction, the
transaction already paid for that code at that address, a legacy access list
lists the address (code-warm for whatever code it has), or a TIP-1176 entry
declares that hash for it.

## 2. Prices

| Access | Declared | General lane, undeclared |
| --- | ---: | ---: |
| Code component | 3,000 | 5,000 |

With TIP-1174's account read, a cold contract costs 10,000 undeclared and
5,000 declared. The access list lane's prices are set by TIP-1177.

## 3. Two-step code loads

`CALL`, `CALLCODE`, `DELEGATECALL`, `STATICCALL`, `EXTCODESIZE`, and
`EXTCODECOPY` are charged in two steps, replacing TIP-1174's code-load rule:

1. Pay the account read price, or 100 if account-read-warm, then look up the
   account and its code hash.
2. If the code hash is non-empty and the address is not code-warm for that
   hash, pay the lane's code component (section 2; TIP-1177 for the access
   list lane), then load the code. A code-warm load adds nothing.

So a cold contract costs 10,000, an address without code costs one account
read (5,000), and a prewarmed or declared contract costs 100.

An EIP-7702 delegation designator is the delegating account's code and is
priced as ordinary bytecode: a cold designator pays step 2 like any other code.
The `CALL` family then charges the delegation target both steps, so a call
through a cold delegating account to a cold contract pays 10,000
twice. `EXTCODESIZE`, `EXTCODECOPY`, and `EXTCODEHASH` do not follow the
designator, as in EIP-7702; `EXTCODESIZE` and `EXTCODECOPY` on a delegating
account pay the designator's code component when it is cold.

The code hash does not say whether the code is a designator, so exempting
designators would force a client to read the code before it can price the load.
Pricing them as code lets the client decide whether a cold code load is
affordable from the code hash and code warmth alone, before any code is read.

## 4. Code-hash declarations

When [TIP-1176](./tip-1176.md) is active, an extended access list entry's
`code_hash` is the empty string (no code declared) or the 32-byte keccak256 of
the bytecode the transaction expects to load from `address`. A non-empty
`code_hash` requires the account read bit and MUST NOT be the hash of empty
code. It costs **3,000** at declaration, on top of the entry's account price, so
declaring code costs 5,000 (7,900 with account write) and makes the address
code-warm for that hash.

A declared hash that does not match the address's code when loaded pays the
lane's undeclared code component; the 3,000 paid at declaration is not refunded.
A code declaration covers the bytecode of the address supplying code: under
`DELEGATECALL` the code and storage come from different addresses, so each
needs its own entry. A call through an EIP-7702 delegation likewise loads two
codes, the designator and the target's bytecode, and each needs its own entry
to be code-warm. No code-write declaration exists: deployment is an account
write, and the new address needs no code hash.

Clients SHOULD prefetch declared bytecode by hash in parallel with the account.

## 5. Activation

At activation the two-step rule takes effect, TIP-1176 entries may carry a
non-empty `code_hash`, and the transaction pool is revalidated. Earlier blocks
replay under their own rules.

# Gas Cost Impact

| Access | TIP-1174 alone, general undeclared | With this TIP |
| --- | ---: | ---: |
| Call to a cold address without code | 5,000 | 5,000 |
| Call to a cold contract | 5,000 | 10,000 |
| Call to a declared contract (code hash) | n/a | 5,100 |
| Call to a contract with a wrong declared hash | n/a | 10,100 |

# Tooling

`tempo_createExtendedAccessList` (TIP-1176) returns the code hash of each loaded
contract at the simulated state, including the designator of each EIP-7702
delegating account it loads. Addresses without code are returned as account
reads without a code hash, and prewarmed addresses get no entry.

# Observability

Traces MUST distinguish account lookups from code loads and report code-hash
mismatches with the declared and actual hash.

# Threat Model

A sender can declare a wrong hash; it pays for the declaration and the
undeclared code component, so a mismatch is never cheaper than no declaration.
Clients prefetch only declared hashes and never follow unlisted code.

# Invariants and Validation

1. The code component is charged at most once per address and code hash, and
   never for an address without code. A delegation designator is code and is
   charged like any other.
2. A mismatched declaration never makes code warm.

Reference tests MUST cover declared hashes that match and do not match,
addresses without code, read-warm and prewarmed targets, native precompile
dispatch, EIP-7702 delegation at top level and via calls (including `EXTCODE*`
on delegating accounts, and cold and warm designators), and calls to code
deployed in the same transaction (including after a reverted creation).
