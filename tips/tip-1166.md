# TIP-1166: Configurable Account Voucher Signers for the Channel Reserve

## Abstract

This TIP lets configurable accounts ([TIP-1107](./tip-1107.md)) sign channel vouchers ([TIP-1034](./tip-1034.md)) with their owners. When a channel opens, the precompile saves the signer's configuration commitment (the hash of its owner set). Vouchers are checked against that saved hash, so rotating owners later does not invalidate vouchers the payee already holds.

## Motivation

Today a configurable account cannot sign vouchers. Since T14, `open` rejects a signer that has a configuration commitment, so these accounts need a separate session key as `authorizedSigner`.

Checking `0x05` vouchers against the account's *current* commitment would let a payer cheat. Any `updateConfig` changes the commitment ([TIP-1109](./tip-1109.md)):

1. Alice opens a channel to Bob with 100 USDC.
2. Alice's owners sign a voucher for 60 USDC, and Bob serves her.
3. Alice rotates her owners, then calls `requestClose`.
4. Bob's voucher no longer matches Alice's config, so `close` fails.
5. After the 15-minute grace period, Alice withdraws all 100 USDC.

Bob can't defend against this, and owner rotation is a normal thing to do (for example, after losing a device). Saving the commitment at open fixes the signer for the channel's lifetime, so Bob's voucher still works.

Alternatives considered:

- **Put the commitment in `ChannelDescriptor`.** No extra storage, but it changes `channelId` and every channel method, breaking existing integrations.
- **Accept any past configuration.** Tempo doesn't store config history.
- **Block `updateConfig` while channels are open.** A user who loses a device couldn't remove it.

## Assumptions

- A commitment covers the whole configuration, including its version. Otherwise two owner sets could share one.
- A version-0 configuration can't be forged for an address it doesn't derive (CREATE2 preimage resistance).
- Payees check the saved commitment before accepting a `0x05` voucher.

# Specification

## Overview

These rules apply from T15. The *signer* is `authorizedSigner` if set, otherwise `payer`. The *snapshot* is the signer's commitment when the channel opened (zero if it had none).

1. `open` saves the snapshot.
2. `settle` and `close` check vouchers against the snapshot, never the current config.
3. A nonzero `topUp` requires the signer's config to be unchanged.
4. `close` and `withdraw` delete the snapshot with the channel.

Nothing the payer does after `open` changes who can sign vouchers for that channel. The one exception is new deposits, so old owners never gain control of new funds.

## Open

- The T14 `RootKeyRetired` check on the signer is removed.
- After the duplicate check, `open` reads the signer's current commitment. If it is nonzero, `open` stores it in `signerSnapshots[channelId]` and emits `SignerSnapshotCached`. A zero commitment stores nothing.
- An `updateConfig` earlier in the same transaction counts.

## Voucher checks

| Snapshot | Signature | Accepted when |
|---|---|---|
| Any | Keychain (`0x03`, `0x04`) | Never (unchanged) |
| Nonzero | `0x05` | Its account is the signer, its config hashes to the snapshot, and its owner signatures reach the threshold |
| Nonzero | Primitive | Never: the signer's root key was retired at open ([TIP-1112](./tip-1112.md)) |
| Zero | `0x05` | Its account is the signer, its config is version 0 and derives the signer's address, and its owner signatures reach the threshold |
| Zero | Primitive | It recovers to the signer (unchanged) |

Owners sign the TIP-1034 voucher digest the same way they sign a `0x05` transaction. Gas follows the signature verifier's `verifyConfigurableAccount` schedule: the `0x05` signature's verification gas, plus the version-0 address-derivation gas when the snapshot is zero. The snapshot, not the signer's current commitment, decides whether the derivation charge applies. All gas is charged before verification. A failed check reverts with `InvalidSignature`.

## Top-up

A nonzero `topUp` reverts:

- with `SignerConfigChanged(signer)` if the snapshot is nonzero and differs from the signer's current commitment;
- with `RootKeyRetired(signer)` if the snapshot is zero and the signer now has a commitment (as at T14).

A zero `topUp` still works and cancels a close request. To add funds after a rotation, the payer closes the channel and opens a new one.

## Payment lane

`settle` and `close` with a well-formed `0x05` signature (1–48 owners, 1–8 signatures) count as payment-lane transactions. The classifier checks encoding only and reads no state.

## Interfaces

Additions to `ITIP20ChannelReserve`. Nothing existing changes.

```solidity
/// @notice Emitted by open when the signer has a nonzero configuration commitment.
event SignerSnapshotCached(bytes32 indexed channelId, address indexed signer, bytes32 commitment);

/// @notice A nonzero topUp was attempted after the signer's configuration changed.
error SignerConfigChanged(address signer);

/// @notice The commitment saved at open, or zero if none or the channel doesn't exist.
function getSignerSnapshot(bytes32 channelId) external view returns (bytes32);
```

Storage: `signerSnapshots: mapping(bytes32 channelId => bytes32)`, set only when nonzero.

# Compatibility

Existing channels have no snapshot and behave as before. The ABI change is additive.

| Integration | What changes |
|---|---|
| Configurable payers | Can sign vouchers with `0x05`, using the config from when the channel opened |
| Payees | Check the voucher's config hash against `getSignerSnapshot` before accepting it |
| SDKs and wallets | Keep each channel's opening config until it closes; on `SignerConfigChanged`, close and reopen |
| Indexers | Index `SignerSnapshotCached` |

# Observability

`SignerSnapshotCached` shows which owner set signs for a channel. Comparing it with the account's latest `MultisigConfigUpdated` event finds channels opened under an old config.

# Threat Model

- **Payer voids vouchers by rotating owners.** Stopped: vouchers are checked only against the snapshot.
- **Removed owner keeps signing.** Old owners who together meet the old threshold can still sign vouchers on channels opened before the rotation. The amount is capped at the deposit and can only go to the payee. To cut this off, the payer closes those channels (`requestClose`, then `withdraw` after 15 minutes).
- **Old owners gain new funds.** Stopped: nonzero `topUp` reverts after a config change.
- **Payee forges a config.** Stopped: it must hash to the snapshot, or derive the signer's address at version 0.

# Invariants

1. A channel's snapshot never changes while the channel exists.
2. While a channel exists, nothing the payer or signer does changes whether a voucher is valid.
3. A deleted channel has no snapshot.
4. A nonzero `topUp` succeeds only if the signer's current commitment equals the snapshot (or both are zero).
5. A channel with a nonzero snapshot accepts only `0x05` vouchers.
6. A channel uses one state slot, plus one snapshot slot only if the snapshot is nonzero (amends TIP-1034 invariant 7).

Tests should cover: configurable payer and configurable `authorizedSigner`; the Alice/Bob rotation case; a voucher from the new config rejected on an old channel; `updateConfig` and `open` in one transaction, in both orders; an unregistered signer that registers later; an EOA upgraded via TIP-1113 after open; `topUp` after rotation; snapshot deletion; payment-lane limits; and unchanged behavior at T14.

## Open questions

2. Should the precompile add a `verifyVoucher` view for payees?
3. Is T15 the right fork?
