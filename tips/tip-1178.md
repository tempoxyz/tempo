# TIP-1178: Zone Fees

## Abstract

From T15, zone blocks carry a nonzero base fee computed by the [TIP-1067](./tip-1067.md) controller, and transactions pay it in a USD-denominated TIP-20 that the zone has enabled. The fee goes directly from the fee payer to the block's beneficiary, with no FeeAMM conversion. A fee token is valued at $1 per unit: the protocol checks only that the token's `currency` is `USD`, not who issued it or what it trades at.

## Motivation

Zones charge a zero base fee today, so blockspace is free and any initialized TIP-20 can be named as a fee token. That makes spam cheap. It also means the fee token rule doesn't matter yet. Once fees are nonzero, it does: zones can enable non-USD tokens such as vault shares, and the fee manager charges every token as if one unit were $1. A share worth $100 would overpay 100x, and a token worth $0.001 would underpay 1,000x.

Alternatives considered:

- **FeeAMM on zones.** Convert any enabled token into the sequencer's token, as L1 does. This handles non-USD tokens but brings pools, liquidity and routing to every zone. Rejected as too complex for now.
- **A per-zone fee token allowlist.** The sequencer lists the tokens it accepts. This closes the self-declared `USD` gap in the [Threat Model](#threat-model) but needs new configuration and an interface. Left for a later TIP.
- **USD-only, as on L1 (chosen).** Reuse L1's check that the fee token's `currency` is `USD`. Operators are expected to sponsor most fees in their own stablecoin, so restricting fee tokens to USD costs users little.

## Assumptions

- Every token on a zone was enabled by the zone's portal admin with `ZonePortal.enableToken`, and its `currency` matches the L1 token's. Enabling is irreversible. If an admin enables a token that declares `USD` but isn't worth $1, fees paid in it are mispriced; the protocol does not prevent this.
- Zones inherit TIP-1067's constants (floor, cap and gas target) unchanged. This TIP doesn't retune them for zone traffic.
- T15 activates on a zone at the timestamp its chainspec sets, or inherits the L1 activation when the zone genesis leaves it unset.

# Specification

## Overview

Two things change at T15: a zone block's base fee, and which tokens can pay it.

1. **Base fee.** Before T15, every zone block's base fee is zero. From the first T15 block, the base fee follows the TIP-1067 controller, starting at the floor.
2. **Fee token.** The token a transaction pays in (its `fee_token`, or the zone default from `ZoneFeeManager`) must be an initialized TIP-20. From T15 it must also have `currency == "USD"`.
3. **Settlement.** Unchanged: `ZoneFeeManager` escrows the maximum fee before execution, refunds unused gas, and transfers the actual fee to the block beneficiary (the sequencer) in the same token. There is no FeeAMM, no validator token preference and no liquidity check.

Fee sponsorship works as on L1: when a transaction has a fee payer, the fee payer pays. An operator can sponsor fees in its own USD token while users hold any enabled token.

## Mechanics

### Base fee per block

For a block at timestamp `t` with parent `p`:

- If T15 is not active at `t`, the base fee is `0`.
- Otherwise the base fee is `tempo_t7_next_block_base_fee(p.base_fee_per_gas, p.gas_used)`, the TIP-1067 controller. A missing parent base fee counts as `0`, which the controller clamps up to the floor, so the T15 activation block starts at the floor.

Consensus checks each header's `base_fee_per_gas` against this value.

### Fee token validation

The handler checks the TIP-20 address prefix, then the zone fee manager checks, in order:

1. The token is initialized. Otherwise the transaction is invalid with `InvalidFeeToken(token)`.
2. From T15 only: the token's `currency` string is exactly `USD`. Otherwise the transaction is invalid with `FeeTokenNotUsdCurrency { address, currency }`. This is the check L1 applies (`ensure_tip20_usd`).

Before T15, step 2 is skipped, so blocks before activation stay valid under the old rules.

### Fee collection and settlement

Before execution, `ZoneFeeManager.collect_fee_pre_tx` checks that the fee payer may send and the beneficiary may receive the token under TIP-403, that the token isn't paused, and that any access-key spending limit covers the maximum fee. It then moves the maximum fee from the fee payer into the fee manager's escrow. A failed check makes the transaction invalid.

After execution, `collect_fee_post_tx` refunds the unused amount to the fee payer and restores the spending limit by that amount, then transfers the actual fee to the beneficiary and emits a TIP-20 `Transfer` from the fee payer to the beneficiary.

### Pool admission

From T15, the zone transaction pool rejects transactions whose `max_fee_per_gas` is below the TIP-1067 floor, as L1 does. Before T15, any fee cap is admitted. Transactions with a fee cap at or above the floor but below the current base fee wait in the pool.

## Interfaces

No new interfaces. The fee token error is the existing `TempoInvalidTransaction::FeeTokenNotUsdCurrency { address, currency }`, and the base fee constants are TIP-1067's.

# Compatibility

| Integration | What changes |
| --- | --- |
| Zone users and wallets | From T15, transactions need a fee cap of at least the floor and a fee paid (by them or a sponsor) in an enabled USD token. Zero-fee transactions are rejected. |
| Non-USD tokens | Vault shares and other non-USD tokens can no longer pay fees from T15. Transfers of them still work when the fee is paid in a USD token. |
| Operators | The sequencer receives fees in whichever USD token each payer used. Operators that sponsor fees need a balance in their sponsor token. |
| Zone RPC | From T15, `eth_gasPrice` and `eth_feeHistory` report the real base fee instead of the redacted constant. `eth_fillTransaction` defaults `max_fee_per_gas` to twice the next base fee, capped at the TIP-1067 cap, with a zero priority fee. |

Implementation: https://github.com/tempoxyz/tempo/pull/9351.

# Observability

N/A. Fees show as TIP-20 `Transfer` events from fee payer to beneficiary, and the base fee is in each block header, as on L1.

# Threat Model

| Actor | Controls | Defense | Remaining risk |
| --- | --- | --- | --- |
| Token creator | Can create an L1 TIP-20 with `currency = "USD"` worth far less than $1 | The token can't reach a zone unless the portal admin enables it | If enabled, fees paid in it are underpaid. Admins must enable only USD tokens they trust to hold $1. |
| Portal admin | Which tokens exist on the zone (irreversible) | None at the protocol level | Enabling a mispriced USD token lets fees be underpaid on that zone permanently. |
| Spammer | Volume of zone transactions | The base fee rises with usage under TIP-1067 and never drops below the floor | Same cost as on L1 at the same usage. |
| Fee payer | Fee token choice | Only initialized USD tokens from T15; TIP-403 and pause checks on the fee token | None beyond the token pricing risk above. |

Excluded: USD tokens whose value drifts from $1 (depegs). The protocol treats every USD token as $1, as L1 does.

# Invariants

- Every zone block before T15 has `base_fee_per_gas == 0`. Every block from T15 has `floor ≤ base_fee_per_gas ≤ cap`, equal to the controller's output for its parent.
- Every transaction in a T15 zone block paid its fee in a TIP-20 whose `currency` is `USD`.
- For each transaction, the fee payer's net fee debit equals the beneficiary's fee credit, and the fee manager's escrow balance is the same before and after the transaction.
- Tests cover: a non-USD fee token accepted before T15 and rejected from T15; the activation block's base fee equal to the floor; a sponsored transaction charging the fee payer, not the sender.
