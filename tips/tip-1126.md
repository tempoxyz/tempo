# TIP-1126: TIP-20 Asset Token Extensions

## Abstract

This TIP adds the features issuers of tokenized securities and funds need to TIP-20 itself: a choice of 6 or 18 decimals at creation, a display multiplier for splits and reinvested dividends (ERC-8056), partial freezes and forced transfers (ERC-7943), the ability to update the token's name and symbol, and issuer metadata made up of an ERC-7572 contract URI and key-value entries such as an ISIN.

Earlier drafts defined these features as a separate token type, TIP-20A, at its own `0x20A0` address prefix. This draft drops the separate type. Every feature is an addition to TIP-20 at the existing `0x20C0` prefix and is available to every TIP-20 token, new or existing. Asset tokens stay out of the fee manager and stablecoin DEX through the existing `currency == "USD"` check, with one new creation rule: an 18-decimal token cannot use the currency `USD`.

## Motivation

Issuers of tokenized assets need controls that TIP-20 does not have:

- **Decimals.** TIP-20 is fixed at 6 decimals. Many asset tokens and bridged assets use 18, and 6 decimals causes rounding problems for bridges and trading.
- **Stock splits and reinvested dividends.** Equity issuers record these by changing a per-token multiplier instead of rewriting every balance. ERC-8056 standardizes this and leaves balances in raw units.
- **Seizure, partial freezes, and lost-key recovery.** Transfer agents must move or hold specific amounts under court orders and sanctions. ERC-7943 standardizes this. A forced transfer is a cleaner record for reconciliation than a burn followed by a mint.
- **Renaming.** Issuers rename tokens after ticker changes, mergers, and fund reorganizations. TIP-20 sets `name` and `symbol` once at creation. Dinari asked for this directly.
- **Security identifiers.** Integrators need to map a token to the security it represents, for example by ISIN.

Asset tokens must also stay out of the fee manager and the stablecoin DEX. Issuers such as money market funds have legal constraints on where their token can be used.

### Alternatives Considered

1. **A separate token type at its own prefix (`0x20A0`).** The earlier draft of this TIP. It makes exclusion from payment components free, but it duplicates routing, recipient validation, keychain rules, and zone enablement for a second prefix, and existing TIP-20 issuers who want the new features would have to move to a new address. The TIP 20 Eng Group (2026-10-21) agreed most features fit in TIP-20 directly.
2. **A separate prefix only for 18-decimal tokens (`0x20C1`).** Decimals do not affect any transfer path. The only components that assume 6 decimals are the fee manager and the stablecoin DEX, and both accept only `USD` tokens. Forbidding `USD` with 18 decimals protects them without a second prefix, and avoids the migration problem of an issuer losing its token address.
3. **A token-level hook that calls an issuer contract on every transfer.** Precompiles cannot call into EVM code today, and zones cannot evaluate arbitrary contracts. Issuer logic belongs in a future TIP-403 policy type (see [Extension Points](#extension-points-non-normative)).
4. **Rebasing balances.** Rebasing changes `balanceOf` whenever the multiplier changes, which breaks DeFi accounting. ERC-8056 keeps balances raw.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| The TIP-20 implementation at activation includes TIP-1006 (`burnAt`), TIP-1028 (receive policies), and TIP-1075 (rewards deprecated). | The frozen-token rules for `burnAt` and receive-policy redirects refer to behavior that does not exist. |
| The fee manager and stablecoin DEX accept a token only if its `currency()` is `USD`, and these are the only components that assume 6 decimals. | An 18-decimal token could reach a component that misprices it. Such a component needs its own decimals check. |
| ERC-8056 is a Draft. This TIP follows the text and reference implementation at ERCs commit `554d3467b29742aae0f864cdd2fdb492510a91ba` (2026-09-01). | Later changes to ERC-8056 do not apply unless a TIP adopts them. |

# Specification

## Overview

Every TIP-20 token gains these features at activation:

| Feature | What the issuer can do | Standard | Gated by |
|---|---|---|---|
| Decimals | Choose 6 or 18 at creation. Immutable. | — | Set at creation |
| Display multiplier | Record splits and reinvested dividends without changing any balance. | ERC-8056 | `UI_MULTIPLIER_ROLE` |
| Partial freeze | Hold a chosen amount of an account's tokens. The rest moves normally. | ERC-7943 | `FREEZE_ROLE` |
| Forced transfer | Move tokens without the holder's authorization, for seizures and lost-key recovery. | ERC-7943 | `FORCED_TRANSFER_ROLE` |
| Name and symbol | Update `name` and `symbol` after creation. | — | `DEFAULT_ADMIN_ROLE` |
| Metadata | Publish a contract URI and key-value entries such as an ISIN. | ERC-7572 (URI) | `DEFAULT_ADMIN_ROLE` |

No role is held by anyone until the admin grants it, so a token that does not use these features behaves exactly as before. Existing tokens read as 6 decimals, a multiplier of `1e18`, nothing frozen, and empty metadata.

### Asset Tokens and Payment Components

There is no separate asset token type. An issuer keeps a token out of the fee manager and stablecoin DEX by choosing a `currency` other than `USD` at creation, since both already reject non-`USD` tokens. Asset tokens SHOULD use a currency other than `USD`, and SHOULD record the denomination of the underlying asset in [extra metadata](#extra-metadata) instead. An 18-decimal token MUST NOT use `USD` (see [Token Creation](#token-creation)).

Asset tokens keep the `0x20C0` prefix, so their transfers are classified as payments under TIP-1045 and they can be used in the TIP-20 channel reserve, as any TIP-20 can. See [Open Questions](#open-questions).

### Example

An issuer creates an 18-decimal fund token with currency `""` and an allowlist transfer policy bound at creation. It grants `FREEZE_ROLE` and `FORCED_TRANSFER_ROLE` to its compliance contract and `UI_MULTIPLIER_ROLE` to its corporate-actions contract.

1. **Freeze.** A holder has 100 tokens. A court order freezes 30. The holder can still transfer up to 70, and `balanceOf` still shows 100.
2. **Seizure.** The court then orders 80 tokens moved. `forcedTransfer` takes the 70 unfrozen tokens and 10 frozen ones. The holder is left with a balance of 20, all of it frozen.
3. **Split.** The fund does a 4-for-1 split. The issuer schedules the multiplier to change from `1e18` to `4e18`. Once it takes effect, `balanceOf(holder)` is still 20 and `balanceOfUI(holder)` is 80.
4. **Rename.** The fund is renamed after a reorganization. The admin calls `setName` and `setSymbol`. The token address, balances, and roles are unchanged.

### Definitions

```
frozen(a)   = frozen amount of a
unfrozen(a) = balanceOf(a) - frozen(a)
```

`balanceOf(a)` is always the holder's total balance, frozen and unfrozen together.

**Protected addresses** are the addresses `burnAt` refuses: the TIP-20 `PROTECTED` system custody addresses active at the current hardfork (including `ReceivePolicyGuard`), the token's own address, and ZonePortal addresses. They can never be frozen, force-debited, or force-credited.

### Naming

Names follow TIP-20 conventions (`setX` setters, `XUpdated(address indexed updater, …)` events, one role per privileged function), except where an ERC fixes the name. ERC-7943, ERC-8056, and ERC-7572 names are used exactly, because integrators detect and call them by selector.

## Activation

All behavior in this TIP applies from the protocol version assigned to it, to every TIP-20 token. Before activation, the new functions follow unknown-selector behavior.

## Token Creation

`TIP20Factory` adds a `createToken` overload with two more arguments, `decimals` and `transferPolicyId`. It validates everything before writing any state:

1. Revert `InvalidDecimals` unless `decimals` is 6 or 18.
2. Revert `InvalidCurrency` if `decimals` is 18 and `currency` is `USD`.
3. Revert `InvalidTransferPolicyId` unless `transferPolicyId` exists in the TIP-403 registry. The built-in allow-all (`1`) and reject-all (`0`) policies exist.
4. Apply every check of the existing `createToken` overload with `logoURI`.

It then creates the token as that overload does, stores `decimals`, and binds `transferPolicyId` to the token. Binding the policy at creation means a regulated token is never unrestricted, even before its first mint. It emits the same events as the existing overload, then `TokenCreatedWithDecimals(token, decimals, transferPolicyId)`.

Tokens created with the existing overloads have 6 decimals and the allow-all policy, as today.

## Decimals

`decimals()` returns 6 or 18. It never changes after creation. Amounts in every function and event stay in raw units.

## Name and Symbol

`setName(newName)` and `setSymbol(newSymbol)`:

1. Revert `Unauthorized` unless the caller holds `DEFAULT_ADMIN_ROLE`.
2. Store the new value.
3. Emit `NameUpdated(msg.sender, newName)` or `SymbolUpdated(msg.sender, newSymbol)`.

They apply the same validation as `createToken` applies to `name` and `symbol`, and work while the token is paused.

The EIP-712 domain separator used by `permit` includes `name`, so a rename changes `DOMAIN_SEPARATOR()`. Permits signed before the rename fail after it. Nonces are unchanged.

## Frozen Tokens

An account with `FREEZE_ROLE` sets a frozen amount per account. The holder cannot move that many tokens, and the rest of the balance moves normally. The frozen amount can never exceed the balance.

### `setFrozenTokens(account, amount)`

1. Revert `Unauthorized` unless the caller holds `FREEZE_ROLE`.
2. Revert `ProtectedAddress` if `account` is protected.
3. Revert `VirtualAddressNotAllowed` if `account` is a TIP-1022 virtual address. Virtual addresses hold no balance; their master does.
4. Revert `InsufficientBalance` if `amount > balanceOf(account)`.
5. Set `frozen(account) = amount`.
6. Emit `Frozen(account, amount)`. Return `true`.

`setFrozenTokens` works while the token is paused. To hold tokens that have not arrived yet, the issuer freezes them after they arrive, or uses the transfer policy to block the account.

### Effect on Each Operation

| Operation | Debited account | Limited to `unfrozen`? | Changes `frozen`? |
|---|---|---|---|
| `transfer`, `transferWithMemo` | caller | Yes | No |
| `transferFrom`, `transferFromWithMemo` | `from` | Yes | No |
| `burn`, `burnWithMemo` | caller | Yes | No |
| Receive-policy redirect of any of the above (TIP-1028) | sender | Yes, same check as the transfer | No |
| Fee payment through the fee manager | payer | Yes | No |
| `burnAt`, `burnBlocked` | burned account | No | Yes, see below |
| `forcedTransfer` | `from` | No | Yes, see below |
| `mint`, incoming transfers | none | n/a | No |
| `approve`, `permit` | none | n/a | No |

**Limited operations.** A limited debit of `amount` from `a` reverts if `amount > unfrozen(a)`. If `amount <= balanceOf(a)`, the error is `ERC7943InsufficientUnfrozenBalance(a, amount, unfrozen(a))`; otherwise it is `InsufficientBalance`. The check runs before the TIP-1028 receive-policy check, so it also limits a transfer that would be redirected to `ReceivePolicyGuard`.

**Privileged debits.** Let `u = unfrozen(a)` before the debit. If `amount > u`, then before the balance changes `frozen(a) = frozen(a) - (amount - u)`, and the token emits `Frozen(a, frozen(a))` before the `Transfer` event.

### Storage of Frozen Amounts

`balances[a]` holds the unfrozen amount, and a separate `frozen[a]` mapping holds the frozen amount. `balanceOf(a)` returns their sum, so wallets show holders their full position. `setFrozenTokens` moves tokens between the two slots and leaves `balanceOf` and `totalSupply` unchanged.

Transfers, fee payment, and the transaction pool's fee-balance check read only `balances[a]`, as today. The frozen check costs nothing on the hot path, and no component outside the token needs to know about freezes. `frozen[a]` is read only by `balanceOf`, the failure path of a limited debit (to choose the error), and privileged debits.

The TIP 20 Eng Group (2026-10-21) also considered storing the frozen amount next to an unchanged total balance. That adds a second storage read to every transfer and fee payment, and needs frozen checks in the fee manager and transaction pool, so it was not adopted.

## Forced Transfer

`forcedTransfer(from, to, amount)`:

1. Revert `Unauthorized` unless the caller holds `FORCED_TRANSFER_ROLE`.
2. Revert `ProtectedAddress` if `from` is protected.
3. Resolve `to` as TIP-20 transfers do (TIP-1022 virtual addresses resolve to their master). Revert `InvalidRecipient` if the resolved target is zero or has the TIP-20 prefix. Revert `ProtectedAddress` if it is protected.
4. Revert `ERC7943CannotReceive(to)` if `canReceive(to)` is false.
5. Revert `PolicyForbids` if the resolved target's TIP-1028 receive policy rejects this token from `from`. A forced transfer is never redirected to `ReceivePolicyGuard`, because the guard's recovery path could return seized tokens to `from`.
6. Revert `InsufficientBalance` if `amount > balanceOf(from)`.
7. Apply the [privileged-debit](#effect-on-each-operation) rule to `from`.
8. Debit `from` and credit the target. Emit `Transfer(from, to, amount)` (plus the TIP-1022 forwarding `Transfer` for a virtual `to`), then `ForcedTransfer(from, to, amount)`. Return `true`.

A forced transfer does not check the pause state, the sender leg of the transfer policy, allowances, or access-key spending limits. A lost-wallet recovery is a `forcedTransfer` of the full balance to the holder's new address.

## Permission Views

The three views revert only if they run out of gas. On any other internal error they return `false`.

- `canSend(account)`: the token's TIP-403 transfer policy authorizes `account` as sender.
- `canReceive(account)`: `account` resolves as a transfer recipient (TIP-1022), and the policy authorizes the resolved address as recipient.
- `canTransfer(from, to, amount)`: the token is not paused, `canSend(from)` and `canReceive(to)` are true, and `amount <= unfrozen(from)`.

They do not evaluate TIP-1028 receive policies, allowances, or access-key spending limits.

## UI Multiplier

The multiplier tells wallets how to display balances. It never changes balances, transfers, allowances, total supply, the supply cap, or any event amount.

The token stores the multiplier in effect now (`uiMultiplier`), a scheduled multiplier (`newUIMultiplier`), and when the scheduled one takes effect (`effectiveAt`). A stored multiplier of 0 reads as `1e18`, so existing tokens need no migration.

```
UI_MULTIPLIER_ONE  = 1e18
MAX_UI_MULTIPLIER  = 1e36
```

### Views

These follow the ERC-8056 reference implementation:

- `uiMultiplier()`: `newUIMultiplier` if `block.timestamp >= effectiveAt`, else `uiMultiplier`.
- `newUIMultiplier()`, `effectiveAt()`: the stored values.
- `toUIAmount(raw) = raw * uiMultiplier() / 1e18`, rounded down.
- `fromUIAmount(ui) = ui * 1e18 / uiMultiplier()`, rounded down.
- `balanceOfUI(a) = toUIAmount(balanceOf(a))`. `totalSupplyUI() = toUIAmount(totalSupply())`.

`toUIAmount` and `fromUIAmount` revert on overflow.

### Scheduling an Update

`setUIMultiplier(newMultiplier, effectiveAtTimestamp)`:

1. Revert `Unauthorized` unless the caller holds `UI_MULTIPLIER_ROLE`.
2. Revert `InvalidUIMultiplier` unless `0 < newMultiplier <= MAX_UI_MULTIPLIER`.
3. Revert `InvalidEffectiveAt` unless `block.timestamp < effectiveAtTimestamp < 2^64`.
4. If no update is pending (`block.timestamp >= effectiveAt`): let `old = newUIMultiplier`. Set `uiMultiplier = old`, `newUIMultiplier = newMultiplier`, `effectiveAt = effectiveAtTimestamp`. Emit `UIMultiplierUpdated(old, newMultiplier, effectiveAtTimestamp)`.
5. If an update is pending: emit `UIMultiplierUpdateCancelled(newUIMultiplier, effectiveAt)`. Set `newUIMultiplier = newMultiplier` and `effectiveAt = effectiveAtTimestamp`. Emit `UIMultiplierUpdated(uiMultiplier, newMultiplier, effectiveAtTimestamp)`.

`cancelUIMultiplierUpdate()`:

1. Revert `Unauthorized` unless the caller holds `UI_MULTIPLIER_ROLE`.
2. Revert `NoPendingUIMultiplierUpdate` unless `block.timestamp < effectiveAt`.
3. Emit `UIMultiplierUpdateCancelled(newUIMultiplier, effectiveAt)`. Set `newUIMultiplier = uiMultiplier` and `effectiveAt = 0`.

Both work while the token is paused, so an issuer can pause trading, apply a corporate action, and unpause. No event is emitted when a scheduled multiplier takes effect; indexers derive that moment from `effectiveAt`.

## Metadata

### Contract URI

`contractURI()` returns the stored string. `setContractURI(newContractURI)` requires `DEFAULT_ADMIN_ROLE`. It reverts `ContractURITooLong` if the value is longer than 1024 bytes, and `InvalidContractURI` if the value is non-empty and its scheme fails the TIP-1026 `logoURI` scheme rules. It then stores the value and emits `ContractURIUpdated()`, which has no parameters because ERC-7572 defines it that way.

### Extra Metadata

`extraMetadata(key)` returns the value stored under `key`, or the empty string.

`setExtraMetadata(key, newValue)`:

1. Revert `Unauthorized` unless the caller holds `DEFAULT_ADMIN_ROLE`.
2. Revert `InvalidExtraMetadataKey` if `key` is empty or longer than 32 bytes.
3. Revert `ExtraMetadataValueTooLong` if `newValue` is longer than 256 bytes.
4. Store `newValue` under `key`, or remove the entry if `newValue` is empty.
5. Emit `ExtraMetadataUpdated(msg.sender, key, newValue)`.

Keys are case-sensitive. Entries cannot be listed on-chain; indexers rebuild them from events. Issuers SHOULD use lowercase keys, SHOULD store a 12-character ISIN under `isin`, and SHOULD store the underlying asset's denomination under `denomination`.

## Roles

| Role | Gates |
|---|---|
| `FREEZE_ROLE` | `setFrozenTokens` |
| `FORCED_TRANSFER_ROLE` | `forcedTransfer` |
| `UI_MULTIPLIER_ROLE` | `setUIMultiplier`, `cancelUIMultiplierUpdate` |

`DEFAULT_ADMIN_ROLE` administers all three and gates `setName`, `setSymbol`, `setContractURI`, and `setExtraMetadata`, as it gates `setLogoURI`. Freezing and forced transfer are separate roles, so an issuer can grant the ability to hold funds without the ability to move them.

## Changes to Other Components

- **TIP-20 Factory.** The new `createToken` overload and the `USD`/18-decimal rule.
- **Fee manager and transaction pool.** No change. Both read `balances[a]`, which holds only the unfrozen amount.
- **No change needed.** Precompile routing, recipient validation, the TIP-403 registry, the account keychain, the stablecoin DEX, the channel reserve, payment classification, and ZonePortal token enablement, since asset tokens are TIP-20 tokens.

## Extension Points (Non-Normative)

Issuer-defined transfer logic belongs in a future TIP-403 policy type whose authorization is answered by a contract. A token adopts it with `changeTransferPolicyId`, and `canSend`, `canReceive`, and `canTransfer` reflect it because they delegate to TIP-403. Amount-aware checks, such as a maximum balance per holder, need a registry call that carries the amount. Until then, issuers run their own logic in contracts that hold the token's roles.

## Open Questions

1. **Zones.** With the `0x20C0` prefix, asset tokens can be enabled in a zone with standard enablement. Still to resolve: whether frozen amounts and forced transfers apply to balances held in a zone, and how a custom TIP-403 policy is enforced there, since arbitrary policy state cannot be synced to a zone. One proposal is to require a simple allowlist or blocklist policy alongside any custom policy for zone use. Name and symbol updates must also reach the zone's copy of the token.
2. **Payment lane.** Asset-token transfers are classified as payments under TIP-1045 because classification is by prefix. Excluding them would need a stateful check at classification time.

### Storage

Each TIP-20 token adds:

| Field | Type | Meaning |
|---|---|---|
| `decimals` | `uint8` | 0 (reads as 6) or 18. Set at creation, immutable. |
| `frozen` | `mapping(address => uint256)` | Frozen amount per account. Default 0. `balances` holds the unfrozen amount. |
| `uiMultiplier` | `uint256` | Multiplier in effect before `effectiveAt`. 0 reads as `1e18`. |
| `newUIMultiplier` | `uint256` | Multiplier in effect from `effectiveAt`. 0 reads as `1e18`. |
| `effectiveAt` | `uint64` | Timestamp at which `newUIMultiplier` takes effect. |
| `contractURI` | `string` | ERC-7572 metadata URI. Default empty. |
| `extraMetadata` | `mapping(string => string)` | Issuer-defined metadata entries. Default empty. |

# Tooling

- **Contract bindings:** add the new functions to `ITIP20` and the factory overload to `tempo-contracts` and the SDKs.
- **Explorers and wallets:** read `decimals()` instead of assuming 6. Show `balanceOfUI` next to `balanceOf` when `supportsInterface(0xa60bf13d)` is true and `uiMultiplier() != 1e18`, and show pending updates from `newUIMultiplier()` and `effectiveAt()`. Refresh `name` and `symbol` on `NameUpdated` and `SymbolUpdated`.
- **`tips/verify`:** extend the TIP-20 reference implementation and invariant suite.

# Threat Model

- **`DEFAULT_ADMIN_ROLE` holder:** fully trusted by holders. Can grant every role, change the transfer policy, rename the token, and change its metadata, including the ISIN. A rename can make a token resemble another; integrators SHOULD identify tokens by address.
- **`FREEZE_ROLE` holder:** trusted to hold funds only when legally required. Can freeze any unprotected account, including while paused. Cannot move funds.
- **`FORCED_TRANSFER_ROLE` holder:** trusted to move funds only when legally required. Can move any unprotected account's balance to any valid recipient, including while paused. Cannot touch protected addresses or bypass the recipient's transfer or receive policy.
- **`UI_MULTIPLIER_ROLE` holder:** trusted to record corporate actions correctly. A wrong multiplier misleads displays and pricing, but cannot change any balance.
- **Holders:** untrusted. Cannot move frozen tokens, including through a receive-policy redirect or fee payment.
- **Integrators and DeFi contracts:** must treat `balanceOf` as raw units, read `decimals()`, and apply `uiMultiplier()` only for display or pricing.

# Invariants

1. The sum of all balances equals `totalSupply()`.
2. `setUIMultiplier`, `cancelUIMultiplierUpdate`, `setFrozenTokens`, `setName`, `setSymbol`, `setContractURI`, and `setExtraMetadata` never change any `balanceOf` or `totalSupply()`.
3. A holder-initiated outflow of `amount` from `a`, including fee payment, succeeds only if `amount <= unfrozen(a)`.
4. `frozen(a)` changes only through `setFrozenTokens`, `forcedTransfer`, `burnAt`, and `burnBlocked`. The last three only decrease it, by exactly the part of the debit that exceeded `unfrozen(a)`.
5. Protected addresses always have `frozen = 0`, and `forcedTransfer` never debits or credits them.
6. `0 < uiMultiplier() <= MAX_UI_MULTIPLIER` at all times.
7. `decimals()` is 6 or 18 and never changes. No token with 18 decimals has currency `USD`.
8. If `canTransfer(from, to, amount)` is `true`, a `transfer` or `transferFrom` of `amount` does not revert for pause, transfer-policy, or frozen-balance reasons.
9. A token that never uses this TIP's functions behaves exactly as it did before activation.
