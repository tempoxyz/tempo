# TIP-1126: TIP-20A Asset Tokens

## Abstract

TIP-20A is a second native token type for tokenized securities, funds, and other non-payment assets. A TIP-20A token has the full TIP-20 interface and behavior, lives at its own reserved address prefix, and adds four things: a choice of 6 or 18 decimals at creation, a display multiplier for splits and reinvested dividends (ERC-8056), partial freezes and forced transfers for transfer agents (ERC-7943), and issuer metadata: a contract metadata URI (ERC-7572) and key-value entries such as an ISIN.

Every rule in this TIP is evaluated natively by precompiles over token state and TIP-403 policy state. Nothing calls into EVM code.

## Motivation

Issuers of tokenized assets need controls that TIP-20 does not have, and TIP-20 has payment-lane properties that asset tokens should not have.

- **Decimals.** TIP-20 is fixed at 6. Most asset tokens in use today use 6 or 18 decimals. TIP-20A allows exactly those two values; any other value adds conversion and display risk for integrators without a matching need.
- **Stock splits and reinvested dividends.** Equity issuers record these by changing a per-token multiplier instead of rewriting every balance. ERC-8056 standardizes this with balances left in raw units.
- **Seizure, partial freezes, lost-key recovery.** Transfer agents must move or hold specific amounts under court orders and sanctions. ERC-7943 (Final) standardizes this, building on ERC-3643.
- **Security identifiers.** Integrators need to map a token to the security it represents, for example by ISIN. A key-value metadata store holds such identifiers on-chain.
- **Separation from payments.** Asset tokens should not be fee tokens, DEX quote tokens, or payment-classified transactions. The fee manager, stablecoin DEX, channel reserve, and payment classification already validate tokens by the `0x20C0` prefix, so a separate prefix keeps TIP-20A out of all four with no change to them.

Names follow TIP-20 conventions (`setX` setters, `XUpdated(address indexed updater, …)` events, one role per privileged function) except where an ERC fixes the name. ERC-7943, ERC-8056, and ERC-7572 names are used exactly, because integrators detect and call them by selector.

### Alternatives considered

1. **A flag on TIP-20 tokens.** Every component that accepts TIP-20 would need a new storage read to exclude asset tokens. A prefix makes the exclusion free and visible from the address.
2. **A token-level hook that calls an issuer contract on every transfer.** Precompiles cannot call into EVM code today, and zones cannot evaluate arbitrary contracts. The extension point for issuer logic is left in TIP-403, where it can be added later without changing TIP-20A tokens (see Extension points).
3. **Rebasing balances.** This changes `balanceOf` whenever the multiplier changes, which breaks DeFi accounting. ERC-8056 keeps balances raw. A rebasing variant can be added later as a separate token type.

## Assumptions

- The T9 TIP-403 registry binding is active: a token's transfer policy id is stored in the TIP-403 registry, not in token storage.
- The TIP-20 implementation at activation includes TIP-1006 (`burnAt`), TIP-1028 (receive policies), and TIP-1075 (rewards deprecated).
- No contract code or EIP-7702 delegation exists at any address with the TIP-20A prefix before activation. Reaching such an address requires a 96-bit prefix collision. If code exists at such an address, activation MUST be blocked until it is handled.
- Zone support for TIP-20A is out of scope. Zones route TIP-20 by the `0x20C0` prefix, and ZonePortal token enablement requires `isTIP20`, so TIP-20A tokens cannot be enabled in a zone until a zone TIP adds support.

# Specification

## Activation

All behavior in this TIP applies from the protocol version assigned to it. Before activation, addresses with the TIP-20A prefix are not precompiles and `createAssetToken` follows unknown-selector behavior. Existing TIP-20 tokens are unchanged, except for the recipient-validation change under "Changes to other components".

## Address space

TIP-20A tokens live at:

```
TIP20A_PREFIX (12 bytes) = 0x20A000000000000000000000
token address           = TIP20A_PREFIX || keccak256(abi.encode(sender, salt))[0:8]
```

This is the TIP-20 derivation with a different prefix. Addresses whose lower 8 bytes are below 1024 are reserved, as for TIP-20. `isTIP20(addr)` returns `false` for every TIP-20A address, and `isTIP20A(addr)` returns `false` for every TIP-20 address.

## Relationship to TIP-20

A TIP-20A token implements every TIP-20 function, event, and error with the same selector and the same behavior, except for the differences listed here. This includes roles, `mint`, `burn`, `burnBlocked`, `burnAt`, memos, supply cap, pause, TIP-403 transfer policies (including compound policies), TIP-1028 receive policies, TIP-1022 virtual recipients, `permit`, access-key spending limits, and `logoURI`.

Differences from TIP-20:

| TIP-20 function | TIP-20A behavior |
|---|---|
| `decimals()` | Returns the value set at creation: 6 or 18. Declared `view`, not `pure`. |
| `quoteToken()`, `nextQuoteToken()` | Return `address(0)`. |
| `setNextQuoteToken`, `completeQuoteTokenUpdate` | Revert with `InvalidQuoteToken`. |
| `transfer`, `transferFrom`, `transferWithMemo`, `transferFromWithMemo`, `burn`, `burnWithMemo` | Additionally limited to the sender's unfrozen balance (see Frozen tokens). |
| `burnAt`, `burnBlocked` | May burn frozen tokens and reduce the frozen amount (see Frozen tokens). |
| Reward functions | Behave as on a TIP-20 token after TIP-1075: `setRewardRecipient` and `distributeReward` are no-ops, reward views return zero, and `claimRewards` returns 0. |

`currency()` works as on TIP-20: free-form, set at creation, no ISO-4217 check. The TIP-20 rule that a USD token needs a USD quote token does not apply, because TIP-20A has no quote token.

## State

In addition to TIP-20 token state, each TIP-20A token stores:

| Field | Type | Meaning |
|---|---|---|
| `decimals` | `uint8` | 6 or 18. Set at creation, immutable. |
| `frozen` | `mapping(address => uint256)` | Frozen amount per account. Default 0. |
| `uiMultiplier` | `uint256` | Multiplier in effect before `effectiveAt`. |
| `newUIMultiplier` | `uint256` | Multiplier in effect from `effectiveAt`. |
| `effectiveAt` | `uint64` | Timestamp at which `newUIMultiplier` takes effect. |
| `contractURI` | `string` | ERC-7572 metadata URI. Default empty. |
| `extraMetadata` | `mapping(string => string)` | Issuer-defined metadata entries. Default empty. |

The quote-token and reward fields of TIP-20 storage are never written by a TIP-20A token.

## Roles

| Role | Identifier | Gates |
|---|---|---|
| `FREEZE_ROLE` | `keccak256("FREEZE_ROLE")` = `0x5789b43a60de35bcedee40618ae90979bab7d1315fd4b079234241bdab19936d` | `setFrozenTokens` |
| `FORCED_TRANSFER_ROLE` | `keccak256("FORCED_TRANSFER_ROLE")` = `0xf46cc65c16907d99724035a1f82735f7ae31bf036bdedbf9639710ffd156e35e` | `forcedTransfer` |
| `UI_MULTIPLIER_ROLE` | `keccak256("UI_MULTIPLIER_ROLE")` = `0xaeb2a04b5c0b03314842538e4cbd28316edd6ab050cf7939cb4fb49cae3766c6` | `setUIMultiplier`, `cancelUIMultiplierUpdate` |

All three are administered by `DEFAULT_ADMIN_ROLE` and granted to nobody at creation. `setContractURI` and `setExtraMetadata` are gated by `DEFAULT_ADMIN_ROLE`, like `setLogoURI`. All TIP-20 roles apply unchanged; `burnAt` stays gated by `BURN_AT_ROLE` and `burnBlocked` by `BURN_BLOCKED_ROLE`.

Freezing and forced transfer are separate roles, as `burnBlocked` and `burnAt` are on TIP-20, so an issuer can grant the ability to hold funds without the ability to move them.

## Frozen tokens

An account with `FREEZE_ROLE` sets a frozen amount per account. The holder cannot move that many tokens; the rest of the balance moves normally. The frozen amount may exceed the balance, in which case tokens that arrive later are also held until the balance exceeds the frozen amount.

Definitions:

```
frozen(a)   = frozen amount of a
unfrozen(a) = balanceOf(a) - frozen(a)   if balanceOf(a) > frozen(a)
            = 0                          otherwise
```

Example: balance 100, frozen 30. The holder can transfer up to 70. If the frozen amount is set to 150, the holder can transfer nothing, and after receiving 80 more (balance 180) can transfer 30.

**Protected addresses** are the addresses `burnAt` refuses: the TIP-20 `PROTECTED` system custody addresses active at the current hardfork (including `ReceivePolicyGuard`), the token's own address, and ZonePortal addresses. They can never be frozen, force-debited, or force-credited.

### `setFrozenTokens(account, amount)`

1. Revert `Unauthorized` unless the caller holds `FREEZE_ROLE`.
2. Revert `ProtectedAddress` if `account` is protected.
3. Revert `VirtualAddressNotAllowed` if `account` is a TIP-1022 virtual address. Virtual addresses hold no balance; their master does.
4. Set `frozen(account) = amount`. Any value is allowed, including values above the balance and 0.
5. Emit `Frozen(account, amount)`. Return `true`.

Works while the token is paused.

### Effect on each operation

| Operation | Debited account | Limited to `unfrozen`? | Changes `frozen`? |
|---|---|---|---|
| `transfer`, `transferWithMemo` | caller | Yes | No |
| `transferFrom`, `transferFromWithMemo` | `from` | Yes | No |
| `burn`, `burnWithMemo` | caller | Yes | No |
| Receive-policy redirect of any of the above (TIP-1028) | sender | Yes, same check as the transfer | No |
| `burnAt`, `burnBlocked` | burned account | No | Yes, see below |
| `forcedTransfer` | `from` | No | Yes, see below |
| `mint`, incoming transfers | none | n/a | No |
| `approve`, `permit` | none | n/a | No |

**Limited operations.** If `amount > unfrozen(from)` and `amount <= balanceOf(from)`, the call reverts with `ERC7943InsufficientUnfrozenBalance(from, amount, unfrozen(from))`. If `amount > balanceOf(from)`, the existing `InsufficientBalance` error applies. The check runs before the TIP-1028 receive-policy check, so a transfer that would be redirected to `ReceivePolicyGuard` is also limited.

**Privileged debits.** Let `u = unfrozen(a)` before the debit. If `amount > u`, then before the balance changes:

```
frozen(a) = frozen(a) - (amount - u)
```

and the token emits `Frozen(a, frozen(a))` before the `Transfer` event. Example: balance 100, frozen 30, `burnAt` of 80 moves 70 unfrozen and 10 frozen tokens; frozen becomes 20 and balance becomes 20.

Protected addresses always have `frozen = 0`, so `ReceivePolicyGuard` claims and burns from the guard are unaffected.

## Forced transfer

`forcedTransfer(from, to, amount)`:

1. Revert `Unauthorized` unless the caller holds `FORCED_TRANSFER_ROLE`.
2. Revert `ProtectedAddress` if `from` is protected.
3. Resolve `to` as TIP-20 transfers do (TIP-1022 virtual addresses resolve to their master). Revert `InvalidRecipient` if the resolved target is zero or has the TIP-20 or TIP-20A prefix. Revert `ProtectedAddress` if the resolved target is protected; this includes `ReceivePolicyGuard`.
4. Revert `ERC7943CannotReceive(to)` if `canReceive(to)` is false.
5. Revert `PolicyForbids` if the resolved target's TIP-1028 receive policy rejects this token from `from`. A forced transfer is never redirected to `ReceivePolicyGuard`, because the guard's recovery path could return seized tokens to `from`.
6. Revert `InsufficientBalance` if `amount > balanceOf(from)`.
7. Apply the privileged-debit unfreeze rule to `from`.
8. Debit `from`, credit the target, and emit `Transfer(from, to, amount)` (plus the TIP-1022 forwarding `Transfer` for a virtual `to`), then `ForcedTransfer(from, to, amount)`, where `to` is the address as passed. Return `true`.

Not checked: pause state, the sender leg of the transfer policy for `from`, allowances, and access-key spending limits.

A lost-wallet recovery is a `forcedTransfer` of the full balance to the holder's new address.

## Permission views

All three views never revert. On any internal error they return `false`.

- `canSend(account)`: the token's TIP-403 transfer policy authorizes `account` in the sender role.
- `canReceive(account)`: `account` is resolved as a transfer recipient (TIP-1022), and the token's TIP-403 transfer policy authorizes the resolved address in the recipient role. An address that fails recipient validation returns `false`.
- `canTransfer(from, to, amount)`: returns `true` only if the token is not paused, `canSend(from)`, `canReceive(to)`, and, when `frozen(from) > 0`, `amount <= unfrozen(from)`. With nothing frozen it does not look at the balance, as ERC-7943 requires.

These views do not evaluate TIP-1028 receive policies, because a receive-policy rejection redirects the transfer rather than failing it. They do not evaluate allowances or access-key spending limits.

Ordinary transfers keep TIP-20's errors: a policy rejection reverts with `PolicyForbids` and a pause with `ContractPaused`. The ERC-7943 errors are used only where this TIP says so.

## UI multiplier

The multiplier tells wallets how to display balances. It never changes balances, transfers, allowances, total supply, the supply cap, or any event amount. A 4-for-1 split is recorded by changing the multiplier from `1e18` to `4e18`: a holder of 100 tokens still holds 100, and `balanceOfUI` shows 400.

Constants:

```
UI_MULTIPLIER_ONE  = 1e18
MAX_UI_MULTIPLIER  = 1e36
```

`MAX_UI_MULTIPLIER` keeps `balance * multiplier` within `uint256` for any balance up to `2^128`, so `balanceOfUI` and `totalSupplyUI` never overflow.

Views, following the ERC-8056 reference implementation:

- `uiMultiplier()`: `newUIMultiplier` if `block.timestamp >= effectiveAt`, else `uiMultiplier`.
- `newUIMultiplier()`, `effectiveAt()`: the stored values.
- `toUIAmount(raw) = raw * uiMultiplier() / 1e18`, rounded down.
- `fromUIAmount(ui) = ui * 1e18 / uiMultiplier()`, rounded down.
- `balanceOfUI(a) = toUIAmount(balanceOf(a))`. `totalSupplyUI() = toUIAmount(totalSupply())`.

`toUIAmount` and `fromUIAmount` take arbitrary inputs and revert on overflow.

`setUIMultiplier(newMultiplier, effectiveAtTimestamp)`:

1. Revert `Unauthorized` unless the caller holds `UI_MULTIPLIER_ROLE`.
2. Revert `InvalidUIMultiplier` unless `0 < newMultiplier <= MAX_UI_MULTIPLIER`.
3. Revert `InvalidEffectiveAt` unless `block.timestamp < effectiveAtTimestamp < 2^64`.
4. If no update is pending (`block.timestamp >= effectiveAt`): let `old = newUIMultiplier`; set `uiMultiplier = old`, `newUIMultiplier = newMultiplier`, `effectiveAt = effectiveAtTimestamp`; emit `UIMultiplierUpdated(old, newMultiplier, effectiveAtTimestamp)`.
5. If an update is pending: emit `UIMultiplierUpdateCancelled(newUIMultiplier, effectiveAt)`; set `newUIMultiplier = newMultiplier`, `effectiveAt = effectiveAtTimestamp`; emit `UIMultiplierUpdated(uiMultiplier, newMultiplier, effectiveAtTimestamp)`.

`cancelUIMultiplierUpdate()`:

1. Revert `Unauthorized` unless the caller holds `UI_MULTIPLIER_ROLE`.
2. Revert `NoPendingUIMultiplierUpdate` unless `block.timestamp < effectiveAt`.
3. Emit `UIMultiplierUpdateCancelled(newUIMultiplier, effectiveAt)`; set `newUIMultiplier = uiMultiplier` and `effectiveAt = 0`.

Both functions work while the token is paused, so an issuer can pause trading, apply a corporate action, and unpause.

The earliest a new multiplier can take effect is the next second after the call. No event is emitted at the moment a scheduled multiplier takes effect; indexers derive it from `effectiveAt`.

## Metadata

### Contract URI

`contractURI()` returns the stored string. `setContractURI(newContractURI)` requires `DEFAULT_ADMIN_ROLE`, applies the TIP-1026 `logoURI` rules (at most 256 bytes; empty, or a scheme among `https`, `http`, `ipfs`, `data`), reverting `ContractURITooLong` or `InvalidContractURI`, stores the value, and emits `ContractURIUpdated()`.

The URI points to, or contains, an ERC-7572 JSON document. ERC-7572 requires only a `name` field. The protocol does not validate the document.

`ContractURIUpdated()` has no `updater` parameter, unlike TIP-20's `LogoURIUpdated`, because ERC-7572 defines it that way.

### Extra metadata

Constants:

```
MAX_EXTRA_METADATA_KEY_BYTES   = 32
MAX_EXTRA_METADATA_VALUE_BYTES = 256
```

`extraMetadata(key)` returns the value stored under `key`, or the empty string if none is stored.

`setExtraMetadata(key, newValue)`:

1. Revert `Unauthorized` unless the caller holds `DEFAULT_ADMIN_ROLE`.
2. Revert `InvalidExtraMetadataKey` if `key` is empty or longer than `MAX_EXTRA_METADATA_KEY_BYTES`.
3. Revert `ExtraMetadataValueTooLong` if `newValue` is longer than `MAX_EXTRA_METADATA_VALUE_BYTES`.
4. If `newValue` is empty, remove the entry under `key`. Otherwise store `newValue` under `key`, replacing any previous value.
5. Emit `ExtraMetadataUpdated(msg.sender, key, newValue)`.

Keys are case-sensitive and compared byte for byte. Entries cannot be listed on-chain; indexers rebuild the set from `ExtraMetadataUpdated` events.

The protocol assigns no meaning to any key. Issuers SHOULD use lowercase keys, and SHOULD store a 12-character ISIN under `isin`.

2. Revert `LogoURITooLong` / `InvalidLogoURI` if `logoURI` fails TIP-1026 rules. Revert `ContractURITooLong` / `InvalidContractURI` if `contractURI` fails the same rules.
3. Revert `InvalidUIMultiplier` unless `0 < initialUIMultiplier <= MAX_UI_MULTIPLIER`.
4. Revert `AddressReserved` if the derived address is reserved, and `TokenAlreadyExists` if a token exists there.

It then initializes the token as `createToken` does (name, symbol, currency, supply cap `2^128 - 1`, transfer policy bound to the allow-all policy in the TIP-403 registry, `DEFAULT_ADMIN_ROLE` granted to `admin`), and additionally sets `decimals`, `uiMultiplier = newUIMultiplier = initialUIMultiplier`, `effectiveAt = 0`, and the two URIs.

Events, in order: the token's role-grant event; `LogoURIUpdated` if `logoURI` is non-empty; `ContractURIUpdated` if `contractURI` is non-empty; `UIMultiplierUpdated(0, initialUIMultiplier, 0)` from the token; then `AssetTokenCreated` from the factory.

`initialUIMultiplier` lets an issuer bring a token from another chain with its existing multiplier.

## Changes to other components

- **Precompile routing.** Created addresses with the TIP-20A prefix dispatch to the TIP-20A implementation. `is_precompile` includes them.
- **Code-creation guard.** CREATE, CREATE2, and EIP-7702 delegation that would place code at an address with the TIP-20A prefix are rejected, using the rule TIP-1047 defines for the TIP-20 prefix. This TIP applies that rule to the TIP-20A prefix whether or not TIP-1047 is active.
- **Recipient validation.** TIP-20 and TIP-20A transfers, mints, and forced transfers revert `InvalidRecipient` when the recipient has the TIP-20A prefix, as they already do for the TIP-20 prefix. This is the only behavior change for existing TIP-20 tokens.
- **TIP-403 registry.** Calls that accept a token address (`tokenTransferPolicyId`, receive-policy token filters) accept TIP-20A tokens. A TIP-20A token's policy binding lives only in the registry.
- **Account keychain (TIP-1011).** Selector rules that restrict the recipients of `transfer`, `transferWithMemo`, and `approve` currently require a target with the TIP-20 prefix. They accept targets with the TIP-20A prefix as well. Spending limits already apply to any token and need no change.
- **No change needed.** The TIP Fee Manager, stablecoin DEX, TIP-20 channel reserve (TIP-1034), payment classification (TIP-1045), the implicit approval list (TIP-1035), and ZonePortal token enablement validate tokens by the TIP-20 prefix and therefore reject TIP-20A. Implementations that reuse the TIP-20 token code for TIP-20A MUST keep TIP-20 address validation rejecting TIP-20A addresses.

## Extension points (non-normative)

This TIP reserves no hook slot on the token. The intended path for issuer-defined logic is TIP-403:

1. **EVM callouts.** A future TIP adds a TIP-403 policy type whose authorization is answered by a contract. A TIP-20A token adopts it with `changeTransferPolicyId`. `canSend`, `canReceive`, and `canTransfer` reflect it automatically, since they delegate to TIP-403. No TIP-20A storage or ABI change is needed.
2. **Amount-aware checks** (for example, a maximum balance per holder) need a registry call that carries the amount. That is a TIP-403 change, not a token change.
3. **Rebasing display** would be a separate token type with its own factory function, not a mode of existing tokens.

Until then, issuers run their own logic in contracts that act on the token: a compliance contract administers the token's allowlist policy, holds `FREEZE_ROLE` and `FORCED_TRANSFER_ROLE` for freezes and seizures, or holds `UI_MULTIPLIER_ROLE` for corporate actions.

# Tooling

- Contract bindings: add `ITIP20A` and the factory additions to `tempo-contracts` and the SDKs.
- SDK helpers: `isTIP20A`, `getAssetTokenAddress`, and a display helper that formats `balanceOfUI` with `decimals()`.
- Explorers and wallets: show `balanceOfUI` next to `balanceOf` when `supportsInterface(0xa60bf13d)` is true, and show pending multiplier updates from `newUIMultiplier()` and `effectiveAt()`. Read `decimals()` instead of assuming 6.
- `tips/verify`: a reference Solidity implementation and invariant suite for TIP-20A, following the existing TIP-20 tests.

# Threat Model

- **`DEFAULT_ADMIN_ROLE` holder:** fully trusted by holders. Can grant every role, change the transfer policy, and change the contract URI and metadata entries, including identifiers such as the ISIN.
- **`FREEZE_ROLE` holder:** trusted to hold funds only when legally required. Can freeze any amount of any unprotected account, including amounts above its balance and while paused. Cannot move funds.
- **`FORCED_TRANSFER_ROLE` holder:** trusted to move funds only when legally required. Can move any unprotected account's balance to any valid recipient, including while paused. Cannot debit or credit protected system custody addresses, or bypass the recipient's transfer policy or receive policy.
- **`UI_MULTIPLIER_ROLE` holder:** trusted to record corporate actions correctly. A wrong multiplier misleads displays and anything that prices tokens from `uiMultiplier()`, but cannot change any balance.
- **Holders:** untrusted. Cannot move frozen tokens, and cannot avoid a freeze by routing a transfer through a receive-policy redirect.
- **Integrators and DeFi contracts:** must treat `balanceOf` as raw units and apply `uiMultiplier()` only for display or pricing. Contracts holding TIP-20A can be frozen or force-debited like any holder.
- **Zones:** out of scope. ZonePortal addresses are protected, so pooled zone custody on mainnet cannot be frozen or force-debited.

# Invariants

1. The sum of all balances equals `totalSupply()`.
2. `setUIMultiplier`, `cancelUIMultiplierUpdate`, `setFrozenTokens`, `setContractURI`, and `setExtraMetadata` never change any balance or `totalSupply()`.
3. A holder-initiated outflow of `amount` from `a` succeeds only if `amount <= unfrozen(a)` at the time of the call.
4. `frozen(a)` changes only through `setFrozenTokens`, `forcedTransfer`, `burnAt`, and `burnBlocked`. The last three only decrease it, and by exactly the part of the debit that exceeded `unfrozen(a)`.
5. Protected addresses always have `frozen = 0`, and `forcedTransfer` never debits or credits them.
6. `0 < uiMultiplier() <= MAX_UI_MULTIPLIER` at all times.
7. `forcedTransfer` never delivers to `ReceivePolicyGuard`.
8. If `canTransfer(from, to, amount)` is `true`, a `transfer` or `transferFrom` of `amount` does not revert for pause, transfer-policy, or frozen-balance reasons.
9. TIP-20A tokens are rejected by the fee manager, stablecoin DEX, channel reserve, and ZonePortal token enablement, and are never payment-classified. `isTIP20` is `false` for them.
