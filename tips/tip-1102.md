# TIP-1102: Reprice Precompile and Opcode Gas Costs

## Abstract

This TIP updates the gas pricing model for EVM precompiles and opcodes whose
measured execution throughput is below 1 GGas/s on Tempo's benchmark suite. The
change may adjust either the underlying gas cost functions, the fixed gas values
for specific operations, or both, depending on how each cost is represented in
the EVM implementation.

The goal is to make gas accounting better reflect resource usage on Tempo while
preserving deterministic execution and compatibility with the fork activation
rules. The final specification will list each affected precompile and opcode,
its old cost, its new cost, its benchmarked throughput, and the rationale for
the repricing.

## Motivation

Some inherited EVM gas prices may not accurately represent Tempo's execution
environment, implementation costs, or desired block resource limits. If an
operation is underpriced, users can consume disproportionate CPU, memory,
database, or cryptographic verification resources relative to the gas charged.
If an operation is overpriced, useful contracts and protocol workflows may be
discouraged despite being inexpensive for Tempo nodes to execute.

Repricing selected precompiles and opcodes gives Tempo a clearer resource
market. It also creates an explicit place to document benchmark evidence,
compatibility impact, and the activation rules needed for node implementations,
tooling, and contract developers.

## Threat Model

If underpriced precompiles or opcodes are not repriced, an attacker can create a
gas-valid block whose execution cost prevents block builders or validators from
validating it in time, potentially denying service across the network.

# Specification

## Repricing Rule

Any precompile or opcode benchmarked below 1 GGas/s MUST be repriced. For a
benchmark result of `measured_mgas_per_second`, the candidate cost multiplier is:

`candidate_multiplier = 1000 / measured_mgas_per_second`

The final gas value MUST be rounded so the repriced benchmark implies at least
1 GGas/s. Integer gas constants MAY round up directly. Dynamic gas functions MAY
change fixed bases, per-word/per-element slopes, or both, as long as the final
function prices every affected benchmark case above the 1 GGas/s threshold.

# Security Considerations

This TIP only increases gas costs; it does not add functionality, expand the
set of accepted inputs, or weaken validation. Because every change is a
monotonic increase, no operation becomes cheaper or can consume more execution
resources within the block gas limit, so the repricing introduces no additional
protocol-level attack vector and reduces the denial-of-service risk from
underpriced execution.
