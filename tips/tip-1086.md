# TIP-1086: Transaction-Carried Access Key Authorizations

## Abstract

An account can sign an access-key authorization once and attach it to every transaction
that uses the key. Validators verify the authorization and enforce its permissions directly
from the transaction, without registering the key or persisting its immutable policy.
Revocation markers and cumulative or periodic spending counters remain onchain. Existing
stored access keys remain supported and retain their existing behavior.

## Motivation

The current inline authorization path writes a key record, spending-limit configuration,
and call-scope entries on first use. This makes first use expensive when an application
creates many short-lived keys or needs several token, contract, selector, or recipient
restrictions. Reusing a stored key amortizes those writes, but does not address workloads
where each key is used only a few times.

The transaction already carries an issuer-signed description of those permissions. Keeping
that certificate and resubmitting it lets the protocol exchange immutable state growth for
transaction bytes and repeated signature verification. The application remains responsible
for retaining the certificate, as it already must do between signing and initial submission.
Enforcement remains a consensus rule and does not depend on an offchain policy service.

This proposal removes policy storage, not all state. Revocation and budgets shared across
transactions require state. It makes no fixed gas-saving, dollar-cost, or throughput claim:
those depend on policy size, signature type, token usage, and certificate reuse.

The existing behavior is specified by [TIP-0001](./tip-0001.md),
[TIP-1011](./tip-1011.md), [TIP-1049](./tip-1049.md), and
[TIP-1053](./tip-1053.md). The current implementation separates
[authorization pricing and fee collection](https://github.com/tempoxyz/tempo/blob/7331a612fae3f9255a55886060bb862da41faa55/crates/revm/src/handler.rs),
[wire encoding](https://github.com/tempoxyz/tempo/blob/7331a612fae3f9255a55886060bb862da41faa55/crates/primitives/src/transaction/key_authorization.rs), and
[keychain state](https://github.com/tempoxyz/tempo/blob/7331a612fae3f9255a55886060bb862da41faa55/crates/precompiles/src/account_keychain/mod.rs).

## Assumptions

- Activation is a future hardfork, not implied by publication of this draft. Historical
  blocks and stored-mode authorizations retain their fork-specific rules.
- Primitive and configurable parents and delegates are supported. The issuer is a primitive
  root, a direct current owner quorum, or a currently active stored primitive admin key.
  The parent and configurable delegate MUST have empty code. Nested delegation and delegated
  code are unsupported. T12 is the implementation gate, not a scheduling or activation decision.
- The issuer can create an unrestricted grant today and is trusted to choose appropriate
  permissions. A certificate is a reusable authorization, not a transaction signature.
- The account's existing transaction nonce mechanism remains the replay guard for each
  transaction. A certificate does not create a separate nonce domain.
- State-dependent authorization and spending decisions are checked against the actual
  execution state, including earlier transactions in the block. A cached pool result is
  insufficient for inclusion.

## Threat Model

The root and active stored admin keys are trusted account authorities. A compromised
authority can grant additional permissions; this proposal does not protect against that.
An access-key holder, certificate distributor, relayer, or sponsor may submit arbitrary
transactions, reuse certificates, omit them, or combine signatures and policy fields.
Possession of a certificate alone MUST NOT allow spending without the access-key signature.

Validators and builders enforce certificate authenticity, current authority, revocation,
expiry, and limits. Builders can delay or order transactions but cannot waive these rules.
Revocation takes effect at its execution position, not when broadcast. Applications must
account for inclusion races and chain reorganizations.

An application may lose or withhold a certificate, causing a recovery or availability
problem. Certificate contents are public when submitted: the witness MUST be an opaque
commitment, not a secret or personal data. Call scopes retain TIP-1011's boundary: they
constrain top-level calls, not all downstream contract behavior.

# Specification

The words MUST, MUST NOT, SHOULD, and MAY specify normative requirements.

## 1. Modes and wire format

The existing `key_authorization` field of type `0x76` transactions becomes a union:
`Stored(SignedKeyAuthorization)` or `Carried(SignedCarriedAuthorizationV1)`.
Omitting it continues to mean that an access-key transaction must use a registered key.
There is exactly one authorization per transaction; modes cannot be combined.

Stored-mode encoding and signing are unchanged. Carried mode has this exact RLP encoding:

```text
SignedCarriedAuthorizationV1 = RLP([
    "tempo-carried-key-v1",         // literal 20-byte ASCII string
    fields,
    issuer_signature               // direct Primitive or Multisig TempoSignature encoding
])

fields = [
    chain_id: u64,
    account: address,
    key_type: u8,                   // 0 = secp256k1, 1 = P256, 2 = WebAuthn, 3 = Multisig
    key_id: address,
    valid_after: u64,
    expiry: u64,
    witness: bytes32,
    limits: None | [TokenLimit, ...],
    allowed_calls: None | [CallScope, ...],
    authority_config: bytes32       // parent configuration commitment, zero if unconfigured
]

TokenLimit = [token: address, amount: uint256, period: u64]
CallScope = [target: address, selector_rules: [SelectorRule, ...]]
SelectorRule = [selector: bytes4, recipients: [address, ...]]
```

All ten fields and all three fields of every `TokenLimit` are present, including
zero-valued integers. `None` is the empty RLP byte string (`0x80`); an empty list (`0xc0`)
means an explicit empty allowlist. Addresses, selectors, and witnesses are byte strings
of exactly 20, 4, and 32 bytes. Integers use minimal unsigned RLP encoding with no leading
zeroes. Unknown versions, incorrect types or widths, extra fields, trailing bytes, and
non-canonical encodings MUST be rejected. The entire signed wrapper is at most 4,096 bytes.

The decoder distinguishes the literal tag from the legacy signed-authorization shape;
it MUST NOT try stored-mode validation after a carried-mode failure. The tag is not an
additional transaction type. Before activation it is unsupported.

The certificate signing digest and identifier are:

```text
authorization_id = keccak256(RLP(["tempo-carried-key-v1", fields]))
```

Primitive `issuer_signature`s sign this digest using the existing verification rules,
including P256 prehash and WebAuthn challenge handling. A configurable issuer signs
`multisig_digest(authorization_id, account, config_version)` under TIP-1114. The identifier excludes
signature bytes: re-signing the same fields, including with another authorized issuer,
MUST NOT create another budget. The tag domain-separates this signature from a stored
authorization. Changing modes requires a new issuer signature.

The ordinary transaction signing hash, sponsor signing hash, and transaction hash MUST
include the complete encoded wrapper wherever TIP-0001 includes `key_authorization`.
Neither the certificate nor its issuer signature may be replaced without invalidating
the affected transaction signatures. This TIP does not introduce an unsigned sidecar.

## 2. Certificate validity

A carried certificate is valid only if all of the following hold:

1. `chain_id` is nonzero and equals the current chain ID. `account` is nonzero and equals
   the transaction sender and the keychain signature's `user_address`.
2. `key_id` is nonzero and differs from `account`. The transaction uses a keychain signature
   whose recovered primitive key or named configurable delegate and type equal `key_id` and `key_type`.
   Root-signed transactions carrying this mode are invalid.
3. `valid_after < expiry` and `valid_after <= block.timestamp < expiry`. Both times are
   Unix seconds. Expiry is mandatory; there is no non-expiring sentinel in this mode.
4. The issuer signature verifies as the primitive root of `account`, its direct current
   owner quorum, or a currently active stored primitive admin key for that account.
   For an admin issuer, its stored signature
   type MUST match the issuer signature type. A carried key cannot be an issuer or admin.
5. The parent has empty code, and the transaction has no EIP-7702/Tempo delegation
   authorizations. This prevents a transaction from changing its own authority model.
6. The legacy `keys[account][key_id]` record is completely unused: neither registered
   (including expired) nor permanently revoked. A stored key and a carried key MUST NOT
   be active under the same `(account, key_id)`.
7. TIP-1053's `(account, witness)` burn marker is false. The witness is mandatory,
   including a valid all-zero value, and MUST be checked on every use.
8. The policy meets the canonical ordering and structural constraints below.
9. `authority_config` equals the parent's current account-leaf configuration commitment.
   The version-zero bootstrap exception below may establish that commitment on first use.

Admin issuer validity is checked on every use. Revoking an admin issuer invalidates its
outstanding carried certificates immediately in execution order. This differs from
stored grants, which retain their existing lifecycle. A stored primitive admin may issue
a carried certificate used by another key; it need not sign the transaction itself.

### 2.1 Configurable accounts and rotation

Use TIP-1114's bounded native verifier for both independently signed roles: the certificate
issuer and the transaction's delegate. Do not accept a keychain signature as an issuer or
inside a delegate quorum. Each quorum has at most eight primitive approvals; the existing
combined sixteen-approval bound and optional sponsor signature remain applicable. The
4,096-byte certificate bound additionally constrains the issuer quorum: eight maximum-size
WebAuthn approvals do not fit and are invalid, even though each approval fits individually.

For an unregistered configurable parent, a direct version-zero quorum may carry its
canonical configuration with `authority_config == config.commitment()`. Verify derivation
using the configured recovery factory before accepting this exception. On inclusion,
register the account-leaf commitment exactly as TIP-1108 requires, including on user-call
failure. This is account setup, not access-key registration: report its 20,000-gas field
write separately. Primitive root/admin certificates cannot bootstrap a native commitment.

Parent rotation invalidates every certificate bound to the old commitment, including
certificates issued by a stored admin. Re-signing under new owners does not make old fields
valid: issuing another certificate with the new commitment creates a new grant and budget.
Never silently restore the old grant's remaining allowance into the new grant.

Delegate rotation keeps its address and grant identity. Its current owners sign each
transaction under TIP-1111; the parent's certificate and cumulative counters do not change.
An unregistered configurable delegate registers its own commitment under the same existing
rules. A parent and delegate cannot be the same account.

T12 retains its existing primitive-root authority rules. This TIP does not anticipate or
bypass TIP-1112's later root-key disablement. That fork must apply its root restriction to
carried issuers and primitive delegates too.

The existing account-leaf primitive stores one current ownership commitment. It cannot
also represent independently evolving per-token counters without changing the witness
format and concurrency model. This implementation shares ownership verification and
rotation with configurable accounts; counters and witness burns remain in AccountKeychain.

The transaction-level access-key restrictions remain applicable, including the ban on
top-level contract creation. Invalid certificates cause transaction rejection before
nonce consumption, fee collection, or durable counter writes. In a proposed block an
invalid transaction makes the block invalid; it is not a successful empty transaction.

## 3. Immutable policy

Token entries MUST be strictly ascending by token address. Targets, selectors within a
target, and recipients within a selector MUST each be strictly ascending by their fixed
width bytes. Duplicates and unsorted input are invalid. This gives each policy one
encoding without an input-dependent sorting pass.

TIP-1011's structural restrictions apply, including the supported recipient-constrained
TIP-20 selectors, nonzero recipients, and the bound `amount <= 2^128 - 1` for periodic
limits. Carried `period == 0` limits accept the full `uint256` range. A zero cap is valid.
Token entries must use the TIP-20 address class. Policies do not require the token or
target contract to have been deployed at certificate signing time.

The following meanings are unchanged:

| Field | `None` | Empty list | Nonempty list |
| --- | --- | --- | --- |
| `limits` | Unlimited protocol-accounted spending | No spending | Only listed tokens, subject to caps |
| `allowed_calls` | Unrestricted address-targeted calls | No calls | Listed targets and selector rules |
| `selector_rules` | Not permitted | Any selector on this target | Listed selectors |
| `recipients` | Not permitted | Any recipient | Listed first-argument recipients |

Every top-level call is checked against the certificate using TIP-1011 scope semantics,
including canonical recipient ABI decoding. Scope checks happen in a metered phase
before any user call begins. A scope mismatch fails the entire batch as an execution
failure, not as an invalid transaction. Nonce consumption and actual fees survive that
failure. Nested calls, token approvals, DEX debits, and other protocol spending hooks
retain their existing semantics; this TIP does not expand the scope language or turn
spending caps into a general cap on arbitrary ERC-20 movement.

The validated certificate is installed in transaction-local execution context as
`Carried(account, key_id, authorization_id, policy)`. Every keychain spending hook,
including hooks reached through internal calls, MUST dispatch on this mode. It MUST NOT
fall back to an absent stored-key record or combine carried and stored permissions.
The context is discarded after the transaction and follows the execution journal across
call rollback. `getTransactionKey()` continues to return `key_id`.
The context authorizes only its named account. Existing debit-owner attribution remains
in force; a nested call cannot apply this certificate as authority for another account.

## 4. Spending state and periods

Counters are keyed by `(account, authorization_id, token)`, not by transaction hash,
nonce key, witness alone, or issuer signature. Different certificates are separate grants.
Signing another certificate, even for the same key, grants another budget; it does not
replace the previous grant. Wallets MUST display this and revoke a superseded certificate
before describing a reduced policy as effective. Reordering the same policy cannot create
another identifier because ordering is canonical.

Only the following new persistent counter words exist:

```text
spent[account][authorization_id][token]: uint256
window[account][authorization_id][token]: uint64  // periodic limits only
```

Both default to zero. No key record, certificate hash registration, policy configuration,
scope, recipient, expiry, cap, or list length is written on successful authorization.
For an unlimited token policy there are no counter writes. Limited tokens allocate state
only when a positive debit actually occurs; a read or zero debit does not initialize state.

Use these storage slots within the existing AccountKeychain precompile:

```text
spent_slot = keccak256(abi.encode(
    keccak256("tempo.carried-key.spent.v1"), account, authorization_id, token))
window_slot = keccak256(abi.encode(
    keccak256("tempo.carried-key.window.v1"), account, authorization_id, token))
```

`abi.encode` uses four 32-byte words with addresses left-zero-padded. `window` occupies
the low 64 bits of its word; the other bits are zero. These domains are independent of
the existing keychain layout. Non-periodic limits never read or write `window_slot`.

For an attempted debit `d` at timestamp `t`:

1. If limits are absent, proceed without counter accounting. If the token is absent from
   an explicit limits list, any positive debit fails with `SpendingLimitExceeded()`.
2. For `period == 0`, let `used = spent`.
3. For `period > 0`, compute `w = floor((t - valid_after) / period)`. Let `used = spent`
   when the stored `window == w`, and zero otherwise. Periods are anchored to the signed
   `valid_after`, never to first submission or the most recent use.
4. Require `used <= amount` and `d <= amount - used`, using checked arithmetic.
5. For a positive successful debit, write `spent = used + d` and, for periodic limits,
   `window = w` if it differs. Do not write zero to a periodic counter merely to roll it
   over; compute rollover in memory and write the final post-debit value.

The windows are half-open intervals starting at `valid_after + w * period`; no carry-over
is allowed. Intermediate arithmetic for endpoints uses at least 128 bits; eligibility
does not require representing an endpoint beyond `u64::MAX`. The quotient fits `uint64`.
Non-periodic exhaustion is represented by `spent == amount`, including at `uint256::MAX`.
There is no ambiguous zero-remaining sentinel.

For example, a certificate with `valid_after = 100`, `period = 60`, and cap `100`
has windows `[100, 160)`, `[160, 220)`, and so on. Spending `30` at timestamp `125`
leaves `70`; reattaching the certificate at `150` still leaves `70`. At `160`, the
effective allowance is `100`, and a debit of `20` stores window `1` and spent `20`.
If the first ever debit occurs at `225`, it starts in window `2`, not a new window
anchored at `225`. These units are raw token units and exclude fees unless stated.

Execution must serialize conflicting counters, including transactions using different
nonce keys, multiple debits within a batch, and fee and user debits of the same token.
A failed user-call batch rolls back its debits and corresponding spend events. Reorgs
roll counters back with the rest of the state. No counter cleanup is introduced by this
TIP; resetting or deleting a live non-periodic counter would replenish authority.

## 5. Fees and failure boundaries

Resolve and validate the certificate before fee collection. For self-paid transactions,
the existing maximum fee-token reservation MUST fit the certificate's remaining fee-token
budget as well as the account balance. Reserve that amount against the same counter used
by user spending before user execution. On settlement, release only the unused fee
reservation; actual fees remain charged even when user execution fails.

The reservation and refund MUST use the same authorization ID and period index computed
at this transaction's timestamp. A refund cannot increase the remaining budget beyond
its pre-reservation value plus any separately reverted user debits. The final counter
equals prior effective spending plus committed user debits plus actual account-paid fees.
Storage gas for reservation and settlement follows existing fee bookkeeping rules and
must not recursively reserve an unbounded amount of additional fees.

When a distinct sponsor pays, sponsor-paid gas does not consume the sender certificate's
budget. User token debits still do. A fee payer equal to the sender remains self-paid,
regardless of which sponsorship encoding was used. Sponsorship does not relax scopes,
revocation, expiry, or transaction-signature binding.

Insufficient balance or fee-budget reservation makes the transaction invalid before any
committed changes. Scope failure, user revert, or user out-of-gas consumes the nonce and
actual fees under the ordinary transaction rules, while reverting all user-call effects.
No stored-key registration survives a carried transaction, successful or otherwise.

## 6. Revocation, replacement, and stored-key interaction

`burnKeyAuthorizationWitness(witness)` from TIP-1053 is the certificate revocation
interface. It uses the existing admin-only guard and event. A burn invalidates every
carried certificate for the account with that witness, including unused certificates.
Successful carried use MUST NOT burn the witness. Applications SHOULD use a distinct
witness per grant unless group revocation is intended.

Add these methods to the existing AccountKeychain precompile:

```solidity
/// @notice Permanently disables carried use of a key, including before first use.
/// @dev Uses the existing root/stored-admin caller guard. Carried keys are not admins.
/// @dev Writes the existing revoked-key tombstone, preventing future stored registration.
/// @dev Reverts UnauthorizedCaller for unauthorized callers, InvalidKeyId for zero or
///      the caller account itself, and KeyAlreadyExists for any registered key.
/// @dev An already-revoked key is a no-op; no duplicate event is emitted.
/// @param keyId Access-key address to disable permanently for the caller's account.
function revokeCarriedKey(address keyId) external;

/// @notice Returns raw accounting for one carried certificate and token.
/// @dev Does not authenticate a certificate or calculate expiry, rollover, or remaining cap.
/// @dev Missing counters return (0, 0); non-periodic counters return windowIndex == 0.
/// @param account Account that owns the grant.
/// @param authorizationId Canonical certificate digest, excluding the issuer signature.
/// @param token TIP-20 token address.
/// @return spent Recorded debit total in the recorded window, or lifetime non-periodic total.
/// @return windowIndex Recorded periodic window index.
function getCarriedSpending(address account, bytes32 authorizationId, address token)
    external view returns (uint256 spent, uint64 windowIndex);
```

`revokeCarriedKey` stores the same tombstone as existing `revokeKey`: `is_revoked = true`
and all other key-record fields zero. On a new tombstone it emits existing
`KeyRevoked(account, keyId)`. For a registered key, including an expired key, callers
must use existing `revokeKey`; its behavior is unchanged. Revocation markers cannot be
cleared by this TIP. Both methods respect existing caller, static-call, and gas guards.

Legacy key getters and mutations remain storage-only. `getKey` does not report a carried
certificate as registered; `getAllowedCalls` and `getRemainingLimit` cannot infer its
policy from `key_id`. `setAllowedCalls` and `updateSpendingLimit` do not mutate carried
certificates. The raw counter getter requires the certificate to compute an effective
remaining amount and MUST NOT be presented as an authorization-validity check.

Registering a previously unused carried `key_id` in stored mode is permitted by existing
rules, but makes every carried certificate for that key invalid. Stored expiry or later
revocation never re-enables those certificates. Wallets SHOULD use a fresh key when
changing modes: the new stored grant has its own explicitly approved budget. There is
no automatic migration, policy overwrite, or transfer of remaining allowance.

TIP-1020 primitive signature verification and TIP-1049 stored-key verification are
unchanged. This TIP does not make a carried certificate usable as a stored-key signature
in arbitrary contracts, ERC-1271, permits, or other offchain-message verification paths.

## 7. Gas and payment classification

Carried mode MUST NOT invoke the stored-authorization pricing formula or pay synthetic
storage-creation charges for a key, policy, or unused limit. It pays for the full wrapper,
additional signature verification, policy processing, and actual state access.

The proposed v1 intrinsic surcharge, in addition to the ordinary transaction base and
the inner access key's primitive-signature surcharge, is:

```text
B = byte length of SignedCarriedAuthorizationV1
Z = number of zero bytes in that encoding
N = B - Z
E = token entries + target entries + selector entries + recipient entries

carried_intrinsic = 4 * Z + 16 * N
                  + 80 * ceil(B / 32)
                  + 20 * E
                  + issuer_verification
                  + 2,000

issuer_verification:
    secp256k1: 3,000
    P256:     8,000
    WebAuthn: 8,000 + 6 * ceil(webauthn_data_length / 32)
    Multisig: sum(primitive verification costs above for each approval)
              + keccak_cost(configuration_commitment_preimage)
              + keccak_cost(multisig_role_domain_preimage)
```

The byte term covers the complete certificate including signature bytes exactly once;
an implementation MUST NOT also apply the legacy WebAuthn byte surcharge to that issuer
signature. The separate access-key transaction signature retains its primitive pricing.
The stored-mode keychain-validation overhead is replaced by the actual state-read
charges below, not added again.
The word term covers certificate decoding and hashing; `20 * E` covers structural and
ordering checks. The buffer covers transaction-local context setup. These are proposed
consensus constants, subject to the benchmark gate below, not measured savings.

Before checking call scopes, deduct `20 * C * (1 + T + S + R)` execution gas, where `C`
is the number of top-level calls and `T`, `S`, and `R` count targets, selectors, and
recipients in the certificate. This bounds a linear scan regardless of early matches.
It replaces stored-scope lookup charging for this mode only. Insufficient gas fails
execution before user calls begin. All arithmetic is checked for overflow.

The reference implementation installs five context words and two words per token in
transient storage, charged through the ordinary metered provider. It stores no policy in
persistent storage. The execution scope check reads the immutable carried policy directly.
Transaction finalization clears the context; call rollback journals its state normally.

Actual key-record, issuer, and witness reads, transient context installation, counter reads/writes, and logs use the
active fork's ordinary storage and log gas schedule. Initial zero-to-nonzero counter
writes are charged as state creation; subsequent writes receive no certificate-specific
discount. Stateful validation reads are charged once on the execution path, even when
the implementation already performed speculative pool checks. Gas parameters are
independent of cache hits and validator-local optimizations. Existing storage-credit
exclusions for fee bookkeeping continue to apply.

Self-paid limited transactions additionally prepay 10,000 regular gas for bounded fee
settlement: warm counter refund, transaction-key activation, and one final spend event.
Fee reservation meters actual counter creation, including T7's 245,000-gas creditable
creation component. Disabling storage-credit bookkeeping MUST NOT accidentally waive
that creation cost. The fee path neither consumes nor mints storage credits. Normal user
counter writes retain the active fork's storage-credit rules. Report those rules when
comparing transactions; do not count omitted policy writes as stored credits.

Nodes MUST enforce the byte bound and sufficient intrinsic gas before expensive
certificate processing. Pool admission may perform bounded speculative validation;
rate limits remain necessary because invalid signatures cannot pay fees.

[TIP-1045](./tip-1045.md) applies the 1,024-byte key-authorization bound to the complete
carried wrapper. All its other payment predicates remain unchanged. A valid certificate
of 1,025 to 4,096 bytes uses the general lane; one above 4,096 bytes is invalid. A
certificate does not make a non-payment call eligible for payment capacity. Key-management
calls remain general transactions. Fee curves and block gas budgets are unchanged.

## 8. Pool, activation, and compatibility

Pool validation checks structural validity, both signatures, account and chain binding,
current authority, revocation, and fee affordability. It tracks expiry as the minimum
of transaction and certificate expiry. A future `valid_after` follows the existing
not-yet-valid transaction policy; it is never executable early.

At execution, nodes MUST repeat state-dependent checks against the selected parent and
earlier block transactions. Builders revalidate affected entries after key registration,
issuer revocation, witness burns, balance changes, or spending. Competing transactions
are not jointly affordable merely because each passed admission against the same state.
Reorg handling drops state-derived cache entries; caching cryptographic verification is
allowed only under the complete signed bytes and signature rules for the active fork.

All new wire handling, counter access, and ABI selectors are hardfork-gated. Before
activation, the carried variant is invalid and the new selectors are unavailable.
After activation, existing stored-mode encodings and signing hashes remain unchanged.
No state migration or pre-existing permission change is required. Stored authorization
pricing is unchanged; T12 debit/refund dispatch additionally meters its transient carried-mode
check, including when the transaction uses a stored key.

## 9. Alternatives and tradeoffs

Storing compact policy hashes still requires one registration write and a mechanism for
supplying the preimage. Carrying the certificate avoids that registration completely.
Shared policy templates can amortize repeated policies but require template lifecycle
state. Both remain possible future options.

Keeping all limits offchain would remove counters but make cumulative limits dependent
on the signer service. Per-transaction caps alone cannot express a lifetime or periodic
budget. This proposal retains onchain counters for those guarantees.

Repeated issuer verification and certificate bytes make carried mode less attractive for
long-lived, frequently used keys. Stored mode remains useful. Certificate-hash counters
also mean separately signed grants have separate budgets; pooling limits across grants
would require another explicitly signed budget identity and lifecycle specification.

Signed period anchors avoid a first-use timestamp write, but differ from stored keys'
registration-anchored periods. Wallets must disclose that distinction. Counter garbage
collection, account-wide revocation epochs, and nested certificate delegation are separate
extensions, not implicit parts of this version. Multisig issuers are supported as above.

# Tooling

SDKs MUST add an explicit carried authorization builder, canonical sorting,
digest calculation, signature verification, and serialization of the tagged wire form.
Stored mode remains the default. RPC objects retain the existing `keyAuthorization` fields
and add `carried: { validAfter, authorityConfig }` only in carried mode. Missing or null
`carried` means stored mode. Account, expiry and witness are mandatory in carried mode;
`isAdmin` must be false. Quantities use the existing hex convention, fixed bytes use hex
data, and absent optional policies use `null`. Unknown fields within `carried` are rejected.
The response includes the issuer signature and all fields needed to round-trip the wrapper;
`authorizationId` is derived, not another input. Native simulation must preserve the
carried fields when replacing the issuer signature with a simulation-only witness.

Wallets retain the full certificate until expiry or revocation and attach it to every use.
They MUST show account, chain, key, issuer, time interval, scopes, limits, witness, and
the separate-grant consequence before signing. Backup/export includes the certificate,
not the private key. A lost certificate may be recovered from a previously submitted
transaction; if never submitted, the user must issue a new grant and revoke the old
grant by its saved witness or revoke the key. Onchain state alone cannot reconstruct it.

`eth_call`, `eth_estimateGas`, tracing, and SDK simulation MUST understand carried mode,
including first counter creation, period rollover, sponsorship, and scope failures.
Estimation must use the certificate and current counters, not simulate a stored
registration. Existing explicit signature overrides for simulation must remain confined
to simulation and cannot bypass consensus validity.

Credential persistence MUST preserve the carried fields and complete issuer signature.
Gas fillers MUST retain a carried certificate on every use, including if a stored key
with the same ID is observed; silently dropping it could switch to different permissions.
The Rust account-store and filler implementation enforces these rules.

Explorer views distinguish stored and carried keys and display decoded certificate
permissions from transaction data. The SDK computes remaining budgets using the signed
cap, signed period anchor, block timestamp, and `getCarriedSpending` result. It separately
checks current issuer authority, key occupancy/tombstone, and witness burn status.

# Observability

Carried use MUST NOT emit `KeyAuthorized`, `AdminKeyAuthorized`, or a registration witness
event: those would imply persistent registration. Witness burns and key tombstones emit
their existing events as specified above.

Add this AccountKeychain event for each committed positive debit from a limited token:

```solidity
event CarriedAccessKeySpend(
    address indexed account,
    bytes32 indexed authorizationId,
    address indexed token,
    address keyId,
    uint256 amount,
    uint256 remaining,
    uint64 windowIndex
);
```

For non-periodic limits `windowIndex` is zero. User-debit events follow ordinary rollback.
Fee reservation does not emit a spend event; settlement emits one for the actual positive
account-paid fee, including on failed execution. Its `remaining` reflects final settlement
after any user rollback. Events use execution order and do not expose certificate secrets.
This event replaces `AccessKeySpend` for carried mode so indexers cannot mistake the
budget for a stored `(account, keyId)` budget.

Transaction traces SHOULD expose mode, authorization ID, issuer, certificate byte size,
intrinsic surcharge, counter-creation gas, and a structured failure reason. Nodes SHOULD
record aggregate counts for carried/stored use, invalid/expired/revoked certificates,
certificate sizes, signature verification time, and counter creation. Addresses,
witnesses, and authorization IDs MUST NOT become unbounded metric labels.

# Invariants

1. A valid carried transaction proves both current issuer authority and possession of the
   authorized key, with account, chain, mode, policy, and time bounds cryptographically bound.
2. Reusing or re-signing identical certificate fields never replenishes a budget, across
   sequential, parallel, or expiring nonce transactions.
3. In each signed period, committed protocol-accounted debits plus actual self-paid fees
   never exceed the certificate cap; non-periodic caps hold across the certificate lifetime.
4. A witness burn or key tombstone rejects subsequent use in execution order, including
   first use. Successful use never writes a registration or consumes the witness.
5. Stored and carried permissions cannot be combined. A carried key is never an admin.
6. A scope failure executes no user call. User rollback never refunds actual fees or
   restores a consumed nonce, and fee refunds never mint additional spending authority.
7. Gas depends on transaction and chain state, not validator cache state. State creation
   charges correspond to actual writes, not omitted immutable policy storage.

## Required validation and success criteria

Before approval, publish executable positive and negative encoding/signature vectors for
all three primitive key types, stored admin issuers, and configurable parent/delegate roles. Include round-trip RPC fixtures,
domain separation from stored authorizations, signature-independent IDs, optional-policy
distinctions, canonical ordering, width and integer boundaries, and exact byte limits.

The reference and node suites MUST additionally cover:

- First use and repeat use with zero immutable-policy writes; unused token limits remain
  unallocated. Unlimited sponsored use produces no new authorization or counter state.
- Pre-use witness burn, group burn, permanent key tombstone, expired stored occupancy,
  issuer revocation, and stored registration between pool admission and execution.
- Cross-account/chain/type mismatch, expired and future certificates, unsupported accounts,
  top-level creation, delegation lists, and attempts to use a carried key as an admin.
- Repeated one-time spending, exact exhaustion, zero and maximum caps, mixed tokens,
  multiple nonce lanes, competing transactions, first periodic debit long after issuance,
  exact period boundaries, long idle gaps, and timestamps near `u64::MAX`.
- Scope and recipient checks for every batched call; nested protocol debit hooks; failed
  batches; out-of-gas; self-paid and sponsored fees; same-token fee plus user spending;
  reservation/refund correctness; and reorg rollback of counters and revocation.
- The 1,024/1,025-byte lane boundary and 4,096/4,097-byte validity boundary, measuring the
  complete signed wrapper. Stored-mode historical vectors remain byte-for-byte identical.

Before scheduling, benchmark stored registration, stored reuse, carried first spend,
carried reuse, and periodic rollover with identical policies. Cover secp256k1, P256, and
maximum-size WebAuthn, maximum valid policy nesting, one and many calls, self-paid and
sponsored transactions, and cold/warm state. Report execution time, bytes, state words,
execution gas, state gas, and the reuse count at which stored mode becomes cheaper.
If the proposed charges do not cover measured worst-case work under the network's gas
calibration target, revise this draft's constants before approval and activation.

The acceptance criterion is lower immutable authorization state growth while preserving
the invariants above. A deployment requires engineering, security, and tooling review
under [TIP-0000](./tip-0000.md), a chosen activation fork, and published SDK fixtures.
The draft implementation is stacked on the configurable-account activation branch in
[PR #7581](https://github.com/tempoxyz/tempo/pull/7581). Its executable receipt-gas matrix
and reproduction instructions are in [the cost report](../docs/benchmarks/tip-1086.md). These results
do not constitute completed security review, production hardware calibration, an SDK
release, relay deployment, or scheduled activation.
