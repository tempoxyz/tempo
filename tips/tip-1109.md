# TIP-1109: Account Configuration Updates

## Abstract

This TIP adds a precompile for changing a configurable account's owners and threshold. The current owner quorum authorises the update. Each successful update increments the configuration version by exactly one and replaces the account-leaf commitment.

The account keeps its address, balances, nonce rules, and access-key permissions. A transaction can contain several updates, each checked against the configuration left by the previous call. The original quorum authorises the whole batch.

Access keys, callbacks, and fee payers cannot authorise rotation. If a top-level call reverts or halts, every owner update and its event in the batch rolls back. Initial registration from the same transaction remains. The precompile also exposes account derivation and the current commitment.

## Motivation

Owners need to replace lost or compromised keys without moving funds or application permissions. Key rotation must be available when configurable accounts launch.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| [TIP-1114](./tip-1114.md) validates configurations and transaction signatures. | An update could be authorised by an invalid quorum or install an unusable configuration. |
| [TIP-1108](./tip-1108.md) stores the commitment and defines its read/write costs. | Calls could disagree on current authority or charge incorrectly for an update. |

# Specification

## Overview

The **current configuration** is the salt, version, threshold, and weighted owner list matching the account's stored commitment. `updateConfig` replaces the owners and threshold while keeping the salt and account address.

| Operation | Result |
|---|---|
| First use under TIP-1114 | Registers version zero before calls execute. |
| `updateConfig` | Stores the next version and emits the complete configuration. |
| Migration under TIP-1113 | Starts at version one; subsequent updates use the same rules. |
| `getConfigCommitment` | Returns the current hash, or zero if no configuration is registered. |
| `deriveAccount` | Derives the initial address from the salt, threshold, and sorted owners. |

For example, a first transaction registers C0 at version zero, updates it to C1 at version one, then fails in a later call. C1 and its event roll back; C0 remains registered.

This TIP changes owner authority. Access-key grants retain their permissions. Recovery that needs to end a grant uses TIP-1111's revocation flow.

## Update rules

### Who can call `updateConfig`

- The transaction must be signed directly by the owner quorum.
- The call must be a top-level call created by the protocol, with `msg.sender == tx.origin`.
- Access keys, contract callbacks, and fee payers cannot authorize rotation.
- No separate approval signature is accepted. The transaction signature already covers the update calldata.

### Installing the next configuration

1. Check the supplied `current` configuration against the account leaf at call time. The initial hash has already been registered under TIP-1114 before calls execute.
2. Keep the current salt.
3. Increase the version by exactly one. Reject version overflow.
4. Replace the threshold and owner list with the supplied values.
5. Validate the new configuration under TIP-1114.
6. Compute its hash and reject a zero hash.
7. Store the hash and emit `MultisigConfigUpdated` with the complete new configuration.

### Versions and batch execution

The first owner update replaces version zero with version one, including in the first transaction. A migrated account already starts at version one under TIP-1113.

Rotation MUST preserve the account address, balances, nonce rules, and access-key permissions.

- Each update checks the hash left by the previous call. Versions must form a consecutive sequence.
- The original quorum approves the entire batch. Later calls do not authenticate the transaction again.
- If any top-level call reverts or halts, all owner updates and their events in the batch roll back, including earlier successful calls.
- Any initial registration from the same transaction persists.
- Later transactions must use the configuration left by the completed transaction.

## Validation and gas

Check caller authorization first. An unauthorized caller gets `UnauthorizedMultisigCaller`.

Check configuration errors in this order:

| Invalid input | Error |
|---|---|
| Empty owner list | `InvalidMultisigOwner` |
| Too many owners | `TooManyOwners` |
| Threshold outside 1–255 | `InvalidThreshold` |
| Invalid owner address | `InvalidMultisigOwner` |
| Zero owner weight | `InvalidWeight` |
| Duplicate owner | `DuplicateOwner` |
| Owners out of address order | `InvalidOwnerOrder` |
| Total weight above 255 | `InvalidWeight` |
| Threshold cannot be reached with at most eight owners | `InvalidThreshold` |

- A stale configuration, zero hash, or version overflow gets `InvalidConfig`.
- An invalid derived account address gets `InvalidAccount`.

Gas charges are:

- Ordinary precompile, input, and event costs.
- Account reads and writes under TIP-1108.
- Standard Keccak costs for checking the current configuration and hashing the next one.
- Both TIP-1110 derivation hashes when calling `deriveAccount`.
- Account access and normal precompile costs when calling `getConfigCommitment`.

Do not add a configuration storage-slot read or write charge.

## Interfaces

The precompile is available at `0xAACC000000000000000000000000000000000000` from activation. The following types and errors define its public interface:

```solidity
interface INativeMultisig {
    struct MultisigOwner {
        address owner;
        uint8 weight;
    }
    struct MultisigConfig {
        bytes32 salt;
        uint64 version;
        uint8 threshold;
        MultisigOwner[] owners;
    }

    /// Derive the initial account from salt, threshold, and sorted owners.
    /// Reverts for an invalid configuration or reserved derived address.
    function deriveAccount(
        bytes32 salt,
        uint8 threshold,
        MultisigOwner[] calldata owners
    ) external pure returns (address account);

    /// Return account's current commitment.
    /// Zero means no account configuration registered.
    function getConfigCommitment(address account)
        external view returns (bytes32 commitment);

    /// Replace msg.sender's owners and threshold, proving current configuration.
    /// Requires a direct owner-quorum transaction and a top-level batch call.
    /// Reverts for unauthorized callers, stale current state, or invalid new config.
    function updateConfig(
        MultisigConfig calldata current,
        uint8 threshold,
        MultisigOwner[] calldata owners
    ) external;

    event MultisigConfigUpdated(
        address indexed account,
        bytes32 salt,
        uint64 version,
        uint8 threshold,
        MultisigOwner[] owners
    );

    error InvalidAccount();
    error InvalidConfig();
    error InvalidThreshold();
    error InvalidMultisigOwner();
    error InvalidWeight();
    error TooManyOwners();
    error DuplicateOwner();
    error InvalidOwnerOrder();
    error UnauthorizedMultisigCaller();
}
```

# Tooling

- Wallets show the proposed owners and threshold, and retain the full configuration.
- Before approving an owner update, wallets should verify that the proposed owners can produce valid signatures meeting the new approval threshold.
- Recovery tooling must show existing access-key grants, including legacy grants, and support explicit revocation. [Owner rotation preserves these grants](./tip-1111.md#owner-rotation-and-revocation).
- Transaction pools and simulators recheck affected transactions when the commitment changes.

# Observability

`MultisigConfigUpdated` records the complete new configuration so indexers can reconstruct the commitment and current owners.

# Threat Model

The current owner quorum controls rotation. Delegates cannot acquire that authority through their grants.

# Invariants

- Removing and later re-adding an owner never makes their old signatures valid again. The configuration version prevents this replay.
- Each update checks the configuration left by the previous call and increments its version by exactly one.
- Reverting or halting a top-level call rolls back all owner updates and their events in the batch.
- Batch execution failure preserves any initial registration from the same transaction.
- Rotation preserves the account address.
- Rotation preserves access-key permissions.
