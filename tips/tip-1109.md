# TIP-1109: Account Configuration Updates

## Abstract

The current owner quorum can replace an account's owners and threshold while retaining its address. A precompile updates the commitment in the account leaf; it does not keep a separate storage mapping.

## Motivation

A useful configurable account must support key rotation from its first release. Separating this interface from the account type makes the authorization and state transition easier to review.

## Assumptions

[TIP-1114](./tip-1114.md) authorizes the transaction and defines valid configurations. [TIP-1108](./tip-1108.md) defines commitment storage and write costs.

## Threat Model

An access key, contract callback, or fee payer must not rotate owners. A previously valid configuration must not regain authority after subsequent rotations. Only the current quorum is trusted to choose the next configuration.

# Specification

## Interface

The precompile is available at `0xAACC000000000000000000000000000000000000` from T12. The following types and errors define its public interface:

```solidity
interface INativeMultisig {
    struct MultisigOwner { address owner; uint8 weight; }
    struct MultisigConfig {
        bytes32 salt;
        uint64 version;
        uint8 threshold;
        MultisigOwner[] owners;
    }

    /// Derive the initial account from salt, threshold, and sorted owners.
    /// Reverts for an invalid configuration or reserved derived address.
    function deriveAccount(bytes32 salt, uint8 threshold, MultisigOwner[] calldata owners)
        external pure returns (address account);

    /// Return account's current commitment; zero means no persisted update.
    function getConfigCommitment(address account) external view returns (bytes32 commitment);

    /// Replace msg.sender's owners and threshold, proving current configuration.
    /// Requires a direct owner-quorum transaction and a top-level batch call.
    /// Reverts for unauthorized callers, stale current state, or invalid new config.
    function updateConfig(MultisigConfig calldata current, uint8 threshold,
        MultisigOwner[] calldata owners) external;

    event MultisigConfigUpdated(address indexed account, bytes32 salt,
        uint64 version, uint8 threshold, MultisigOwner[] owners);

    error InvalidAccount();
    error InvalidConfig();
    error InvalidThreshold();
    error InvalidMultisigOwner();
    error InvalidWeight();
    error TooManyOwners();
    error DuplicateOwner();
    error InvalidOwnerOrder();
    error UnauthorizedMultisigCaller();
}
```

## Update rules

`updateConfig` requires a protocol-created top-level frame with `msg.sender == tx.origin`, a direct multisig outer signature, and no access-key authority. No separate approval signature is accepted; the transaction signs the complete update calldata.

At call time, validate `current` against the account leaf using TIP-1114's initial/current witness rules. The next configuration preserves its salt, increments its version by one without overflow, and replaces its threshold and owners. Validate it under TIP-1114, require a nonzero commitment, write that commitment, and emit `MultisigConfigUpdated` with the complete new configuration.

Version zero is never written. The first update writes version one. An account migrated by TIP-1113 already starts at version one. The account address, balances, nonce rules, and access-key permissions are unchanged by rotation.

Each call checks the then-current commitment, so multiple updates in one batch must form a consecutive version chain. The outer quorum authorizes that entire batch; later calls do not rerun transaction authentication. Any reverted call rolls back its write and event under ordinary batch execution rules. Later transactions validate against the resulting commitment.

## Validation and gas

Configuration errors are checked in order: empty owner list, too many owners, threshold outside 1–8, invalid owner address, zero weight, duplicate/unsorted owner, weight sum above 255, then unreachable threshold. These map respectively to the interface's owner, count, threshold, weight, duplicate, and ordering errors. Stale witnesses, zero commitments, and version overflow use `InvalidConfig`; invalid derived addresses use `InvalidAccount`. Unauthorized update contexts use `UnauthorizedMultisigCaller` before the update is evaluated.

Charge ordinary precompile/input/event costs, TIP-1108 account access and write costs, and standard Keccak gas for the exact current-proof and next-commitment preimages. `deriveAccount` charges both TIP-1110 derivation hashes; the getter charges account access only in addition to normal precompile costs. Do not charge an additional configuration storage-slot read or write.

# Tooling

Wallets show the next quorum before signing and retain the complete configuration. Pools and simulators revalidate witnesses when commitments change. Removed owners' old signatures stay invalid even if those owners are later re-added, because the version has increased.

# Observability

`MultisigConfigUpdated` identifies the new authority and allows reconstruction of its hash. Indexers must follow canonical receipts and undo orphaned events.

# Invariants

Test initial and repeated rotation, self-as-primitive-owner in a positive version, stale witnesses, version overflow, rejected delegated/indirect calls, batch rollback, unchanged address and access keys, and invalidation of pending transactions after rotation.
