# TIP-1109: Account Configuration Updates

## Abstract

This TIP adds `updateConfig` so the current owner quorum can replace owners and threshold at the same address. Each update increments the configuration version by exactly one. Balances, nonce rules, and access grants survive rotation; recovery revokes unwanted grants separately.

## Motivation

Owners need to replace lost or compromised keys without moving funds or application permissions, starting when configurable accounts launch.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| [TIP-1114](./tip-1114.md) validates configurations and transaction signatures. | An update could be authorised by an invalid quorum or install an unusable configuration. |
| [TIP-1108](./tip-1108.md) stores the commitment and defines its read/write costs. | Calls could disagree on current authority or charge incorrectly for an update. |

# Specification

## Overview

The **current configuration** is the salt, version, threshold, and weighted owner list matching the stored commitment.

1. **Approve:** the current quorum signs the complete transaction, including update calldata.
2. **Check:** verify the current commitment and replacement configuration.
3. **Install:** store the next commitment and emit the complete configuration.

TIP-1114 registers version zero before first-use calls and emits `ConfigurableAccountConfigUpdated` for it; TIP-1113 migration starts at version one. `getConfigCommitment` returns the current hash, or zero if unregistered. `deriveAccount` derives the initial address from salt, threshold, and sorted owners.

For example, a first transaction registers C0 at version zero and updates it to C1 at version one. If a later call fails, C1 and its event roll back; C0 remains registered.

## Update rules

### Who can call `updateConfig`

- Require a direct owner-quorum signature and a protocol-created top-level call with `msg.sender == tx.origin`.
- Access-key authority, contract callbacks, and fee-payer signatures cannot authorize rotation.
- Accept no separate approval signature: the transaction signature covers the update calldata.

### Installing the next configuration

1. Check the supplied `current` configuration against the account leaf at call time.
2. Keep the current salt.
3. Increase the version by exactly one. Reject version overflow.
4. Replace the threshold and owner list with the supplied values.
5. Validate the new configuration under TIP-1114.
6. Compute its hash and reject a zero hash.
7. Store the hash and emit `ConfigurableAccountConfigUpdated` with the complete new configuration.

### Versions and batch execution

Rotation MUST preserve the account address, balances, nonce rules, and access-key permissions.

- Each update checks the hash left by the previous call. Versions must form a consecutive sequence.
- The original quorum approves the entire batch. Later calls do not authenticate the transaction again.

| Outcome | Commitment and event | Next action |
|---|---|---|
| Caller or input rejected | No update or event; a top-level failure rolls back the batch. | Correct the caller or input; for stale state, fetch the current configuration and obtain approval again. |
| Update succeeds and the batch completes | Commitment and update events remain. | Use the resulting configuration for later transactions. |
| Any top-level call reverts or halts | All batch updates and their events roll back; initial registration and its version-zero event persist. | Read the resulting commitment before retrying. |

## Validation and gas

Check caller authorization first. An unauthorized caller gets `UnauthorizedConfigurableAccountCaller`.

Check configuration errors in this order:

| Invalid input | Error |
|---|---|
| Empty owner list | `InvalidConfigurableAccountOwner` |
| Too many owners | `TooManyOwners` |
| Threshold outside 1–255 | `InvalidThreshold` |
| Invalid owner address | `InvalidConfigurableAccountOwner` |
| Zero owner weight | `InvalidWeight` |
| Duplicate owner | `DuplicateOwner` |
| Owners out of address order | `InvalidOwnerOrder` |
| Total weight above 255 | `InvalidWeight` |
| Threshold cannot be reached with at most eight owners | `InvalidThreshold` |

- A stale configuration, zero hash, or version overflow gets `InvalidConfig`.
- An invalid derived account address gets `InvalidAccount`.

Gas charges are:

- Ordinary precompile, input, and event costs.
- Account reads and writes under TIP-1108.
- Standard Keccak costs for checking the current configuration and hashing the next one.
- The TIP-1110 derivation hash when calling `deriveAccount`.
- Account access and normal precompile costs when calling `getConfigCommitment`.

Do not add a configuration storage-slot read or write charge.

## Interfaces

The precompile is available at `0xAACC000000000000000000000000000000000000` from activation.

```solidity
interface IConfigurableAccount {
    struct ConfigurableAccountOwner {
        address owner;
        uint8 weight;
    }
    struct ConfigurableAccountConfig {
        bytes32 salt;
        uint64 version;
        uint8 threshold;
        ConfigurableAccountOwner[] owners;
    }

    /// Derive the initial account from salt, threshold, and sorted owners.
    /// Reverts for an invalid configuration or reserved derived address.
    function deriveAccount(
        bytes32 salt,
        uint8 threshold,
        ConfigurableAccountOwner[] calldata owners
    ) external pure returns (address account);

    /// Return account's current commitment.
    /// Zero means no account configuration registered.
    function getConfigCommitment(address account)
        external view returns (bytes32 commitment);

    /// Replace msg.sender's owners and threshold, proving current configuration.
    /// Requires a direct owner-quorum transaction and a top-level batch call.
    /// Reverts for unauthorized callers, stale current state, or invalid new config.
    function updateConfig(
        ConfigurableAccountConfig calldata current,
        uint8 threshold,
        ConfigurableAccountOwner[] calldata owners
    ) external;

    event ConfigurableAccountConfigUpdated(
        address indexed account,
        bytes32 salt,
        uint64 version,
        uint8 threshold,
        ConfigurableAccountOwner[] owners
    );

    error InvalidAccount();
    error InvalidConfig();
    error InvalidThreshold();
    error InvalidConfigurableAccountOwner();
    error InvalidWeight();
    error TooManyOwners();
    error DuplicateOwner();
    error InvalidOwnerOrder();
    error UnauthorizedConfigurableAccountCaller();
}
```

# Compatibility

- Wallets show the proposed owners and threshold, and retain the full configuration.
- Before approval, wallets should verify that proposed owners can sign to meet the threshold; configuration validation does not prove key possession.
- Recovery tooling must show current status for existing access grants, including legacy grants, and support [explicit revocation](./tip-1111.md#owner-rotation-and-revocation).
- Transaction pools and simulators recheck affected transactions when the commitment changes.

# Observability

Reconstruct the complete configuration from `ConfigurableAccountConfigUpdated` and match its hash against `getConfigCommitment` at the selected state; later updates can supersede an event.

After a failed first-use batch, the version-zero `ConfigurableAccountConfigUpdated` event, the authorization witness and account state show initial registration; update events follow the [rollback rules](#versions-and-batch-execution).

# Threat Model

| Actor | Trust boundary |
| --- | --- |
| Current owners / recovery providers | The quorum can install any valid owners and threshold; threshold-level compromise or collusion can remove other owners and take control. |
| Wallets | Control the configuration shown for approval; signatures bind the actual update. Misrepresentation can install unintended owners or thresholds. |
| Access-key holders / contract callers / fee payers | Only direct quorum authority and a protocol-created top-level call pass the [caller checks](#who-can-call-updateconfig); grants, callbacks, and sponsor signatures cannot authorize rotation. |


# Invariants

- Removing and later re-adding an owner never makes their old signatures valid again. The configuration version prevents this replay.
- Each update checks the configuration left by the previous call and increments its version by exactly one.
- Reverting or halting a top-level call rolls back all owner updates and their events in the batch.
- Batch execution failure preserves any initial registration from the same transaction.
- Rotation preserves the account address.
- Rotation preserves access-key permissions.
