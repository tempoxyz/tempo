# TIP-1109: Account Configuration Updates

## Abstract

This TIP defines a precompile for replacing a configurable account's owners and approval threshold. Current owners whose combined weight meets the approval threshold authorise each update. The update replaces the configuration hash in the account leaf and increments the configuration version while preserving the account address. Signatures for earlier versions become invalid.

## Motivation

Users need to replace signing keys while keeping their account address, funds, and application permissions. This precompile makes key rotation available when configurable accounts launch, with each replacement authorised by the current owners meeting the approval threshold.

## Assumptions

- [TIP-1114](./tip-1114.md) defines valid configurations and checks the transaction's signatures.
- [TIP-1108](./tip-1108.md) defines where the configuration hash is stored and what writes cost.

# Specification

## Interface

The precompile is available at `0xAACC000000000000000000000000000000000000` from T12. The following types and errors define its public interface:

```solidity
interface INativeMultisig {
    struct MultisigOwner {
        address owner;
        uint8 weight;
    }
    struct MultisigConfig {
        bytes32 salt;
        uint64 version;
        uint8 threshold;
        MultisigOwner[] owners;
    }

    /// Derive the initial account from salt, threshold, and sorted owners.
    /// Reverts for an invalid configuration or reserved derived address.
    function deriveAccount(
        bytes32 salt,
        uint8 threshold,
        MultisigOwner[] calldata owners
    ) external pure returns (address account);

    /// Return account's current commitment.
    /// Zero means no account configuration registered.
    function getConfigCommitment(address account)
        external view returns (bytes32 commitment);

    /// Replace msg.sender's owners and threshold, proving current configuration.
    /// Requires a direct owner-quorum transaction and a top-level batch call.
    /// Reverts for unauthorized callers, stale current state, or invalid new config.
    function updateConfig(
        MultisigConfig calldata current,
        uint8 threshold,
        MultisigOwner[] calldata owners
    ) external;

    event MultisigConfigUpdated(
        address indexed account,
        bytes32 salt,
        uint64 version,
        uint8 threshold,
        MultisigOwner[] owners
    );

    error InvalidAccount();
    error InvalidConfig();
    error InvalidThreshold();
    error InvalidMultisigOwner();
    error InvalidWeight();
    error TooManyOwners();
    error DuplicateOwner();
    error InvalidOwnerOrder();
    error UnauthorizedMultisigCaller();
}
```

## Update rules

### Who can call `updateConfig`

- The transaction must be signed directly by the owner quorum.
- The call must be a top-level call created by the protocol, with `msg.sender == tx.origin`.
- Access keys, contract callbacks, and fee payers cannot authorise rotation.
- The transaction signature covers the update calldata and is the sole approval signature.

### Applying an update

1. Check the supplied `current` configuration against the account leaf at call time. The initial hash has already been registered under TIP-1114 before calls execute.
2. Keep the current salt.
3. Increase the version by exactly one. Reject version overflow.
4. Replace the threshold and owner list with the supplied values.
5. Validate the new configuration under TIP-1114.
6. Compute its hash and reject a zero hash.
7. Store the hash and emit `MultisigConfigUpdated` with the complete new configuration.

### Versions and account state

- First use stores version zero before any update call executes.
- The first owner update replaces that hash with version one, including an update in the first transaction.
- A migrated account already starts at version one under TIP-1113.
- An owner removed from the configuration loses its authority as an owner.
- Rotation preserves the account address, balances, nonce rules, and access-key permissions.

### Multiple updates and rollback

- Each update checks the hash left by the previous call. Versions must form a consecutive sequence.
- The original quorum approves the entire batch. Later calls do not authenticate the transaction again.
- A reverted call rolls back its write and event under ordinary batch execution rules.
- If transaction execution reverts, owner updates made during that execution are rolled back. The account retains any initial registration from the same transaction.
- Later transactions must use the configuration left by the completed transaction.

## Validation

Check caller authorisation first. An unauthorised caller gets `UnauthorizedMultisigCaller`.

Check configuration errors in this order:

| Invalid input | Error |
|---|---|
| Empty owner list | `InvalidMultisigOwner` |
| Too many owners | `TooManyOwners` |
| Threshold outside 1–8 | `InvalidThreshold` |
| Invalid owner address | `InvalidMultisigOwner` |
| Zero owner weight | `InvalidWeight` |
| Duplicate owner | `DuplicateOwner` |
| Owners out of address order | `InvalidOwnerOrder` |
| Total weight above 255 | `InvalidWeight` |
| Threshold cannot be reached | `InvalidThreshold` |

- A stale configuration, zero hash, or version overflow gets `InvalidConfig`.
- An invalid derived account address gets `InvalidAccount`.

## Gas accounting

Charge:

- Ordinary precompile, input, and event costs.
- Account reads and writes under TIP-1108.
- Standard Keccak costs for checking the current configuration and hashing the next one.
- Both TIP-1110 derivation hashes when calling `deriveAccount`.
- Account access and normal precompile costs when calling `getConfigCommitment`.

Do not add a configuration storage-slot read or write charge.

# Tooling

- Wallets show the proposed owners and threshold, and retain the full configuration.
- Before approving an owner update, wallets should verify that the proposed owners can produce valid signatures meeting the new approval threshold.
- Recovery tooling must identify and revoke access or admin keys on a lost device; replacing an owner does not revoke those keys.
- Transaction pools and simulators recheck affected transactions when the commitment changes.

# Observability

- `MultisigConfigUpdated` records the complete new configuration so indexers can reconstruct the commitment and current owners.

# Threat Model

Current owners meeting the approval threshold control rotation. Delegates, including admin access keys, cannot acquire that authority through their grants.

# Invariants

- Each owner update increments the configuration version by exactly one.
- Signatures for earlier versions remain invalid, including after a removed owner is re-added.
- Each update checks the configuration hash at call time, including changes from earlier calls in the batch.
- A reverted update rolls back its configuration write and event under ordinary batch execution rules.
- Reverting an owner update preserves any initial registration from the same transaction.
- Rotation preserves the account address.
- Rotation preserves existing access-key permissions.
