# TIP-1107: Configurable Accounts (Meta)

## Abstract

Configurable accounts keep the same address when the keys controlling them change.

- A person can replace their signing key without moving their funds.
- A team can change its owners or the approvals needed to spend funds.

This Meta TIP brings together the proposals for this account model.

- **T12** adds the new account type and the ability to change its owners.
- **T13** adds access keys, root-key disablement, and migration of existing accounts.

Each component remains Draft until it completes the TIP review process.

## Motivation

The first version adds the new configurable account type. It enables key rotation with a static address.

- A 1-of-1 account has one owner and needs one signature.
- A multisig account can have several owners and require several approvals.

The next version adds access keys, disabling EOA root keys, and migrating in place.

- Existing accounts can become configurable without changing their address.
- Treasuries can give employees or smaller multisigs limited access to funds.

## Assumptions

- The four T12 components activate together.
- The T13 components build on them and activate together.

## Threat Model

- CREATE2 address derivation assumes that nobody knows the EOA private key for the derived address.
- In T13, an account with a stored configuration hash rejects normal transactions signed by its EOA root key. The chain enforces this even if someone obtains that key.
- Root-key disablement is a step toward post-quantum protection. Full protection also requires a suitable signing algorithm.
- Recovery on other chains trusts the initial owners. Enough of those owners must still have their keys to approve recovery.
- Replacing owners on Tempo does not replace the recovery owners on other chains. Losing the initial signing quorum can make recovery impossible.

## User experience

**T12: create an account and rotate its keys**

- Alice creates a 1-of-1 account and receives funds.
- She replaces her signing key and keeps the same account address.
- A team can do the same with weighted owners. Each owner contributes a chosen amount toward the required approval threshold.
- The account can pay its own transaction fees. There is no need to fund a separate account to submit its transactions.
- Access keys and migration of existing EOAs are not enabled yet.

**T13: delegate access and migrate existing accounts**

- A treasury gives an employee or another multisig limited spending access.
- An existing EOA becomes configurable at its current address.
- After migration, its old root key cannot authorize ordinary transactions directly.
- Existing access keys keep their current restrictions.

## Decisions to retain

- Store one configuration hash in the account leaf. Transactions carry the full owner configuration so the chain can check it against that hash.
- Keep weighted owners. Do not allow another multisig to sign as an owner.
- TIP-1114 proposes a maximum threshold of eight and at most eight owner signatures. These are separate from the limit on how many owners an account can have.
- TIP-1111 allows a T13 transaction to both grant access and use it. That can require two quorums, with at most sixteen owner-signature checks in total.
- Keep address derivation and recovery in one TIP. Changing the recovery contracts can change the derived account addresses.
- TIP-1110 retains the existing recovery design while its simplification is reviewed.
- Include owner rotation in T12. The first release should already let users replace their keys.

## Future work

The following features are not scheduled here:

- Multisigs signing as owners of other multisigs.
- Recovery after a period of inactivity.
- Timelocks.
- Programmable policies.
- Moving access-key configuration into the account hash.

T13 keeps access-key data in AccountKeychain. Spending counters change as keys are used, so they still need to be tracked in authenticated onchain state.

# Tooling

- Wallets must distinguish T12 account creation from T13 migration and delegation.
- Users who need access keys should not migrate before the T13 features are available.
- Wallets should show cross-chain recovery eligibility separately from who currently controls the account on Tempo.

# Observability

This Meta TIP adds no events.

- The configuration and migration TIPs define events for changes to account ownership.
- Existing keychain events describe access-key grants and revocations.

# Invariants

- Owner changes preserve the account address.
- Only the current account authority can change its configuration.
- Delegated access never permits owner rotation.
- Signature verification stays within the limits for each supported transaction type.

Release tests must cover:

- Key rotation for a 1-of-1 account.
- Weighted multisig approvals.
- Cross-chain recovery eligibility.
- Delegated access with spending limits.
- Migration that preserves the address and existing permissions.
