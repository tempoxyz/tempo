# TIP-1107: Configurable Accounts (Meta)

## Abstract

Configurable accounts separate an account's address from the keys that control it. A person can rotate a key without changing address; a team can change its members or quorum without moving its assets.

This Meta TIP groups the design into independently readable proposals. T11 introduces the account type and configuration together. T12 adds access keys, root-key disablement, and migration of existing accounts. These are the proposed release assignments; each component remains Draft until it completes the TIP review process.

## Motivation

The first release should solve stable-address key rotation, including a 1-of-1 account, and ordinary multisig ownership. It should make the hard-to-change decisions about address derivation and account storage now, while leaving additional delegation and migration features for the next release.

## Assumptions

The four T11 components activate together. The T12 components build on them and activate together so migration retains access-key functionality. This document coordinates scope; each linked component owns its normative rules.

## Threat Model

An account trusts its current owner quorum, not any individual owner. Delegates have only their assigned permissions. Untrusted transactions must not cause unbounded unpaid verification. Cross-chain recovery uses the initial owners, not the current Tempo owners.

## User experience

**T11:** Alice creates a 1-of-1 account, receives funds, and replaces her signing key while keeping the same address. A team does the same with weighted owners. Transactions come from the account and can pay their own fees; no funded executor is required. Access keys on these accounts and migration of existing EOAs are not enabled yet.

**T12:** A treasury delegates limited spending to an employee or another multisig. An existing EOA can install a configuration at its current address and permanently retire bare root-key authority. Existing access keys survive migration under their existing restrictions.

## Decisions to retain

- Store a single configuration hash in the account leaf; carry the complete owner configuration with signatures.
- Keep weighted owners, but no multisig-as-owner nesting. TIP-1114 proposes both a threshold cap of eight and an eight-signature cap; the owner-list limit is separate. TIP-1111 separately bounds a T12 grant-and-use transaction at two quorums and sixteen owner verifications.
- Keep address derivation and recovery in one TIP because the recovery artifacts determine the address. TIP-1110 retains the existing recovery baseline pending the design review; changing it changes derived addresses.
- Keep configuration updates in T11. Do not ship a static multisig first and rotation in a later fork.
- Do not equate key rotation with post-quantum security. Root-key disablement and suitable signing algorithms are separate requirements.

## Future work

Nested owners, inactivity recovery, timelocks, and programmable policies are not scheduled by this Meta TIP. Moving access-key configuration into the commitment is also deferred: mutable spending counters still need authenticated state. T12 uses the existing AccountKeychain storage model.

# Tooling

Wallets must distinguish T11 account creation from T12 migration and delegation. Do not migrate users who require access keys before the T12 components are available. Display recovery eligibility separately from current Tempo ownership.

# Observability

No new events. Component TIPs define configuration and migration events; existing keychain events describe delegation.

# Invariants

Addresses survive owner changes. Only current authority can change configuration. Delegation never grants owner-rotation authority. Verification stays bounded across all signature roles. Release tests must cover 1-of-1 rotation, weighted quorum, cross-chain recovery eligibility, limited delegation, and migration without loss of address or existing permissions.
