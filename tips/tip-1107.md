# TIP-1107: Configurable Accounts (Meta)

## Abstract

This TIP combines weighted ownership, rotation, recovery and delegated spending at one address. Owners and approval thresholds can change without moving the account.

**The central attack class is treating a recovered or claimed address as proof of current account authority.**

## Motivation

Users and treasuries need key rotation, recovery and multisig control without moving funds or changing deposit addresses and application permissions. Separately granted access keys let devices or employees spend within their permissions without collecting owner approvals for every payment.

## Assumptions

- The Phase 1 components below activate together at T14. Migration depends on root-key disablement.

# Specification

## Account model

The design separates three things:

1. **Account identity:** the address, derived from the initial configuration or retained through EOA migration.
2. **Current ownership:** weighted owners, threshold, salt and version. The account leaf stores their configuration hash; each owner witness supplies the full configuration and approvals.
3. **Delegated permission:** AccountKeychain grants with their own limits, scopes, expiry and counters. Changing owners does not revoke these grants.

## Operations

**Create and register.** A wallet [derives the address](./tip-1110.md#address-derivation) from the initial configuration; it can receive funds before registration. The first valid included transaction the account authorises [registers its commitment](./tip-1114.md#onboarding), even if execution fails. Later witnesses must match the stored commitment.

**Transact.** Owners use secp256k1, P256 or WebAuthn signatures. A [current quorum](./tip-1114.md#authorization) approves the whole transaction, including every call in a batch. The configurable address is the transaction sender and the caller seen by directly called contracts. Applications can use [stateful message verification](./tip-1114.md#on-chain-signature-verification).

**Rotate or recover.** The current quorum calls [updateConfig](./tip-1109.md) to replace owners or the threshold. The version increases, invalidating old-version approvals. For example, Alice's passkey has weight 2 and two recovery providers each have weight 1, with threshold 2. Either Alice or both providers can spend and replace owners; the providers' offchain identity checks are not protocol restrictions.

**Migrate an existing account.** Its live primitive root calls [upgradeAccount](./tip-1113.md) to install a configuration at the same address. [TIP-1112](./tip-1112.md) then rejects independent protocol root authority, subject to its funded-channel exception.

**Delegate spending.** A configurable account can grant access or act as another account's delegate under [TIP-1111](./tip-1111.md). Only the parent's direct authority manages grants; delegates cannot replace its owners.

## Scope boundaries

- Configurable accounts cannot have deployed EVM code or EIP-7702 delegation.
- Accounts have up to 48 owners. The threshold is 1–255 and must be reachable with at most eight owner signatures.
- One threshold governs direct owner-authorised spending and ownership changes. Recovery providers have no recovery-only permission.
- Nested multisig owners and access-key owner approvals are excluded. Configurable delegates use TIP-1111's separate, bounded validation path.
- Timelocks and arbitrary programmable authorisation policies are outside this component set.

# Compatibility

These are proposed Phase 1 rules; individual application and SDK support needs verification.

| Integration | What changes |
|---|---|
| Wallets and SDKs | Retain the full configuration, collect owner approvals independently for its version, and recheck current state before submission. [Witness construction](./tip-1114.md#compatibility). |
| Fee sponsorship | Self-payment and sponsorship work; a separate sponsor must use a live secp256k1 root. [Sender and fees](./tip-1114.md#sender-and-fees). |
| Token approvals: TIP-20 permit and Permit2 | TIP-20 rejects retired-root permits; Permit2 can still spend standing allowances with the old key. Apps supporting direct approvals can use quorum-authorised `approve`. [Approval flows](./tip-1112.md#token-approvals). |
| Message signing and sign-in: ERC-1271 | Configurable accounts have no contract code for ERC-1271; apps must add Tempo's stateful verifier to accept current-quorum signatures. [Message verification](./tip-1114.md#on-chain-signature-verification). |
| Wallets and contracts reading access-key records | Configurable grants use key type 3; migrated delegates can retain primitive grant types while requiring current-quorum signatures. [Grant compatibility](./tip-1111.md#migration-compatibility). |
| Contracts verifying access-key signatures | Native transactions support configurable delegates; the onchain `verifyKeychain` helpers still accept only primitive inner signatures. [Helper limits](./tip-1114.md#on-chain-signature-verification). |
| Payment channels | Primitive voucher signers survive owner rotation. Retiring one blocks new channels and further deposits, but preserves claims against existing deposits to the fixed payee. [Channel rules](./tip-1112.md#protocol-precompiles). |
| Zones | Zones reject configurable signatures and ownership changes; a migrated EOA's old root still controls its Zone address. Wallets must block configurable accounts' Zone deposits. [Zone restrictions](./tip-1114.md#zones). |
| Other chains | Tempo owner changes do not affect foreign authority. Derived addresses have no recovery path in this design; migrated EOAs retain their original key there. [Cross-chain recovery](./tip-1110.md#cross-chain-recovery). |
| Nodes, indexers and account-proof libraries | Account decoding gains an optional commitment field that must survive storage, proofs and historical-state restoration. [Account encoding](./tip-1108.md#compatibility). |

# Observability

Check the commitment at the selected state; an old event does not prove current ownership. [TIP-1108](./tip-1108.md#observability) defines registration evidence and the `AccountUpgraded` and `ConfigurableAccountConfigUpdated` events; [TIP-1111](./tip-1111.md#observability) defines grant evidence.

# Threat Model

Phase 1 assumes correct consensus, secure signatures and hashes, and no known primitive private key for an unregistered derived address.

| Actor | Capability and trust boundary |
|---|---|
| Owners / recovery providers | A [current quorum](./tip-1114.md#authorization) can spend, replace owners and manage grants. The protocol cannot distinguish legitimate approval from quorum compromise or provider collusion. |
| Original root before migration | Can spend, create grants or install different owners until [migration succeeds](./tip-1113.md#installing-the-configuration). A compromised root can win the ordering race; submission does not revoke it. |
| Retired-root holder | Can still produce valid primitive signatures. [Native checks](./tip-1112.md#authority-check) reject independent root authority, except funded-channel settlement to the fixed payee. Applications, Zones and other chains enforce [their own rules](#compatibility). |
| Application / authentication verifier | Must verify the [current quorum](./tip-1114.md#on-chain-signature-verification) or reject retired bare roots before authorising an action. Accepting `ecrecover` or a claimed address alone can bypass the configured owners. |
| Wallet / key generator | Chooses configurations, presents calls and may handle recovery keys. The protocol checks signed bytes, not display accuracy, custody or replacement-key possession. A compromised wallet can solicit harmful approvals. |
| Delegates / their future owners | Can spend within the [grant's expiry, scopes and supported spending limits](./tip-1111.md). Delegate rotation transfers use of that grant; parent rotation leaves a compromised delegate authorised. |
| Protocol clients / precompiles | Must check every [signing role](./tip-1112.md#authority-check) and [preserve the commitment](./tip-1108.md) through execution, cleanup and restoration. A missed check admits a retired root; losing the field can restore its authority. |
| RPC / proof providers | Can withhold configurations or return stale state. A checked proof binds data to a chosen root, not the latest canonical state. Wallets must select the state and obtain its matching configuration. |
| Signature collectors / relayers / fee payers | Can withhold approvals, delay submission or decline sponsorship. Changing the signed operation, account or version requires fresh approvals; submission and fee payment grant no owner authority. |
| Public submitters | Can send invalid witnesses without paying fees. Owner/signature limits and rejection of recursion bound work per attempt, but do not prevent repeated invalid submissions. |

Losing enough owner keys or the full configuration can prevent authorisation.

# Invariants

- Ownership changes preserve the account address.
- Owner rotation preserves ordinary access-key grants, permissions and spending counters.
- Owner approvals match the configuration and version at the transaction's position in the block.
- Access keys cannot manage the parent's keys or change its owners.
- Successful migration retires independent protocol root authority, except funded-channel settlement under TIP-1112.
- Every configurable signer of an included transaction retains a nonzero commitment, even if execution fails.
- Owner updates follow execution rollback without undoing initial registration.
- Tempo ownership changes do not change authority on other chains or Zones, or make applications enforce retirement automatically.
