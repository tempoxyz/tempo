# TIP-1107: Configurable Accounts

## Abstract

This TIP adds configurable accounts. A configurable account has a fixed address, up to 48 weighted owners, and an approval threshold that at most eight owner signatures can reach.

The protocol stores a hash of the current owners and threshold on the account and checks every transaction against it. The current owners can therefore replace or update themselves without moving funds or changing the address.


## Motivation

Today a Tempo account is controlled by one key. Access keys can spend for it, but only that key can manage them. If that key is lost, the account can't be recovered. If it leaks, the owner has to move everything to a new address before an attacker does. Then they have to give payers the new address and re-approve every application. They also have to re-grant every access key and ask issuers to move any roles held at the old address.

Shared control has the same problem, plus another. A company that wants two of three executives to approve payments can use a contract wallet such as Safe. A contract can't send transactions, so a separate key has to submit and pay for each one. Tempo features tied to the transaction sender, such as its fee-token preference, then apply to that submitter, not the treasury.

Configurable accounts move ownership into the protocol. The account itself is the transaction sender, and its owners can change while balances, approvals, roles and access keys stay at the same address.

Alternatives considered:

- **Contract wallets.** They provide shared control, but they need a separate submitter and pay contract-execution costs on every transaction.
- **EIP-7702 delegation.** It gives an existing account wallet code. The original key can still change or remove the delegation at any time, so a leaked key can't be retired.
- **CREATE2-style addresses with recovery contracts on other chains.** These would let a new account recover funds sent to it on another chain. They need factory and wallet contracts deployed and maintained on every destination chain. This TIP uses a plain hash instead, and [TIP-1113](./tip-1113.md#cross-chain-recovery) describes how to create an account that can recover cross-chain funds.

This TIP is the entry point for the feature:

- [TIP-1113](./tip-1113.md) lets existing accounts become configurable at their current address and retires their original key.
- [TIP-1111](./tip-1111.md) lets configurable accounts give and receive access keys.

The three activate together at T14.

## Assumptions

| Assumption | Consequence if violated |
|---|---|
| Owners use Tempo's existing secp256k1, P256 or WebAuthn signature schemes. | A new scheme would need its own encoding, verification and cost rules. |
| Nobody holds a private key whose address equals a new account's derived address. Whoever sets up the account could search for one, at about 2^80 work. | That key could act as the account until its first transaction. Applications that only check `ecrecover` would accept it even afterwards. |
| Execution clients treat the stored owner hash as part of each account's record, in state roots, proofs, snapshots and reorgs. | Clients would disagree on state roots, or a lost hash could let the account be claimed again. |
| TIP-1113 and TIP-1111 activate in the same fork. | A migrated account's original key could bypass its owners. |

# Specification

## Overview

**Terms.** These terms have the same meaning in all three TIPs.

| Term | Meaning |
|---|---|
| Owner | A key that can approve for the account, identified by its address, with a weight from 1 to 255. |
| Configuration | The account's salt, version, threshold and owner list. |
| Approval | One owner's signature over a transaction or message for the account. |
| Quorum | A set of approvals whose owners' weights add up to at least the threshold. |
| Configurable-account signature | The signature format for these accounts, type byte `0x05`. It carries the account, the full configuration and the quorum's approvals. |
| Commitment | The 32-byte hash of the current configuration, stored on the account. Zero means the account is not registered. |
| Registration | The first write of the commitment, made during the account's first included transaction. |
| Owner update | Replacing the owners or threshold. It writes a new commitment and increases the version by one. |
| Derived address | A new account's address, computed by hashing its first configuration. |
| Original key | The private key that controlled an existing account before it became configurable under TIP-1113. |

**Who authorises what.** The current quorum authorises everything: transactions, owner updates, and access-key grants under TIP-1111. One threshold governs all of them. There is no separate recovery role and no timelock. This is the central trust boundary: owners who together reach the threshold control the account completely.

**Lifecycle.** This example is illustrative; the rules are under Mechanics.

Alice's wallet sets up three owners and a threshold of 2:

| Owner | Weight |
|---|---|
| Alice's passkey | 2 |
| Her wallet provider | 1 |
| An independent recovery provider | 1 |

Alice can approve anything alone. Neither provider can act alone. Together, the providers can replace her passkey, and they can also spend her funds.

1. **Create.** The wallet hashes the configuration to get Alice's address. No transaction is needed. Alice can share the address and receive funds. Her account has no commitment yet.
2. **First transaction.** Alice pays a merchant. Her wallet sends a configurable-account signature containing the configuration and her passkey's signature. The protocol checks that the configuration hashes to her address and that her weight meets the threshold. It then writes the commitment (registration) and runs the payment. If the payment had reverted, the registration would still stand. An account that has acted never goes back to unregistered.
3. **Later transactions.** The protocol checks the configuration in each signature against the stored commitment.
4. **Recovery.** Alice loses her phone and makes a new passkey. Both providers sign a transaction calling `updateConfig` to replace the old passkey. Their combined weight, 2, meets the threshold. The version goes from 0 to 1, so nothing signed for version 0 works any more, including signatures from the lost passkey. Her address, balances and approvals don't change.

**Scope.** This TIP defines the configuration, the address, the signature and how it is checked, and registration. It also defines where the commitment is stored, owner updates, verification from contracts, gas, and where the signature is accepted. TIP-1113 covers existing accounts and their original key. TIP-1111 covers access keys.

## Mechanics

### Configuration

A configuration has four fields, encoded in this order: `salt` (32 bytes), `version` (uint64), `threshold` (uint8) and `owners`, a list of (address, weight) pairs.

A configuration MUST satisfy all of these rules:

- It has 1 to 48 owners.
- Owner addresses are nonzero, unique and in ascending order.
- Each weight is at least 1, and all weights together add up to at most 255.
- The threshold is 1 to 255.
- The eight largest weights, or all of them if there are fewer than eight owners, add up to at least the threshold. So no quorum ever needs more than eight signatures.

Version 0 is the configuration the address is derived from. Each owner update increases the version by exactly one. A version-0 configuration MUST NOT list its own derived address as an owner.

### Address derivation

A new account's address is the last 20 bytes of a hash of its version-0 configuration:

```text
account = last20(keccak256(
  "tempo:configurable-account:account" || salt || uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
))
```

The domain string is raw ASCII. The salt is 32 bytes, each address 20 bytes, each `uint8` one byte, and owners are in sorted order. There is no version field, no chain ID, and no ABI or RLP encoding.

Binding the address to the version-0 configuration means only those owners can register it. Derivation needs no deployed contract.

A derived address MUST be rejected if it is zero, a virtual address, an active precompile, a TIP-20 token or a ZonePortal contract.

The address never changes afterwards. It exists only on Tempo, so funds sent to it on another chain cannot be recovered.

### Signature format

A configurable-account signature is `0x05` followed by an RLP list:

```text
signature = 0x05 || rlp([account, config, approvals])
config    = [salt, version, threshold, owners]
owner     = [address, weight]
```

`approvals` holds 1 to 8 ordinary Tempo signatures: secp256k1, P256 or WebAuthn. Each is at most 2,049 bytes. Each owner signs:

```text
configurable_account_digest(inner_digest, account, version) =
  keccak256("tempo:configurable-account:signature" || inner_digest || account || uint64(version))
```

For a direct transaction, `inner_digest` is the transaction's existing signing hash. TIP-1111 defines `inner_digest` for access-key use. Integers are fixed-width and big-endian. Including the account and version means an approval can't be replayed on another account, or on the same account after an owner update.

Decoding rules:

- RLP MUST be canonical, with no trailing fields.
- A 65-byte approval is decoded as secp256k1, whatever its first byte.
- An approval MUST NOT itself be a configurable-account signature or an access-key signature.
- Before T14, signature type `0x05` MUST be rejected in every context.

### Authorization

The protocol checks every configurable-account signature in a transaction separately, in two steps. A transaction can carry up to two: its own signature, and a grant signature under TIP-1111.

**1. The quorum.** This step needs no state. Nodes MAY run it during sender recovery and cache the result, as they already do for access-key signatures:

1. Recover each approval's signer from the digest.
2. Require the signers in strictly ascending address order, and require each to be an owner in the signature's configuration.
3. Add up their weights. The last approval MUST bring the total to the threshold. Reject a total below the threshold, and reject any approval after it is reached.

**2. The configuration.** This step reads the account at the transaction's position in the block:

1. Reject the account if it has code or an EIP-7702 delegation.
2. If the commitment is zero, require version 0, require the configuration's derived address to equal `account`, and require its commitment hash (see Commitment storage) to be nonzero.
3. If the commitment is nonzero, require the configuration's hash to equal it exactly.

Until step 2 passes, the account named in the signature is only a claim. Software outside consensus that authenticates users, such as an RPC login, MUST run step 2 too.

### Registration

Registration runs after validation and fee collection succeed, and before any call runs. It covers every configurable account that signed the transaction and still has a zero commitment. That includes accounts granting or using access keys under TIP-1111.

The write happens outside the transaction's rollback checkpoint. Calls see it from their first step:

| Outcome | Registration | Call changes |
|---|---|---|
| Transaction invalid | Not written | Not run |
| Included, calls succeed | Kept | Kept |
| Included, calls revert or halt | Kept | Rolled back, including owner updates and their events |

Rolling back an owner update MUST preserve registration from the same transaction. The commitment returns to the version-0 hash, never to zero.

Receiving funds, computing an address and read-only verification do not register an account. An existing balance, storage or nonce does not prevent registration. RPC simulation registers only in its temporary state.

### Commitment storage

The commitment is:

```text
commitment = keccak256(
  "tempo:configurable-account:config" || salt || uint64(version) ||
  uint8(threshold) || uint8(owner_count) ||
  owner[0].address || uint8(owner[0].weight) || ...
)
```

It is encoded like the address, plus the 8-byte version. A stored commitment MUST be nonzero.

The commitment is stored in the account leaf. The leaf is the per-account record in Tempo's state, so the commitment is available whenever the account is loaded:

```text
not registered: rlp([nonce, balance, storageRoot, codeHash])
registered:     rlp([nonce, balance, storageRoot, codeHash, 0x00 || commitment])
```

The fifth field is exactly 33 bytes: a layout tag `0x00`, then the hash. Unregistered accounts keep the existing four-field encoding byte for byte, and a zero fifth field MUST NOT be appended. Activation migrates nothing. Decoders MUST reject any other tag, malformed fields and extra fields. They MUST reject the five-field form before T14.

Only registration, owner updates and migration (TIP-1113) may write the commitment. Ordinary storage writes, contract creation, delegation and account clearing MUST NOT change or clear it.

A registered account MUST NOT be deleted as empty, even if its other fields would allow it. EVM execution treats it as existing:

- With no code, `EXTCODEHASH` returns `keccak256("")`.
- `CALL` or `SELFDESTRUCT` naming it as recipient charges no new-account cost.

State roots, account proofs, execution witnesses and snapshots MUST preserve the commitment. Historical replay, rollback and reorgs MUST restore its value for the selected state.

JSON-RPC request parameters and existing response fields don't change. Responses use the request's selected state, including historical reads, and the encoding active at that block. A nonzero commitment makes an account present even if its balance, nonce and code are empty.

- `eth_getAccount` and `eth_getAccountInfo` return an optional `extension` field: `0x00 || commitment` as 33 bytes of `DATA`, omitted when the commitment is zero.
- `debug_accountAt` and `debug_accountInfoAt` follow the same rule where they are exposed.
- `eth_getProof` and `eth_getMultiProof` include the fifth field in their leaf proof nodes. Their summary fields don't change.

### Owner updates

`updateConfig(current, threshold, owners)` on the configurable-account precompile replaces the caller's owners and threshold.

The transaction MUST be signed directly by the current quorum. The call MUST be one of the transaction's own top-level calls, not a call made by a contract, with `msg.sender == tx.origin`. Access keys, contract callbacks and fee-payer signatures cannot authorise an update. No separate approval is needed, because the quorum's signature already covers the calldata.

The precompile:

1. Checks `current` against the commitment at call time.
2. Keeps the salt and sets the version to `current.version + 1`, rejecting overflow.
3. Validates the new configuration, computes its hash and rejects zero.
4. Stores the hash and emits `ConfigurableAccountConfigUpdated`.

A batch may contain several updates. Each one checks the configuration left by the one before, so versions stay consecutive, and the original quorum's signature covers the whole batch. If any top-level call in the batch reverts or halts, every update and its event roll back. Registration from the same transaction stays.

Rotation MUST preserve the address, balances, nonce state and access-key grants. Revoking grants is a separate step under TIP-1111.

Errors:

- An unauthorised caller gets `UnauthorizedConfigurableAccountCaller`, before anything else is checked.
- A stale `current`, a zero hash or a version overflow gets `InvalidConfig`.
- An invalid derived address gets `InvalidAccount`.
- An invalid new configuration fails on the first rule it breaks, in this order:

| Invalid input | Error |
|---|---|
| Empty owner list | `InvalidConfigurableAccountOwner` |
| More than 48 owners | `TooManyOwners` |
| Threshold outside 1–255 | `InvalidThreshold` |
| Zero owner address | `InvalidConfigurableAccountOwner` |
| Zero weight | `InvalidWeight` |
| Duplicate owner | `DuplicateOwner` |
| Owners out of order | `InvalidOwnerOrder` |
| Weights add up to more than 255 | `InvalidWeight` |
| Threshold not reachable with eight owners | `InvalidThreshold` |

### Verification from contracts

Configurable accounts have no code, so ERC-1271 does not apply to them. TIP-1020's `SignatureVerifier` precompile adds `verifyConfigurableAccount(account, hash, signature)`. It runs both authorization steps against state at call time, with owners signing `configurable_account_digest(hash, account, version)`. It never writes state or registers an account, and it works under `STATICCALL`.

| Outcome | Result |
|---|---|
| Account mismatch, commitment mismatch, address-derivation failure, or account with code or delegation | Returns `false` |
| Encoding or configuration error | Reverts with `InvalidFormat()` |
| Quorum error | Reverts with `InvalidSignature()` |
| Valid | Returns `true` |

The caller supplies `hash`. The verifier proves only that the current owners approved it. As with `ecrecover`, the application is responsible for domain separation, chain scope and replay protection. The stateless `recover` and `verify` functions do not accept `0x05`.

### Gas

Hashing `n` bytes costs `K(n) = 30 + 6 × ceil(n / 32)`, and `calldata_gas` uses the active calldata schedule. Checking a configurable-account signature costs:

```text
V = calldata_gas(rlp(account) || rlp(config))
  + configuration_proof_cost
  + K(96)
  + Σ approval_cost
```

- **`configuration_proof_cost`** is `K(75 + 21 × owner_count)` for a registered account. For an unregistered account it is `K(68 + 21 × owner_count)` for the address plus `K(75 + 21 × owner_count)` for the commitment. The fixed lengths include the 36-, 34- and 33-byte domain strings, and each owner adds 21 bytes.
- **`approval_cost`** is 3,000 for secp256k1 and 8,000 for P256 or WebAuthn. WebAuthn also pays its existing data calldata charge.
- A transaction adds `V − 3,000` to intrinsic gas. Ordinary intrinsic gas already includes one 3,000 base signature, so it is subtracted exactly once.
- Reading the commitment of an already loaded account costs nothing extra. Direct authorization adds no separate precompile storage read and no keychain processing charge.
- **Registration** adds 20,000 per account, charged once per account across all roles. If registration creates the account (zero nonce, zero balance, no code), it also adds TIP-1000's new-account cost, including the state-gas part.
  - The sender skips that cost only when another TIP-1000 charge already pays for creating it.
  - With `nonce_key == 0`, the `nonce == 0` charge creates it.
  - With a 2D or expiring nonce, a first-call `CREATE` from an account with nonce zero creates it.
  - A 2D-nonce `nonce == 0` charge pays for the new nonce-key slot, not the account, so it doesn't count.
- **An owner update's write** costs 5,000. Commitment writes neither use nor create TIP-1060 storage credits, have no clearing refund, and carry no extra storage-slot charge.
- **`verifyConfigurableAccount`** charges precompile input and account-access costs plus `V`, without the 3,000 subtraction or any registration cost.

Intrinsic gas and fee affordability are computed before any signature is checked. Invalid transactions pay no fees, so the eight-signature cap limits the unpaid work each one can cause.

For example, eight P256 approvals cost 64,000 gas for signature checks alone, or 67,000 with a secp256k1 fee payer. Configuration hashing, calldata and WebAuthn data come on top. A transaction that also grants and uses an access key under TIP-1111 can carry two quorums and a fee payer: 16 × 8,000 + 3,000 = 131,000 gas.

### Supported contexts

From T14, a configurable-account signature is accepted in three places:

- **As a transaction's outer signature.** The account is `tx.from`, `tx.origin` and the top-level `msg.sender`. The quorum authorises every call in the batch, and existing nonce, fee-token and sponsorship rules apply.
- **Inside access-key signatures and access-key grants**, under TIP-1111.
- **In `verifyConfigurableAccount`.**

It is rejected everywhere else:

- **Fee payers.** A separate fee payer still signs with secp256k1. Sponsoring gives it no authority over the account. A configurable account can pay its own fees or be sponsored, but it can't sponsor others.
- **Authorization lists.** An EIP-7702 or Tempo authorization-list entry signed with `0x05`, directly or inside an access-key envelope, makes the transaction invalid. This holds before and after T14. Entries with ordinary signatures keep their existing rules, plus TIP-1113's retirement check.
- **Permits and vouchers.** There is no `0x05` format for TIP-20 `permit` or payment-channel vouchers. A configurable account can fund a channel, but it must name an ordinary `authorizedSigner` for vouchers when opening it. Owner updates don't change that signer.
- **Zones.** Zones keep their own account state and receive no owner updates from Tempo, so accepting these signatures could admit removed owners. Until a later TIP syncs configurations, zones MUST reject `0x05` in every context, configurable access-key parents and delegates, `updateConfig`, and TIP-1113's `upgradeAccount`. Funds sent to a derived address on a zone cannot be moved until then.

The transaction format gains no fields. Transactions without `0x05` signatures are unchanged.

## Interfaces

The configurable-account precompile is at `0xAACC000000000000000000000000000000000000` from T14. TIP-1113 adds `upgradeAccount` to it.

```solidity
interface IConfigurableAccount {
    struct ConfigurableAccountOwner {
        address owner;
        uint8 weight;
    }

    struct ConfigurableAccountConfig {
        bytes32 salt;
        uint64 version;
        uint8 threshold;
        ConfigurableAccountOwner[] owners;
    }

    /// @notice Computes a new account's address from its version-0 configuration.
    /// @dev Charges the address hash.
    /// @return account The derived address.
    /// Reverts with InvalidConfig or InvalidAccount for an invalid configuration or reserved address.
    function deriveAccount(bytes32 salt, uint8 threshold, ConfigurableAccountOwner[] calldata owners)
        external pure returns (address account);

    /// @notice Returns an account's commitment.
    /// @dev Charges normal account access. Zero means the account is not registered.
    function getConfigCommitment(address account) external view returns (bytes32 commitment);

    /// @notice Replaces msg.sender's owners and threshold.
    /// @param current The configuration matching the current commitment.
    /// @param threshold The new threshold.
    /// @param owners The new owners, sorted by address.
    /// Reverts per the Owner updates errors.
    function updateConfig(
        ConfigurableAccountConfig calldata current,
        uint8 threshold,
        ConfigurableAccountOwner[] calldata owners
    ) external;

    event ConfigurableAccountConfigUpdated(
        address indexed account,
        bytes32 salt,
        uint64 version,
        uint8 threshold,
        ConfigurableAccountOwner[] owners
    );

    error InvalidAccount();
    error InvalidConfig();
    error InvalidThreshold();
    error InvalidConfigurableAccountOwner();
    error InvalidWeight();
    error TooManyOwners();
    error DuplicateOwner();
    error InvalidOwnerOrder();
    error UnauthorizedConfigurableAccountCaller();
}
```

Added to TIP-1020's `SignatureVerifier`:

```solidity
/// @notice Returns true if the account's current owners approved `hash`.
/// Reverts with InvalidFormat() or InvalidSignature(); returns false per the verification table.
function verifyConfigurableAccount(address account, bytes32 hash, bytes calldata signature)
    external view returns (bool);
```

`updateConfig` charges ordinary precompile, input and event costs, the two configuration hashes, and the commitment write.

# Compatibility

| Integration | What changes |
|---|---|
| Wallets and SDKs | The chain stores only the commitment, so the wallet must keep the full configuration. Wallets must support collecting approvals independently and combining them in owner-address order. Changing any signed value, including an owner update's version, needs fresh approvals. Before submitting, recheck the commitment, nonce and validity window. Before creating an account or approving an update, check that the owners can actually reach the threshold. |
| Gas estimation | Cost depends on which owners sign and with which key type, so simulation needs the configuration and the planned signers. Simulation applies the same authorization rules and reports the state it used. Observed: open PR 7579 adds request fields for both. |
| Transaction pools | Revalidate pooled transactions when any signer's commitment changes, including on registration and after reorgs. Registration emits no event, so pools must watch state, not events. Observed: open PR 7580 diffs commitments from each block's state changes. |
| TIP-20 approvals | Use a quorum-signed `approve`. There is no configurable-account `permit`. |
| Contracts checking signatures | Call `verifyConfigurableAccount`. Neither `ecrecover` nor ERC-1271 works for these accounts. |
| Payment channels | Name an ordinary `authorizedSigner` at opening. |
| Zones | Don't send funds to configurable accounts on zones until a sync TIP ships. |
| Other chains | Warn users that funds sent to a derived address on another chain are lost. For accounts that need recovery, use TIP-1113's recovery flow. Contracts on Tempo should not treat a message signed for the same address on another chain as approval by the Tempo account. |
| Proof consumers | Decode the optional fifth leaf field. `getConfigCommitment` returns the hash without proof decoding. Historical reads use the encoding active at the requested block. |

# Observability

| Event | Fields | Question it answers |
|---|---|---|
| `ConfigurableAccountConfigUpdated` (MUST be emitted on each owner update) | `account` (indexed), `salt`, `version`, `threshold`, `owners` | What is the account's configuration after this update? |

Registration emits no event. Two things show it happened, and both survive a failed transaction: the configuration inside the first included transaction's signature, and the nonzero commitment in state.

To find the current configuration:

1. Take the configuration from the first transaction's signature, or from `AccountUpgraded` under TIP-1113.
2. Apply each later `ConfigurableAccountConfigUpdated` event.
3. Check the result against `getConfigCommitment` at the chosen block. A later update may have superseded an event.

A failed batch leaves no update events. `verifyConfigurableAccount` leaves no evidence beyond its return value.

# Threat Model

The most consequential attack this design allows is a threshold of colluding or compromised owners taking the account. That includes recovery providers. There is no recovery-only role, so providers whose combined weight reaches the threshold can spend, replace the other owners and manage access keys. Wallets that add recovery providers as owners should explain this to users.

This TIP owns the actors shared across the three TIPs. TIP-1113 and TIP-1111 add their local boundaries.

| Actor | Capability and trust | Boundary check and failure consequence |
|---|---|---|
| Current quorum | Controls all direct actions, owner updates and grants. Trusted to approve only what the owners intend. | [Authorization](#authorization) step 2 at the transaction's position in the block. A compromised quorum can replace the other owners and take the account. |
| Owner below the threshold | Controls only its own approval. Not trusted to act alone. | Weights must reach the threshold. One compromised owner can do nothing alone. |
| Removed owner | Holds old approvals. Not trusted. | The version is in every digest, so old approvals can't be replayed. |
| Wallet | Controls what owners see and holds the full configuration. Trusted to show updates accurately and keep the configuration. | Approvals bind the real calldata, account and version. A misleading wallet gets owners to approve something unintended. Once the account is registered, a lost configuration can be rebuilt from transaction history. Before that, only the wallet has it, and losing it strands the account's funds. |
| Fee payer, relayer | Controls submission and timing. Not trusted with authority. | They can't change the signed operation, account or version, and sponsoring grants no authority. The worst they can do is delay or withhold the transaction. |
| RPC or proof provider | Serves state and proofs. Not trusted for freshness. | Readers verify proofs against a canonical state root they chose. A stale or withheld answer can't prove current ownership. |
| Public submitter | Sends invalid transactions without paying. Not trusted. | Size and signature limits apply before any cryptography. The cost is unpaid verification work, bounded per attempt. |
| Whoever chooses a configuration | Chooses the salt. Trusted not to search for a colliding key. | No check beyond the ~2^80 cost. A successful search gives a key that acts as the account until its first transaction, and in `ecrecover`-only applications afterwards. |

Residual risks:

- An owner set that can no longer reach the threshold locks the account.
- An unregistered account whose configuration is lost can't be used.
- Zones and other chains are outside these checks (see Supported contexts).
- Applications that verify signatures with plain `ecrecover` are outside protocol enforcement.

# Invariants

System invariants for the three TIPs:

1. An account's address never changes: not through creation, registration, owner updates or migration. Derivation is deterministic and chain-independent.
2. Only the current quorum, checked at the transaction's position in the block, authorises direct actions and owner updates. Approvals for an earlier version never become valid again.
3. Once an account has authorised an included transaction, its commitment is nonzero and nothing can clear it.
4. An account with a commitment has no original-key authority on Tempo, except voucher settlement on channels it funded earlier (TIP-1113).
5. Access keys stay within their grants, survive owner updates and migration, and never gain key-management or owner-update power (TIP-1111).
6. Verification work per transaction is bounded before any signature is checked.

Critical test cases for this TIP:

- Registration happens when calls revert or halt, and never for an invalid transaction.
- Registration is visible to the first call, including an owner update in that same call.
- Rolling back an owner update in the registering transaction restores the version-0 hash, not zero.
- The last approval reaches the threshold, and an approval after that is rejected. Limits hold even when the last approval is invalid.
- A threshold above eight works only when eight owners can reach it, including in updates and migration.
- A later transaction in the same block sees the commitment an earlier one left.
- Registration that creates an account charges TIP-1000's new-account cost exactly once, under every nonce type.
- Unregistered accounts keep byte-identical leaves and state roots. Emptying an account never clears its commitment.
- `verifyConfigurableAccount` writes no state, matches its result table exactly, and fails without enough gas.
