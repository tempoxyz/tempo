# TIP-1107: Configurable Accounts (Meta)

## Abstract

Configurable accounts keep the same address when their owners change.

This Meta TIP groups the work into two releases:

- **T12:** new accounts with key rotation, weighted multisig ownership, and access keys.
- **T13:** root-key disablement and migration of existing accounts.

## Motivation

Users should be able to replace keys without moving funds or application permissions.

- A 1-of-1 account gives an individual key rotation.
- A treasury can require several owners to approve transactions and delegate limited spending access.

## Assumptions

- The five T12 components activate together.
- The T13 components build on them and activate together.

## Threat Model

- Derived addresses assume nobody knows their EOA private keys. T13 blocks bare root authority once a configuration hash is stored.
- Cross-chain recovery trusts the initial owners. Rotation on Tempo does not replace them, and losing their signing quorum can make recovery impossible.
- Root-key disablement alone does not provide post-quantum security. That also requires a suitable signing algorithm.

## Open decisions

The component TIPs retain two open review points:

- TIP-1114 proposes a threshold cap of eight.
- TIP-1111 proposes at most sixteen primitive verifications for combined grant-and-use transactions.
- Both bounds need confirmation and worst-case benchmarks.
- TIP-1110 retains the existing recovery contracts while a smaller proxy design is reviewed. Changing these contracts can change derived addresses.

## Future work

Nested multisig owners, inactivity recovery, timelocks, and programmable policies are deferred.

Access-key data remains in AccountKeychain. Moving it into the configuration commitment is also deferred.

# Tooling

Wallet changes are defined in the component TIPs. T13 migration builds on T12 access-key support so existing grants remain usable.

# Observability

No additional events. The component TIPs define ownership and access-key events.

# Invariants

- After a configurable account authorizes an included transaction, its account leaf always has a nonzero configuration hash, even if execution fails.
- The release groups activate together: T12 includes rotation and access keys from the start. T13 adds root-key disablement and migration together.
