# TIP-1148: Automatic Validator Fee Payouts

## Abstract

This TIP pays the block beneficiary's accumulated fees in its preferred fee token once at block end. It reuses the existing permissionless `distributeFees` operation, including token compliance and receive-policy behavior. A reverted or halted payout leaves the fees claimable without invalidating the block. Activation requires a coordinated protocol upgrade; no upgrade is scheduled by this draft.

## Motivation

Fee settlement already converts transaction fees into the beneficiary's preferred token and records them in `collectedFees[beneficiary][token]`. Anyone can call `distributeFees(beneficiary, token)`, but the caller cannot choose another recipient. Requiring a separate transaction adds an operational step to move funds to an already selected destination.

This proposal performs that transfer once per block rather than once per transaction. The beneficiary remains the configured fee recipient: the validator administration address and treasury wallet can remain separate, as specified in [TIP-1017](./tip-1017.md). The proposal does not change validator registration, fee-recipient selection, or fee-token preferences.

Automatic payouts increase the number of treasury balance movements and remove an operator's ability to choose a later payout batch. These are accounting and custody integration tradeoffs that require stakeholder review. The existing permissionless claim already allows third parties to trigger distribution.

Alternatives considered:

- **Keep permissionless manual claims.** Preserves the current workflow and lets an operator choose when to submit a claim, although another caller can distribute earlier.
- **Run an offchain claim service.** Requires no consensus change, but depends on transaction submission, funding, and service availability.
- **Pay after every transaction.** Adds repeated transfer processing and makes the proceeds available to later transactions in the same block.
- **Add opt-in payouts, thresholds, or a payout interval.** Offers more batching control, but introduces configuration and additional consensus rules; these are outside this proposal.

The TIP owner is @SuperFluffy. A reference implementation is available separately in [PR #8330](https://github.com/tempoxyz/tempo/pull/8330).

## Assumptions

- All validators agree on the block beneficiary under the existing rules. This TIP uses that address and does not derive a recipient from a proposer key or validator control address.
- Existing transaction fee collection, AMM routing, and refunds continue to run before payout. The amount available is the existing claim ledger, not a new calculation from receipt gas or nominal fees.
- FeeManager custody remains sufficient for pool reserves and outstanding claims. Payout uses the existing claim operation and cannot withdraw pool reserves as fees.
- Token pause state, TIP-403 policies, [TIP-1028](./tip-1028.md) receive policies, virtual-address resolution, and reward accounting remain authoritative. An inability to deliver tokens does not justify bypassing them.
- Every executing node activates the same rule at the agreed fork. An activation mismatch can produce different state roots and invalidate blocks across versions.

# Specification

## Activation and ordering

Before activation, execution MUST retain the existing manual-claim behavior. After activation, the executor MUST attempt one automatic payout for each block, including blocks with no user transactions.

The attempt MUST run after all block transactions, incentive-section gas validation, and any end-of-block committee update. It runs before execution returns the final state used to calculate the block state root. If a preceding required operation fails, normal block-processing failure applies.

This adds one call to the automatic system-call selection in [TIP-1119](./tip-1119.md). Its other ordering and exclusion rules remain unchanged.

The activation upgrade and timestamp are TBD. T14 in the reference implementation is a provisional gate, not an upgrade scheduling decision. Engineering, research, security, and integration review and the TIP-0000 approval process MUST precede rollout.

## Selecting the claim

Let `B` be the block's beneficiary address. Read FeeManager's effective validator-token preference for `B` from the state after the block's transactions. Let `T` be that token, falling back to the existing default fee token when the stored preference is zero.

The executor MUST use the same beneficiary and preference semantics as transaction fee settlement. The existing restriction against the beneficiary changing its validator-token preference within its own block remains in effect.

The amount selected is the entire remaining `collectedFees[B][T]`, including fees accumulated before activation or in earlier failed payout attempts. The executor MUST NOT enumerate other validators or tokens. Balances for another beneficiary or in a previously selected token remain manually claimable; selecting a new token does not migrate those balances.

## System call

Execute the existing FeeManager operation with the following parameters:

| Field | Value |
| --- | --- |
| Caller | `0x0000000000000000000000000000000000000000` |
| Target | `0xfeec000000000000000000000000000000000000` |
| Calldata | ABI-encoded `distributeFees(address validator, address token)` with `validator = B` and `token = T` |
| Native value | Zero |
| Execution gas limit | 250,000,000, matching the existing internal system-call limit |
| Transaction fee | None |

This is an implicit system call, not a signed transaction or a new public ABI entry point. It MUST NOT add a block transaction, consume a user nonce, or charge a fee payer. It MUST NOT contribute to block gas capacity, header gas used, receipt cumulative gas, blob gas used, or execution requests.

## State transitions and failures

The call MUST run in an isolated EVM execution whose returned state is committed only on success:

1. Read `A = collectedFees[B][T]`. If `A` is zero, the claim is a no-op.
2. For a nonzero amount, apply the existing `distributeFees` transition: clear the claim ledger and transfer `A` units of `T` from FeeManager custody to `B` through the ordinary TIP-20 transfer path.
3. Preserve all existing effects of that transfer, including recipient resolution, token rewards, and receive-policy handling. A receive-policy rejection that routes a payment into the existing guard is a successful guarded delivery, not an EVM revert; its custody and recovery accounting MUST remain intact.
4. On success, commit the returned state through the normal database commit path, including state-change hooks used for state-root computation.
5. On an EVM revert or halt, discard the attempt's state changes. In particular, the tentative claim-ledger reset MUST NOT persist. Continue block processing without changing the successful transactions already executed.
6. A database failure, failure to read the preference, or EVM invocation error MUST propagate as a block-processing error. These failures MUST NOT be converted into a successful deferred payout.

A paused token, a TIP-403 rejection, or another ordinary transfer failure therefore cannot prevent block production through this hook. There is no alternate-token or alternate-recipient fallback. A later block with the same beneficiary and selected token retries any remaining claim; permissionless manual claims remain available at all times.

The existing claim path's [TIP-1060](./tip-1060.md) restriction on minting storage credits from clearing protocol-created fee custody MUST remain in force. This TIP introduces no storage fields, changes no AMM pricing or routing rules, and performs no separate ledger migration.

## Receipts and compatibility

The implicit call MUST NOT create a receipt or append its logs to another transaction's receipt. Logs generated inside the call are available to execution tracing where supported, but MUST NOT enter the block's receipt log bloom or `eth_getLogs` results. Existing user transactions, including explicit claims, keep their ordinary receipts and logs.

Transactions within a block observe fee proceeds only from preceding explicit transfers or claims. The automatic payout becomes visible in the final block state and to execution of the next block. Existing claim balances in the selected token may be swept even in an otherwise empty block.

This is a consensus-breaking state-transition change: executing the same block under the old and new rules can produce different token balances, claim balances, and state roots. Historical blocks MUST continue to replay under their original rules.

# Tooling

The public FeeManager ABI, token preferences, validator configuration, and explicit claim tools remain unchanged. Operators MUST retain the ability to query `collectedFees` and manually distribute balances in older tokens or for beneficiaries that no longer produce blocks.

Treasury and custody integrations MUST account for per-block payouts rather than relying on an operator-selected claim schedule. Receipt-only indexers MUST NOT infer that an unchanged claim ledger or an absent transfer event means no payout occurred. They need final block state or execution replay/tracing to reconcile automatic payouts, including guarded deliveries.

Execution, payload building, import, historical replay, and simulation tools that finalize a whole block MUST apply the same activation and ordering rules. Single-transaction simulations MUST NOT append an automatic block-end payout to their transaction result. Test fixtures MUST initialize the policy registry and other precompiles used by the claim path.

# Observability

No new consensus events or receipt types are introduced. For a successful nonzero claim, the existing claim path emits `FeesDistributed(address indexed validator, address indexed token, uint256 amount)` and the ordinary TIP-20 transfer path emits its existing events, including guard-related events where applicable. Their normal field meanings remain unchanged; during an automatic payout these logs are internal to the implicit call and absent from transaction receipts.

Monitoring MUST reconcile final block state or execution replay using the block hash and number, beneficiary, selected token, claim amount before and after the attempt, and resulting custody balances. For ordinary delivery, the selected claim falls to zero and the recipient's balance receives the transfer under existing token semantics. For guarded delivery, monitoring MUST follow the guard's custody and recovery records. For a reverted or halted attempt, the claim and custody balances remain unchanged by that attempt.

A diagnostic trace of a deferred payout should include the block identifier, beneficiary, selected token, and EVM revert or halt reason. An RPC state-read or replay failure is an observability failure, not evidence of a zero or successfully paid claim.

# Threat Model

- **Block proposer.** Can select and order transactions within existing validity rules, but cannot omit the finalization hook on validating nodes, redirect its recipient, or substitute an amount. Token administration transactions may cause a payout to defer; their existing permissions still apply.
- **Validator operator and treasury.** Control their existing administrative and fee-recipient settings. Automatic payout grants no new authority over either wallet and provides no opt-out or batching control.
- **Token issuer and policy administrators.** Retain pause, compliance, and receive-policy authority. Their actions may defer delivery or route funds into the existing guard; they cannot use this hook to bypass transfer restrictions or invalidate otherwise valid blocks with an ordinary transfer revert.
- **Permissionless claim caller.** May distribute an existing claim before finalization, but cannot choose a different destination or obtain a second payment of the same claim.
- **Node and indexer operators.** Must activate consistent rules and distinguish execution failure from delivery deferral. Receipt-only indexing is insufficient to reconstruct these implicit transfers.

The call uses native precompile execution and introduces no user-selected callback target. Its work is bounded by one selected claim and the existing system-call gas limit, not the number of validators or historical fee tokens. Performance of token reward and guard processing remains part of upgrade readiness review.

# Invariants

- Before activation, block state roots, receipts, and fee balances match historical execution.
- After activation, builders and validators make exactly one attempt after transactions and the committee update, including in empty and epoch-boundary blocks.
- Selection uses the configured fee recipient, not the validator control wallet; default and custom token preferences behave identically to existing settlement.
- Successful ordinary delivery pays the selected claim exactly once. A subsequent empty block cannot pay it again.
- A successful guarded delivery clears the claim only while preserving the matching custody and recovery accounting.
- A reverted or halted attempt changes neither the selected claim nor token/reward/guard state; subsequent transactions remain committed and the block remains valid.
- Infrastructure and database errors remain errors, rather than silent payout deferrals.
- Claims for other beneficiaries and other tokens remain unchanged, as do pool reserves except for existing transaction fee settlement.
- Same-token, direct-AMM, and two-hop fee collection preserve existing swap amounts and refunds; payout distributes only the resulting claim amount.
- Explicit claims earlier in the block and fee-token changes between blocks cannot duplicate, erase, or redirect a claim.
- Payout does not mint prohibited storage credits, alter public interfaces, or change transaction receipts, logs, gas accounting, or execution requests.
- Normal state-change hooks receive the successful payout so state-root computation includes it.

## Success criteria and rollout gates

The test suite MUST cover the invariants above, including default/custom tokens, accumulated balances at activation, zero balances, token pauses, rejected policies, guarded and virtual recipients, reward accounting, retries, balance-overflow failures, database errors, and competing explicit claims. Build/import agreement MUST be demonstrated across the activation boundary and an epoch boundary.

Before testnet rollout, measure block-finalization overhead for ordinary, guarded, and failed payouts; complete security review; and verify treasury reconciliation without receipt logs. Engineering, research, security, and accounting/custody stakeholders must review the payout frequency and observability implications through the [TIP-0000](./tip-0000.md) process. Review results, the target upgrade, and the activation schedule remain prerequisites to changing this draft's status.
