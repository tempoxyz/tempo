# TIP-1182: Post-Quantum Signatures Without History Growth

## Abstract

Post-quantum (PQ) signatures are 10–40× larger than the secp256k1 and BLS signatures Tempo stores today. If Tempo kept them in history, signatures would become most of every archival node's disk. This TIP changes what history keeps instead. Nodes drop transaction signatures once a block is final and outside a retention window. A new header field, `bodiesRoot`, commits to signature-less transaction bodies so pruned history can still be authenticated. Consensus finality is stored as hash-based proofs that roll up into one root per epoch. Accounts can also register a commitment to a future PQ key now. The main limitation is that pruned history is authenticated by consensus rather than by each transaction's own signature. A later TIP will choose the PQ transaction signature scheme and the leader-election beacon.

## Motivation

Tempo stores one signature per transaction and one BLS threshold certificate per block. Today both are small. A TIP-20 transfer is 283 B on the wire, of which 65 B is the secp256k1 signature. A finalization certificate is about 96 B no matter how many validators there are.

Replacing them with standardized PQ schemes changes the size of history:

| Item | Today | With PQ signatures kept |
|---|---|---|
| Transfer, signature and public key per transaction | 65 B (secp256k1) | 1,563 B (Falcon-512), 3,732 B (ML-DSA-44), 7,888 B (SLH-DSA-128s) |
| Transfer, Falcon-512 key-recovery mode | n/a | 1,850–1,867 B per transfer, 2.8× the transfer's size today |
| Finality certificate, 100 validators | ~96 B | ~45 KB (67 Falcon-512 signatures), ~162 KB (67 ML-DSA-44) |

These figures are measured or computed from scheme sizes. At sustained load, signatures would make up 72–86% of an archival node's disk, compared with about 10% today. One year of signatures would be 11,000–26,000× the size of the whole balance ledger. Key recovery, compact encodings and storing public keys in state recover at most about 40% of that.

The alternatives were measured and rejected:

- **Keeping PQ signatures on each transaction.** This is the size problem above.
- **One zk proof per block of every transaction signature.** Verifying a Falcon signature costs about 327,000 SP1 cycles. Keeping up with 10k TPS would take an estimated 1,100–3,400 high-end GPUs, and the proofs would still cost 620–850 B per transfer.
- **BLS-style aggregation of PQ signatures.** No standardized PQ scheme aggregates. Lattice threshold schemes come closest, but they still grow with the validator count and produce no VRF output.

A signature is needed to decide whether a transaction may execute. Once a block is final, its certificate already vouches for that decision. This TIP keeps signatures until then and drops them afterwards. Measured on 6,000 mainnet blocks, a plain transfer then needs 61.9 ±0.7 B of history with a compact storage format, compared with 474.7 B on disk today. The consensus history in this TIP measured 3.2 B per view, flat from 4 to 1,000 validators.

## Assumptions

- **Finality implies validity.** A block finalized by a quorum of validators contained only transactions whose signatures verified. A node that accepts a finalized header without re-executing its signatures trusts the quorum. Light clients and state sync already rely on this.
- **Retention window.** Every node keeps signatures for at least `SIGNATURE_RETENTION_BLOCKS` behind the finalized head. Peers that sync from scratch within that window verify signatures. Peers that sync older history authenticate it through `bodiesRoot` and the consensus proofs.
- **Hash-based security.** The PQ consensus proofs rely only on hash functions: leanXMSS signatures, proven in a hash-based proof system (leanVM). Their parameters are not final. This TIP names the proof statements, not the parameter sets.
- **Fixed validator set per roll-up epoch.** A roll-up epoch commits to one validator set. Changing the validator set or a validator key takes effect only at the next roll-up epoch.
- **Standards.** FIPS 206 (FN-DSA) is not yet published. This TIP doesn't depend on it.

# Specification

## Overview

The TIP changes three things, in the order a block moves through its life:

1. **Admission and execution do not change.** Every transaction still carries a full signature, and validators verify it before execution.
2. **The header commits to signature-less bodies.** Each block header adds `bodiesRoot`, a root over the block's transactions encoded without their signature fields. `transactionsRoot` and transaction hashes do not change.
3. **History drops what finality makes redundant.** Once a block is final and older than the retention window, nodes may delete transaction signatures. They keep the signature-less body, the transaction hash and the recovered sender. They authenticate it through `bodiesRoot` and the block's finality proof.

Consensus finality follows the same pattern. Validators sign votes with a hash-based scheme. One proof per view shows a quorum signed. Recursive proofs then combine a whole epoch of views into one root. Nodes verify the per-view proof (or the raw votes) to finalize, and keep only the epoch root.

Accounts can register `pqKeyCommitment`, a 32-byte hash of a future PQ public key, at any time. It has no effect until a later TIP enables PQ transaction signatures.

## Mechanics

### Committing to signature-less bodies

For each transaction, `body(tx)` is its canonical encoding with every signature field omitted. For Tempo Transactions (type `0x76`), that means `signature` and `feePayerSignature`. For legacy, EIP-2930, EIP-1559 and EIP-7702 transactions, it's `v`, `r` and `s`. An EIP-7702 authorization list keeps its entries but drops each entry's signature.

`bodiesRoot` is the ordered Merkle Patricia root of `body(tx)` keyed by transaction index, computed the same way as `transactionsRoot`. The block producer sets it. A validator rejects a block whose `bodiesRoot` doesn't match the transactions it carries.

A pruned node checks a stored body against the header in three steps:

1. Recompute `bodiesRoot` from the stored bodies.
2. Check it equals the header's `bodiesRoot`.
3. Check the header is final under the consensus proofs below.

Receipts don't change. `receiptsRoot` already authenticates them, and a node needs no signatures to recompute it.

### Pruning signatures

A node MAY delete a transaction's signature fields once both of these hold:

- The block is finalized, and the node has verified and stored its finality proof.
- The block is more than `SIGNATURE_RETENTION_BLOCKS` behind the finalized head.

Before deleting them, the node MUST have stored, for each transaction:

- the transaction hash (32 B), so lookup by hash keeps working;
- the recovered sender;
- the fee payer, when one was present;
- the signature-less body.

Signature fields can't be recovered after pruning. RPC methods that return transactions or raw blocks below the horizon return them without signature fields (see [Compatibility](#compatibility)). A node that wants to serve full signed history keeps every signature and is an archival node in the current sense.

### Consensus votes and per-view proofs

Each validator holds a leanXMSS key registered in the validator set for the roll-up epoch. A vote signs the view's digest, which is the same digest Simplex votes sign today.

An aggregator, normally the next leader, collects a quorum of votes. It produces a quorum leaf proof showing:

- at least `q` distinct validators of the epoch's validator set signed the view digest;
- each counted signature verifies under its validator's registered key.

The proof binds the validator-set root, the view digest and `q`. It doesn't carry a per-view signer bitmap.

A view is final once a node verifies either the leaf proof or `q` raw votes. Raw votes keep finality working when proving is slower than the view time. Leaf proofs replace raw votes for anything stored or served.

### Rolling up an epoch

A roll-up epoch is `ROLLUP_EPOCH_VIEWS` consecutive views. Commit nodes each verify up to 16 child proofs. They chain the children's statements into an accumulator:

```
acc' = H(COMMIT_TAG, acc, H(H(statement), digest))
```

With `ROLLUP_EPOCH_VIEWS = 65,536`, the tree has four levels: 4,096, 256, 16 and 1. The epoch root states that every view in the epoch reached quorum under the epoch's validator set, and it commits to the ordered view digests.

While an epoch is in progress, nodes keep the newest level-1 and level-2 commit proofs, and leaf proofs or raw votes for views not yet covered by a commit. Once the epoch root is verified, a node MAY delete the leaf and intermediate commit proofs for that epoch. It keeps:

- the epoch root;
- the epoch's validator-set root and public keys;
- the headers.

A header is authenticated by checking that its digest is in the epoch root's ordered digest commitment.

### Registering a PQ key commitment

An account MAY set `pqKeyCommitment = keccak256("tempo:pq-key:v1" ‖ scheme ‖ pq_public_key)` in its keychain entry. Writing it needs the account's current authority. Setting it again replaces the previous value. The protocol stores the commitment and doesn't interpret it. A later TIP will define how a PQ signature is checked against it, and when classical keys stop being accepted.

## Interfaces

### Header

Add one field to `TempoHeader`, after the fields TIP-1031 added:

```rust
/// Ordered MPT root over the signature-less encodings of the block's transactions.
pub bodies_root: B256,
```

It is RLP-encoded in field order. Blocks before activation omit it.

### Parameters

| Name | Value | Meaning |
|---|---|---|
| `SIGNATURE_RETENTION_BLOCKS` | 64,800 (~9.7 h at 539 ms blocks) | Minimum depth behind the finalized head before signatures may be pruned |
| `ROLLUP_EPOCH_VIEWS` | 65,536 (~9.8 h) | Views per consensus roll-up epoch |
| `COMMIT_FANOUT` | 16 | Child proofs per commit node |

### Certificate statements

| Object | Public statement |
|---|---|
| Quorum leaf | `(validator_set_root, view, view_digest, q)` |
| Commit node | `(validator_set_root, first_view, last_view, acc)` |
| Epoch root | Commit node with `first_view` and `last_view` at the epoch's bounds |

### Keychain

Add `pqKeyCommitment: bytes32` to the account keychain entry, defaulting to zero. A zero value means no commitment.

# Compatibility

| Integration | What changes |
|---|---|
| Block producers and validators | Compute and verify `bodiesRoot`. Sign votes with leanXMSS keys and produce leaf and commit proofs. |
| Full nodes | May prune signatures past the horizon. Sync below the horizon checks bodies against `bodiesRoot` and headers against epoch roots, not signatures. |
| RPC | Below the horizon on pruning nodes, `eth_getTransactionByHash`, `eth_getBlockByNumber` and the raw-transaction and raw-block methods return transactions without signature fields, and `from` comes from the stored sender. Transaction hashes don't change. |
| P2P | Peers serving signed bodies below the horizon must be archival nodes. A pruned body response carries signature-less encodings checked against `bodiesRoot`. |
| Indexers and explorers | Anyone who needs historical signatures must run an archival node or index them before the horizon. |
| Light clients | Verify finality against the epoch root, or against leaf proofs within the current epoch, instead of a BLS certificate. |
| Wallets and accounts | No change until a later TIP enables PQ signatures. Registering `pqKeyCommitment` is optional. |

The compact history format behind the 61.9 B figure stores transactions and receipts in range-coded, chunked records with a shared address table. It's a storage format, not a consensus rule, so each client can adopt it on its own schedule.

# Observability

- Nodes MUST expose the pruning horizon and the oldest block with signatures as metrics.
- Nodes MUST log and count `bodiesRoot` mismatches, rejected leaf proofs and rejected commit proofs, with the view or block number.
- Aggregators MUST expose leaf-proof and commit-proof latency, so operators can see when finality falls back to raw votes.

# Threat Model

| Actor | Controls | Defense | Remaining risk |
|---|---|---|---|
| A quorum of validators | Finality | Assumed honest at the protocol's fault threshold. This is unchanged. | Below the horizon, a malicious quorum could finalize a transaction that was never signed, and a pruned node couldn't detect it. Archival nodes still can. |
| Malicious block producer | Block contents | Validators recompute `bodiesRoot` before voting. | None beyond today's. |
| Malicious peer serving history | Bodies and proofs it sends | Bodies are checked against `bodiesRoot`, and headers against epoch roots. | Withholding: a peer can refuse to serve data, but can't forge it. |
| Aggregator | Leaf and commit proofs | Proofs are checked against the validator-set root, and nodes fall back to raw votes. | Slow proofs delay finality and storage roll-up, not safety. |
| Quantum adversary | Classical keys | Consensus moves to hash-based keys. Accounts can register PQ key commitments. | Accounts stay classical until a follow-up TIP enables PQ signatures. Leader election still uses the BLS threshold VRF until it is replaced. |

# Invariants

- For every block after activation, `bodiesRoot` equals the root of `body(tx)` over its transactions in order. A test MUST cover every transaction type, sponsored transactions and EIP-7702 authorizations.
- Removing signatures never changes a transaction hash, sender, fee payer, receipt or `receiptsRoot`.
- No signature is deleted from a block that is either not final or within `SIGNATURE_RETENTION_BLOCKS` of the finalized head.
- Every stored header after activation is covered by exactly one verified epoch root or, for the current epoch, by a verified commit or leaf proof.
- A leaf proof verifies only if at least `q` distinct members of the epoch's validator set signed the same view digest.
- A validator-set change within a roll-up epoch is rejected.

# Open Questions

- A PQ replacement for the threshold VRF beacon used for leader election.
- The PQ transaction signature scheme, and how a signature is checked against `pqKeyCommitment`.
- Vote-signing and proving costs under Multimmit's ~150 ms views, where a leaf proof doesn't currently fit in the view.
- Final leanXMSS and leanVM parameters.
- Address-table growth over full history rather than a 6,000-block sample.
