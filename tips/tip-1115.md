# TIP-1115: Ordered Fallback Fee Tokens

## Abstract

Replace the pathUSD fee-token fallback with an ordered list of stablecoins.
Select the first token whose balance covers the transaction's maximum gas fee.

## Motivation

Users holding other stablecoins should be able to pay fees by default without
acquiring pathUSD or setting a fee-token preference.

## Assumptions

Listed tokens are deployed USD-denominated TIP-20s.

---

# Specification

## Fallback List

Define `FALLBACK_FEE_TOKENS` as an ordered list of distinct token addresses in
protocol configuration. The initial list is `[pathUSD, OUSD]`, in this order:

1. pathUSD: `0x20c0000000000000000000000000000000000000`.
2. OUSD: `0x20c0000000000000000000006a37da5c996874be`.

Changes to the list take effect through protocol upgrades. The activation
version is TBD.

## Selection

Replace only the final pathUSD fallback. Existing explicit fee-token choices,
preferences, and inference rules retain their precedence; failures under those
rules do not enter the fallback list.

When the fallback is reached, compute the maximum fee in TIP-20 base units:

```text
maxFee = ceil(gasLimit * maxFeePerGas / 10^12)
```

For legacy transactions, use `gasPrice` in place of `maxFeePerGas`.
Using the fee payer's balances before execution:

```text
for token in FALLBACK_FEE_TOKENS:
    if balance(token, feePayer) >= maxFee:
        return token

fail with insufficient funds
```

One token must cover the entire fee. A zero maximum fee selects pathUSD.

Only insufficient balance advances the search. Once a token is selected,
existing pause, policy, access-key, and FeeAMM liquidity checks apply; a failure
does not try another token. Fee collection and refunds use the selected token
under the existing rules. The validator's default fee token remains pathUSD.

## Validation

Pool validation and execution use the same selection rule. Changes to the fee
payer's balance in any examined token require revalidation, including tokens
skipped for insufficient balance. Replay must track these read dependencies.
Before activation, historical execution uses the existing pathUSD fallback.

## Gas Overhead

For a list of `N` tokens, transactions rejected because every candidate has
insufficient balance require `N - 1` additional storage reads. The worst-case
number of storage reads per transaction also increases by `N - 1`, since even a
valid transaction may need to check the entire list.

The gas charged for fee-token selection remains constant regardless of the
number of tokens checked.

# Tooling

This change applies only to transactions that omit `feeToken` and whose fee-payer
address has no stored fee-token preference. Existing fee-token inference rules
still take precedence.

# Observability

Existing receipt `feeToken` and `feePayer` fields identify the payment. No new
events are needed.

# Threat Model

A transfer into an earlier token can change which token pays for a pending
transaction. Users can specify a fee token explicitly to pin that choice.

# Invariants

- `TEMPO-FEE-FALLBACK-PATHUSD-BEFORE-T13`: Before T13, a transaction whose fee token comes from no explicit `feeToken`, `setUserToken` call, stored preference or inference rule pays fees in pathUSD (`DEFAULT_FEE_TOKEN`), whatever its balances.
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_before_t13_remains_path_usd_only`
- `TEMPO-FEE-FALLBACK-KEEPS-EXPLICIT-TOKEN`: A transaction's explicit `feeToken` pays its fees even when the fee payer cannot cover the maximum fee in it, and the fallback list is not consulted.
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_does_not_replace_explicit_token`
- `TEMPO-FEE-FALLBACK-KEEPS-PREFERRED-TOKEN`: A fee payer's stored `userTokens` preference pays its fees even when it cannot cover the maximum fee, and the fallback list is not consulted.
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_does_not_replace_preferred_token`
- `TEMPO-FEE-FALLBACK-KEEPS-INFERRED-TOKEN`: A fee token inferred from the transaction's TIP-20 call pays its fees even when the fee payer cannot cover the maximum fee in it, and the fallback list is not consulted.
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_does_not_replace_inferred_token`
- `TEMPO-FEE-FALLBACK-FIRST-SUFFICIENT`: When the fallback is reached and `maxFee = ceil(gas_limit * max_fee_per_gas / 10^12)` (`gasPrice` for legacy transactions) is non-zero, the fee token is the first of `[pathUSD, OUSD]` (`TempoHardfork::fallback_fee_tokens`) whose `balanceOf(feePayer)` before execution is at least `maxFee`.
  - Since: T13
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_skips_underfunded_token`
- `TEMPO-FEE-FALLBACK-NO-COMBINED-BALANCES`: When the fallback is reached with a non-zero `maxFee` and no single listed token's balance covers it, the transaction is invalid with `InsufficientFeeTokenBalance`, even if the balances together would cover it.
  - Since: T13
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_does_not_combine_balances`
- `TEMPO-FEE-FALLBACK-ZERO-FEE-PATHUSD`: When the fallback is reached with `maxFee == 0`, the fee token is pathUSD and no fallback balance is read.
  - Since: T13
  - Checked by: none
- `TEMPO-FEE-FALLBACK-NO-RETRY`: Only an insufficient balance moves the search to the next listed token: once a token is selected, a failure in its pause, TIP-403 policy, access-key or FeeAMM liquidity checks invalidates the transaction instead of trying another candidate.
  - Since: T13
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_does_not_skip_funded_paused_token`
- `TEMPO-FEE-FALLBACK-TOKEN-PAYS`: The selected fallback token is the token `collect_fee_pre_tx` collects, `collect_fee_post_tx` refunds and swaps, and the receipt reports as `feeToken`.
  - Since: T13
  - Checked by: `crates/node/tests/it/tip_fee_manager.rs::test_tip1115_estimate_and_pay_with_ousd_fallback`
- `TEMPO-FEE-FALLBACK-POOL-MATCHES-EXECUTION`: Transaction pool validation selects the fee token by running the same EVM handler as block execution, with the same `maxFee`, over the pool's latest state.
  - Since: T13
  - Checked by: none
- `TEMPO-FEE-FALLBACK-POOL-REVALIDATES`: The transaction pool re-validates a pending transaction whose fee token came from the fallback list whenever a block moves its fee payer's balance of a listed token, up to and including the cached choice, across the transaction's `fee_token_cost`, and fallback balance changes that cross no such threshold trigger no re-validation.
  - Since: T13
  - Checked by: `crates/node/tests/it/pool.rs::test_fallback_balance_updates_revalidate_only_relevant_crossings`
- `TEMPO-FEE-FALLBACK-REPLAY-RECORDS-AFFORDABILITY`: Fallback selection records one `StorageAction::FeeTokenBalanceCheck(token, slot, balance, maxFee, sufficient)` for each listed token it examines, up to and including the selected one, and no raw `Sload` of those balance slots, so replay depends on affordability rather than exact balances.
  - Since: T13
  - Checked by: `crates/evm/src/evm/tests.rs::test_fee_fallback_records_affordability_instead_of_exact_balances`

The fallback is reached only when the transaction sets no `feeToken`, is not a `setUserToken` call by its own fee payer, the fee payer has no stored preference, and neither TIP-20 nor Stablecoin DEX inference applies.
