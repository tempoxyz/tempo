# TIP-1012: Encrypted Forced Withdrawals for Zones

## Abstract

This TIP lets a Zone account withdraw one token's full balance by submitting an encrypted, root-signed request on L1. The fee payer pays a fixed 0.1-token fee to the portal admin at admission. The Zone state transition function (STF) validates the request and, if it succeeds, creates an ordinary withdrawal with the existing bounce-back recovery path. The mechanism relies on a live sequencer; it is not an exit path for operator failure and gives no bounded-time inclusion guarantee.

## Motivation

A Zone account holder should be able to start a withdrawal from L1 without getting an ordinary Zone transaction included or setting up an allowance. This TIP formalizes the design in [Zones PR #1425](https://github.com/tempoxyz/zones/pull/1425).

Reusing the encrypted deposit envelope hides the account, recipient, and signature at admission, so signature and replay checks move to the Zone. Limiting the request to a full-balance withdrawal keeps the authorized action narrow, and the upfront fee pays for processing regardless of outcome. General forced transactions and partial withdrawals are out of scope.

This TIP builds on the existing [deposit encryption](https://github.com/tempoxyz/zones/blob/main/specs/spec.md#encrypted-deposit-cryptography), [withdrawal processing](https://github.com/tempoxyz/zones/blob/main/specs/spec.md#withdrawal-processing), and [bounce-back](https://github.com/tempoxyz/zones/blob/main/specs/spec.md#withdrawal-failures-and-bounce-back) rules.

## Assumptions

| Assumption | Consequence if violated |
| --- | --- |
| A live sequencer imports checkpoints, processes the inbox, settles batches, and processes withdrawals. | Requests remain pending indefinitely. |
| Settlement enforces correct execution. Today this is a settlement quorum certificate; the L1 `Verifier` is a stub. Production requires an enforcing execution-proof verifier. | Incorrect execution signed by the quorum would be accepted. |
| Historical encryption keys and decryption material remain available. | Admitted requests cannot be processed. |
| The maximum admitted workload fits execution, proving, and settlement limits. | The transition aborts; requests are never skipped. |

# Specification

## Overview

1. **Request on L1:** the client signs and encrypts an authorization; the portal collects the fee and queues the request in the shared deposit inbox.
2. **Process on Zone:** the STF decrypts and authorizes the request, then either debits the full balance into a withdrawal or consumes the entry with no effect on principal.
3. **Prove and settle:** the prover re-executes the same STF, and L1 settlement commits the resulting state and withdrawals.
4. **Deliver on L1:** the existing withdrawal queue pays the recipient, or bounces the principal back to the account.

| Identifier | Meaning |
| --- | --- |
| `(account, nonce)` | Zone replay key, separate from transaction nonces. It has no token component and need not be sequential. |
| `requestId` | Portal-local forced-request ID, starting at 1. |
| `depositNumber` | Position in the shared inbox (deposits, bounce-backs, and forced requests). |
| `fallbackNonce` | Outbox counter value mapped to the debited account, used to route a bounce-back. |

Forced exits are off by default on every portal and must be enabled by the admin (see [Activation](#activation-and-compatibility)). The portal stores no processing result. The replay map lives only in Zone state.

## Step 1: Request on L1

```solidity
uint128 constant FORCED_EXIT_COMPENSATION = 100_000; // 0.1 token
uint64 constant FORCED_EXIT_ADMISSION_WEIGHT = 14;

struct ForcedExitAuthorization {
    address account;
    uint256 zoneChainId;
    address token;
    address recipient;
    uint256 nonce;
    uint64 admitBefore; // exclusive L1 admission deadline, not an execution deadline
}

struct ForcedExit {
    uint64 requestId;
    address token;
    uint256 keyIndex;
    DepositPayload encrypted;
    address feePayer;
    uint64 requestedAtBlock;
    uint64 requestedAtTime;
}

/// @notice Queue an encrypted authorization to withdraw an account's full balance of `token`.
/// @param token Fee token; must equal the signed token on the Zone.
/// @param keyIndex Zone encryption key index, under existing key-validity rules.
/// @param encrypted DepositPayload carrying the encoded authorization and signature.
function requestForcedExit(address token, uint256 keyIndex, DepositPayload calldata encrypted)
    external
    returns (uint64 requestId, uint64 depositNumber);

function forcedExitCount() external view returns (uint64);
function forcedExitRequests(uint64 requestId) external view returns (address token, uint64 depositNumber);
function remainingDepositCapacity() external view returns (uint64); // weighted units, incl. reserve

event ForcedExitRequested(uint64 indexed depositNumber, ForcedExit entry);
event ForcedExitCompensationPending(address indexed admin, address indexed token, uint128 amount);

error InvalidForcedExitCiphertextLength(uint256 actual);
error ForcedExitCompensationRejected();
```

### Authorization

The signing hash is EIP-712 with domain name `TempoZoneForcedExit`, version `"1"`, the L1 chain ID, and the portal as verifying contract, over:

```
ForcedExitAuthorization(address account,uint256 zoneChainId,address token,address recipient,uint256 nonce,uint64 admitBefore)
```

`signature` is a raw [TIP-0001](./tip-0001.md#signature-types) primitive signature of at most 2049 bytes. Keychain/access-key envelopes are not accepted. For P256, the trailing `pre_hash` byte must be exactly `0` or `1`.

### Encryption

Use the existing `DepositPayload` and [encrypted-deposit cryptography](https://github.com/tempoxyz/zones/blob/main/specs/spec.md#onchain-decryption-verification), with empty AAD and this HKDF-SHA256 `info`, a raw concatenation with no padding:

```
"forced-exit-v1" || portal (20) || keyIndex (32, big-endian) || ephemeralPubkeyX (32) || feePayer (20)
```

The salt is the existing `ecies-aes-key`. `feePayer` is `msg.sender`, so a relayed request must be encrypted with the relayer as `feePayer`.

The plaintext is `abi.encode(uint8(1), authorization, signature)`. Its length is 288 bytes plus the signature padded to 32 bytes. That gives 384 bytes for a 65-byte secp256k1 signature and 2368 bytes for a 2049-byte signature, so L1 requires `384 <= ciphertext.length <= 2368` and `ciphertext.length % 32 == 0`.

### Admission

`requestForcedExit` reverts unless all of the following hold:

- Forced exits are activated (`ForcedExitsNotActivated()`).
- No withdrawal processing is in progress (`ReentrantWithdrawal()`), so withdrawal callbacks cannot call it.
- The portal is unpaused, and `msg.sender` passes the existing depositor access check.
- `token` is enabled. `depositsActive` does not apply.
- The ephemeral key point, encryption key, and capacity checks pass, using the existing deposit errors.
- The ciphertext length is within bounds (`InvalidForcedExitCiphertextLength`).

The portal then collects the fee:

1. It checks that TIP-403 permits `msg.sender → portal`; otherwise it reverts with `ForcedExitCompensationRejected()`. This stops a diverted transfer from being paid out of deposit backing.
2. It calls `transferFrom(msg.sender, portal, FORCED_EXIT_COMPENSATION)`, which reverts on failure.
3. It tries to transfer the fee to the current admin. If that fails, admission still succeeds: the fee is credited to `refunds[token][admin]` for `claimRefund`, and the portal emits `ForcedExitCompensationPending`. The admin cannot block forced exits by refusing payment.

Finally, the portal assigns `requestId` and `depositNumber`, stores `forcedExitRequests[requestId]`, appends the entry to the inbox as `DepositType.ForcedExit = 2` with hash `keccak256(abi.encode(DepositType.ForcedExit, entry, previousHash))`, and emits `ForcedExitRequested`.

The fee is never refunded, whatever happens to the request later.

### Capacity

Forced requests share the deposit inbox's outstanding-entry budget of 230 units. A forced request costs 14 units; deposits and bounce-backs cost 1 unit each. Public deposits and forced requests may fill only 210 units, leaving a 20-unit reserve for callback deposits and bounce-backs created during withdrawal processing. At most 15 forced requests can be outstanding at once.

Weight is released only when settlement advances the processed inbox cursor past the entry; the budget does not reset per block. `processWithdrawals` checks its batch size against the same weighted `remainingDepositCapacity()`, so outstanding forced requests also reduce withdrawal throughput.

A payer can therefore fill public capacity with requests that later reject, blocking deposits and forced requests until the next settlement. The fee deters this but does not prevent it.

## Step 2: Process on Zone

Each Tempo advance must process every entry queued at its imported L1 anchor, in order, and the whole advance rolls back on any fatal error. A forced entry is accepted only under the activating fork (T14+) with `forcedExitVersion == 1` at the anchor. Each forced request consumes one `DecryptionData`. The STF reads the historical key by `keyIndex`, verifies the Chaum-Pedersen proof, and decrypts. Unlike an ordinary deposit, an invalid proof here aborts the transition instead of bouncing.

### Checks

Checks run in this order. The first failure determines the result:

1. **Payload:** the GCM tag is valid, the prefix is `1`, and the ABI encoding is canonical (re-encoding reproduces the plaintext exactly).
2. **Authorization:**
   - account and recipient are nonzero;
   - `zoneChainId` and `token` match;
   - `requestedAtTime < admitBefore`;
   - the signature is valid and recovers to `account`.

   There is no ERC-1271 support.
3. **Replay:** `(account, nonce)` has not been consumed. Mark it consumed from this point on.
4. **Balance:** read the account's balance `B` at this point in inbox order, so it includes credits received after admission. If `B > type(uint128).max`, reject. If `B == 0`, the result is `Empty`.
5. **Policy**, checked against the imported L1 anchor where noted:
   1. the token is enabled on L1;
   2. the recipient holds `Role.Account` when access enforcement is on, and is not a `Role.CallbackGateway` when gateway enforcement is on;
   3. the token is not paused on L1;
   4. the token is not paused on the Zone;
   5. TIP-403 (mirrored from L1) permits `account → outbox`;
   6. no receive policy would divert that transfer.
6. **Debit:** transfer `B` from the account to the outbox and burn it, through an inbox-only path that bypasses allowances and keeps TIP-20 hooks. Allocate a fallback nonce mapped to `account`, then enqueue the withdrawal.

Debit, hooks, fallback mapping, and enqueue are atomic. Forced withdrawals pay no withdrawal fee and do not count toward the per-block user withdrawal cap. The account's portal membership, `depositsActive`, and portal pause do not affect execution.

### Withdrawal

The withdrawal uses the existing `Withdrawal` encoding with empty callback data, zero gas limit, zero memo, and an empty encrypted sender. Its sender tag uses the normal formula, with a private request hash in place of the transaction hash:

```solidity
bytes32 privateRequestHash = keccak256(abi.encode(uint8(1), authorization, signature));
bytes32 senderTag = keccak256(abi.encodePacked(account, privateRequestHash, uint64(fallbackNonce)));
```

The outbox emits this Zone-local event, and the block must end with `finalizeWithdrawalBatch`:

```solidity
event ForcedWithdrawalRequested(
    uint64 indexed withdrawalIndex,
    address token,
    bytes32 senderTag,
    address to,
    uint128 amount,
    uint64 fallbackNonce
);
```

### Results

Results are internal to execution; nothing is published on L1.

| Code | Result | Cause | Nonce | Principal |
| --- | --- | --- | --- | --- |
| — | Abort | Bad or missing decryption data or proof, missing witness, malformed outer entry, entry before activation or newer than the anchor, out of gas, unclassified error | Rolled back | Rolled back |
| 1 | `InvalidPayload` | Payload check failed | Unchanged | Unchanged |
| 2 | `InvalidAuthorization` | Authorization check failed | Unchanged | Unchanged |
| 3 | `NonceAlreadyConsumed` | Replay | Unchanged | Unchanged |
| 4 | `BalanceOverflow` | `B > uint128` | Consumed | Unchanged |
| 0 | `Empty` | `B == 0` | Consumed | Unchanged |
| 5 | `PolicyRejected` | Policy check failed, or `ContractPaused`/`PolicyForbids` during the debit | Consumed | Debit attempt rolled back |
| 0 | `Exited` | Success | Consumed | `B` debited, one withdrawal |

Only the policy conditions listed above produce `PolicyRejected`; any other error aborts. A policy rejection still consumes the nonce, so retrying needs a new authorization and another fee.

## Step 3: Prove and settle

The prover re-executes the same STF over the batch, using authenticated L1 and Zone witnesses. For every forced request it covers:

- decryption under the historical key;
- the authorization and replay checks;
- which result applied;
- the exact debit;
- the resulting withdrawal, including its sender tag and fallback mapping.

Because these effects land in the Zone state root and the withdrawal queue, settlement commits to them without any new commitment. A sequencer cannot skip a forced request, change its result, or substitute its withdrawal without producing an invalid batch.

`submitBatch`, the withdrawal queue hash, and the `Withdrawal` encoding are unchanged. Settlement advances `lastProcessedDepositNumber`, which shows that a request was processed, but not its result or its withdrawal.

Today, batches are accepted on a settlement quorum certificate, and the L1 `Verifier` is a stub. Until settlement enforces the prover's output, execution correctness rests on the quorum. Settlement never forces the sequencer to keep running.

## Step 4: Deliver on L1

Forced withdrawals use the existing `processWithdrawals` and bounce-back path unchanged. If delivery fails, the principal bounces back to the account through `fallbackNonce`, or becomes a pending credit if policy blocks the remint. A bounce-back does not restore the authorization nonce.

## Activation and compatibility

Every portal starts with forced exits disabled: `forcedExitVersion` is 0, and `requestForcedExit` reverts with `ForcedExitsNotActivated()`. Enabling them needs both of the following:

- **Zone fork:** nodes and the prover accept forced entries only from T14 onward.
- **Portal switch:** the portal admin key calls `activateForcedExits()`, which sets `forcedExitVersion` to 1 and emits `ForcedExitsActivated(1)`. The switch is one-way; a second call reverts with `ForcedExitsAlreadyActivated()`. Zone execution also requires `forcedExitVersion == 1` at the imported anchor.

```solidity
function forcedExitVersion() external view returns (uint64);
function activateForcedExits() external; // onlyAdmin
event ForcedExitsActivated(uint64 version);
error ForcedExitsNotActivated();
error ForcedExitsAlreadyActivated();
```

The admin must activate only after the fork is live. An entry admitted earlier would be rejected by every Zone node and stall the shared inbox.

Existing deposit types and encodings, `DepositPayload`, `Withdrawal`, and recovery are unchanged. Portal storage is append-only. Changing the fee requires a new signed-domain version.

# Tooling

Forced exits are only usable if client tooling supports them. The protocol needs no wallet changes to keep working, but an account can only use this path through a client that builds the request.

- **xtask (reference CLI):**
  - `forced-withdraw` builds, signs (secp256k1 root key), encrypts, and submits a request. It supports an optional separate fee payer, the recipient, the nonce, the admission deadline, and fee approval.
  - `--wait-for-processing` waits until the request is settled.
- **Wallets and SDKs:**
  - To offer forced exits, a wallet must build the EIP-712 authorization, sign it with the account's root key (not an access key), and encrypt it to the Zone's current key with the actual fee payer bound into the HKDF context.
  - It then approves and pays the 0.1-token fee and submits the request.
  - It should then track the request as described in [Observability](#observability).
  - User flows should explain that the fee is non-refundable, that the balance withdrawn is the balance at processing time, the admission deadline, and that processing depends on a live sequencer.
- **Sequencer, settlement, and backing checks:** must read `ForcedWithdrawalRequested` to rebuild the withdrawal, using its `senderTag` directly. They account for the principal with no fee and count parked compensation as a portal refund liability.

# Observability

### Tracking a forced exit

A user follows a request through these stages:

| Stage | How to observe it |
| --- | --- |
| Admitted | The `requestForcedExit` receipt returns `requestId` and `depositNumber` and emits `ForcedExitRequested`. `forcedExitRequests(requestId)` confirms it later. |
| Processed, proven, and settled | `BatchSubmitted` advances `lastProcessedDepositNumber` to at least `depositNumber`. |
| Result | Through authenticated Zone RPC, the account sees its own TIP-20 `Transfer` of the full balance to the outbox if the request succeeded. If its balance is unchanged, the request was empty or rejected. The rejection reason is not public. |
| Delivered | On L1, `WithdrawalProcessed(to, senderTag, token, amount, …)` pays the recipient. |
| Bounced back | On L1, `WithdrawalBounceBack` is emitted. On the Zone, the account sees a `Mint` back to itself, or the amount is recorded as a pending credit (`WithdrawalBounceBackPending`) to claim later. |

### Events

| Event | Purpose |
| --- | --- |
| `ForcedExitsActivated` | Records when the admin enabled forced exits. |
| `ForcedExitRequested` | Admission. Used for queue reconstruction and wait-time tracking. |
| `ForcedExitCompensationPending` | Parked admin fee, for backing reconciliation. |
| `BatchSubmitted` (existing) | Processed inbox cursor. |
| `ForcedWithdrawalRequested` (Zone-local) | Withdrawal reconstruction and accounting. |
| `WithdrawalProcessed`, `WithdrawalBounceBack`, `WithdrawalBounceBack{Processed,Pending}` (existing) | Delivery and recovery. |

L1 events and public RPC must not expose the decrypted account, nonce, deadline, signature, or private request hash. Private Zone receipts do link the account to the withdrawal, through the adjacent TIP-20 `Transfer`/`Burn` logs, so they must stay access-controlled.

Operators should monitor oldest outstanding request, inbox occupancy, settlement lag, parked compensation, and decryption or capacity failures.

# Threat Model

| Actor | Trust |
| --- | --- |
| Account holder | The root key authorizes the withdrawal. Root-key compromise is out of scope. |
| Fee payer / relayer | Paying grants no withdrawal authority. |
| Sequencer | Trusted for liveness. Cannot alter results if settlement enforces correct execution. |
| Settlement quorum / verifier | Trusted for execution correctness until an enforcing verifier is in place. |
| Portal admin / token issuers | Keep existing pause and policy powers, and can cause `PolicyRejected`. The admin activates the feature and cannot block admission by refusing the fee. |
| Public submitters | Can spam rejected requests to fill capacity until the next settlement. The fee deters but does not prevent this. |

Encryption hides the request from the public. The sequencer and holders of decryption material can read it. L1 delivery reveals recipient and amount; timing and amount correlation remain possible.

# Invariants

1. Only the account's root key can authorize a forced withdrawal, and each `(account, nonce)` is consumed at most once.
2. Every forced entry is processed exactly once, in inbox order. Entries are never skipped; a fatal error aborts the whole transition.
3. A successful debit removes exactly `B` and creates exactly one withdrawal, atomically. Every other result leaves principal unchanged.
4. Principal stays backed through withdrawal, payment, bounce-back, and pending credit, and is paid or recovered at most once.
5. The fee creates no Zone liability. A parked admin fee is a single L1 refund liability.
6. Outstanding admission weight never exceeds 230, public and forced admission never use the 20-unit reserve, and weight is released only by settlement.

Tests must cover every result row and the check order; replay and domain, account, and token binding; deadline boundaries and later credits; fee and debit atomicity; parked admin fees; activation and fork boundaries; capacity exhaustion and release; and single-use delivery and recovery across policy changes and upgrades.
