# TIP-1012: Encrypted Forced Withdrawals for Zones

## Abstract

This TIP lets a Zone account withdraw one token's full balance by submitting an encrypted, root-signed request on L1. The fee payer pays a fixed 0.1-token fee to the portal admin at admission. The Zone state transition function (STF) validates the request and, if it succeeds, creates an ordinary withdrawal with the existing bounce-back recovery path. The mechanism relies on a live sequencer; it is not an exit path for operator failure and gives no bounded-time inclusion guarantee.

## Motivation

A live sequencer can refuse to include a particular account's Zone transactions, leaving that account unable to withdraw. A forced exit lets the account start a full-balance withdrawal from L1 instead: the sequencer must process every inbox entry in order, and the STF, not the sequencer, decides the result. This TIP formalizes the design in [Zones PR #1425](https://github.com/tempoxyz/zones/pull/1425).

Reusing the encrypted deposit envelope hides the account, recipient, and signature at admission, so signature and replay checks move to the Zone. The fee payer is public, so an account that pays its own fee is still linked to the request. Limiting the request to a full-balance withdrawal keeps the authorized action narrow, and the upfront fee pays for processing regardless of outcome. General forced transactions and partial withdrawals are out of scope.

This TIP builds on the existing [deposit encryption](../zones/specs/spec.md#encrypted-deposit-cryptography), [withdrawal processing](../zones/specs/spec.md#withdrawal-processing), and [bounce-back](../zones/specs/spec.md#withdrawal-failures-and-bounce-back) rules.

## Assumptions

| Assumption | Consequence if violated |
| --- | --- |
| A live sequencer imports checkpoints, processes the inbox, settles batches, and processes withdrawals. | Requests remain pending indefinitely. |
| Settlement enforces correct execution. Today this is a settlement quorum certificate; the L1 `Verifier` is a stub. Production requires an enforcing execution-proof verifier. | Incorrect execution signed by the quorum would be accepted. |
| Historical encryption keys and decryption material remain available. | Admitted requests cannot be processed. |
| The maximum admitted workload fits execution, proving, and settlement limits. | The transition aborts; requests are never skipped. |
| The Zone runs T14 rules before its portal activates forced exits. | Requests produce `NotActivated` and their fees are lost. |

# Specification

## Overview

1. **Request on L1:** the client signs and encrypts an authorization; the portal collects the fee and queues the request in the shared deposit inbox.
2. **Process on Zone:** the STF decrypts and authorizes the request, then either debits the full balance into a withdrawal or consumes the entry with no effect on principal.
3. **Prove and settle:** the prover re-executes the same STF, and L1 settlement commits the resulting state and withdrawals.
4. **Deliver on L1:** the existing withdrawal queue pays the recipient, or bounces the principal back to the account.

A *forced exit* (or forced request) is the L1 request, queued in the inbox as a *forced entry*; a *forced withdrawal* is the Zone withdrawal that a successful forced exit creates.

| Identifier | Meaning |
| --- | --- |
| `(account, nonce)` | Zone replay key, separate from transaction nonces. It has no token component and need not be sequential. |
| `requestId` | Portal-local forced-request ID, starting at 1. |
| `depositNumber` | Position in the shared inbox (deposits, bounce-backs, and forced requests). |
| `fallbackNonce` | Outbox counter value mapped to the debited account, used to route a bounce-back. |

Forced exits are off by default on every portal and must be enabled by the admin (see [Activation](#activation-and-compatibility)). The replay map lives only in Zone state.

## Step 1: Request on L1

```solidity
uint128 constant FORCED_EXIT_FEE = 100_000; // 0.1 token
uint64 constant FORCED_EXIT_ADMISSION_WEIGHT = 14;
uint64 constant FORCED_EXIT_DEBIT_GAS = 5_000_000; // Zone-side debit gas bound; see Step 2

struct ForcedExitAuthorization {
    address account;
    uint256 zoneChainId;
    address token;
    address recipient;
    uint256 nonce;
    uint64 admitBefore; // exclusive L1 admission deadline, not an execution deadline
}

struct ForcedExit {
    uint64 requestId;
    address token;
    uint256 keyIndex;
    DepositPayload encrypted;
    address feePayer;
    uint64 requestedAtBlock;
    uint64 requestedAtTime;
}

/// @notice Queue an encrypted authorization to withdraw an account's full balance of `token`.
/// @param token Token to withdraw and to pay the fee in; must equal the signed token on the Zone.
/// @param keyIndex Zone encryption key index, under existing key-validity rules.
/// @param encrypted DepositPayload carrying the encoded authorization and signature.
function requestForcedExit(address token, uint256 keyIndex, DepositPayload calldata encrypted)
    external
    returns (uint64 requestId, uint64 depositNumber);

function forcedExitCount() external view returns (uint64);
function forcedExitRequests(uint64 requestId) external view returns (address token, uint64 depositNumber);
function remainingDepositCapacity() external view returns (uint64); // weighted units, incl. reserve

/// @notice Fees parked for `admin` because the payout at admission failed.
function pendingForcedExitFees(address token, address admin) external view returns (uint128);

/// @notice Claim the caller's parked fees in `token`, paid to the caller.
function claimForcedExitFees(address token) external returns (uint128 amount);

event ForcedExitRequested(uint64 indexed depositNumber, ForcedExit entry);
event ForcedExitFeePending(address indexed admin, address indexed token, uint128 amount);
event ForcedExitFeesClaimed(address indexed admin, address indexed token, uint128 amount);

error InvalidForcedExitCiphertextLength(uint256 actual);
error ForcedExitFeeRejected();
```

### Authorization

The signing hash is EIP-712 with domain name `TempoZoneForcedExit`, version `"1"`, the L1 chain ID, and the portal as verifying contract, over:

```
ForcedExitAuthorization(address account,uint256 zoneChainId,address token,address recipient,uint256 nonce,uint64 admitBefore)
```

`signature` is a raw [TIP-0001](./tip-0001.md#signature-types) primitive signature of at most 2049 bytes. Keychain/access-key envelopes are not accepted. For P256, the trailing `pre_hash` byte must be exactly `0` or `1`.

### Encryption

Use the existing `DepositPayload`, [encrypted-deposit cryptography](../zones/specs/spec.md#encrypted-deposit-cryptography), and [onchain verification](../zones/specs/spec.md#onchain-decryption-verification), with empty AAD and this HKDF-SHA256 `info`, a raw concatenation with no padding:

```
"forced-exit-v1" || portal (20) || keyIndex (32, big-endian) || ephemeralPubkeyX (32) || feePayer (20)
```

The salt is the existing `ecies-aes-key`. `feePayer` is `msg.sender`, so a relayed request must be encrypted with the relayer as `feePayer`.

The plaintext is `abi.encode(uint8(1), authorization, signature)`. Its length is 288 bytes plus the signature padded to 32 bytes. That gives 384 bytes for a 65-byte secp256k1 signature and 2368 bytes for a 2049-byte signature, so L1 requires `384 <= ciphertext.length <= 2368` and `ciphertext.length % 32 == 0`.

### Admission

`requestForcedExit` reverts unless all of the following hold:

- Forced exits are activated (`ForcedExitsNotActivated()`).
- No withdrawal processing is in progress (`ReentrantWithdrawal()`), so withdrawal callbacks cannot call it.
- The portal is unpaused, and `msg.sender` passes the existing depositor access check.
- `token` is enabled. `depositsActive` does not apply.
- The ephemeral key point, encryption key, and capacity checks pass, using the existing deposit errors.
- The ciphertext length is within bounds (`InvalidForcedExitCiphertextLength`).

The portal then collects the fee:

1. It checks that the portal's [TIP-1028](./tip-1028.md) receive policy accepts a direct transfer from `msg.sender`; otherwise it reverts with `ForcedExitFeeRejected()`. This stops a diverted transfer from being paid out of deposit backing. TIP-403 authorization is enforced by `transferFrom` itself.
2. It calls `transferFrom(msg.sender, portal, FORCED_EXIT_FEE)`, which reverts on failure.
3. It tries to transfer the fee to the current admin. It first checks the admin's TIP-1028 receive policy with the portal as sender; a rejection counts as a failed payout, so the fee cannot be redirected to `ReceivePolicyGuard`. If the payout fails, admission still succeeds: the fee is credited to `pendingForcedExitFees[token][admin]`, and the portal emits `ForcedExitFeePending`.

Parked fees are kept apart from the user `refunds` registry. `claimForcedExitFees(token)` zeroes `pendingForcedExitFees[token][msg.sender]`, transfers the amount to `msg.sender` with the same TIP-1028 precheck as `claimRefund`, and emits `ForcedExitFeesClaimed`. If the transfer fails, it reverts with the existing `CallbackRejected()` and the balance is unchanged. Like `claimRefund`, it is not blocked by pause, and a claim with nothing parked transfers zero. Unlike `claimRefund`, it does not require `Role.Account`: the admin is not necessarily an allowed account, and after AccessPolicy abdication it can never become one. Fees stay with the address that was admin at admission, so a former admin can still claim them. Payment goes only to that address, so a TIP-403 block on the admin freezes its parked fees just as it freezes a user's parked refund.

Finally, the portal assigns `requestId` and `depositNumber`, stores `forcedExitRequests[requestId]`, appends the entry to the inbox as `DepositType.ForcedExit = 2` with hash `keccak256(abi.encode(DepositType.ForcedExit, entry, previousHash))`, and emits `ForcedExitRequested`.

The fee is never refunded, whatever happens to the request later.

### Capacity

Forced requests share the deposit inbox's outstanding-entry budget of 230 units. A forced request costs 14 units; deposits and bounce-backs cost 1 unit each. Public deposits and forced requests may fill only 210 units, leaving a 20-unit reserve for callback deposits and bounce-backs created during withdrawal processing. At most 15 forced requests can be outstanding at once.

The portal appends `forcedExitVersion`, `forcedExitCount`, `forcedExitRequests[requestId] = (token, depositNumber)`, a private cursor `lastProcessedForcedExitId`, and `pendingForcedExitFees[token][admin]` after the existing storage. Outstanding weight is `(depositCount − lastProcessedDepositNumber) + (FORCED_EXIT_ADMISSION_WEIGHT − 1) × (forcedExitCount − lastProcessedForcedExitId)`. When settlement advances `lastProcessedDepositNumber` to `n`, the portal advances the cursor past every forced request with `depositNumber ≤ n`, visiting at most 15 records. Admission compares outstanding weight plus the new entry's weight against these limits.

Weight 14 is conservative. Under T14 gas parameters, including the atomic debit attempt, and with 20 bounce-backs and 8 maximum-metadata token enablements, the worst mix is deposit-only (210 deposits), at 195.4M gas in `advanceTempo`. The worst mix with a forced exit (1 exit, 196 deposits) uses 186.6M, and 15 successful maximum-size WebAuthn forced exits use 62.9M. The worst measured successful debit uses about 2.8M gas. Charging every forced exit the full `FORCED_EXIT_DEBIT_GAS` raises the worst forced-exit mix to about 189.1M, still below the deposit-only case. All stay below the 225M target, which leaves a buffer under the 250M system-call gas limit. Tests check the debit bound and the 15-exit budget under T14 gas parameters, so a change that makes the debit more expensive fails before it ships. Proving runs the same STF in a Nitro enclave, so its cost tracks execution gas.

The budget does not reset per block. `processWithdrawals` checks its batch size against the same weighted `remainingDepositCapacity()`, so outstanding forced requests also reduce withdrawal throughput.

Because weight is released only by settlement, a payer can fill public capacity with requests that later reject, until the next settlement (see [Threat Model](#threat-model)).

## Step 2: Process on Zone

Each full `advanceTempo` block must process every entry queued at its imported L1 anchor, in order, and the whole advance rolls back on any fatal error. Each forced entry consumes one `DecryptionData`; a missing one aborts. If the Zone block does not run T14 rules, or `forcedExitVersion != 1` at the anchor, the entry produces `NotActivated` and its `DecryptionData` is not verified. The version check is defensive: admission requires version 1, and the switch is one-way. Otherwise the STF reads the historical key by `keyIndex`, verifies the Chaum-Pedersen proof, and decrypts. Unlike an ordinary deposit, an invalid proof here aborts the transition instead of bouncing.

### Checks

Checks run in this order. The first failure determines the result:

1. **Payload:** the GCM tag is valid, the prefix is `1`, and the ABI encoding is canonical (re-encoding reproduces the plaintext exactly).
2. **Authorization:**
   - account and recipient are nonzero;
   - `zoneChainId` and `token` match;
   - `requestedAtTime < admitBefore`;
   - the signature is at most 2049 bytes, is valid, and recovers to `account`.

   There is no ERC-1271 support.
3. **Replay:** `(account, nonce)` has not been consumed. Mark it consumed from this point on.
4. **Balance:** read the account's balance `B` at this point in inbox order, so it includes credits received after admission. If `B > type(uint128).max`, the result is `BalanceOverflow`. This is defensive: TIP-20 caps supply at `uint128`, so it is unreachable today. If `B == 0`, the result is `Empty`.
5. **Policy**, each check reading the state named:
   1. *(L1 anchor)* the token is enabled. This is defensive: admission requires it, and tokens cannot be disabled;
   2. *(L1 anchor)* the recipient holds `Role.Account` when access enforcement is on, and is not a `Role.CallbackGateway` when gateway enforcement is on;
   3. *(L1 anchor)* the token is not paused on L1;
   4. *(Zone)* the token is not paused on the Zone;
   5. *(Zone, mirrored from L1)* TIP-403 permits `account → outbox`;
   6. *(Zone)* no TIP-1028 receive policy would divert that transfer.
6. **Debit:** transfer `B` from the account to the outbox and burn it, through an inbox-only path that bypasses allowances and keeps TIP-20 hooks. Allocate a fallback nonce mapped to `account`, then enqueue the withdrawal.

A failed check, or an error raised while evaluating one, produces that check's result; only the abort causes under [Results](#results) stop the transition. Conditions that valid state cannot produce, such as the account's balance changing between the balance check and the debit, are internal invariants, and a failure there aborts.

The debit attempt (debit, policy hooks, fallback mapping, and enqueue) is atomic: any error other than an abort cause under [Results](#results), including token errors added later, rolls it back entirely and produces `DebitFailed`. Before the attempt, the advance must have at least `FORCED_EXIT_DEBIT_GAS` (5,000,000) left, or it aborts as exceeding its execution budget. The attempt is metered on the advance's own gas rather than a separate limit, and its gas use is compared with `FORCED_EXIT_DEBIT_GAS` after it ends: an attempt that used more is rolled back as `DebitFailed`, but if it leaves the advance without enough gas to continue, the advance aborts as exceeding its execution budget. Neither happens for valid state: the attempt runs only native code with no user-supplied logic, and tests keep its cost well below the bound (see [Capacity](#capacity)). Forced withdrawals pay no withdrawal fee and do not count toward the per-block user withdrawal cap. The account's portal membership, `depositsActive`, and portal pause do not affect execution.

### Withdrawal

The withdrawal uses the existing `Withdrawal` encoding with empty callback data, zero gas limit, zero memo, and an empty encrypted sender. Its sender tag uses the normal formula, with a private request hash in place of the transaction hash:

```solidity
bytes32 privateRequestHash = keccak256(abi.encode(uint8(1), authorization, signature));
bytes32 senderTag = keccak256(abi.encodePacked(account, privateRequestHash, uint64(fallbackNonce)));
```

The outbox emits this Zone-local event. Forced entries count toward `TempoAdvanced.depositsProcessed`, so the existing post-T13 rule that such a block ends with `finalizeWithdrawalBatch` applies:

```solidity
event ForcedWithdrawalRequested(
    uint64 indexed withdrawalIndex,
    address token,
    bytes32 senderTag,
    address to,
    uint128 amount,
    uint64 fallbackNonce
);
```

### Results

Results are Zone-local; nothing is published on L1.

| Code | Result | Cause | Nonce | Principal |
| --- | --- | --- | --- | --- |
| — | Abort | Bad or missing decryption data or proof, missing witness, malformed outer entry, entry newer than the anchor, internal invariant failure, advance exceeds its execution budget | Rolled back | Rolled back |
| 7 | `NotActivated` | Zone not on T14 rules, or `forcedExitVersion != 1` at the anchor | Unchanged | Unchanged |
| 1 | `InvalidPayload` | Payload check failed | Unchanged | Unchanged |
| 2 | `InvalidAuthorization` | Authorization check failed | Unchanged | Unchanged |
| 3 | `NonceAlreadyConsumed` | Replay | Unchanged | Unchanged |
| 4 | `BalanceOverflow` | `B > uint128` | Consumed | Unchanged |
| 0 | `Empty` | `B == 0` | Consumed | Unchanged |
| 5 | `PolicyRejected` | Policy check failed | Consumed | Unchanged |
| 6 | `DebitFailed` | Debit attempt reverted or used more than `FORCED_EXIT_DEBIT_GAS` | Consumed | Debit attempt rolled back |
| 0 | `Exited` | Success | Consumed | `B` debited, one withdrawal |

Abort is reserved for invalid or missing input supplied by the sequencer (decryption data, proofs, witnesses, the outer entry), for an advance that exceeds its execution budget (which admission weights and the tested debit bound prevent), and for internal invariant failures that valid state cannot trigger. The sequencer can fix these causes and retry. Every other failure, whether it comes from a request or from token state, is deterministic and would fail the same way on every retry, so it produces a terminal result and never stops the inbox. `PolicyRejected` and `DebitFailed` still consume the nonce, so retrying needs a new authorization and another fee.

Once authorization succeeds, the inbox emits a Zone-local event for the result (`NonceAlreadyConsumed`, `BalanceOverflow`, `Empty`, `PolicyRejected`, `DebitFailed`, or `Exited`):

```solidity
event ForcedExitProcessed(
    address indexed account,
    uint64 indexed requestId,
    uint256 nonce,
    uint8 reason,  // code from the table above; Empty and Exited share 0
    uint128 amount // B for Exited (always nonzero), otherwise 0
);
```

`NotActivated`, `InvalidPayload`, and `InvalidAuthorization` emit nothing: the account is unknown or unauthenticated, and an event would let anyone write into an arbitrary account's private log view. Authenticated Zone RPC shows the event only to `account`.

## Step 3: Prove and settle

The prover re-executes the same STF over the batch, using authenticated L1 and Zone witnesses. For every forced request it covers:

- decryption under the historical key;
- the authorization and replay checks;
- which result applied;
- the exact debit;
- the resulting withdrawal, including its sender tag and fallback mapping.

Because these effects land in the Zone state root and the withdrawal queue, settlement commits to them without any new commitment. A sequencer cannot skip a forced request, change its result, or substitute its withdrawal without producing an invalid batch.

`submitBatch`, the withdrawal queue hash, and the `Withdrawal` encoding are unchanged.

## Step 4: Deliver on L1

Forced withdrawals use the existing `processWithdrawals` and bounce-back path unchanged. If delivery fails, the principal bounces back to the account through `fallbackNonce`, or becomes a pending credit if policy blocks the remint. A bounce-back does not restore the authorization nonce.

## Activation and compatibility

Every portal starts with forced exits disabled: `forcedExitVersion` is 0, and `requestForcedExit` reverts with `ForcedExitsNotActivated()`. `requestForcedExit` and `activateForcedExits` exist only in the T14 portal runtime, which L1 installs at its T14 boundary, so every forced entry is admitted at or after L1's T14. The admin calls `activateForcedExits()`, which sets `forcedExitVersion` to 1 and emits `ForcedExitsActivated(1)`. The switch is one-way; a second call reverts with `ForcedExitsAlreadyActivated()`.

```solidity
function forcedExitVersion() external view returns (uint64);
function activateForcedExits() external; // onlyAdmin
event ForcedExitsActivated(uint64 version);
error ForcedExitsNotActivated();
error ForcedExitsAlreadyActivated();
```

A Zone processes a forced entry only if its block runs T14 rules and `forcedExitVersion == 1` at the imported anchor; otherwise the entry produces `NotActivated` (see [Step 2](#step-2-process-on-zone)). A Zone's fork schedule can lag L1's, because an explicit or `null` fork time in Zone genesis is not inherited, so operators must schedule T14 on the Zone before activating its portal. This changes no previously valid Zone block: forced entries cannot exist before L1's T14, and older Zone nodes treat a `ForcedExit` entry as malformed and abort, so no previously valid block contains one.

The admin switch is transitional. A future hard fork, still to be chosen, will activate forced exits on every Zone, whether or not its admin has called `activateForcedExits()`.

Existing deposit types and encodings, `DepositPayload`, `Withdrawal`, and recovery are unchanged. Portal storage is append-only. The fee is a portal constant and is not part of the signed authorization. The fee payer accepts it through the token approval at admission. Changing it requires a new portal runtime at a hard fork.

# Tooling

An account can use forced exits only through a client that builds the request; existing wallets need no changes.

- **xtask (reference CLI):**
  - `forced-withdraw` builds, signs (secp256k1 root key), encrypts, and submits a request. It supports an optional separate fee payer (and warns when the account pays its own fee), the recipient, the nonce, the admission deadline, and fee approval.
  - `--wait-for-processing` waits until the request is settled.
- **Wallets and SDKs:**
  - To offer forced exits, a wallet must build the EIP-712 authorization, sign it with the account's root key (not an access key), and encrypt it to the Zone's current key with the actual fee payer bound into the HKDF context.
  - It then approves and pays the 0.1-token fee and submits the request. Paying from the account's own address publishes `feePayer = account` on L1, so wallets should default to a separate fee payer or warn before self-paying.
  - Anyone holding the signed authorization can submit it until `admitBefore`, and it withdraws the full balance at processing time. Wallets should use a short deadline (minutes to hours) and a fresh nonce, and give a relayer only the ciphertext, never the signed plaintext. They should default to a fresh recipient so delivery is identifiable on L1.
  - It should then track the request as described in [Observability](#observability).
  - User flows should explain that the fee is non-refundable, that the balance withdrawn is the balance at processing time, the admission deadline, and that processing depends on a live sequencer.
- **Sequencer, settlement, and backing checks:** must read `ForcedWithdrawalRequested` to rebuild the withdrawal, using its `senderTag` directly. They account for the principal with no fee and count `pendingForcedExitFees` as a portal fee liability, separate from user refunds. The sequencer must size withdrawal batches from the weighted `remainingDepositCapacity()`, not the entry count (portals without the T14 runtime have no forced requests, so the count is exact there), and keep the existing limit of 20 withdrawals per `processWithdrawals` call.

# Observability

### Tracking a forced exit

A user follows a request through these stages:

| Stage | How to observe it |
| --- | --- |
| Admitted | The `requestForcedExit` receipt returns `requestId` and `depositNumber` and emits `ForcedExitRequested`. `forcedExitRequests(requestId)` confirms it later. |
| Processed, proven, and settled | `BatchSubmitted` advances `lastProcessedDepositNumber` to at least `depositNumber`. |
| Result | Through authenticated Zone RPC, the account sees `ForcedExitProcessed` with the result code and amount. If settlement has passed `depositNumber` and no event appeared, the request was not activated on the Zone, or its payload or authorization was invalid; the nonce was not consumed. Results are not public. |
| Delivered | On L1, `WithdrawalProcessed(to, senderTag, token, amount, …)` pays the recipient. A user who cannot rely on Zone RPC can track delivery on L1 alone by signing with a fresh recipient and filtering `WithdrawalProcessed` by its indexed `to`. |
| Bounced back | On L1, `WithdrawalBounceBack` is emitted. On the Zone, the account sees a `Mint` back to itself, or the amount is recorded as a pending credit (`WithdrawalBounceBackPending`) to claim later. |

### Events

| Event | Purpose |
| --- | --- |
| `ForcedExitsActivated` | Records when the admin enabled forced exits. |
| `ForcedExitRequested` | Admission. Used for queue reconstruction and wait-time tracking. |
| `ForcedExitFeePending` | Parked admin fee, for backing reconciliation. |
| `ForcedExitFeesClaimed` | Parked admin fees claimed, for backing reconciliation. |
| `BatchSubmitted` (existing) | Processed inbox cursor. |
| `ForcedExitProcessed` (Zone-local, account-scoped) | Result and nonce consumption, for the account. |
| `ForcedWithdrawalRequested` (Zone-local) | Withdrawal reconstruction and accounting. |
| `WithdrawalProcessed`, `WithdrawalBounceBack`, `WithdrawalBounceBack{Processed,Pending}` (existing) | Delivery and recovery. |

L1 events and public RPC must not expose the decrypted account, nonce, deadline, signature, or private request hash. Private Zone receipts do link the account to the withdrawal, through `ForcedExitProcessed` and the adjacent TIP-20 `Transfer`/`Burn` logs, so they must stay access-controlled.

Operators should monitor oldest outstanding request, inbox occupancy, settlement lag, parked fees, and decryption or capacity failures.

### Success criteria

- Every admitted forced request is processed in the first full `advanceTempo` block whose anchor includes it, with no transition aborted by a forced entry.
- Each `ForcedWithdrawalRequested` is delivered or bounced back on L1 exactly once, and portal backing reconciles with parked fees counted separately.
- `advanceTempo` gas stays below the 225M target at full admitted capacity.

# Threat Model

| Actor | Trust |
| --- | --- |
| Account holder | The root key authorizes the forced exit. Root-key compromise is out of scope. |
| Fee payer / relayer | Paying grants no withdrawal authority. A relayer holding the signed plaintext can delay or repeat submission until `admitBefore`, but only to the signed recipient, and the nonce executes at most once. |
| Sequencer | Trusted for liveness. Cannot alter results if settlement enforces correct execution. |
| Settlement quorum / verifier | Trusted for execution correctness until an enforcing verifier is in place. |
| Portal admin / token issuers | Keep existing pause and policy powers, and can cause `PolicyRejected` or `DebitFailed`. The admin activates the feature and cannot block admission by refusing the fee. |
| Public submitters | Can spam rejected requests to fill capacity until the next settlement. The fee deters but does not prevent this. |

Encryption hides the request from the public. The sequencer and holders of decryption material can read it. The ciphertext length reveals the signature-size bucket (secp256k1 or P256 versus WebAuthn); this is accepted rather than padding every request to 2368 bytes. L1 delivery reveals recipient and amount; timing and amount correlation remain possible.

# Invariants

1. Only the account's root key can authorize a forced exit, and each `(account, nonce)` is consumed at most once.
2. Every forced entry is processed exactly once, in inbox order. Entries are never skipped; a fatal error aborts the whole transition. Only sequencer-supplied input, exceeding the advance's execution budget, or an internal invariant failure that valid state cannot trigger can abort. No request or token state can, provided the debit attempt stays within `FORCED_EXIT_DEBIT_GAS`; this rests on the tested worst-case bound (see [Capacity](#capacity)), not a runtime limit.
3. A forced exit admitted at L1 block N is processed in the first full `advanceTempo` Zone block (not checkpoint-only) whose imported anchor is at or above N.
4. A successful debit removes exactly `B` and creates exactly one withdrawal, atomically. Every other result leaves principal unchanged.
5. Principal stays backed through withdrawal, payment, bounce-back, and pending credit, and is paid or recovered at most once.
6. The fee creates no Zone liability. A parked admin fee is a single L1 liability to the admin credited at admission, claimable by that address regardless of access policy, and never counted as a user refund.
7. Outstanding admission weight never exceeds 230, public and forced admission never use the 20-unit reserve, and weight is released only by settlement.

Tests must cover every result row and the check order; `ForcedExitProcessed` for every authenticated result and its absence otherwise; replay and domain, account, and token binding; deadline boundaries and later credits; fee and debit atomicity; debit reverts and debits over `FORCED_EXIT_DEBIT_GAS` producing `DebitFailed`; the worst-case debit staying within `FORCED_EXIT_DEBIT_GAS` under T14 gas parameters; parked admin fees, including the admin receive-policy precheck, and their claim, including by an admin without `Role.Account` after AccessPolicy abdication, by a former admin, and a claim that reverts under a TIP-403 block with the balance unchanged; activation and fork boundaries, including `NotActivated` on a Zone whose T14 lags L1's and when `forcedExitVersion != 1` at the anchor; capacity exhaustion and release; and single-use delivery and recovery across policy changes and upgrades.


### Alternatives considered

- **Fixed-size ciphertext.** Padding every request to 2368 bytes would hide the signature type, but adds about 2 KB of calldata to every request. Variable length is kept (see [Threat Model](#threat-model)).
- **A memo only the user can compute.** The memo appears only in `processWithdrawals` calldata, not in an event, so it is hard to find. A fresh recipient, found by filtering `WithdrawalProcessed` by its indexed `to`, gives the same L1-only tracking.
- **A Zone-side cancel or a protocol cap on `admitBefore`.** A censored account could not get a cancel included, and the Zone knows only the admission time, not the signing time, so a cap would not bound how long an authorization stays usable. Wallets use short deadlines instead.
- **Letting the admin sweep parked fees to any address.** This would let an admin blocked under TIP-403 route around the issuer, so parked fees are paid only to the credited admin.
