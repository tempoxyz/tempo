# TIP-1118: Flattened Payment State Access

## Abstract

This TIP reduces dependent state reads for native TIP-20 payments by storing the preferred fee token in the fee payer's account leaf and materializing each token's effective policy IDs and types. It also defines mandatory, metered read groups, including both possible blocked-receipt amount slots, so clients can load independent state together without performing uncharged speculative reads. Authorization decisions and receipt formats remain compatible, while gas costs and access traces change at activation.

## Motivation

A transaction identifies the payment token, sender, and recipient, but does not generally identify its fee token or the policies governing the payment. Today, resolving these can require reading a fee preference, a token's policy binding, a compound policy's component IDs, and the component policies' types before deriving membership slots.

Receive policies add a different dependency: the blocking reason is part of the receipt hash. The guard's amount slot cannot be selected until policy evaluation finishes. Loading both candidate slots removes that dependency only if the protocol actually performs and charges for both loads, including when delivery succeeds and neither amount is used.

Short-circuiting creates similar dependencies elsewhere. This proposal groups the bounded reads needed for policy evaluation, fee routing, and access-key scope validation. It does not require enumerating policy members or changing policy administration.

## Assumptions

- Activation is after TIP-1092 and the T8 removal of payment reward hooks. Earlier blocks retain their original execution and gas rules.
- Simple policy types and a compound policy's three component IDs are immutable. Membership and policy administrators remain mutable. A future change to these invariants must also specify descriptor invalidation or replacement.
- The activation state contains an account fee preference and a flattened descriptor for every applicable legacy entry, as specified under Migration. A lazy fallback cannot satisfy the advertised bound.
- The account encoding must compose with the proposed [TIP-1108 account configuration commitment](https://github.com/tempoxyz/tempo/pull/7510). TIP-1108 is a draft dependency; its eventual encoding must be reconciled before scheduling this TIP.
- The depth analysis concerns logical account/slot reads against a consistent prestate. It does not count internal trie-node traversal, disk-cache misses, proof verification, or execution of arbitrary EVM contracts.

The implementation audit uses Tempo commit [`4a11606398e0a5c472b349e9602e57a81043bef8`](https://github.com/tempoxyz/tempo/tree/4a11606398e0a5c472b349e9602e57a81043bef8). The proposed groups below are changes to that baseline, not descriptions of already deployed behavior.

## Threat Model

- Token administrators may replace a token's policy, and simple-policy administrators may change membership at any time. Execution must use the policy and membership at the operation's position in the block, including earlier successful writes in the same transaction.
- Callers may choose inputs that exercise cold storage, both rejection conditions, zero amounts, repeated calls, and out-of-gas boundaries. Mandatory work must be bounded, charged, and visible to state-access tracking.
- Receivers control their receive policy and recovery authority. Receipt preparation must not create a claim, move funds, or advance a nonce for an allowed delivery.
- Migration tools and off-chain caches are not authorities. A descriptor or fee preference must be authenticated by consensus state; a cache hit must never substitute stale authorization data.

# Specification

## 1. Activation and terminology

The activation fork, called `F` below, is not yet scheduled. All behavior in this TIP is gated on `F`.

A **read round** contains logical account or storage reads whose keys can be derived without the results of other reads in that round. The first round uses transaction inputs, block context, and protocol constants. An **indirection** is a dependency from one round's returned value to a later round's key.

A **mandatory read group** is an ordered list of actual consensus reads. Once execution enters a group, it must perform every listed applicable read before applying the group's state-dependent decision, unless execution halts. A successful read is charged even if its value does not affect the eventual result.

The rules specify observable gas and access behavior, not a requirement to perform physical I/O serially. Implementations may issue reads concurrently if they preserve logical order, warmness, errors, and gas. They must not fetch an unfunded tail of a group on an out-of-gas path. Ordinary validation before entering a group may still reject the operation. Groups do not authorize speculative reads across those earlier failure gates; the depth claim is about address dependencies, not a guarantee of three end-to-end I/O barriers on every execution path.

## 2. Native account fee preference

### State and fee selection

Add `preferred_fee_token: address` to the authenticated native account record. Zero means no stored preference. This is part of the account leaf, not an account storage slot and not a pointer to another object.

When the fee payer's account is loaded, its preference is available from that same logical read. Replace the `FeeManager.user_tokens[feePayer]` lookup with this field. Preserve the existing selection order:

1. An explicit transaction fee token.
2. The existing non-AA, self-paid `setUserToken` special case, which uses the requested token immediately.
3. The fee payer's nonzero native preference.
4. Existing eligible TIP-20-call or DEX-input inference.
5. The protocol default fee token.

The fee payer's preference is used even when the fee payer differs from the transaction sender. Validator preferences remain in `validator_tokens[beneficiary]`.

`FeeManager.setUserToken(address token)` keeps its selector, caller authority, deployed-TIP-20 and USD checks, and `UserTokenSet(address indexed user, address indexed token)` event. It updates the caller's native field. Setting the existing value succeeds without a write or event. Existing preference getters return the native field, with their existing defaulting semantics. They must not consult the legacy mapping after `F`.

Updates are journaled and revert with the enclosing execution. They affect subsequent fee selections, not a fee token already selected for the current transaction. Contract callers continue to set their own preference. Ordinary storage writes, delegation, contract creation, and account clearing cannot overwrite the field.

### Account encoding

Let `base = [nonce, balance, storageRoot, codeHash]` and let `config_hash` denote the TIP-1108 commitment, or zero if that feature is inactive. At `F`, use these canonical RLP forms:

| Configuration hash | Fee preference | Account leaf |
| --- | --- | --- |
| Zero | Zero | `rlp(base)` |
| Nonzero | Zero | `rlp(base ++ [config_hash])` |
| Any | Nonzero | `rlp(base ++ [config_hash, preferred_fee_token])` |

The fifth field is exactly 32 bytes, including when it is zero in the six-field form. The sixth field is exactly 20 bytes and must be nonzero. A five-field leaf with a zero commitment, a six-field leaf with a zero preference, incorrect lengths, and extra fields are noncanonical and must be rejected. A nonzero commitment is valid only when its governing feature is active. Before `F`, retain the previously active leaf decoder.

An account with either nonzero extension field must not be deleted as empty. It counts as nonempty for account-existence gas and `EXTCODEHASH`; an extant code-free account returns the empty-code hash. Account proofs, witnesses, snapshots, history, reorgs, and every database representation must preserve both fields independently.

### Account-field gas and RPC

Reading the preference from an already loaded protocol account has no separate SLOAD charge. Public precompile getters and the setter's account access use the active warm/cold account-access schedule.

The proposed field-write charge is 20,000 regular gas for zero to nonzero and 5,000 regular gas for replacement of a nonzero preference, in addition to account access, token validation, and event costs. An unchanged preference has no write charge. These writes do not consume or mint storage credits and have no clearing refund; this TIP adds no clearing operation. These constants require the account-growth benchmark described under Invariants before scheduling.

Account response objects that expose native extensions add an optional `preferredFeeToken`, encoded as exactly 20 bytes of JSON-RPC `DATA`; omit it for zero. Preserve the existing meaning of the configuration `extension` field. Account proofs contain the complete leaf; proof summary fields remain unchanged. Historical queries use the state and encoding at the requested block.

## 3. Flattened token policy descriptor

### Layout

Append `token_policy_descriptors: mapping(address => uint256)` to TIP-403 storage, at mapping base slot `5` in the current layout. Existing mapping roots and fields must not move.

The descriptor for token `T` is stored at `keccak256(abi.encode(T, uint256(5)))`. Bit numbers below start at the least significant bit:

| Bits | Field |
| --- | --- |
| 0–63 | Sender simple-policy ID |
| 64–127 | Recipient simple-policy ID |
| 128–191 | Mint-recipient simple-policy ID |
| 192–193 | Sender mode |
| 194–195 | Recipient mode |
| 196–197 | Mint-recipient mode |
| 198 | Initialized flag; must be one for an existing token |
| 199–255 | Reserved; must be zero |

Modes are `0 = REJECT_ALL`, `1 = ALLOW_ALL`, `2 = WHITELIST`, and `3 = BLACKLIST`. These are descriptor-specific codes, not a cast of the existing registry enum. Reject-all must have ID `0`; allow-all must have ID `1`; whitelist and blacklist IDs must identify existing simple policies of that type. An all-zero descriptor is missing, not reject-all.

The original top-level policy ID remains in the TIP-1092 binding for `transferPolicyId()`, registry getters, administration, and existing events. Payment authorization loads the descriptor directly by token address; it does not first load that binding.

### Construction and updates

On token creation and every successful policy assignment:

1. Validate the chosen top-level policy using existing authorization and validity rules.
2. For a built-in or simple policy, use that same policy for all three roles.
3. For a compound policy, resolve its sender, recipient, and mint-recipient simple policies and their immutable types.
4. Write the top-level binding and canonical descriptor atomically. A default allow-all token also receives an initialized descriptor.

The assignment path pays for these reads and writes under the active precompile gas and storage-credit rules. Failed validation or an enclosing revert leaves both binding and descriptor unchanged. A later call in the same transaction sees the new descriptor if the assignment succeeded.

Do not cache membership bits or authorization results. Read `policy_set[leafId][subject]` from TIP-403 whenever the mode requires it. A membership update affects every referencing token immediately, without rebuilding descriptors. Administrator changes also require no rebuild. Compound components and simple types remain immutable.

The descriptor replaces policy traversal in native token authorization, including fee collection, transfers, minting, and other token-keyed checks. Generic TIP-403 APIs that receive a policy ID rather than a token retain their existing interfaces and policy traversal; they are outside this optimization.

### Interface

Add the following view to TIP-403:

```solidity
/// @notice Return the canonical flattened transfer-policy descriptor for token.
/// @param token A deployed TIP-20 token address.
/// @return descriptor The initialized word encoded by TIP-1118.
/// @dev Reverts with the same invalid-token error as tokenTransferPolicyId.
///      Existing tokens must have a descriptor after activation. Missing or
///      noncanonical descriptors are invalid consensus state, not allow-all.
function tokenTransferPolicyDescriptor(address token)
    external view returns (uint256 descriptor);
```

An implementation must fail closed on a missing or noncanonical descriptor; it must not silently authorize, synthesize a default, or traverse legacy policy state. Such a failure indicates an invalid activation or implementation, not an ordinary user error.

### Mandatory authorization reads

For each token authorization group, derive all required `(leafId, subject)` pairs from the descriptor and the existing operation's role requirements. Load every non-built-in membership before combining the results. In a transfer, load sender and recipient memberships even if the sender will be rejected. A sender-only fee check does not load recipient or mint memberships; a mint uses only its mint-recipient role.

Preserve the existing always-authorized protocol-address exemptions exactly where they currently apply. Do not extend them to receive policies. Exempt subjects and built-in modes require no dummy membership read because the descriptor and subject already determine the answer.

Order reads by the operation's existing role-check order. Within one group, duplicate physical slots are read and charged once, at their first occurrence. Evaluate the original authorization predicates only after completing the group. With enough gas, authorization results and policy errors are unchanged; low-gas calls may now halt before returning a policy error.

## 4. Mandatory inbound preparation

### Applicability

Every transfer or mint that reaches the TIP-1028 `validate_inbound_or_block` stage performs the following preparation, including zero-amount calls and receivers without an active receive policy. Existing parsing, recipient resolution, reserved-address rejection, pause, token-policy, issuer, allowance, and spending checks that precede this stage remain gates to entry.

This group is for guard-eligible deliveries. Receive-policy views, guard claims, and T12 channel deliveries that reject instead of creating a blocked receipt do not prepare dummy receipts. Their actual policy checks still follow the membership grouping below.

### Configuration and potential destinations

Once the recipient is resolved, perform these reads in order, irrespective of later allow/block decisions:

1. The receiver's packed receive-policy configuration.
2. The receiver's separate recovery-address word, even in originator or receiver mode, or with no active policy.
3. The guard's receipt nonce, without incrementing it.
4. The payment token's balance for the resolved receiver.
5. The payment token's balance for the guard.
6. The TIP-1060 persistent credit word for the payment token.
7. The TIP-1060 persistent credit word for the guard.

These addresses are known without the configuration's contents and can be loaded in one round. Deduplicate equal physical slots within the group. The credit words are included because a later zero-boundary write may need them; receipt creation must not trigger an additional cold read after selecting the receipt amount slot. Transient credit-mode and budget bookkeeping remains transaction-local.

Use the stored third-party recovery address only in third-party mode. Originator mode encodes `address(0)` in the receipt; receiver mode encodes the resolved receiver. With no active receive policy, use originator mode for candidate construction and ignore inactive configuration fields. Loading a word does not validate or adopt an inactive recovery address.

### Policy memberships and receipt candidates

Let `n = max(stored_nonce, 1)`, without writing the nonce. Construct two `ClaimReceiptV1` values that differ only in `blockedReason`:

| Field | Value in both candidates unless stated otherwise |
| --- | --- |
| `version` | `1` |
| `token` | Payment token |
| `recoveryAuthority` | Recovery value selected as above |
| `originator` | The existing logical originator for this delivery |
| `recipient` | The literal virtual alias, if any, otherwise the resolved receiver |
| `blockedAt` | Block timestamp converted to `uint64` using existing saturation rules |
| `blockedNonce` | `n` |
| `blockedReason` | `TOKEN_FILTER = 1` or `RECEIVE_POLICY = 2` |
| `kind` | `TRANSFER = 0` or `MINT = 1` |
| `memo` | Existing memo, or zero for a call without one |

The guard continues to store only an amount per receipt hash, not the receipt body:

```text
receiptHash(reason) = keccak256(abi.encode(ClaimReceiptV1(reason)))
amountSlot(reason)  = keccak256(abi.encode(receiptHash(reason), uint256(1)))
```

Here `1` is the existing `ReceivePolicyGuard.balances` mapping base slot. The receipt ABI is ten static words, or 320 bytes. Its format and hash remain unchanged.

Perform this second group in order:

1. If a receive policy is active and its token filter is non-built-in, load `policy_set[tokenFilterId][token]`.
2. If a receive policy is active and its sender policy is non-built-in, load `policy_set[senderPolicyId][originator]`, even if the token filter rejects.
3. Hash the token-filter receipt and load `amountSlot(TOKEN_FILTER)` in the guard.
4. Hash the receive-policy receipt and load `amountSlot(RECEIVE_POLICY)` in the guard.

All applicable keys can be derived from the preceding round. Both amount loads are mandatory even if neither policy rejects, no receive policy exists, the amount is zero, or only one rejection reason is possible. A client cache or an optional access-list entry does not replace these metered operations. Membership duplicates are read once within this group; both receipt operations remain mandatory.

Pure receive-policy validation also loads both applicable memberships before selecting its result. It need not read a recovery address when no receipt or recovery result can be produced.

### Selection and writes

After preparation, preserve the existing decision order: no active receive policy permits delivery; otherwise token-filter rejection takes precedence over sender-policy rejection. If both pass, deliver normally. If both reject, create only the token-filter receipt.

Allowed delivery does not increment the guard nonce, write either receipt amount, credit the guard, or emit `TransferBlocked`. Unused candidate balances, credit words, and recovery data have no business effect.

For a blocked delivery, preserve the existing transfer/mint-to-guard behavior, then advance the nonce once with checked `n + 1`, write the selected receipt's amount, and emit the existing events. The unselected amount slot is not written. Preserve existing zero-amount blocked-delivery behavior. A saturated receipt nonce must not reject an allowed delivery merely because candidates were prepared; overflow matters only when committing a blocked receipt.

Use the journal's current values for balance updates and SSTORE accounting. Reuse the prepared receipt hash and selected amount read; do not add a redundant SLOAD merely to choose the slot. Existing balance-delta and storage-credit operations keep their ordinary charges, including any warm reads they perform. A preloaded balance is not permission to overwrite intervening journal changes.

All writes and logs roll back under existing call and transaction rules. Receipt preparation must not expose a callback or other reentrant operation between nonce preparation and blocked-receipt commitment.

## 5. Other mandatory read groups

The following audit distinguishes bounded reads that must move ahead of a decision from reads whose keys genuinely require earlier state.

### Fee AMM routing

For unequal user and validator fee tokens, load the user's `quoteToken` even when a direct route has sufficient liquidity. Once that value is known, load the direct pool and both fallback pools before selecting a route. Load the second fallback pool even if the first is insufficient or the direct route wins.

If the quote token is zero or equals the validator token, omit fallback pool reads: those cases are known from the quote value and do not define a distinct valid fallback. Preserve the invariant that a token cannot quote itself. Equal user and validator tokens retain the same-token path without these pool or quote reads.

Logical order is quote-token read, direct-pool read, first-fallback-pool read, second-fallback-pool read. The direct pool can physically be fetched alongside the quote token because its key is already known. Preserve direct-route priority, output arithmetic, liquidity requirements, and selected-route-only reservation and settlement. Do not fail a valid direct route because an unused fallback is insufficient or its unused amount arithmetic would overflow.

Protocol fee hooks currently use externally charged storage rather than the ordinary call gas meter. Add a route-preparation charge of `3 * C` once per included transaction with unequal user and validator fee tokens, where `C = warm_storage_read_cost + cold_storage_additional_cost` for the active fork. This conservative charge covers the quote and at most two fallback pool reads, including routes that use fewer of them. The existing charge for the direct route remains. The surcharge is regular gas, is included in required initial gas after fee-token resolution and before fee deduction, and is included in final charged gas even if user execution reverts. Reject a transaction whose gas limit cannot cover the resulting initial gas. Simulations that skip liquidity validation must still report this charge.

Every actual route read must still update the journal and state-access recorder. Do not additionally deduct the same preparation reads from the user-call gas meter or add another surcharge during settlement. This fixed protocol charge is deliberately distinct from the exact warm/cold metering of ordinary precompile read groups.

### Access-key call scopes

For a non-root access key and a top-level CALL, group the following point reads before evaluating scope flags or set membership:

1. Key scope's `is_scoped` flag.
2. Target's membership position in the target set.
3. Target's selector-set length.
4. Selector's membership position, if calldata has at least four bytes.
5. That selector's recipient-set length, if the selector is available.
6. First ABI word's recipient membership position, if calldata has at least 36 bytes and the word is a canonical address.

All keys are derivable from the account, access-key ID, target, and calldata; no set enumeration is required. Perform syntactically applicable reads even for an unrestricted key or target. Then apply the existing coarse-to-fine authorization rules and malformed-input handling. In particular, unrestricted targets may still allow calldata that would be invalid for a recipient-constrained selector.

Charge these reads through the existing metered scope-prevalidation path, including reads whose values are ignored. Root-key calls do not create dummy scope reads. The corresponding scope-view APIs need not adopt this group.

### Reads that do not require a new unconditional rule

| Area | Reason |
| --- | --- |
| Expiring nonce eviction | Ring pointer, ring entry, and the old hash's seen entry already form at most three rounds. Omit the old seen entry when the returned hash is zero; its address is only needed after that round. |
| Periodic spending limits | The current payment path reads the complete two-word limit state before period arithmetic. Both word addresses follow from account, key ID, and token; no policy-outcome-derived pointer remains. |
| Root-key spending bypass | The absence of an access key is known from transaction authorization, so no dummy key or limit reads are needed. |
| Mint/burn role checks | Required role constants and subjects identify membership slots directly. Administrative role-parent traversal is outside the payment operation set. |
| Channel payer/reserve choice | The descriptor is supplied in calldata, and the channel's sender-selection flag can be read with receive configuration. The selected membership address is therefore available for the next round without loading both sender candidates. |
| Post-T8 rewards | Payment reward hooks are disabled. Do not load old reward-delegate state. |
| Public guard claims | Receipt bytes are supplied by the caller, so their amount slot is directly derivable. Do not manufacture alternative-reason claims. |

This list is not an instruction to prefetch every syntactically imaginable branch. Additional optional prefetching beyond these groups is an implementation choice and is not promised to be charged or covered by the bound.

## 6. Metering, caches, and state-access recording

For ordinary precompile groups, each actual SLOAD costs the active warm-read cost plus the cold surcharge when applicable. Charge both receipt hashes using the existing metered Keccak helper: each 320-byte receipt costs `30 + 6 * 10 = 90` gas. Mapping-key derivation retains the existing precompile convention; this TIP does not add a separate opcode-style Keccak charge for every mapping index.

Warmness follows logical execution, including the active rollback rules. Reads may reduce a subsequent write's cold surcharge, but do not remove its static, state-creation, storage-credit, or refund accounting. Loading an empty candidate creates no storage and earns no storage credit. Do not apply SSTORE accounting to unused candidates.

Mandatory loads must appear in execution witnesses and storage-action tracking as reads, even when their returned values are discarded. Preserve existing specialized balance-delta and fee-liquidity actions as appropriate, while also recording the new mandatory reads. No implementation may replace mandatory reads with an unmetered database prefetch, suppress their charge because of a cache hit, or charge only the selected receipt slot.

Duplicate suppression applies only within the explicitly specified group. A later group or operation performs its own logical reads and pays the resulting warm or cold costs. An internal cached value is usable only while it agrees with the current journal. Earlier writes, reverts, block changes, and reorgs must invalidate or version caches and derived access plans.

## 7. Migration and compatibility

Before processing the first transaction under `F`, consensus state must satisfy:

- Every legacy nonzero `user_tokens[A]` is represented by the same `A.preferred_fee_token`; every other account has a zero preference unless explicitly initialized in genesis.
- Every deployed TIP-20 token has an initialized descriptor matching its effective policy immediately before activation. Resolve TIP-1092's binding-or-legacy rule during migration, not during payment execution.
- Existing registered top-level bindings remain unchanged. For unregistered tokens, install the effective top-level binding with the descriptor. Consequently, the registry getter reports these tokens as registered after activation.

Legacy preference and token-local policy slots remain frozen historical data; they are neither consulted nor maintained after activation. Retaining them avoids granting storage credits for a protocol-directed deletion. Existing public APIs continue to return effective current values. TIP-1092's permissionless migration API becomes a no-op for already registered tokens, as they all are after a successful migration.

The migration is a deterministic fork transition, outside user gas, with no user events or storage-credit minting. Nodes may prepare it in advance, but must apply all intervening preference, policy-assignment, and token-creation changes through the activation parent. Replay across the fork and rollback must reproduce the same roots.

**Required deployment decision:** the per-network migration artifact, complete source-key inventory, derivation program, activation-parent binding, and resulting state-root checks are not yet specified. These are scheduling gates, not permission to use an incomplete snapshot or a lazy runtime fallback. Completeness must be checked against canonical source state, including genesis and system-created entries; event indexing alone is insufficient. TIP-1092 records more than fifteen million testnet tokens, so eager descriptor materialization needs explicit storage, runtime, and rollout measurements. If eager migration is impractical, this TIP must be revised to define a transition period and a weaker depth claim before approval.

The account-leaf change requires upgraded node databases, proof readers, witness tooling, and account RPC consumers. Existing signed transactions keep their encoding, but estimates and gas-sensitive behavior change. Historical receipts remain claimable with their original bytes and reason-bound hashes.

## 8. Depth and scope of the result

For one guard-eligible payment against its current prestate, the longest relevant address-dependency chains are:

| Round 1 | Round 2 | Round 3 |
| --- | --- | --- |
| Fee payer account, validator preference | Fee-token descriptor | Sender-policy membership |
| Fee payer account, validator preference | Fee-token quote and direct pool | Both fallback pools |
| Virtual-address master mapping | Receive configuration and recovery word; nonce and destination preparation no later than this round | Receive memberships and both receipt amount slots |
| Expiring-nonce ring pointer | Ring entry | Seen entry for the old hash |

Independent chains overlap. A directly addressed recipient eliminates the virtual-resolution step. Token balances, allowances, pause flags, fixed roles, and required bookkeeping reads can be placed alongside the round in which their subjects become known. Access-key scope point reads form one group after the key identity is known.

Thus the target is at most **three logical read rounds, or two state-to-state indirections**, for the described payment and fee paths after complete migration. This is a bound on deriving and loading the relevant state, not a promise that execution has no sequential arithmetic, validation, or writes. Early rejection and insufficient gas may stop before all rounds.

Do not generalize this into three global passes for every TIP-1045-classified transaction. Multi-call batches may observe earlier writes. In particular, the guard nonce advances only for actual blocked deliveries, so a later call's candidate nonce depends on earlier outcomes. Preparing only two reason variants does not enumerate all possible batch nonce offsets. Implementations must plan against the updated journal per call, or separately specify and pay for a larger candidate set. This TIP does not introduce that larger set or change nonce allocation.

Generic EVM execution, token administration, policy creation, guard recovery callbacks, and legacy reward paths have no new depth guarantee. Channel operations preserve their current delivery semantics; this TIP does not force unused channel deliveries or enumerate all batch outcomes merely to claim a uniform transaction-wide bound.

## 9. Alternatives considered

- Adding the top-level policy ID to transaction payloads does not resolve mutable token assignments or the remaining compound/type reads without further witnesses and validation.
- Caching compound expansions only off-chain does not authenticate the token's selected policy and cannot define mandatory, metered state access across implementations.
- Removing the blocking reason from the receipt hash would change receipt authentication and recovery-consumer assumptions. Loading both existing keys preserves the format.
- Charging only the chosen receipt while speculatively loading both leaves the extra state work outside protocol metering. This TIP requires both actual loads.
- Incrementing the receipt nonce on every attempted delivery would simplify batch planning but changes nonce and event behavior and adds writes to allowed payments. It is not adopted.
- Reading only branch-selected state can use less gas, but preserves decision-dependent waits. The mandatory groups trade additional reads for a shallower schedule.

# Tooling

- Publish canonical storage-layout fixtures and descriptor encode/decode helpers, including built-ins and duplicate role IDs.
- Extend account codecs, proofs, RPC models, and database migrations with the native fee preference while preserving configuration commitments.
- Update simulation and estimation to execute the mandatory groups and include the protocol routing surcharge. Report both receipt slots even on successful delivery.
- State planners must report the block/prestate and fork used, distinguish addresses from values, and invalidate plans after relevant writes. Batch planning must account for actual receipt-nonce progression.
- Provide reproducible migration tooling and completeness checks before scheduling. Operators need measured disk growth, runtime, catch-up behavior, and rollback procedures for each network.

# Observability

No new business events are required. Preserve `UserTokenSet`, `TransferPolicyUpdate`, token transfer/mint events, and the complete existing `TransferBlocked` event. An allowed delivery must not emit a blocked-receipt event merely because its candidate slots were loaded.

Expose mandatory reads through existing access traces and witness tools, including owner address, slot, returned value, and charge. Fee-routing diagnostics must distinguish pools that were read from the route selected for reservation and settlement. Instrument descriptor-missing failures and migration-completeness failures as implementation/state-integrity faults.

# Invariants

1. **Policy equivalence:** for every role, descriptor evaluation equals canonical policy traversal. Cover simple/compound policies, all built-ins, duplicate leaves, exemptions, both rejecting sides, reassignment, membership edits, and same-transaction visibility.
2. **Descriptor integrity:** bit packing is canonical, all reserved bits are zero, reject-all differs from missing state, construction is atomic, and membership updates need no descriptor writes. Payment traces contain no legacy binding-to-compound-to-type traversal.
3. **Fee preference integrity:** preserve selection priority and sponsorship behavior. Cover zero preferences, unchanged setters, the immediate-use special case, contract callers, reverts, independent configuration updates, empty-account handling, proofs, snapshots, and reorgs.
4. **Mandatory inbound matrix:** cover no policy, both allow, only token rejection, only sender rejection, and both reject, across all recovery modes, direct/virtual recipients, transfer/mint, memo/no memo, and zero/nonzero amounts. Both amount reads, recovery/nonce reads, both destination balances, and credit-word reads occur whenever the group completes.
5. **Receipt equivalence:** selected receipt bytes, hash, amount, recovery semantics, events, and successful claim behavior match the existing format. Only a blocked delivery advances the nonce and writes one amount; test nonce zero, maximum nonce, repeated allowed calls, and multiple blocked calls in a batch.
6. **Gas and warmness:** test every warm/cold combination of the two amount slots, repeated groups, duplicate memberships, and gas exhaustion at each preparation step. Verify actual gas deductions, state gas, credit mint/spend behavior, refunds, rollback, and no uncharged tail fetch. Include sender rejection before recipient selection and no-policy success.
7. **Fee routes:** test same-token, direct, both fallback legs, invalid fallback, each insufficient leg, and unused fallback arithmetic overflow. Verify mandatory quote/both-leg reads, direct priority, unchanged reservations, recorded dependencies, and exactly one `3*C` surcharge when tokens differ, including execution revert and insufficient initial gas.
8. **Access scopes:** test unrestricted, deny-all, unconstrained targets/selectors, every missing membership, short calldata, noncanonical address words, duplicate calls, and inline key authorization. Verify only bounded point reads and the existing acceptance rules, with the new gas charges.
9. **Migration:** compare every migrated value with canonical source state; exercise registered and legacy-only tokens, genesis/system entries, activation-boundary updates, rollback, and historical replay. No supported post-activation payment uses a lazy fallback.
10. **Measured success:** compare baseline and proposed cold-state traces and latency for ordinary payments, virtual recipients with third-party recovery, blocked payments, access keys, and two-hop fees. Demonstrate the three-round per-payment dependency graph; separately report batch counter dependencies, read-count/gas increases, descriptor storage growth, migration cost, and account-field creation cost. These measurements are required before scheduling, and no performance result is claimed by this draft.
