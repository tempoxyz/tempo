# TIP-1071: Token Name Updates

## Abstract

Adds `setName(string)` to TIP-20 tokens so the token admin can update the name returned by `name()`. The update emits `NameUpdated`. The symbol, currency, decimals, and token address are unchanged.

## Motivation

A TIP-20 token's name is written once by `TIP20Factory.createToken` and cannot change afterwards. TIP-20 tokens are precompiles, so an issuer cannot upgrade or redeploy the token at the same address to correct it. A name that is wrong, outdated, or no longer matches the issuer's branding stays onchain permanently, and every wallet, explorer, and indexer that reads `name()` shows it.

For example, OUSD (`0x20c0000000000000000000006a37DA5C996874BE`) was created with the name `OpenUSD` while the asset is branded `Open USD`. The only workarounds today are per-app display overrides, which make apps disagree with the chain and with each other, or deploying a new token at a new address, which fragments balances, liquidity, and integrations.

TIP-1026 made `logoURI` admin-mutable metadata. This TIP applies the same model to `name`.

### Alternatives Considered

- **Offchain overrides in token lists and apps.** Each integrator has to adopt the override, and anything reading the chain still shows the old name.
- **Redeploying the token.** This creates a new address and requires migrating balances, liquidity, and integrations.
- **Also allowing symbol updates.** Symbols are used as tickers and trading identifiers, so changing them carries more impersonation and integration risk. This TIP leaves `symbol` immutable; symbol updates can be proposed separately.

## Assumptions

- The `DEFAULT_ADMIN_ROLE` holder is the party entitled to set the token's metadata, as with `setLogoURI` and `setSupplyCap`.
- Integrators read `name()` from the chain or react to `NameUpdated`, rather than treating the `TokenCreated` event as the permanent name.
- EIP-712 signers do not rely on the domain name staying fixed for an unsigned period. Permits signed against the old name no longer verify after an update (see [Permit Domain](#permit-domain)).

## Threat Model

- **Token admin:** trusted to set the token's metadata. A compromised or malicious admin can rename the token to impersonate another asset. The same admin can already change transfer policy, pause the token, and set `logoURI`, so this adds no new trust. Integrators still rely on offchain curation for trust, as in TIP-1026.
- **Non-admin callers:** untrusted. They MUST NOT be able to change the name.
- **Permit signers and relayers:** a rename changes the EIP-712 domain separator. An admin can therefore invalidate outstanding permits by renaming the token. This does not let anyone spend funds without a valid signature.

# Specification

## Interface

The following function is added to `ITIP20`:

```solidity
/// @notice Sets the token name (requires DEFAULT_ADMIN_ROLE).
/// @param newName The new token name.
/// @dev Reverts with Unauthorized if the caller does not hold DEFAULT_ADMIN_ROLE.
///      Changes the EIP-712 domain separator, invalidating permits signed
///      against the previous name.
function setName(string calldata newName) external;
```

## Events

```solidity
/// @notice Emitted when the token name is updated.
/// @param updater The account that performed the update.
/// @param newName The new token name.
event NameUpdated(address indexed updater, string newName);
```

## Behavior

- `setName(string)` is restricted to `DEFAULT_ADMIN_ROLE` and reverts with `Unauthorized` for any other caller.
- On success it stores `newName`, so `name()` returns `newName`, and it emits `NameUpdated(msg.sender, newName)`.
- `newName` has the same validation as the `name` argument of `createToken`, which is currently none. Setting the current name again is allowed and emits the event.
- `setName` works while the token is paused, like other admin metadata functions.
- `symbol()`, `currency()`, `decimals()`, `logoURI()`, balances, allowances, roles, and the token address are unchanged.
- The `TokenCreated` event and the `createToken` selectors are unchanged.

### Permit Domain

The TIP-20 EIP-712 domain separator is computed from the current name on each call:

```
keccak256(abi.encode(EIP712_DOMAIN_TYPEHASH, keccak256(bytes(name())), keccak256("1"), chainId, address(this)))
```

After `setName`, `DOMAIN_SEPARATOR()` returns the value for the new name. Permits signed against the previous name revert with `InvalidSignature`. Permit nonces are unchanged. Signers MUST read `DOMAIN_SEPARATOR()` or `name()` from the chain when signing and MUST NOT cache the domain separator.

## Activation

`setName` is gated behind the activating hardfork. Before activation, calls to the `setName` selector revert with `UnknownFunctionSelector`.

# Tooling

- SDKs and ABIs (`tempo-std` `ITIP20`, viem/wagmi Tempo actions) add `setName` and `NameUpdated`.
- Wallets, explorers, and indexers that cache token names SHOULD refresh on `NameUpdated`, or re-read `name()` periodically.
- Permit tooling MUST compute the domain from the current onchain name.

# Observability

- `NameUpdated(address indexed updater, string newName)` is emitted from the token address on every successful update. It records which admin renamed which token, what the new name is, and when the change happened.

# Invariants

1. **Admin-only mutation.** `setName` MUST revert with `Unauthorized` for any caller without `DEFAULT_ADMIN_ROLE`. No other function changes `name()` after creation.
2. **Scoped mutation.** A successful `setName` changes only `name()` and the name-derived domain separator. `symbol()`, `currency()`, `decimals()`, `logoURI()`, `totalSupply()`, balances, allowances, nonces, and roles are unchanged.
3. **Event emission.** Every successful `setName` emits exactly one `NameUpdated` with `updater = msg.sender` and `newName` equal to the stored name.
4. **Domain consistency.** `DOMAIN_SEPARATOR()` always equals the separator computed from the current `name()`.
5. **Activation gating.** Before the activating hardfork, the `setName` selector reverts with `UnknownFunctionSelector` and the name cannot change.
6. **Backwards compatibility.** The `createToken` selectors and the `TokenCreated` event signature are unchanged.
